03 · Architecture options to research

Compare these paths in the first HTML artifact

Option A — Microsoft Bot Framework + Azure Bot Service

Best for: production Teams bot with supported auth, tenant controls, app catalog deployment, and Teams-native experiences.

  • Teams user sends message to bot.
  • Bot service calls a Hermes API/gateway endpoint.
  • Hermes profile performs retrieval over approved ACMA knowledge pack.
  • Bot returns answer with citations and manifest link.

Option B — Teams app + messaging extension

Best for: structured search/query UX where users want to find project facts, reports, citations, or generated answer cards.

  • Users invoke search/action command in Teams.
  • Extension queries retrieval service or Hermes-backed search.
  • Results returned as cards with links to HTML artifacts.

Option C — Graph/webhook bridge to Hermes

Best for: internal proof-of-concept or controlled channel integration, if org permits subscriptions/webhooks.

  • Message event or webhook forwards text to Hermes.
  • Hermes processes question with constrained tools.
  • Response delivered through Graph, webhook, or configured Teams delivery.

Option D — Incoming webhook / workflow-only POC

Best for: delivery-only notifications or posting generated HTML/report links. Not sufficient as an interactive Q&A bot unless paired with a separate input channel.

  • Use only for low-risk review notifications or status updates.
  • Do not use for broad private-content Q&A without identity-aware authorization.
Recommended research hypothesis: use Option A for production and Option C only for a narrow POC if Teams app approval is slow. Validate this against actual tenant policies before committing.
03A · Teams/Azure/security gates

Concrete approval checklist before any live POC

Teams admin center checks

  • Custom app upload / sideloading policy for pilot users.
  • Org-wide app settings and app permission policies for custom apps and bots.
  • App setup policy or targeted pilot-user installation path.
  • Bot scopes allowed: 1:1 only for first pilot unless Teams admin approves private channel/team scope.
  • Teams app manifest review: valid domains, bot commands, webApplicationInfo, privacy/terms URLs, tenant restrictions.

Azure / Graph least privilege

  • Single-tenant Azure app registration unless admins explicitly approve otherwise.
  • Default Graph posture: no Graph message-read scopes for the Bot Framework POC. Use Bot Framework activity payloads for inbound bot messages instead of tenant-wide message access.
  • Allowed by default: OpenID/profile/sign-in scopes required for Teams/Bot auth; app-specific bot credentials; Graph read scopes only for identity/group checks if admin-approved.
  • Conditionally allowed: User.Read, GroupMember.Read.All, or equivalent group-membership validation only when needed for authorization and admin-approved.
  • Prohibited unless separately approved: channel/chat/message read application scopes such as broad ChannelMessage.Read.All, Chat.Read.All, Channel.ReadBasic.All, mailbox/file scopes, or any tenant-wide content-read permission.
  • Admin consent evidence must be captured with approver, timestamp, app ID, and exact approved scopes.
  • Prefer managed identity or certificate credentials; if client secret is used, require expiry, rotation owner, and approved secret store.

Authorization and data leakage controls

  • Map Teams identity to content authorization before retrieval: Azure AD group, Teams membership, repo collaborator mapping, or explicit allowlist.
  • Default pilot surface: 1:1 bot or restricted private Team/channel; block broad/public channel responses until approved.
  • Classify answer before posting and include citations; refuse if source is outside user entitlement.
  • Account for Teams retention, eDiscovery, forwarding, screenshots, and channel membership drift.

Hermes execution boundary

  • Dedicated locked-down Hermes profile with only approved read/retrieval and Teams response tools.
  • No write access to raw data or repo during answer generation; no external posting except approved Teams response path.
  • Disable persistent memory of private/client content unless explicitly approved.
  • Prompt-injection tests must cover malicious repo text, data exfiltration, citation spoofing, and overbroad retrieval.
Approval artifact required: no POC starts until named owners are recorded for Teams admin, Azure app registration, security/privacy review, repo/data ownership, hosting/network, secrets rotation, and rollback execution.
03B · Logging and credential policy

Hard controls before any bot runtime exists

Logging policy

  • Default: do not persist full prompts, full answers, retrieved private snippets, repo file contents, access tokens, or raw Teams message bodies.
  • Allowed logs: request ID, timestamp, hashed/pseudonymous Teams user ID, authorization decision, source IDs/citation IDs, artifact path, high-level status, and error category.
  • Retention must be explicitly set before POC; default target is short retention for pilot diagnostics only.
  • Access to logs must be limited to named operators; logs must not be sent to third-party analytics or external LLM traces without approval.
  • Client/private content in logs is treated as an incident unless deliberately captured in an approved evidence artifact.

Repo credential policy

  • Preferred: prebuilt, approved knowledge pack generated from a pinned repo commit; bot runtime reads the pack, not the full repository.
  • If runtime repo access is needed, use a read-only deploy key or fine-grained token restricted to vamseeachanta/llm-wiki-acma; avoid broad personal access tokens.
  • Credentials must live only in an approved secret store or platform secret facility, never in HTML artifacts, repo files, Hermes memory, logs, or prompts.
  • Define rotation cadence, secret owner, revocation command/path, emergency disable procedure, and audit evidence before pilot.
  • Hermes tools must be configured so token values and private snippets cannot be echoed into Teams or persisted to unapproved logs.
04 · Step-by-step plan

Plan before implementation

Confirm scope and artifact inventory

  • Create reports/teams-bot/issue-2/ or equivalent local staging path for HTML artifacts if approved.
  • Define artifact names: teams-bot-research.html, teams-permissions-checklist.html, poc-architecture.html, poc-validation-report.html.
  • Record issue URL, repo URL, and privacy classification in each artifact header.

Map available knowledge and data residency

  • Inventory sources/, pages/, projects/, reports/, and ledgers.
  • Classify which content is eligible for bot retrieval: private repo curated pages, report manifests, citation JSON, HTML reports, and approved extracted derivatives.
  • Explicitly exclude raw project data unless a separate permission gate approves it.

Design retrieval and answer provenance contract

  • Define an answer schema: question, answer, source citations, confidence, private/public classification, retrieved files, manifest path, follow-up suggestions, refusal/escalation notes, and user authorization basis.
  • Reuse the report-layer manifest model from reports/B1528/issue-2760/.
  • Specify how generated answer HTML should cite evidence and expose links for review.

Research Teams/Azure integration choices

  • Compare Bot Framework, Teams app + messaging extension, Graph/webhook bridge, and incoming webhook/workflow-only POC. Also research existing Hermes Gateway/Teams/Graph support, profile configuration, skills/tools, memory posture, retrieval/indexing options, and locked-down toolset design.
  • For each option, document hosting, auth, tenant admin requirements, Graph permissions, operational complexity, auditability, and data-leakage risk.
  • Generate the comparison as a single HTML decision matrix.

Review organization Teams settings and permission path

  • Check whether custom Teams apps are allowed, whether sideloading is disabled/enabled, and whether org app catalog publishing is available.
  • Check app permission policies, app setup policies, bot installation policies, and whether external/custom apps require admin approval.
  • Identify Azure app registration owner, Graph permission approver, Teams admin owner, repo/content owner, and hosting/network owner.

Draft the POC architecture

  • Recommended default: Teams Bot Framework bot → Hermes API/gateway endpoint → dedicated Hermes profile → read-only retrieval over approved ACMA knowledge pack → cited Teams answer.
  • Define secrets: bot app ID/secret, tenant ID, Graph credentials if needed, Hermes provider key, repo token/read-only deploy key.
  • Define rollback: uninstall Teams app, disable bot endpoint, revoke app secret, remove Graph subscription, disable Hermes profile/cron/webhook.

Plan POC tests and validation

  • Use 5–10 representative oil and gas / ACMA project questions.
  • Validate answer grounding: every factual claim links to a repo source or says insufficient evidence.
  • Validate access controls: unauthorized Teams users cannot retrieve private content.
  • Validate HTML artifacts render locally and include manifest/provenance sections.

Run adversarial review before implementation

  • Review the plan against security, privacy, Teams policy, and repo evidence standards.
  • Mark plan as status:plan-review.
  • Proceed to implementation only after user approval changes status to status:plan-approved.

07 · Risks and open questions

Review before approval

Risks

  • Tenant policy risk: Teams custom app or bot installation may be restricted by admin policy.
  • Graph permission risk: Graph application permissions may require admin consent and security review.
  • Data leakage risk: private ACMA content must not be returned to unauthorized Teams users or public channels.
  • Grounding risk: oil and gas answers can be technically consequential; bot must cite sources and refuse when evidence is weak.
  • Operational risk: endpoint hosting, secrets rotation, logs, and incident response need an owner.

Open questions

  • Who owns Teams admin approval for custom apps/bots?
  • Which Teams channel or group should pilot the bot?
  • Should bot access be limited to repo collaborators, an Azure AD group, or a Teams team?
  • What hosting target is acceptable: Azure App Service, container, internal VM, or existing Hermes gateway host?
  • Should the POC use only existing repo artifacts, or may it build a retrieval index from approved local derivatives?
Hard gate: do not implement a live bot or expose private repo content to Teams until the permissions checklist and user approval are complete.
