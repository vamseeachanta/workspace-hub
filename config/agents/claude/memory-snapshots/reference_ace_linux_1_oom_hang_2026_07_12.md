**Incident:** ace-linux-1 hung ~06:08 on 2026-07-12; user power-cycled. NOT the GPU/GDM pattern (that's ace-linux-2).

**Root cause chain:**
1. Box idles at ~80% swap used (32 GB RAM + 8 GB swap; Chrome + Immich + VS Code + Claude sessions) — little headroom.
2. 05:40–05:50: one `claude.exe` (Claude Code CLI; process comm is literally `claude.exe` on Linux) ballooned to **17.6 GB anon RSS in <10 min**, at session wrap-up (share-recap.sh / skill-analysis Stop-hook phase of two /mnt/local-analysis sessions).
3. Swap hit 100%, page cache evicted to ~0 → thrash livelock. Kernel OOM killed the process at 05:47 but box never recovered; second claude.exe stuck in D-state (likely NTFS-FUSE [[ntfs-fuse-git-stalls-local-analysis]]); journald flushing 1 line per ~40 s; journal ends mid-call-trace.

**Why no guardrail fired:** systemd-oomd was active but `oomctl` shows **"Swap Monitored CGroups:" EMPTY** — Ubuntu default arms only ManagedOOMMemoryPressure on user@.service (50%/20s), never ManagedOOMSwap. Swap-exhaustion path has NO userspace killer by default. oomd logged zero kills in 12 days incl. the incident.

**Diagnosis recipe (worked well):** `journalctl --list-boots` → `journalctl -b -1 -p err` + `-k` grep oom → sar (`/var/log/sysstat/saNN`, `sar -r`/`-S -f`) for the ramp timeline → `find ~/.claude/projects -newermt` to ID the session. Stretched kernel-log timestamps (~40 s/line) = starvation signature, not instant panic.

**Fix applied/recommended:** install `earlyoom` (poll-based, robust under livelock) and disable systemd-oomd to avoid double killers; or arm oomd swap kills via drop-in `ManagedOOMSwap=kill` on `-.slice`. User installed earlyoom 2026-07-12 (active-state confirmation pending).
