**Mechanism (verified, load-bearing):**
- **YAML at `.claude/memory/kanban/` is SoT** (git-tracked); `~/.hermes/kanban.db` is replayed FROM it by `scripts/load.py`. Edit YAML, never SQLite.
- **CRITICAL CORRECTION (was wrong in v1):** the `*/20` cron `.github/workflows/kanban-reconcile.yml:75` does `git reset --hard origin` → regenerates every `cards:` block from live GitHub labels → commits only `boards/`. So **the `cards:` list is a pure derived view; the ONLY durable lever for card placement is the GitHub `domain:` label.** Hand-editing a board YAML's cards is clobbered within 20 min. Migration is **LABEL-FIRST**, not YAML-edit-first.
- Two tiers: **scaffolding** (board headers, `manifest.yaml`, `domains.yaml`, `routing-rules.yaml`, `SCHEMA.yaml`) survives `reset --hard` once committed; **placement** (`cards:`) never does.
- Assignment = first `domain:<name>` label + `manifest.yaml` `(repo,domain)→board` in `reconcile.py:284 target_board()` — **repo-bound**; `issue_key()`:267 = `gh:<repo>#<n>`. **Cross-repo routing is IMPOSSIBLE via labels/YAML** (CRITICAL finding). `reconcile.py` only READS labels (no write path); `route.py labels_for():328` only ADDS `domain:` when none exists, never removes.
- **Adding a board = 4-file scaffolding** (board YAML + manifest+children + domains.yaml + **routing-rules.yaml** if it needs non-default machine/provider) + a **bulk-relabel** of issues. New domains otherwise lose machine dispatch (`routing-rules.yaml:70` exact-matches `domain: solver`/`hydro`).

**4 user decisions (locked 2026-05-30):** (1) ecosystem/cross-repo → **`gh issue transfer`** (real issue moves, separate batch, trips per-repo `--allow-shrink`, per-card judgment); (2) survey un-analyzed boards → **done**; (3) domain×project (client wikis) → **own Phase-3 issue** (full-stack: schema+manifest+loader+dispatch+`client-wikis.yml`+slug, NOT reconcile-only); (4) routing matcher → **prefix/glob** (`domain: hydro*` inherits rule).

**GATE RESULT (2026-05-30, probe done, comment 4584273312): board-scoped = the lossy case.** Hermes kanban is **one SQLite DB PER BOARD** at `~/.hermes/kanban/boards/<slug>/kanban.db` (NOT a single `~/.hermes/kanban.db` with a board column — corrects the old assumption); each board has its own DB+workspaces+dispatcher; NO board-move CLI (`reassign`=profile-scoped). So a label-driven move RE-CREATES the card on the destination (new id, NO comments, NO links) and STRANDS the original as an orphan on the source; `load.py` is additive-only (never prunes) and imports NO GitHub comments and replays NO links. Durable annotation surface for a GH-mirror card = the **GitHub issue itself** (GH comments persist); Hermes runtime comments/links are ephemeral local worker state. Migration options: A=preserving-move (relabel.py reads/recreates/re-emits, most code), B=clean board-DB rebuild (`boards rm --delete` + re-run load.py, loses runtime-only state), C=GitHub-durable policy + B (lossless of consequence) — **recommended C, awaiting user A/B/C decision** (changes relabel.py scope). Probe cleaned up (test boards hard-deleted).
