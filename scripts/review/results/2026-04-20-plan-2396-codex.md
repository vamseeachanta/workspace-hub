### Verdict: MAJOR

### Summary
The plan contains multiple correctness-critical claims that are unverified on the face of the document, and it also appears to violate the repo's documented hard gate by proposing implementation before Codex/Gemini adversarial review artifacts are complete. Dominant defects are dependency/status assertions without proof, incomplete acceptance-test mapping, and unresolved operating-model / cross-machine / security details.

### Issues Found
- [P1] Unverified resource-intel claims: the plan asserts concrete repo findings such as `Found: .claude/mcp-servers/`, `Found: scripts/orchestrator/hermes/`, `Found: scripts/data/document-index/`, and `Distinct sources consulted: 10`, but provides no file-level evidence, issue status evidence, or concrete findings per source. This fails the mandatory Resource Intelligence Summary verification requirement.
- [P1] Hard-gate violation in review status: the header says `Status: plan-review`, but `Adversarial Review Summary` shows `Codex | PENDING` and `Gemini | PENDING` while also listing `Review artifacts: scripts/review/results/2026-04-20-plan-2396-claude.md | ...-codex.md | ...-gemini.md`. That is internally inconsistent and does not affirmatively prove the required review artifacts exist before approval.
- [P1] Dependency correctness is unverified for cited issues: `Related issue #1804`, `Related issue #2393`, `Related issue #2395`, and `Issue: https://github.com/vamseeachanta/workspace-hub/issues/2396` are treated as live dependencies/context, but the plan does not show current issue status, labels, or whether those issues exist in the cited states. This violates the explicit dependency correctness check.
- [P1] The deliverable expands beyond the issue title without justification: issue title is `MCP server exposing doc_key lookup, wiki search, registry query`, but `Deliverable` and `Pseudocode` add `coverage_status` and `cfr_lookup` plus multi-agent registrations, audit logging, and allowlist work. That is scope creep unless the issue body explicitly authorizes it.
- [P1] TDD coverage is incomplete against acceptance criteria. `Acceptance Criteria` includes `Server invocable from Gemini CLI (smoke test manually)`, `Server invocable from Hermes bridge (integration test)`, `Review artifacts posted`, and Claude registration via `claude mcp list`, but `TDD Test List` has no Gemini registration/config test, no Claude registration/config test, no test for review-artifact posting, and no explicit Hermes bridge test matching that criterion.
- [P1] The plan introduces a durability/logging design without verifying operating-model compliance. It cites `Operating model §7` but never proves that `logs/mcp/doc-intel/queries-YYYY-MM-DD.jsonl` is an allowed storage tier, whether logs are git-tracked metadata vs local cache vs shared mount, or whether daily JSONL logs under `logs/` violate the cross-machine tier rules it claims to respect.
- [P1] `doc_key` compliance is unproven. The mandatory review check requires `sha256:` namespace and avoidance of path-only identity, yet the plan never states that `doc_key_lookup` accepts or returns `sha256:` keys, and `wiki_search` returns `[{doc_key, path, excerpt, similarity}]` without specifying `sha256:` identity semantics. This is a correctness-critical omission.
- [P1] Ownership-model compliance is unverified. The plan cites `Operating model §7` only and never addresses the mandatory §2 ownership constraint forbidding invented `between-layer` / `L<n>-adjacent` classes. `wiki_search` explicitly filters `layer="L3"` and discusses surfacing `L2 summaries`, but no section verifies that these layers match the current operating model taxonomy or avoid forbidden new classifications.
- [P1] Flow-rule compliance is unverified. The plan proposes `log_query(name, args, caller)` on every tool call and persistent audit logs, but never verifies §4 flow rules, especially whether the server may emit or persist L3/L5-derived content into durable logs or create circular flows via `Hermes bridge` + logs + registry reads.
- [P1] Artifact paths are speculative and in some cases admitted as unknown. `Artifact Map` lists `.gemini/mcp-servers.yaml (or equivalent config file)`, which is not a concrete path. The mandatory check requires cited file paths to exist or be explicit `Create` actions; `or equivalent config file` is an unresolved placeholder, not an executable plan.
- [P1] Security model is incomplete for a path-sensitive server. The plan claims `read-only`, `allowlist`, and `deny secrets/, .env, .claude/state/`, but does not address path traversal, symlink escape, mount boundary crossing, log injection via arguments, secret leakage through excerpts, or untrusted caller metadata. For code touching paths/mounts/logs, the threat model is missing.
- [P2] `Standards: Not applicable.` conflicts with later citations to `Operating model §7` and MCP spec. If operating-model rules and MCP protocol rules constrain design, standards are applicable; the section is misleading and suggests incomplete resource accounting.
- [P2] `Memory feedback_codex_needs_pushed_artifact.md + feedback_codex_sandbox_write_blocked.md — Codex can't read local FS` is an unverified and overly broad capability claim used to justify architecture. No evidence is shown, and it may be false or stale relative to current tool capabilities.
- [P2] The plan claims `Gap: no internal MCP server for doc-intel; each agent reimplements lookup logic` without evidence. No search results, code citations, or examples of duplicated logic are provided, so the core problem statement remains unverified.
- [P2] `test_read_only_no_writes | static check | grep for write methods = 0` is not a robust test for the acceptance criterion `read-only`. A grep-based heuristic will miss writes performed through imported helpers, logging code, shell calls, or non-obvious APIs; it also conflicts with the plan's own requirement to write audit logs.
- [P2] `test_perf_doc_key_lookup_p95` asserts a performance budget but no acceptance criterion states the exact threshold except the note `matches issue-body performance budget commitment`, which is unquoted and unverified. The performance target is therefore unsupported by the plan itself.
- [P2] The risk mitigation `weekly compress step in cron` introduces operational work that is absent from Files to Change, TDD tests, and acceptance criteria. This is either unplanned scope or an untracked dependency.
- [P2] The plan says `cfr_lookup.py` may be a stub if #2395 not yet shipped, but `Deliverable` still promises 5 tools and `test_server_boots` requires advertising 5 tools. The plan does not define whether a stubbed tool with unavailable backing data is acceptable for the issue's intended scope or how clients distinguish partial implementation from success.
- [P2] Frontmatter authority is unaddressed where docs are created/updated. The plan creates `docs/document-intelligence/mcp-server.md` and updates `docs/plans/README.md`, but if these participate in wiki/domain indexing the plan does not state required baseline fields (`title`, `last_updated`, `doc_key`) or whether they are outside the §8.1 scope. This remains unverified rather than resolved.

### Suggestions
- Replace every asserted repo/issue fact in `Resource Intelligence Summary` with concrete evidence lines: exact paths, filenames, issue status snapshots, and one factual finding per cited source.
- Do not move past `plan-review` until Codex and Gemini review artifacts are actually produced and cited by exact existing paths, or explicitly narrow the review policy exception with justification.
- Add a dependency matrix listing each cited issue (`#2396`, `#1804`, `#2393`, `#2395`), current status, whether blocking or parallel, and what behavior occurs if it is absent.
- Reduce scope to the issue title or explicitly justify each added deliverable (`coverage_status`, `cfr_lookup`, multi-agent registration, audit logging) against the issue body.
- Add tests for every acceptance criterion: Claude registration discovery, Gemini registration/config resolution, Hermes bridge invocation, review-artifact existence/posting, and any manual smoke tests you want to eliminate.
- State explicit `doc_key` invariants: require `sha256:` namespace in inputs/outputs, forbid path-only identity, and add negative tests for non-`sha256:` identifiers.
- Add an operating-model compliance section that explicitly verifies §2 ownership taxonomy, §4 flow rules, §7 storage tiers, and whether audit logs are durable/local/cache/shared-mount artifacts.
- Replace `.gemini/mcp-servers.yaml (or equivalent config file)` with one concrete file path or split into conditional tasks with preconditions and fallback behavior.
- Write an actual threat model for paths/logs: symlink traversal, `..` traversal, mount escape, secret-containing excerpts, caller spoofing, and log injection; then add tests for each.
- Remove the weak `grep for write methods = 0` check and replace it with behavioral tests plus code-level constraints that permit only the intended audit-log write path.
- If cron-based log compression is required, add explicit files/tasks/tests for it; otherwise remove it from the plan to avoid hidden scope.
- Clarify whether newly created docs are wiki-indexed artifacts; if yes, add required frontmatter fields, and if no, state why §8.1 does not apply.
