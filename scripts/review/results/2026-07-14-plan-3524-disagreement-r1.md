### codex

- The non-mutation contract contradicts the reporting contract. Plan §Pseudocode says “never mutate when mode is Audit or WhatIf” but also unconditionally says “emit structured JSON”; Phase 0 requires archiving a local JSON report, while TDD test `test_whatif_changes_nothing_and_does_not_claim_report_written` requires “No registry/file/report write,” and Acceptance Criteria require default invocation to be non-mutating. The source script `D:\ws\Repair-RdpMicrophone.ps1` writes a JSON report by default even in Audit and `-WhatIf`. The plan never defines whether audit reporting requires an explicit `-ReportPath`, writes only to stdout, or is an allowed mutation. These requirements cannot all pass as written.
- Phase 0 is not executable for every client type the plan explicitly supports. Plan §Gaps identifies `mstsc.exe`, `msrdc.exe`, or Windows App, yet Phase 0 and Acceptance Criterion 1 require the “exact `.rdp` profile used,” and §Pseudocode requires an explicit `rdp_file`. The cited Microsoft documentation only establishes `.rdp` files as the configuration point for Remote PC connections; the plan supplies no Windows App/MSRDC configuration extraction procedure or fail-closed branch when no user-selected `.rdp` file exists. The evidence gate can therefore block indefinitely or falsely associate an unrelated profile with a modern-client session.
- Negotiation-event evidence is not scoped to the newly tested connection. Plan §Pseudocode `classify_audio_events(messages)` classifies arbitrary messages solely by token matches, and Acceptance Criteria accept “RdpCoreTS evidence” after reconnect. The source implementation `D:\ws\Repair-RdpMicrophone.ps1` reads the shared RdpCoreTS Operational log over the preceding four hours without filtering by session, client, user, connection activity, or a before/after timestamp. On shared RDS02, another user or earlier connection can supply `AUDIN` and create a false pass. The plan needs correlation boundaries and tests proving stale/unrelated events cannot satisfy the acceptance criterion.
- Mutation coverage does not match the repairs authorized by Phase 2. Plan §Phased Execution authorizes “per-user/per-app privacy correction” and “documented administrative policy change,” but the TDD Test List tests only per-app deny detection, profile mutation, and consent deletion. There are no tests for exact per-app privacy writes, global privacy writes, elevation failure, policy value/type selection, `ShouldProcess`, partial registry failure, or rollback/reporting of prior registry values. This violates the repository’s tests-first gate for safety-critical live registry changes.
- The plan does not make registry repairs reversible despite promising an “explicitly selected reversible repair” in §Deliverable. `reset_target_consent` only exports the prior value in JSON and deletes it; Phase 2 merely says to print rollback commands for modified RDP profiles. No pseudocode, artifact requirement, test, or acceptance criterion requires restoration commands for consent, privacy, or administrative policy changes. Host-local JSON is also described as volatile and uncommitted, so losing that file loses the only stated prior value.
- The Windows placement claims overstate the cited sources. Resource Intelligence says `scripts/windows/README.md` “establishes `scripts/windows/` as the canonical location for Windows-native PowerShell tooling,” and the Standards table says `docs/standards/CONTROL_PLANE_CONTRACT.md` requires that placement. `scripts/windows/README.md` describes OS-appropriate launchers for the Windows ecosystem and specific Linux/Windows pairs; it does not declare that directory canonical for every Windows operational tool. Grepping `docs/standards/CONTROL_PLANE_CONTRACT.md` found no `scripts/windows` placement rule. The chosen path may be reasonable, but the asserted source support is false.
- The keyboard-routing requirement misstates `keyboardhook:i:2`. Plan Acceptance Criteria says “With `keyboardhook:i:2` or full-screen routing,” implying two alternatives. Microsoft Learn states value `2` sends Windows key combinations to the remote computer only in full-screen mode. The criterion must require both value `2` and full-screen operation, or use another documented routing value where supported; otherwise the Win+H test can fail despite satisfying the written setup.
- The proposed event classifier is too permissive to serve as correctness evidence. Plan §Pseudocode accepts any message matching `AUDIN` or `AUDIO_INPUT/AUDIO_CAPTURE variants`. There are no negative fixtures for channel close/failure/rejection events, unrelated descriptive text, or historic events containing those tokens. `test_audin_or_audio_input_is_success_evidence` therefore risks defining token presence—not successful channel negotiation—as success.
