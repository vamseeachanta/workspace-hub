### claude

- **Pseudocode `pending_work_report` does not scope-filter local-state counts (plan §Pseudocode `pending_work_report`).** D2 says the low-level store accepts any `account_id`, and D7 says disabled-alias records "never make `mailbox_empty` false," but the pseudocode computes `inbound_count`/`decision_count`/`needs_schema_count` over all local-state rows with no account-scope filter. A disabled-account (e.g., `skestates`) or placeholder-account thread persisted via the permissive low-level store would flip `tracked_empty`/`mailbox_empty` false, contradicting the prose. No test in the TDD list covers disabled-account rows in *local state* — `test_rejects_out_of_scope_account_alias_at_report_boundary` only covers inbox-snapshot records. Add an explicit test: out-of-scope local-state rows are excluded from (or separately bucketed in) tracked counts.
- **Inconsistent sentinel in the `config_missing` branch (plan §Pseudocode, `pending_work_report` early return).** The fail-closed return sets `unknown_count`, `out_of_scope_count`, `reactivation_pending_count` to `None` (not evaluated) but `noise_excluded: 0`, which reads as "evaluated, none found." Use `None` for consistency or document why noise exclusion is evaluable without a config.
- **Cross-cycle no-trigger duplicates are silently skipped instead of raising `StaleStateError` (plan D5 last bullet + D11).** The historical-retry search matches on `(account_id, thread_id, from_state, to_state, dedup_event_id)` — `cycle_id` is excluded. For no-trigger events `dedup_event_id` is the constant `legacy:no-trigger`, so a stale caller replaying a cycle-1-shaped transition after reactivation (current state differs) matches the cycle-1 key and is skipped as an "idempotent retry" rather than rejected as stale. State is not corrupted (nothing appends), but the loud-failure signal D11 promises for stale `from_state` is lost for exactly this class. Either include cycle candidates in the historical match or document the silent-skip as accepted behavior with a test.
- **Cold-start bootstrap is mechanically open to all callers, restricted only by prose (plan D5, D11, §Pseudocode `reactivate_reply`).** D5 says the bootstrap fallback is "only for the existing single-call #2017 contract test," but the pseudocode grants `bootstrap_reactivation` to any `reactivate_reply` call whenever no snapshot record exists — no id of any kind required, and `MissingReactivationId` is unreachable in the cold-start branch. The mitigations (stamped `bootstrap_reactivation: true`, checker reports `baseline_missing` instead of calling cold) are real but normative. This is the residual of R5 blocker #1; acceptable as an audit-trailed compatibility seam, but the implementation notes must record it as such, and the production reactivation checker must be tested to never invoke `reactivate_reply` for threads absent from local state.
- **Sweep apply can purge a thread with an unprocessed new reply (plan D9 + issue body "Grace Period Logic").** Issue #2026 specifies "If new unread message arrives during grace period: revert to inbox." `sweep_grace(apply)` checks only still-`completed` local records and never consults an inbox snapshot; if the reactivation checker has not run first, a replied-to thread is purged locally. Mitigated because purge is local-only and `purged -> extracted/inbound` reactivation is valid, but the plan should state the ordering contract (reactivation check before sweep apply) for the scheduled job and any future #2423 wiring, where purge stops being harmless.
- **The r6 dispatched-provider artifacts are zero-byte files, not UNAVAILABLE records (plan line 9 + `scripts/review/results/2026-06-11-plan-2026-r6/`).** The 17:37 fanout failed (gemini: sandbox/tool errors in `.err`; codex: 325 KB `.err`; claude: empty). Per the repo's documented degradation convention, failed provider rounds must be recorded as explicit UNAVAILABLE files — empty `.md` files can be misread as silent passes. The plan's review-artifact inventory (line 9, Artifact Map) also stops at r5 and should be updated to reflect r6 disposition.

### codex

- Plan D5 requires production reactivation checkers to pass `latest_message_id` or stable `reactivation_id`, otherwise `MissingReactivationId` is raised (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:311`, `:477-485`). But the public `reactivate_reply()` API accepts `triggering_message_id`/`reactivation_id`, not `latest_message_id` (`:520-535`), and `reactivation_candidates()` only says it returns planned `reactivate_reply` calls without specifying how inbox `latest_message_id` is mapped (`:623-626`). The TDD row only asserts a planned call exists (`:725`), not that it carries a valid message/reactivation id. This can still implement a checker that always fails or silently uses bootstrap/no-trigger semantics in production.
- Grace sweeping depends on `completed_at`, but the plan does not define who stamps it during normal `extracted -> completed` transitions. `sweep_grace()` filters records where `now - completed_at > grace_days` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:561-566`), while the current schema makes `completed_at` optional (`docs/design/email-queue-state-schema.yaml:51-54`, `:115-117`) and the transition API/pseudocode has no rule to set it when `to_state == "completed"` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:458-495`). The boundary tests use “completed at now-7d” fixtures (`:700-701`) but do not require real completion transitions to populate the field.
- Live label setup is still underspecified for two Gmail accounts. The plan requires creating labels for both `ace` and `personal` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:288-301`, `:755-757`), but the executable contract is `ensure_labels(account_scope, gmail_client=None, apply=False)` with a single `gmail_client` (`:616-620`). Gmail label APIs operate on the authenticated mailbox (`docs/design/email-as-queue-workflow.md:377-384`), so a single-client API can pass fake-client tests while only mutating one mailbox. No test requires per-account client selection or verifies two authenticated accounts; the listed tests use one fake Gmail client/surface (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:720-723`).
- The paired learning-log/state-log write is not crash-consistent. `_append_events_locked()` appends the learning row first, then the state event (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:497-508`). A file lock does not make two appends atomic across process crash, so `extraction_missing_on_reactivation` can be durably logged without the corresponding state transition. The plan has no transaction id, recovery rule, or test for half-written paired events; the only related test checks that a learning event is emitted and state becomes inbound (`:707`).
- Snapshot freshness is a declared module/behavior but not pinned by tests. The plan creates `scripts/email/state/meta.py` for “Snapshot metadata freshness checks” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:654`) and `lookup()` reads the snapshot only “if meta is fresh” otherwise rebuilds (`:511-515`). The TDD list has path derivation and apply-rebuild checks (`:683-704`) but no stale-meta, bad-hash, changed-log-offset, missing-meta, or corrupt-snapshot test. That leaves a correctness-critical read path unverified.

### gemini

- **Hallucinated Files:** The plan's "Evidence (embedded verification)" section explicitly claims `docs/design/email-as-queue.md`, `docs/design/email-queue-state-schema.yaml`, and `tests/email/test_state_machine_contract.py` exist in the repository. Empirical checks via `glob` confirm these files do not exist at HEAD. The plan is validating against a non-existent or hallucinated repository state.
- **`sweep_grace` Batch Crash:** Plan § D9 states `sweep_grace` processes records in batches under one lock, claiming "dynamic current-state validation skips records reactivated before the batch lock". However, the pseudocode for `_append_events_locked` and `prepare_event` contradicts this by explicitly executing `raise StaleStateError` if `current.state != event.from_state`. A reactivated record will crash the entire batch operation rather than gracefully skipping.
- **Unlocked State Check Race Condition:** Plan § Pseudocode for `reactivate_reply` sets `bootstrap_reactivation = no current snapshot record exists for account_id/thread_id` *before* delegating to `_append_events_locked`. This forces an unlocked read of the snapshot to evaluate the boolean, creating a race condition if the state changes before the lock is acquired, and redundantly double-reads the snapshot.
- **Unbounded `prior_state` on Bootstrap:** Plan § D11 mandates that the cold-start `reactivate_reply` wrapper accepts missing snapshot records *only* when "prior_state in {'awaiting-reply', 'completed', 'purged'}". The pseudocode for `reactivate_reply` completely fails to validate `prior_state` against this allowlist before generating the `QueueStateEvent` with `bootstrap_reactivation=True`. 
- **Missing CLI Thread Enumeration API:** Plan § D10 and the Acceptance Criteria claim the `report` CLI command will show "all tracked threads plus counts". The `pending_work_report` pseudocode only returns aggregated counts/flags. Furthermore, the designated public API (§ D6) only exposes `lookup` (for a single thread), `transition`, `count_entries`, and `reactivate_reply`. There is no list/enumeration method provided for the CLI to actually fetch all tracked threads.
- **KeyError on Snapshot Lookup:** Plan § Pseudocode for `lookup(log_path, account_id, thread_id)` ends with `return snapshot[f"{account_id}::{thread_id}"]`. If the snapshot loads successfully but the requested thread is unknown, this will throw an unhandled `KeyError` rather than safely returning `None`, which breaks absence checks.
- **Hand-wavy Historical Dedup Match:** Plan § D5 requires historical retry detection to find keys "with the same (account_id, thread_id, from_state, to_state, dedup_event_id)"—a 5-tuple match. The `prepare_event` pseudocode assigns a 6-tuple `event.dedup_key` (which includes `cycle_id`) and hand-waves the cross-cycle search logic by asserting "compute provisional dedup key ... and historical cycle candidates ... if provisional dedup key exists in historical_dedup_index". This fails to define a concrete mechanism for cycle-agnostic matching.
- **Undefined "reactivation event" Identification:** Plan § Pseudocode for `prepare_event` contains the branch `if event is reactivation:`. The plan provides no algorithmic or state-machine definition of how the system identifies an event as a "reactivation" (e.g., checking specific `from_state` -> `to_state` vectors). Without this, `transition()` cannot enforce the correct `cycle_id` logic.
