## Findings
1. Plan D5 requires production reactivation checkers to pass `latest_message_id` or stable `reactivation_id`, otherwise `MissingReactivationId` is raised (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:311`, `:477-485`). But the public `reactivate_reply()` API accepts `triggering_message_id`/`reactivation_id`, not `latest_message_id` (`:520-535`), and `reactivation_candidates()` only says it returns planned `reactivate_reply` calls without specifying how inbox `latest_message_id` is mapped (`:623-626`). The TDD row only asserts a planned call exists (`:725`), not that it carries a valid message/reactivation id. This can still implement a checker that always fails or silently uses bootstrap/no-trigger semantics in production.

2. Grace sweeping depends on `completed_at`, but the plan does not define who stamps it during normal `extracted -> completed` transitions. `sweep_grace()` filters records where `now - completed_at > grace_days` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:561-566`), while the current schema makes `completed_at` optional (`docs/design/email-queue-state-schema.yaml:51-54`, `:115-117`) and the transition API/pseudocode has no rule to set it when `to_state == "completed"` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:458-495`). The boundary tests use “completed at now-7d” fixtures (`:700-701`) but do not require real completion transitions to populate the field.

3. Live label setup is still underspecified for two Gmail accounts. The plan requires creating labels for both `ace` and `personal` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:288-301`, `:755-757`), but the executable contract is `ensure_labels(account_scope, gmail_client=None, apply=False)` with a single `gmail_client` (`:616-620`). Gmail label APIs operate on the authenticated mailbox (`docs/design/email-as-queue-workflow.md:377-384`), so a single-client API can pass fake-client tests while only mutating one mailbox. No test requires per-account client selection or verifies two authenticated accounts; the listed tests use one fake Gmail client/surface (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:720-723`).

4. The paired learning-log/state-log write is not crash-consistent. `_append_events_locked()` appends the learning row first, then the state event (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:497-508`). A file lock does not make two appends atomic across process crash, so `extraction_missing_on_reactivation` can be durably logged without the corresponding state transition. The plan has no transaction id, recovery rule, or test for half-written paired events; the only related test checks that a learning event is emitted and state becomes inbound (`:707`).

5. Snapshot freshness is a declared module/behavior but not pinned by tests. The plan creates `scripts/email/state/meta.py` for “Snapshot metadata freshness checks” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:654`) and `lookup()` reads the snapshot only “if meta is fresh” otherwise rebuilds (`:511-515`). The TDD list has path derivation and apply-rebuild checks (`:683-704`) but no stale-meta, bad-hash, changed-log-offset, missing-meta, or corrupt-snapshot test. That leaves a correctness-critical read path unverified.

## Blockers
- Finding 1: production reactivation id mapping is not executable.
- Finding 2: grace sweep cannot be reliable without a completed-at stamping contract.
- Finding 3: two-account Gmail label setup can pass tests while only touching one mailbox.
- Finding 4: paired learning/state append can leave inconsistent durable logs.
- Finding 5: snapshot freshness/rebuild behavior is untested despite being part of the read correctness contract.
