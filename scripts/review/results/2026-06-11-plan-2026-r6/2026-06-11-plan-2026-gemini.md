## Findings
1. **Hallucinated Files:** The plan's "Evidence (embedded verification)" section explicitly claims `docs/design/email-as-queue.md`, `docs/design/email-queue-state-schema.yaml`, and `tests/email/test_state_machine_contract.py` exist in the repository. Empirical checks via `glob` confirm these files do not exist at HEAD. The plan is validating against a non-existent or hallucinated repository state.
2. **`sweep_grace` Batch Crash:** Plan § D9 states `sweep_grace` processes records in batches under one lock, claiming "dynamic current-state validation skips records reactivated before the batch lock". However, the pseudocode for `_append_events_locked` and `prepare_event` contradicts this by explicitly executing `raise StaleStateError` if `current.state != event.from_state`. A reactivated record will crash the entire batch operation rather than gracefully skipping.
3. **Unlocked State Check Race Condition:** Plan § Pseudocode for `reactivate_reply` sets `bootstrap_reactivation = no current snapshot record exists for account_id/thread_id` *before* delegating to `_append_events_locked`. This forces an unlocked read of the snapshot to evaluate the boolean, creating a race condition if the state changes before the lock is acquired, and redundantly double-reads the snapshot.
4. **Unbounded `prior_state` on Bootstrap:** Plan § D11 mandates that the cold-start `reactivate_reply` wrapper accepts missing snapshot records *only* when "prior_state in {'awaiting-reply', 'completed', 'purged'}". The pseudocode for `reactivate_reply` completely fails to validate `prior_state` against this allowlist before generating the `QueueStateEvent` with `bootstrap_reactivation=True`. 
5. **Missing CLI Thread Enumeration API:** Plan § D10 and the Acceptance Criteria claim the `report` CLI command will show "all tracked threads plus counts". The `pending_work_report` pseudocode only returns aggregated counts/flags. Furthermore, the designated public API (§ D6) only exposes `lookup` (for a single thread), `transition`, `count_entries`, and `reactivate_reply`. There is no list/enumeration method provided for the CLI to actually fetch all tracked threads.
6. **KeyError on Snapshot Lookup:** Plan § Pseudocode for `lookup(log_path, account_id, thread_id)` ends with `return snapshot[f"{account_id}::{thread_id}"]`. If the snapshot loads successfully but the requested thread is unknown, this will throw an unhandled `KeyError` rather than safely returning `None`, which breaks absence checks.
7. **Hand-wavy Historical Dedup Match:** Plan § D5 requires historical retry detection to find keys "with the same (account_id, thread_id, from_state, to_state, dedup_event_id)"—a 5-tuple match. The `prepare_event` pseudocode assigns a 6-tuple `event.dedup_key` (which includes `cycle_id`) and hand-waves the cross-cycle search logic by asserting "compute provisional dedup key ... and historical cycle candidates ... if provisional dedup key exists in historical_dedup_index". This fails to define a concrete mechanism for cycle-agnostic matching.
8. **Undefined "reactivation event" Identification:** Plan § Pseudocode for `prepare_event` contains the branch `if event is reactivation:`. The plan provides no algorithmic or state-machine definition of how the system identifies an event as a "reactivation" (e.g., checking specific `from_state` -> `to_state` vectors). Without this, `transition()` cannot enforce the correct `cycle_id` logic.
