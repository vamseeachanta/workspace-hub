## Findings

1. The acceptance transaction is not atomic. Plan lines 216–220 say it will “atomically append accepted event and replace accepted-release pointer,” but those are separate files at lines 121–122 and 234–235. A crash can leave an accepted ledger event with the old pointer or the new pointer without its event. `test_accepted_pointer_updates_atomically_after_authorized_smoke` at line 267 cannot make a two-file operation atomic. The plan needs one authoritative atomic object or a write-ahead/recovery protocol with crash-point tests.

2. The concurrency model cannot serialize the declared topology. `record_candidate` uses a “repository-local lock” and local `expected_accepted_hash` at lines 211–214, while line 10 declares `parallel-worktree`. Separate worktrees or machines do not share that lock or working-copy state. No remote-ref CAS, fetch-before-write, push-race handling, or recovery rule exists. This violates `docs/standards/PARALLEL_FIRST_EXECUTION.md:24-25,39-52`, which requires explicit path ownership and serialization for shared files.

3. Production-smoke failure leaves contradictory state. Lifecycle P6 at lines 148–150 necessarily mutates production before read-only smoke can inspect it, but acceptance is recorded only after smoke at lines 216–220. If smoke fails, production can be R2 while `accepted-release.json` remains R1. There is no deploy-pending state, failed-production transition, rollback operation, timeout/unknown state, or reconciliation procedure, contradicting acceptance line 290.

4. Fresh production authorization is caller-forgeable and replayable. `accept_candidate(candidate, user_authorization, production_smoke)` at line 216 accepts an untyped argument. The plan never live-fetches its author/content, nor binds it to the candidate evidence root, HF SHA, website commit, deployment environment, action, expiry, or one-time nonce. The schema list at line 280 omits authorization, and the TDD list has no forged/stale/wrong-release authorization test. Therefore line 293’s “fresh explicit authorization” is unenforced.

5. Plan approval verification does not bind the repository’s actual approval authority. Lines 188–193 mention an unspecified “approval marker” and any configured-owner comment predating implementation. They do not require `.planning/plan-approved/<issue>.md`, bind that marker and comment to the exact reviewed blob, or define an unambiguous approval phrase/comment ID. The canonical workflow explicitly requires that marker at `.claude/skills/coordination/issue-planning-mode/SKILL.md:172-186`. An owner-authored architecture or approval-request comment could otherwise satisfy the proposed lookup.

6. Receipt hashing does not prove trusted execution. Lines 197–206 accept child-authored build, browser, deployment, and scan receipts; lines 199 and 252 only schema-check and rehash them. A caller can manufacture internally consistent PASS receipts and hashes. The plan does not bind evidence to a named child Git blob, trusted CI run, deployment API response, or signed attestation, nor prove that the registry blob belongs to the website SHA actually deployed. `test_browser_build_deployment_and_scan_receipts_are_required` at line 268 checks presence, not provenance.

7. The user-facing approval packet is stale relative to the plan’s safety-critical lifecycle. `docs/plans/2026-07-16-field-explorer-plan-approval-packet.html:62-69` presents a five-step flow ending with generic promotion, omitting the preview R1→R2→R1 drill, fresh production authorization, production smoke, ledger transition, and rollback authority introduced at parent-plan lines 147–150 and 211–220. The packet is listed as an approval artifact at line 114 but is absent from Files to Change and parity tests. It cannot support informed approval in its current form.

8. Review provenance does not bind the current plan bytes. Parent line 11 identifies commit `06216c5c...`, but the working plan materially differs from that commit and is currently an untracked replacement over an index deletion. Round-2 Claude/Codex outputs are zero-byte and Gemini is UNAVAILABLE; `.gitignore:577` also ignores the entire review-results directory, while the workflow requires final artifacts to be committed and pushed (`issue-planning-mode/SKILL.md:149-162`). Before approval, evidence must be revision-stamped, non-empty, remotely retrievable, and bound to the final plan blob.

The inspected Explorer inputs were not among the changed files, so this is MINOR now, but the plan must label the SHA as the local inspected baseline and require fresh-main reconciliation before child implementation.
