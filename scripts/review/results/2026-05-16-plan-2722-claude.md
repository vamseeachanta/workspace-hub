## Findings

1. **"Three landed fix PRs" claim is FALSE** (plan §Resource Intelligence Summary, lines 35-39). Plan asserts the three PRs are "landed" and uses them in §Evidence/Reproduction proofs (line 117) as "the audit + 3 landed fix PRs serve as the empirical evidence." Live state: `worldenergydata#415`, `aceengineer-website#15`, `assethold#51` are **all OPEN**. This is a load-bearing factual error — the plan's forward-validation assumes the sibling repos are clean, but if the fix PRs haven't merged, the markers may still be on `main` in those siblings. Installing the new hook on those repos via §Acceptance criterion 12 ("hook installed on ≥2 sibling repos…verified to block a deliberately constructed marker-containing commit") would *also* block legitimate work until those PRs merge.

2. **"40 existing + 16 new = 56" is WRONG** (plan §Acceptance Criteria, the no-regression criterion ~line 342). Actual `grep -c "^def test_" tests/enforcement/*.py` total = **36** test functions, not 40. Math becomes 36 + 16 = 52, not 56. Replace the magic number with a delta-form invariant (e.g., "existing test count + 16 new").

3. **Self-exclude is a blanket file-level exemption — exploitable defense bypass** (plan §Pseudocode line 174). `if "$file" == "scripts/enforcement/check-no-conflict-markers.sh": continue` permanently whitelists the entire script from marker detection. Any future modification to that script — including a malicious one that adds conflict-marker text outside the documentation block — would land silently. The mitigation should be per-line sentinel matching (`# CONFLICT_MARKER_FORENSIC_OK` end-of-line tag, as `check-no-abs-paths.sh:28` does with `# abs-path-allowed`), NOT per-file exemption.

4. **Forensic-whitelist sentinel reads working tree, but marker scan reads staged blob — TOCTOU divergence** (plan §Pseudocode lines 172, 178-179). Marker scan uses `grep ... (staged blob via git show :"$file")`; sentinel check uses `grep -q "<!-- CONFLICT_MARKER_FORENSIC_OK -->" "$file"` (working tree). An attacker can place the sentinel ONLY in the working tree (not staged), defeating the whitelist gate while landing markers in stage. Both reads must come from the same source — the staged blob.

5. **TIER1_REPOS path resolution unspecified — installer is non-deterministic** (plan §Pseudocode line 210). `REPO_PATH = "$HOME/$repo" OR "$WS_ROOT/../$repo" OR configured base` defers a critical decision. On this machine `~/workspace-hub` is a sparse overlay (per CLAUDE.md `Sparse overlay`); siblings exist at both `/mnt/local-analysis/<repo>` and possibly under `~/<repo>`. The installer needs a single resolution order (preferably `${WORKSPACE_HUB:-…}/../$repo` then fallback) with a test of `-d "$REPO_PATH/.git"` to confirm. Without it, installer behavior on this user's actual layout is undefined.

6. **GNU sed `i\` insert-before-pattern is non-portable to BSD/macOS** (plan §Install-hooks.sh wiring, lines 272-278). The `sed -i '/^exit 0$/i\...'` form is GNU-specific. BSD sed (macOS default) requires `-i ''` (empty string) and a different newline-escaping form for `i\`. `bootstrap-machine.sh` claims cross-OS support (lines 22-27 detect Linux/macOS/Windows). This sed invocation will fail silently or destructively on macOS. Either gate on `[[ "$(uname -s)" == "Linux" ]]` or rewrite using Python/awk for portability.

7. **#2411 issue title contradicts the plan's characterization as "7-repo audit"** (plan §Documents consulted, line 34). The issue's actual title is "feat(release-readiness): tier-1 provider entrypoint and parity surface inventory" — the 7-repo audit is a *comment* deliverable that satisfies that issue, not the issue itself. Re-cite as "#2411 audit comment ([issuecomment-4467824635](...))" without conflating issue and comment scope.

8. **Pseudocode `^>>>>>>> ` trailing-space requirement misses git's lower-bound** (plan §Pseudocode line 179, §Acceptance Criteria 3). Plan claims "git always writes that form" (with trailing space). True for the standard merge writer, but `recursive`/`diff3` styles, custom merge drivers (`git config merge.<driver>.recursive`), and external tools can emit `<<<<<<<\n` with no trailing space when the ref name is empty or when output is generated mechanically. False-negative consequences listed in §Risks acknowledge a "stray `=======`" case but not the "no trailing space" case. Either weaken the anchor to `^<<<<<<<\b` / `^>>>>>>>\b` or document why this risk is accepted.

9. **`docs/governance/**` pattern semantics undefined** (plan §Pseudocode line 172). `matches pattern "docs/governance/**"` reads as a glob but the script is bash. `[[ "$file" == docs/governance/* ]]` (single `*`) matches one level; `**` requires `shopt -s globstar`. Pseudocode should disambiguate; otherwise implementer guesses and gets either too-broad or too-narrow scope.

10. **Cadence-helper "pattern lifted" comparison overstated** (plan §Pseudocode line 238). The cadence-helper sync at `install-hooks.sh:158-178` is a `cat >> pre-push` append for installation + a separate `sync-cadence-helper.sh` byte-compare. The plan's drift-check pseudocode uses `sha256` comparison — that is *similar in spirit* but is NOT the same idiom. Either inspect `scripts/sync/sync-cadence-helper.sh` and adopt its actual mechanism (likely `cmp -s` or `diff -q`, not sha256) or drop the "lifted from" wording, which falsely implies a verified-to-work pattern.

11. **`docs/plans/README.md` row addition is named but not specified** (plan §Artifact Map line 137, §Files to Change). No format, no column ordering. README rows typically have a strict shape; the implementer must guess. Either pin the row format or remove the "Update" entry.

12. **Acceptance criterion 12 ("hook installed on ≥2 sibling repos") is unverifiable from inside this plan** (line ~343). Sibling repos are git-independent — there's no way for a workspace-hub CI/test to attest the install state of `digitalmodel/.git/hooks/pre-commit` without writing to those repos. The criterion needs an explicit verification command (e.g., `bash check-pre-commit-hook-drift.sh && grep -q "check-no-conflict-markers" $sibling/.git/hooks/pre-commit`) or it becomes self-attestation.

13. **No mention of how the new hook interacts with the existing dead-code state** (plan §Resource Intelligence Summary line 22 identifies it; §Install-hooks.sh wiring lines 268-280 patches around it but does not remove it). The plan correctly notes the state-file size guard at `.git/hooks/pre-commit:51-54` is dead code, but the wiring block inserts BEFORE `exit 0` without removing the dead code below. This is fine for the marker check, but leaves the state-file size guard broken — an in-scope cleanup the plan should either commit to OR explicitly defer with citation.
