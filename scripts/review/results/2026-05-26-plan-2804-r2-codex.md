# Adversarial Plan Review: Issue #2804 r2

## Findings

### BLOCKER: #2804 acceptance still depends on executing #2802, so the claimed scope split is not real

The plan says `#2804 (this plan) is DONE when the route is codified + demonstrated once -- it does NOT depend on #2802 being merged`, and also says `#2802 stays its own implementation issue`. But the acceptance criteria require `#2802 executed via broker in an isolated worktree`, `Code-stage T3 review on the #2802 diff completed`, and `scripts/legal/legal-sanity-scan.sh passes on the #2802 diff`.

That makes #2804 completion dependent on #2802 implementation, review, and legal-scan state. It does not depend on merge, but it absolutely depends on #2802 being materially executed. This reintroduces cross-issue coupling and lets an infrastructure route plan fail because a separate product/implementation issue has unrelated defects or review churn.

Concrete fix: split acceptance into two gates:

- #2804 acceptance: installer/profile/config codified, clean-checkout smoke test proves `codex exec` and broker write/test capability in a disposable fixture worktree, documentation updated, pilot run launched with recorded command/session id.
- #2802 acceptance: separate issue/PR owns its TDD, dry-run, code review, legal scan, and user merge.

If a real pilot must remain mandatory for #2804, make it a minimal synthetic repo-local pilot owned by #2804, not #2802's functional implementation.

### MAJOR: The installer acceptance criterion is unverifiable and under-specified for a privileged host change

Acceptance criterion 1 says running the installer on a clean checkout reproduces a working Codex sandbox. The plan does not specify how a reviewer will verify this without repeatedly mutating `/etc/apparmor.d/`, whether the installer supports dry-run, whether it detects preexisting local modifications, how it backs up/restores a profile, how it reloads AppArmor, or how it fails closed when `sudo`, `apparmor_parser`, `/usr/bin/bwrap`, or Ubuntu/AppArmor layout differs.

This is a privileged host mutation, so "idempotent installer" is not enough. A bad installer can leave the machine in a misleading partially-configured state while the smoke test passes only because the session already had the manual fix.

Concrete fix: add explicit installer requirements and tests:

- `--dry-run` prints exact files/commands and performs no writes.
- `--check` verifies current state without mutation and exits nonzero on drift.
- `--install` requires explicit confirmation or an environment guard, writes a managed profile with a sentinel header, refuses to overwrite unmanaged local content, reloads AppArmor, and verifies with fresh `bwrap --unshare-user`.
- Smoke test must first prove the clean checkout did not rely on session residue by checking the expected profile content and AppArmor reload status.
- Add shell tests or a documented harness for no-op/idempotency/refuse-overwrite behavior.

### MAJOR: `network_access=true` is accepted without a bounded threat model or rollback criteria

Risk R4 says widened egress is "accepted -- required for gh/git; scoped to workspace-write mode; documented." That is not a mitigation. The stated objective is to restore Codex's sandboxed execution with paid credits and provider strengths. Turning on network for all workspace-write Codex sessions changes the sandbox contract and could allow unintended egress from any future broker task, including tasks that do not need GitHub/network access.

The plan also commits config mutation into the same installer as the AppArmor fix, making the network change look inseparable from userns restoration. It does not define when network must be enabled, whether it can be task-scoped, whether a no-network mode remains supported, or how secrets/environment exposure is constrained.

Concrete fix: separate the two changes:

- AppArmor userns grant is the baseline route fix.
- Network access is an opt-in profile or flag for tasks that need `gh`/`git` remote access.
- The installer must preserve existing config unless explicitly asked to set network access, show the before/after diff, and document rollback.
- Acceptance should include a no-network smoke test for local writes/tests and a separate network-required smoke test for GitHub operations.

### MAJOR: Mandatory worktree path is not isolated enough from repo and credential state

The plan mandates `/mnt/local-analysis/wt-2802` and says this isolates completely from the 101-file dirty tree. It isolates the working tree files, but not the global Git config, credentials, Codex auth/config, broker plugin cache, issue labels, or remote branch namespace. It also does not specify branch creation, branch name, cleanup behavior if Codex leaves untracked files, or protection against reusing a stale `/mnt/local-analysis/wt-2802` from a prior run.

"Completely" is therefore overstated and dangerous. The biggest failure mode is believing the dirty tree risk is gone while Codex still pushes, labels, or writes artifacts through shared global state.

Concrete fix: replace the worktree step with a stricter runbook:

- Before `git worktree add`, assert the path does not exist or archive/remove only after explicit inspection.
- Use a named branch such as `codex/2802-<slug>` created from a recorded `origin/main` SHA.
- Record `git worktree list --porcelain`, `git -C <wt> rev-parse HEAD`, `git -C <wt> status --short`, and `git -C <wt> branch --show-current`.
- Define allowed write paths and forbidden paths for Codex in the prompt.
- Require post-run checks for untracked files, branch refs, and pushed commits before cleanup.
- Avoid the word "completely"; state exactly what is isolated and what remains shared.

### MAJOR: The plan still lets Claude erode cross-provider value during monitoring and review loops

v2 correctly pivots away from brain/hands, but the execution section says Claude "monitors, verifies gates, runs the code-stage T3 review, opens/loops the PR." That leaves an ambiguous repair path: when the Codex-produced diff fails review, does Codex patch it, does Claude patch it, or does Claude rewrite the prompt/output until the result is effectively Claude-authored?

The plan needs a provenance contract, because the central objective is to use Codex execution credits and provider strengths under Claude orchestration. Without a repair-loop rule, the brain/hands failure mode can come back after the first review finding.

Concrete fix: add a loop contract:

- Codex owns implementation patches for #2802 unless the orchestrator explicitly terminates the pilot and records why.
- Claude may only apply mechanical metadata fixes outside the Codex-owned implementation diff, or must mark the run as mixed-author and not count it as a clean Codex-under-Claude pilot.
- Review findings are relayed back to Codex as defects to fix; Claude verifies after each Codex patch.
- Pilot report must record authorship/provenance: initial Codex commit(s), any Claude edits, and whether the result still qualifies as a Codex execution pilot.

### MAJOR: TDD evidence remains too easy to game

Risk R3 says reviewers require a behavioral assertion failure red-to-green. That is better than import failure, but not enough for this route plan. The plan does not require the failing test to exist before implementation in version control history, does not require the red command to run against the pre-implementation commit, and does not require proof that the green result corresponds to the same test after implementation.

Codex could still generate a test and implementation together, then show a contrived red by temporarily disabling code or running against the wrong tree. Claude monitoring does not fix that unless the runbook pins commits and commands.

Concrete fix: require a TDD trace:

- Commit or stash point A: failing behavioral test only.
- Run exact red command at point A and record output.
- Commit or stash point B: implementation.
- Run exact green command at point B and record output.
- Pilot report cites both SHAs or patches and confirms the same test file/test id was used.

### MAJOR: Version guard handling is hand-waved and could silently bypass the very safety it was meant to provide

The plan notes `lib/codex-version-guard.sh:37` returns INCOMPATIBLE under `CLAUDECODE=1`, `env -u CLAUDECODE` escapes it, and the broker does not go through this guard. Risk R6 says record `codex --version` and pin only if regression appears. That does not resolve the design gap: two Codex invocation paths now have different compatibility behavior, and the chosen production route bypasses the repo's guard entirely.

If 0.133.0 is known-good, the broker path should enforce or at least check it. If the guard is stale/wrong under `CLAUDECODE`, the plan should fix the guard. Recording a version after the fact is not a safety control.

Concrete fix: make compatibility part of #2804 scope:

- Add a broker preflight that records and validates `codex --version` against a supported range.
- Fix or document `CLAUDECODE` guard semantics so raw review scripts and broker behavior do not diverge silently.
- Acceptance criterion: both raw `codex exec` review path and broker write path report the same compatibility decision or an explicitly documented reason for divergence.

### MAJOR: Legal/security scan criterion is attached only to #2802, not to #2804's own privileged scripts and docs

Acceptance criterion 6 requires `scripts/legal/legal-sanity-scan.sh` on the #2802 diff. But #2804 itself will add `scripts/install/codex-bwrap.aa`, `scripts/install/setup-codex-sandbox.sh`, handoff docs, memory/documentation changes, and a pilot report. Those are the artifacts that introduce privileged host changes and potentially hardcoded local paths, usernames, machine facts, or unsafe command examples.

Concrete fix: add #2804-specific verification:

- Run legal/security scan on the #2804 diff before moving to plan-review/approval.
- Add shellcheck or equivalent lint for the installer.
- Add explicit no-secrets/no-client-identifiers check for config and report artifacts.
- Keep #2802 legal scan in #2802's plan, not as the primary #2804 safety gate.

### MINOR: The profile target assumes `/usr/bin/bwrap` is stable across all target machines

Risk R1 calls `/usr/bin/bwrap` stable. That is true for the validated host but not guaranteed across package managers, distro variants, Nix, Homebrew-on-Linux, or future Codex packaging. The plan says npm/Codex relocation does not matter because bwrap is system path, but the installer should prove that rather than assume it.

Concrete fix: installer should resolve `command -v bwrap`, require it to be `/usr/bin/bwrap` or generate a profile for the resolved path only after explicit user confirmation, and write the detected path into the report. If AppArmor profile path syntax cannot safely support the detected path, fail closed with a clear message.

### MINOR: The plan says memory is already updated before the plan is approved

Scope item 2 says `feedback_codex_sandbox_write_blocked` memory is "already updated". For an issue plan still awaiting review and user approval, pre-updating durable memory can bake in unapproved or still-contested conclusions. This also weakens review because the memory artifact may now assert Option 6 as settled before the approval gate.

Concrete fix: mark memory update as a planned post-approval artifact, or revise the memory entry now to say "validated draft route pending #2804 approval" until the gate clears.

### MINOR: "No privileged host change beyond..." is not enough rollback evidence

Acceptance criterion 7 says no privileged host change beyond the one-time AppArmor/config step. Config mutation under `~/.codex/config.toml` is not privileged, but it is still environment mutation. The AppArmor change needs a rollback procedure and proof that it does not require runtime sudo. The plan says reversible in risks but does not define the actual reverse command or expected validation after reversal.

Concrete fix: add documented rollback:

- Remove/disable `/etc/apparmor.d/codex-bwrap`.
- Reload AppArmor.
- Restore previous `~/.codex/config.toml`.
- Verify `bwrap --unshare-user` fails again if the profile is removed and succeeds after reinstall.

## VERDICT

REJECT
