## Findings

1. **`OGManufacturing` is silently dropped from `dev-primary` runtime access without acknowledgement.** Live `config/workstations/registry.yaml:29-35` includes `OGManufacturing` in `machines.dev-primary.repos`, and line 44 includes it in `telegram_hermes.data_access_profile.repos`. The proposed `repos` list (plan lines 83-101) and `tier1_baseline` buckets (lines 110-141) exclude `OGManufacturing` entirely (no `required`/`optional`/`non_tier1_machine_access_current`/`historical` membership). Acceptance criterion line 290 then requires `data_access_profile.repos` to "contain no unclassified repo," which forces `OGManufacturing` to be removed from dev-primary dispatch routing. This is a behavior change for telegram_hermes — not just a registry tidy. Plan §"Risks and Open Questions" (lines 313-317) does not mention it. Either classify `OGManufacturing` (e.g., `reference_only` or new bucket) or surface the deliberate routing removal explicitly with rationale tied to #2770.

2. **`placement_rules.*_policy` schema is declared but never consulted by the pseudocode.** Lines 142-156 define `direct_nested_git_policy: error`, `optional_absence_policy: warning`, `dirty_policy.*: warning`, `ahead_policy.*: warning`, etc. The pseudocode (lines 186-199) hardcodes "missing required → blocker; missing optional → warning; nested → blocker" without reading these fields. Two sources of truth that cannot disagree at write-time but can drift at any future revision. Either wire the policy table into the checker (table-driven) or strip the unused fields. As written, the policy block is decorative.

3. **Readiness merge breaks the `status`/`overall_status` contract.** Pseudocode line 209 does `host_entry["dispatchable"] = host_entry["dispatchable"] and host_entry["repo_placement"]["dispatchable"]`. Live `scripts/readiness/telegram_hermes_readiness.py:418-420` computes `overall_status` from each host's `status`, not from `dispatchable`. If `repo_placement.dispatchable=false` only flips `dispatchable` without also appending to `failures` and degrading `status` to `"fail"`, the report can emit `overall_status="pass"` with `dispatchable=false` on the same host — contradictory. The plan must specify the `failures`/`status` update path explicitly, not just the `dispatchable` AND-merge.

4. **The checker's machine binding is undefined.** Pseudocode line 165 asserts `machine.hostname == "ace-linux-1"`, but the checker has no input contract: does it iterate all machines in the registry, select `dev-primary` by registry key, or resolve by `socket.gethostname()` (existing pattern at `telegram_hermes_readiness.py:96-97`)? If run from `ace-linux-2` (dev-secondary) the assertion blows up; if run from CI it has no machine identity. This affects whether `tier1_baseline` is per-machine or only for `dev-primary`. The Files-to-Change table lists exactly one checker file — implying one machine — but registry has 6 machine entries. Either constrain scope explicitly to `dev-primary` and gate the assertion behind a `--machine` arg, or generalize `tier1_baseline` schema across machines.

5. **Inventory table omits `agent-worktrees` sibling.** `ls /mnt/local-analysis/` shows `drwxrwxrwx ... May 20 18:34 agent-worktrees` as a sibling under `tier1_repo_root: /mnt/local-analysis`. The plan's verified inventory table (lines 22-40) lists 17 repos but does not enumerate `agent-worktrees`. Under the proposed `unknown_sibling_git_policy: warning`, the checker would either emit a warning (if `agent-worktrees/.git` exists) or remain silent (if it's a non-git infra dir). Plan must either (a) verify and document that `agent-worktrees` has no `.git`, OR (b) add an infrastructure-directory allowlist to placement_rules — pseudocode line 193 says "repo != infrastructure directory" without defining that set.

6. **`test_checker_is_readonly` is unfalsifiable as stated.** Line 248 says "Checker never calls clone/fetch/pull/push/mv/rm/delete/sync." A static grep of the source file is brittle (`subprocess.run(["git", ...])` constructed at runtime evades it) and a no-mutation runtime check requires either filesystem snapshot diff or an `unshare`/`fakeroot` sandbox. Plan needs an explicit method — e.g., `monkeypatch subprocess.run` to assert no `git fetch|pull|push|clone` or `mv|rm` invocation, OR strace-equivalent — otherwise this AC always passes vacuously.

7. **`inventory_timestamp_utc: now` makes the readiness payload non-deterministic.** Pseudocode line 206 emits a wall-clock timestamp into the readiness payload. Test `test_readiness_payload_adds_host_scoped_repo_placement` (line 249) cannot snapshot the field without clock injection; existing `telegram_hermes_readiness.py` does not currently inject a clock. Either inject `now` via a fixture or omit `inventory_timestamp_utc` from snapshot comparisons explicitly. Otherwise the test is flaky.

`★ Insight ─────────────────────────────────────`
- The plan's strongest defect class is **decorative schema fields** — `placement_rules.*_policy` looks like a policy table but the checker doesn't read it. Configuration that no code consumes becomes lying documentation within one revision.
- The readiness payload has two near-orthogonal axes (`status` ∈ {pass, warn, fail}, `dispatchable` ∈ {true, false}) and the plan only updates one of them. Whenever you AND-merge a new gate into a downstream field, audit every consumer of every sibling field — `overall_status` aggregation is computed from `status`, so leaving `status` untouched silently drops the new gate from the rollup.
- The `OGManufacturing` removal is a representative "boundary set" defect: when a refactor introduces classification buckets, any in-scope live entry that ends up in none of them is implicitly *removed* by membership-completeness assertions downstream. The fix is to require the new schema to be a **partition** of the existing live set, surfaced as an explicit AC, not derived as a side-effect of disjointness.
