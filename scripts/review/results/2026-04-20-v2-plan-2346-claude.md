## New v3 findings

### D1 MINOR — Internal path inconsistency between gating-table and Files-to-Change / Note / tests

- **Evidence:** Line 135 (Gating mechanism table row a, RECOMMENDED) specifies `/prospects/<sha256-hash-of-(prospect-id + salt + date)>/index.html`. Lines 511-512 (Files to Change) + 515 (Note) + 584-585 (tests) + 622-623 (acceptance) all specify `/private/<hash>/<slug>.html`. Line 515 explicitly notes "`/private/` (not `/prospects/`) is chosen so the `Disallow` rule in `robots.txt` matches a single top-level path" — i.e. v3 changed the prefix but **forgot to update the table at line 135**.
- **Severity:** MINOR. An implementer reading line 135 would create `/prospects/`-prefixed files; the robots.txt rule `Disallow: /private/` would not match; gated reports would be crawler-indexed. The acceptance test at 622 would catch this on deploy, but the defect is in the plan, not implementation.
- **Fix:** one-line edit at line 135 — change `/prospects/` → `/private/` and `index.html` → `<slug>.html`.

### D2 MINOR — Sidecar schema `fallback_code` enum contradicts prose on which codes trigger logging

- **Evidence:** Line 459: "Every fallback application **must be logged** in `docs/gtm/deliveries-log.md` … with the fallback code (**F2/F3/F5**), and the adapter … must emit a structured JSON record to a … fallback-audit sidecar". This enumerates F2/F3/F5 (omitting F1 and F4). Line 472 sidecar schema: `"enum": ["F1", "F2", "F3", "F5"]` — this INCLUDES F1 but omits F4. Two issues: (a) F1 is "refuse + email back, no report" — if F1 triggers sidecar logging per the schema, the prose at 459 must be revised; (b) F4 "clarify" also produces no report but behaviourally is a fallback decision — if F2/F3/F5 are logged then F4 should logically also be logged. The prose, the schema, and the matrix (line 446) disagree on the logging domain.
- **Severity:** MINOR. Easy to resolve either way (pick one): (a) "all fallback decisions log, enum = F1-F5"; OR (b) "only report-producing fallbacks log, enum = F2,F3,F5" and strip F1 from schema enum.
- **Fix:** reconcile line 459 prose, line 472 schema enum, and the matrix at 446 on one rule.

### D3 MINOR — Cross-repo sequencing not acknowledged for aceengineer-website modifications

- **Evidence:** `ls -la aceengineer-website/.git` → separate git repository (own `.git` directory). `git ls-files | grep -c '^aceengineer-website/'` → 0 files tracked in workspace-hub. Lines 511-512 prescribe `Modify aceengineer-website/robots.txt` and `aceengineer-website/vercel.json` without acknowledging these land in a SEPARATE git repo, requiring a separate PR, separate CI, and separate deploy to Vercel before the acceptance test at line 622-623 (`curl https://aceengineer.com/robots.txt`) can pass. The "Upstream Dependencies" subsection at lines 666-671 analyzes #2342/#2343 sequencing but misses the aceengineer-website deploy dependency.
- **Severity:** MINOR. The v3 plan IS an improvement over v2 (which didn't list the file changes at all) but doesn't explain the cross-repo mechanics. An implementer could reasonably commit the file changes and then be surprised when acceptance tests fail until Vercel redeploys.
- **Fix:** add a line to Upstream Dependencies naming `aceengineer-website` as a separate repo requiring its own PR + deploy; optionally reclassify acceptance criteria 622-623 as "post-deploy verification" vs "implementation-complete".

### D4 MINOR — Dual delivery state machine missing transition: DELIVERED_EMAIL_ONLY → DELIVERED

- **Evidence:** Lines 150-154 define state transitions for `DELIVERED`, `FAILED_EMAIL`, `DELIVERED_EMAIL_ONLY`, `UNPUBLISHED`, and item 5 ("Late URL publish") covers the happy case of URL-retry-within-backoff-window eventually succeeding. But: if retry is EXHAUSTED (line 152 "Retry URL publish 3×. On persistent failure, state = `DELIVERED_EMAIL_ONLY`"), and later an engineer manually re-publishes the URL (e.g. Vercel outage resolved next day), the plan does not define whether state transitions `DELIVERED_EMAIL_ONLY` → `DELIVERED` or stays at `DELIVERED_EMAIL_ONLY` with a delivery-log amendment. Line 155 delivery-log schema says "appended never mutated" — so by construction the state can never be "upgraded" after the row is written. This contradicts a plausible real-world recovery flow.
- **Severity:** MINOR. Resolvable by either (a) appending a SECOND row on late publish with a new state `DELIVERED_LATE`; or (b) allowing the `state` field to be the latest-of-N rows under the same `prospect_id + demo` key. Not in the plan.
- **Fix:** add one paragraph defining the late-manual-publish recovery — 3 sentences.

### D5 TRIVIAL — `fallback_code` sidecar enum excludes `F4` without explanation

- **Evidence:** Line 472 enum `["F1", "F2", "F3", "F5"]` — F4 "clarify" is absent without explicit rationale. Reader must infer "F4 produces no report, therefore no sidecar". Plausible but not stated.
- **Severity:** TRIVIAL. One-line comment in the schema header would resolve.

### D6 TRIVIAL — "four authorized fallbacks" phrasing at line 434

- **Evidence:** Line 434 reads "The SOP allows **four** authorized fallbacks in addition to 'refuse and email'" — mathematically correct (F2+F3+F4+F5 = 4 non-refuse, plus F1 refuse = 5 total), but visually jars against the Revision History line 15 "reconciled to 5 authorized fallbacks F1-F5" (Codex M7 fix).
- **Severity:** TRIVIAL — not wrong, just ambiguously worded.
- **Fix:** rephrase line 434 as "five authorized fallbacks (F1 refuse + F2-F5 fix-paths)".

### D7 TRIVIAL — Matrix row "Numerical failure / F2 ALLOWED if pre-auth AND root cause is vessel" still lacks root-cause-detection protocol
