## Findings

1. **Test assertion field casing is assumed, not verified.** Plan §Pseudocode and §TDD Test List assert `generated["LineTypes"][i]["Name"]`, `OuterDiameter`, `InnerDiameter`, `MassPerUnitLength`, `WaveType`, `WaveHeight`, `EndAConnection`, `WaterDepth` — all PascalCase, OrcaFlex-native style. The plan does not cite a line in `spec_to_single.py` that proves the converter emits these keys under those exact spellings. The spec YAML uses snake_case (`outer_diameter`, `mass_per_length`). If `SpecToSingleConverter` currently emits anything other than exact OrcaFlex keys (e.g., leaves some spec-level snake_case for unknown sections, emits `MassPerUnitLength` vs `MassPerLength`), the entire TDD list fails on first run. Plan should add a retrieval-verification task: *"Before writing tests, read `spec_to_single.py` and record the exact output-key contract, then freeze test assertions against observed names."*

2. **Converter invocation signature is slightly misstated.** Plan §Pseudocode line `SpecToSingleConverter().convert(source, target)` uses positional args. `test_spec_conversions.py` lines 89-95 and 100-101 show the public API is `converter.convert(source=spec_file, target=output)` with keyword arguments. Minor, but a code-reading reviewer will flag this as "plan does not match current API".

3. **semantic_diff helper behavior for ordered YAML lists is unspecified.** Plan §Pseudocode shows `semantic_diff(left_dict, right_dict, taxonomy_rules) -> list[Diff]` but never states how list elements are aligned. OrcaFlex `WaveTrains`, `LineTypes`, `Lines`, `Currents` are lists keyed by `Name`. If the helper aligns by index, a deliberately-reordered LineTypes list would produce spurious Category D diffs; if by `Name`, the helper needs name-key heuristics per list path. Neither is stated. This is a correctness gap in the plan's deliverable, not a nice-to-have.

4. **Category B "OrcaFlex defaults registry" is a hand-wave.** Plan §Taxonomy says Category B includes "raw_properties fields that are OrcaFlex defaults for an unset value". There is no listed default registry, no citation for where those defaults come from (OrcaFlex 11.6 docs? reverse-engineered from native YAMLs?), and no mechanism for the test to know that a given field is a Category-B default vs a Category-D drift. On first real diff run this will collapse into "everything not in A/C becomes D" or "everything not strictly D becomes B" — neither is a meaningful gate.

5. **Roadmap readiness promotion has no test-enforced invariant.** Plan §Acceptance Criteria line "Roadmap lazy-wave riser moved from Partial but high-value into Ready now" is a doc-edit diff — there is no automated check that the promotion was made, and no regression that prevents it from silently being reverted by a future roadmap edit. At minimum, the plan should add a lightweight doctest or grep-based CI check that asserts the roadmap "Ready now" block contains "OrcaFlex lazy-wave riser".

6. **No test exercises `SpecToModularConverter` against A05.** Plan scopes forward fidelity to `SpecToSingleConverter`. Issue #2456 uses the phrase "semantic roundtrip / semantic diff harness"; modular is the canonical on-disk forward output per roadmap (`master.yml` + includes). Proving A05 semantic fidelity on *only* the single-file path and not modular leaves half the forward contract unproven. Plan should explicitly scope this in or scope it out with a reason; current text ignores the choice.

7. **Sandbox-blocked cross-provider review + self-approval risk.** Memory feedback_never_offer_to_self_label_plan_approved applies here. The plan correctly says it will not self-approve. But the *next* agent that reads this review must know: only one provider was available, and it was the same model family that wrote the plan. The review artifact must carry that provenance explicitly (this file does — flagged to preserve when the plan-review-fanout is rerun from a less-restricted session).

8. **Plan index row is left as "main session will add".** Plan §Files to Change lists `docs/plans/README.md` as forbidden in this worker. That is correct per the worker write-boundary. But until the README row exists, README-driven audit scripts (per `iterative-plan-hardening-with-adversarial-waves` SKILL) will classify #2456 as a missing-plan item even though the plan file is committed. Plan should explicitly flag this governance hand-off and list which downstream agent is expected to pick it up, or the check will fire as a false positive.

9. **Category-C tolerance may be too tight for `198.623920105366`.** Plan §Taxonomy sets relative tolerance 1e-6 for Category C. The A05 Lazy Buoyed `mass_per_length: 198.623920105366` is at ~15 significant digits, which is right at Python float64 precision. A YAML round-trip may drop the last digit. `1.06e-8` drift is possible even on a same-machine pure-YAML roundtrip. Recommend tightening the tolerance spec or flagging it as "may need relaxation on first empirical run".
