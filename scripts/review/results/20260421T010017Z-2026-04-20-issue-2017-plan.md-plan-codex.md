### Verdict: MAJOR

### Summary
The plan is materially stronger than earlier versions and most core decisions are now explicit, but it still has a few blocking specification gaps around ownership/scope boundaries, multi-account identity, and test/acceptance criteria alignment. Those gaps are small enough to fix in-plan, but they should be fixed before approval because they affect implementation handoff and correctness.

### Issues Found
- [P1] Critical: Thread identity is underspecified for a 3-account workflow. The plan keys state and idempotency on `thread_id`, but Gmail thread IDs are account-scoped in practice; without an explicit `(account, thread_id)` primary key in the JSONL/snapshot/schema/tests, state collisions and incorrect reactivation are possible across accounts.
- [P1] Critical: Ownership boundaries between `#2017`, `#2024`, and `#2026` are still blurred. This plan says `#2017` does not produce pipeline code, but it also creates `tests/email/test_queue_state.py` and defines behavior that `#2026` is described as implementing. That leaves unclear which issue owns the state read/write logic, the snapshot rebuild path, and the test harness needed to make those xfail contracts executable.
- [P2] Important: Acceptance criteria still mix plan artifacts with implementation/integration outcomes in a way that can block closure for reasons outside this issue’s scope. `uv run pytest` full-suite pass and “all 3 v2 verdicts are APPROVE or MINOR” are governance/integration gates, not direct deliverables of the design/config work; they should be separated into approval gates vs completion criteria.
- [P2] Important: The concurrency design names locking and atomic rename, but the test matrix does not cover the highest-risk failure modes: concurrent appenders, stale lock recovery, snapshot/log divergence recovery, and duplicate transitions from overlapping inbound+sweep activity. Those are central to D1 and should have explicit contract tests, even if initially xfail.
- [P3] Minor: Unknown-sender fallback is defined, but the plan does not state whether sender matching is by full email, domain, subdomain normalization, or plus-address variations. That leaves routing/schema lookup behavior ambiguous and can create drift between `email-routing.yaml`, spam rules, and schema selection.

### Suggestions
- Add an explicit identity contract everywhere: primary key = `(account_id, thread_id)` and include `account_id` in JSONL entries, snapshot schema, fixture filenames, idempotency rules, and pseudocode.
- Split responsibilities cleanly: `#2017` should own design docs, schemas/configs, fixtures, and contract tests; `#2026` should own queue-state storage/read-write implementation; `#2024` should own pipeline orchestration/extraction flow. Reflect that split in the dependency table, files-to-change list, and acceptance criteria.
- Separate approval gates from issue completion criteria. Keep cross-review verdict quality and maybe full-suite pass as pre-merge gates, but make issue acceptance focus on the artifacts this issue actually produces.
- Add explicit contract tests for concurrent writers, stale lock timeout behavior, snapshot rebuild when log is newer, and duplicate reply/sweep races.
- Define normalization rules for sender matching and schema lookup: exact sender vs domain, lowercase normalization, subdomain handling, and default behavior when multiple rules match.

### Questions for Author
- What is the canonical account identifier for the 3-account workflow, and will every queue-state record be keyed by `(account_id, thread_id)` rather than `thread_id` alone?
- Which issue is the single owner of the queue-state read/write implementation: `#2017` or `#2026`? Right now the plan implies both.
- Do you want full-suite pass and cross-review verdict quality to be formal acceptance criteria for `#2017`, or should they be documented as merge/approval gates outside the artifact completion checklist?
