### Verdict: MAJOR

### Summary
Solid T2 plan with strong resource intelligence, clear TDD list, and well-scoped deliverables. Two issues warrant changes before approval: (1) the idempotency contract's `last_generated` timestamp is incompatible with a reliable regenerate-drift CI check on the committed artifact, and (2) the pseudocode assumes llm_wiki.py's frontmatter helpers are importable without confirming module shape or listing a refactor step. Several thresholds and performance expectations are also under-specified.

### Issues Found
- [P1] Idempotency/drift tension: the plan states the committed portal must be regenerated and drift-checked (risk #4, deferred CI follow-up), but the contract carves out a mutable `last_generated:` YAML line. A drift check against the committed artifact will then need either (a) line-excluded diffing, or (b) removal of the timestamp in favor of a content hash. Decide now — otherwise the first nightly/CI run perpetually diffs and either forces noisy churn commits or silently defeats the drift check.
- [P2] Unverified reuse assumption: pseudocode comment says `reuses llm_wiki.py helpers` and the Resource Intel block lists frontmatter schema constants, but nothing confirms `parse_frontmatter` (or equivalent) is an importable top-level function vs. a private CLI-only helper inside `llm_wiki.py` (1,465 lines). If it is not importable as-is, a refactor/extract step is missing from Files-to-Change and TDD list.
- [P2] Threshold metric ambiguity: the plan uses page counts (e.g. marine-engineering ~19,200 pages vs threshold 500) in one place, but the open question proposes `page_count ≥ 500 OR wiki/index.md line count ≥ 2000`, and the small-domain evidence cites line counts of `index.md` (121, 77). Page count and index-line count are different signals; pick one or specify precedence and test fixtures accordingly.
- [P2] Performance budget missing: `rank_by_inbound_link_count` scans every page body for `[[page]]` references against 19,161 sources pages. No budget (wall-clock ceiling, memory, or caching) is stated. A naive implementation may be order-of-minutes or OOM on source bodies, and none of the 8 tests covers large-scale behavior.
- [P2] Standard-regex narrowness: the enum `^(api|dnv|iso|astm|nace)-` omits common marine/offshore publishers present in the corpus (e.g., ABS, BV, LR, IMO, OCIMF). Either broaden to an exhaustive publisher list with evidence from `knowledge/wikis/marine-engineering/wiki/sources/`, or explicitly document the list as initial-and-expandable with a test that pins the expansion contract.
- [P3] CLI surface under-documented: acceptance criteria invoke `generate_wiki_portal.py <domain>` but pseudocode and tests reference `--force`, `--top-tags N`, `--threshold`, and `out_path`. The CLI synopsis should be added to the Deliverable or Acceptance Criteria section so review can confirm flag names and defaults.
- [P3] Tie-breaking undefined for Top Entries: `test_top_entries_ranked_by_inbound_links` asserts an ordered list but the pseudocode does not specify secondary sort (e.g., alphabetical, frontmatter `added` date). Without a tiebreaker, the idempotency test can fail non-deterministically on filesystem ordering.
- [P3] Atomic-write path not tested: pseudocode promises `write_atomic(...)` (temp + rename), but no TDD entry verifies a failed run leaves the prior portal intact. Given the artifact is committed and consumed by docs navigation, a partial-write regression is user-visible.
- [P3] Navigation edit idempotency covers only `wiki/index.md`: `test_portal_link_not_duplicated_in_index` asserts index.md de-dup but there is no matching test for `docs/document-intelligence/README.md` modification, which is also a navigation surface edited by the plan.

### Suggestions
- Replace `last_generated` timestamp with a content hash over the facet payload (e.g., `content_sha256`) so regeneration is truly byte-identical when inputs are unchanged. This makes the deferred CI drift check trivially implementable and removes the carve-out from the idempotency contract.
- Add a preparatory task to Files-to-Change: either (a) extract frontmatter helpers from `scripts/knowledge/llm_wiki.py` into `scripts/knowledge/_frontmatter.py` and import from both, or (b) explicitly verify and cite the current export surface of llm_wiki.py used by the generator.
- Specify a performance budget in the plan (e.g., `generator completes in <90s on marine-engineering with warm filesystem cache`) and add one test that runs the generator against a fixture-scaled-up directory (~2K synthetic pages) to guard regressions.
- Expand the standard-regex publisher list with evidence from `ls knowledge/wikis/marine-engineering/wiki/sources/ | awk -F'-' '{print $1}' | sort -u` and pin the allowed set via a test fixture so future expansion is a deliberate code change, not an invisible filter.
- Resolve the threshold open question before implementation: pick one of (page_count, index_lines), document the rationale, and capture it in `llm-wiki-portal-design.md`. The ambiguity will otherwise surface during code review.
- Add a Top-Entries tiebreaker (e.g., `(inbound_links DESC, title ASC)`) to the pseudocode and reference it in `test_top_entries_ranked_by_inbound_links` to guarantee stable output across platforms.
- Add tests for (a) atomic-write crash safety, (b) `docs/document-intelligence/README.md` link idempotency, and (c) the sources/ aggregate-row rendering (count-only, non-enumerated).
- Add an explicit CLI usage block to the Deliverable section listing flags, defaults, and example invocation — this aligns acceptance criteria with test expectations.
