## Findings

### F1 — MINOR: Scoring rubric mismatch with #2370 sibling (claimed compatibility is inaccurate)

**Severity:** MINOR
**Dimension:** Cross-plan contract integrity

**Claim (plan line 273):** `# Mirrors #2370 rubric: reusable methodology + stable decision value + evidence richness`

**Evidence:**
- **#2375 plan** uses a **0..3 composite score** with three binary increments (`has-patterns` +1, `durable-category` +1, `has-evidence` +1). Single integer output.
- **#2370 plan** uses a **4-dimension × 0-5 rubric** (methodology 0-5, durability 0-5, evidence 0-5, overlap 0-5) producing a weighted composite that ranges [-1.0, +4.0]. Fundamentally different architecture.

The plans share the same *philosophical* dimensions (methodology, durability, evidence) but not the same *numeric contract*. A "mirrors rubric" claim creates a false expectation that score=3 in #2375 is comparable to a composite of 4.0 in #2370. The #2374 plan explicitly references this rubric for merge compatibility.

**Patch recommendation:**
- Replace "Mirrors #2370 rubric" with "Inspired by #2370 promotion dimensions" or "Shares #2370 scoring philosophy but uses a simpler 0..3 binary-increment rubric."
- Document in Risks that the scoring scales differ across siblings and that any future unified ledger merge must normalize scores.

### F3 — MINOR: Pseudocode references three undefined helpers with no TDD coverage

**Severity:** MINOR
**Dimension:** Implementation contract completeness

**Evidence — undefined functions in pseudocode:**
1. `existing_wiki_page_for(entry)` (line 260) — decides extend-vs-create by checking if a wiki page already covers this entry. **Not defined anywhere** in the pseudocode, not in the TDD test list, and contradicts line 39: "Wiki-candidate routing identifies *target* wiki domains by category rule, not by reading existing wiki content."
2. `DURABLE_CATEGORIES` (line 277) — a constant used in scoring. **Not defined** — no list of which categories count as "durable." Not in the TDD test list.
3. `route_engineering_subdomain(subcategory)` (line 286) — routes engineering subcategories to finer domains. **Not defined** — no pseudocode body, no TDD test case for subcategory routing.

The test `test_wiki_extend_vs_create` (line 348) tests the *output* but its input says "mocked existing-page lookup" — this confirms the helper needs a wiki-page index lookup, which is potentially a nontrivial I/O dependency.

**Patch recommendation:**
- Define `DURABLE_CATEGORIES` explicitly (e.g., `{"engineering", "data", "harness"}`) in the pseudocode or document that it will be derived from existing `categorize_uncategorized.RULES` categories.
- Either (a) simplify `existing_wiki_page_for()` to a static mapping/heuristic (no I/O) or (b) acknowledge the wiki-index dependency and add a TDD test for it.
- Add stub pseudocode for `route_engineering_subdomain()`.

### F5 — LOW: `classify()` function name vs pseudocode `apply_rules()`

**Severity:** LOW
**Dimension:** Implementation contract accuracy

**Evidence:**
- Plan pseudocode line 223: `cat, sub = apply_rules(title.lower(), rules)`
- Actual function in `categorize_uncategorized.py` line 218: `def classify(title: str) -> tuple[str, str]:`
- The actual function does `title.lower()` internally; the pseudocode passes a pre-lowercased title

The pseudocode implies the implementer will write a new `apply_rules()` function, when in fact they should import and call `classify()` directly. Minor naming mismatch, but could cause confusion during implementation.

**Patch recommendation:** Change pseudocode to `cat, sub = classify(title)` and note the import: `from categorize_uncategorized import classify`.

**Dimension:** Schema contract drift

**Evidence:**
- #894 architecture plan (line 165) defines `completed_at` as: `ISO8601 | ✅ | When the WRK was archived (replaces learned_at)`
- The #2375 plan's pseudocode for `normalize_raw_record()` sets `completed_at: None` (line 228) because raw records have no timestamp

The plan correctly identifies that raw memory-migration records have no timestamp, but doesn't flag the schema deviation from #894's "required" designation. The normalization report should explicitly call out how many entries have `completed_at: None` as a field-fill-rate metric.

**Patch recommendation:** In the Acceptance Criteria, add: "Field-fill report explicitly counts `completed_at` nulls (expected: 21 from memory-migration cohort) and documents this as an accepted deviation from #894's required-field designation."
