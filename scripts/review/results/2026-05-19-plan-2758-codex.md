## Findings
1. Plan omits the template-required embedded evidence block. `docs/plans/_template-issue-plan.md` requires an `### Evidence (embedded verification)` section with issue statuses, file existence, line excerpts, gap proofs, and source count. The plan’s `Resource Intelligence Summary` lists assertions, but it does not embed command output, `ls`, `gh issue view`, line excerpts, or gap proofs. This violates the plan retrieval contract and leaves reviewers unable to verify cited paths or “no existing” claims from the plan artifact itself.

2. The new registry risks becoming a conflicting authority source because the plan does not resolve existing workstation key mismatches. The plan proposes `config/workstations/repo-placement.yaml` with machines like `ace-linux-1` and `ace-linux-2`, while `scripts/readiness/harness-config.yaml` currently defines `dev-primary`, `dev-secondary`, `licensed-win-1`, and `macbook-portable` under `workstations:`. The plan’s “Risk / issue” row says the registry must not drift from setup scripts, but `Files to Change` only says “Update `scripts/setup/aggregate-machine-status.sh` or companion status docs” conditionally. There is no required alias/mapping/migration rule tying `ace-linux-1` to `dev-primary` or `ace-linux-2` to `dev-secondary`.

3. The validator is likely to fail current Hermes config or silently bless the wrong model because the plan does not specify how to handle existing nested tier-1 skill paths. `config/agents/hermes/config.yaml.template` includes `__WS_HUB_PATH__/digitalmodel/.claude/skills`, `__WS_HUB_PATH__/assetutilities/.claude/skills`, and similar paths under the workspace-hub root. The plan’s authority model says sibling tier-1 repos are separate checkouts such as `/mnt/local-analysis/digitalmodel`, and `test_skill_external_dirs_are_classified` expects known sibling repo vs workspace-hub subfolder classification. `Files to Change` does not include `config/agents/hermes/config.yaml.template`, and the plan does not define whether those existing template paths are legacy exceptions, failures, or in-scope fixes.

4. The generated-artifact edit rule is under-specified and bypassable. Plan pseudocode says “fail if direct edit is staged without source changes or regenerated outputs,” and the test list only covers “changed `SOUL.runtime.md` and unchanged sources” versus “changed source and matching generated outputs.” A direct edit plus any source change could pass unless the validator actually regenerates artifacts and compares exact output. The plan does not state that `scripts/agents/build-soul-runtime.sh` or `scripts/enforcement/check-soul-runtime-drift.sh` must be invoked as the authority check.

5. The plan creates `config/workstations/repo-placement.schema.yaml` but does not define a real schema mechanism. The file extension is YAML, while the pseudocode only says `validate schema_version`; no validation tool is named (`yq`, Python parser, JSON Schema, custom Bash/Python), no CI invocation is specified, and `tests/validation/test_agent_runtime_authority.py` is expected to validate registry parsing without an implementation path. This is a design gap for a correctness-critical artifact.

6. The plan overreaches the issue’s requested deliverables by adding a machine × repo × user placement registry and validator without pinning which facts are allowed to be hand-authored. Issue `#2758` asks for an architecture contract and validation/check script; machine placement decisions are explicitly split into `#2754`-`#2757`. The plan’s `Placement matrix model` includes `desired_state`, `canonical_path`, `owner_user`, `allowed_users`, `write_policy`, `data_access`, and `license_access`, which are exactly the decision surfaces in `#2754`-`#2757`. Marking them `decision-pending` mitigates some risk, but the plan still creates the authoritative structure before those issues complete.

7. The report/output artifact is not listed as a file to change even though `emit_report(findings, output)` is part of the validator behavior. The plan says reports will render machine summaries, placement matrices, provider runtime matrices, multi-user risks, and follow-up suggestions, but `Artifact Map` has no report path except review artifacts and no acceptance criterion requiring the generated report to be committed, ignored, or local-only. This leaves provenance and cleanup ambiguous.

## Blockers
- Finding 1: add embedded evidence required by `docs/plans/_template-issue-plan.md`.
- Finding 2: define how the new registry maps to or extends existing `scripts/readiness/harness-config.yaml` workstation identities.
- Finding 3: specify treatment of current Hermes nested tier-1 skill paths before adding a validator that classifies external dirs.
- Finding 4: require deterministic regeneration/drift comparison for generated runtime artifacts, not just “source changed” heuristics.
- Finding 6: constrain registry contents so `#2758` does not pre-decide machine placement work reserved for `#2754`-`#2757`.
