### claude

- **Plan refuses to commit to a single design at plan time; root-cause divergence can silently recur.** Files to Change line 303 says of `setup-cron.sh`: "Use shared rendering semantics **or** keep current behavior under parity tests." Gaps line 44 admits "No shared rendering helper exists." The issue's stated problem (Resource Intel line 18) is precisely that "the legacy installer and transactional installer currently diverge." The plan's preferred path adds a *second* Python expansion implementation in `cron_apply.py` alongside the existing inline-Python expander in `setup-cron.sh:135-140`, and the two TDD tests (`test_setup_cron_dry_run_expands_workspace_hub_and_log`, `test_run_cutover_renders_applied_new_text_...`) exercise each path **in isolation**. No test feeds the same catalog task through both paths and asserts byte-identical output. Divergence — the exact defect being fixed — can reappear undetected. **Blocker resolution:** either extract one shared renderer consumed by both, or add an explicit cross-parity test asserting `cron_apply` and `setup-cron` produce identical command lines for the same task+context. Resolve the `or` in line 303 before implementation.
- **AC#4 contains a near-unfalsifiable escape hatch.** Line 338: "...without `git_probe_timeout` under tracked 30/120 defaults, **or the implementation justifies any remaining timeout as non-required/non-current residue**." Verified timing: `git status --porcelain=v1 --untracked-files=all` on workspace-hub is already 11.81s (plan line 187), 39% of the proposed 30s probe budget. The OR-clause lets any observed timeout be waved through as "residue," so the criterion can pass regardless of outcome. Pin it: "all 6 governed repos on the running host (`registry.yaml:58`) complete with zero `git_probe_timeout`," and require any exception to be a named, per-repo logged justification rather than free-form prose.
- **`test_repo_hygiene_timeout_defaults_are_production_safe` cannot catch an over-large total timeout.** TDD list line 324 asserts defaults are "exactly **or at least** `30`/`120`" and "total timeout remains bounded." Pseudocode line 278-279 states "TOTAL remains below cron-health window safety budget" but no test asserts the upper bound. The hygiene→cron-health gap is 10 min (catalog: hygiene `35 5`, cron-health `45 5`, plan line 41) = 600s; current `TOTAL_TIMEOUT_SEC` default is 480. A regression typo pushing TOTAL past 600 would make hygiene overrun into the cron-health window and go uncaught. Add an assertion `TOTAL_TIMEOUT_SEC < 600` (or < the computed gap).
- **The new "latest evidence line wins" logic is not reconciled with the unchanged generic `ERROR_PATTERNS` scan over the same tail.** `cron-health-check.sh:230-255` scans `tail -n 100` of the hygiene log with patterns including `ERROR:`, `Traceback`, `fatal:`, `No such file or directory` for any task ≠ `cron-health`. The pseudocode `cron_health_check_task_log` (plan 281-292) adds the status-line parse but does not state precedence between the two. Verified mitigant: the hygiene log normally contains only `task=...status=...` lines because git stderr is captured by `run_bounded` (`repo-ecosystem-hygiene-audit.sh:175`), not echoed — so today there is no conflict. But the plan should state this invariant and the precedence explicitly; otherwise AC#6 ("newer WARN/OK clears older ERROR") is silently defeated the first time any future change lets a generic-pattern token (e.g. a leaked `fatal:` or a Python traceback on crash) reach that log alongside an older `status=ERROR`.
- **Plan never cites how `classify_line` buckets bare `VAR=value` env lines**, yet AC#2 and `test_plan_cutover_preserves_workspace_hub_and_log_env_lines_verbatim` (TDD line 321) depend on `WORKSPACE_HUB=`/`LOG=` classifying as preserved/ignore rather than uncataloged (which would make `plan_cutover` abort, per `cron_apply.py:158`). The captured dry-run (plan lines 142-147) empirically shows them in `preserved`, so the behavior holds at HEAD — but the test author needs the exact `classify_line` branch cited to assert the correct bucket and to guard against a future classifier change turning silent preservation into a fail-closed abort.
- **Regex engine is unspecified; "latest match wins" + capture is idiom-dependent.** Pseudocode line 286 gives a POSIX ERE but the existing scan uses `grep -Eq` (`cron-health-check.sh:237`), which yields no ordered last-match/capture cleanly — a bash `[[ =~ ]]` loop with `BASH_REMATCH[2]` is required for "last matching line wins." The regex itself is **verified sound** against the real format (`task=repo-ecosystem-hygiene status=ERROR artifact=...`), so Gemini's portability flag is largely a false positive on Linux; name the engine so the implementer doesn't reach for `grep` and lose ordering.

- Plan still has the OR-shaped dry-run executability contract it claims to have removed. `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:270` says “include rendered `new_text` or `managed_preview`”, test row `:320` expects “`new_text` or `managed_preview`”, and acceptance criterion `:335` repeats “rendered `new_text` or managed preview”. That contradicts the revision claim at `:360` that the OR-shaped path was removed. A preview can diverge from the actual `plan_cutover(...)[new_text]` path in `scripts/cron/cron_apply.py:156-166` and `scripts/cron/cron_transaction.py:356-380`, so this remains an approval blocker.
- The latest-evidence-line plan does not address older generic execution failures in the same append-only hygiene log tail. The plan promises at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:305` that newer `status=WARN`/`status=OK` clears task-level failure, and tests only older `status=ERROR` followed by newer WARN/OK at `:326-327`. But `scripts/cron/repo-ecosystem-hygiene-audit.sh:752-764` emits `ERROR: repo-ecosystem-hygiene execution_failed...` on execution failure, and `scripts/monitoring/cron-health-check.sh:83-92` plus `:226-254` will still scan the last 100 lines for `ERROR:` and mark the task red. The plan needs explicit semantics and tests for “older `ERROR:` execution_failed followed by newer machine-readable OK/WARN”.
- Timeout acceptance is internally inconsistent with the live governed repo set. The plan sets per-probe/per-repo defaults to 30/120 at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:274-279` and acceptance `:338` requires completing across the live governed repo set, but current code keeps total timeout default 480 seconds at `scripts/cron/repo-ecosystem-hygiene-audit.sh:12` and `:39`. The governed set is built from required, optional, and `non_tier1_machine_access_current` buckets in `scripts/cron/repo-ecosystem-hygiene-audit.sh:292-305`; `config/workstations/registry.yaml:65-86` defines 17 total governed repos for `dev-primary`. A 120-second per-repo budget across 17 repos cannot be reconciled with a 480-second total budget without an explicit scheduling/bounding policy. The fallback clause “or justifies any remaining timeout” at plan `:338` is also too loose to prove the fix.
- The setup-cron parity test does not cover the actual selection-contract divergence. The plan calls `setup-cron.sh` the “semantic parity reference” at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:323`, but `scripts/cron/setup-cron.sh:117-122` selects tasks only by `machines`, while `scripts/cron/cron_transaction.py:205-263` selects by role and legacy machine pin with conflict behavior. The proposed test only checks a hostname alias emits hygiene/health entries; it does not include a role-vs-machine conflict fixture proving transactional rendering and setup-cron rendering are being compared over the same selected task set.

### r1-claude

- **Pseudocode reintroduces the stale-tail false positive the existing code explicitly guards against (BLOCKER).** Plan §Pseudocode line 264 marks the task ERROR if `recent_tail has /^task=repo-ecosystem-hygiene .*status=ERROR\b/`. But `cron-health-check.sh:235` scans `tail -n 100` of an append-only daily log (audit emits one evidence line per run via `repo-ecosystem-hygiene-audit.sh:744` `print(...)` → crontab `>>`). The plan's OWN reproduction at `docs/plans/...:178-181` shows a tail with `status=ERROR` (13:23) followed by `status=WARN` (13:27, 13:33) — latest state is WARN, yet the proposed regex matches the older ERROR and flips the task red. This directly contradicts the plan's stated intent (Risk line 343: "only treat the final … evidence line") AND the existing append-only-log protection (`cron-health-check.sh:232-234`). No TDD row covers "older ERROR + newer WARN/OK → not flagged." Must parse the LAST matching evidence line, with a test for it.
- **The executability contract is self-contradicting OR-shaped (BLOCKER).** Deliverable/AC require the crontab to run "without manual WORKSPACE_HUB / LOG edits" (`...:222`, `311`), but TDD rows 296-297 accept *either* concrete command rendering *or* an "emitted env contract," and AC 311 says "or equivalent rendered preview." Current `cron_apply.py:162-166` dry-run returns only `status/preserved/conflicts/selected` — a JSON-only "required env contract" could pass review while applied `new_text` on a clean/no-env crontab still lacks executable paths. The fix must commit to one enforceable mechanism (expand placeholders into the managed command lines is the plan's own recommendation at 341/345) and test the APPLIED `new_text`, not a JSON side-channel. (Consensus with Codex Finding 2.)
- **Plan's rendering helper derives `WORKSPACE_HUB` and `variant` from DIFFERENT sources than `setup-cron.sh`, so "parity" is not achievable as written (MAJOR).** Pseudocode `cron_env_for_machine` (lines 230-237) reads `machine.workspace_root` from the registry and `variant = machine.schedule_variant or "full"`. But `setup-cron.sh:22` sources `WORKSPACE_HUB` from the live env / script location (`$(cd "${SCRIPT_DIR}/../.." && pwd)`), NOT registry, and `setup-cron.sh:54/62/72` defaults the variant to **"contribute"**, not "full". Two concrete divergences the plan's Risk #1 (line 340) hand-waves: (a) a machine with no `schedule_variant` gets `cron-wrapper.log` from the plan vs `/tmp/workspace-hub-cron.log` from setup-cron; (b) on a host where registry `workspace_root` ≠ the actual checkout path (e.g., ace-linux-2's `~/workspace-hub` sparse overlay per global CLAUDE.md), the plan renders a path setup-cron would never produce. A "shared pure helper" cannot unify these unless setup-cron is also refactored to read the registry — which the plan lists only as optional ("If helper extraction changes the source of truth", Files-to-Change line 279).
- **`test_status_short_probe_avoids_pathological_untracked_scan_or_uses_safe_timeout` is unfalsifiable (MINOR).** TDD row line 301 passes if "*either* no full untracked scan for expensive path *or* timeout policy prevents git_probe_timeout." An OR over both candidate mitigations means the test cannot distinguish a correct fix from a no-op that merely keeps the existing timeout path — it pins no behavior. Pick the mitigation first (plan recommends tracked timeout defaults, Risk line 342), then write a test that asserts that specific outcome.
- **No idempotency / second-cutover coverage for the newly-expanded managed block (MINOR).** After the fix, `render_block` emits EXPANDED commands while `catalog_commands` (`cron_apply.py:153`) remains the unexpanded catalog form fed to `plan_cutover`'s uncataloged-abort classifier. The managed block is marker-bounded so a re-run should be safe, but the plan adds no test that a second `run_cutover` over a crontab already containing the expanded block neither aborts as "uncataloged" nor duplicates lines. Given `plan_cutover` aborts fail-closed on classification mismatch, this is worth one explicit idempotency test.
- **Live-timeout AC only probes 2 of N governed repos (MINOR).** AC line 313 names only `workspace-hub` and `digitalmodel`, but the audit iterates all registry-governed repos (`repo-ecosystem-hygiene-audit.sh` ~674-686; registry lists more). A fix can pass the two named probes while a slower sibling still hits `git_probe_timeout` or exhausts `TOTAL_TIMEOUT_SEC=480`. Probe the full governed set, or justify the two-repo sample as worst-case. (Consensus with Codex Finding 4.)

### r1-gemini

- **Unverified File Existence**: Plan §Files to Change, §Artifact Map, and §Acceptance Criteria mandate modifying and testing `scripts/cron/tests/test_validate_schedule.py`. However, this file is explicitly absent from the 'File existence' (`rg --files`) proof in §Evidence. Assume it does not exist.
- **Fatal Execution Mismatch (Python in Bash)**: §Evidence excerpts for `scripts/cron/repo-ecosystem-hygiene-audit.sh` (lines 37, 144) reveal strict Python syntax (`def git_readonly(operation: str...`). Yet the Reproduction proof reveals the live crontab invokes this file using bash (`bash scripts/cron/repo-ecosystem-hygiene-audit.sh`). Running Python via `bash` guarantees a syntax error at execution.
- **Missing CLI Parameter in Live Crontab**: The Reproduction proof demonstrates `cron-health-check.sh` succeeding by explicitly passing `--workspace "$tmp"`. However, the live crontab proof runs the task as `cd $WORKSPACE_HUB && bash scripts/monitoring/cron-health-check.sh` (without `--workspace`). The plan fails to flag or remediate this divergence, risking execution failures.
- **Invalid Bash Regex Syntax**: §Pseudocode for `cron_health_check_task_log` proposes regex `/^task=repo-ecosystem-hygiene .*status=ERROR\b/`. Since `cron-health-check.sh` is a bash script, standard `[[ =~ ]]` does not use `/` delimiters, and `\b` is a non-portable PCRE boundary often unsupported by POSIX ERE. This will cause silent matching failures.
- **Misidentified Shell Script (`setup-cron.sh`)**: §Evidence excerpts for `scripts/cron/setup-cron.sh` (lines 106-140) display Python syntax (`command = command.replace...`). The plan treats it as the "legacy installer parity reference" but ignores that a `.sh` file containing raw Python is either improperly invoked or misnamed, invalidating it as a behavioral reference.
- **Contradictory Environment Preservation**: §Pseudocode `render_catalog_task_for_cron` hardcodes variable expansion (replacing `$WORKSPACE_HUB` with absolute paths). However, `run_cutover` states it will "preserve existing external/ignore lines exactly," which §Evidence shows includes `WORKSPACE_HUB=/mnt/local-analysis/workspace-hub` at the top of the crontab. Preserving the global env variable while hardcoding identical paths inside individual commands violates DRY and creates untracked drift.
