## Findings
1. The plan contradicts the issue’s fixed predicate names. GitHub issue `#2889` defines the three predicates as `memory:read`, `skills:invoke`, and `workflow:gates`; the plan also claims that exact contract at `docs/plans/2026-06-10-issue-2889-provider-harness-parity.md:37`, but the deliverable, constants, row construction, tests, and acceptance criteria switch to `memory`, `skills`, and `workflow` at lines 145, 152-153, 189-190, 216-221, and 234. This can pass the planned tests while failing the issue contract for `harness:<provider>:<capability>` rows.

2. The plan under-tests the issue’s required machine scope. GitHub issue `#2889` acceptance requires Claude/Codex/Hermes sub-rows across 4 active machines. The current roster has four active entries in `scripts/readiness/harness-config.yaml:37-93` (`dev-primary`, `dev-secondary`, `ace-win-1`, `ace-win-2`), but the planned matrix test uses “fixture equality reports for two active machines” at `docs/plans/2026-06-10-issue-2889-provider-harness-parity.md:221`, and the acceptance criteria only require “all 9 provider/capability rows” at line 234. That misses the required 3 providers x 3 predicates x 4 active-machine cells.

3. The collector pseudocode returns from inside the provider loop. `docs/plans/2026-06-10-issue-2889-provider-harness-parity.md:155-161` places `return structured statuses...` inside `for provider in PROVIDERS`, which would emit only the first provider if implemented literally. The acceptance criteria at line 233 only require `dimensions.provider_harness` to exist, not that Claude, Codex, and Hermes all have all three predicates populated.

4. `workflow:gates` is not specified or meaningfully tested. The issue requires `workflow:gates`; the plan only names `evaluate_workflow_gates` in pseudocode at `docs/plans/2026-06-10-issue-2889-provider-harness-parity.md:160` and never defines what counts as per-provider gate parity. The current collector’s gate evidence is Claude/workspace-level behavior probes (`scripts/readiness/collect-equality.sh:156-168`), not provider-specific workflow enforcement. The TDD list at plan lines 215-223 has no test that validates Claude/Codex/Hermes `workflow:gates` semantics.

5. New measured inputs are not wired into the existing stale-checkout dirty allowlist. `scripts/readiness/collect-equality.sh:194-199` says the `MEASURED` allowlist must stay in sync with dimensions probed, but it currently omits `.codex/skills`, `.codex/hooks`, `.codex/settings.json`, `config/agents/codex/AGENTS.runtime.md`, and `config/agents/codex/MEMORY.runtime.md`; `git ls-files` confirms those provider inputs are tracked. The plan proposes provider predicates using `.codex/skills` and Codex runtime/memory files at plan lines 166-168 and 217, but it has no file-change/test item requiring `MEASURED` to include those inputs. Result: provider-harness rows can be computed from dirty/stale provider adapter files while the report still grades as fresh.

6. Gemini scope is internally inconsistent. The issue and plan v1 roster are Claude/Codex/Hermes only (`docs/plans/2026-06-10-issue-2889-provider-harness-parity.md:37`, 145, 152), and the plan recommends keeping Gemini out at line 265. But `test_skill_adapter_rejects_regular_file_pseudo_symlink` includes `.gemini/skills` at line 215. That either expands v1 scope without acceptance criteria or creates an untested side condition unrelated to the deliverable.
