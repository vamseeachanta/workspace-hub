### Issues Found
- [P3] Minor: The 'concurrency-safe master-index merge' claim is narrower than the framing implies. `tempfile.NamedTemporaryFile(delete=False) + os.replace` prevents two writers from clobbering each other's *staging* file, but it does NOT prevent last-writer-wins data loss at the final `os.replace` when two processes read `existing` concurrently (process A reads existing, process B reads existing, A writes, B writes — A's `extended` subtree is lost). `test_master_index_merge_unique_temp_filename` as described only asserts distinct temp paths, not that concurrent ingestions preserve both writers' contributions. Either tighten the claim to 'prevents partial-file observation and stage-file collision; single-writer contract assumed' OR add fcntl.flock on the master path. Given only `ingest_orcina_extended.py` writes the `extended` key and only `ingest-orcina.py` writes sibling keys, the risk is low in practice, but the plan's current wording over-promises.
- [P3] Minor: ZIP path-traversal check `str(safe_path.resolve()).startswith(str(dest.resolve()))` has a known edge case — if `dest` is `/tmp/foo` and a crafted entry resolves to `/tmp/foobar/evil`, the `startswith` passes. The belt-and-suspenders second check (`info.filename.startswith('/') or '..' in Path(info.filename).parts`) mostly covers this, but a cleaner primary is `safe_path.resolve().is_relative_to(dest.resolve())` (Python 3.9+ — available in `uv`-managed envs). Add to `test_training_zip_extract_rejects_path_traversal` a prefix-confusion fixture (entry name that resolves to a sibling dir sharing a common prefix) to lock the stronger check.
- [P3] Minor: Attested-evidence line numbers are internally consistent except the `from bs4 import NavigableString, Tag` at line 137 citation sits two lines after `_convert_element` at line 135 — strongly suggesting that import is inside `_convert_element`'s body rather than at module top. If so, moving `_convert_element` verbatim into `orcina_common.py` will carry that inline import along, which is fine; but step 1 of the Build Sequence should acknowledge that the extraction will copy the function body including nested imports, so nothing is silently left behind in `ingest-orcina.py`.
- [P3] Minor: `iter_paginated` default cap is `MAX_PAGINATION_DEPTH = 20` and fixture-test `test_release_notes_pagination_cap_enforced` fabricates a 25-page chain. The WARN is placed after the `for` loop finishes — which fires only if every iteration found a `next_link` (the loop never `return`s early). Good. But the test's acceptance criterion ('exactly 20 pages fetched') assumes the cap stops consumption; since the generator `yield`s and the consumer (`parse_release_notes`) keeps iterating, this is correct only because the generator returns after emitting the WARN. Add an explicit line to the TDD description confirming the generator exhausts after the cap.

### Suggestions
- Add `safe_path.resolve().is_relative_to(dest.resolve())` as the primary path-traversal gate, demoting the `startswith` variant to a fallback comment. Extend the traversal fixture to include a prefix-confusion case (e.g., entry that resolves to a sibling directory sharing the dest prefix).
- Reword the concurrency-safety claim in Risks and in AC line referring to `test_master_index_merge_unique_temp_filename` to: 'prevents partial-file observation and stage-file collision; a single-writer contract is assumed between `ingest-orcina.py` and `ingest_orcina_extended.py` since they write disjoint top-level keys. If concurrent execution becomes intentional, gate the read-modify-write under `fcntl.flock(master_path)`.'
- In Build Sequence step 1, explicitly call out that `_convert_element`'s inline `from bs4 import NavigableString, Tag` (at line 137 per attestation) moves with the function body into `orcina_common.py`; add a post-extraction grep (`grep -n 'from bs4' scripts/data/llm-wiki/ingest-orcina.py` should now show only at line 26 or be empty if all bs4 use migrated) to the PR checklist.
- Consider adding a `--dry-run` flag to `ingest_orcina_extended.py` so CI smoke-checks can exercise the robots+pagination+merge wiring without hitting the live Orcina site. Plan currently defers this; filing the follow-up issue at PR-merge time would be the natural trigger.
- Add a smoke-run expectation that `jq -e '.extended.categories | keys' data/llm-wiki/index.json` returns exactly `["examples","news","releases","resources","training"]` — this pins the merge contract at runtime, not just in unit tests.
- The `EXAMPLES_MIN_EXPECTED = 40` constant is tuned to real-world expectations (~54 examples); consider making it configurable via env var or CLI flag so a future catalog size change doesn't require a code edit to silence the WARN.
