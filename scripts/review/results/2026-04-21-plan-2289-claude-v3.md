## 5. New v3 defects (MINOR)

### N1. `--format=raw` is not a valid `git diff --cached` option

§Log Schema: "`staged_files_digest` — `sha256(git diff --cached --format=raw)` (content-based; v3)".

`git diff` does not support `--format=raw`. `--raw` is a short-format option (different flag). `--format=` is a pretty-format option for `git log`, not `git diff`. The correct expression for content-hash of the staged changes is one of:

- `git diff --cached | sha256sum` (full unified diff, content-sensitive)
- `git diff --cached --patch | sha256sum` (explicit patch mode)
- `git ls-files --stage <paths> | sha256sum` (index tree hash, no per-file content)

**Required:** Replace `--format=raw` with a correct git invocation. Recommendation: `git diff --cached --patch --no-color | sha256sum` (deterministic, excludes color codes).

### N2. `log_only_pushed_unknown` and `log_only_unresolved` are semantically overlapping

Both verdicts indicate "advisor cannot make a confident decision due to data gap." §Pseudocode emits `log_only_unresolved` when `event.resolved_sha` is None; emits `log_only_pushed_unknown` when `resolve_pushed_state` returns "unknown." `--strict` treats both as exit-1 triggers. Operator-facing distinction is subtle (SHA resolution gap vs remote-tracking-ref freshness gap).

**Required:** Either (a) merge into a single `log_only_observability_gap` verdict with a `cause` field (`unresolved_sha` / `pushed_unknown` / `auth_failed`); or (b) document the operator-facing rationale for keeping three distinct observability verdicts.

### N3. `synthesize_observer_events()` will false-positive on historical commits pre-dating observer install

The observer logs every commit from its install time forward. `synthesize_observer_events()` treats every observer-logged commit with no matching pre-commit event as a `--no-verify` bypass candidate. Commits made BEFORE `install-hooks.sh` wired the observer will appear in the observer log only from install-date onward — so pre-install commits in repo history will NOT appear. But what about commits DURING the transition window, where hooks are partially installed?

**Required:** Add a "observer_started_at" watermark (timestamp of first observer log entry) and skip advisor evaluation for any commit with `committer_date < observer_started_at`. Add `test_advisor_skips_commits_before_observer_watermark`.

### N4. Install-hook wiring must handle single `.git/hooks/post-commit` file

Git only invokes ONE `.git/hooks/post-commit` file per repo. v3's §Files to Change adds TWO post-commit hook scripts (correlator + observer). `install-hooks.sh` must handle chaining — either:
- Generate a single `.git/hooks/post-commit` that calls both scripts in sequence, or
- Use a post-commit multiplexer pattern (common via husky / pre-commit.com).

§Pseudocode and §Files to Change don't specify which. The test `test_install_hooks_wires_post_commit_hooks` asserts both are invoked but doesn't constrain HOW.

**Required:** Specify the chaining mechanism in §Files to Change for `install-hooks.sh`. Recommendation: generated `.git/hooks/post-commit` is a shell script that sources/calls both scripts in fixed order (observer first, then correlator).

## 7. Medium findings

### MM1. `has_been_reverted_via_revert_commit` misses non-default revert messages

The regex `^Revert "` matches git's default revert message. Users who run `git revert --no-edit` or edit the revert commit message lose the `Revert "` prefix. The body-pattern fallback (`This reverts commit <sha>`) catches most cases but not all. Risk: commit reverted via custom-message PR → advisor emits `revert_recommended` for an already-reverted commit → human sees spurious proposal.

**Recommendation:** Acceptable risk (advisory, human declines), but document in §Risks.
