    84|#### M1 — Radial-layer geometry validator is under-specified (continuity vs. monotonicity)
    85|
    86|- **Section:** Pseudocode (`validate radial layers ordered inner-to-outer with nondecreasing diameters`); TDD test `test_invalid_layer_order_rejected`.
    87|- **Why it matters:** For physical layered cylinders, the correct invariant is **continuity**: `layer[i].outer_diameter == layer[i+1].inner_diameter` (within a tolerance). "Nondecreasing diameters" admits gaps (annular voids) and overlaps (negative thicknesses summing). The TDD test as named ("outer diameter smaller than previous layer") only covers the overlap case. Acceptance criterion #4 says "validation catches ... invalid layer order" but the spec underneath is too weak.
    88|- **Required fix:** Replace pseudocode line with: "validate radial layers contiguous inner-to-outer: for each i, `layer[i].outer_diameter == layer[i+1].inner_diameter` (within `1e-9 m` or configurable epsilon); first layer's `inner_diameter == 0` permitted for solid core." Add TDD test row: `test_radial_layer_gap_rejected` (gap between layer outer and next inner) and `test_radial_layer_overlap_rejected` (overlap).
    89|
    90|#### M2 — Geometry under-determination: `thickness OR (ID, OD)` is not enough
    91|
    92|- **Section:** Pseudocode (`validate geometry has either thickness or ID/OD pair`).
    93|- **Why it matters:** Thickness alone does not place the layer radially. For a layer with `thickness=5mm` and no ID/OD anchor, you cannot compute its position; the layer is geometrically meaningless without either an inner-diameter, an outer-diameter, or an inferred chain from the previous layer. Either commit to "thickness valid only when chained from previous layer's OD" or require at least two of {ID, OD, thickness}.
    94|- **Required fix:** Tighten pseudocode: "validate geometry has at least two of {inner_diameter, outer_diameter, thickness}; if only thickness is provided, validator chains from previous layer's `outer_diameter` (or `inner_diameter=0` for the first layer)." Add a note: "If chaining is used, the chained `inner_diameter` is materialized into the model after validation so downstream consumers don't need to re-chain."
    95|
    96|#### M3 — `design_metadata: dict[str, UnitValue | str | number]` undermines the roundtrip acceptance test
    97|
    98|- **Section:** Pseudocode (`CrossSectionDefinition.design_metadata`); TDD test `test_fixture_roundtrip_preserves_family_units_and_provenance`.
    99|- **Why it matters:** Heterogeneous-value dicts are a known Pydantic v2 footgun (`Union[UnitValue, str, float, int]` with no discriminator forces tag-and-type guessing on deserialize). Roundtrip stability of `{value: 5, unit: 'm'}` vs. a bare `5.0` is not guaranteed without a discriminated union or per-field schema. The roundtrip test will be flaky on edge cases.
   100|- **Required fix:** Replace open-ended dict with named optional fields covering the canonical metadata: `water_depth: Optional[UnitValue]`, `design_temperature: Optional[UnitValue]`, `design_pressure: Optional[UnitValue]`, `notes: Optional[str]`. If extensibility is required, gate it behind an explicit `extra_metadata: dict[str, str]` (string values only) so roundtrip is deterministic.
   101|
   102|#### M4 — Unit ontology is undefined; `unit: str` validator is shallow
   103|
   104|- **Section:** Pseudocode (`UnitValue ... validate unit is non-empty`).
   105|- **Why it matters:** Two fixtures emitting `mm` vs. `millimeter` would both validate but downstream consumers (#2515 reports, future ampacity calcs) cannot compare them. The acceptance criterion "Validation catches missing units" is met at the schema level but not at the semantic level. There is also no constraint on dimensional consistency (e.g., a `density` field with unit `mm`).
   106|- **Required fix:** Add either (a) a unit whitelist per field role (length: {`m`, `mm`}, mass-density: {`kg/m^3`, `g/cm^3`}, etc.) loaded from a small constants file, or (b) explicit deferral: "Unit-string normalization is deferred to a future issue; v1 validates only non-empty unit strings. Fixtures use a documented canonical set: `m`, `mm`, `kg/m^3`, `kV`, `kN/m`, `bar`, `°C`." Either way, name the choice and add a TDD test for it.
   107|
   108|#### M5 — Provenance source_type `"calculation"` is self-referential without a back-link
   109|
   110|- **Section:** Pseudocode (`Provenance.source_type ... enum(wiki, standard, vendor_catalogue, project_assumption, calculation)`).
   111|- **Why it matters:** A layer marked `source_type=calculation` with no `derived_from` field is a black-box provenance hole — the audit trail dead-ends. The calc-citation contract at `.claude/rules/calc-citation-contract.md` requires defensible provenance; "calculation" without upstream IDs defeats that.
   112|- **Required fix:** Either (a) drop `calculation` from the enum (force fixtures to cite the upstream standard/wiki page that justifies the value), or (b) require `Provenance.derived_from: list[str]` (list of upstream `source_id`s) when `source_type=calculation`, validated by a `model_validator`.
   113|
   114|#### M6 — 5th fixture (`power_optical_hybrid_umbilical`) is plan-driven scope expansion vs. issue body
   115|
   116|- **Section:** Files to Change; Acceptance Criteria; In-scope list.
   117|- **Why it matters:** Issue #2514 body lists four fixtures: 66 kV inter-array cable, 220 kV HVAC export cable, steel-tube umbilical, concrete-coated pipeline. The plan adds a fifth (`power_optical_hybrid_umbilical`) and includes it in the acceptance criteria as if it were issue scope. This is a defensible expansion (the issue's family list does include "power/optical hybrid umbilical"), but conflating "family in scope" with "fixture required" sets a precedent: future T3 plans can silently expand AC.
   118|- **Required fix:** In the Acceptance Criteria, mark this fixture as "**Plan-added (beyond issue body):** power/optical hybrid umbilical fixture, included to validate the umbilical packed-component schema across two service-role mixes." Either keep it (and document the expansion) or move it to Follow-up Issues.
   119|
   120|#### M7 — `__init__.py` for `cross_sections` not declared with public API surface
   121|
   122|- **Section:** Files to Change (`digitalmodel/src/digitalmodel/subsea/cross_sections/__init__.py`).
   123|- **Why it matters:** Listed only as "Public import surface" with no list of what's exported. For a typed schema package, the public API (`CrossSectionDefinition`, `RadialLayer`, `PackedComponent`, `Provenance`, `UnitValue`, `validate_cross_section`, `load_cross_section_fixture`, `dump_cross_section_fixture`, `ValidationReport`) should be enumerated so downstream consumers (#2515, future OrcaFlex export) know the stable surface.
   124|- **Required fix:** In Files to Change, list the `__all__` contents inline or in a follow-up subsection: `__all__ = ["CrossSectionDefinition", "RadialLayer", "PackedComponent", "Provenance", "UnitValue", "ValidationReport", "validate_cross_section", "load_cross_section_fixture", "dump_cross_section_fixture"]`.
   125|
   126|#### M8 — YAML library choice is not declared; both PyYAML and ruamel.yaml are installed
   127|
   128|- **Section:** Pseudocode (fixture loader/serializer); pyproject ships `pyyaml>=6.0.0` AND `ruamel.yaml>=0.18.0`.
   129|- **Why it matters:** ruamel.yaml preserves comments and key order; PyYAML does not (without a custom Dumper). The "stable YAML/JSON preserving units and provenance" promise in dump pseudocode is achievable with ruamel.yaml but only partially with PyYAML. Roundtrip tests can pass for one and fail for the other depending on key-ordering assertions.
   130|- **Required fix:** Declare the choice in Decisions: "YAML I/O via `ruamel.yaml` (round-trip preserving) for fixture load/dump; JSON via stdlib `json` with `sort_keys=True` and `indent=2`." Justify the choice in one line.
