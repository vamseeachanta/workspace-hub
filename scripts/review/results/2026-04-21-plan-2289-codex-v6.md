### Verdict: MAJOR

### Summary
v6 closes some of the v5 issues, but it is not ready for approval. The main blocker is a new internal contradiction: the taxonomy says any later approval evidence yields `log_only_approved_later`, while the scenario matrix says `bypass → revert → re-approval of plan` must still resolve to `log_only_reverted_later`. The timestamp-based model also remains underspecified for ties and for comparing heterogeneous timestamp sources.

### Issues Found

**MAJOR:**
- Internal contradiction on approval after revert. §Verdict definitions: `log_only_approved_later` applies whenever post-commit approval evidence exists after the bypass. §Scenario matrix: `bypass → revert → re-approval of plan` is forced to `log_only_reverted_later` because plan approval does not un-revert the SHA. Those rules cannot both be normative as written.

**HIGH:**
- Timestamp-based precedence only partially specified. v6 compares marker-file mtime, GitHub label-transition time, and revert commit time but never defines authoritative/comparable sources, exact git timestamp to use, or tie-breaking.

**MEDIUM:**
- Scenario matrix incomplete. Omits `auth_failed`, same-timestamp terminal events, and mixed cases where a terminal event is known but branch state later becomes unreachable.
- `terminal_event_timestamp` semantics not fully clear. Doesn't specify nullability, source-native vs normalized UTC, or heterogeneous evidence type representation.
- Documentation-ownership gap for `FORCE_PLAN_GATE=1`. Plan says #2445 carries it but doesn't name the operative document.
- `git ls-remote --exit-code origin HEAD` overbroad. Treats no-remote / auth-failed / network-failed identically.

### Suggestions

- Narrow `log_only_approved_later` so it only applies when the bypassed SHA remains the live subject of approval at `T_approval`, or explicitly state that approvals after a revert do not count as terminal approval for that SHA.
- Define a single timestamp normalization contract: exact source per event type, UTC serialization, allowed precision, deterministic tie-break order.
- Add matrix rows for `auth_failed`, equal-timestamp conflicts, `safe_paths + later terminal event`, and `terminal event known but later branch deletion/sha disappearance`.
- Clarify `terminal_event_timestamp` nullability and format.
- Name the future operative home for `FORCE_PLAN_GATE=1` documentation.
- Tighten offline rule to apply only to true connectivity absence, not generic `ls-remote` failure.

- Should a post-revert plan approval ever change the verdict for the original SHA, or is approval only meaningful while that SHA remains unreverted?
- What exact document will become the operative source for `FORCE_PLAN_GATE=1` once #2445 is implemented?
