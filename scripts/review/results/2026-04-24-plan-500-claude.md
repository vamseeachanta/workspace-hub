## Findings

1. **MeshFormatType enum mis-stated → format-suffix validator will reject valid formats.** Plan §Resource Intelligence line 21 cites `input_schemas.py:47-48` and summarizes the enum as "`MeshFormatType` enum (GDF/DAT)". Actual enum at `input_schemas.py:44-52` is `{GDF, DAT, STL, MSH, OBJ, AUTO}` — six values. The Pseudocode at plan line 131 then encodes the mis-summary as logic: `if ext not in {"gdf", "dat"}: return warning(unknown_format)`. A body with legitimately-declared `mesh_format: MeshFormatType.STL` (a supported enum value) will be treated as unknown-format and its suffix-vs-declared mismatch check at line 132 will either emit spurious warnings or raise `ValueError("suffix stl ≠ declared stl")` — the latter is possible because line 132 compares `ext != declared_format.value.lower()` which returns `"stl" != "stl" = False`, so no raise — but the prior warning branch triggers. Either way the validator's behavior is wrong by construction, and will invalidate multibody specs that use STL meshes (STL is used by sibling `validate_geometry.py` cited in plan line 23). **Fix:** read the enum at implementation time; extend the allowed set or restrict preflight to GDF only with an explicit narrative note.

2. **Heterogeneous `mesh_format` types break the `MESH_SURFACE_ITER` pattern.** `input_schemas.py:127` types `VesselGeometry.mesh_format` as `MeshFormatType` (an Enum with `.value`), but `input_schemas.py:551` types `DampingLid.mesh_format: str = "gdf"` and line 577 types `FreeSurfaceZoneSpec.mesh_format: str = "fdf"` — plain strings with no `.value`. Plan Pseudocode `validate_format_suffix` at line 132 unconditionally calls `declared_format.value.lower()`. That attribute access raises `AttributeError` on the damping-lid and FSZ branches. **Additional:** `"fdf"` is not a `MeshFormatType` enum member at all — the plan's enumeration at line 20 ("Confirms ... four mesh-consuming surfaces") does not acknowledge this type divergence, and the iterator design glosses over it. **Fix:** coerce strings to enum (or Optional[enum]) inside `MESH_SURFACE_ITER`, add a lookup for `"fdf"`, and stipulate the return tuple's `mesh_format` contract.

3. **`suffix` basename-collision policy omits the backend from Files to Change.** Plan §Risks line 276 acknowledges that option (C) `suffix` "mutates `BodyMeshFileName` writes in backend and requires downstream reference rewrite" — yet `Files to Change` (lines 199–208) does not list `orcawave_backend.py`. The backend at `orcawave_backend.py:240` (and 249) writes `body["BodyMeshFileName"] = Path(geom.mesh_file).name` — the raw basename from the spec. Under `suffix` policy the runner copies to `hull_0.gdf` while the backend emits `BodyMeshFileName: hull.gdf`. OrcaWave then fails to find the mesh and reports a confusing mismatch. The plan offers `suffix` as a user-selectable policy but has not scoped the edit required to make it work.

4. **`parse_gdf_header` line-count contradiction.** Plan Pseudocode line 137 says "read first **5** non-empty lines" then at lines 138–141 enumerates only **4** lines (header / ULEN GRAV / ISX ISY / NPAN). One of the two numbers is wrong; the TDD test `test_parse_gdf_header_valid` at plan line 220 says "parses sample **4-line** header." Under TDD, implementer must pick one; picking 5 (as written in the narrative step) will fail the test written in the same plan.

5. **Cross-platform bypass heuristic is one-directional and unreliable.** Plan §Risks line 280 proposes making preflight advisory "when `spec_dir` resolves to a path with drive letter or `\` separators on non-Windows." On linux CI, a spec with *relative* mesh paths intended for execution on win-1 will show neither a drive letter nor backslashes — the heuristic fails to trigger, and the preflight still runs. Meshes on the win-1 filesystem will be absent from linux, so preflight raises `FileNotFoundError` for specs that would succeed at runtime. The mitigation as written inverts the intended direction. **Fix:** gate on the runner's target platform (e.g., `config.target_platform`) rather than spec-string heuristics.

6. **Iterator registry claim about #501 is speculative.** Plan line 45 describes #501 as "QTF/field-points/irregular-freq" and line 282 then asserts `MESH_SURFACE_ITER` "mitigates" by auto-registering #501's 5th "mesh-consuming surface." Field-points are coordinate lists, not meshes; irregular-freq removal uses interior surface panels (backend flag, not a mesh file). There is no evidence that #501 introduces a 5th *mesh-consuming* surface. The plan asserts decoupling from a gap it has not verified.

7. **`prepare()` short-circuit gap mis-described.** Plan line 17 says "`prepare()` proceeds to `execute()` even when `error_message` is set." Actual: `prepare()` at `orcawave_runner.py:246-288` returns the RunResult and does not call `execute()`. The pipeline step that skips the gate is `run()` at lines 216–244 (`self.prepare(...)` then unconditional `self.execute()`). The claimed gap is real but sited in the wrong method; a reader implementing the short-circuit at the plan's named location (`prepare`) will not close the hole in `run()`. Pseudocode §prepare at plan line 182 doubles down by returning from `prepare` on failure — but `run()` will still call `execute()` after that return unless `run()` is also patched, and `run()` is not in Files to Change-level detail.

8. **Acceptance criterion unverified against actual fixtures.** Plan line 246: "existing tests in `test_orcawave_runner.py:189-233` still pass with new strict default (fixtures point at real meshes)." The plan asserts this without citing the fixture source. If any fixture uses a synthetic `"mesh.gdf"` string without creating a real file (common in unit tests that stub the backend), strict-by-default breaks backward compat. The plan has not produced the fixture audit that this claim presumes.

9. **GDF header "authoritative reference" is a local writer, not a standard.** Plan line 22 cites `gmsh_mesh_builder.py:54-64` as "authoritative reference for GDF header structure." It is the project's own *writer*. Using the local writer as ground truth means any upstream spec divergence (OrcaWave accepts headers the local writer does not emit) won't be caught by the parser. Combined with §Standards line 30 ("WAMIT §3.1: gap (not ledgered)"), the preflight is being grounded in an in-tree round-trip assumption. The plan notes the gap but proceeds without flagging it as a limitation of the preflight's validity domain.

10. **Plan docstring update listed twice in Artifact Map / Files to Change.** Artifact Map line 103 lists `orcawave_runner.py` docstring as "Docs update"; Files to Change row for `orcawave_runner.py` (line 204) also mentions "add path-resolution docstring." Duplicate accounting, not a correctness defect, but cosmetic redundancy that should collapse to one row.

## Blockers

- **Finding 1** (MeshFormatType mis-summary → rejects STL/MSH/OBJ): design must be revised before implementation; implementer following the plan verbatim will produce wrong behavior for STL specs.
- **Finding 2** (heterogeneous `mesh_format` types → `AttributeError` on `.value`): Pseudocode `validate_format_suffix` is broken for DampingLid and FSZ branches. Fix the iterator contract before writing code.
- **Finding 3** (`suffix` policy misses `orcawave_backend.py` edit): offering `suffix` as a user choice without the backend edit ships a silent-corruption path. Either drop `suffix` from the initial scope or add the backend edit to Files to Change.
- **Finding 5** (cross-platform bypass heuristic inverted): implementing the heuristic as written will break linux CI for win-1-targeted specs. Redesign the gate before coding.
- **Finding 7** (short-circuit sited in `prepare`, hole is in `run`): short-circuit must land in `run()` or `prepare()` must signal `run()` to skip `execute()`; plan currently does neither explicitly.

Findings 4, 6, 8, 9, 10 are MINOR — resolve during implementation but not load-bearing.
