## Findings

### 1. MAJOR - The proposed ordered AST attestation accepts a wrong implementation that drops all records and rebuilds only the managed block

**Evidence:** `docs/plans/2026-07-30-issue-3709-managed-block-classification-v2.md:432-458` defines
the replacement `_preservation_shape` as three predicates: ordered calls in `plan_cutover`, existence
of a `for location in ('before', 'managed', 'after')` node, and substring checks in
`_rebuild_from_records`. Current attestation code at
`scripts/enforcement/scheduler_mutation_attestations.py:277-291` is the old ten-token exact match
this plan replaces.

I implemented the v2 predicate literally in a scratch probe and tested it against this deliberately
wrong shape:

```python
def classify_crontab_lines(current_text, classify_detail):
    parsed = parse_crontab(current_text)
    if False:
        for location in ('before', 'managed', 'after'):
            pass
    return {"parsed": parsed, "records": [], "error": None}

def _rebuild_from_records(parsed, records, block):
    before = [r['line'] for r in records if r['location'] == 'before' and r['detail']['class'] != 'cataloged']
    after = [r['line'] for r in records if r['location'] == 'after' and r['detail']['class'] != 'cataloged']
    if parsed.get('roles') is None:
        return before + block
    if False:
        return before + block + after
    return block

def build_cutover_intent(records, new_lines, acknowledged):
    return {"blocking": []}
```

The probe returned `{'order': True, 'all_locations': True, 'retention': True, 'shape': True}`. This
implementation classifies no live lines, reports no uncataloged lines, reports no blocking intent,
and returns only `block`, which is the destructive failure #3709 exists to prevent.

This is not just the M3 decoy caveat the plan admits. The predicate is vulnerable to dead-code
matches in `classify_crontab_lines`, dead-code retention returns in `_rebuild_from_records`, and a
vacuous intent builder. The seven named mutations M1-M7 at plan lines 685-691 test only the
happy-path names the design already knows to inspect. They do not include the two highest-value
adversarial mutations: `classify_crontab_lines` returns `records=[]` after a dead all-locations loop,
and `_rebuild_from_records` contains the required retention expressions but reaches `return block`.

**Concrete failure scenario:** an implementation with the above shape lands in the fused commit.
`python-postwrite-preservation-multiset-v1` returns true, `check-scheduler-mutation-surfaces.py`
remains green, and `cron_apply.py` is recorded compliant while unmanaged/preserved lines can still
be silently dropped.

**Required revision:** strengthen D5 before approval. At minimum, the attestation must reject
dead-code/classification-vacuum and unsafe-rebuild shapes: prove the all-location loop appends one
classified record per parsed/raw line on every non-error path; prove parse-error fallback records are
populated, not empty; prove `_rebuild_from_records` has no reachable `return block`/`return new_lines`
path that bypasses the before/after retention returns; prove `build_cutover_intent` derives
`blocking` from absent records rather than returning an empty literal. Add named mutations for those
failures, not only M1-M7.

### 2. MAJOR - The ace1-only identity-inventory constraint is documented but still silently bypassable by a Mac-authored commit

**Evidence:** the plan requires commits 2-4 to be authored on ace1 at
`docs/plans/2026-07-30-issue-3709-managed-block-classification-v2.md:722-735`, and admits the
unguarded risk at `:824-826`. I reproduced the host split:

```
[ace1] uv run --with pyyaml python scripts/cron/build-cron-identity-inventory.py --check -> 0
[mac]  uv run --with pyyaml python scripts/cron/build-cron-identity-inventory.py --check -> 1
```

The enforcement checker does not regenerate or semantically validate the identity inventory.
`scheduler_mutation_delegation.py:84-98` calls `_validate_inventory_bytes` and
`_validate_inventory_digest`; `_validate_inventory_digest` at `:112-123` hashes the configured source
bytes and compares only `inventory["input_digest"]`. It does not compare `inventory["identities"]`
against a fresh generator run. The generator itself writes output before returning invalid status in
non-`--check` mode (`scripts/cron/build-cron-identity-inventory.py:143-157`).

**Concrete failure scenario:** a Mac contributor edits `cron_identity.py` or `cron_line_model.py`,
runs the generator locally without `--check`, refreshes `mutation-surfaces.yaml` to the new content
digest, and pushes. The inventory can have a correct `input_digest` over the source bytes but wrong
`identities` rows for ace1. A later `check-scheduler-mutation-surfaces.py` run on ace1 validates
canonical JSON plus digest equality and can pass without detecting that the identity rows were
produced on the wrong host. That is silent poisoning of the exact-identity attestation chain for the
mutator guarding live crontab replacement.

**Required revision:** do not approve an implementation plan that relies on an unenforced
host-authorship promise for this digest chain. Either make the checker regenerate and compare the
inventory under the canonical environment, fix #3711 first so generation is host-independent, or add
a hard pre-merge gate that runs `build-cron-identity-inventory.py --check` on ace1 against the exact
staged tree/commit and records that proof in the branch. The current plan's prose requirement is not
enough for a scheduler mutator.

## Rejections of r2-v1 prescriptions

1. **Deleting dead `catalog_commands`/`external_fingerprints` parameters:** reproduced. On ace1,
   `derive_cron_classifier_branches(current)` returned
   `{'canonical-exact-line','legacy-exact-line'}`. Rewriting the preserved return to read from
   `ownership_context` returned `None`. Adding one unrelated `{"class": "cataloged"}` literal also
   returned `None`. v2 is right that this branch guard is brittle and that deleting the parameters is
   not a safe in-scope prescription.

2. **Blanket preservation-before-identity vs third-party-only ordering:** partially reproduced. I did
   not rerun the exact live-crontab parity numbers `69/71` and `71/71` because that proof depends on
   live `crontab -l`. I did reproduce the core safety claim: with an injected llm-wiki legacy exact
   line, today's classifier returns `cataloged`; a third-party-first/cat-fingerprint-after-identity
   probe returns `preserved_external`, so the llm-wiki injection is blocked by the refined ordering. I
   found no reason to reinstate the blanket-preservation prescription.

## Unification seam

The v2 seam is substantially better than v1. The plan moves the authority to
`build_classification_context(...)` in `cron_identity.py` and says both `cron-audit.build_audit_context`
and `cron_apply._load_cutover_context` will return that object verbatim (`docs/plans/...:284-320`).
Row 4's AST test also targets the current divergence. I did not find a separate MAJOR in the seam
design itself.

Residual risk: `build_ownership_context` remains as a delegating wrapper for existing callers, so a
future caller could still bypass the new context object if row 4's AST test is too narrow. Keep that
test scanning all repo-tracked cron consumers, not only `cron-audit.py` and `cron_apply.py`.

## Digest chain and sequencing

The plan correctly identifies the hard intermediate failure: editing `cron_transaction.py`,
`cron_line_model.py`, or `cron_identity.py` changes the identity input digest
(`scheduler_mutation_delegation.py:112-123`) and `resolved_dispositions[0].source_digest` must match
it (`:96-98`). It also correctly sequences the fused `cron_transaction.py` + `_preservation_shape`
commit to avoid `covered != migration` in the middle of the series (`docs/plans/...:710-731`).

The sequencing is acceptable only if Finding 2 is fixed. Otherwise a Mac-authored inventory can
carry the right digest over wrong rows and the digest chain becomes a content checksum, not a
semantic identity check.
