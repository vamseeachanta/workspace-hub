# Codex adversarial plan review — #2486

Verdict: MAJOR

**CRITICAL**
- Severity: CRITICAL. Title: Usage/staleness integration currently violates the read-only artifact-first contract. Evidence: the plan requires `usage tier changes where available from skill-usage-report.py or successor logic` while also requiring the weekly run to stay read-only and artifact-first. Current [`scripts/skills/skill-usage-report.py`](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/skills/skill-usage-report.py) writes `.claude/state/skill-usage-report/YYYY-MM-DD.json` and updates `.claude/state/skill-scores.yaml`, so direct reuse is not read-only and does not stay inside `logs/maintenance/skills-curation/`. Why it matters: this would dirty repo state on the canonical cron path and make v2 not an extension of the current deterministic artifact contract. Concrete fix: make the plan explicitly forbid calling the current writeful script from `skills-curation`; require either a pure read-only library adapter or a new `--read-only --stdout-only` mode first, with tests proving no writes occur outside the redirected audit output root.

**HIGH**
- Severity: HIGH. Title: Auxiliary signal sources do not share one canonical audit universe. Evidence: the plan proposes combining `audit-skills.py`, `skill_eval_ecosystem.py`, `skill-usage-report.py`, and existing duplicate detection, and its own resource summary already notes overlapping scopes and inconsistent runtime behavior. The repo confirms the mismatch: v1 audit excludes `_archive` and `_diverged` and de-emphasizes `_core/_internal`; `skill-usage-report.py` excludes `_archive/_core/_internal` but not `_diverged`; `detect_duplicate_skills.py` excludes `_archive/_diverged` but not `_core/_internal`. Why it matters: counts, deltas, waivers, and “same finding” identity will churn week to week even when the tree is unchanged. Concrete fix: require one canonical inventory builder in `weekly_skills_audit.py`, and require every v2 signal family to consume that inventory or a normalized adapter with documented inclusion/exclusion semantics.

- Severity: HIGH. Title: Several required v2 signal families are still too subjective for a deterministic weekly baseline. Evidence: the plan’s required signals include `description quality/length violations`, `missing related-skill/cross-reference hints`, and `high-risk skills that should be split, wrapped, or consolidated`. Why it matters: those are editorial judgments, not bounded deterministic findings like v1 duplicates/wrappers/leaf collisions. They will turn this from “housekeeping audit” into ongoing taxonomy/content redesign. Concrete fix: trim v2 to measurable signals only, or define exact policy thresholds now for each subjective family so the implementation has no discretion.

- Severity: HIGH. Title: GitHub update and follow-up correlation are not specified tightly enough to prevent noise. Evidence: the plan says default is artifact-only, but also introduces optional weekly issue updates, `follow_up_candidates[]`, `existing_issue_links[]`, and possible future per-finding issue creation with idempotence by `finding_key`. It does not define the dedupe marker, search query, reopen/closed behavior, or how unchanged candidates map to one umbrella issue vs separate issues. Why it matters: the spam risk called out in review question 3 is real unless the contract is exact. Concrete fix: keep #2486 v2 strictly artifact-only plus optional single-comment dry-run/body-rendering only; defer per-finding issue creation and correlation to a separate child issue after several stable weekly runs. If correlation stays in-scope, define the exact marker format and lookup algorithm in the plan.

- Severity: HIGH. Title: Grouping/category findings do not yet have a stable identity model. Evidence: the plan requires deterministic handling for alias drifts such as `workspace_hub_learned` vs `workspace-hub-learned`, `business_admin` vs `business/admin`, and `_archive` vs `_archived`, but only tests that they are detected. It does not define what the `finding_key` is built from for these families. Why it matters: baseline deltas, waivers, and future candidate issue idempotence all depend on finding identity stability. Concrete fix: add a per-family key contract now, for example `classification + alias_family_id + normalized_target + sorted offender set`, and add tests that moves/renames within the same alias family do not create false-new findings.

- Severity: HIGH. Title: Optional GitHub behavior is not reconciled with the current cron dependency contract. Evidence: current `skills-curation` in [`config/scheduled-tasks/schedule-tasks.yaml`](https://github.com/vamseeachanta/workspace-hub/blob/main/config/scheduled-tasks/schedule-tasks.yaml) requires only `python3`, `uv`, and `bash`. The plan adds optional GitHub update behavior but never states that the canonical scheduled path must remain fully GH-free. Why it matters: either the schedule metadata becomes false, or the shared audit script grows a hidden dependency/auth requirement not present on the current cron contract. Concrete fix: state explicitly that the default weekly cron path must not require `gh` or network auth, and add a test proving the default invocation never attempts GitHub access.

**MEDIUM**
- Severity: MEDIUM. Title: Schema migration is still ambiguous between `schema_version` and `policy_version` bump. Evidence: the plan says `schema_version or bumped policy_version`, while also requiring v1 baseline continuity and non-breaking v1 fields. Current v1 baseline loading keys off `policy_version` plus `audit_scope`. Why it matters: this can accidentally wipe delta continuity or cause v2 to compare against the wrong baseline class. Concrete fix: choose one migration mechanism now and define exact compatibility rules, including a test for first v2 run against an existing v1 artifact set.

- Severity: MEDIUM. Title: The blast radius is larger than necessary around a stable cron path. Evidence: the files-to-change table still includes `scripts/cron/skills-curation.sh` and `config/scheduled-tasks/schedule-tasks.yaml`, even though the current wrapper and schedule already match the desired weekly path and the plan says modify them only if needed. Why it matters: unnecessary wrapper/schedule edits increase regression risk for little value. Concrete fix: make `weekly_skills_audit.py`, policy, waivers, docs, and tests the default write set; require a specific contract change before touching wrapper or scheduler config.

**LOW**
- Severity: LOW. Title: The plan should explicitly state that v2 extends v1 sections rather than replacing the existing Markdown/report semantics wholesale. Evidence: the plan says “extend the existing weekly JSON + Markdown artifact” but then defines a new ten-section Markdown layout. Why it matters: this is mostly a reader/consumer clarity issue, not a blocker. Concrete fix: say whether the old sections are superseded, preserved as aliases, or mapped directly into the new section names so downstream expectations stay clear.
