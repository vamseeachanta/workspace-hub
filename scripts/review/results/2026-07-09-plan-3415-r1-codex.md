## Findings
1. Plan preselects the research answer before the proposed scorecard exists. `docs/plans/2026-07-09-issue-3415-landman-pilot-validation.md:109` says the deliverable will “lock” Colorado/Piceance/Rio Blanco, and line 197 requires YAML/HTML to select that outcome. But live issue #3415 lines 7 and 16-18 require the research to choose a jurisdiction/county cluster after comparing TX/OK/CO and deciding federal-acreage relevance. The plan’s tests can be satisfied by hardcoding the desired answer rather than letting sourced scoring determine it.

2. The owner-decision fallback branch is acceptance-critical but untested. The plan says “If Rio Blanco fails a hard public-access/provenance gate” the report will stop for owner decision and present Texas/Midland fallback (`docs/plans/2026-07-09-issue-3415-landman-pilot-validation.md:111`, `:141`, `:197`). The TDD list only asserts a complete selected pilot (`:180`) and does not define the required YAML/HTML shape, status, source ledger, or parity checks for `owner_decision_required`. That leaves the stated fail-closed behavior unverifiable.

3. The Garfield dependency is underspecified. The plan says Garfield remains conditional “until worldenergydata issue 914 verifies it” (`docs/plans/2026-07-09-issue-3415-landman-pilot-validation.md:140`, `:181`, `:231`), but live `worldenergydata#914` only requires “priority county selection logic” and “for each priority county” coverage; it does not name Garfield or Rio Blanco, and it is blocked by `worldenergydata#911` (issue body lines 15-23). The plan needs a Garfield-specific dependency condition or an explicit rule that Garfield stays excluded unless a named Garfield evidence row exists.

4. Closeout review criteria conflict with repo policy. The plan requires “at least two providers before issue close” (`docs/plans/2026-07-09-issue-3415-landman-pilot-validation.md:205`), while `docs/standards/AI_REVIEW_ROUTING_POLICY.md:27-32` says all three agents review plan-stage and code/artifact-stage work by default, with reduction allowed only when explicitly scoped down or unavailable (`:34-42`). The plan should require all three by default and document any unavailable provider.

5. The mandatory completeness gate is absent from acceptance criteria. `.claude/skills/coordination/issue-planning-mode/SKILL.md:21-27` requires Cross-review → Completeness gate → Close, including a completeness score, report, issue stamp, and `status:completeness-verified`. The plan’s closeout criteria stop at legal scan and provider review (`docs/plans/2026-07-09-issue-3415-landman-pilot-validation.md:204-205`), so an implementer following the plan can still violate the required issue lifecycle.
