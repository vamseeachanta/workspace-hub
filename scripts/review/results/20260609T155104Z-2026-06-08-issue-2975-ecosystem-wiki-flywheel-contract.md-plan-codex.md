### Verdict: MAJOR

### Summary
The plan is much stronger than prior rounds, but it is not implementation-ready because several scope boundaries still contradict the stated blocking floor. The biggest defects are around stale-pointer/scheduler enforcement, public-projection destination semantics, and the undefined machine-readable staged-publishing schema.

### Issues Found
- [P1] Critical: The MVP boundary contradicts the blocking-test boundary for stale-pointer/link validation. The Deliverable section says the MVP includes “stale quick-reference pointers” and fixture-local link behavior, but the Blocking Tests section explicitly defers `test_broken_wiki_target_fails`, `test_stale_pointer_existing_target_fails`, and `test_stale_pointer_uses_reference_time`. Acceptance criteria also say stale-pointer requirements are future hardening. This leaves implementers unable to know whether fixture-local stale/broken pointer enforcement is required for #2975 or follow-up scope.
- [P1] Critical: Public projection destination rules are internally inconsistent. The allowlist table says public projection `destination.repo` may be `worldenergydata-wiki` for `public_federal_wiki` or `llm-wiki` “only for private quick-reference pointers,” but the same section says public projections must not include private artifacts and must be allowlist-only public-safe data. A public projection cannot safely encode “private quick-reference pointers” without a precise redaction/pointer contract, and the plan does not define one.
- [P2] Important: The staged publishing order is required as a blocking test and acceptance criterion, but the plan does not define the machine-readable config/schema shape that will encode it. It says BSEE/federal first, FDAS after classification/citation coverage, and HSE/marine after segregation/redaction/legal checks, but no keys, object model, enum values, or fixture layout are specified. That makes `test_staged_publishing_order_is_machine_readable` underdefined.
- [P2] Important: Scheduler criteria are split inconsistently between blocking and follow-up scope. The Test List includes `test_two_clean_manual_runs_required_before_scheduling` and `test_clean_run_requires_reviewed_generated_diff`; the follow-up section marks both non-blocking, while acceptance criteria require the standard to document weekly/scheduled publishing and clean-run criteria. The plan should explicitly separate “standard-only machine-readable definition” from “validator enforcement” and name which tests prove each.
- [P2] Important: The plan still overloads #2975 with a very large manual validator surface despite calling live scans/hooks/CI out of scope. The blocking subset includes enum/config drift, schema composition, public/private contamination, projection leakage scanning, legal rehashing, wrapper gates, stable IDs, staged order, deterministic output, and self-artifact safety. That may be feasible, but the plan lacks a phase-by-phase minimal acceptance cutoff if validator complexity threatens reviewability.
- [P3] Minor: The attested evidence shows `docs/standards/README.md`, `docs/standards/ECOSYSTEM_WIKI_FLYWHEEL_CONTRACT.md`, the governance decision, and `config/ecosystem-wiki-flywheel/source-classification.yaml` are missing, which matches create-target claims. No contradiction there, but the plan should avoid implying any of those are already present outside the explicit “new — this plan will create” evidence block.

### Suggestions
- Define a single scope table with three columns: standard-only, fixture validator blocking, and follow-up live enforcement. Move each stale-pointer, broken-link, scheduler, and clean-run test into exactly one column.
- Rewrite the public projection destination rule so `llm-wiki` means public generic index pointers only, or remove `llm-wiki` from public projection destinations in #2975. Do not use the phrase “private quick-reference pointers” in a public projection schema unless the redaction contract is fully specified.
- Add the exact YAML structure for staged publishing order to `source-classification.yaml` or the standard fenced block, including required keys and failure conditions for missing prerequisites.
- For scheduler readiness, add a machine-readable standard block if #2975 only documents it, and defer validator tests cleanly. If the validator must test it, promote the scheduler tests back into the blocking subset.
- Add an implementation cutoff rule: if any blocking test is deferred, the follow-up issue must be filed and the deferral must not weaken public-output gating. The plan says this generally, but it should identify which current blocking tests are non-deferrable public-output gates.

### Questions for Author
- Should fixture-local stale/broken wiki pointer validation be blocking for #2975, or is all stale/link enforcement follow-up scope?
- Is `llm-wiki` intended to hold public quick-reference pointers, or private quick-reference pointers? The current destination rule says both by implication.
- Where exactly will the staged publishing order live: `source-classification.yaml`, the standard fenced enum block, or a separate schema/config block?
