### claude

- **MAJOR — The new YAML dependency has no execution path in CI; `skills-validation.yml` adds no Python/uv/PyYAML setup.** The plan's deliverable is "a test-covered validator path that YAML-parses" running through `.github/workflows/skills-validation.yml`, but that job is only `actions/checkout@v4` + `run: bash scripts/skills/validate-skills.sh` — no `setup-python`, no `setup-uv` (verified by `grep`). Sibling enforcement workflows (`enforcement-gate.yml`) explicitly add `actions/setup-python@v5` + `astral-sh/setup-uv@v4` first. If the upgraded validator calls `uv run --with pyyaml` (as the plan's own test guidance suggests, plan line 228), `uv` is absent in this job and the step errors. If it calls bare `python3 -c "import yaml"`, it relies on the ubuntu runner's system Python silently shipping PyYAML — an undocumented, unstated assumption (the local `yaml 6.0.3` proves nothing about the runner). The "Files to Change" table lists the workflow only under **"Consider"** for the `continue-on-error` toggle and never mentions adding a setup step. This is the load-bearing gap.
- **MAJOR (compounding) — Removing `continue-on-error: true` while finding #1 is unresolved produces a hard-red CI.** The plan's Risks/Open recommendation (lines 289) is to remove the soft-fail "immediately after the validator passes live inventory." Combined with finding #1, removing the safety net before the runner can satisfy the new dependency converts a silent no-op into a blocking CI failure on an unrelated cause (missing interpreter/lib, not a malformed skill). Sequence and dependency must be pinned before this toggle flips.
- **MEDIUM — 3111 files under a 10-minute CI timeout: the plan never pins single-process parsing.** `skills-validation.yml` sets `timeout-minutes: 10`. The pseudocode (lines 216-223) says "for each SKILL.md under root: parse extracted frontmatter with yaml.safe_load" without specifying that all files are parsed in **one** Python process. A per-file shell-out — especially `uv run --with pyyaml` per file (3111 dependency-resolution startups) — would blow the timeout. The implementation must iterate the whole tree inside a single interpreter invocation; the plan should state this as a constraint, not leave it to implementer discretion.
- **MEDIUM — Two divergent frontmatter-extraction methods in the plan's own evidence; none is pinned, and none is tied to the real consumer's parser.** The live-inventory probe (lines 126-131) uses `text.find('\n---', 4)` + `text[4:end]`; the reproduction probe (line 156) uses `text.split('---', 2)[1]`; the existing bash uses `awk` matching `^---[[:space:]]*$`. These differ on edge cases (no trailing newline, `---` inside the body, trailing chars after `---`). More importantly, the validator's verdict is only meaningful if it mirrors what Claude Code's / Codex's skill loader actually does — the plan asserts "Strict YAML parsers reject this file" (line 17) but never identifies the parser the real consumers use. Pin one canonical extraction and justify that it matches the loader, or the gate can diverge (false-pass or false-fail) from real load behavior.
- **MINOR — The new regression test has no demonstrated CI wiring.** `skills-validation.yml` triggers only on `scripts/skills/*.sh` and `.claude/skills/**/SKILL.md` (not `*.py`, not `tests/**`). The plan adds `tests/enforcement/test_validate_skills_frontmatter.py` and all RED/GREEN acceptance criteria run it via local `uv run pytest`, but nothing in the plan shows which CI workflow collects `tests/enforcement/`. If the intent is durable enforcement (not a one-time local check), the plan should name the CI path that runs the new test, or add it.
- **MINOR — The workflow's soft-fail justification comment is already factually false and the plan doesn't flag its removal.** Lines 90-92 of the workflow claim files under `_diverged/` and `_internal/` "do not yet have YAML frontmatter," justifying soft-fail. The live inventory proved `missing_frontmatter=0` (and my strict re-run found 0 missing). When the plan edits this file it must delete this stale false comment, not just toggle the flag — otherwise a disproven justification persists in-tree.

### codex

- Plan lines 226-228 allow “an embedded Python/YAML parse step or a small helper,” but `.github/workflows/skills-validation.yml` lines 7-10 and 15-17 only trigger on `.claude/skills/**/SKILL.md`, `scripts/skills/*.sh`, and the workflow file. If implementation chooses a Python helper under `scripts/skills/*.py`, future helper-only changes will not trigger CI validation. The plan must either require embedding the parser in `validate-skills.sh`, list the helper path in Files to Change, and update workflow path filters, or explicitly forbid a helper.
- Plan lines 115-151, 228, and 258-259 rely on bare `uv run` commands. In this session, the same command shape failed with `Failed to initialize cache at /home/vamsee/.cache/uv ... Read-only file system`; the command only worked after setting `UV_CACHE_DIR=.claude/state/uv-cache`. The plan’s evidence and acceptance commands are not executable in the declared workspace unless they include a writable cache strategy or avoid runtime dependency installation.
- Plan line 228 says to use `uv run --no-project --with pyyaml` if PyYAML is not guaranteed, but `.github/workflows/skills-validation.yml` lines 30-35 currently runs only `bash scripts/skills/validate-skills.sh` with no `uv` setup, no cache configuration, and no dependency installation step. If the validator starts requiring PyYAML through `uv`, the plan does not specify the CI dependency/runtime contract needed for the workflow to run reliably.
- Plan lines 216-223 require `yaml.safe_load` and “non-empty name and description fields,” but the TDD list lines 249-252 only covers malformed colon text, quoted colon text, missing description, and live tree pass. It omits YAML-valid but semantically wrong values like `name: 123`, `description: false`, or `description: []`. Since downstream skill loaders treat these fields as strings, the plan can produce a validator that accepts YAML-valid frontmatter that still breaks consumers.
- Plan line 251 says `test_validator_requires_name_and_description` verifies existing metadata requirements, but its expected input is only “missing `description`.” It does not test `description: ""` or whitespace-only values. That leaves a direct gap against the plan’s own pseudocode line 221, which says fields must be non-empty.

### gemini

- Plan references `.claude/skills/coordination/flywheel-closeout/SKILL.md`, `scripts/skills/validate-skills.sh`, and `.github/workflows/skills-validation.yml` — no such files exist in the workspace at HEAD.
- Plan §Pseudocode proposes `for each SKILL.md under root: ... parse extracted frontmatter with yaml.safe_load`. Plan §Implementation direction suggests `extending scripts/skills/validate-skills.sh with an embedded Python/YAML parse step`. If the existing shell script loops over the 3,111 files and invokes a Python interpreter per file, it will cause a catastrophic performance regression. The plan fails to explicitly mandate batching the reads in a single Python execution.
- Plan §Implementation direction recommends `Use uv run --no-project --with pyyaml in tests if PyYAML is not guaranteed`. However, Plan §Files to Change omits updating `.github/workflows/skills-validation.yml` to guarantee `uv` or `pyyaml` is installed on the runner. If the GitHub Actions runner lacks these dependencies, the validator will break the build.
- Plan §Pseudocode states `require non-empty name and description fields`. The original validation (`grep -Eq '^name:[[:space:]]*[^[:space:]].*'`) strictly required strings. `yaml.safe_load` evaluates unquoted inputs like `name: 123` to an integer. The plan fails to mandate type-checking the parsed frontmatter, risking downstream crashes in tools expecting string data.
- Plan §TDD Test List entry `test_validator_requires_name_and_description` only verifies behavior against a `tmp SKILL.md missing description`. It fails to define a test case for an *empty* description string (e.g., `description: ""`), which is a distinct failure mode that the old regex blocked and the pseudocode claims to handle.
- Plan §Live inventory of YAML parse failures uses `text.find('\n---', 4)` to locate the closing delimiter. This hardcodes LF line endings and will fail to find the delimiter in files using CRLF (`\r\n---`). The implementation plan fails to specify cross-platform line ending support.
