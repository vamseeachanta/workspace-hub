# #3549 Implementation-Plan Amendment Compatibility Review — Round 1

**Verdict: MAJOR**

**Reviewed range:** `ff410225583d42d84d4b1e7fb2167621d74d0c5f..8f159199d60d66bb248e8954731fba43ccb7fc8b`

## Blocking findings

1. **The proposed caller migration silently changes the target machine.** The amendment claims that `scripts/workspace` will “preserve its existing menu outcome” while all Linux/Windows entries pass or print `dev-secondary` (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md`, Implementation Amendment item 3 and Acceptance Criteria lines 359–361). That is false. The four generic helpers currently identify the primary workstation: `connect-workspace-linux.sh:5`, `connect-workspace-windows.ps1:8`, `connect-workspace-tailscale.sh:5-6`, and `connect-workspace-tailscale.ps1:8-9` all point to the primary/`vamsee-linux1` surface, while `config/workstations/registry.yaml` maps `dev-primary` to `ace-linux-1`/`vamsee-linux1` and `dev-secondary` to `ace-linux-2`. Only `ssh-dev-secondary.sh` is a secondary-machine entry point. Passing `dev-secondary` from `scripts/workspace:283,314,345,350` would therefore retarget existing primary-workstation menu actions. **Required change:** preserve each caller’s existing logical destination (`dev-primary` for the four generic menu entries; the fixed `dev-secondary` only for `ssh-dev-secondary.sh`), and add exact argv/output tests that distinguish those machine IDs.

2. **The Windows Tailscale menu is planned as a guaranteed failure while the amendment claims preservation.** The amendment requires the PowerShell Tailscale entry to print an explicit fallback switch (`Implementation Amendment` item 3; TDD sequence item 4). The normative design says Windows fallback must return exit 4 until native ACL validation exists (`docs/superpowers/specs/2026-07-15-3549-registry-connection-helpers-design.md:221-229,243-252`), and the plan repeats that boundary at Acceptance Criteria lines 352–354 and 384–386. Thus the proposed Windows menu command cannot connect and does not preserve the current Tailscale helper’s outcome. **Required change:** explicitly retire/disable and label that menu entry as unsupported, or change it to hostname mode and rename its semantics; do not emit a command that is known to fail while calling it compatibility preservation. Add a native-Windows assertion for the chosen UX.

3. **`scripts/workspace` does not call the governed wrapper paths, and the proposed RED cases do not require fixing this.** `scripts/workspace:21` sets `SCRIPTS_DIR` to the repository’s `scripts` directory, but its four connection entries use `$SCRIPTS_DIR/connection/...` at lines 283, 314, 345, and 350. No `scripts/connection` path exists; the five wrappers are under `scripts/operations/connection`. A test that merely forbids “no-argument generic call or printed command” (Amendment TDD sequence item 4) can pass after appending machine/fallback flags while leaving every menu entry broken. **Required change:** make the plan require exact canonical wrapper paths for all four menu entries and test that each referenced path exists. PowerShell guidance must be an actually runnable command, not the current Linux absolute path text.

4. **The amendment is not implementable under the stated 400-line rule with its current changed-path map.** The amendment frames the split as compliance with a “hard 400-line limit” (`Implementation Amendment` item 1), then adds `scripts/workspace` to the canonical changed-path map. That file is currently 575 lines. The line/function gate named in Amendment TDD sequence item 5 only has a demonstrated Python checker (`scripts/enforcement/check_python_function_lengths.py`); it does not make the modified Bash file compliant. **Required change:** either authorize and plan a focused split of `scripts/workspace` into sub-400-line files (including every new path and caller test), or cite an explicit applicable grandfathering policy and adjust the claim. The plan cannot presently claim that all modified implementation files remain below 400 lines.

5. **The cross-platform test contract does not prove the compatibility boundaries requested by the amendment.** The generic Bash group mentions non-repository CWD and a spaced checkout (`TDD Test List`, Bash wrappers; Implementation Sequence Slice D), but the `scripts/workspace` caller tests only check flags, and the PowerShell group says only “native Windows proof.” It never requires native Windows execution from a non-repository CWD with a checkout path containing spaces. Printed PowerShell guidance also lacks an exact quoting/call-operator contract. Further, the existing alleged executable test `tests/workstations/test_connection_cli.py:234-249` invokes `[sys.executable, script, ...]`; it does not exercise the executable bit or shebang despite the amendment’s claim that tests will cover “the executable script/shebang boundary” (`Implementation Amendment` item 2 and TDD item 1). **Required change:** specify RED tests that (a) invoke the CLI path directly on POSIX from a non-repo CWD and a spaced checkout, (b) verify its executable mode/shebang, (c) run each PowerShell wrapper natively on Windows from a non-repo CWD and a spaced checkout, and (d) parse/execute the exact printed PowerShell command with safe quoting. The native-required CI lane must run these nodes without skip.

6. **The exit/argparse RED cases are not precise enough to prevent overbroad fixes, and the final focused gate omits the new CLI suite.** Amendment TDD item 1 names `ENOEXEC`, `--fall`, child `-SIGINT`, and overlay `OSError`, but it does not state the exact exception construction and negative controls. An implementation could catch every `OSError` as 126, or accept another abbreviation, and satisfy a weak test. The exact gate at Acceptance Criteria lines 376–377 also omits `tests/workstations/test_connection_cli.py`, despite that file owning all amended exit behavior. **Required change:** require `OSError(errno.ENOEXEC, ...) -> 126`, `PermissionError/EACCES -> 126`, `FileNotFoundError/ENOENT -> 127`, unrelated launch `OSError` not mapped to 126, `returncode == -signal.SIGINT -> 130`, unchanged nonnegative child statuses, and every long-option prefix (`--fall`, `--dry`, `--reg`, `--over`, `--use`) to raise sanitized usage exit 2 without resolution/launch. Specify which overlay read failure maps to exit 4 versus 5 and prove it cannot become registry exit 3. Add `tests/workstations/test_connection_cli.py` to the exact final focused command and Windows CI selection.
