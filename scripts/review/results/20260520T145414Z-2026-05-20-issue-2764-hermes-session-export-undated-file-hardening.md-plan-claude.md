### Verdict: MAJOR

### Summary
The plan is well-scoped, surgical, and correctly identifies the root cause (undated basenames aborting under `set -euo pipefail`), with a sensible patch shape and a TDD test list that covers the key partitions. However, several issues block approval: the proposed `grep -oE '[0-9]{8}' | head -1 || true` pattern still has subtle pipefail/precedence concerns and overmatches non-date 8-digit runs; one of the listed test cases is a tautology rather than a behavior test; the env-override surface is introduced without specifying defaults or backward compatibility; and the plan claims fresh adversarial review artifacts exist but they are not attested.

### Issues Found
- [P1] Patch shape correctness: `grep -oE '[0-9]{8}'` will match ANY 8-digit run anywhere in the basename (e.g., `session_bg_12345678.json`, or a UUID fragment), producing a spurious 'date' that then proceeds to conversion as if it were dated. The regex must anchor to the documented Hermes naming convention (e.g., `^[0-9]{8}_` or a documented prefix), otherwise the fix silently mis-routes files instead of skipping them.
- [P1] Pipefail interaction: under `set -o pipefail`, `printf ... | grep -oE ... | head -1` can still fail the pipeline when `grep` finds no match (exit 1) AND when `head` closes the pipe early on a match (SIGPIPE/EPIPE makes `grep` exit non-zero). The trailing `|| true` is on the *command substitution*, which masks BOTH cases — but it also masks any other failure in the pipeline (e.g., `grep` segfault, missing binary). Plan should spell out the exact semantics or prefer a pure-bash `[[ $base =~ ^([0-9]{8}) ]]` extraction, which has no pipefail interaction.
- [P2] `test_tests_do_not_touch_live_hermes_home_or_logs` is a meta-assertion about test hygiene, not a behavior test of the script. It belongs as a test-harness invariant (sentinel directory check in setup/teardown), not as a numbered TDD case. As written it's also unfalsifiable without specifying HOW 'no files created under real ~/.hermes' is verified.
- [P2] Env-override contract is under-specified. The plan introduces `HERMES_SESSION_EXPORT_HOME`, `..._SOURCE_DIR`, `..._OUTPUT_DIR` 'if needed', but does not pin: (a) which of these are required vs optional, (b) their default fallbacks, (c) precedence between `_HOME` and `_SOURCE_DIR`/`_OUTPUT_DIR` when both set, (d) whether existing cron consumers will keep working unchanged. Adding env-override surface as a side effect of a bugfix is scope creep unless contracted.
- [P2] Acceptance criterion 'Fresh adversarial plan review artifacts are saved under scripts/review/results/' is a meta-criterion about the planning process, not about the deliverable. It also conflicts with the plan's own 'Status: draft — fresh re-review required' header — these artifacts are NOT attested as existing yet, so listing the file paths under 'Adversarial Review Summary' as if they were produced is misleading.
- [P3] `test_provider_audit_smoke_after_export_dry_run` is described as 'both exit 0 or exporter skip is explained' — the disjunction is too loose to fail meaningfully. Specify the exact expected exit code and stdout/stderr assertion.
- [P3] No mention of locale/`LC_ALL` for `grep -oE` matching, nor of busybox vs GNU grep portability. Bash `[[ =~ ]]` avoids both concerns and is a stronger choice for a script run under cron.
- [P3] Skip count is logged but not surfaced via exit metadata (file, structured log line, or JSONL summary). Downstream audit consumers will need to grep human-readable strings to detect skips — fragile.

### Suggestions
- Replace the pipeline-based extraction with pure bash regex: `if [[ $base =~ ^([0-9]{8})_ ]]; then session_date="${BASH_REMATCH[1]}"; else skipped_unsupported=$((skipped_unsupported+1)); log ...; continue; fi`. No pipefail interaction, no `|| true`, no SIGPIPE class, no busybox/GNU divergence, and the anchor enforces the documented prefix convention.
- Move the 'tests don't touch live HOME' check into a setUp/tearDown invariant (e.g., snapshot `~/.hermes` mtime and assert unchanged) rather than a standalone test case, and drop it from the TDD count.
- Promote env-override design to its own short subsection: name each var, its default, its precedence, and assert backward compatibility (cron invocation with no env set must behave identically to today's pass case).
- Either attest the three round-1 review artifacts exist (file path + sha + commit SHA) or restate that they are referenced for future round-2 dispatch — don't list them as if they're already filed.
- Add a structured-log line for skip events (e.g., one JSON object per skip with `event=skip_unsupported_filename`, `basename=...`, `reason=no_yyyymmdd_prefix`) so the provider-audit pipeline can detect skip-rate regressions without string-matching prose.
- Add a test case for the 'spurious 8-digit run in non-date position' boundary (e.g., `session_bg_12345678.json`) — confirms the anchor works and prevents the P1 overmatch from silently regressing later.
- Reproduction proof would be stronger as a captured stderr snippet showing the exact `set -e` abort line; the current text only narrates the reproduction.

### Questions for Author
- What is the documented Hermes session filename convention? Is it strictly `YYYYMMDD_<rest>.json`, or can the date appear elsewhere in the basename? The regex anchor depends on this answer.
- Are there existing consumers (audit script, dashboards) that depend on a specific exit code or summary format when the exporter encounters skipped files? Adding a skip counter could break them.
- Should malformed undated files (e.g., not valid JSON AND no date) be skipped silently or surfaced? The current spec only addresses the basename axis; a file like `session_bg_22fe54.json` containing garbage JSON would skip on basename before JSON validity is checked.
- Is `HERMES_SESSION_EXPORT_HOME` a new env var or does it already exist? If new, who else needs to know (Hermes upstream, cron unit files, other scripts)?
- Are the round-1 review artifacts actually present at the cited `scripts/review/results/2026-05-20-plan-2764-*.md` paths, or are those forward-references? The 'Status: draft' header implies the latter; the artifact list implies the former.
- Does the production cron invocation set `LC_ALL`? GNU `grep -oE '[0-9]{8}'` is locale-stable for ASCII digits, but a defensive `LC_ALL=C` on the pipeline would remove a class of future surprises.
