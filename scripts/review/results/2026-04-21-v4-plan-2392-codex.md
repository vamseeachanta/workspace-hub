### Verdict: MAJOR

### Summary
The plan still has correctness-critical gaps and internal contradictions. It does not yet define behavior tightly enough to avoid false negatives/false positives in the detector, and at least one manual verification step is incomplete relative to the plan’s own required-input contract.

### Issues Found
- `Identity Join Contract -> Canonical rule` says bare hex is normalized to `sha256:<hex>` by readers, but the pseudocode under `Pseudocode` says `normalize_wiki_doc_key_for_coverage(... )  # sha256 only; bare hex stays warning-only`, and `TDD Test List -> Wiki/frontmatter behavior` requires `test_nonconforming_wiki_doc_key_not_added_to_coverage_index`. Those are incompatible contracts. Either bare-hex wiki keys normalize for compatibility, or they are excluded from coverage; the plan currently asserts both.
- `Authoritative source inputs for this detector` labels `data/document-index/standards-transfer-ledger.yaml`, `data/document-index/dde-standards-inventory.yaml`, and `data/document-index/promotions/*.yaml` as part of the `join corpus`, but the same section also marks them `Optional inputs (must degrade gracefully if absent)` with `missing file != crash`. That creates a false-negative path: missing join-corpus inputs silently shrink the source universe and can make the detector under-report gaps while still exiting successfully. The plan needs a fail-closed or at least degraded-results contract for join-bearing optional inputs, not just “record skipped input in _summary.md”.
- `L3 Coverage Boundary` says wiki pages are coverage-bearing only when they `include pages with a conforming doc_key in frontmatter`, but `Identity Join Contract -> Wiki diagnostics` says `wiki-schema-warning` applies when `a coverage-bearing wiki page is missing title, last_updated, or a conforming doc_key`, and the tests require `test_wiki_page_missing_doc_key_emits_schema_warning`. A page cannot both require a conforming `doc_key` to be in-scope and also be in-scope for missing-`doc_key` warnings. The selection rule for schema validation is not defined coherently.
- `Manual verification before approval` and the matching acceptance criterion only precheck `test -f data/document-index/index.jsonl`, but `Pseudocode` declares two required inputs: `data/document-index/index.jsonl` and `data/design-codes/code-registry.yaml`. The smoke-run gate is therefore incomplete against the plan’s own required-input contract and can proceed into a guaranteed failure mode the plan claims to guard against.
- `Pseudocode` builds `wiki_index[key] = page` with no duplicate-key handling. If two wiki pages carry the same canonical `doc_key`, the later one silently wins, the source record is treated as covered, and the data-integrity defect disappears from reporting. Because coverage correctness depends on a one-to-one canonical identity, duplicate wiki `doc_key` handling is correctness-critical and currently unspecified.
- `Candidate Record Shape` requires every normalized source record to have `domain`, and the deliverable emits per-domain YAML, but the plan only defines fallback mapping for some cases: `index-record` via `source_root_domain_map`, `design-code` via defaults, `ledger/promotion-manifest` via source-provided domain or config mapping. It never defines what happens when none of those mappings resolve. Without an explicit error/degraded-status contract, unmapped records can be dropped, misbucketed, or produce invalid output filenames, all of which change detector results silently.

### Suggestions
- Make the bare-hex rule explicit per side: define one contract for source records and one for wiki pages, then align pseudocode and tests to that exact behavior.
- Split optional inputs into two classes: `reporting-only optional` and `coverage-affecting optional`. For the latter, either fail closed when configured-but-missing or emit a top-level degraded run status that blocks acceptance/scheduling.
- Define a precise wiki validation universe, for example: all markdown files under `knowledge/wikis/*/wiki/**/*.md` except structural excludes are schema-validated, but only pages with canonical `sha256:` `doc_key` participate in coverage indexing.
- Add the missing precheck for `data/design-codes/code-registry.yaml` and require the smoke test to run only after all required inputs pass.
- Add a duplicate canonical `doc_key` diagnostic with an explicit policy: fail closed, or mark run degraded and report duplicates in `_summary.md` without counting them as clean coverage.
- Add an explicit unresolved-domain policy, such as `domain-unresolved` status plus summary accounting, or fail normalization when a source record cannot be assigned to a valid output domain.

### Questions for Author
- Are join-bearing ledgers/manifests truly optional for correctness, or only optional because they may not exist in some repos? The current contract treats absence as non-fatal but also relies on them for coverage enumeration.
- Should a wiki page with bare 64-hex `doc_key` count as coverage during migration, or must it remain diagnostic-only until rewritten to `sha256:<hex>`?
- What is the intended behavior when two wiki pages claim the same canonical `doc_key`?
