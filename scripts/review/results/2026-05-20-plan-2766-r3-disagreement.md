### claude

- **`OGManufacturing` is silently dropped from `dev-primary` runtime access without acknowledgement.** Live `config/workstations/registry.yaml:29-35` includes `OGManufacturing` in `machines.dev-primary.repos`, and line 44 includes it in `telegram_hermes.data_access_profile.repos`. The proposed `repos` list (plan lines 83-101) and `tier1_baseline` buckets (lines 110-141) exclude `OGManufacturing` entirely (no `required`/`optional`/`non_tier1_machine_access_current`/`historical` membership). Acceptance criterion line 290 then requires `data_access_profile.repos` to "contain no unclassified repo," which forces `OGManufacturing` to be removed from dev-primary dispatch routing. This is a behavior change for telegram_hermes — not just a registry tidy. Plan §"Risks and Open Questions" (lines 313-317) does not mention it. Either classify `OGManufacturing` (e.g., `reference_only` or new bucket) or surface the deliberate routing removal explicitly with rationale tied to #2770.
- **`placement_rules.*_policy` schema is declared but never consulted by the pseudocode.** Lines 142-156 define `direct_nested_git_policy: error`, `optional_absence_policy: warning`, `dirty_policy.*: warning`, `ahead_policy.*: warning`, etc. The pseudocode (lines 186-199) hardcodes "missing required → blocker; missing optional → warning; nested → blocker" without reading these fields. Two sources of truth that cannot disagree at write-time but can drift at any future revision. Either wire the policy table into the checker (table-driven) or strip the unused fields. As written, the policy block is decorative.
- **Readiness merge breaks the `status`/`overall_status` contract.** Pseudocode line 209 does `host_entry["dispatchable"] = host_entry["dispatchable"] and host_entry["repo_placement"]["dispatchable"]`. Live `scripts/readiness/telegram_hermes_readiness.py:418-420` computes `overall_status` from each host's `status`, not from `dispatchable`. If `repo_placement.dispatchable=false` only flips `dispatchable` without also appending to `failures` and degrading `status` to `"fail"`, the report can emit `overall_status="pass"` with `dispatchable=false` on the same host — contradictory. The plan must specify the `failures`/`status` update path explicitly, not just the `dispatchable` AND-merge.
- **The checker's machine binding is undefined.** Pseudocode line 165 asserts `machine.hostname == "ace-linux-1"`, but the checker has no input contract: does it iterate all machines in the registry, select `dev-primary` by registry key, or resolve by `socket.gethostname()` (existing pattern at `telegram_hermes_readiness.py:96-97`)? If run from `ace-linux-2` (dev-secondary) the assertion blows up; if run from CI it has no machine identity. This affects whether `tier1_baseline` is per-machine or only for `dev-primary`. The Files-to-Change table lists exactly one checker file — implying one machine — but registry has 6 machine entries. Either constrain scope explicitly to `dev-primary` and gate the assertion behind a `--machine` arg, or generalize `tier1_baseline` schema across machines.
- **Inventory table omits `agent-worktrees` sibling.** `ls /mnt/local-analysis/` shows `drwxrwxrwx ... May 20 18:34 agent-worktrees` as a sibling under `tier1_repo_root: /mnt/local-analysis`. The plan's verified inventory table (lines 22-40) lists 17 repos but does not enumerate `agent-worktrees`. Under the proposed `unknown_sibling_git_policy: warning`, the checker would either emit a warning (if `agent-worktrees/.git` exists) or remain silent (if it's a non-git infra dir). Plan must either (a) verify and document that `agent-worktrees` has no `.git`, OR (b) add an infrastructure-directory allowlist to placement_rules — pseudocode line 193 says "repo != infrastructure directory" without defining that set.
- **`test_checker_is_readonly` is unfalsifiable as stated.** Line 248 says "Checker never calls clone/fetch/pull/push/mv/rm/delete/sync." A static grep of the source file is brittle (`subprocess.run(["git", ...])` constructed at runtime evades it) and a no-mutation runtime check requires either filesystem snapshot diff or an `unshare`/`fakeroot` sandbox. Plan needs an explicit method — e.g., `monkeypatch subprocess.run` to assert no `git fetch|pull|push|clone` or `mv|rm` invocation, OR strace-equivalent — otherwise this AC always passes vacuously.
- **`inventory_timestamp_utc: now` makes the readiness payload non-deterministic.** Pseudocode line 206 emits a wall-clock timestamp into the readiness payload. Test `test_readiness_payload_adds_host_scoped_repo_placement` (line 249) cannot snapshot the field without clock injection; existing `telegram_hermes_readiness.py` does not currently inject a clock. Either inject `now` via a fixture or omit `inventory_timestamp_utc` from snapshot comparisons explicitly. Otherwise the test is flaky.
- **Base fanout artifacts still present and unaddressed.** The R1/R2 evidence section (line 48) states that base names are not cited "because plan-review-fanout.sh overwrites them on rerun." Yet `scripts/review/results/2026-05-20-plan-2766-{claude,codex,gemini,disagreement}.md` (unsuffixed) currently exist on disk. The next R3 fanout will overwrite them, destroying R1 or R2 ancestry if the durable copies were not yet renamed. Add an explicit pre-R3 step: rename existing base files to `-r1` or `-r2` (if not already), or delete them, before running r3 fanout.
- **Disjointness assertion does not cover `data_access_profile.repos`.** Pseudocode line 175 asserts disjointness across the six `tier1_baseline` classification buckets, and line 177 asserts data-access membership in `required ∪ optional ∪ non_tier1_machine_access_current ∪ reference_only`. Either require `data_access_profile.repos ⊆ machines.dev-primary.repos`, or add an explicit handling rule for `reference_only` repos in dispatch.
