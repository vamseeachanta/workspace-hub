## Findings
### Finding 1 — MAJOR — Broken Idempotency Claim Under Concurrency
- Plan claim: "idempotency: skip records whose (event, provider, date) tuple already appears in any file under .claude/state/session-signals/ for the same date"
- Location: Pseudocode (`emit_signals`)
- Evidence: `write_jsonl(path, dedupe(records, against=scan_existing_signals(date)))` where `path` is `f".claude/state/session-signals/{date}-{now.strftime('%H%M%S')}.jsonl"`.
- Why it matters: Scanning prior files and then writing to a newly generated timestamped filename provides zero concurrency protection. Simultaneous runs will both scan, find nothing, and write duplicate records to different files.
- Suggested fix: Use atomic file creation, or write to a deterministic per-day file using a filesystem lock, instead of generating a new timestamped file per run.

### Finding 2 — MAJOR — Unmeasurable Acceptance Criterion
- Plan claim: "assets/issue-43/session-compliance-audit.md exists with per-provider gate-compliance scores >=0.90 OR documented explanation of why the >=0.90 target was not met"
- Location: Acceptance Criteria
- Evidence: The "OR documented explanation of why..." clause is purely narrative.
- Why it matters: Acceptance criteria must be mechanically verifiable by automated tests or agents. An arbitrary "documented explanation" cannot be reliably asserted in a CI/CD pass/fail context.
- Suggested fix: Enforce a strict numeric threshold, or define a strict machine-readable schema for the "explanation" bypass that a test script can validate.

### Finding 3 — MAJOR — Pseudocode Violates Its Own TDD Contract
- Plan claim: `test_score_zero_sessions` returns `{status: "insufficient_data"}` when given empty input.
- Location: TDD Test List & Pseudocode (`score_provider`)
- Evidence: The `score_provider` function performs `count(...) / total_expected` without checking if the denominators are zero.
- Why it matters: The proposed pseudocode will throw a DivisionByZero error on empty cohorts, directly failing its own specified unit test and proving the design is incomplete.
- Suggested fix: Add explicit guard clauses in `score_provider` to check for zero denominators and return the promised `{status: "insufficient_data"}` dictionary.

### Finding 4 — MINOR — Undefined Schema for `routing-rules.yaml`
- Plan claim: "routing-rules.yaml = declarative static policy; routing-config.yaml continues as the dynamic smart-router runtime config."
- Location: Design Decisions (Q2)
- Evidence: The plan fails to define the exact schema, keys, or structure that `routing-rules.yaml` will use to differentiate itself from the existing dynamic config.
- Why it matters: Leaving the schema undefined guarantees the implementing agent (Codex) will guess the format, likely leading to parse errors or silent overlap with the runtime config.
- Suggested fix: Explicitly draft the minimum viable YAML schema for `routing-rules.yaml` in the Design Decisions or Deliverable section.

## Summary
The plan exhibits critical logical flaws in its core mechanisms. The concurrency-blind idempotency approach will result in duplicate event emissions, the pseudocode contains fatal math errors that violate its own TDD guarantees, and the inclusion of subjective acceptance criteria makes the plan unverifiable by automation. These issues must be addressed before implementation can safely begin.
