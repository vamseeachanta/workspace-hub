# Adversarial Review — Plan #2046 (Codex)

Date: 2026-04-14

Reviewer: Codex CLI

Overall verdict: MAJOR

Retrieval adequacy: insufficient

Top blockers
1. The evidence model does not credibly answer the core question “did any agent begin coding before approval?” because it only compares approval evidence to commit timestamps.
2. The scope baseline is unresolved: the plan mixes all-issue workflow expectations from docs/plans/README.md with engineering-critical hard-stop enforcement from HARD-STOP-POLICY.md and does not define which policy is authoritative for scoring.
3. Retrieval omitted stronger audit sources already present in-repo, especially the existing canonical report at docs/reports/2026-04-09-planning-workflow-compliance-audit.md and richer session/bypass evidence.
4. has_review and label checks are too shallow; file existence and label presence are not enough to prove adversarial review quality or correct sequencing.
5. The test plan does not cover the failure modes most likely to produce false compliance or false non-compliance.

Critical findings
- The proof for implementation-before-approval is not aligned to the audit question; git log --grep="#issue" misses local edits before first commit, commits without issue refs, squash/rewrite patterns, and relabeling after work started.
- The repo already has richer audit surfaces than the plan uses, including session logs, bypass logs, and review-artifact quality checks.
- Policy scope is internally inconsistent across README vs hard-stop policy and the plan does not define cohort-specific compliance semantics.
- There is governance drift in the issue context itself: GitHub labels say status:plan-approved while the plan file still says adversarial-reviewed.

High findings
- Retrieval is missing the already-existing compliance report, which contains methodology and evidence categories the new plan should reconcile with.
- has_review = check scripts/review/results is not trustworthy enough; the audit needs content validation, verdict parsing, and sequencing proof.
- has_plan = check docs/plans is underspecified given phantom index entries and status drift.
- The plan does not specify exact GitHub timeline/events evidence for label transitions/comments.
- Acceptance criteria do not require reproducibility of the denominator via explicit included/excluded issue lists.

Medium findings
- The fixture strategy misses multiple important cases, including retroactive labels, missing markers, malformed review artifacts, and commits with no issue refs.
- The plan does not define how indeterminate issues affect headline compliance metrics.
- No explicit bypass-evidence check is planned even though bypass detection is central to audit integrity.
- The artifact map chooses a shell script for API-heavy audit/reporting logic without justifying why shell is the right implementation surface.

Low findings
- Standards: N/A is too coarse for a governance audit.
- The deliverable sentence should clarify whether the report is a one-time snapshot or rerunnable audit.
- The review artifact path is singular; multi-provider review should anticipate multiple artifacts.

Required revisions before user approval
1. Define the authoritative policy matrix up front for engineering-critical, non-engineering, and mixed/legacy issues.
2. Upgrade the evidence model for coding-before-approval beyond commit timestamps to include session logs and bypass logs, while documenting confidence levels.
3. Reconcile with the existing compliance report as baseline input or explain why it is replaced.
4. Specify exact GitHub evidence sources/checks: timeline endpoint/events, label transition parsing, plan-comment detection, and review-artifact validation.
5. Expand tests for false positives/negatives, especially retroactive labels, phantom plan entries, and invalid review artifacts.
6. Make report output falsifiable with included issue list, excluded issue list with reasons, per-issue evidence summary, and separate compliant/non-compliant/indeterminate counts by cohort.
