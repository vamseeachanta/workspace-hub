# Adversarial Review: Plan for [#2608](https://github.com/vamseeachanta/workspace-hub/issues/2608) — `fix/triage-punch-list-2026-05-02` disposition

**Reviewer stance:** defect-hunting. Charitable reading not applied. Goal: find what makes the close-as-superseded recommendation unsafe before any branch is deleted.

**Verdict:** MINOR — 3 defects. Recommendation stands (close-as-superseded), but two pre-deletion gates must be added before execution.

## Defects

### D1 — MAJOR (downgraded to MINOR by mitigation): Plan's "blob match" evidence is necessary but not sufficient because it only sampled the union of files **changed by the branch's two commits**, not the full tree

**Where:** plan.md → Resource Intel table & Acceptance Criterion #1.

**Defect:** The plan asserts equivalence by checking 6 files (the union of `git show --name-only` for `15d57451` and `0faf6416`). This proves only that the *delta* the branch introduces is on main. It does NOT prove the branch tip's *full tree* is equivalent to main's full tree. A subtle scenario: if the branch was created off a much older `main` and never merged forward, then a third file might have a state on main that the branch tip resurrects to its old form simply by being old. The branch's working content for *unchanged* files would silently shadow newer main content during any merge or worktree switch.

**Why it survives:** mitigated because (a) the branch is only 2 commits (no third party file changes are possible without showing in `git log origin/main..branch`), and (b) `git log fix/...~..origin/main` already shows the 10 main-side advances the branch is missing — those CAN'T have collided silently because they touch other files.

**Defense added:** Acceptance Criterion #1 now ends with `git diff origin/main fix/triage-punch-list-2026-05-02 -- .` should be empty or trivial. **That gate must be PRE-DELETION, not post.** If it is non-empty, stop and re-classify. The current plan lists this in Risks → Mitigation but does not actually wire it into Execution Sequence step 2.

**Required fix to plan:** Plan execution step 2 already says "Re-run the equivalence check from Acceptance Criteria #1" — but #1's wording says "the 6 files the branch touches." Tighten to: "and `git diff origin/main fix/triage-punch-list-2026-05-02 -- .` produces only changes that are subsets of expected drift (uv.lock auto-sync resolution, none expected)." If the full-tree diff has unexpected files, halt.

### D2 — MINOR: "Auto-sync uv.lock equivalence" reasoning is correct but the *path* is fragile

**Where:** plan.md → Resource Intel row 2 ("Superseded by main's seaborn commits").

**Defect:** The plan correctly notes `0faf6416:uv.lock` blob (`0561238d`) equals `origin/main:uv.lock` blob. Therefore the *content* is the same. But the lineage is dependent: branch tip happened to converge on main's lockfile because both did the same `seaborn` move (out of `viz` extras into main deps). If a future developer rebases this same branch tomorrow against a *different* main with a still-different uv.lock, the equivalence breaks. This is not a defect for *today's* close decision but it is a defect for any "we can rebase this later if needed" fallback that someone might infer. The plan's rollback strategy (tag the tip) handles this — but only if the tag is actually applied before deletion.

**Required fix to plan:** Make the tag-before-delete step (Execution Sequence #4) non-skippable. Add a CI-style assertion: `git rev-parse --verify archive/triage-punch-list-2026-05-02` must succeed *before* `git branch -D` runs.

### D3 — MINOR: "Was the branch ever pushed to origin?" is a binary question the plan defers to execution time

**Where:** plan.md → Acceptance Criterion #3, Execution Sequence #3.

**Defect:** Planning-phase research did not check `git ls-remote origin refs/heads/fix/triage-punch-list-2026-05-02`. If the branch is on origin, the plan needs a more careful comms step (other machines may be rebasing it). If it is *not* on origin, the disposition is a pure local op and most of the risk table is moot. This affects the choice of communication: silent local cleanup vs. issue-comment-with-24h-grace. The plan punts that to step 3 of execution rather than nailing it down now. A reviewer should flag any plan whose risk profile depends on a fact we could have looked up but didn't.

**Why it isn't MAJOR:** the agent task scope explicitly forbids git ops, and `ls-remote` is technically a network read against the upstream — borderline acceptable but conservative to skip. The plan's gate at execution step 3 still catches this before deletion.

**Required fix to plan:** none — flag is acknowledgment that this fact should be the *first* thing the executor checks, before tagging.

## Specific Question From The Brief

> Does the plan provide enough evidence that the "superseded" classification is correct (not just "looks like the same change")?

**Yes, conditionally.** The evidence is per-file blob-hash equality across the entire delta the branch introduces, plus uv.lock blob equality at the branch tip. This is stronger than subject-line matching (which fooled the initial read because `60d59565` and `15d57451` share an exact subject but differ in patch-id due to PR #543 squashing in #2580). The conditional is D1's full-tree gate — must be PRE-deletion.

> What's the rollback if the branch is deleted but turns out to have unique work?

**Three layers:**
1. Reflog (90 days, default) — primary path. `git reflog show fix/triage-punch-list-2026-05-02` survives `branch -D`.
2. Local tag `archive/triage-punch-list-2026-05-02` at `0faf6416` — permanent until manually deleted, REQUIRED pre-deletion per D2.
3. Object-graph recovery via `git fsck --lost-found` if both above are lost — the SHAs `0faf6416` and `15d57451` are recorded in this plan and in issue [#2608](https://github.com/vamseeachanta/workspace-hub/issues/2608)'s comment trail, so they are knowable for as long as the pack files retain them (typically months past reflog expiry, until `git gc --prune=now`).

This is sufficient. No additional rollback needed.
