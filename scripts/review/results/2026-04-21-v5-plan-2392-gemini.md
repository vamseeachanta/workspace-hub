### Verdict: MAJOR

### Summary
The v4 plan resolves previous identity join ambiguities and defines concrete allowlists, but contains critical logic and schema mapping flaws. Specifically, it fails to define an output destination for required source-side warnings, mismatches fields between internal state and YAML output, and incorrectly allows duplicated wiki keys to falsely satisfy coverage instead of invalidating the key.

### Issues Found
- The 'Candidate Record Shape' defines the internal field as `suggested_slug`, but the 'Gap YAML entry fields' specifies `suggested_page`. The pseudocode fails to map between these, meaning the generated YAML will either lack the required `suggested_page` field or output the undefined `suggested_slug`.
- The 'Identity Join Contract' mandates that for source-side records, a bare hex value must 'normalize to sha256:<hex> for compatibility and emit a warning'. However, neither the `_summary.md` definition nor the pseudocode tracks or outputs these source-side warnings (the summary only accounts for `wiki-schema-warning` and `duplicate_wiki_doc_keys`).
- In the pseudocode, when a duplicate wiki `doc_key` is detected, it logs the duplicate and continues, but the *first* page encountered remains actively mapped in `wiki_index[key]`. This means an ambiguous/duplicate `doc_key` will still falsely count as 'covered' for source records, rather than invalidating the key and exposing the gap.

### Suggestions
- Standardize on either `suggested_slug` or `suggested_page` across both the internal normalized record and the output YAML schema.
- Add a `source_identity_warnings` array to the `_summary.md` deliverable and update the pseudocode to track and report bare-hex source key normalizations.
- Update the pseudocode to remove `key` from `wiki_index` (or map it to an explicit invalid state) when a duplicate `doc_key` is encountered, ensuring duplicated keys cannot satisfy coverage.

### Questions for Author
- Should a duplicated wiki `doc_key` result in a `gap` for any associated source records, or should it just mark the run as degraded while accepting the coverage?
- For the scheduled bash command `$(date +\%Y-\%m-\%d)`, does the target YAML parser and shell environment require escaping the `%` symbol? If this executes in a standard bash shell, the `\` may be passed literally.
