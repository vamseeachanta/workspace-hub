## Findings

### F1 — Plan asserts non-existent state files as evidence (FACTUAL ERROR)
Plan lines 74-75 assert under "Evidence (embedded verification)":
```
- EXISTS: `~/.config/gemini/state.json`, `~/.config/gemini/oauth_creds.json`
```
Live verification on this machine: `/home/vamsee/.config/gemini/` **does not exist**. The actual files live under `/home/vamsee/.gemini/state.json` and `/home/vamsee/.gemini/oauth_creds.json`. The plan's "Evidence" block is therefore contradicted by live filesystem state — the very paths the plan tags `EXISTS:` are absent. Severity: this is a category-A retrieval defect since the section is the contract that justifies the rest of the plan.

### F2 — Current `query_gemini()` reads the wrong path; plan inherits the bug silently
`scripts/ai/assessment/lib/providers.sh:221` reads `${HOME}/.config/gemini/state.json` and `:233` finds files under `${HOME}/.config/gemini/tmp` — neither path exists. The plan's pseudocode (line 184) repeats the same wrong path: `# read ~/.config/gemini/state.json's dailyRequestCount when populated`. Plan should either (a) flag the path bug as a precondition to fix, or (b) explicitly state it is correcting the path. Currently it does neither — it copies the broken path forward as the new "heuristic" rung. Same defect at `scripts/ai/assessment/lib/display.sh:107`.

### F3 — `dailyRequestCount` field is fictional on this Gemini CLI (MAJOR)
Live `cat ~/.gemini/state.json` returns:
```json
{ "tipsShown": 10, "defaultBannerShownCount": { "...": 2, "...": 2 } }
```
There is no `dailyRequestCount` key. The plan's `probe_gemini_state_json()` (lines 184-188) asserts it can read `~/.config/gemini/state.json`'s `dailyRequestCount when populated` and assign `confidence_level: heuristic`. Question: how does the plan know the field exists? The original `query_gemini` already conditions on `dailyRequestCount // 0` and that branch never fires (which is why the file-count fallback was added). The plan adds no new evidence for the field's existence. This rung of the Gemini ladder is therefore not a heuristic source — it is a no-op that always falls through to the estimated rung. With this defect, the Gemini ladder collapses from 4 rungs to 2 (CLI-quota probe + tmp-filecount), and the CLI-quota rung is itself unverified (see F4).

### F4 — `gemini quota --json` subcommand does not exist
Live `gemini --help` (Gemini CLI on PATH at `/home/vamsee/.npm-global/bin/gemini`) lists subcommands: `mcp`, `extensions`, `skills`, `hooks`. There is **no `quota` subcommand**. There is also no flag in the option list that surfaces quota. The plan's risk section (line 304) softens this with "the CLI surface is unstable. Mitigation: probe is feature-detected", but the deliverable rests on a subcommand the plan never demonstrates exists. The acceptance criterion (line 274) "emits `confidence_level: \"exact\"` for Gemini when `gemini quota --json` is supported" can never be exercised on this machine. The plan should either (a) cite the CLI version where the subcommand exists, or (b) drop the `exact` rung from the Gemini ladder entirely. As stated, the entire Gemini "exact" path is aspirational, which means the plan delivers no path stronger than `heuristic` for Gemini — directly conflicting with the issue acceptance criterion "Gemini usage source is stronger than `estimated` in the normal healthy path".

### F5 — Anthropic Admin-API endpoint shape is asserted but lightly evidenced
Plan pseudocode (line 137):
```
curl GET https://api.anthropic.com/v1/organizations/{ORG_ID}/usage_report/messages
```
Live probe `curl https://api.anthropic.com/v1/organizations/test/usage_report/messages` returns 404 `{"type":"error","error":{"type":"not_found_error","message":"Not Found"}}`. The endpoint string itself is not obviously rejected as malformed (a malformed path typically returns a different error pattern), but the plan provides no doc citation, no link to the published Admin-API spec, no schema of the response. Risk-1 (line 301) admits "Anthropic may not expose org-level message-count usage via Admin API … the public Admin API surfaces token usage and cost, not message-count quota." If true, this means the entire Admin-API rung returns a token figure that cannot be converted to a message-count `pct_remaining` against a *weekly message ceiling*. The plan acknowledges this then proposes to "translate token usage into a derived `pct_remaining`" — but does not show the formula, the conversion ratio, or the weekly-message-ceiling source. That conversion is the load-bearing logic for the entire deliverable; leaving it as a TBD is a MAJOR gap.

### F7 — `confidence_level` axes overlap; plan does not define the boundary
Plan declares 4 levels: `exact | heuristic | estimated | absent` (used per-agent), and aggregation introduces a 5th level `mixed` (line 207, 217). Definitions are inferred from context only:
- `exact`: live API/CLI returning ground truth (e.g., Admin-API, gemini-cli-quota)
- `heuristic`: local-state-derived (stats-cache, ccusage, gemini state.json)
- `estimated`: filecount/activity proxy
- `absent`: no signal

The dividing line between `heuristic` and `estimated` is unstated. Why is `stats-cache.json` heuristic (line 151) but `tmp filecount` estimated (line 192)? Both are local activity proxies — neither is calibrated against ground truth. Without an explicit decision rule (e.g., "heuristic = source counts the same units as the limit; estimated = source counts a proxy unit"), reviewers and downstream consumers cannot reason about the field. A test cannot verify the assignment, only its emission. This is a contract gap in the schema addition.

### F8 — `overall_targeting_confidence` aggregation rule is internally contradictory
Plan line 217 (pseudocode `routing_confidence`):
- `"mixed"  if any one is exact and others are heuristic/estimated`
- `"heuristic" if none are exact but at least one is heuristic`
- `"estimated" if all are estimated`

But the per-week rule (line 207, `derive_confidence_level`) treats `mixed` differently — it returns `mixed` if "at least one exact source" is among the entries, even if all others are exact. The two functions use the same five-value vocabulary but disagree on what triggers `mixed`. The acceptance criterion (line 275) says weekly payload carries `overall_targeting_confidence` "for the current week", but the test list (line 261) describes it as "worst-case downgrade" — yet the pseudocode is not a worst-case rule (worst-case would return `estimated` if any provider is estimated). The plan ships three different mental models for the same field name. Pick one and write it down.

### F9 — TDD test list has aspirational entries
- **`test_rate_limit_self_throttle`** (line 265): asserts "15-min cache TTL" — but `CACHE_TTL_SEC=900` (verified at `scripts/ai/assessment/query-quota.sh:20`) is the cache for the **whole `query-quota.sh` invocation**, not a per-probe cache. The plan does not specify whether the new probe libraries inherit the existing cache (which is at a higher level — gating the entire JSON snapshot) or introduce a second-level cache. If they inherit, the test as written is the same test as the existing top-level cache test (duplicate). If they don't, the plan needs to specify cache key, invalidation, and storage location — none of which appear. Test is unimplementable as drafted.
- **`test_gemini_cli_quota_path_returns_exact`** (line 253): mock `gemini quota --json` with valid output `{used: 12, limit: 1000}`. There is no live shape to mock against (F4) — the test will pass against a fictional contract.
- **`test_claude_admin_api_path_returns_exact`** (line 247): same problem — what is the response schema being mocked? Plan does not cite it.

### F10 — Cache TTL claim is hand-wavy on cache-key/invalidation
Plan line 303 / line 279: "the Admin-API probe will be wrapped by the existing 15-minute cache (`CACHE_TTL_SEC=900` …)". Inspection of `query-quota.sh` shows the existing cache is keyed on `agent-quota.json` and applies to the whole snapshot (line 32 `(( age < CACHE_TTL_SEC ))`). It does not provide per-probe caching. If the Admin-API probe is re-invoked across multiple non-cron callers (e.g., `query-quota.sh --refresh` from human invocation, plus the scheduled cron, plus any agent-side direct call), the existing top-level cache only protects the snapshot — the per-probe call still fires once per `--refresh`. The plan does not specify a per-probe cache and does not specify cache-key (org_id? week-bucket?) or invalidation (TTL? on-401? on-rate-limit-header?). Cache contract is hand-wavy.

### F11 — Open user-policy questions are incomplete
Plan surfaces 2 open questions (lines 308-309). Missing:
- **Q3:** When `confidence_level: exact` is cached for 15 min, should it decay to `heuristic` after the TTL expires (because the "exactness" was as of the API call, not as of the read)? Issue asks "exact vs heuristic" — staleness changes the answer.
- **Q4:** Should `confidence_level` be revision-bound (per `feedback_issue_2460_approval_binding`) — i.e., persisted with the SHA + timestamp at which the call was made? Currently the plan emits the field but does not version it.
- **Q5:** What happens when the Admin-API returns a 401/403 (auth revoked) vs 404 (path mismatch) vs 5xx — the plan says "log non-fatal warning" (line 143) but does not say whether the probe records the failure mode for later auditability. For `feedback_attestation_enables_contradiction_detection`, the difference between "auth missing" and "auth refused" matters.
- **Q6:** Where is `ANTHROPIC_ORG_ID` discovered? Plan references it as required env (line 135) but does not say how an operator finds it (`https://console.anthropic.com/settings/admin-keys` only? scriptable lookup?). Plan-approved means the operator needs to enable this — without a discovery step, the operator cannot move the system off `absent`.

## Blockers

1. **F1+F2+F3:** Gemini ladder is built on path/field claims that are factually wrong on the only machine where it would run. The "Evidence" section asserts files exist at `~/.config/gemini/` when they live at `~/.gemini/`, and the `dailyRequestCount` field that the heuristic rung depends on is not present in the actual `state.json`. Without correcting these, the Gemini side of the deliverable cannot achieve the issue's acceptance criterion ("source stronger than `estimated`").

2. **F4:** `gemini quota --json` does not exist on the installed CLI. The plan must either pin the CLI version that exposes the subcommand and verify on this machine, or remove the rung. As written, the "exact" Gemini path is aspirational and the test for it (`test_gemini_cli_quota_path_returns_exact`) tests a fictional contract.

3. **F5:** Anthropic Admin-API rung lacks (a) a doc citation for the endpoint, (b) the response schema, (c) the token→message conversion formula. The risk section concedes the API may not return weekly message ceiling, which is the load-bearing primitive. The plan must specify how it derives `pct_remaining` from token usage when message-count is unavailable, OR accept that Claude `confidence_level: exact` is unreachable and re-tag the rung as `heuristic`.

4. **F8:** `overall_targeting_confidence` aggregation has three contradictory specifications (per-week rule, top-level rule, test description). Pick one and document it.

5. **F6:** Plan's Artifact Map self-reference points to a non-existent file. Tools and reviewers chasing the table will hit a missing-file error.

## Strengths (max 3)

1. **Resource Intelligence is structurally well-organized.** The "Evidence (embedded verification)" subsection is the right shape — file-existence checks, line excerpts, gap proofs via grep. The execution is flawed (F1) but the format is exemplary and the failure mode is detectable on a single re-verification.

2. **Schema migration is genuinely additive.** Plan correctly identifies that `confidence_level` is a new field on existing artifacts, never removes a key, and notes that downstream consumers opt in. This avoids the kind of consumer-breaking change that would require coordinated rollout.

3. **Fallback-safety acceptance criterion is testable.** AC line 278 — "forcibly disabling all probes … results in `source: \"unavailable\"` / `confidence_level: \"absent\"` for both providers and the cron refresh exits 0" — is concretely testable and protects the no-regression contract from the issue body. Even though the path-up rungs are wobbly (F2-F4), the path-down floor is well-specified.
