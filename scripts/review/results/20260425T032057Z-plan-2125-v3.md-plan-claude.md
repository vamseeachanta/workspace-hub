### Verdict: APPROVE

### Summary
Strong v3 plan that systematically closes all r1 (Codex MAJOR) and r2 (Claude MAJOR + Gemini APPROVE) findings with explicit traceability tables, schema locks, defensive control flow, and matching TDD rows. The Attested Evidence block independently verifies every load-bearing claim against base SHA 12b4be83, and the per-test sys.path-shim discovery mechanism is documented inline so implementers cannot drift. One latent defect remains in the papers cache-hit path (legacy-meta `entry` key not defensively handled), but it is narrow enough to fix during implementation rather than block plan approval.

### Issues Found
- [P2] Defensive-lookup asymmetry in `ingest_papers` cache-hit path. The pseudocode (lines ~414-419) does `entries.append(cached["entry"])` and (lines ~425-429) `entries.append(cached["entry"])` on the fast-path branches. `safe_get_papers_entry` is only invoked in the prune branch (line 448). For a legacy/partial `papers_meta.json` row that lacks an `entry` key but happens to match `last_modified` + `content_length` (or `bytes_sha256`), this raises `KeyError` — exactly the failure mode the P2 #4 fix was meant to eliminate. The defensive lookup should be threaded through every path that reads `cached["entry"]`, not just pruning, OR the schema-lock should explicitly state that legacy rows missing `entry` are ineligible for the cache-hit fast-path and must be re-downloaded.
- [P3] Timezone inconsistency in `changelog_path`. The base name uses `date.today().isoformat()` (local timezone) while the collision suffix uses `datetime.now(timezone.utc).strftime("T%H%M%S")`. On a machine whose local tz crosses midnight relative to UTC, two refreshes ~minutes apart could produce filenames whose `<date>` segment doesn't match the `<HHMMSS>` segment's wall-clock day. Pin both to UTC (or both to local) for monotonic readability.
- [P3] `atomic_write_text` does not specify an encoding for `tmp.write_text(text)`. `Path.write_text` defaults to the platform's `locale.getpreferredencoding(False)` which is not always UTF-8 (notably on Windows non-en_US). Pass `encoding="utf-8"` explicitly so changelog markdown emitted from any host is byte-identical.
- [P3] `atomic_write_text` atomicity assumes `tmp` and `path` are on the same filesystem. `path.with_suffix(path.suffix + ".tmp")` keeps them in the same directory, so this holds in practice, but a one-line comment confirming the same-filesystem invariant would prevent a future refactor from silently breaking atomicity (e.g., redirecting tmp to `/tmp/`).

### Suggestions
- Replace `entries.append(cached["entry"])` in both fast-path branches of `ingest_papers` with `entry = safe_get_papers_entry(stored_meta, url); if entry is None: <fall through to download>; else: entries.append(entry)`. Add a TDD row `test_refresh_redownloads_when_legacy_meta_matches_headers_but_lacks_entry` to lock the behavior.
- Pin `date.today()` in `changelog_path` to `datetime.now(timezone.utc).date()` so date and timestamp segments share a clock. Update the existing `test_changelog_path_appends_timestamp_on_collision` to assert the date segment is UTC.
- Add `encoding="utf-8"` to `tmp.write_text(text)` in `atomic_write_text` and to any `read_text()` call on JSON/markdown side-files for symmetry.
- Optionally add a one-line acceptance-criteria check that running `--refresh` with `LLM_WIKI_DATA_DIR=/tmp/some-path` lands every artifact under `/tmp/some-path/{changelog,supplementary,papers}/...` — a live exercise of the output-root contract beyond the monkeypatched test, since the env-var branch of `resolve_wiki_dir` is the production deployment surface.

### Questions for Author
- For the legacy `papers_meta.json` cache-hit case, do you intend rows without an `entry` key to be (a) re-downloaded to backfill `entry`, (b) skipped entirely, or (c) tolerated as opaque cache hits? The P2 #4 closure documents the prune path only; the cache-hit path's intended behavior should be locked before implementation.
- Is there an expected upper bound on the refresh wallclock against a cold cache (~717 topics + 6 supplementary + N PDFs)? Acceptance criteria mention `< 60s for topics alone` on a warm cache but no ceiling on a cold first-`--refresh` run. Without one, a runaway implementation could pass tests but be unusable in the cron follow-on.
- If `assemble_product_topic_changes` receives a `product_results` list shorter than the three expected products (e.g., `ingest_product` raised on one), should `all_changes["product_topics"]` carry partial data, or should the changelog be suppressed entirely? Current pseudocode is silent on the partial-failure mode.
