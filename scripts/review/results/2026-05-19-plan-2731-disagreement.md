### claude

- **Quoted "Operating-model proof" text does not appear at the cited line range.** Plan §Evidence > Operating-model proof (lines 101-108) cites `docs/document-intelligence/llm-wiki-resource-doc-intelligence-operating-model.md`, lines 46-53, and quotes prose like `L1 Source documents — raw external/source files and original locations.` The actual content at lines 46-53 is the `## 2. This is the textbook "retrieval skepticism" failure case from rule #5 of the review prompt.
- **The operating model has six layers; the plan cites four.** The source file enumerates L1 Source documents, L2 Registry/provenance, L3 Durable knowledge, L4 Entry-point, L5 Execution state, L6 Transient session. The plan omits L4 and L6 in both the "Documents consulted" and "Operating-model proof" sections. Any future "owner layer" classification in the ledger (Pseudocode §`build_location_ledger`: "record … owner layer") will be incomplete if it inherits the plan's truncated layer set.
- **`llm-wiki` is not "planned/absent" — it already exists in three locations under `/mnt/ace`.** Acceptance criterion: "ledger defines planned private client `llm-wiki` repo targets as planned/absent unless explicitly created by a later approved issue." `ls /mnt/ace` shows `llm-wiki/`, `acma-llm-wiki/`, and `llm-wiki-archive/` are live directories today. The plan's classification cannot mark these "planned" without contradicting the filesystem. The contract needs an explicit reclassification decision for the three live `/mnt/ace/*llm-wiki*` directories, not a "planned" placeholder.
- **Stale-path scope is undefined and grossly under-scoped against live state.** Pseudocode §`validate_docs_contract` and test `test_selected_docs_do_not_reintroduce_unannotated_nested_repo_paths` both say "scan selected docs" without enumerating the set. Files-to-Change touches 4 docs (`data-intelligence-map.md`, `mounted-source-registry.yaml`, `ROUTING_INDEX.md`, `CONTENT_INDEX.md`). My `grep -rln "/mnt/local-analysis/workspace-hub/<repo>"` returns ≥38 docs across `docs/reports/`, `docs/handoffs/`, `docs/field-development/`, `docs/architecture/`, `docs/ops/mount-map.yaml`, `docs/governance/`, `docs/document-intelligence/mount-drive-knowledge-map.md`, plus several plan and overnight-prompt files. Either the test scope is the 4 named files (and 34+ stale references survive, defeating the contract) or it is "all docs" (and the implementer is silently signed up for 34+ corrections this plan does not scope). The plan needs an explicit `SELECTED_DOCS` list with rationale for inclusion/exclusion.
- **Proposed `repo-data-location-ledger.yaml` overlaps with existing `data/document-index/repo-portfolio-inventory.yaml`.** The plan creates a new ledger without acknowledging the pre-existing portfolio inventory in the same directory. Either the new ledger subsumes/supersedes the existing one (then the plan must say so and define migration), or it duplicates it (then it violates single-source-of-truth and creates drift risk). Plan §"Gap identified" claim ("No machine-readable ledger currently classifies each relevant path class…") is too narrow — the existing inventory at least covers the repo-class axis.
- **"Tier-1 repo" is used in acceptance criteria but never defined or anchored.** Acceptance: "ledger enumerates the live checkout set observed during implementation and does not claim every tier-1 repo is present on ace-linux-1." Test: `test_contract_declares_adjacent_sibling_checkout_model` for "tier-1 repos." Existing `docs/standards/TIER1_INDEXING_AND_CODE_PLACEMENT_CONTRACT.md` defines tier-1 — the plan never consumes it. Without a canonical reference, the test input is undecidable and the contract risks defining a second, conflicting tier-1 set.
- **Stale review artifacts contradict the "PENDING" claim and may mislead future scanners.** Plan §Adversarial Review Summary says all three providers PENDING. The filesystem already has `scripts/review/results/2026-05-19-plan-2731-{claude,codex,gemini}.md` as 0-byte files, plus `2026-05-19-plan-2731-claude.md.err` from a prior failed Claude attempt. The plan header at line 7 ("Review artifacts: …claude.md | …codex.md | …gemini.md") presents these as available evidence; combined with the 0-byte state, a future reader could be tricked into believing reviews ran. Either delete the empty placeholders before posting, or document the failed attempt and the `.err` sibling explicitly in the plan.
- **No worktree exemption for the "nested `workspace-hub/<repo>` is non-canonical" rule.** `.claude/worktrees/<feature>/<repo>` and similar parallel-session patterns (see `feedback_worktree_gitlink_pollution.md` in user memory) create transient nested-repo paths under `workspace-hub/`. Pseudocode `classify_path`: "if path matches /mnt/local-analysis/workspace-hub/<repo>: return legacy/non-canonical nested checkout reference unless explicitly temporary" — "explicitly temporary" is hand-waved. Without a concrete worktree-path allowlist (e.g., `^/.claude/worktrees/`) the contract and lint will flag normal parallel-agent operation. This is the same defect class the SHARED_SOUL.md "Enforcement scripts must not block their own artifacts" rule warns about.
- **No enforcement hook proposed; rule lives only in pytest.** `.claude/rules/patterns.md` describes the maturity gradient prose → script → hook and instructs promotion toward Level 3 for must-never-miss enforcement. This plan's gap statement says "No validation currently blocks future docs from reintroducing nested checkout references," and the response is a pytest test (Level 2 at best). A docs-writing PR can land stale paths between pytest runs. If the deliverable is a *contract*, prevention belongs in a pre-commit hook under `scripts/enforcement/`, not (only) in `tests/docs/`.
- **`CONTENT_INDEX.md` is acknowledged as generated but the generator is unnamed and not gated.** Plan §Risks: "docs/CONTENT_INDEX.md is large and may contain generated/stale inventory." Files-to-Change writes corrections directly into the generated file. Without identifying the regenerator and adding it to the change set, the next regeneration silently reverts the corrections. The plan does not name the generator script nor add it to Files-to-Change.
- **`test_live_layout_probe_is_documented` is a self-confirming check, not a defect-finding one.** The test verifies the implementer wrote something into the HTML notes file. It cannot fail on a real wrong claim about the filesystem; it only fails if the implementer skips a step. This is the same class as the "weak-fixture circular acceptance criterion" called out in the review prompt's example findings. Replace with a test that re-runs the probe and diffs against the HTML notes' recorded set.
- **"Optional" Files-to-Change row is unreviewable.** Files-to-Change row for `scripts/docs/check-repo-data-location-contract.py` is marked "Optional deterministic scanner if tests need reusable path-reference classification logic." Either the tests need this scanner (then it is required) or they don't (then it shouldn't be in the change set). "Optional" in a plan is a deferred-decision smell — the reviewer cannot evaluate the contract surface without knowing whether this script will exist.
- **`mounted-source-registry.yaml` change is undefined.** Plan says "Normalize source-root policy references where they conflict with `/mnt/ace` canonical/alias wording; avoid bulk source moves." Reading the file: `source_id: workspace_hub_local` already uses `/mnt/local-analysis/workspace-hub` (matches plan's control-plane statement), and `ace_standards_local`/`ace_project_local` already use `/mnt/ace/*` paths (no `/mnt/ace-data` references). The plan does not cite a specific conflict that needs normalizing. Either name the line-level edits or remove this row from Files-to-Change.
- **RED-phase acceptance is honor-system.** Acceptance: "RED phase is captured: `uv run pytest …` fails before the contract/ledger exists." Nothing forces a separate RED commit; the implementer can write tests + contract + ledger in one commit and then re-derive a "would have failed" claim. Per the TDD-mandatory gate, the plan needs an explicit commit-sequence (e.g., "Commit 1: tests only — RED; Commit 2: contract + ledger — GREEN") referenced in acceptance criteria.
- **Per-machine vs portfolio-canonical contract is unresolved.** Acceptance: "ledger enumerates the live checkout set observed during implementation and does not claim every tier-1 repo is present on ace-linux-1." This makes the ledger inherently machine-relative. But the contract document is a portfolio-canonical standard. Reviewer needs an explicit statement of which artifact is the per-machine snapshot and which is the portfolio invariant, plus how the test handles a multi-machine ledger (one file with all machines? one file per machine? machine-stamp envelope?). Today's plan implies one ledger file with one machine's data, which will conflict on a different machine.
