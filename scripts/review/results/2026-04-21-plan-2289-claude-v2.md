## 5. New v2 defects (MINOR)

### N1. `staged_files_digest` definition is internally inconsistent

**Claim A** (§Log Schema table): "`staged_files_digest` ✓ (sha256 of staged file **names**)"
**Claim B** (§Risks): "staged_files_digest includes staged-file **content-hash**, not just names"

These are different: a hash of file NAMES would be stable across content changes on the same file set; a hash of file CONTENT would differ. The correlator's join semantics depend on which is used. If the pre-commit hook hashes names and the post-commit correlator joins on content, correlation fails silently.

**Required:** Pick one. Recommendation: hash both (names + content-sha256) so content-aware collision avoidance AND quick lookup both work. Or explicitly scope as hash of the staged-file-names list only, and accept the (small) risk of two commits with identical file sets landing within 5s.

### N2. `has_approval_intent` "explicit approval phrase" is not defined

`has_approval_intent(commit_sha)` is specified to detect "marker file contents containing explicit approval phrase, or a post-commit GitHub label transition to `status:plan-approved`." The exact phrase pattern is not defined — is it the literal string "Approved by:", any regex match, etc.?

**Required:** Add a normative definition, e.g., "marker file must contain a line matching the regex `^Approved by: [^\\s]+` to count as explicit intent." Otherwise the test `test_advisor_distinguishes_advisory_mode_from_explicit_approval` has no deterministic oracle.

### N3. `--strict` exit semantics silent on unresolvable events

The advisor emits `log_only_unresolved` when a bypass event has no resolvable commit SHA. §Pseudocode: `if not event.resolved_sha: event.verdict = "log_only_unresolved"; continue`. §Key Design Decision #6 says `--strict` exits 1 "when `revert_recommended` verdicts exist" — but does NOT mention unresolved events. Should `--strict` also exit non-zero on unresolved events?

**Required:** Explicit decision. Recommendation: `--strict` exits non-zero for `revert_recommended` OR `log_only_unresolved`, since unresolved SHAs indicate observability gap worth surfacing.

### N4. Install-hook wiring is not under test

§Files to Change adds a post-commit hook wiring to `install-hooks.sh`, but §TDD Test List has no test verifying the wiring actually installs. If a user runs `install-hooks.sh` and the post-commit hook isn't invoked, none of the advisor flow fires.

**Required:** Add `test_install_hooks_wires_post_commit_bypass_logger` — fixture: clean `.git/hooks/` dir, run `install-hooks.sh`, assert `.git/hooks/post-commit` contains or sources `post-commit-bypass-logger.sh`.
