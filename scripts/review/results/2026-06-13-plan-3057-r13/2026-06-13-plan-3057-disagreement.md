### claude

- **Module-cycle hazard between `cron_transaction.py` and the new `cron_render.py` is unspecified.** Files-to-Change (line 503) places the shared raw+rendered catalog-key builder *and* the shared one-space line renderer in `cron_transaction.py`, while the key builder must call `render_catalog_task_for_cron` (pseudocode 343–352, living in `cron_render.py`), and `render_block` (cron_transaction.py:269) must consume the shared `render_cron_line`. That forces `cron_transaction → cron_render`. The plan never states that `cron_render` imports **nothing** back from `cron_transaction` (markers, `parse_crontab`, `_is_ignore_line`). Across a 6-file rewire this is the single most likely way the focused-test gate fails at import time. Recommend the plan pin the import direction explicitly (cron_render is leaf; cron_transaction depends on it, never the reverse) and add it to the `cron-audit.py --json` smoke rationale (line 544 only covers "imports and runs after moving shared helpers," not the cycle direction).
- **Schedule-by-machine precedence is only tested for the live-host alias case; cross-machine `--machine` preview is untested and may pick the wrong stagger.** Pseudocode line 334 sets `hostname_short = live hostname when rendering for the current host, else machine.hostname`. Acceptance only exercises `--machine vamsee-linux1` resolving to `dev-primary` *on its own host* (line 570) where live hostname `ace-linux-1` correctly yields `5 4`. But `provider-dream-bridge` carries distinct sbm values per machine (`dev-primary:0 4`, `ace-linux-1:5 4`, `dev-secondary:10 4`). If `cron_apply.py --machine dev-secondary` is ever run from ace-linux-1, "current host" detection vs explicit `--machine` is ambiguous in the pseudocode and could emit ace-linux-1's `5 4` for a dev-secondary plan. No TDD entry (525–527) covers a `--machine` that is *not* the live host. Add a test or an explicit statement that `--machine <non-live>` uses the resolved machine's registry hostname for sbm precedence.
- **`TOTAL_TIMEOUT_SEC=480` safety margin rests entirely on warm-cache evidence.** The only live timing in the plan is `elapsed=16.13` for 17 repos (line 235), explicitly warm-cache; individual probes already hit 11.81s/10.41s (205–209), and the 480s budget leaves only a stated 120s buffer to the 600s gap (Risk, line 695). The acceptance (line 579) defers cold-cache proof to implementation closeout, which is acceptable — but the *plan* asserts production-safety of 480 without any cold-cache or larger-repo-set datapoint. This is correctly flagged as residual risk, not hidden; noting it so reviewers don't read 16.13s as the worst case.
- **Redundant `REPO_ECOSYSTEM_HYGIENE_*` env lines survive forever and can silently override the new tracked defaults.** The fix moves 30/120 into the script, but the live crontab env lines `REPO_ECOSYSTEM_HYGIENE_PROBE_TIMEOUT_SEC=30` / `=120` (reproduction 142–143) classify as `ignore` and are preserved verbatim (zero-removal). If a future maintainer raises the tracked default, the stale crontab env line wins at runtime with no warning. The plan accepts this (Risk, line 693) but does not note the *override-precedence* consequence — worth one sentence so the redundancy isn't mistaken for harmless duplication.
- **`catalog_commands` is being relocated and signature-widened (`fallback_mode=`), but caller inventory is asserted, not enumerated.** The plan assumes `cron_apply.py:153` and `cron-audit.py` are the only consumers. No grep evidence in the plan confirms there are no other importers of `cron_apply.catalog_commands`. A stray caller would break silently after the move. Low cost to enumerate; recommend a `grep -rn catalog_commands` line in the evidence section.

### codex

- Plan §Pseudocode lines 464-467 makes `cron_audit` call `classify_line_detail` with “all catalog task ids”, while §Pseudocode lines 451-453 makes `cron_apply.py` call `plan_cutover` with only `selected_task_ids`. That contradicts acceptance criteria lines 568-569 and test row line 543, which require audit/apply classification agreement and dedupe “only when the catalog task is selected.” The concrete hazard is `notification-purge`: it is machine-pinned to `dev-primary`/`ace-linux-1` in `config/scheduled-tasks/schedule-tasks.yaml:311-315`, and the loose preserved-local fingerprint matches by `find logs/notifications/` + `-delete` in `config/workstations/harness-state-classes.yaml:120-130`. On a machine where `notification-purge` is not selected, audit would classify the loose line as catalog-owned/cataloged, while apply would not. The plan needs target-machine selected ids for audit, or explicit unselected catalog-owned tests and semantics.
- The verification gates can produce false passes for newly created files. The plan creates `scripts/cron/cron_render.py` and `tests/cron/test_cron_render.py` at lines 501 and 510, but the legal gate at line 590 runs `scripts/legal/legal-sanity-scan.sh --diff-only`; that script builds its file list with `git diff --name-only HEAD` at `scripts/legal/legal-sanity-scan.sh:185-188`, which does not include untracked files. The absolute-path gate at line 591 runs `scripts/enforcement/check-no-abs-paths.sh` with no path args; that script scans `git ls-files '*.sh' '*.py'` at `scripts/enforcement/check-no-abs-paths.sh:62-68`, also excluding untracked new files. The plan must require staging/tracking before these gates or pass the new file paths explicitly.
