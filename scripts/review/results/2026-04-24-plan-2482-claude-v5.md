## Findings

### MAJOR

1. **`signoff_sha` semantics undefined — schema is ambiguous on what SHA to pin.** The schema inline comment says "SHA of the wiki page at approval time" (line 296) but that phrase could mean three distinct things:
   - `git log -n1 --format=%H -- <path>` (commit that last touched the file — *per-file blame SHA*)
   - `git hash-object <path>` (blob SHA of the file's content — *content-addressable*)
   - Repo HEAD at approval time (*tree SHA*)
   Different choices have different invalidation semantics: a blob SHA invalidates only when the file's bytes change; a per-file commit SHA invalidates when ANY commit touches the file (even renames/whitespace); a tree SHA invalidates on every commit to the repo. The linter's Rule 6 compares `signoff_sha` to `$HEAD` (line 265) — i.e., repo HEAD. If the ledger intends blob or per-file SHA, the linter is wrong; if the ledger intends HEAD, every commit invalidates every ledger entry (which is almost certainly not the intent). The v4 review flagged this as an open question and v5 did not resolve it. Fix: schema comment must specify exactly one of the three; linter pseudo-code at line 265 must match. Recommend `git hash-object <path>` (blob SHA) — stable against rename, invalidates only on content change, matches #2460's revision-binding pattern.

2. **Python fallback is a dangling reference — not in Files-to-Change, not acceptance-criterion-covered.** Line 264 names `tools/gtm-boundary-ledger.py` as the fallback for environments without yq. `ls tools/gtm-boundary-ledger.py` returns ENOENT. Files-to-Change table has no row for it. Acceptance Criteria do not require it. Yet yq is NOT on the review machine, so the linter as written would fail Rule 6 on this very machine unless yq is installed or the fallback exists. The plan has created a conditional dependency it does not fulfill. Fix: either (a) add a Files-to-Change row creating `tools/gtm-boundary-ledger.py` and an acceptance criterion that it runs the same ledger query, OR (b) make yq a hard dependency and add an acceptance criterion that installs yq OR exits the linter with a clear "install yq" message rather than failing silently.

3. **Exit-code semantics block contradicts new Rule 2 behavior.** Lines 273–274 state "`exit 0` requires a valid ledger entry" and "`exit 2` is the max state a page can reach without a ledger entry". Under v5, scope-bounding pages (`overview.md/index.md/log.md`) reach exit 2 REGARDLESS of ledger state — a ledger entry does NOT promote them. The semantics block does not acknowledge this exception. A reader using only the semantics block (not the pseudo-code) will infer that writing a ledger entry for `overview.md` yields exit 0 — exactly the bootstrapping-hazard reading that Rule 2's terminal fix was meant to eliminate. Fix: append to the semantics block something like: "Exception: scope-bounding pages (Rule 2) are never ledger-eligible. For those paths, exit 2 is terminal regardless of ledger state; a ledger entry for a scope-bounding path is a governance error and is ignored by the linter."

### MINOR

1. **Exercise table row 2 wording is stale.** Line 355 still reads "Rule 2 carve-out applies → Rule 6 ledger check returns empty → exit 2". Under v5 terminal Rule 2, this should read "Rule 2 carve-out applies → terminal exit 2 (ledger check SKIPPED)". Cosmetic but misleading for a reviewer running `bash -x` and expecting to see ledger-file access.

2. **No defined path to add a legitimate new top-level wiki file.** Rule 1b's default-deny for `knowledge/wikis/*.md` is good conservative policy, but plan does not specify how a future legitimate top-level artifact (e.g., a hand-curated domain map) would be made publish-eligible. Implicit answer: the page would need `auto_generated: true` (but that's a lie if hand-curated) or would need an explicit exception added to Rule 1b. Plan should state the exception-addition procedure, or declare top-level files permanently ineligible.

3. **Schema edge cases undefined.** Schema block lists `scope: single-publish | recurring-until-<date>` but does not define: (a) revocation — how does an approver rescind an entry, and does the linter treat revocations? (b) expiry — does `recurring-until-<date>` auto-fall-off when date passes, and does the linter check it? (c) multi-approver co-signs — required for high-stakes content? (d) what happens if two entries exist for the same path with different SHAs (newest wins? both valid?). Small-team project context may make these low-priority, but they should be explicitly deferred rather than silently omitted.

4. **Acceptance criterion line 394 is stale.** Reads "Fresh Claude adversarial self-review of **v3** returns APPROVE". Should be v5. Textual cleanup.

5. **"Signoff commit signature" is prose-only.** Line 311 says the pre-commit hook "blocks ledger edits that don't include a matching signoff commit signature" without defining what a "signoff commit signature" is — GPG sign? Committer-identity-equals-approver? Trailer like `Signed-off-by:` per DCO? The hook is "in scope" per the same line but has no behavioral spec. This overlaps with MAJOR 2 but deserves separate flag: even if the hook file is added to Files-to-Change, the behavioral contract is undefined.

6. **Concurrent ledger edits / missing ledger file not discussed.** The initial state is `entries: []` but the plan does not say what the linter does if `docs/governance/gtm-publish-ledger.yaml` is entirely absent (first run before commit). Rule 6 pseudo-code would cause `yq` to fail with file-not-found, and the linter's exit code is unspecified. Conservative default should be: missing ledger → treat as empty → exit 2 (not exit 0, not error). Spell it out.

## Verdict rationale

v5 makes substantive progress on all four v4 MINORs: Rule 2 correctly terminates at exit 2 (closing the bootstrapping hazard — this is a clean fix), Rule 1b correctly handles today's top-level file surface (verified against `ls knowledge/wikis/*.md`), a ledger schema block is written out, and the parser choice is named. However, the v5 sweep introduced consistency and completeness regressions serious enough to warrant MAJOR re-review:

- MAJOR 1: `signoff_sha` semantics are ambiguous and the linter pseudo-code appears to compare to repo HEAD (which would invalidate every entry on every commit) — the revision-binding contract is not implementable as written.
- MAJOR 2: the Python fallback and pre-commit hook are referenced as live artifacts but absent from Files-to-Change, and yq is not actually present on this machine, so the linter in its current form cannot satisfy Rule 6 here.
- MAJOR 3: the exit-code semantics block was not updated to reflect the terminal Rule 2 change, leaving the plan internally inconsistent and reintroducing (in prose) the very bootstrapping reading the pseudo-code fix eliminated.

Plus six MINORs, most of which are documentation sweep items (exercise-table wording, acceptance-criterion version-number, stale re-review pointer) but several of which are substantive enforcement gaps (top-level-file exception-addition procedure, signoff signature mechanism, missing-ledger-file behavior).

Verdict: **MINOR is not tenable** — the dangling Python fallback + ambiguous `signoff_sha` + inconsistent exit-code semantics are implementation-blocking. **MAJOR** is the correct call — one-more-iteration is warranted, but each finding has a concrete 1-to-3-line fix. v6 can reasonably close all of them.
