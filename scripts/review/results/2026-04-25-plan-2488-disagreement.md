### claude

- **Inconsistent invocation chain for `verify_issue_2488_baseline_order` between Pseudocode and Files to Change.** Pseudocode line 225 says: "have `scripts/skills/reconcile_filesystem_only_skills.py` invoke `scripts/skills/verify_issue_2488_baseline_order.py --base-ref <base> --head-ref <head>` in strict mode" — i.e., the Python script is invoked directly. Files-to-Change line 252 says of the `.sh` file: "The manual reconcile script invokes this in strict mode, making it a closeout-script gate". Two contradictory invocation chains: reconcile→`.py` direct (Pseudocode) vs. reconcile→`.sh`→`.py` (Files-to-Change). TDD line 297 (`test_manual_reconcile_invokes_baseline_order_guard_in_strict_mode`) does not pin which target the reconcile invokes. Implementer must pick one and the test will need to assert the chosen entrypoint by name.
- **Exit code 1 unspecified in manual reconcile CLI contract.** Plan §Pseudocode line 206 enumerates exit codes 0 (success), 2 (ledger validation/terminal-state failures), 3 (untrusted git/filesystem inventory), and 4 (CLI usage errors). Acceptance criterion line 322 mirrors this: "exit codes 0/2/3/4". The most common nonzero failure mode — `missing_tracked_active>0` (a tracked active skill present in `git ls-files` is absent from the filesystem, indicating real loss) — has no enumerated code. Implementation will fall through to either implicit `1` or get classified under `2` ("terminal-state failures"), but the plan does not pin which. The docs/ops/scheduled-tasks.md acceptance bullet asserts the documentation must list exit codes 0/2/3/4 only, which means the missing-tracked case will either be undocumented or silently bucketed.
- **`scan_attestation.tool_or_method` is a free string with no minimum-quality threshold.** Plan §Pseudocode line 215: `scan_attestation schema: {tool_or_method, scope: full_file|frontmatter|content_overlap, scanned_at, finding_count, finding_summary, reviewer}`. Plan TDD line 298 (`test_scan_attestation_required_for_promote_commit_and_personal_or_memory_skills`) tests presence/absence but does not test attestation quality. A reviewer could record `tool_or_method: "manual review"` and pass validation for promoting a skill from `digitalmodel/*` (gitignored as `digitalmodel/` per `.gitignore:14`) without any actual secret-scanner invocation. The `user_authorization_when_personal` requirement only applies to `personal-*` leaf slugs (acceptance line 327), not to `digitalmodel/*` or `memory/*` ignored paths. Pin a minimum scanner contract (e.g., `tool_or_method ∈ {gitleaks, trufflehog, manual:reviewer-attestation}` with explicit semantics, or require regex+entropy evidence in `finding_summary`) to close this gap.
- **`--inventory-json` "matching trust attestation" matching semantics undefined.** Plan §Pseudocode line 205: "rejected for real manual closeout unless paired with --trust-attestation containing a matching live trust attestation generated during the same run". Plan §Pseudocode line 211 schema includes `inventory_json_sha256_when_replayed`, suggesting hash equality is the intended match key — but this is not stated. TDD row at line 280 (`test_manual_reconcile_inventory_json_requires_trust_attestation`) describes "matching trust_attestation in closeout mode" without pinning what equality constitutes a match. As written, an implementation could ship with a trust-attestation match check that compares only `repo_root` or `git_head` and would silently accept a stale or fabricated inventory JSON. Pin: "match means `sha256(inventory_json) == trust_attestation.inventory_json_sha256_when_replayed`".
- **`v2.rules.filesystem-inventory.filesystem-only-active` notation in Files-to-Change line 244 is ambiguous between flat-dotted-key and nested-dict shape.** Verified at config/skills/weekly-audit-policy.yaml line 309-339: existing entries use the flat-dotted-key shape (e.g., `content-quality.malformed-frontmatter:` as a single YAML key). `_finding_defaults()` at scripts/skills/weekly_skills_audit.py:343-345 looks up `cfg.get(f"{family}.{rule_id}", {})`, confirming the flat shape. Plan acceptance line 311 says: "`v2.rules.filesystem-inventory.filesystem-only-active`" — this could be misread as a 4-level nested path (`v2 → rules → filesystem-inventory → filesystem-only-active`). An implementer who normalizes this to nested YAML will produce a key the existing loader cannot resolve. Pin the literal YAML excerpt: `v2.rules: { "filesystem-inventory.filesystem-only-active": { severity: ..., headline: true, ... } }`.

### codex

- The plan is not approval-ready on its own stated evidence contract. Its frontmatter `Review artifacts:` still points at `scripts/review/results/20260425T125029Z-plan-2488-*.md`, and its `## Adversarial Review Summary` explicitly says the “current immutable review evidence ... still contain MAJOR findings” and “do not move to `status:plan-review` until a subsequent pushed re-review has no unresolved MAJOR findings.” The later acceptance criterion requiring “fresh post-revision timestamped `*-plan-2488-*.md`” therefore fails against the artifacts this revision cites. This is a blocker for any claim that the plan is ready to advance.
- The manual replay trust contract is internally inconsistent. In the `manual CLI contract for scripts/skills/reconcile_filesystem_only_skills.py`, the plan says `--inventory-json PATH` is rejected unless paired with `--trust-attestation` “containing a matching live trust attestation generated during the same run.” In `validate_and_render_dispositions_for_manual_reconcile(...)`, the same plan says to “write trust_attestation JSON at the configured path.” That makes `--trust-attestation` both required preexisting input and generated output in the same execution. A single run cannot consume a file that only comes into existence later in that same run.
- The source of truth for `issue_body_six_drift` is undefined. In `build_skill_inventory_with_git(...)`, the required JSON schema includes `inventory_summary.paths.issue_body_six_drift`, and later `validate_and_render_dispositions_for_manual_reconcile(...)` requires `issue_body_drift_note` when a known issue-body path vanished. But the only authoritative list of those six paths is prose in issue `#2488` / the plan narrative itself; no tracked config file, constant source, or ledger seed file is named for the weekly audit to read. As written, the implementation either has to hard-code issue prose in Python or cannot populate this field deterministically.
- `_diverged` handling is still under-specified for the numeric counts. In `build_skill_inventory_with_git(...)`, the `active_filter(path)` description says `_archive` and `_archived` are non-active, while `_diverged` is “excluded from active-loss findings” and also reported separately in `legacy_diverged_compatibility_total`. The same function returns `tracked_active` and `filesystem_active`, but the plan never pins whether those counts include or exclude `_diverged`. Issue `#2488`’s baseline counts exclude only `_archive` and `_archived`; the plan’s loss-risk semantics additionally quarantine `_diverged`. Without an explicit rule for the count fields, future runs can drift while still appearing compliant.
- The shell helper contract leaves a repo-policy violation path open. `AGENTS.md` says “Python: `uv run` always — never bare `python3`.” The plan creates `scripts/skills/verify_issue_2488_baseline_order.sh` plus `scripts/skills/verify_issue_2488_baseline_order.py`, but nowhere in `Files to Change`, `Pseudocode`, or `Acceptance Criteria` does it bind the shell wrapper to invoke the Python helper via `uv run --no-project python`. That omission is smaller than the blockers above, but it leaves an avoidable policy hole in an otherwise very prescriptive plan.
