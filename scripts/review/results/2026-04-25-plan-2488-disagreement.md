### claude

- **Pseudocode/proof drift on path-segment matching.** Plan §Pseudocode line 156 says active filtering must use "exact path segments _archive and _archived"; but the embedded live-inventory proof (lines 70-71 of the plan, which the plan promotes as the implementation rule) uses `f'/{x}/' in p` — a substring scan, not a segment-equality test. The drift bites in two ways: (a) any path that begins at the root segment `_archive/...` lacks a leading slash and would not match `'/_archive/'`; (b) the plan's own test `test_inventory_summary_excludes_archive_archived_and_reports_diverged_compatibility_count` requires "substring-only names do not over-match", which `f'/{x}/'` satisfies only by accident of `.claude/skills/...` always producing leading slashes. Implementation must pin the exact rule (use `Path.parts`, not substring) so the test isn't testing a coincidence.
- **Pseudocode line 155 misstates existing `build_inventory` pruning.** Plan claims the existing walk "prunes `_archive`/`_diverged` and would undercount archived filesystem-only files." Verified at `scripts/skills/weekly_skills_audit.py:32,72`: `EXCLUDED_DIRS = {"_archive", "_diverged"}` — `_archived` is NOT pruned by the existing walk. So the existing audit already counts `_archived` filesystem-only files; the rationale "would undercount archived filesystem-only files" is half-wrong. The plan should re-anchor this rationale to "`_archive`/`_diverged` are pruned but `_archived` is not, so neither the existing walk nor a strict-active filter alone is sufficient" — otherwise the implementer may believe they need to bypass `EXCLUDED_DIRS` entirely.
- **Render-pipeline integration is underspecified.** Plan §Pseudocode lines 192-193 require BOTH (a) an unconditional Markdown section "Filesystem-only skill files" listing every path regardless of ledger state, AND (b) a high-signal finding when `unresolved_filesystem_only_active_count > 0`. The audit script's existing `_all_active_findings()` (verified at `weekly_skills_audit.py:766`) iterates a fixed family-key list (`findings`, `content_quality_findings`, `grouping_findings`, `size_findings`, `usage_findings`); `_append_finding_section` (line 793) consumes a finding shape with `classification`, `finding_key`, `severity`, `confidence`, `paths`, `recommended_action`, `summary`, `headline`. The plan does not specify (i) the new family-key name to add to `_all_active_findings`, (ii) the exact finding-shape fields a `filesystem_only_active` entry must populate, or (iii) how the unconditional inventory section relates to the filtered finding render. Acceptance criterion #283's claim that tests will "prove the weekly-audit parser plus `_all_active_findings()`/Markdown rendering consume those keys" cannot be implemented without this contract being pinned in the plan.
- **Acceptance criterion line 285 "duplicate/collision delta is zero" is undefined.** Verified: AC reads "implementation must record a pre-change `_archived` duplicate/collision baseline and assert duplicate/collision delta is zero". "Delta" is not specified — total finding count, finding-id set equality, per-classification counts, or per-finding-key equality? Test list test #275 (`test_existing_duplicate_collision_fixture_counts_unchanged`) tightens this to "duplicate/collision summary counts and finding IDs are unchanged", but the AC and test use different language. Implementer can pass the loose AC trivially while breaking the strict test, or vice versa. Tighten AC to mirror the test wording.
- **Manual reconcile CLI surface not pinned.** Acceptance criterion line 292 names the manual-reconcile invocation as `scripts/skills/reconcile_filesystem_only_skills.py --disposition-report docs/reports/2026-04-25-skills-disposition-2488.md`, but §Pseudocode line 197 only declares a function `validate_and_render_dispositions_for_manual_reconcile(disposition_yaml)` taking a YAML path. Missing from the plan: the script's full argparse surface — does it take `--disposition-yaml`, `--disposition-report`, `--skills-dir`, `--strict`? Where does it source the inventory snapshot? Test #261 `test_manual_reconcile_hard_fails_on_untrusted_or_partial_inventory` requires a "git adapter" injection seam, but the plan does not specify it as a CLI flag or environment input. Without a pinned CLI contract, the test list cannot be implemented as written.
- **Optional ledger-annotation flag is implied but not declared.** §Files to Change row for `scripts/skills/weekly_skills_audit.py` (line 226) calls for "optional read-only ledger annotation"; acceptance criterion line 292 also says "the existing weekly audit CLI flags ... remain backward-compatible." But how does the audit script reach the new ledger at `config/skills/filesystem-only-skill-dispositions.yaml`? Either (a) a new flag (e.g. `--ledger`) must be added — in which case `tests/cron/test_skills_curation.py` and the plan's wrapper-invariance language need updating — or (b) the path is hard-coded — in which case test seam injection must be specified. The plan picks neither.
- **Symlink-mirror acceptance criterion is unverified by test.** Acceptance criterion line 286 requires `.codex/skills` and `.gemini/skills` "remain symlink mirrors; no provider duplicate skill trees are created." Test list entry `test_inventory_summary_records_provider_skill_mirror_symlinks` only verifies the resolver-injection seam serializes link metadata correctly using injected fixture data — no test exercises the live symlink state. The AC is therefore checked manually, not enforced. Either add a test that asserts `Path('.codex/skills').is_symlink() and Path('.codex/skills').readlink() == Path('../.claude/skills')` against the live tree, or downgrade the AC to a manual operator check.
- **`_diverged` tracked-active count is asserted from a filesystem-only spot-check.** Plan §Resource Intelligence line 19 / 104 says "928 - 6 = 922" with the 6 being tracked `email/_archived`, and asserts compatibility by saying a "parity spot-check found zero current `_diverged` filesystem-only active SKILL.md paths." Verified independently: tracked `_diverged` SKILL.md count is 0, so the arithmetic happens to be correct — but the plan's own evidence sentence cites a *filesystem-only* spot-check to back a *tracked-count* assumption. Add a tracked-count check to the embedded proof so the 928↔922 reconciliation is directly evidenced, not coincidentally correct.
- **Latent policy↔code inconsistency is not flagged as a follow-up.** Discovered (not in plan): `config/skills/weekly-audit-policy.yaml` lines 299-308 already define `category_alias_families: [{id: archive, canonical: _archive, aliases: [_archive, _archived]}]`. The policy already considers `_archive` and `_archived` semantically equivalent for category aliasing, but the audit script's `EXCLUDED_DIRS` does not. The plan's deliberate decision to keep `EXCLUDED_DIRS` unchanged (to preserve duplicate/collision behavior) is defensible, but it widens the policy↔code drift without acknowledgement. Add a Risk entry or a follow-up issue note so the inconsistency isn't lost.
- **`logs/maintenance/` path claim conflicts with `.gitignore`.** Plan §Risks acknowledges "`logs/maintenance/...` is transient/ignored" and routes durable state elsewhere. Verified: `.gitignore` line 95 (`logs/*`) plus the explicit allow-list at lines 96-111 do not negate `logs/maintenance/`, so audit artifacts under that path are gitignored as the plan claims. No defect — but the AC line 282 says "Active filesystem-only files that remain on disk are listed regardless of ledger status" — operators reading the cron-emitted Markdown will see the listing only in untracked log output, not in any tracked artifact. The plan should make this explicit so reviewers don't assume the recurring report is tracked.

### codex

- The plan weakens the issue’s explicit six-skill acceptance into a moving-target runtime set. Issue `#2488` says `All six active filesystem-only skills are individually classified with an explicit disposition.` The plan’s acceptance criteria instead say `the current known count is six local files, but success is not hard-coded to six if live state changes.` That allows one of the six issue-listed paths to disappear before implementation and then never be dispositioned or explained. The plan needs a fail-closed rule for the issue-body six: either each gets a recorded terminal disposition, or the plan must require an explicit drift note for any path that vanished before reconcile.
- The plan’s JSON contract is internally inconsistent. In `Pseudocode`, `inventory_summary.paths` is defined as `filesystem_only_active: [{path, informational_namespace}]`, `missing_tracked_active: [{path, informational_namespace}]`, and `filesystem_only_archived: [{path, informational_namespace}]`. In `Acceptance Criteria`, the same arrays are required to contain `{path, informational_namespace, ledger_status}` objects, and the weekly mode text depends on `ledger_status: resolved_ignored`. That field is missing from the pseudocode schema, so the data contract the implementer is supposed to build is not stable.
- The policy-driven design is underspecified against the current implementation. The plan says `filesystem_only_active` should be appended to `config/skills/weekly-audit-policy.yaml` and consumed through the existing policy loader plus `_all_active_findings()` / `_write_markdown_artifact()` instead of hard-coded Python. But `scripts/skills/weekly_skills_audit.py` currently aggregates only fixed families (`findings`, `content_quality_findings`, `grouping_findings`, `size_findings`, `usage_findings`) and `_write_markdown_artifact()` renders a fixed section list. `config/skills/weekly-audit-policy.yaml` likewise has fixed `weekly_summary_sections` and `ranking_policy`. The plan does not specify the required schema and code refactor that would make `filesystem_only_active` a first-class policy-driven family rather than another bespoke branch. As written, the acceptance criterion is not implementable without inventing design details during coding.
- The plan adds a new weekly Markdown section but does not define whether it is inside or outside the current policy-controlled section order. The acceptance criteria require `Weekly Markdown output includes a high-signal section listing active filesystem-only skills when any exist.` The current policy file defines only five weekly sections in `weekly_summary_sections`, and `docs/standards/weekly-skills-audit-policy.md` documents that same five-section order. If the new filesystem-only section is policy-governed, the plan must say how `weekly_summary_sections` and `ranking_policy` change. If it is outside policy, that contradicts the plan’s own “policy-driven rather than bespoke constants” requirement.
- The baseline-proof step is sequenced too loosely to be trustworthy. The plan requires a pre-change fixture at `tests/fixtures/skills/issue-2488-archived-duplicate-baseline.json` and a regression asserting duplicate/collision delta is zero, but `implementation_flow()` only says `RED/GREEN` on `_archived` exclusion and never requires capturing that fixture before any audit logic change. Without an explicit “capture baseline first” step, an implementer can generate the baseline after the new code lands and trivially prove `delta = 0` against their own post-change output.
