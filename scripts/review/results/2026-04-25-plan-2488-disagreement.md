### codex

- The plan expands far past the issue-defined scope without a cited requirement. Issue `#2488` scopes this to re-running inventory, classifying filesystem-only skills, prioritizing the six active ones, and adding weekly high-signal reporting. The plan’s `Pseudocode` and `Files to Change` add a new manual subsystem: `scripts/skills/reconcile_filesystem_only_skills.py`, `config/skills/filesystem-only-skill-dispositions.yaml`, `docs/reports/issue-2488-skills-disposition-trust-attestation.json`, replay trust rules, exit-code semantics, hash schemas, and per-disposition attestation contracts. That is a new reconciliation framework, not a bounded extension of the weekly audit, and no source in the issue or existing policy files requires it.
- The recurring JSON schema is internally contradictory. In the plan’s `Pseudocode`, `inventory_summary.paths` is pinned to objects containing only `{path, informational, ledger_status}`, and it explicitly says “Issue-specific drift … is manual-closeout report content, not recurring weekly-audit schema.” The `Acceptance Criteria` repeats that weekly path arrays use `{path, informational, ledger_status}` objects. But the TDD row `test_inventory_summary_schema_separates_counts_paths_and_mirrors` still allows “drift fields for issue-body drift” in those recurring path objects. That gives the implementer two incompatible contracts for the same JSON surface.
- The ledger/validation model is inconsistent for vanished issue-body paths. In `validate_and_render_dispositions_for_manual_reconcile(...)`, the plan says to “require one entry per active filesystem-only skill discovered at implementation time,” but in the same section it also requires `issue_body_drift_note when a known issue-body path is absent before reconcile`. The `Acceptance Criteria` goes further: “The six issue-body paths must each have either a terminal disposition or `issue_body_drift_note` if the path vanished before reconcile.” A vanished path is not an active filesystem-only skill, so the plan never defines where that non-live row belongs or how the validator distinguishes historical drift-note entries from live inventory entries.
- The plan’s own retrieval conclusion for scheduled-task docs conflicts with the implementation contract it later imposes. Under `Documents consulted`, it says `docs/ops/scheduled-tasks.md` “should update docs only if output semantics materially change.” But `Files to Change` and the later `Acceptance Criteria` require that same scheduled-task inventory doc to become a full manual CLI reference for `reconcile_filesystem_only_skills.py`, including all flags and exit codes `0/2/3/4`. That is not the recurring scheduled-task contract described in `docs/ops/scheduled-tasks.md`; it is new operator-tool documentation grafted onto a different source-of-truth file.
