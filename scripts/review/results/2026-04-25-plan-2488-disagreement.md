### claude

- **Adversarial Review Summary correctly reports REVISING, but the cited immutable evidence has no post-revision re-run.** Plan line 343 says "REVISING — current immutable review evidence … still contain MAJOR findings, so do not move to `status:plan-review` until a subsequent pushed re-review has no unresolved MAJOR findings." The plan correctly self-blocks. However, the plan has been revised since those immutable artifacts were generated (lines 345-349 list revisions). The current plan text at HEAD has addressed several prior MAJOR findings (e.g., `BooleanOptionalAction` at line 205, `_baseline_finding_sources()` integration at line 197, `--skills-dir` resolved path at line 207) — but no fresh immutable re-review has been generated against this revision. **This is not a plan defect** — the plan's own gate correctly prevents premature `status:plan-review`. The finding is informational: the plan needs one more review cycle to produce clean immutable evidence before it can proceed.
- **Baseline-order enforcement script (`verify_issue_2488_baseline_order.sh`) has no durable caller binding.** Plan line 225 says the manual reconcile script invokes this in strict mode, making it a "closeout-script hard failure." But `scripts/skills/reconcile_filesystem_only_skills.py` is itself a manual entrypoint — no hook, CI, or `scripts/enforcement/` registration ensures it runs. Per `.claude/rules/patterns.md` enforcement gradient, this is Level 0 (prose). The plan's own language "closeout fails if …" implies Level 2+ enforcement. The mitigation (line 300, test `test_manual_reconcile_invokes_baseline_order_guard_in_strict_mode`) tests that reconcile *calls* the guard, but not that reconcile itself is called. This is acceptable for a one-time closeout task but should be documented as a prose convention, not a gate — or the acceptance criteria should say "operator must invoke `reconcile_filesystem_only_skills.py` as a manual step" rather than implying automated enforcement.
- **Tentative disposition table assigns `pending_full_scan` uniformly to 5 of 6 skills without pre-routing.** Lines 116-121 defer every decision to implementation-time scan. This is pragmatic, but the plan provides no criteria for distinguishing `promote_commit` vs. `archive_intentionally` vs. `ignore_generated_transient` outcomes. The `classify_filesystem_only_skill()` pseudocode (line 179-191) lists all six dispositions but doesn't specify decision thresholds (e.g., "archive if last-modified > 60 days and no incoming references"). Without thresholds, an implementation can classify arbitrarily and pass all tests. This is low-risk given user review of each disposition, but the plan's implicit guarantee of "valuable skills are preserved" (Acceptance line 319) is unfalsifiable without criteria.
- **`_write_markdown_artifact()` policy-ordering refactor scope is unclear.** The plan says (line 199) the refactor consumes `ranking_policy.section_order` for "exactly six policy-governed sections" but "v2-family sections such as Content Quality, Grouping / Taxonomy Drift, Oversized / Maintainability, Usage / Staleness, and Follow-up Candidates remain literal legacy sections." Test `test_policy_section_order_reorders_all_policy_governed_sections` (line 287) asserts reordering exactly those six, and `test_markdown_refactor_preserves_legacy_literal_sections` (line 288) asserts legacy sections survive. This is well-specified in the TDD list, but the pseudocode line 199 is a single run-on sentence — an implementer could misread "refactor `_write_markdown_artifact()`" as applying to all sections. The boundary between policy-ordered and literal sections should be called out in a comment or constant in the implementation, not just in tests.
- **Complexity rated T3 may be optimistic.** The plan creates 7 new files, modifies 5 existing files, introduces a new finding family with full policy/baseline/carry-forward integration, adds a separate manual reconcile CLI with 4 exit codes and trust-attestation cryptographic verification, and includes 30+ TDD tests. The typical T3 is "moderate multi-file maintenance." This is closer to T4 based on the number of new abstractions (trust attestation, disposition ledger, baseline-order guard, policy-driven section rendering). Under-rating complexity risks under-scoping review and implementation time. This is advisory, not a blocker.
- **Mutable fanout `2026-04-25-plan-2488-claude.md` is 0 bytes.** The Artifact Map (line 139) lists this as "Mutable fanout output — Claude (diagnostic only; not approval evidence)." The plan correctly marks these as non-authoritative. However, `2026-04-25-plan-2488-codex.md` (mutable) has content while the Claude equivalent is empty, with a sibling `.err` file. The plan's overall result section (line 343) correctly says mutable artifacts are diagnostic only. No action needed since immutable artifacts are the authority, but the empty mutable file should be either populated on the next review pass or removed to avoid confusion.
- **Disposition table line 121 gitignore citation is correct but non-obvious.** The hermes-memory-bridge row cites `.gitignore:291 memory/` — verified correct via `git check-ignore -v`. However, `.gitignore:292` is `!.claude/memory/` which might suggest to a reader that `.claude/skills/memory/` is also negated. It is not — the negation is for `.claude/memory/`, not `.claude/skills/memory/`. The plan should note this distinction to prevent implementation from incorrectly assuming the path is not ignored.
