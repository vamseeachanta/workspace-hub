### claude

- **Approval-gate evidence path is currently un-cleanable; plan does not pin the unblock.** Plan frontmatter line 8 says approval-gate artifacts are "TBD after fresh post-revision review". Plan §Adversarial Review Summary line 312 vaguely describes recovery ("retry Codex with an artifact-inline/no-tools prompt or GitHub-connector review mode … create an explicit timestamped UNAVAILABLE artifact"). Live verification: `2026-04-25-plan-2488-{claude,codex,gemini}.md` are all 0 bytes; `2026-04-25-plan-2488-codex.md.err` records `OpenAI Codex v0.125.0` hitting `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` during this planning cycle, which is a stronger failure than the documented 0.124.0 stdin-hang in `feedback_codex_cli_0_124_upstream_regression.md`. The plan does not pin (a) which fallback to use, (b) where the reviewed plan SHA256 is recorded inside the timestamped artifact, or (c) how an UNAVAILABLE artifact for the empty Claude run is captured when its `.err` is also 0 bytes. Acceptance §295 will be unverifiable until this is pinned.
- **`_write_markdown_artifact()` "policy-driven" rendering is decorative.** Plan §Pseudocode line 199 declares `_write_markdown_artifact()` "an explicit canonical renderer for this issue rather than a general section-order refactor" and inserts `filesystem_only_inventory` at a fixed position. TDD row `test_markdown_refactor_preserves_legacy_literal_sections` (line 269) pins the explicit literal order ("New → Changed → Filesystem-only → Content Quality → Grouping → Oversized → Usage → Follow-up → Unresolved → Suppressed → Errors"). Acceptance §284 also frames this as canonical. Live `weekly_skills_audit.py:809-881` already calls each section by literal name, and the plan does not require the renderer to *read* `weekly_summary_sections.filesystem_only_inventory` to compute order. An implementer can satisfy every test with a single hard-coded if-branch that ignores the policy key entirely. The "policy-driven" framing in Acceptance §283 is unverifiable.
- **`legacy_diverged_compatibility_total` ships dead weight into a stable recurring schema.** Plan §Pseudocode lines 173-175 and Acceptance §282 add this field to `inventory_summary.counts`. The snapshot at `docs/reports/issue-2488-planning-inventory-snapshot.json:12` records `"legacy_diverged_compatibility_total": 0` and `paths.legacy_diverged_compatibility: []`. Risks §327 says "record the policy/code drift as a named follow-up issue during implementation if not fixed here" but reserves no issue number. There is no operator-facing consumer, no follow-up issue pinned, and no rule that downgrades or removes the field once the underlying drift is resolved. This is a forever-zero column the plan promises to ship.
- **Active filter hand-rolls an exclusion list that already exists in policy as `category_alias_families`.** `config/skills/weekly-audit-policy.yaml:306-308` already declares `id: archive, canonical: _archive, aliases: [_archive, _archived]`. Plan §Pseudocode line 164 hand-codes the same exclusion in `active_filter(path)` as a hard literal. If a future maintainer adds a third alias to `category_alias_families.archive.aliases`, the active filter silently drifts. The plan should either (a) wire the active filter through `category_alias_families`, or (b) add a TDD row asserting that the filter set equals `category_alias_families[archive].aliases`. Neither is in the plan.
- **Acceptance §300 introduces an implementation-time hard-block that the plan-approval gate does not surface.** §300 mandates that a personal-* skill cannot be promoted without "explicit user authorization recorded in the disposition report"; otherwise it must be archived/deleted/ignored. Disposition table line 118 leaves `personal-tax-filing-packet` as `pending_full_file_scan_and_user_authorization`. The plan-approval gate (Acceptance §297) only requires `status:plan-review → user approves → status:plan-approved`; it does not require the implementer to obtain personal-skill authorization at approval time. So implementation will hit a hard block that should have been resolved at plan time. Either move the user-authorization capture into the approval gate or explicitly disposition `personal-tax-filing-packet` as ignore/archive in the plan now.
- **`scripts/cron/skills-curation.sh` invariance is asserted without an enforcing test.** Acceptance §292 says "scripts/cron/skills-curation.sh remains unchanged unless a test proves wrapper changes are necessary". TDD list (lines 247-275) has no row asserting wrapper file content invariance (e.g., sha256 lock, frozen-text fixture). The `tests/cron/test_skills_curation.py` rows the plan modifies cover *behavior* (dry-run/help/output-root/stale-workspace), not file content. A cosmetic edit (whitespace, comment, helper extraction) ships without breaking anything observable, but the criterion is asserted with no checker.
- **`scripts/skills/issue_2488_disposition_report.py` CLI surface is unpinned.** §Files-to-Change line 236 introduces this file as a "bounded issue-specific helper". TDD row `test_issue_2488_disposition_helper_invokes_report_end_to_end` (line 272) names invocation `uv run --no-project python scripts/skills/issue_2488_disposition_report.py --output docs/reports/issue-2488-skills-disposition.md --dry-run-fixture <fixture>` but no Acceptance criterion pins the helper's exact flag set, and no row asserts the file exists at that path or is invokable as a CLI module. An implementer can satisfy `test_disposition_report_written_to_tracked_docs_path_with_stable_schema` (line 271) by writing the report directly from a test fixture and never producing a runnable helper script — leaving the human operator without an executable closeout entry point.
- **`test_issue_body_drift_uses_planning_inventory_snapshot` silently swaps the issue body for the snapshot file as authority.** TDD row line 273 sources the "vanished original six paths" from `docs/reports/issue-2488-planning-inventory-snapshot.json`. ### codex

- The plan’s approval-gate artifact contract is not implementable with the cited tooling. In `Acceptance Criteria`, the plan requires fresh timestamped review artifacts that “record the reviewed plan commit or plan SHA256,” but `scripts/review/plan-review-fanout.sh` only writes date-scoped files named `${TODAY}-plan-${ISSUE_NUM}-${prov}.md`, and its UNAVAILABLE stub contains no commit/SHA metadata. `Files to Change` does not include `scripts/review/plan-review-fanout.sh` or `scripts/review/lib/disagreement-diff.sh`, so the plan cannot satisfy its own gate evidence requirement as written.
- The plan misstates the current policy schema. In `Pseudocode`, `Files to Change`, and `Acceptance Criteria`, it repeatedly requires `weekly_summary_sections.filesystem_only_inventory`, but `config/skills/weekly-audit-policy.yaml` defines `weekly_summary_sections` as a list of objects with `id`, not a keyed map. This is not a wording nit: the plan says it is extending the existing schema append-only, but the cited path shape does not exist in that schema.
- The sparse/partial Git safety requirement is underspecified to the point of being non-executable. `Acceptance Criteria` requires the audit to detect and downgrade partial `git ls-files` states, but `Pseudocode` for `build_skill_inventory_with_git(...)` only says to call `git ls-files` and report warnings on failure. A successful `git ls-files` call is not evidence of completeness, and the plan never specifies how sparse checkout or “tracked count far below the tracked planning snapshot” is detected without baking in a brittle repo-specific heuristic. That leaves a correctness-critical gap around false `missing_tracked_*` findings.
- The section-order contract is internally contradictory. `config/skills/weekly-audit-policy.yaml` currently has one governed `ranking_policy.section_order`, and `docs/standards/weekly-skills-audit-policy.md` documents that linear order. But the plan’s `Pseudocode`, `TDD Test List`, and `Acceptance Criteria` also require hard-coded literal family sections in a custom before/after sequence around the new filesystem section. As written, YAML is not actually authoritative for output order, despite the plan claiming policy-driven rendering.
