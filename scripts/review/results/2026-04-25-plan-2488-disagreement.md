### claude

- **Plan promises a "narrow `.gitignore` negation" alternative that is not actually narrow for any of the six known active filesystem-only paths** (Plan §"Files to Change", `.gitignore` row, line 230; §"Risks and Open Questions" decision bullet, line 313; §"Files to Change" promotion row, line 229; §Acceptance Criteria item 7, line 276; TDD list `test_promote_ignored_skill_requires_force_add_attestation`, line 259). All six known paths sit under directories matched by `digitalmodel/`, `memory/`, or `personal-*`, which are *parent-directory* ignore patterns. Per `gitignore(5)`: "It is not possible to re-include a file if a parent directory of that file is excluded." I empirically verified this in `/tmp/giproof`: a single-line `!.../SKILL.md` negation is silently overridden by the parent rule. Re-inclusion requires a multi-line cascade (re-include parent dir → re-exclude its siblings → re-include the child file). The plan's wording invites an executor to write a one-liner negation, observe it not working, and burn time. Either drop the negation alternative for these paths and require `git add -f`, or rewrite the bullet to specify the multi-line cascade and forbid single-line negations.
- **The plan introduces three new CLI flags but never enumerates the existing CLI surface** (Plan §Pseudocode `validate_and_render_dispositions`, line 195; §Acceptance Criteria, line 280). The audit script today exposes `--skills-dir / --output-dir / --policy / --waivers / --render-github-payload` (script lines 1035-1059). The plan adds `--mode`, `--disposition-ledger`, `--disposition-report`, but the "Files to Change" row for `weekly_skills_audit.py` (line 222) does not list them, and acceptance criterion at line 280 references `--mode manual_closeout --disposition-report ...` without naming the existing flags that must continue to behave identically. An executor cannot tell from this plan which flags are preserved verbatim, which are renamed, and which are added — backward-compatibility cannot be reasoned about from the plan alone.
- **`test_existing_weekly_audit_behavior_remains_backward_compatible` is not a test, it is a sentinel statement** (Plan §TDD Test List, line 263). "Existing fixture tests" → "existing tests still pass" describes a regression *property*, not an executable assertion. Either delete this row (the property is implicit in CI) or replace it with a concrete fixture that asserts a *specific* duplicate/collision finding count on a frozen fixture before and after the inventory extension.
- **The `_archived` legacy-collision-baseline acceptance bullet contradicts the corresponding TDD test** (Plan §Acceptance Criteria item starting at line 273 vs. TDD `test_archived_loss_filter_does_not_create_new_duplicate_findings`, line 260, plus the next-to-last acceptance bullet at line 283). The acceptance text simultaneously requires (a) "no new duplicate/collision finding is introduced" AND (b) "if current legacy behavior already reports `_archived` collisions, document that as pre-existing" AND (c) "records a pre-change `_archived` duplicate/collision baseline ... so regression tests cannot claim 'pre-existing' without evidence." The TDD test asserts (a) absolutely. If today's audit (with `EXCLUDED_DIRS = {"_archive", "_diverged"}` per script line 32) already emits `_archived` collisions, the unit test will fail in implementation even though the acceptance criterion accepts the pre-existing case. The plan needs one consistent posture: either compute the baseline first and assert delta = 0, or assert absolute count = 0. Pick one.
- **`test_inventory_summary_records_provider_skill_mirror_symlinks` underspecifies its injection seam** (Plan §TDD Test List, line 244; §Pseudocode `build_skill_inventory_with_git`, line 148). The pseudocode signature shows `symlink_resolver=None` but the test row only says "resolver-injection seam supplies `.codex/skills` and `.gemini/skills` link targets." The signature/contract (does it return a `Path`, a string, raise on non-symlink, accept absolute or repo-relative inputs?) is not pinned, so the RED test cannot be written deterministically before implementation. Specify the resolver function signature and exception contract.
- **The "Files to Change" table conflates implementation files with planning-lifecycle files** (Plan §"Files to Change" line 231, "Update `docs/plans/README.md`"). Updating `docs/plans/README.md` to `status:plan-review` is part of the planning gate workflow, not the implementation diff. Mixing it into the implementation file table risks an executor either (a) bundling that edit into an implementation commit, polluting the diff that gets cross-reviewed, or (b) skipping the lifecycle update entirely. Move that row to a separate "Planning lifecycle" section or strike it.
- **Acceptance criterion `inventory_summary.paths` schema (`{path, informational}` objects) is asymmetric with how `_core`/`_internal` are described elsewhere** (Plan §Acceptance Criteria, line 270; vs. §Pseudocode line 152 and TDD `test_filesystem_only_core_and_internal_skills_are_not_suppressed` line 247). The pseudocode says `_core`/`_internal` "remain in-scope for filesystem-only loss-risk reporting; do not reuse INFORMATIONAL_DIRS to suppress them." But the JSON shape mandates an `informational` boolean per path. Implementation must be told explicitly: should `_core`/`_internal` filesystem-only paths carry `informational: true` (a flag) or `informational: false` (active loss-risk)? Today the script's `INFORMATIONAL_DIRS = {"_core", "_internal"}` (line 33) is used as an informational marker — reusing the term in the new schema while reversing its semantic meaning is a footgun.
- **The `personal-tax-filing-packet` user-authorization gate is documented in acceptance criteria (line 285) but not reflected in the disposition ledger schema** (Plan §Pseudocode line 200, the `validate_and_render_dispositions` field list). Required fields are `path, disposition, reason, reviewed_at, reviewer, reviewed_file_sha256, final_status, final_path, scan_attestation, force_add_attestation_when_ignored`. There is no `user_authorization` (or equivalent) field, so the personal-data gate cannot be machine-checked. Either add the field to the schema or describe how the existing fields (`reviewer`?) suffice — and add a TDD row asserting promotion of any `personal-*` skill fails closeout without the explicit authorization marker.

### codex

- The plan allows non-authoritative inventory data in the very mode that is supposed to prove reconciliation is complete. In `## Pseudocode`, `classify_filesystem_only_skill(path)` says “git-history lookup failures are non-fatal warnings in `weekly_report` and `manual_closeout` evidence,” while `validate_and_render_dispositions(disposition_yaml, mode)` makes `manual_closeout` the gate that must prove every active filesystem-only skill is resolved. The same draft also adds `test_git_inventory_failure_is_reported_not_cron_fatal` and `test_sparse_checkout_or_partial_git_inventory_is_warned_not_trusted`. A warning-only manual closeout is incompatible with the acceptance claim “Manual closeout validation confirms both `missing_tracked_active = 0` and `unresolved_filesystem_only_active = 0`.” This needs a hard-fail rule for `manual_closeout` when git inventory is partial/untrusted.
- Citations: plan `## Pseudocode`; plan `## TDD Test List`; plan `## Acceptance Criteria`.
- The plan introduces a mandatory “explicit user authorization” gate for `personal-tax-filing-packet` but never defines any workflow step that can satisfy it. The draft requires “Any promotion of `personal-tax-filing-packet` requires explicit user authorization in the disposition ledger,” and the tentative disposition table marks that file `pending_full_file_scan_and_user_authorization`. But `docs/plans/README.md` only defines user approval for the plan as a whole (`status:plan-approved`), not per-artifact authorization or user-authored ledger entries. As written, the plan adds a blocker with no acquisition path, so completion is underspecified.
- Citations: plan `### Tentative disposition table for the known active filesystem-only skills`; plan `## Acceptance Criteria`; `docs/plans/README.md` sections `The Workflow`, `Step 6: User Approval`.
- The draft widens the canonical scheduled audit executable into a dual-purpose closeout tool that can write tracked docs, but it does not isolate that risk from the cron-owned path. Current `scripts/skills/weekly_skills_audit.py` describes itself as a “read-only audit” that emits local artifacts only, and the approved parent plan `docs/plans/2026-04-24-issue-2486-v2-periodic-skill-ecosystem-housekeeping-audit.md` locks the scheduled/default run to writes under `logs/maintenance/skills-curation/` only. This draft instead puts `validate_and_render_dispositions(...)` and tracked output `docs/reports/2026-04-25-skills-disposition-2488.md` into the same script (`## Files to Change` says modify `scripts/skills/weekly_skills_audit.py` for ledger validation/rendering). A mode flag alone is not a sufficient isolation story for a cron-owned entrypoint; the plan should require a separate manual-closeout entrypoint/module or equivalent hard separation.

The approved #2486 plan explicitly identifies `tests/cron/test_skills_curation.py` as the wrapper regression suite, and `scripts/cron/skills-curation.sh` is the only scheduled entrypoint. This draft adds only one wrapper-oriented test in the audit test list (`test_cron_wrapper_dry_run_command_parses_with_default_mode`) and does not list `tests/cron/test_skills_curation.py` in `## Files to Change`. That is under-scoped for a CLI change whose safety depends on preserving cron compatibility.
