### MINOR

1. **Ledger schema is implicit, not defined.** Rule 6 reads `ledger = load_yaml(docs/governance/gtm-publish-ledger.yaml)` and matches on `entry where path == current_path and signoff_sha matches HEAD-tracked revision`. The Files-to-Change row creates the ledger "empty initially" but provides no schema template or example entry. Two implementers could pick incompatible shapes (list-of-maps vs map-of-path-keys; `signoff_sha` vs `sha` vs `revision`). Fix: add a 5-line schema block to the governance doc or to the Files-to-Change reason column, e.g.:
   ```yaml
   # docs/governance/gtm-publish-ledger.yaml
   entries:
     - path: knowledge/wikis/engineering/wiki/overview.md
       signoff_sha: <git sha of reviewed revision>
       signed_by: <user>
       signed_at: <ISO date>
       rationale: <one-line why this is allow-eligible>
   ```
   Without this, the "mechanical" Rule 6 is specified at a higher abstraction than the rest of the rule set.

2. **`load_yaml` in bash is underspecified.** Rule 6 pseudo-code uses `load_yaml(...)`; the implementation target is `scripts/enforcement/check-gtm-boundary.sh` (shell). Plan does not say whether this will shell out to `yq`, python, or inline awk. For a governance tool that gates publishing, the parser choice is load-bearing (trailing-whitespace tolerance, multi-doc YAML handling, schema validation). Flag as MINOR: the plan should name the implementing technology (e.g., "uses `yq` 4.x; falls back to `python3 -c` if yq absent"). This is the one remaining shell-vs-pseudocode abstraction gap.

3. **Scope-bounding pages can be escalated to publishable via a ledger entry.** Rule 2 sends scope-bounding basenames (`overview.md`, `index.md`, `log.md`) to Rule 6. If a ledger entry is ever written for one of these paths, the linter exits 0 and the page is publish-eligible. But scope-bounding pages describe internal conventions ("how we engineer, not what we engineer" per memory) and should NEVER be firm-copy GTM candidates. The carve-out was intended to prevent the linter from self-contradicting its own classification exercise — not to create a publishable class via the ledger. Fix: either (a) change Rule 2 to terminate at `exit 2` unconditionally (scope-bounding pages are never publishable, regardless of ledger state), or (b) add an explicit rule in the governance doc that scope-bounding basenames are ineligible for ledger entries, and the linter rejects any ledger row whose `path` matches a scope-bounding basename. Option (a) is simpler and closes the bootstrapping concern entirely.

4. **`knowledge/wikis/cross-links.md`-class top-level registries are covered only by `auto_generated`.** The rule added for exercise 8 is correct and specific, but it's frontmatter-field-dependent. If a future hand-curated top-level navigation file (e.g., `knowledge/wikis/README.md` or `knowledge/wikis/domain-map.md`) is added without `auto_generated: true`, and without a `collection` field or forbidden tag, it would fall to Rule 6 and exit 2 (allow-eligible-needs-signoff) rather than deny. Plan does not treat `knowledge/wikis/` top-level as a deny-listed root (correctly — that would break the 6 wiki subtrees). Consider adding a narrower rule: "files at `knowledge/wikis/<basename>.md` top level (not under `<domain>/wiki/`) require explicit whitelisting; default is deny." Lower priority — current design handles today's surface (cross-links.md has the flag) and the policy decision to be conservative here is defensible.

### Questions for author (optional)

- The ledger is gitignored or committed? Plan says "committed (empty)" (acceptance criterion line 345), implying tracked. If so, a ledger entry's `signoff_sha` naming "HEAD-tracked revision" is in tension with the ledger itself being modified alongside the signed file (the signed file's sha changes when ledger is updated in the same commit). Consider: does `signoff_sha` mean "sha of the target file's last commit before signoff" (measurable with `git log -n1 --format=%H -- <path>`) or "sha of the tree at signoff time"? Disambiguate in the governance doc.
- Is there a CI enforcement point for Rule 6? The plan's nightly-audit recommendation (Risks section line 373) says pre-commit + nightly, but ledger signoff is a manual user action — the natural hook point is at publish-attempt time, not commit time. Currently unspecified.
