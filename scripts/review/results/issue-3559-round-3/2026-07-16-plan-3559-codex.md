## Findings
1. Round 3 has no revision-bound, durable review input. The plan header at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:11-15` names Round 1 and Round 2 input commits but no Round 3 input commit. The current plan is an untracked replacement over a staged deletion, and `.gitignore:577` ignores `scripts/review/results/`, so the cited Round 2/3 artifacts are not contained in commit `a703e619c14fde5aea003010e3479b80f15e1d19`. The plan therefore cannot prove which exact Round 3 bytes received the final verdict.

2. The plan falsely characterizes GitHub account activity as non-forgeable human authorization. `verify_approvals` at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:192-199` trusts an owner-applied label event, marker, and comment; `authorize_and_deploy` at lines 234–242 similarly trusts an owner comment. GitHub proves which account or token performed an action, not that the human owner personally approved it. Any automation credential acting as that account can manufacture every listed signal. The test claim `test_approval_requires_live_owner_label_event_marker_review_comment_and_plan_blob — canonical approval evidence is exact and non-forgeable` is therefore false. A distinct trust boundary—such as protected-environment approval by a separately authenticated reviewer or signed authorization—is missing.

3. The proposed PR mechanism is not a remote compare-and-swap. `transition_release` at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:228-232` says a promotion PR will start from `expected_remote_sha` and merge through “non-force fast-forward/PR CAS.” Creating a PR from an expected base does not prevent the base from advancing before merge, and the plan defines no merge-time base-SHA assertion, state-path merge queue, required check against the current target ref, or atomic ref-update operation. Two promotion PRs based on the same state can consequently both become mergeable and overwrite or fork the release history. The unit-level race test cannot establish remote GitHub serialization without an exact ref-update protocol.

4. The external deployment crash window has no recovery or idempotency contract. `authorize_and_deploy` at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:238-242` records `deploy_pending`, performs deployment, and only afterward records acceptance or failure. A crash after Vercel mutates production but before its deployment ID/result is committed leaves `deploy_pending` indefinitely; retrying can create a second deployment. The `unknown` transition is defined only for an unproven rollback, not process death, timeout, or ambiguous deployment completion. No deployment idempotency key, resumable lookup, lease, timeout, or reconciliation test is listed.

5. “Trusted workflow” is circular rather than an enforceable policy. `verify_trusted_receipts` at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:203-209` fetches the run event but never specifies allowed events, workflow ID/path/ref, target branch, triggering actor, run attempt, protected-environment approval, or immutable action dependencies. “Reject fork/untrusted workflow” supplies no rule for deciding trust. The child workflow artifacts in `docs/plans/2026-07-16-issue-1045-wed-hf-browser-snapshot.md` and `docs/plans/2026-07-16-issue-74-website-pinned-field-well-drilldown.md:154-168` do not close those parent-side verification requirements. A successful same-repository run with a matching head SHA could therefore satisfy the described checks without satisfying the intended protected publication path.

6. The supposedly immutable evidence/history can be rewritten by a legal transition. `transition_release` at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:228-232` updates one mutable `release-state.json` and “immutable evidence paths,” but it does not require prior event history to remain a byte-for-byte prefix, require creation-only content-addressed evidence paths, or validate ancestry against every previously accepted state. The test `test_single_state_object_and_remote_ref_cas_survive_crash_and_race_points` covers races, not truncation or alteration of earlier events/evidence. The release history and rollback proof are therefore only conventionally immutable.
