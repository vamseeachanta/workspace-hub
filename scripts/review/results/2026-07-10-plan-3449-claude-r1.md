## Findings

1. **`openat2`/`renameat2` have no named implementation mechanism.** Plan §Pseudocode (`open requested_source relative to that root with Linux openat2 RESOLVE_BENEATH…`, `atomically install staging with Linux renameat2(RENAME_NOREPLACE)`) and §CLI paragraph make both syscalls load-bearing for the plan's two central security properties (TOCTOU-free open, no-replace install). CPython's `os` module exposes neither `openat2` nor `renameat2`/`RENAME_NOREPLACE`; the implementation requires raw `ctypes`/`libc.syscall` wrappers with arch-specific syscall numbers and a packed `struct open_how`, or a third-party dependency — and `pyproject.toml` lists no candidate. The plan says "fails closed when `openat2` is unavailable" but never says how the syscalls will be reached, how that wrapper is tested, or on which architectures the syscall numbers are pinned. A plan whose security core rests on an unnamed, nontrivial FFI layer is not yet implementable as written.

2. **The <400-line/<50-line module constraint contradicts the module's own scope.** §Implementation Sequence step 2 commits to "functions … below 50 lines and the file below 400 lines" for `scripts/client_llm_wiki/bootstrap_contract.py`, while §Files to Change assigns that single file: a duplicate-key-rejecting YAML loader, the classifier, the root/base validator (lstat/resolve containment), the live `gh` PRIVATE verifier, the Git-object archive renderer with tar-member inspection and manual extraction, staged-manifest validation, the `openat2` wrapper, the `renameat2` installer, manifest SHA-256 binding, and a 4-subcommand CLI — with ~34 of the 40 TDD rows targeting it. Either the constraint will be silently violated at GREEN, or the module will be split into files that do not appear in §Files to Change (making the plan's file inventory wrong). One of the two commitments must change now, not at implementation time.

3. **The shell checker's new Python dependency has no specified invocation or failure mode.** §Files to Change says `check-client-wiki-registry.sh` will "Invoke the contract validator", but the plan never states how (system `python3`? `uv run`? what supplies PyYAML?) nor what the checker does when `scripts/client_llm_wiki/` is absent — which is exactly the state of the sparse worktree this plan was authored in (`git sparse-checkout list` materializes `scripts/enforcement/` but not `scripts/client_llm_wiki/`). AC #1 acknowledges sparse materialization for pytest but not for the checker's runtime dependency. In a plan whose stated thesis is that audit-degrade-open vs operation-fail-closed must never blur (§Locked Contract, final paragraph), leaving this specific degrade/fail decision unwritten is a real gap, not a detail.

4. **Cross-review artifacts cited in the header do not yet contain reviews.** Plan header line 10 cites three result paths. On disk: the claude file was empty (this review now fills it), `…-codex.md` is 0 bytes beside a 358 KB `.err` transcript of a failed dispatch, and `…-gemini.md` records UNAVAILABLE (no non-interactive auth). The plan is T3 (§Complexity requires three-provider review); as of this review zero completed provider verdicts existed. Gemini's UNAVAILABLE is documented per the `scripts/review/results/` convention (T3→T2 degrade), but the codex failure is neither a result nor a documented UNAVAILABLE — it must be re-dispatched or recorded as UNAVAILABLE before the review summary table can be filled honestly.

5. **Evidence section misstates the factory's substitution ordering.** §Evidence: "the factory requires a raw variable, checks its mount path, and substitutes `<CLIENT_RAW_ROOT>` before repository creation." In the skill, the mount check (line 88) does precede `gh repo create` (line 96), but the `<CLIENT_RAW_ROOT>` sed substitution runs at line 158 — after repository creation, before first push. The issue's core claim still reproduces (raw root is a hard prerequisite), but embedded reproduction evidence must be accurate.

6. **`test_factory_verifies_private_repo_before_render_and_before_push` asserts on prose, not behavior.** §TDD list says the test passes via "skill command-order assertion" — i.e., grepping SKILL.md for the textual order of commands in an operator document. That is a documentation-format test masquerading as a behavioral guarantee: it passes if the markdown mentions commands in the right order and says nothing about what an operator or agent actually runs. Either downgrade its claimed verification ("What it will verify" column) or move the before-render/before-push PRIVATE checks into the renderer/CLI where they are testable as behavior.

7. **HEAD-binding makes enabled ingestion brittle with no stated re-attestation path.** §Locked Contract step 4 and `test_open_source_requires_matching_repo_commit_and_reader_manifest_hash` bind reads to `covered_repo_commit == local wiki HEAD`. Consequence: every commit to an enabled client wiki — including a pure docs commit — invalidates all raw reads until a separately-approved private change re-stamps the registry. §Risks does not surface this operational cost or any re-attestation cadence/automation. If intended, say so and state the expected workflow; as written, downstream operators will discover it as a surprise outage.

8. **`open_authorized_raw_source` never specifies where the "derived local wiki HEAD" comes from.** §Pseudocode requires `derived local wiki HEAD == covered_repo_commit`, but the current schema's `local_working_clone` is optional (the live checker null-guards its absence, Fix 2, `check-client-wiki-registry.sh:153-155`), and neither the schema-0.2 field list (§Locked Contract ¶1) nor `classify_entry` requires or validates a clone path for enabled rows. An enabled row without a resolvable local checkout makes the commit/manifest checks undefined. Specify the field, its requiredness for `SOURCE_BACKED_ENABLED`, and its containment rules.

9. **AC pins exact host tool versions it cannot guarantee.** AC: "`shellcheck …` pass using the installed shellcheck 0.11.0/yq 4.53.2 toolchain." Installed versions were not verifiable in this review (probe denied), and pinning point versions of host binaries in an acceptance criterion makes the AC host-specific and stale on the next upgrade. State minimum versions or drop the pins; the repo has no lockfile for these tools (contrast `.claude/rules/verify-ci-lint-toolchain.md`, which pins via `uv.lock` — no analogous mechanism exists for shellcheck/yq).
