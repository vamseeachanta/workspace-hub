### claude

- **Approval-gate artifact metadata contract has no tooling backing.** Plan Status header (line 8) and Acceptance Criterion (line 295) require the gate runner to "copy latest non-empty fanout/fallback stdout into timestamped immutable artifacts, prepend `Reviewed-Commit:` and `Plan-SHA256:` metadata." But `scripts/review/plan-review-fanout.sh:67,75` writes `${TODAY}-plan-${ISSUE_NUM}-${prov}.md` (date-only, not timestamped) and the UNAVAILABLE stub at lines 109–124 emits no `Reviewed-Commit` or `Plan-SHA256` line. The "Files to Change" table on lines 226–241 does not include `scripts/review/plan-review-fanout.sh`, nor any new gate-runner script, nor `scripts/review/lib/disagreement-diff.sh`. The plan therefore mandates an artifact contract it provides no implementation surface for. (Codex review §Findings #1, verified live.)
- **Markdown section-order is simultaneously claimed policy-driven and hard-coded.** Plan Pseudocode (line 196) says "use existing v2 policy/ranking from `config/skills/weekly-audit-policy.yaml` … instead of hard-coding a second policy surface," and the canonical render path goes through `_write_markdown_artifact()`. But the very next paragraph (line 200) and Acceptance Criterion (line 284) hard-code an 11-section literal sequence: `New → Changed → Filesystem-only → Content Quality → Grouping → Oversized → Usage → Follow-up → Unresolved → Suppressed → Errors`. `config/skills/weekly-audit-policy.yaml:172–178` defines `ranking_policy.section_order` with only 5 abstract IDs (`new_findings`, `changed_findings`, `unresolved_high_confidence_findings`, `suppressed_carry_forward_findings`, `operational_errors_or_skipped_inputs`). The legacy family sections (`Content Quality`, `Grouping`, `Oversized`, `Usage`, `Follow-up`) appear nowhere in `weekly_summary_sections` (lines 160–170) or `ranking_policy.section_order`. The plan only adds `id: filesystem_only_inventory` to `weekly_summary_sections` — it does not propose extending `ranking_policy.section_order` to include the legacy family sections it now wants policy-bound. So either YAML is the source of truth (and the test on line 268 must fail) or the hard-coded sequence wins (and the policy-driven claim is false). Pick one. (Codex review §Findings #4, verified.)
- **Sparse-checkout / partial-inventory acceptance gate is unimplementable from the pseudocode.** Acceptance Criterion (line 299) requires the audit to "report sparse checkout with the skills dir outside the sparse patterns, or returns a tracked count far below the tracked planning snapshot without an explicit override," and TDD test `test_sparse_checkout_or_partial_git_inventory_is_warned_not_trusted` (line 269) asserts "successful-but-partial git inventory does not create false loss findings." But Pseudocode (lines 160–166) only documents the failure path: "if test seam … else call git_list_fn or default git ls-files … never hard-code .claude/skills." There is no specified detection mechanism for a *successful* `git ls-files` returning a sparse view: no sparse-config probe (`git config core.sparseCheckout`), no `git sparse-checkout list` invocation, no threshold for "far below the planning snapshot," and no override flag named. A test cannot be written for behavior the design does not specify. (Codex review §Findings #3, verified — pseudocode has no sparse-detection helper.)
- **Live inventory baseline drift in the Resource Intelligence Summary and Risks section.** Plan line 21 and line 324 cite `tracked 3028 / tracked_active 922 / filesystem 3100 / filesystem_active 928`. Re-running the plan's own embedded proof script on 2026-04-26 from the working tree yields `tracked 3030 / tracked_active 924 / filesystem 3102 / filesystem_active 930` — `+2` across all four counts. The 6 untracked active `SKILL.md` paths are unchanged. The plan acknowledges this drift class in Risks (line 324) and says implementation recomputes live, so this is not blocking, but the cited "verified 2026-04-25" snapshot is already stale at planning-time `+1 day` and either deserves a refresh or an explicit "snapshot-only, not gate evidence" annotation matching the same treatment given to mutable review artifacts.
- **Codex review (the cited evidence) issued MAJOR; the plan's Adversarial Review Summary table understates its weight.** `scripts/review/results/2026-04-25-plan-2488-codex.md` returns `## Verdict\nMAJOR` with 4 numbered blockers. The plan's §Adversarial Review Summary row for Codex (line 309) describes the verdict as "scope creep, recurring-schema contradiction, vanished-path closeout ambiguity, and scheduled-task doc drift" — paraphrasing rather than naming the four concrete blockers (gate-artifact contract not implementable, schema-shape misstatement, sparse-checkout under-spec, section-order self-contradiction). Three of those four are still live in the current revision (Findings 1, 2, 3 above). The plan's own gate text (Acceptance Criterion 295) says "no unresolved MAJOR findings from available reviewers before the gate" — by its own rule, the plan cannot move to `status:plan-review` until those Codex blockers are demonstrably resolved.
- **Acceptance Criterion 295 self-references a contract whose script is not yet built.** The criterion says provider artifacts must "record the reviewed plan commit or plan SHA256." No script in `scripts/review/` currently emits either. The plan has no Files-to-Change row creating such a wrapper. Same root cause as Finding 1, restated as an acceptance-criteria executability defect: an AC that no commit can satisfy is structurally MAJOR.

### codex

- The plan’s policy-source-of-truth story is internally inconsistent. In `Pseudocode -> run_weekly_audit_extension()` and `Files to Change`, it requires adding `weekly_summary_sections` entry `filesystem_only_inventory` and then claims the canonical Markdown order becomes `New → Changed → Filesystem-only → ...`, but it never requires updating `config/skills/weekly-audit-policy.yaml` `ranking_policy.section_order`, which is the file the repo already documents as locking ranking behavior. Current YAML only lists `new_findings`, `changed_findings`, `unresolved_high_confidence_findings`, `suppressed_carry_forward_findings`, and `operational_errors_or_skipped_inputs`, and [docs/standards/weekly-skills-audit-policy.md](https://github.com/vamseeachanta/workspace-hub/blob/main/docs/standards/weekly-skills-audit-policy.md) explicitly says the YAML locks section ordering. As written, the plan would create a new section id without updating the policy order that is supposed to govern it.
- The plan leaves `_core` / `_internal` handling contradictory. `Acceptance Criteria` says those filesystem-only skills “remain active loss-risk but carry `informational: true`,” and `Pseudocode -> run_weekly_audit_extension()` also says the Markdown report must list every `filesystem_only_active` path. Current implementation in [scripts/skills/weekly_skills_audit.py](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/skills/weekly_skills_audit.py) routes informational findings through `_split_informational_findings()` into `suppressed_findings`, and `_write_markdown_artifact()` renders family sections from active findings, not suppressed ones. The plan never states whether the new filesystem-only section bypasses that suppression rule or honors it. That is not a stylistic gap; it changes whether `_core` / `_internal` paths appear in the headline section at all.
- The new family’s baseline identity is underspecified. The plan requires `filesystem_inventory_findings` to participate in `_baseline_finding_sources()`, `_all_active_findings()`, carry-forward logic, and tests such as `test_filesystem_only_family_participates_in_baseline_and_summary_counts`, but `Pseudocode -> run_weekly_audit_extension()` never defines how `finding_key` is computed for this family. Current baseline behavior in [scripts/skills/weekly_skills_audit.py](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/skills/weekly_skills_audit.py) is entirely keyed off stable `finding_key` values. Without a deterministic key recipe for filesystem inventory findings, the plan does not actually specify how weekly “new vs carry-forward vs changed” behavior remains stable.
- The path-format contract is missing where it matters. The issue body, `docs/reports/issue-2488-planning-inventory-snapshot.json`, and the plan’s own embedded evidence all use repo-relative paths like `.claude/skills/...`, but current `build_inventory()` in [scripts/skills/weekly_skills_audit.py](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/skills/weekly_skills_audit.py) stores paths relative to `skills_dir`, not repo root. `Acceptance Criteria` and `Pseudocode -> inventory_summary.paths` require stable objects `{path, informational}` but never lock whether `path` is repo-relative or skills-dir-relative. That ambiguity breaks the later requirement to reconcile against the snapshot file and to render `issue_body_drift` rows from the original six paths.
- The plan invents a “structural test” linking `weekly_summary_sections` ids to `v2.rules` family/rule keys, but no mapping contract is specified anywhere. `Pseudocode -> run_weekly_audit_extension()` says a structural test should prove `weekly_summary_sections` entry `filesystem_only_inventory` “agrees with” rule key `filesystem-inventory.filesystem-only-active`, yet current policy YAML uses `weekly_summary_sections` for report sections and `v2.rules` for per-rule defaults; they are different namespaces with no existing canonical transform between them. The plan asserts a validation rule without defining the mapping it wants the code to enforce.
