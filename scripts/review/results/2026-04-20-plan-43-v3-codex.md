## Findings
### Finding 1 — MAJOR — The “3 derivable dimensions” claim is internally inconsistent
- Plan claim: “Scorer computes only the 3 derivable dimensions (lifecycle, user-review adherence, log completeness)”
- Location: `## v3 Revision Notes — 8 distinct blockers absorbed`, item 3; pseudocode under `score_provider`
- Evidence:
  - v3 says the verified corpus is `session_tool_summary`, `stage_exit`, `codex_session`: https://github.com/vamseeachanta/workspace-hub/blob/5068a48de/docs/plans/2026-04-20-issue-43-v3.md
  - The same plan describes `stage_exit` only as `wrk`, `stage`, `date`, `timestamp`, then scores `user_review_adherence` using `e.next_gap_seconds >= 60`, which is not in the admitted shape.
  - It also extracts hard-gate violations via `e.type == "gate_bypass"`, another field/event not admitted in the verified corpus.
- Why it matters: v3 claims to have reduced scope to what is measurable, but one of its “derivable” dimensions and its violation extractor still depend on unverified fields. That breaks the central v3 correction.
- Suggested fix: either reduce scope again to only the actually derivable dimensions, or expand Resource Intelligence with concrete event samples proving `next_gap_seconds` and `gate_bypass` exist in the target corpus.

### Finding 2 — MAJOR — The proposed `session-analysis.sh` jq insertion would corrupt the existing skill-scoring loop
- Plan claim: “AFTER: jq '(select(.event == "session_end") | .signals.skill_invocations[]?), (select(.event == "gate_compliance_score") | {event, provider, score, date}), (select(.event == "provider_capability") | {event, provider, lifecycle_complete, date})'”
- Location: pseudocode block “Pipeline handler for `scripts/analysis/session-analysis.sh`, near line 101”
- Evidence:
  - Real script loop reads jq output into `skill` and increments `skill_usage["$skill"]`: https://github.com/vamseeachanta/workspace-hub/blob/5068a48de/scripts/analysis/session-analysis.sh
  - Current jq emits only skill names from `.signals.skill_invocations[]?`.
  - The plan’s replacement would mix JSON objects into that same stream, so the loop would treat object blobs as skill names.
- Why it matters: this is not a safe conceptual patch. It would not “pick up” the new events; it would pollute skill scoring and still leave no defined downstream consumer for the new objects.
- Suggested fix: keep skill extraction unchanged and add a separate jq/loop path for the new event types, with an explicit target artifact or summary section.
