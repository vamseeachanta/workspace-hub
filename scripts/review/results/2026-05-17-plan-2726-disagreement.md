### claude

- **Acceptance-criteria coverage gap vs the issue body — plan does not trace.** Issue #2726 Acceptance Criteria explicitly require that "Report outputs are classified by audience: raw evidence, internal review, client-facing HTML, **limited PDF**, chatbot/query surfaces" and that "Security/legal constraints are documented, including **no client identifiers or secrets in public repos**", and elsewhere demand a "boundary matrix" with **retention expectations**. The plan's Acceptance Criteria (lines 145-152) require child plans to exist, layer taxonomy to be defined, source classes to include `/mnt`/client/tier-1/etc., promotion gates, and legal scan to pass — but never name (a) audience-tier classification including limited-PDF, (b) explicit no-client-identifier guarantee, or (c) retention expectations. The plan can satisfy its own acceptance criteria while leaving the issue's acceptance criteria unmet.
- **TDD/Validation list is non-executable (lines 134-142).** Every entry in the table is a documentation inspection check rendered as a "test_*" name. None is wired to a runnable harness, fixture, or schema. `test_source_matrix_has_required_columns` has no validator path; `test_layer_transitions_are_explicit` has no parser; `test_legal_scan_passes` names a script (`scripts/legal/legal-sanity-scan.sh`, verified to exist) but the plan never declares how the test invokes it or what the pass condition is. This violates the SOUL.runtime.md gate "TDD mandatory — tests before implementation; no exceptions" because the listed tests are not implementable as drafted. Either move to JSON-Schema/regex validators (concrete scripts under `scripts/validation/`) or stop calling them tests.
- **Evidence block double-counts issue #2726 (lines 60-62).** The "Issue statuses" listing names `#2726 — OPEN — feat(architecture): review data, execution, and report layer boundaries` twice with the same title; the second is labeled "parent architecture issue" but #2726 IS the parent. There is no separate parent. The Distinct-sources comment at line 85 then claims "6 distinct sources" when only 5 are real (issue body, DATA_RESIDENCE_POLICY, mounted-source-registry, content-pipeline README, capabilities summary) — issue body and "parent" are the same source. False source-count inflation undermines the resource-intel attestation.
- **Path inconsistency between Resource Intelligence Summary and Source Table.** Line 15 enumerates registry roots and does NOT include `/mnt/ace/acma-codes`. Line 46 ("Mounted standards/literature" row) then asserts `/mnt/ace/acma-codes` as an example. Either the registry was not actually inspected for that path (the line-15 enumeration is a paraphrase, not a verbatim grep), or the row at 46 fabricates a path. Both possibilities are problems for an architecture inventory plan whose value is provenance accuracy. Plan should embed a verbatim `grep -E "^(- |  )" data/document-index/mounted-source-registry.yaml` excerpt rather than paraphrased prose.
- **Line-excerpts block (lines 71-76) is paraphrased, not quoted.** Strings like "Tier 1 Collection Data = worldenergydata; Tier 2 Engineering Reference Data = digitalmodel" are summaries, not actual line content from `docs/DATA_RESIDENCE_POLICY.md`. Per the workspace's review rule on retrieval skepticism, paraphrased excerpts are assertions, not evidence. Replace with actual quoted lines and the source-file line numbers.
- **Parent/child plan ordering is undefined.** Plan line 7 says "Review artifacts: pending after user source-curation pass" and acceptance criterion 1 (line 146) requires child plans for #2727/#2728/#2729 to be "source-curated and reviewed." But three child plans (totaling ~45 KB) are already on disk dated 2026-05-17 — written before this parent plan was reviewable. The plan never declares (a) whether the parent must be approved before children proceed, (b) whether children can be approved independently, or (c) whether this parent is a meta-plan that locks the shape of child plans. Without that, reviewers and the user have no way to sequence the four approvals. This is a procedural blocker for a T3 multi-plan rollout.
- **Terminology conflict flagged but not resolved (lines 162-165).** "Risk: Data-level names may conflict with existing `DATA_RESIDENCE_POLICY.md` tier names." The plan defers reconciliation to "acceptance" without naming the resolution mechanism. Existing policy uses "Tier 1/2/3"; this plan introduces "L1/L2/L3" levels. The risk text suggests "use distinct labels" as one option but doesn't commit. Cross-provider reviewers will independently flag this; resolve in-plan now or it returns as a defect in r2/r3.
- **No citation-emission policy for architecture contract.** Workspace rule `.claude/rules/calc-citation-contract.md` requires `Citation` sidecars when calc modules use standards-derived constants — the architecture contract will reference standards (DNV, API, ISO via the engineering-reference data layer) but the plan never declares whether the contract itself needs citations or how it handles standards references in matrix cells. Either declare the contract is meta-prose exempt, or wire in citation requirements for any standards-name cells. Silence here will produce a downstream lint defect.
- **`Files to Change` includes `docs/plans/README.md` "Plan index entry" without specifying schema.** Line 130 says "Update `docs/plans/README.md`" — but there is no test or acceptance criterion verifying the index entry exists/is correct, and no template for the entry. Reviewers cannot evaluate completeness.
- **Pseudocode (lines 109-118) is so abstract it cannot be reviewed.** Every line is a verb-noun stub ("inventory known source classes", "define allowed transitions", "define required gates"). For a T3 architecture plan, the pseudocode should at minimum reference the column shape of the matrix, the layer-state machine vertices, and the file path each operation writes to. As drafted, it imposes no constraint on the implementer.
- **Reproduction proof is "N/A" but issue is not a runtime failure exemption (line 83).** Workspace gate `feedback_discovery_first_on_stale_plan_approved` and the `issue-planning-mode` skill require a Step-1.5 reproduction step — for governance issues, the equivalent is a "current state is broken/unclear because…" inventory. The plan asserts N/A and skips. Strengthen by adding an explicit "state-of-art today" inventory section showing the actual ambiguity, not just "no single contract exists."
- **Two acceptance criteria are tautological / circular (lines 151-152).** "Adversarial plan review artifacts exist before applying `status:plan-review`" and "No implementation or publication changes occur before user approval" — both are restatements of the universal gate from AGENTS.md, not plan-specific content. They consume acceptance-criterion slots without adding falsifiable content. Replace with content criteria: "Matrix lists ≥15 source classes mapped to layer/level/owner/posture/gate columns; all client-named paths use opaque source IDs."

### codex

- Plan Resource Intelligence is insufficient for the issue labels. Issue `#2726` is labeled `cat:data-pipeline`, `cat:document-intelligence`, `domain:knowledge`, and `domain:reporting`; `docs/plans/README.md` requires Data Pipeline sources such as `registry.yaml` and `resource-intelligence-maturity.yaml`, and Knowledge/Intelligence sources such as the `#2205` operating model, sibling contracts, and accessibility map. The plan’s “Documents consulted” only lists `#2726`, `docs/DATA_RESIDENCE_POLICY.md`, `data/document-index/mounted-source-registry.yaml`, `docs/content-pipeline/README.md`, and `docs/WORKSPACE_HUB_CAPABILITIES_SUMMARY.md`, omitting `docs/document-intelligence/README.md`, `docs/document-intelligence/llm-wiki-resource-doc-intelligence-operating-model.md`, `docs/document-intelligence/durable-vs-transient-knowledge-boundary.md`, `data/document-index/registry.yaml`, and `data/document-index/resource-intelligence-maturity.yaml`.
- Plan proposes new layer level names without binding them to the existing normative intelligence-layer model. Plan “Gaps identified” says “No approved level taxonomy yet for data L1 raw → L2 raw-llm-wiki/staging → L3 public `llm-wiki`/chatbot knowledge,” but `docs/document-intelligence/llm-wiki-resource-doc-intelligence-operating-model.md` already defines a six-layer model where L1 is Source documents, L2 is Registry/provenance, L3 is Durable knowledge, L5 is Execution state, and explicitly forbids “between,” “adjacent,” or hybrid layer inventions. The plan only flags a naming-conflict risk against `docs/DATA_RESIDENCE_POLICY.md`, not against the stronger normative `#2205` model.
- “All tier-1 repo data” is not empirically defined and conflicts with repo inventory sources. Plan Acceptance Criteria says “Initial known source classes include ... all tier-1 repo data,” and the source-class table lists `workspace-hub`, `digitalmodel`, `assetutilities`, `worldenergydata`, `llm-wiki`, `assethold`, `aceengineer-website`, and `aceengineer-strategy` as tier-1 repo data. `docs/WORKSPACE_HUB_CAPABILITIES_SUMMARY.md` lists Tier-1 repositories as `digitalmodel`, `assetutilities`, `assethold`, and `worldenergydata`; `docs/BUSINESS_BRAIN.md` lists Tier-1 as `workspace-hub`, `digitalmodel`, `assetutilities`, and `aceengineer-website`. The plan does not reconcile the conflicting inventories or define the authoritative tier-1 set before requiring coverage of “all” tier-1 data.
- Parent plan has validation tests but no concrete test artifact path. Plan “TDD / Validation List” names five tests, but “Artifact Map” has no Tests artifact and “Files to Change” has no test file. `docs/plans/_template-issue-plan.md` requires the Artifact Map to include Tests, and `docs/plans/README.md` requires TDD before implementation. This makes the validation work non-executable for the `#2726` parent scope.
- Evidence section duplicates `#2726` and omits child issue status evidence despite child plans being acceptance-critical. Plan “Evidence (embedded verification)” lists `#2726` twice; Acceptance Criteria requires child plans for `#2727`, `#2728`, and `#2729` to be source-curated and reviewed. The plan does not embed status evidence for those child issues, even though their existence/state is correctness-critical to the parent plan.
- Legal scan acceptance is under-specified for multi-repo/public-private publication risk. Plan “TDD / Validation List” only says `test_legal_scan_passes` expects “plan/docs paths” to pass, while `docs/BUSINESS_BRAIN.md` requires legal/IP checks before raw data, client-derived context, standards extracts, document intelligence, or code-porting insights become public-facing `llm-wiki` pages, GTM artifacts, GitHub issues, PRs, or demo reports. `scripts/legal/legal-sanity-scan.sh` supports `--repo`, `--all`, and `--diff-only`, but the plan does not specify which scan mode applies to architecture docs that classify client/project roots and public chatbot/report eligibility.
- Plan depends on “user-added sources” without a required artifact or acceptance criterion for capturing them. Plan pseudocode says “inventory known source classes from registry, repo docs, issues, and user-added sources,” and the status says “source-curation pass pending,” but the Artifact Map has no source-curation artifact and Acceptance Criteria do not require a curated source list or diff from the user pass. This leaves the plan-review gate able to pass before the declared pending source input is captured.

This is factually false; a filesystem search yields zero matches for `llm-wiki`. Furthermore, `docs/WORKSPACE_HUB_CAPABILITIES_SUMMARY.md` § "Knowledge & Intelligence Ecosystem" confirms that LLM-Wikis reside at `knowledge/wikis/` within `workspace-hub`, not in a standalone repository. The plan's open question ("Which repo is canonical for private llm-wiki...") is based on this false premise.

However, the corresponding test in § "TDD / Validation List" (`test_source_matrix_has_required_columns`) explicitly checks only for `source_class, owner, canonical_path, layer, level, public_posture, promotion_gate` and omits the required `report_chatbot_eligibility` column.
- **Missing issue verification:** Plan § "Evidence (embedded verification)" claims to have verified issue statuses via `gh issue view`, but it erroneously lists issue `#2726` twice and omits verification for `#2727`, `#2728`, and `#2729`. Yet, Plan § "Acceptance Criteria" #1 sets the curation of these three missing issues as a hard gate.
