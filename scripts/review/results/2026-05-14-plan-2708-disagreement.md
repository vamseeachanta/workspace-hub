### claude

- **TDD step "Verify pickup occurred" uses the wrong directory.** Plan §TDD Test List row 4: `git pull && ls queue/.processed/ | tail -3` — but `queue/.processed/` is written by `scripts/solver/watch-results.sh:91` (`local marker="${PROCESSED_MARKER_DIR}/${job_name}.done"`), NOT by `scripts/solver/process-queue.py`. The dispatcher under test moves the job to `queue/completed/<job-name>/` (`process-queue.py:172-174`). On a host where `watch-results.sh` is not also running (the plan never establishes that it is on licensed-win-1), `.processed/` will never be touched even after a successful OrcaFlex dispatch. The verification step would falsely report "no pickup" on a successful run, OR (worse) report stale prior `.done` markers as evidence of pickup. Pickup signal MUST be `queue/completed/<job-name>/` OR `queue/failed/<job-name>/` directory creation.
- **Failure path is invisible to the verification chain.** Plan §TDD row 5 checks `queue/completed/<job-name>/result.yaml`. But `process-queue.py:207-213` moves a failed job to `FAILED_DIR / job_name` (a different directory) when the OrcaFlex run raises. The verification command will then report "missing" for both "not yet picked up" and "picked up and failed" — two materially different states the operator must distinguish. The plan needs an explicit branch: check `queue/completed/<job-name>/` first, then `queue/failed/<job-name>/`.
- **`post-process-hook.py` blast radius is acknowledged but not contained.** Plan §Risks (line 165) admits the hook is OrcaWave-tuned and may error on `.sim`, then says "log and skip rather than fail the run; track as follow-up." That recommendation describes an implementation change to `post-process-hook.py` or `watch-results.sh` — but the plan's complexity is T1 ("operational validation, no new code") and the change is not in §Files to Change. If `watch-results.sh` is running on licensed-win-1 and the hook crashes on the new `.sim`, the watcher's lock-file (`scripts/solver/watch-results.sh:14`) may keep firing into a failure loop until manually intervened. Either confirm `watch-results.sh` is NOT running on licensed-win-1 (and document why), or expand scope to include the hook hardening.
- **`submit-job.sh` always writes `export_excel: true`, but `run_orcaflex()` ignores the flag.** `submit-job.sh:32` hard-codes `export_excel: true`; `process-queue.py:375-411` accepts the parameter but never uses it (no `if export_excel:` branch like OrcaWave at `run_orcawave():362-371`). The submitted job YAML will assert behavior the dispatcher won't deliver. Acceptance criterion #4 only checks for `.sim`, so it doesn't fail — but the plan should either acknowledge this divergence as a known gap or override `export_excel: false` at submit time to keep the YAML truthful.
- **Acceptance criterion #6 is incorrect under multi-submitter conditions.** Line 142: "queue/pending/ will be empty after run (job moved to completed/)". `process-queue.py:472` enumerates ALL pending YAML files, so any concurrent submission from another machine into `queue/pending/` after this plan's submit but before licensed-win-1 polls will leave that other job behind, violating the criterion through no fault of the OrcaFlex dispatch. Restate as: "the submitted job's YAML will be absent from `queue/pending/`" — not "the directory will be empty".
- **Pre-flight check named in Risks is missing from the TDD list.** Plan §Risks line 163 says "ask user to confirm task state via `Get-ScheduledTask -TaskName SolverQueue` before submission." But the TDD Test List (lines 122-132) jumps straight to "Submit job" with no step to confirm the scheduled task is actually registered, enabled, and in `Ready` state. If the task doesn't exist or is `Disabled`, the operator will burn the full 30-minute wait window before discovering the problem. Add a row 0: `Get-ScheduledTask -TaskName SolverQueue \| Format-List State,LastRunTime,LastTaskResult` with expected `State : Ready` and a non-stale `LastRunTime`.
- **"Verify push landed" command needs an explicit fetch.** §TDD row 2: `git log -1 origin/main --format=%s`. The local `origin/main` ref is only as fresh as the most recent `git fetch`/`pull`. After `submit-job.sh` runs `git push`, the local `origin/main` ref does get updated by the push itself; that part is fine. But if step 2 runs in a separate shell or after a context switch, it should be `git fetch origin && git log -1 origin/main --format=%s` to be safe. Minor reliability issue.
- **30-minute polling claim oversimplifies.** §Deliverable line 96: "30-min Task Scheduler pickup". Per `setup-scheduler.ps1:35-37`, the trigger is `-Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 30)` — meaning the next firing moment is anchored to whenever `setup-scheduler.ps1` was originally run, NOT a 30-minute clock starting at submit time. Worst-case wait can be the full 30 min; expected wait is ~15 min on average; but the plan should not promise "within 30 min" without noting the offset.
- **Job-name capture is implicit; chain step is fragile.** §TDD rows 4-7 reference `<job-name>` as if it's a known shell variable, but `submit-job.sh` only echoes it once on stdout (line 43). If the operator doesn't capture it (`JOB_NAME=$(submit-job.sh ... | grep -oP '...')`), they'll have to re-derive it from the timestamp. Spell out the capture in row 1's expected result so the downstream rows are runnable verbatim.
- **`.gitignore` not verified for `.sim` blast radius.** Plan §Risks line 164 ("Open" — should `.sim` commit if >50MB?) is unanswered. `process-queue.py:121-129` does `git push origin main` from licensed-win-1 with whatever's been added to `queue/`; if `.sim` is large and not in `.gitignore`, the push will balloon the repo. The plan should either pre-add a size-conditional `.gitignore` rule or run `git check-ignore queue/completed/anything.sim` before the smoke test and document the answer.
