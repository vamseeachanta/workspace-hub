### Verdict: MAJOR

### Summary
Plan is thorough and well-evidenced with verified line numbers, file existence checks, and a phased execution model that addresses prior-wave MAJOR findings. However, the Wave 3 revision to "direct-to-main per assethold repo convention" contradicts two still-unreverted artifacts — Acceptance Criterion #6 and the TDD "feature-branch CI gate" — which would leave the executor without an unambiguous execution strategy. A couple of scope/coupling items also need tightening before approval.

### Issues Found
- [P1] Execution-strategy contradiction: Wave 3 revisions state execution is 'direct-to-main per assethold repo convention, not feature-branch,' and the pseudocode PHASE GATE block now says 'Direct-to-main per assethold repo convention — no branch/PR required.' But Acceptance Criterion #6 still reads 'Phase 1 and Phase 2 are separate commits on a feature branch with CI verification between them (P1 push → verify jobs register → P2 push → verify smoke green → PR to main).' The TDD section also references a 'Feature-branch CI gate' as the canonical sibling-less verification. The plan has two mutually exclusive execution strategies in normative sections — an executor cannot proceed without guessing which is authoritative.
- [P1] TDD test list carries a 'Feature-branch CI gate' mandate that the Wave 3 revision invalidated. The phrase 'push P2 commit to feature branch, wait for CI, verify smoke cell green before merging to main' must be rewritten to the direct-to-main model (e.g., 'push P1 commit, observe CI, verify jobs[] != []; only then push P2 commit') or the direct-to-main decision reversed — pick one.
- [P2] Deliverable text still bundles 'docs.yml hardening' into Phase 3 ('(3) full matrix + docs.yml hardening'), while Wave 3 revisions make docs.yml 'explicitly out-of-scope for P1/P2 success criteria' and Acceptance Criteria treats it as optional ('either goes green OR a follow-on issue is filed'). Deliverable prose should be reconciled so the executor doesn't interpret docs.yml as a hard P3 gate.
- [P2] T2 complexity claim is partially unsupported. The justification says 'the remediation is mechanically deterministic (all fix sites already identified).' This is true for P1 and the P2 install/checkout edits, but P3 'drive remaining matrix cells / jobs to green' and 'full quality-gate chain' depend on latent test-red state in a workflow that has never been green. Either carve P3 out into a distinct T2/T3 follow-on, or acknowledge in the complexity stanza that P3 has non-deterministic scope and re-scope success accordingly.
- [P2] `ref: main` coupling is accepted without a concrete fallback. The plan acknowledges that an assetutilities main breakage flips assethold CI red but offers no pin-to-SHA fallback in this plan's execution — only a vague 'if volatile, pin in a follow-on.' Given this is the FIRST green attempt in 7 months, a transient assetutilities breakage during execution would mis-attribute a P2 failure. Consider pinning to the current-verified SHA for the initial green run and switching to `ref: main` in a follow-on once the baseline is established.
- [P3] Concurrent-modification risk unaddressed: direct-to-main across two commits with CI wait-between creates a window where an unrelated push to assethold main could interleave. No mitigation (e.g., 'no other pushes to main between P1 and P2 confirmation') is stated.
- [P3] No explicit rollback contract for direct-to-main. If P1 lands and exposes a different startup-rejection mode not predicted by the local yaml.safe_load check, the plan doesn't say what to do (revert vs forward-fix). One sentence on rollback policy would close this.
- [P3] The 'phase-1: upload-artifact is v4 exactly' test asserts exactly 3 occurrences, but the Files to Change table already records the 3 P1 upload-artifact bumps — fine. However, `rg -c 'upload-artifact@v3\|upload-sarif@v2\|codecov-action@v3' ...` uses alternation that in ripgrep requires either an `-e` flag per pattern or a single alternation inside a character class — the escaped-pipe form inside single quotes won't behave as alternation in ripgrep without regex mode; verify the exact incantation or switch to three `rg -c` calls.

### Suggestions
- Resolve the feature-branch-vs-direct-to-main contradiction by rewriting Acceptance Criterion #6 and the TDD 'Feature-branch CI gate' entry to match the Wave 3 direct-to-main decision (or revert Wave 3 and keep feature-branch). Add a single sentence in the Adversarial Review Summary noting which artifacts were touched for this reconciliation.
- For the sibling checkout step, pin `ref:` to the current HEAD SHA of `vamseeachanta/assetutilities` main captured at plan-execution time. Record that SHA in the plan footer and file a follow-on issue to switch to `ref: main` once a baseline green exists. This removes a non-deterministic failure mode during the first-green attempt.
- Add a one-line rollback clause to the PHASE GATE ENFORCEMENT block: 'If P1 CI shows a regression not predicted by the local yaml.safe_load check, revert the P1 commit before investigating; do not forward-fix on top of a broken main.'
- Split P3 into two named sub-gates in the Acceptance Criteria: (a) 'quality-gate chain reaches success with current tests green' vs. (b) 'if latent test failures are exposed, file follow-on issues and declare P2-green as the shipped deliverable.' This removes the risk that P3 scope balloons post-hoc.
- Verify the `rg -c` alternation in the TDD list actually matches — consider replacing with three separate assertions (`upload-artifact@v3 == 0`, `upload-sarif@v2 == 0`, `codecov-action@v3 == 0`) to remove any ambiguity about ripgrep regex behavior.
- Consider adding a short 'Preconditions for Execution' subsection listing the exact gh/ripgrep/python versions used in the Evidence section, so re-verification by the executor reproduces the same counts.
