## MAJOR Findings

### M1. OS-name token inconsistency would break the AI-provider bootstrap integration (G1)

**Severity:** MAJOR — silently breaks the critical G1 integration that is the headline deliverable.

**Evidence:**
- `scripts/memory/bootstrap-machine.sh:26` uses `Darwin) OS="macos" ;;` (verified just now).
- This plan §Pseudocode `detect_os()` proposes `Darwin*) echo "darwin"`.
- The two values diverge. When `new-machine-setup.sh` Step 10 invokes `bootstrap-machine.sh`, the latter expects `macos` internally; if the new shared `detect-os.sh` returns `darwin`, downstream conditionals (e.g., `if [[ "$OS" == "darwin" ]]`) will silently miss the macOS branch.
- Existing `new-machine-setup.sh:34-37` and `verify-setup.sh:25-28` use `WH_OS` (already-inconsistent variable name) and **neither has a Darwin case at all** — they treat macOS as `linux`.

**Required:** Plan must pick a canonical token (`darwin` OR `macos`) and explicitly document the rename pass: either patch `bootstrap-machine.sh:26` to use the new token, or align the new `detect-os.sh` to use `macos`. The current Files-to-Change row "Modify `bootstrap-machine.sh`" is missing.

### M2. CLI install method is not uniform — `pkg_install <cli>` pseudocode is wrong

**Severity:** MAJOR — the auto-install (G2) deliverable cannot work as designed.

**Evidence (verified live):**
- `claude` = npm package: `npm install -g @anthropic-ai/claude-code`
- `codex` = npm package, version-pinned via `scripts/install/pin-codex.sh`
- `gemini` = npm package: `/home/vamsee/.npm-global/bin/gemini` confirms npm origin
- `gh` = system package: apt/brew/choco

**Plan §Pseudocode line:** `for cli in [claude, codex, gh, gemini]: ... run pkg_install <cli>` — assumes uniform package manager. Three of four CLIs are npm packages; only `gh` is system pkg. `apt install -y claude` will fail; `apt install -y codex` will fail; `apt install -y gemini` will fail.

**Required:** Pseudocode must branch by install-channel, not by OS:
- `gh` → per-OS system pkg (apt/brew/choco)
- `claude`, `gemini` → `npm install -g <pkg>` (Node prerequisite check needed first)
- `codex` → existing `scripts/install/pin-codex.sh` (reuse, don't reinvent)
- Hermes → out-of-band, document URL

Also: plan must verify `npm` is available before npm-installs and chain Node-install if missing on darwin (`brew install node`) and Windows (`choco install nodejs`). On Linux this is already handled at `new-machine-setup.sh:171`.

### M3. "Auto-install no prompt" + "Interactive auth" is contradictory UX that the plan does not reconcile

**Severity:** MAJOR — user-facing contract is ambiguous; promised behavior cannot be delivered as stated.

**Evidence:**
- §User decisions captured: "Verify + auto-install no prompt — bash will run `apt/brew/choco install -y` for each missing CLI".
- §Risks: "Auto-install (no-prompt per user decision) requires elevated privileges".

These two are in tension. On Linux, `sudo apt install -y` still triggers a *sudo password prompt* (not the `-y` confirmation prompt). On macOS, `brew install` runs as user but writes to `/usr/local/Cellar` (Intel) or `/opt/homebrew` (Apple Silicon) and may sudo. On Windows, `choco install -y` requires elevated PowerShell. "No prompt" is true for the install-confirmation question but false for elevation.

Then Step 12 (auth) is **explicitly interactive** — `claude auth login` etc. spawn browser flows that block the script.

**Net contract**: the script is "sometimes silent, sometimes blocks for a sudo prompt, sometimes blocks for a browser." This is fine — but the plan must say so. The acceptance criterion "All four provider CLIs auto-install when missing" is unverifiable in CI without mocking elevation.

**Required:**
- Add explicit UX-contract section: "fully unattended phases" vs "elevation-required phases" vs "browser-blocking phases" — itemized.
- Clarify acceptance criterion to say "auto-install path is exercised; elevation prompt is acceptable; browser flows complete user-side".
- Add `--non-interactive` flag for CI mode that mocks auth and skips elevation-requiring steps.

## MINOR Findings

### m1. Hermes does not have an `auth login` command — plan conflates auth flows

**Evidence:** §Pseudocode `orchestrate_auth()` shows a loop over `[claude auth login, codex auth login, gh auth login, gemini auth]`. Hermes is correctly treated separately (`.env` prompts). But `gemini auth` may not be the actual subcommand — Gemini CLI uses different auth flows depending on installation method (OAuth via browser vs. service-account). Plan should verify the actual command syntax before TDD-locking it.

**Fix:** Add a discovery step: "Verify `gemini auth` is the correct invocation for the installed gemini CLI version. If not, substitute with documented alternative."

---

### m2. PowerShell parity is hand-wavy — some bash steps have no Windows equivalent

**Evidence:** Plan asserts "functional parity" for `new-machine-setup.ps1` but:
- Step 4 shell aliases: bashrc-snippets vs. PowerShell `$PROFILE` — different concept
- Step 6 crontab vs. Windows Task Scheduler — XML-driven, not crontab
- Step 8b tmux: no Windows equivalent (Windows Terminal panes work differently)
- Step 7 SSH key: works on PowerShell but uses different commands

**Fix:** Add a §"PowerShell-to-Bash mapping table" in the plan showing which of the 14 steps map 1-to-1, which map differently, and which are skipped. Existing precedent: `scripts/windows/setup-scheduler-tasks.ps1` already exists for Task Scheduler.

### m4. `config/machine-baselines/<hostname>.yaml` PII risk — hostname may leak

**Evidence:** Plan does not address hostname sanitization. Some hostnames embed user/company identifiers (e.g., `vamsee-laptop-tx-bjk-01`). The file is git-tracked → public on the repo. The `collect-machine-baseline.ps1` precedent uses redaction but its output is local-only, not committed.

**Fix:** Add §"Hostname publication policy":
- (a) Use hostname as-is (current draft, risks PII), OR
- (b) Use a stable machine-id (UUID) with a separate private mapping table, OR
- (c) Use a documented alias (e.g., `ace-linux-1` already aliased) and require an alias to exist before status emission.

Recommend (c) with fallback to (b) for unaliased machines.
