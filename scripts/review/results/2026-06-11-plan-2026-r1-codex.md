## Findings
1. Plan D5 requires `triggering_message_id` in the dedup key, but the authoritative schema does not define that field or include it in `dedup_key`. The plan says “adding `triggering_message_id` where available” and the pseudocode says “build dedup key including triggering_message_id” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:232-255`), while `docs/design/email-queue-state-schema.yaml:31-66` has no `triggering_message_id` property and keeps `dedup_key` to `account_id`, `thread_id`, `from_state`, `to_state`. The Files to Change list omits `docs/design/email-queue-state-schema.yaml` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:290-309`), so implementation can pass code tests while leaving the contract artifact stale.

2. The plan introduces `needs-user-decision` / `needs_user_decision` as a pending-work state or count without defining it in the state contract. D3 lists `needs-user-decision` as a durable bucket and says empty requires zero `needs-user-decision` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:216-226`); pseudocode counts `needs_user_decision` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:279-281`); the TDD list uses “one needs-user-decision” as test input (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:330-331`). But the schema allows only `inbound`, `extracted`, `awaiting-reply`, `completed`, `purged` for entries and snapshots (`docs/design/email-queue-state-schema.yaml:3-8`, `docs/design/email-queue-state-schema.yaml:34-39`, `docs/design/email-queue-state-schema.yaml:108-110`), and the current design state machine also lists only those five states (`docs/design/email-as-queue.md:53-68`). The plan must either add a schema-backed field/classification for user-decision backlog or stop treating it like a state.

3. Missing-extraction reactivation semantics contradict the current contract. The design says if a linked extraction is missing, the system emits `extraction_missing_on_reactivation` “then treats the message as new inbound” (`docs/design/email-as-queue.md:41-43`). The plan pseudocode instead appends the learning event and transitions `prior_state -> extracted` with `reason="missing-extraction"` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:265-270`). The planned test only verifies that a learning event is emitted (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:329`), so it would not catch the wrong final state.

4. The plan downgrades live Gmail label work below the issue’s stated verification without getting explicit approval for that scope cut. Issue #2026 body includes “Gmail Labels (visual + API-friendly)” and implementation task “Create Gmail labels via API”; the 2026-06-10 issue comment says verification includes “Labels created.” The plan changes this to “label-operation plan” and “live Gmail label mutation must be off by default” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:228-230`) with acceptance only that a planner exists and mutation is opt-in (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:353`). That may be a reasonable safety decision, but as written it silently narrows issue scope.
