### claude

- **Caller-migration of `select_tasks` is unenumerated in Files-to-Change — silent break risk at `cron_transaction.py:393`.** The plan's Files-to-Change (`docs/plans/...:425`) says "Extend `select_tasks` to accept machine-token legacy matching," changing the 3rd parameter from a single `machine_id: str` to a token collection. But `grep` finds **7 surviving string-arg callers** the plan never lists for migration: the in-module self-check `select_tasks(tasks, ["worker"], "host1")` at `scripts/cron/cron_transaction.py:393`, and 6 calls in `tests/cron/test_cron_transaction.py:170,177,183,193,203,215`. The plan's only stated edit to `test_cron_transaction.py` (`...:431`) is "Add tests for preserving `WORKSPACE_HUB=`/`LOG=` env lines" — it does **not** mention migrating these 6 existing calls. If the parameter becomes a list and a bare string `"host1"` is passed, set/membership matching silently changes semantics (`set("host1")` → char-set, or shifted `in` behavior). The 6 pytest calls would surface under TDD, but the `__main__` self-check at line 393 is **not** in the focused gate (AC `...:491` runs pytest, never `python cron_transaction.py`) and would break silently.
- **Internal contradiction: pseudocode names a new function `select_cron_tasks`, Files-to-Change says modify `select_tasks` in place.** Pseudocode `...:352` defines `select_cron_tasks(tasks, roles, machine_tokens)` and `run_cutover` (`...:376`) calls `select_cron_tasks(...)`, while Files-to-Change (`...:425`) says "Extend `select_tasks`." These are two different implementation strategies (new parallel function vs. in-place signature change) with different blast radii — and the plan's own §Risks (`...:568`) warns precisely against "two independent implementations" causing divergence. The plan must pick one and, if in-place, list the call-site updates from Finding 1.
- **`catalog_commands` `[:60]` truncation change is under-scoped to `notification-purge`.** The plan frames the fallback-key fix around `notification-purge` (TDD list `...:456`, revision R6 `...:554`: "changed fallback catalog keys for non-script tasks from truncated 60-character prefixes to full raw/rendered command keys"). But `catalog_commands` at `cron_apply.py:119-130` applies `cmd.strip()[:60]` to **every** task lacking a `scripts/*.sh|*.py` token, and its keys feed `classify_line` for *all* out-of-block line classification. Removing truncation globally is a behavioral change to the classifier's matching surface for any other non-script catalog task; the plan tests only the `notification-purge` shape and does not assert the change is safe (or no-op) for other fallback-keyed tasks. Risk is collision-reduction (benign direction), but the scope is broader than the plan's test coverage claims.
- **Live full-set acceptance proof (AC `...:485`) is single-host and the plan's own memory lineage flags per-machine partiality.** The 16.13s / `repo_count=17` proof was run only on ace-linux-1. I verified `17 = required(6)+optional(2)+non_tier1(9)`, so coverage *is* complete here — but the AC asserts completion "across the live governed repo set" as a general gate, and SHARED_SOUL's "Verify coverage assumptions empirically" rule records that ace-linux-1 once had only 3 of 7 tier-1 siblings checked out. The acceptance criterion is satisfiable today on this host but is not portable; the plan should state the gate is host-local closeout evidence (which AC #12's automated bucket-enumeration test, `...:486`, correctly separates) rather than a cross-machine guarantee.
- **`--machine vamsee-linux1` alias resolution gap is real but the fix locus is under-specified.** The plan's AC (`...:479`) requires `cron_apply.py --machine vamsee-linux1` to resolve to `dev-primary`. Verified that `main()` at `cron_apply.py:222-224` only matches `e.hostname.startswith(host) or m == host` and never consults `hostname_aliases`, so `vamsee-linux1` currently falls through to `machine_roles(registry,"vamsee-linux1")` → empty → `status:skip`. The plan's pseudocode `resolve_machine` (`...:305`) correctly adds alias matching, but Files-to-Change (`...:424`) attributes alias resolution to `cron_apply.py` generically without noting the specific `main()` host-resolution block (lines 222-224) that must change versus the `run_cutover`/`machine_roles` path — leaving ambiguity about whether alias resolution lands before `machine_roles` is called (it must).

### codex

- `notification-purge` can still be duplicated because the plan allows the live legacy line to classify as preserved while also selecting/rendering the catalog task. Plan pseudocode says to preserve existing external/ignore lines exactly and only assert expanded/unexpanded `notification-purge` legacy lines classify as “cataloged/preserved” (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:388-389`, `:456`, `:478`). Existing classification checks fingerprints before catalog keys (`scripts/cron/cron_transaction.py:191-198`), and `notification-purge` has a preserved-local fingerprint matching `find logs/notifications/` plus `-delete` (`config/workstations/harness-state-classes.yaml:120-130`). The same task is also in the catalog (`config/scheduled-tasks/schedule-tasks.yaml:311-320`) and the plan requires its selected command to appear in `plan["new_text"]` (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:456`). That combination preserves the old out-of-block line and adds the managed one. The existing state-class comment explicitly says the live duplicate should be deduped, not merely preserved (`config/workstations/harness-state-classes.yaml:126-128`). The plan needs an explicit rule/test that catalog-owned preserved-local lines such as `notification-purge` are not duplicated after cutover.
- The plan omits `scripts/cron/cron-audit.py`, leaving the pre-cutover classifier inconsistent with the planned raw+rendered full-command catalog matching. The deliverable promises “raw-and-rendered catalog matching for placeholder fallback tasks” (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:296`), but Files to Change excludes `scripts/cron/cron-audit.py` (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:421-436`). `cron-audit.py` is documented as the fail-closed pre-cutover gate (`scripts/cron/cron-audit.py:6-12`) and builds its own catalog fragments with raw command fallback only (`scripts/cron/cron-audit.py:72-98`). The plan changes `cron_apply.py` catalog keys (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:378-381`, `:424`) but leaves the audit path able to report different classifications from the cutover path. Either the shared catalog-key/rendering helper must be used by `cron-audit.py`, or the plan must explicitly scope out the pre-cutover audit and explain why inconsistent audit/apply classification is acceptable.
