### Verdict: MAJOR

### Summary
The v2 re-draft is substantially stronger than v1: design decisions are locked with rationale and rejected counter-options, the state machine is internally consistent, the dependency contract is explicit, and TDD coverage grew from 7 to 19 tests. However, a scope/test contradiction blocks approval: the plan explicitly excludes pipeline code ("this issue does not produce the pipeline code itself — that is #2024"), yet mandates that state-machine behavior tests (e.g., `test_transition_inbound_to_extracted_writes_log`) pass as an acceptance criterion. Those tests cannot pass without the #2024 implementation. Secondary concerns around concurrency, PII redaction, and timezone semantics are fixable with small edits.

### Issues Found
- [P1] Scope/acceptance contradiction: Deliverable section says this issue produces a design doc + config/schema/fixtures only, with pipeline code in #2024, but the Acceptance Criteria require `uv run pytest tests/email/ -v` to pass and the test list includes behavioral tests (transition log writes, snapshot replay, reactivation, grace-boundary sweep, idempotency) that are impossible to green without the #2024 pipeline. Either move those tests to #2024, include a minimal reference implementation in #2017, or mark them xfail/skip with an explicit policy.
- [P1] skylineseven.ccsend.com routing decision is listed as 'user decision required' and conditional, but the plan asks for plan approval before that decision lands. Approvers would be signing off on an artifact whose routing table row is unresolved. Either resolve before approval or explicitly declare the routing edit out of scope for this plan.
- [P2] Concurrency model for `queue-state.jsonl` + `queue-state-snapshot.yaml` is not specified. Daily sweep + inbound handler + reply handler can all write concurrently; plan should declare single-writer semantics (fcntl/flock) or a queue, otherwise `test_transition_idempotent_on_duplicate` is insufficient coverage.
- [P2] No corruption-recovery contract. Tests cover atomic snapshot write, but not: JSONL mid-line truncation, snapshot-vs-log divergence detection, or rebuild-from-log procedure. Given JSONL is the authoritative state, a single corrupt append could be catastrophic.
- [P2] Test fixtures at `tests/fixtures/email/` will contain real email content (the plan says 'redacted sample corpus'). Redaction procedure, ownership, and automated verification (e.g., a linter that fails on patterns matching emails/phone numbers/names) are unspecified. PII leak risk on first commit.
- [P2] `lookup_schema(message.sender_domain)` fallback for unknown senders is not defined in pseudocode or state machine. What state does a message with no matching schema end up in?
- [P3] Timezone for `completed_at` is unstated. Grace-period boundary tests (day 6 vs day 8) are non-deterministic across TZ unless UTC is pinned in the schema.
- [P3] Acceptance criterion 'All 3 v2 verdicts are APPROVE or MINOR (no MAJOR)' couples plan approval to external provider behavior that could deadlock if any provider chronically returns MAJOR on a defensible plan. Consider an override path (e.g., user may approve with documented dissent).
- [P3] Volume estimate double-counts: 50 threads/day × 365 = 18,250 threads, but JSONL logs *transitions* (potentially 3–5 per thread across inbound → extracted → completed → purged), so annual JSONL lines could be 55k–90k. Compaction threshold should be based on transition count, not thread count.
- [P3] 'If extraction missing → treat as new inbound' silently loses thread history. Should emit a structured log event (`reason=extraction_missing_on_reactivation`) for the quarterly learning review, otherwise this failure mode is invisible.
- [P3] `test_snapshot_atomic_write` simulates 'write failure mid-snapshot' but doesn't specify the atomic-write technique (tmpfile + rename, O_TMPFILE + linkat, fsync ordering). Implementation is free to pick an unsafe approach and still pass a narrow test.
- [P3] Quarterly learning review has no named owner, no output artifact (issue? doc? dashboard?), and no trigger (calendar cron? manual?). As written, it is aspirational, not operational.

### Suggestions
- Resolve the scope/test contradiction: either (a) move behavioral state-machine tests to #2024 and keep only config/schema validity tests in #2017, or (b) add a minimal `queue_state.py` reference implementation to #2017's Files to Change, or (c) mark the behavioral tests `@pytest.mark.xfail(reason='pending #2024')` with an acceptance criterion stating they are written but not required to pass.
- Pin all timestamps to UTC in `email-queue-state-schema.yaml` and add a test that rejects non-UTC `completed_at` values.
- Add a `concurrency` section to the design doc: declare single-writer via fcntl advisory lock on the JSONL file, with writer-identity logged in each entry for diagnostics.
- Add a snapshot-divergence detector: `snapshot.sha256` alongside the snapshot file, verified on read; on mismatch, rebuild from log and alert.
- Commit a redaction tool (e.g., `scripts/email/redact-fixture.py`) with a pre-commit hook that fails if any file under `tests/fixtures/email/` contains patterns matching real email addresses, phone numbers, or the user's known domains.
- Extend the precedence rule into the pseudocode explicitly — currently `apply_precedence` is called but not defined.
- Specify an unknown-sender fallback classification (likely `archive` with a `needs_schema` flag) and add a test for it.
- Decouple plan approval from external-reviewer consensus: change the acceptance criterion to 'v2 cross-review artifacts exist and are summarized in the Adversarial Review Summary' and let the user decide whether any remaining MAJOR blocks approval.
- Name the quarterly learning review owner, output (a dated markdown report under `docs/reviews/`), and scheduling mechanism (GitHub trigger or calendar reminder).
- Split the 'legitimate-inquiries' false-positive corpus into source-domain buckets so coverage gaps are visible (e.g., ≥3 from CRE senders, ≥3 from engineering inquiries, ≥4 from misc).

- Is the skylineseven.ccsend.com routing decision a blocker for plan approval, or only for implementation? The plan says one thing in the deliverable and another in the risks section.
- What is the single-writer guarantee for `queue-state.jsonl`? Multiple entry points (inbound handler, reply handler, daily sweep, manual corrections) all write to it.
- How will test fixtures be redacted, and is redaction verified by an automated check before commit?
- What happens in `classify_inbound` when `lookup_schema(message.sender_domain)` returns no schema — which state does the message land in, and is there a test for it?
- What timezone governs `completed_at`, and how will the grace-boundary tests be made deterministic across CI runners in different TZs?
- Does `transition(..., reason=reactivation)` actually change state when the source state was already `extracted`? The state diagram allows extracted→extracted only via reactivation, but idempotency rules could suppress it — which wins?
- What is the rebuild-from-log procedure if the snapshot is lost or corrupted, and is it tested?
