### Verdict: MAJOR

### Summary
The plan has strong context and a reasonable decomposition, but it is not yet complete enough to approve. The main gaps are around unresolved design decisions being treated as deliverables without clear acceptance criteria, an underspecified re-activation/deletion mechanism given Gmail scope constraints, and a test strategy that relies on ad hoc samples rather than committed fixtures/contracts.

### Issues Found
- [P1] The core design decisions are still open or only marked as tentative, yet the plan proposes downstream-unblocking deliverables. Approval should require explicit choices for state authority, deletion policy, re-activation mechanism, and schema ownership, not just a promise that the design doc will decide later.
- [P1] The re-activation and deletion flow is technically under-specified and may be infeasible as written. The plan acknowledges current Gmail scope may not support label/state mutation, but it does not define a concrete implementation boundary or fallback, so the proposed state machine may not be actionable for #2024/#2026.
- [P2] Acceptance criteria are incomplete for a contract-setting design issue. They require files to exist, but do not require a transition table, authoritative state source, failure/rollback behavior, idempotency rules, duplicate-event handling, or a precise downstream interface for consumers.
- [P2] Dependencies are identified informally, but not modeled explicitly enough. The plan should state which issue is blocked by which design output, what inputs each downstream issue expects, and whether introducing `queue-state.jsonl`, `spam-detection-rules.yaml`, or a schema file creates additional follow-on work not captured here.
- [P2] The test strategy is too weak for a semantic-contract plan. Config parse tests are fine, but the behavioral tests depend on `/tmp` session artifacts and fabricated samples rather than committed fixtures, and they do not cover edge cases like repeated replies, trash restoration failure, false-positive spam on legitimate CRE mail, or duplicate extraction events.
- [P3] Scope is drifting beyond the stated 4 open decisions. New routing entries, a spam-rule system, possible schema versioning, docs index updates, and optional `.planning/INDEX.md` changes are reasonable adjacent work, but the plan does not distinguish required scope from opportunistic additions, which increases creep risk.
- [P3] There is a consistency issue in the pseudocode/state model. `noise` and `actionable` appear as transition targets but are not listed in the declared states, and `re-activated` is described as a transition target while also implying a transient label rather than a true state.

### Suggestions
- Turn the tentative recommendations into explicit plan decisions before review approval, or split this into a design-decision phase and a later documentation/config phase.
- Add a small contract section that defines the authoritative state store, Gmail label semantics, event triggers, idempotency rules, and the exact interface downstream issues will consume.
- Replace `/tmp`-based examples with committed redacted fixtures under the repo, and expand tests to cover duplicate replies, restore-from-trash behavior, grace-period expiry, and spam false-positive/false-negative boundaries.
- Tighten scope by labeling items as required for #2017 versus deferred follow-on work; if schema versioning or broader spam-rule infrastructure is needed, capture that explicitly as a dependency or follow-up issue.
- Add a dependency table mapping #2017 outputs to #2024, #2026, and #2019 inputs so downstream teams know what is guaranteed once this plan is approved.
