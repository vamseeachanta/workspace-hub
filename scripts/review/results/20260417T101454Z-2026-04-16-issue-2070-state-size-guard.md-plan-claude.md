### Verdict: MAJOR

### Summary
The plan is well-researched, correctly scoped to T1, and mirrors an existing hook pattern, but it has a concrete defect in the pre-commit guard (sizes the working tree instead of the staged blob), a rotation design that may silently break the #1782 learning pipeline, and a headroom math issue at the 90 MB threshold that leaves only ~10 MB of safety margin against GitHub's 100 MB hard cap.

### Issues Found
- [P1] Critical: The hook reads working-tree size via `stat` on `working_tree/$file` rather than the staged blob size. A developer can `git add` a 95 MB file, then truncate or delete it on disk before committing, and the hook will pass while the oversized blob still enters the index and gets pushed. Use `git cat-file -s :0:$file` (staged blob size) — and the test `test_hook_uses_working_tree_size` actually codifies the wrong behavior.
- [P1] Critical: Rotation risk to #1782/#1720 pipelines is listed as a 'Risk' but there is no verification task, no consumer-contract check, and no rollback plan. The plan proposes to `mv` and `truncate` a file that downstream learning jobs depend on; this must be validated (or the consumer updated to read `cost-tracking*.jsonl.gz` + live) before the rotation script runs in production.
- [P2] Important: 90 MB threshold leaves only 10 MB of headroom against the 100 MB GitHub hard limit. Because a single append to a 89 MB file can easily exceed 100 MB before the next commit runs, the guard cannot by itself prevent the failure class it claims to prevent. Recommend 75 MB (already noted as a risk but not adopted).
- [P2] Important: Acceptance criterion 'After rotation, a fresh `git push` succeeds (regression of the original failure)' does not actually regression-test the hook — it tests that rotation reduces size. Add a criterion that attempts to commit a synthesized 95 MB file and verifies the push is blocked at commit time, not at GitHub's server.
- [P2] Important: The rotation script auto-commits (`git commit -m ...`) which will bypass the normal PR/review flow and may fire other pre-commit hooks (plan-approval-gate, gsd-validate-commit). Behavior under those hooks is undefined; plan should either invoke `--no-verify` intentionally (with justification) or run rotation via a dedicated branch/PR.
- [P2] Important: Scope creep is acknowledged ('scan all of `.claude/state/**`' vs just `session-signals/`) but left as an open question. The 'Deliverable' and 'Acceptance Criteria' reference `.claude/state/`, while the issue title says 'session-signal files'. Resolve before implementation so tests reflect the real watch list.
- [P3] Minor: `test_rotate_creates_archive_and_resets` expects the source file to be '0 bytes' after rotation, but the pseudocode uses `touch $SRC` which is correct for creating an empty file — however on some filesystems `touch` on an existing file does not truncate. Use `: > $SRC` or `truncate -s 0` explicitly and update the test.
- [P3] Minor: `.gitignore` modification adds `.claude/state/session-signals/archive/` but says 'gzip rotated archives stay tracked' — these two statements contradict unless an explicit `!*.gz` re-include is added. Spell out the exact rule.
- [P3] Minor: No mention of pre-push hook despite the Artifact Map saying it wires `Bash(git push*)`. The hook only inspects the staged index (`git diff --cached`), which is empty at push time. Need a separate pre-push check that inspects the commits being pushed (e.g., `git rev-list @{u}..HEAD` + `git ls-tree`) or drop the push claim.
- [P3] Minor: No performance bound on the weekly report — if `.claude/state/**` grows to thousands of files, `du`/`find` scans are fine, but this should be stated so future maintainers know the cron is O(files), not O(git-history).

### Suggestions
- Replace the `stat` on working tree with `git cat-file -s :0:$file` inside the pre-commit hook so the guard reflects what actually enters the repository. Rename the existing test to `test_hook_reads_staged_blob_size` and add a regression test where the working-tree file is truncated after `git add`.
- Add an explicit pre-implementation task: 'Verify #1782 / #1720 consumers handle rotated `.jsonl.gz` archives' with a named file to inspect. Either update the consumer to glob `cost-tracking*.jsonl*` or keep the file unrotated and use LFS — decide before writing the rotation script.
- Lower the block threshold to 75 MB and keep the 50 MB warning, or make both configurable via env vars (`STATE_SIZE_BLOCK_MB`, `STATE_SIZE_WARN_MB`) so the values can be tuned without editing the hook.
- Split the pre-commit and pre-push gates into two scripts with a shared core, or document that only pre-commit is wired and remove the pre-push claim from Artifact Map + settings entry.
- Add an acceptance test that stages a 95 MB file, runs `git commit`, and asserts the commit is refused — this is the actual regression test for the 103 MB push failure.
- Resolve the 'scan all state vs only session-signals' open question explicitly before TDD. If the answer is 'all of `.claude/state/**`', rename the plan and update the issue to reflect the broader scope.
- For the rotation auto-commit, either (a) route through a PR using `gh pr create` so review gates still apply, or (b) add an allowlist entry in `plan-approval-gate.sh` for rotation commits and justify the bypass in the runbook.
- Consider Git LFS vs gzip-in-tree now rather than deferring. LFS keeps file paths searchable and avoids the recurring rotation maintenance burden; the tradeoff is a new tool dependency. Document the decision rationale in the plan.
- Add a 'How to synthesize a 95 MB fixture cheaply' note to the bats tests (e.g., `head -c 95M /dev/zero > fixture.jsonl`) so the test suite does not bloat the repo.

### Questions for Author
- Which consumers actually read `.claude/state/session-signals/cost-tracking.jsonl` today, and will they handle a rotated `.jsonl.gz` + live-file pair, or do they expect a single contiguous file?
- Is the intended gate pre-commit only, or both pre-commit and pre-push? The settings wiring mentions both, but the pseudocode only handles the staged index.
- Why 90 MB and not 75 MB, given the 10 MB headroom concern you flagged yourself — is there a scenario where 90 MB is strictly better?
- Should the scope be `.claude/state/**` (as the pseudocode says) or only `.claude/state/session-signals/**` (as the issue title suggests)? The acceptance criteria should match whichever is chosen.
- Is auto-commit from `rotate-cost-tracking.sh` intentional, and how does it interact with `plan-approval-gate.sh` and other existing pre-commit hooks?
- Has the option of Git LFS for `cost-tracking.jsonl` been evaluated and rejected, or is it deferred? If deferred, what triggers a revisit?
- For the weekly size report at `docs/reports/state-size-YYYY-WW.md` — is a committed markdown file the right output, or should it be a GitHub issue comment / actions summary to avoid polluting git history?
