### Verdict: MAJOR

### Summary
The plan still has correctness-critical contradictions and underspecified contracts around status semantics, publication-mode execution, domain inference, and schema mapping. It is not approval-ready.

### Issues Found
- `Identity Join Contract` vs `Candidate Record Shape` is internally contradictory. The plan says source records "must be exactly one of: `gap`, `covered`, `identity-unresolved`, `domain-unresolved`", but later `Allowed source statuses` adds `domain-mismatch`, and the cross-domain policy explicitly classifies records as `domain-mismatch`. A consumer cannot implement or validate statuses correctly when the canonical enum disagrees across sections.
- `Candidate Record Shape` and `Deliverable` do not define whether `domain-mismatch` records belong in per-domain YAML. The plan says a wrong-domain wiki match should be classified as `domain-mismatch` and "continue treating the source-domain record as not covered for per-domain gap accounting", and the pseudocode then calls `add_gap(...)`. But `Deliverable` and `Acceptance Criteria` require per-domain YAML only for "true canonical gaps". That leaves the output contract ambiguous for one of the key edge cases the plan is supposed to settle.
- `Pseudocode` and `Scheduled Task Contract` disagree on how publication mode is activated. The pseudocode signature is `run(config_path, dry_run=False, publication_mode=False)` and only enters clean-worktree/lock/write/exit-2 publication behavior when `publication_mode` is true. The scheduled command runs `uv run python scripts/knowledge/detect_wiki_gaps.py --config config/ai-tools/wiki-gap-detection.yaml` without any publication flag, while the config merely contains `publication_mode: git-commit`. The plan never specifies that config loading flips the runtime into publication mode, so the scheduled path may execute the non-publication branch and silently skip the stated safeguards/exit-code behavior.
- `Candidate Record Shape` makes cross-domain coverage depend on `wiki_domains_by_key[canonical_key] == record.domain_slug`, but the plan never defines a concrete, testable wiki-domain normalization contract. `infer_wiki_domain(page, fm, config)` appears only in pseudocode, and `Scheduled Task Contract` defines `source_root_domain_map` and `design_code_domain_defaults` but no equivalent mapping/rule for wiki pages. Without a normative rule for deriving wiki domain from path/frontmatter, the plan cannot guarantee stable `covered` vs `domain-mismatch` classification.
- `Supplemental source field contracts` remains too vague to implement safely. Claims such as "title/name field", "canonical source path or reference field", "standard family/domain field", and "`doc_path` or equivalent source reference" do not identify actual field names or a deterministic fallback order for each source type. Because these heterogeneous files drive coverage accounting, leaving authoritative keys at the "or equivalent" level pushes correctness-critical schema decisions into implementation and makes the acceptance criteria non-verifiable from the plan.
- `Resource Intelligence Summary` asserts `data/document-index/index.jsonl` as a required input and the manual approval gate depends on it, but the plan provides no attested or plan-derived evidence that this file exists on the target repo state. The same section's `Current-state evidence` only verifies `data/design-codes/code-registry.yaml`. For a required input that gates both runtime and approval, the resource-intel section is incomplete.

### Suggestions
- Unify the status model into one canonical enum and state explicitly whether `domain-mismatch` is a source-record status, a diagnostic overlay, or both.
- Define the per-domain YAML contract for `domain-mismatch` records in one sentence: either exclude them from YAML entirely or include them with an explicit non-gap status and justify why that still satisfies the "true canonical gaps" acceptance criterion.
- Specify exactly how publication mode is enabled: CLI flag, config field consumed at runtime, or both. Then align pseudocode, scheduler command, and exit-code contract to that single mechanism.
- Add a normative wiki-domain derivation rule, including precedence between path, frontmatter, and config mappings, plus normalization examples and collision behavior.
- Replace each supplemental-source "field or equivalent" description with concrete field names and fallback order per file type, or point to a checked-in schema/mapping config that the implementation must use.
- Verify and record the existence/path contract for `data/document-index/index.jsonl` in the plan's resource-intelligence section before approval.

- What exact mechanism turns a scheduled run into `publication_mode` so that clean-worktree, locking, and exit code `2` actually apply?
- What is the authoritative rule for deriving a wiki page's normalized domain from `knowledge/wikis/*/wiki/**/*.md`?
