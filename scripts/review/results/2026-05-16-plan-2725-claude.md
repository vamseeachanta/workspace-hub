## Findings

1. **§Resource Intel line 15 — SHARED_SOUL.md line count is materially wrong.** Plan asserts "(66 lines after #2724 commit `4676f6d6b`)". `git show 4676f6d6b:config/agents/SHARED_SOUL.md | wc -l` returns **114**, and HEAD is also 114. The plan is off by 48 lines (73% error). This is the headline retrieval claim of the Resource Intel section; if it's wrong, every line-count-derived statement in the plan ("respects 20-line harness limit", "Claude: 181 lines... 8% of 2KB budget") needs re-verification.

2. **§Resource Intel lines 20-21 — CLAUDE.md and GEMINI.md line counts off by one.** Plan claims "CLAUDE.md (top-level, 11 lines)" and "GEMINI.md (top-level, 6 lines)". Actual: 12 and 7 respectively. Trivial on its own, but reinforces that none of the cited line counts were freshly verified before writing the plan.

3. **§Risk table line 272 — context-budget math is off by an order of magnitude.** Plan asserts "adding 181 lines is ~8% of typical 2KB budget allocation". The runtime file is **18,784 bytes** (~18 KB) per `stat`, not 8% of 2 KB. The workspace CLAUDE.md (loaded in this very session) states the project budget is "Project 8KB" — 18 KB would consume 235% of that slot, not 8%. The mitigation ("Acceptable per CONTROL_PLANE_CONTRACT.md scope") cites the contract but `docs/standards/CONTROL_PLANE_CONTRACT.md` (read in full) does **not discuss byte budgets** — the citation is non-substantive. This is the central scalability risk and the plan misreports it.

4. **§Pseudocode line 257 — final commit pathspec includes a forbidden marker file.** Plan lists `.planning/plan-approved/2725.md` in the final commit. Memory `feedback_dispatch_local_marker_rationalization` records: *"dispatch lanes can write `.planning/plan-approved/<n>.md` rationalizing user instruction; forbid markers AND label"*. The marker file is forbidden by rule. The prior #2724 commit (`4676f6d6b`) did create `.planning/plan-approved/2724.md`, so the rule is being violated in practice — but the new plan should either (a) drop the marker file from the pathspec, or (b) explicitly call out a request to revisit the rule. Currently it silently continues the violation.

5. **§Pseudocode line 220-223 — push happens BEFORE the empirical test.** Pseudocode for Phase 1: `edit → commit → push → test (manual)`. If the `@file` import fails the empirical test, a broken CLAUDE.md has already shipped to remote and (per `feedback_autosync_silent_pusher`) auto-sync will propagate it to other workstations. Sequencing should be: edit → commit (local) → test (manual, fresh session) → push only on PASS. The fallback branch (line 226-230) doesn't help — by the time it runs, broken state is on `origin/main`.

6. **§TDD test step 3 — the "ask Claude" verification is unreliable.** Line 149: *"In the new session, ask: 'Does your system prompt contain Promote generalizable review findings?'"*. Asking a Claude model to introspect on its own system prompt is hallucination-prone — the model can confidently say "yes" when the string is absent, especially with priming. The reproduction section (lines 58-75) used the correct method (capture the verbatim `<claudeMd>` system reminder); the test should do the same: ask the new session to dump or quote the relevant system-reminder block, not yes/no its presence. Per `feedback_mock_vs_live_invocation_divergence`, indirect verification is unsafe.

7. **§Gaps line 52 — claimed grep was deferred to implementation time.** Plan asserts "No existing `@file` import precedent in workspace-hub (grep across CLAUDE.md, GEMINI.md, .claude/rules/, .claude/skills/ at impl time → empty)". The grep is a 5-second operation that the planning author chose to defer. Either it was verified (then say "verified 2026-05-17 SHA <x>") or it wasn't (then mark as unverified). Asserting an empty grep result with deferred verification reads as confirmation it was checked when it wasn't.

8. **§Phase 2 is unbounded research with a 20-30 min estimate.** Line 98-102 + line 302: "Phase 2: ~20-30 min (research + 1 of 3 branches)". Phase 2 names no specific docs URL, no specific Gemini CLI version, no concrete tests for branches 2a/2b/2c. Gemini CLI bundle-loading semantics are not documented in this repo and external docs change. Either pre-identify the source-of-truth URL in the plan, OR carve Gemini out as a separate issue with research-first as the deliverable (per Open Question #2 the planner already flags this).

9. **§Approach C — symlink fallback has unaddressed cross-platform risk.** `.claude/rules/SOUL.runtime.md` as a git-tracked symlink works on Linux/macOS but breaks on Windows checkouts (where git either creates a text file containing the link target, or requires `core.symlinks=true`). The plan operates on a primarily-Linux workspace, but the `~/.claude/CLAUDE.md` global instructions explicitly distinguish Linux vs Windows machine layouts — implying Windows is in scope. The plan does not address what happens on Windows for Approach C. Even on Linux, `bootstrap-machine.sh` integration is hand-waved ("add symlink-creation step if fallback chosen").

10. **§Acceptance Criteria lines 207-208 — out-of-band verification with no recording protocol.** "Empirical Claude session test" and "Empirical Gemini session test" cannot run in CI (the plan acknowledges this at line 152). But the acceptance criteria don't define: who runs the test, where the evidence is stored (screenshot? transcript link? committed file?), what counts as PASS, and how a reviewer verifies the box was checked honestly. Without this, the box can be checked based on hand-wave during merge.

11. **§TDD test "Drift-check regression" line 180 — `git stash -- CLAUDE.md` is the deprecated form.** `git stash --help` (read above): the form that accepts pathspec is `git stash push -- <pathspec>`. The bare `git stash -- CLAUDE.md` works as a deprecated alias but the docs say the no-`push` form "cannot take pathspec" in some git versions. Use `git stash push -- CLAUDE.md` for clarity and forward compatibility.

12. **§Acceptance Criteria line 209 — T3 review wave is gated AFTER plan publication.** "T3 adversarial plan review: Claude + Codex + Gemini submit verdicts to `scripts/review/results/2026-05-16-plan-2725-{claude,codex,gemini}.md`". The plan's own header (line 3) says *"Status: draft → plan-review after T3 adversarial review wave completes"*. This review IS that wave (or one of three). The criterion can't be self-referentially "this review approves itself" — the criterion should require all 3 reviews' verdicts logged AND r3-absorb evidence, before the plan-approved label is applied.
