## Findings

### F1 — MAJOR — Pseudocode contradicts ModularModelGenerator's actual API
- **Location:** plan lines 144 (TDD pseudocode `native_yaml = ModularModelGenerator(spec_in).generate(tmp_path)`).
- **Defect:** `ModularModelGenerator.__init__` signature in `digitalmodel/src/digitalmodel/solvers/orcaflex/modular_generator/__init__.py:69` accepts a `spec_file: Path`, NOT a `ProjectInputSpec`. To pass an in-memory spec object you must use `ModularModelGenerator.from_spec(spec_in)` (defined at line 73-86). Additionally, `generate(output_dir)` returns `None` — it does not return a YAML payload — and emits a multi-file modular structure: `output_dir/includes/<file>.yml` + `output_dir/master.yml` + `output_dir/inputs/parameters.yml` (init.py:140-179). It is NOT a single "native_yaml" file.
- **Evidence:** read `digitalmodel/src/digitalmodel/solvers/orcaflex/modular_generator/__init__.py:66-179`.
- **Why it matters:** the entire TDD pseudocode and Equivalence-Criteria section assume a single-file generated artifact; reality is a directory of include files. The plan never declares which artifact (`master.yml`? all includes? a re-monolithed single?) the new `OrcaFlexInputParser.parse()` consumes. Implementation will discover this on day 1 and the contract will mutate post-approval.
- **Recommended fix:** rewrite pseudocode to either (a) generate then re-monolith via `format_converter/modular_to_single.py` then reverse-parse, or (b) add a `parse_directory(master_yml_path)` API that walks the `!include` chain, and update Equivalence Criteria accordingly. Either way, name the entry-point artifact explicitly.

### F2 — MAJOR — Schema-version pinning rests on an unverified key (`OrcaFlexVersion`)
- **Location:** plan line 121 (`SCHEMA_VERSION_PINNED = "..."  # from a known-good OrcaFlex YAML header`), line 190 (`test_reverse_parser_raises_on_unknown_schema_version`), line 234 acceptance criterion, line 268 risk.
- **Defect:** the plan never cites a concrete header key it intends to pin. I grep'd the entire `digitalmodel/docs/domains/orcaflex/` tree for `OrcaFlexVersion` (the symbol the plan implicitly invokes) and found zero matches. The canonical `spec.yml` fixtures begin with a `metadata:` block (PLET-to-PLEM line 1: `metadata:\n  name: plet_to_plem ...`) — there is no `OrcaFlexVersion` in canonical specs. The native OrcaFlex YAML *export* surface does carry such a header, but those binary-derived exports are explicitly out of scope (#1652 / licensed boundary). What does the parser pin against, if the only artifacts in scope are forward-generated by `ModularModelGenerator` from spec.yml — and those do not preserve any upstream OrcaFlex version because they're synthesized in-Python?
- **Evidence:** grep returned empty in `digitalmodel/docs/domains/orcaflex/`; spec.yml fixtures use `metadata:` only.
- **Why it matters:** the schema-pinning test is a pre-emptive defense to "what if OrcaFlex format changes upstream?" but the in-scope generation chain is internal Python — there is no upstream-OrcaFlex artifact in this issue's surface to drift. If the test merely asserts a key the plan itself emits, it's testing nothing. This conflates two distinct schema-drift sources (canonical spec.yml schema vs OrcaFlex native YAML schema) and the plan owes a clarification.
- **Recommended fix:** explicitly distinguish (a) canonical-spec schema version (already pinned by `ProjectInputSpec` Pydantic) from (b) native-YAML target-format version (only meaningful if reverse-parser also handles real exports — which it shouldn't, per scope). Drop or scope the schema-pinning test to one of the two; pick.

### F3 — MAJOR — Tautology risk: forward + reverse both written by same authors against same fixtures
- **Location:** risk acknowledged at plan lines 270-271 ("Selected fixtures may already happen to round-trip due to PR #528 forward generator covering only fields present in the spec. The proof is fixture-bound."). Mitigation gestured at via `test_reverse_parser_distinguishes_ignored_default_from_divergence` (line 191) and the open question on a stronger negative test.
- **Defect:** this is THE core defect for any round-trip equivalence claim and the plan only weakly mitigates it. If `ModularModelGenerator` only emits the fields the canonical spec carries, and `OrcaFlexInputParser` only reads what `ModularModelGenerator` wrote, an empty diff is guaranteed by construction — the round-trip proves serialization/deserialization symmetry, not OrcaFlex semantic correctness. Claiming "semantic equivalence" from such a closed loop is the precise failure mode that #520's "best-effort + actionable_gaps" classification was designed to prevent. Plan line 257 dismisses single_to_spec.py as "best-effort" but the new parser, operating on the same internally-generated native YAML, does not actually escape the same closure.
- **Evidence:** `single_to_spec.py:77-89` returns `actionable_gaps` because *real* OrcaFlex single YAMLs contain fields the canonical spec doesn't model. The new parser operating only on `ModularModelGenerator`-produced output never sees those fields, so it gets a free empty-diff.
- **Recommended fix:** add MANDATORY (not optional) negative-test surface: feed the new parser a real OrcaFlex `single.yml` (e.g. one of the sample inputs in `digitalmodel/docs/domains/orcaflex/`) and assert it produces a non-empty `unmapped_native_keys` set. This proves the parser distinguishes "wrote it ourselves and read it back" from "actually parses arbitrary OrcaFlex native YAML." Add explicit AC: at least one fixture in the test suite must be an OrcaFlex-export-style single.yml NOT generated by ModularModelGenerator.

### F6 — MINOR — IGNORED_NATIVE_KEYS registry has no review gate beyond "non-empty reason"
- **Location:** plan lines 151-156 (registry sketch), line 195 (`test_ignored_fields_registry_each_entry_has_justification` — only checks `reason` field non-empty), line 233 acceptance criterion.
- **Defect:** "non-empty reason field" is satisfied by a developer typing `"because"` or `"see ticket"`. Plan's adversarial-review section line 256 claims the registry gate is robust, but the only mechanical test is character-count > 0. There is no taxonomy enforcement (e.g. must classify into {timestamp, comment, format-only, precision-only}) and no PR-time human-review requirement. - **Evidence:** plan acceptance criterion line 233 says "at least one documented entry per category (timestamp/comment/format-only/precision-only)" — but the CATEGORY field is not declared in the schema sketch at lines 151-156 and there's no test asserting category presence.
- **Recommended fix:** make the registry entry a `dataclass(frozen=True)` with `key: str`, `category: Enum[Timestamp|Comment|FormatOnly|PrecisionOnly|Telemetry]`, `reason: str` with `len(reason) >= 30`, plus a `last_reviewed_iso: date` and `reviewer: str`. Add `test_ignored_fields_registry_categories_valid` and a CODEOWNERS rule on `reverse_parser_ignored_fields.py` so additions force human review.

### F7 — MINOR — Floating-point and YAML-specific risks named only partially
- **Location:** plan line 205 (numeric tolerance `rtol=1e-9, atol=0`); line 209 (units); plan does NOT name BOM/encoding, key-ordering, or list-vs-tuple coercion.
- **Defect (per checklist #9):**
  - Line 205 says floats compared at `rtol=1e-9, atol=0` — but `atol=0` means strictly proportional comparison, which fails for any field with a true value of exactly 0.0 (a zero-valued tilt, current, offset, etc.). Many environment fields legitimately default to 0.
  - YAML key-ordering is mentioned obliquely (line 209: "canonical unit on emit equals canonical unit on reverse-parse") but never as a separate concern. `ModularModelGenerator` writes with `sort_keys=False` (init.py:169), so order matters only if a downstream test diffs by string. The plan's "object identity preserved" criterion at line 204 is unaffected, fine.
  - BOM (UTF-8 BOM in OrcaFlex Windows-exported YAML) is named in adversarial-defenses line 260 but not in the actual TDD test list (line 194 covers multi-doc YAML, not BOM). This is exactly a CHECKLIST-9 item the plan only half-defends.
  - Newline normalization (CRLF vs LF) is unaddressed.
- **Recommended fix:** raise `atol` to a small absolute floor (e.g., `1e-12`) for safety on zero values; add explicit `test_reverse_parser_handles_utf8_bom` and `test_reverse_parser_handles_crlf_yaml` to the TDD list.
