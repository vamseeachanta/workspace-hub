This is not just citation hygiene: `#2731` already requires `docs/architecture/data-location-contract.md`, `docs/reports/YYYY-MM-DD-data-location-inventory.md`, and `config/data-location-contract.yml`; `#2732` requires `docs/architecture/repo-ecosystem-mount-map.md`, `docs/architecture/repo-ecosystem-folder-taxonomy.md`, and `config/repo_ecosystem_path_contract.yml`. The plan’s `## Files to Change` creates `docs/architecture/source-layer-classification-matrix.md` and `docs/architecture/data-execution-report-layer-contract.md` without defining precedence or avoiding duplicate canonical contracts. That can create competing architecture sources.

2. Plan `## Risks and Open Questions` says “Mounted project/source paths can contain sensitive client names; inventories must support redaction and source IDs,” but `## TDD / Validation List` has no redaction test and no structural check blocking exact client/project child names in `docs/architecture/source-layer-classification-matrix.md`. This conflicts with `#2732`’s explicit public-doc rule: exact client/project child names under private roots are forbidden unless approved. `test_legal_scan_passes` is not enough because a deny-list scan cannot prove path-class redaction unless every sensitive name is already in `.legal-deny-list.yaml`.

3. Plan `## Acceptance Criteria` requires child plans for `#2727`, `#2728`, and `#2729` to be “source-curated and reviewed,” but `## Files to Change` also says this parent implementation will update all three child plan files. Those child plans are themselves `status:plan-review` and not approved. Updating unapproved child plans as part of implementing `#2726` blurs the gate order: child plans should either be upstream dependencies that must be approved/revised before this parent implementation, or downstream artifacts only referenced by the parent contract. The plan does not specify which, so implementation can mutate review-gated plans under a different approved issue.

4. If the matrix fixture contains source IDs, path classes, or posture data, excluding fixtures from the legal/security scan leaves a path for sensitive strings to enter tracked test data while the acceptance criterion “Legal/security scan passes for all created docs” still appears satisfied.
