## Findings
1. Plan Resource Intelligence is insufficient for the issue labels. Issue `#2726` is labeled `cat:data-pipeline`, `cat:document-intelligence`, `domain:knowledge`, and `domain:reporting`; `docs/plans/README.md` requires Data Pipeline sources such as `registry.yaml` and `resource-intelligence-maturity.yaml`, and Knowledge/Intelligence sources such as the `#2205` operating model, sibling contracts, and accessibility map. The plan’s “Documents consulted” only lists `#2726`, `docs/DATA_RESIDENCE_POLICY.md`, `data/document-index/mounted-source-registry.yaml`, `docs/content-pipeline/README.md`, and `docs/WORKSPACE_HUB_CAPABILITIES_SUMMARY.md`, omitting `docs/document-intelligence/README.md`, `docs/document-intelligence/llm-wiki-resource-doc-intelligence-operating-model.md`, `docs/document-intelligence/durable-vs-transient-knowledge-boundary.md`, `data/document-index/registry.yaml`, and `data/document-index/resource-intelligence-maturity.yaml`.

2. Plan proposes new layer level names without binding them to the existing normative intelligence-layer model. Plan “Gaps identified” says “No approved level taxonomy yet for data L1 raw → L2 raw-llm-wiki/staging → L3 public `llm-wiki`/chatbot knowledge,” but `docs/document-intelligence/llm-wiki-resource-doc-intelligence-operating-model.md` already defines a six-layer model where L1 is Source documents, L2 is Registry/provenance, L3 is Durable knowledge, L5 is Execution state, and explicitly forbids “between,” “adjacent,” or hybrid layer inventions. The plan only flags a naming-conflict risk against `docs/DATA_RESIDENCE_POLICY.md`, not against the stronger normative `#2205` model.

3. “All tier-1 repo data” is not empirically defined and conflicts with repo inventory sources. Plan Acceptance Criteria says “Initial known source classes include ... all tier-1 repo data,” and the source-class table lists `workspace-hub`, `digitalmodel`, `assetutilities`, `worldenergydata`, `llm-wiki`, `assethold`, `aceengineer-website`, and `aceengineer-strategy` as tier-1 repo data. `docs/WORKSPACE_HUB_CAPABILITIES_SUMMARY.md` lists Tier-1 repositories as `digitalmodel`, `assetutilities`, `assethold`, and `worldenergydata`; `docs/BUSINESS_BRAIN.md` lists Tier-1 as `workspace-hub`, `digitalmodel`, `assetutilities`, and `aceengineer-website`. The plan does not reconcile the conflicting inventories or define the authoritative tier-1 set before requiring coverage of “all” tier-1 data.

4. Parent plan has validation tests but no concrete test artifact path. Plan “TDD / Validation List” names five tests, but “Artifact Map” has no Tests artifact and “Files to Change” has no test file. `docs/plans/_template-issue-plan.md` requires the Artifact Map to include Tests, and `docs/plans/README.md` requires TDD before implementation. This makes the validation work non-executable for the `#2726` parent scope.

5. Evidence section duplicates `#2726` and omits child issue status evidence despite child plans being acceptance-critical. Plan “Evidence (embedded verification)” lists `#2726` twice; Acceptance Criteria requires child plans for `#2727`, `#2728`, and `#2729` to be source-curated and reviewed. The plan does not embed status evidence for those child issues, even though their existence/state is correctness-critical to the parent plan.

6. Legal scan acceptance is under-specified for multi-repo/public-private publication risk. Plan “TDD / Validation List” only says `test_legal_scan_passes` expects “plan/docs paths” to pass, while `docs/BUSINESS_BRAIN.md` requires legal/IP checks before raw data, client-derived context, standards extracts, document intelligence, or code-porting insights become public-facing `llm-wiki` pages, GTM artifacts, GitHub issues, PRs, or demo reports. `scripts/legal/legal-sanity-scan.sh` supports `--repo`, `--all`, and `--diff-only`, but the plan does not specify which scan mode applies to architecture docs that classify client/project roots and public chatbot/report eligibility.

7. Plan depends on “user-added sources” without a required artifact or acceptance criterion for capturing them. Plan pseudocode says “inventory known source classes from registry, repo docs, issues, and user-added sources,” and the status says “source-curation pass pending,” but the Artifact Map has no source-curation artifact and Acceptance Criteria do not require a curated source list or diff from the user pass. This leaves the plan-review gate able to pass before the declared pending source input is captured.
