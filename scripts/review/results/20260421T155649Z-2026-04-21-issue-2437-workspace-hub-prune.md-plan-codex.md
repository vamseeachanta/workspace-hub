### Verdict: MAJOR

### Summary
The prune itself is reasonable, but the plan is not ready for approval because its verification strategy is weaker than the repo’s stated gate policy and several plan claims conflict with the attested evidence or overstate the expected outcome. Tightening the acceptance criteria and separating guaranteed outcomes from follow-on work would make this plan feasible and reviewable.

### Issues Found
- [P1] Critical: The test strategy is not TDD-executable as written. The plan’s primary proof is 'next push to main' and 'workflow completes', which defers validation until after merge instead of defining pre-change failing checks and post-change local/branch checks. For this repo, that is too weak for a plan that claims mandatory TDD and gated implementation.
- [P2] Important: The plan presents review artifacts as concrete paths in the header and Artifact Map, but the attested evidence shows all three review result files are currently missing. Those should be described as outputs to be generated during review, not existing artifacts.
- [P2] Important: The deliverable says this work will 'restore the workflow to green', but the plan’s own test table says remaining steps may still fail on their own merits. That overstates scope and success criteria; this plan only removes known missing-script failures.
- [P2] Important: Acceptance requires filing follow-on issues for template and test-surface cleanup, but the plan does not define those issue IDs, owners, or whether plan approval is blocked on creating them. That mixes this prune with additional scope and makes closure ambiguous.
- [P3] Minor: The embedded evidence block claims issue #2437 carries `status:plan-approved` while the plan itself is still `draft` and the adversarial review section is pending. Even if the label claim is accurate, the plan should explain that state clearly because it currently reads as a governance inconsistency.

### Suggestions
- Replace the CI acceptance with explicit before/after checks that can run pre-merge, such as asserting the referenced paths are absent from `.github/workflows/baseline-check.yml` and `.pre-commit-config.yaml`, plus running the remaining local validation surface that actually exists.
- Change the review artifact references to 'planned outputs' until the files exist, or remove them from the artifact map until adversarial reviews are written.
- Narrow the deliverable to 'eliminate missing-script failures caused by WRK-era references' instead of promising a fully green baseline workflow.
- Move the two follow-on issue creations into implementation notes or add concrete child issue numbers before approval so this plan has a clean, self-contained done condition.
- Clarify the gate state around `status:plan-approved` versus `draft`/pending adversarial review so the plan matches the repo’s documented approval flow.

### Questions for Author
- What exact pre-merge checks will be used to satisfy the repo’s TDD/gated workflow for this config-only prune, given that 'next push to main' is currently the main proof?
- Are the follow-on issue filings required to complete #2437, or are they advisory outputs that should not block closing this prune?
- Is the intent to remove only missing-script references, or to make the entire baseline workflow green? The plan currently says both.
