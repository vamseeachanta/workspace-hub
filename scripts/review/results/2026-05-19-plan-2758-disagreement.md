### claude

- **`config/workstations/registry.yaml` already exists as the canonical machines registry — plan proposes a parallel `config/workstations/repo-placement.yaml` in the same directory without acknowledging the prior art.** `registry.yaml:1-4` reads: *"registry.yaml — Single source of truth for all workstations. Read by: scripts/cron/setup-cron.sh, scripts/operations/workstation-status.sh. HARD RULE: all machine identity/capability data lives here."* The existing file already encodes 6 machines (`dev-primary`/ace-linux-1, `dev-secondary`/ace-linux-2, `licensed-win-1`, `licensed-win-2`, `macbook-portable`, `gali-linux-compute-1`) with `os`, `role`, `workspace_root`, `ssh`, `tailscale_ip`, `capabilities`, `storage`, `repos`, `telegram_hermes`, `data_access_profile`, `readiness_freshness_thresholds`. The plan's §Resource Intelligence Summary (lines 13-23) cites `scripts/readiness/harness-config.yaml` and `config/agents/hermes/config.yaml.template` but never names `config/workstations/registry.yaml`. The plan's own Risk row "Registry becomes another stale authority source" (line 251) is triggered by the proposal itself. **This is the central blocker.**
- **A pre-existing authority-map artifact at `.claude/skills/workspace-hub/repo-structure/references/agent-runtime-authority-map.md` already defines authority classes for the same domain — plan ignores it.** That file (untracked but present, 48 lines, dated `May 19 10:43` — same day as this plan) defines 5 authority classes (`Canonical source`, `Generated runtime`, `Local runtime/symlink`, `Bridge output`, `Cache/snapshot/state`) with agent behavior rules. The plan proposes `docs/architecture/agent-runtime-folder-authority.md` with 9 classes (lines 75-85), no mention of the existing skill reference or whether the skill is being replaced/extended/duplicated. Two parallel authority taxonomies with different cardinalities and naming will harm, not reduce, agent/human confusion — directly contradicting issue #2758's purpose.
- **Schema's machine-ID scheme is incompatible with the existing canonical registry.** Plan example (lines 93-111) keys machines by hostname: `machines:\n  ace-linux-1:\n    os_family: linux\n    ...`. Existing `config/workstations/registry.yaml` keys machines by role (`dev-primary:`, `dev-secondary:`) with `hostname:` as a *field*. The plan's Open Question #4 asks "should the registry live under `config/workstations/` as proposed, or should it be folded into `scripts/readiness/harness-config.yaml`" — but the real question (fold into the *existing* `config/workstations/registry.yaml`) is not asked, and the machine-ID scheme mismatch is not surfaced. The plan would silently fork machine naming.
- **`tier1_repos`/`skill external_dirs`/`registry.yaml.repos` divergence is observed by plan but not reconciled.** `scripts/readiness/harness-config.yaml:22-26` declares 4 tier-1 repos (`assetutilities, digitalmodel, worldenergydata, assethold`). `config/agents/hermes/config.yaml.template:40-45` declares 6 external_dirs (adds `workspace-hub, CAD-DEVELOPMENTS, achantas-data`, drops `assethold`). `config/workstations/registry.yaml` line 27-33 declares 6 repos for dev-primary (`worldenergydata, digitalmodel, assetutilities, assethold, workspace-hub, OGManufacturing`). The plan cites the first two surfaces in §Sources but the proposed registry will become a *fourth* repo list rather than reconciling them. No "supersedes" or "deprecates" statement appears anywhere.
- **Top-level `workspace-hub/AGENTS.md` — the canonical workflow contract per `SHARED_SOUL.md:6` — is absent from the authority taxonomy.** AGENTS.md exists at repo root and `SHARED_SOUL.md` line 6 calls it the *"Canonical workflow contract."* The plan's class table (lines 75-85) lists `canonical-repo-source` with examples `SHARED_SOUL.md`, provider deltas, scripts, docs — but never names AGENTS.md or its provider-specific siblings (CLAUDE.md, GEMINI.md, the codex `AGENTS.runtime.md` symlink target). A folder-authority contract that omits the load-bearing workflow file is incomplete.
- **§Scope "read-only validation" conflicts with §Pseudocode and §Tests that require content inspection of user-home secret files.** §Scope line 59: *"Add validation that is read-only except for test fixtures and documented outputs."* But `check_authority_rules` (lines 174-188) verifies "generated header" and "build script reference" — content reads. Tests `test_registry_rejects_secret_like_values`, `test_local_runtime_symlink_target_matches_machine_root`, and `test_report_redacts_home_auth_and_token_paths` (lines 220, 224, 230) imply reading `~/.hermes/.env`, `~/.codex/auth.json`, or scanning for token-like content. The plan must distinguish "doesn't mutate filesystem" from "doesn't read secret files" and explicitly forbid the latter, per `feedback_skill_content_scanner_docs_tension` in your memory (skill scanners trip on `~/.hermes/.env`, `curl ${TOKEN}`).
- **Cited line ranges paper over precision.** `scripts/agents/build-soul-runtime.sh:1-61` is the entire 61-line file (`wc -l`). `install-soul-runtime.sh:1-87` is the entire 87-line file. `emit-machine-status.sh:1-26` is the entire 26-line file. Citing `1-N` adds no precision over citing the file. Replace with specific function/section line ranges or drop the range.
- **Schema example shows `users.vamsee.provider_runtime: enabled` but neither the validator nor the field enumeration mentions `provider_runtime`.** Lines 99-103 introduce a `users:` block with `provider_runtime: enabled` — but the per-repo schema field list (lines 115-124) and the validator pseudocode (lines 174-188) never refer to it. The multi-user prose section (§3, lines 127-134) doesn't wire it to anything either. Dead field, or unspecified semantics.
- **`inspect_current_machine` pseudocode is incoherent with the proposed schema.** Line 163: *"resolve machine entry by explicit flag or hostname aliases"*. But the plan's example registry (lines 93-111) keys machines by hostname-string, not by an alias-resolving structure. The existing `config/workstations/registry.yaml` *does* have `hostname:` + `hostname_aliases:` fields for resolution — another sign the plan should be extending the existing file rather than inventing a new one.
- **Acceptance criterion #11 ("Plan-stage adversarial review will complete before `status:plan-review` is applied") is a workflow precondition, not a falsifiable acceptance criterion.** Line 245. This belongs in §Status / Gate, not in the test/acceptance list. Trims to padding.
- **Plan promises report-only vs enforcement modes but specifies no mode flag.** Risk-mitigation row (line 259): *"First implementation will support report-only mode and enforcement mode separately."* §Files to Change names a single script `scripts/validation/check-agent-runtime-authority.sh`. §Pseudocode `emit_report` mentions "enforcement mode" but no flag or env-var contract. Either spec the flag (`--enforce`/`--report-only` plus exit-code semantics) or remove the promise.
- **`config/machine-baselines/README.md` references `config/agents/machines.yaml`** (per its line 17: *"If `config/agents/machines.yaml` contains `aliases: { <hostname>: <alias> }`, use the alias"*). This is a fourth potential machines-config path adjacent to `config/workstations/registry.yaml`, `scripts/readiness/harness-config.yaml.workstations`, and the proposed `config/workstations/repo-placement.yaml`. The plan must reconcile the alias-resolution surface, or the validator's hostname-alias resolution will diverge from the #2751 baseline emitter's resolution.

### codex

- Plan omits the template-required embedded evidence block. `docs/plans/_template-issue-plan.md` requires an `### Evidence (embedded verification)` section with issue statuses, file existence, line excerpts, gap proofs, and source count. The plan’s `Resource Intelligence Summary` lists assertions, but it does not embed command output, `ls`, `gh issue view`, line excerpts, or gap proofs. This violates the plan retrieval contract and leaves reviewers unable to verify cited paths or “no existing” claims from the plan artifact itself.
- The new registry risks becoming a conflicting authority source because the plan does not resolve existing workstation key mismatches. The plan proposes `config/workstations/repo-placement.yaml` with machines like `ace-linux-1` and `ace-linux-2`, while `scripts/readiness/harness-config.yaml` currently defines `dev-primary`, `dev-secondary`, `licensed-win-1`, and `macbook-portable` under `workstations:`. The plan’s “Risk / issue” row says the registry must not drift from setup scripts, but `Files to Change` only says “Update `scripts/setup/aggregate-machine-status.sh` or companion status docs” conditionally. There is no required alias/mapping/migration rule tying `ace-linux-1` to `dev-primary` or `ace-linux-2` to `dev-secondary`.
- The validator is likely to fail current Hermes config or silently bless the wrong model because the plan does not specify how to handle existing nested tier-1 skill paths. `config/agents/hermes/config.yaml.template` includes `__WS_HUB_PATH__/digitalmodel/.claude/skills`, `__WS_HUB_PATH__/assetutilities/.claude/skills`, and similar paths under the workspace-hub root. The plan’s authority model says sibling tier-1 repos are separate checkouts such as `/mnt/local-analysis/digitalmodel`, and `test_skill_external_dirs_are_classified` expects known sibling repo vs workspace-hub subfolder classification. `Files to Change` does not include `config/agents/hermes/config.yaml.template`, and the plan does not define whether those existing template paths are legacy exceptions, failures, or in-scope fixes.
- The generated-artifact edit rule is under-specified and bypassable. Plan pseudocode says “fail if direct edit is staged without source changes or regenerated outputs,” and the test list only covers “changed `SOUL.runtime.md` and unchanged sources” versus “changed source and matching generated outputs.” A direct edit plus any source change could pass unless the validator actually regenerates artifacts and compares exact output. The plan does not state that `scripts/agents/build-soul-runtime.sh` or `scripts/enforcement/check-soul-runtime-drift.sh` must be invoked as the authority check.
- The plan creates `config/workstations/repo-placement.schema.yaml` but does not define a real schema mechanism. The file extension is YAML, while the pseudocode only says `validate schema_version`; no validation tool is named (`yq`, Python parser, JSON Schema, custom Bash/Python), no CI invocation is specified, and `tests/validation/test_agent_runtime_authority.py` is expected to validate registry parsing without an implementation path. This is a design gap for a correctness-critical artifact.
- The plan overreaches the issue’s requested deliverables by adding a machine × repo × user placement registry and validator without pinning which facts are allowed to be hand-authored. Issue `#2758` asks for an architecture contract and validation/check script; machine placement decisions are explicitly split into `#2754`-`#2757`. The plan’s `Placement matrix model` includes `desired_state`, `canonical_path`, `owner_user`, `allowed_users`, `write_policy`, `data_access`, and `license_access`, which are exactly the decision surfaces in `#2754`-`#2757`. Marking them `decision-pending` mitigates some risk, but the plan still creates the authoritative structure before those issues complete.
- The report/output artifact is not listed as a file to change even though `emit_report(findings, output)` is part of the validator behavior. The plan says reports will render machine summaries, placement matrices, provider runtime matrices, multi-user risks, and follow-up suggestions, but `Artifact Map` has no report path except review artifacts and no acceptance criterion requiring the generated report to be committed, ignored, or local-only. This leaves provenance and cleanup ambiguous.

### gemini

- **Missing source files at HEAD:** Plan §Sources consulted cites `config/agents/SHARED_SOUL.md`, `scripts/agents/build-soul-runtime.sh`, `scripts/agents/install-soul-runtime.sh`, `config/agents/hermes/config.yaml.template`, and `scripts/readiness/harness-config.yaml`. None of these files or directories exist in the current workspace.
- **Bash vs. Python testing mismatch:** Plan §Files to Change proposes creating a Bash script for validation (`scripts/validation/check-agent-runtime-authority.sh`). However, Plan §TDD Test List proposes testing it with Python (`tests/validation/test_agent_runtime_authority.py`) and expects internal state returns (e.g., "Parser returns normalized registry."). A Python unit test cannot assert against internal state or returned objects of a Bash script without complex wrapping or JSON translation, which the plan omits.
- **Missing YAML parser dependency:** Plan §Pseudocode for `load_registry(path)` requires a Bash validator to "read YAML registry". Bash cannot natively parse YAML schemas. The plan fails to define how cross-platform YAML parsing (e.g., via `yq` or Python) will be handled without introducing a new unstated dependency.
- **Validation logic contradicts multi-machine scope:** Plan §Issues That May Arise claims "The validator will compare registry paths against live filesystem observations and existing machine baseline reports". However, Plan §Pseudocode for `inspect_current_machine` only reads live paths for the *current* machine and lacks any logic to ingest or parse the aggregated machine baseline reports from other machines.
- **Open Question contradicts Acceptance Criteria:** Plan §Open Questions for User Approval asks whether the registry should "include only the four current machines... or should it reserve placeholders...". However, Plan §Acceptance Criteria already mandates "The architecture doc will include a per-provider/per-machine table for Hermes, Claude, Codex, and Gemini across ace-linux-1, ace-linux-2, licensed-win-1, and licensed-win-2." The plan simultaneously leaves the machine scope open for approval while statically enforcing it as a hard requirement.
- **Vocabulary collision on "canonical":** The stated issue goal is to "Clarify agent/runtime folder architecture to reduce human and agent confusion". However, Plan §2 Placement matrix uses `canonical_path` to refer to the local filesystem mount path of a checkout, while Plan §1 Authority model defines `canonical-repo-source` as human-authored git-tracked files. Reusing "canonical" for both local mount directories and git-tracked source files actively undermines the goal of reducing vocabulary confusion.
- **Read-only validation vs. Mutating schema:** Plan §Scope asserts validation is "read-only except for test fixtures and documented outputs." However, Plan §2 Placement matrix model defines `last_verified` as a schema field representing a "timestamp emitted by validation, not hand-authored in the plan." If the validator writes this timestamp back into the source-controlled `repo-placement.yaml`, it violates the read-only constraint and will cause a dirty git tree on every run.
