### Verdict: MINOR

### Summary
The plan is well-structured, thoroughly documented, and addresses the core requirements with sound technical choices like file-locking and round-trip YAML parsing. However, it relies heavily on the `llm_wiki.py` CLI being the sole mutator of wiki pages, which risks data drift if manual edits occur.

### Issues Found
- [P2] Important: The design assumes all wiki page modifications flow through `llm_wiki.py`. Manual edits, direct file modifications, or git merges that change a page's `doc_key` without invoking the emitter will cause silent drift between the wiki frontmatter, the side-cache, and the L2 registries.
- [P3] Minor: The plan lacks explicit error handling for cases where the target L2 registry YAML files are already malformed or unreadable when the emitter attempts to load them.

### Suggestions
- Integrate `backfill_wiki_refs.py --reconcile` into the CI pipeline to gate PRs if the materialized L2 registries drift from the actual L3 wiki state.
- Define a clear fallback or alert mechanism if the side-cache (`wiki-refs-cache.jsonl`) becomes corrupted or unparseable, rather than just handling its absence.
- Long-term, consider decoupling the reverse-lookup data into a dedicated, fully generated index file rather than mutating human-authored L2 registries, which would eliminate write contention and YAML round-trip risks entirely.

### Questions for Author
- How will we detect and heal drift if a user manually edits a wiki page's frontmatter and commits it via git, bypassing the CLI emitter?
- If the first registry update succeeds but the second fails, the plan suggests logging a warning. Should the CLI exit with a non-zero status in this scenario to explicitly alert the user or CI environment?
- Does the `wiki-refs-cache.jsonl` handle pruning for deleted pages, or will it grow indefinitely with stale paths?
