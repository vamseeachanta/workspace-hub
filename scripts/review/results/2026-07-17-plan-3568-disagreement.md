### claude-r1

- **[BLOCKER] The contract's applicability layer binds to a capability authority that does not exist, inside a roster file that competes with a declared hard rule.** Plan §Resource Intel calls `scripts/readiness/harness-config.yaml` "the live roster authority"; AC-9 enumerates roster coverage from it; pseudocode `grade_interaction_evidence` requires "explicit roster capability; never infer it from hostname"; tests `test_roster_semantics_are_explicit_and_fail_closed` and `test_applicability_is_not_inferred_from_hostname` require an "explicit authority". But (a) no GUI/headless capability field exists in `harness-config.yaml` — `gpu-claw` carries `role: linux-execution`, identical to GUI-capable `dev-secondary`, so today's roster cannot distinguish an "explicitly declared headless role" from a GUI machine; (b) `config/workstations/registry.yaml:3` declares "HARD RULE: all machine identity/capability data lives here" and already carries a distinct per-machine capability taxonomy (`role: gpu-executor`, `harness_profile.roles: [sim-worker]`). The plan never reconciles the two authorities, never names the new field/enum, and assigns its creation to no one: §Files to Change contains no roster mutation, the parent forswears modifying "equality collectors/renderers", and §Risks only says "#3567 will require an explicit roster capability" while §Documents-consulted scopes #3567 as not mutating behavior — leaving the load-bearing capability declaration unowned. The contract YAML (the parent's core deliverable) cannot specify fail-closed applicability against an authority whose surface and shape are undefined.
- **The freshness gap and AC-13 mischaracterize the publish mechanism as a "fingerprint".** §Gaps: "No interaction-evidence freshness policy reconciles evidence timestamps with the equality report fingerprint. Excluding the observation time from all hashing could prevent refreshed HITL evidence from publishing." AC-13: "`observed_at` will affect the persisted interaction-evidence/report fingerprint so refreshed HITL evidence publishes." The actual equality publish gate is `scripts/readiness/publish-equality.sh` lines 60-61/104: a lexical `generated_at` newer-than comparison ("nothing newer than $REMOTE/$BRANCH; no commit needed") — no content hashing exists in that path. The only "fingerprint" scripts (`scripts/monitoring/equivalence-fingerprint.sh`, #3059) are a separate drift-sentinel surface the plan never cites. The requirement's substance (a refresh must publish) is sound, but the contract will encode a constraint against a mechanism that doesn't exist as described; #3567 could design to the wrong gate. Cite `publish-equality.sh:60-104` and pin the requirement to `generated_at` semantics, or explicitly specify the new fingerprint the contract expects #3567 to introduce.
- **Template header nonconformance.** The plan header omits the `> **Project:**` line required by `docs/plans/_template-issue-plan.md` line 8 (the field is optional to *populate*, but the header line is part of the template and Rule E consumers key off it). All other header fields and `##` sections conform.
- **The Codex CR→LF normalization claim is an unverified upstream assertion baked into the paste contract.** §Documents-consulted: "Current Codex normalizes CR to LF before composer insertion" — cited to openai/codex#17103 "and source". The issue exists and matches the paste-event/key-event split topic, but its title/body do not establish the normalization behavior, and no pinned Codex commit or version-specific source citation is given. `validate_paste_fixture` then hard-codes "normalize CR and CRLF to LF exactly as the Codex composer contract specifies". `canonicalization_version` in the fixture schema partially mitigates, but the plan should require #3566 to empirically re-verify normalization on the pinned codex-cli (0.144.5) before the contract's canonical-equality policy is treated as fact.
- **Pre-existing review-artifact residue contradicts the PENDING table and risks being committed as evidence.** `scripts/review/results/2026-07-17-plan-3568-claude.md` and `-codex.md` already exist as 0-byte files with `.err` companions (failed dispatches: untrusted-workspace for Claude; Codex run died), and `-gemini.md` is an UNAVAILABLE stub (no non-interactive auth). The plan's §Adversarial Review Summary says PENDING ×3, which is consistent with intent but not with the tree. Zero-byte files must never be committed as review evidence; the Gemini outage means the T3 review degrades to T2 per the cross-review routing rules and that depth reduction must be disclosed at the HITL gate (the plan promises this generically but does not record the already-observed Gemini auth failure).

Private-path exclusion for YAML/HTML rests solely on `legal-sanity-scan.sh --diff-only` and the contract test's own denylist; the AC should state that division of labor rather than implying scanner coverage.

### claude-r2

- **`home-win` reconciliation disposition is unspecified, leaving a projection-only machine with no defined verdict.** Plan §Resource Intel (lines 40-43) frames the drift one-directionally ("omits `gali-linux-compute-1`… fail-closed gap"), and AC-9 protects only `macbook-portable` and `gali-linux-compute-1` from disappearing. The contract must state the disposition: either #3567 adds `home-win` to the registry with explicit status, or removes it from the projection, and any projection-only machine must fail reconciliation loudly rather than vanish.
- **AC-16's evidence requirement cannot be produced by the named tool.** AC-16 requires "the scan's non-empty target list plus exit 0 will be recorded", but `scripts/legal/legal-sanity-scan.sh` never prints its target list (`file_args` at lines 184-215 is consumed internally, no listing output) and its usage (lines 86-103) accepts no positional path arguments for a path-scoped scan. The operator would have to record `git diff --name-only HEAD` separately as a proxy; the plan should say that explicitly or the requirement is unfalsifiable as written.
- **`test_legal_scan_passes` is vacuous after commit.** TDD row `test_legal_scan_passes` claims to verify "no restricted identifier… enters the artifacts", but `--diff-only` derives targets from `git diff --name-only HEAD` (`legal-sanity-scan.sh:187-188`) and returns 0 on an empty list — so once the artifacts are committed, the pytest passes forever without scanning anything. As a durable regression test it proves nothing; it only has teeth at pre-commit time. Specify it as a pre-commit/CI-diff gate check or scope it to assert scanner behavior on a synthetic fixture instead.
- **`> **Project:** workspace-hub` misuses the template field's defined semantics.** Template line 8 defines `Project:` as "populate when plan scopes to a single project under the client; consumed by check-wiki-sibling-frontmatter.py Rule E", and `.claude/rules/wiki-sibling-routing.md` Rule D says projects exist only inside client wikis. With `Client: N/A`, the value `workspace-hub` is not a client project; the field should be blank/N/A. (Claude r1 finding 3 asked for the header *line*; the populated value introduces a new, smaller inconsistency.)
- **The r2 Gemini expectation is contradicted by current environment state.** The review table (r2 row) says Gemini is "expected fresh auth preflight", but the on-disk r2 slot `scripts/review/results/2026-07-17-plan-3568-gemini.md` already contains an UNAVAILABLE failure ("no non-interactive gemini auth configured") identical in size to r1's. ### codex-r1

- The plan assigns capability authority to the wrong file. Plan lines 34–37, 50, 238, and 328 call `scripts/readiness/harness-config.yaml` authoritative for roster roles and require an explicit GUI/headless capability. `config/workstations/registry.yaml:1-4` instead declares itself the single source of truth for all machine identity and capability data, reinforced by `tests/readiness/test_registry_sso_completeness.py:30-35`. Neither registry currently contains a GUI/headless capability, and Plan §Files to Change provides no child obligation to add it to the authoritative registry. The proposed grading therefore has no valid source for applicability.
- Plan §Gaps lines 110–111 requires semantic shortcut parity to remain separate from privacy parity, but §Pseudocode lines 241–244 returns one `EXPECTED-DIVERGENCE` verdict whenever a passing outcome has an OS/privacy difference. Acceptance Criteria lines 340–342 repeats that collapse. A dictation outcome cannot be represented as semantic `EQUAL` with a separate privacy-boundary annotation/divergence, contradicting the stated contract.
- The machine-wide headless shortcut in §Pseudocode lines 236–244 is not predicate-specific: any explicitly headless machine immediately returns `EXPECTED-DIVERGENCE` for the whole interaction family. That can suppress applicable terminal or remote-input predicates merely because desktop dictation is inapplicable. The contract needs applicability per machine-and-predicate, not a blanket role verdict.
- The supposedly exact contract is undefined. Plan lines 287 and 307 require an exact set of “four initial predicates” without naming them anywhere. Lines 295 and 309 likewise require an exact, complete child DAG without specifying its edge set; line 322 only implies that 3567 consumes interfaces from 3565 and 3566. The issue body for 3567 names the predicates, but the durable contract plan must freeze them and the dependency edges explicitly so tests do not invent their own oracle.
- Epic closeout would fail the repository’s enforced completeness gate. Plan lines 275 and 354–357 provide an HTML report and owner label only. `.github/workflows/completeness-gate.yml:54-61` requires a fenced machine-readable `completeness` JSON record in the issue body, while `scripts/workflow/completeness_gate_check.py:72-114` validates issue binding, class, percentage, label authority, and post-edit freshness. None of those required closeout transactions appears in the plan.
- The privacy validation is denylist-based while the acceptance contract is allowlist-based. Plan line 230 and `test_privacy_denylist_rejects_raw_interaction_content` only reject enumerated field names, but lines 333–336 promise that evidence will serialize *only* bounded allowed types. Renamed fields such as `payload_text` or arbitrary additional properties could pass. The plan needs a closed schema, rejection of unknown fields and nested values, and adversarial alias/value tests.
- The legal gate can pass without scanning the principal new artifacts. Plan lines 299 and 349–350 invoke `legal-sanity-scan.sh --diff-only`, but `scripts/legal/legal-sanity-scan.sh:185-188` derives targets solely from `git diff --name-only HEAD`, which omits untracked files and returns success on an empty list. Live issue 3566 §Desired behavior requires “the exact same clipboard bytes,” while Codex v0.144 intentionally converts CR/CRLF to LF. That is an unresolved scope contradiction, not an implementation detail; either the child issue must be amended by the owner or the plan must test route equivalence and normalization loss separately.
- Plan lines 162–177 and 386–388 say a configuration collision was reproduced, but the recorded bindings are `<Super>h` for minimize and `<Super><Shift>v` for dictation—distinct chords. The evidence proves that the *proposed migration* to `<Super>h` would collide; it does not reproduce a current collision.
