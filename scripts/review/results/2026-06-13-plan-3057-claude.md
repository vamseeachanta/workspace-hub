## Findings

1. **Plan refuses to commit to a single design at plan time; root-cause divergence can silently recur.** Files to Change line 303 says of `setup-cron.sh`: "Use shared rendering semantics **or** keep current behavior under parity tests." Gaps line 44 admits "No shared rendering helper exists." The issue's stated problem (Resource Intel line 18) is precisely that "the legacy installer and transactional installer currently diverge." The plan's preferred path adds a *second* Python expansion implementation in `cron_apply.py` alongside the existing inline-Python expander in `setup-cron.sh:135-140`, and the two TDD tests (`test_setup_cron_dry_run_expands_workspace_hub_and_log`, `test_run_cutover_renders_applied_new_text_...`) exercise each path **in isolation**. No test feeds the same catalog task through both paths and asserts byte-identical output. Divergence — the exact defect being fixed — can reappear undetected. **Blocker resolution:** either extract one shared renderer consumed by both, or add an explicit cross-parity test asserting `cron_apply` and `setup-cron` produce identical command lines for the same task+context. Resolve the `or` in line 303 before implementation.

2. **AC#4 contains a near-unfalsifiable escape hatch.** Line 338: "...without `git_probe_timeout` under tracked 30/120 defaults, **or the implementation justifies any remaining timeout as non-required/non-current residue**." Verified timing: `git status --porcelain=v1 --untracked-files=all` on workspace-hub is already 11.81s (plan line 187), 39% of the proposed 30s probe budget. The OR-clause lets any observed timeout be waved through as "residue," so the criterion can pass regardless of outcome. Pin it: "all 6 governed repos on the running host (`registry.yaml:58`) complete with zero `git_probe_timeout`," and require any exception to be a named, per-repo logged justification rather than free-form prose.

3. **`test_repo_hygiene_timeout_defaults_are_production_safe` cannot catch an over-large total timeout.** TDD list line 324 asserts defaults are "exactly **or at least** `30`/`120`" and "total timeout remains bounded." Pseudocode line 278-279 states "TOTAL remains below cron-health window safety budget" but no test asserts the upper bound. The hygiene→cron-health gap is 10 min (catalog: hygiene `35 5`, cron-health `45 5`, plan line 41) = 600s; current `TOTAL_TIMEOUT_SEC` default is 480. A regression typo pushing TOTAL past 600 would make hygiene overrun into the cron-health window and go uncaught. Add an assertion `TOTAL_TIMEOUT_SEC < 600` (or < the computed gap).

4. **The new "latest evidence line wins" logic is not reconciled with the unchanged generic `ERROR_PATTERNS` scan over the same tail.** `cron-health-check.sh:230-255` scans `tail -n 100` of the hygiene log with patterns including `ERROR:`, `Traceback`, `fatal:`, `No such file or directory` for any task ≠ `cron-health`. The pseudocode `cron_health_check_task_log` (plan 281-292) adds the status-line parse but does not state precedence between the two. Verified mitigant: the hygiene log normally contains only `task=...status=...` lines because git stderr is captured by `run_bounded` (`repo-ecosystem-hygiene-audit.sh:175`), not echoed — so today there is no conflict. But the plan should state this invariant and the precedence explicitly; otherwise AC#6 ("newer WARN/OK clears older ERROR") is silently defeated the first time any future change lets a generic-pattern token (e.g. a leaked `fatal:` or a Python traceback on crash) reach that log alongside an older `status=ERROR`.

5. **Plan never cites how `classify_line` buckets bare `VAR=value` env lines**, yet AC#2 and `test_plan_cutover_preserves_workspace_hub_and_log_env_lines_verbatim` (TDD line 321) depend on `WORKSPACE_HUB=`/`LOG=` classifying as preserved/ignore rather than uncataloged (which would make `plan_cutover` abort, per `cron_apply.py:158`). The captured dry-run (plan lines 142-147) empirically shows them in `preserved`, so the behavior holds at HEAD — but the test author needs the exact `classify_line` branch cited to assert the correct bucket and to guard against a future classifier change turning silent preservation into a fail-closed abort.

6. **Regex engine is unspecified; "latest match wins" + capture is idiom-dependent.** Pseudocode line 286 gives a POSIX ERE but the existing scan uses `grep -Eq` (`cron-health-check.sh:237`), which yields no ordered last-match/capture cleanly — a bash `[[ =~ ]]` loop with `BASH_REMATCH[2]` is required for "last matching line wins." The regex itself is **verified sound** against the real format (`task=repo-ecosystem-hygiene status=ERROR artifact=...`), so Gemini's portability flag is largely a false positive on Linux; name the engine so the implementer doesn't reach for `grep` and lose ordering.
