### gemini

- Plan §Pseudocode for `pending_work_report` returns a false negative for `mailbox_empty` when tracked threads have unhandled replies. The logic `unknown_count = count enabled in-scope snapshot threads missing from local state` explicitly ignores threads that already exist in local state (e.g., `completed`). If the inbox snapshot contains a new reply for a completed thread, the report evaluates `unknown_count == 0` and returns `mailbox_empty = True`, directly violating D3's mandate of "no pending work for any known in-scope thread".
- Plan §D5 causes a `cycle_id` collision and silent deduplication on repeated `no-trigger` reactivations. By assigning `event.cycle_id = "compat:" + stable hash of linked_extraction_or_reason`, multiple reactivations instantiated for the same reason (e.g., the hardcoded `reason="missing-extraction"` from D8) will share the exact same `cycle_id`. The second reactivation's dedup key will perfectly match the first in `historical_dedup_index` and be incorrectly skipped as an idempotent retry, causing `test_multicycle_without_trigger_can_extract_complete_and_purge_twice` to fail.
- Plan §Pseudocode for `prepare_event` breaks idempotency for late historical retries by dynamically stamping them with the snapshot's current `cycle_id`. For non-reactivation events, it assigns `event.cycle_id = snapshot_before.get(event.key, {}).get("cycle_id", "initial")`. If a caller retries an older Cycle 1 event (e.g., original `cycle_id="initial"`) after the thread has entered a new reactivation cycle (e.g., `cycle_id="reactivation:123"`), the retry inherits the new `cycle_id`. Its dedup key will fail the `historical_dedup_index` lookup and incorrectly throw `StaleStateError` (per D11) instead of being skipped.
- Plan §D11 claims "The implementation must store reactivation baselines in snapshots: `last_seen_message_id`, `last_seen_received_at_utc`" for the checker to compare against. However, the plan's `transition()`, `_append_events_locked()`, and `prepare_event()` pseudocode completely lacks logic to extract these fields from the transition payload or write them to the materialized snapshot. Without them, the checker will permanently report `baseline_missing`.
- Plan §Pseudocode for `pending_work_report` violates the structured return schema defined in D3. In the fail-closed config scenario, it dictates `return mailbox_empty=None, unknown_status="config_missing"`. This is invalid Python syntax that conceptually resolves to a 2-element tuple, dropping mandatory keys like `tracked_empty` and `per_account_counts`. Callers unwrapping or accessing the structured dictionary will crash.
