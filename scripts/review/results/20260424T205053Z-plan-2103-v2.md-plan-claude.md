### Verdict: MAJOR

### Summary
The v2 plan materially closes r1 Codex findings: the `search-wiki.py` gap is resolved with a concrete PRODUCTS diff + three TDD assertions, the hyphen-import defect is solved via an underscore-named `llm_wiki_common.py` helper module, and the cat:data-pipeline retrieval contract is cited with per-artifact findings. Attested Evidence is strong and independently checkable. Two implementation gaps should be tightened before approval: (1) the sys.path resolution mechanics when tests load hyphenated ingester files via `importlib.util.spec_from_file_location` and those files then do `from llm_wiki_common import ...` are not documented — this is the exact seam where hyphen-path defects historically recur; and (2) the coordination strategy with sibling plan #2124 v3's `orcina_common.py` is a "whichever lands first wins" race that the workspace's merge-race memory explicitly warns against.

### Issues Found
- [P2] Test sys.path mechanics undocumented: When `test_ingest_bemrosetta.py` loads `ingest-bemrosetta.py` via `importlib.util.spec_from_file_location(...)`, the loaded module executes `from llm_wiki_common import fetch_page, ...`. Python resolves this via sys.modules/sys.path at load time; unless `scripts/data/llm-wiki/` is on sys.path (via a conftest.py sys.path.insert, a PYTHONPATH env, or a preceding spec_from_file_location for llm_wiki_common), the import will raise ModuleNotFoundError. The plan does not specify this setup. This is the same class of hyphen-path seam that the plan is trying to fix — leaving the resolution mechanic implicit is a recurrence risk.
- [P2] #2124 v3 coordination is a race, not a reconciliation: Risks section proposes 'whichever lands first' — either plan's common module becomes canonical and the other re-exports. The workspace memory `feedback_merge_race_silent_revert.md` and `feedback_multi_agent_commit_serialization.md` both warn that parallel sessions touching overlapping files under auto-sync can silently revert work. Two agents each creating a shared helper module with overlapping helper surfaces is exactly that pattern. Needs a concrete coordination commitment (e.g., block this plan on #2124 v3 landing first, or vice versa; or pre-land an empty `llm_wiki_common.py` as a synchronization point before either ingester work begins).
- [P2] Hyphen-named ingester files perpetuate the anti-pattern: The plan keeps `ingest-bemrosetta.py` and `ingest-aqwa.py` hyphenated for 'parallelism with ingest-orcina.py', but the Attested Evidence and memory note together document three hyphen-path recurrences on 2026-04-24 alone. Rationale for hyphen-filename symmetry is weaker than the recurrence evidence; underscore-named ingesters would eliminate the importlib-gymnastics class of seam entirely and let the grep-regression guard be the only enforcement. The existing `ingest-orcina.py` can be left alone or renamed as a follow-up.
- [P3] cat:data-pipeline contract compliance is partial: The plan cites `registry.yaml`, `llm-wiki-external-source-priority-queue.yaml`, and `resource-intelligence-maturity.yaml` (which satisfies retrieval), but actually only updates maturity.yaml. Registry and priority-queue updates are deferred to 'follow-up'. The contract wording in docs/plans/README.md:53 says issues of this class must 'consult' those artifacts — consultation is satisfied — but if the class also implies 'update all three', the plan falls short. Clarify whether consultation-only is the intent; if updates are required, add them to Files-to-Change.
- [P3] BEMRosetta `topic_count ≥ 5` acceptance criterion is live-dependent: If the upstream BEMRosetta wiki/doc tree yields fewer than 5 topics on the day of implementation (e.g., upstream has pruned pages), this acceptance criterion fails for reasons unrelated to code quality. Either specify the criterion against a fixture tree, or reduce the lower bound and document 'any successful parse' as the gate.
- [P3] Atomic-write guarantee only on master index: `update-master-index.py` uses tempfile + os.replace, but each ingester writes its per-product `index.json` with `(product_dir / 'index.json').write_text(...)` — non-atomic. If a second merger run overlaps with an ingester rewrite, the merger may read a half-written per-product index. Low risk given standalone-only trigger, but if future automation chains ingest→merge, this becomes a real hazard. Consider applying the same atomic-write pattern to per-product indexes.
- [P3] search-wiki.py `papers` special-case unverified for new products: Attested evidence notes `_load_topics` returns topics from `topics` key 'or `papers` for the papers product'. The plan asserts the generic path works for `bemrosetta`/`aqwa` as long as they use a `topics: [...]` key, which is plausible, but the plan does not include a direct code excerpt of the branching logic. The TDD test covers this at runtime but verifying the branch statically in the plan would close the last ambiguity.

### Suggestions
- Add an explicit conftest.py entry to Files-to-Change that does `sys.path.insert(0, str(Path(__file__).parent.parent))` so that tests loading hyphenated ingester files via importlib can resolve `from llm_wiki_common import ...` without surprise. Document this in the Pseudocode section as part of the 'Implementation rule' paragraph.
- Commit to a concrete coordination mechanism with #2124 v3: either (a) declare this plan blocked on #2124 v3's `orcina_common.py` landing first, (b) pre-commit an empty `llm_wiki_common.py` as a synchronization point in its own PR before either ingester plan executes, or (c) merge the two plans into one. 'Reconcile at implementation time' repeats the parallel-agent commit-serialization hazard.
- Reconsider the hyphen-filename-for-parallelism argument. Renaming new ingesters to `ingest_bemrosetta.py` / `ingest_aqwa.py` (underscore) eliminates the entire importlib class of test seam, lets tests use `from ingest_bemrosetta import ingest_bemrosetta` directly, and leaves the existing `ingest-orcina.py` as the lone legacy hyphen-name that a follow-up can rename. Parallelism-of-filenames is a weak argument against recurrence-of-defect evidence.
- Replace the `topic_count ≥ 5` live-dependent acceptance criterion with either a fixture-based gate (≥5 topics against the committed fixture HTML) or a minimum of ≥1 topic from the live upstream. Keep the live ≥5 check in the Build Sequence 'live smoke' step where it's informational, not gating.
- Apply the atomic-write pattern (tempfile + os.replace, unique per-process suffix) to per-product `index.json` writes in both new ingesters, not just the master merger. Negligible cost and consistent with the workspace pattern.
- State explicitly whether cat:data-pipeline contract requires only consultation or also requires registry.yaml + priority-queue.yaml updates — cite the contract text or the issue that established the class. If updates are required, add them to Files-to-Change; if consultation-only, call that out to pre-empt a later reviewer re-raising it as P2.
- Include the `search-wiki.py:_load_topics` relevant code excerpt (lines 25-30) verbatim in the Master-index contract section so reviewers can verify the `papers` branch doesn't break the generic path without reading the source.
