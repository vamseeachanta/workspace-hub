### claude

- **The cited AQWA skill source files do not exist on disk.** Plan §Resource Intelligence cites `knowledge/wikis/engineering/raw/papers/SKILLS_SUMMARY.md:1557-1573` and the underlying `_archive/.../aqwa/batch-execution/*/SKILL.md` files for invocation patterns, license env vars, success-vs-failure checks, and probe ordering. The `_archive/engineering/marine-offshore/aqwa/` directory returns *"No such file or directory."* Only the *index row* in `SKILLS_SUMMARY.md` remains; the linked SKILL.md content cannot be verified. Per the retrieval-skepticism rule, citations to nonexistent files don't count as evidence.
- **The plan misquotes `SKILLS_SUMMARY.md:1558`.** Plan §Pseudocode line 248 and r1-revision #5 claim line 1558 supports a "Framework/bin/Win64 listed first" Windows probe order. The actual line 1558 row reads: *"Directory is `lnx64` on most installations. Verify on your site — may also be `lnamd64`."* That is a **Linux** directory reference, not Windows. The Windows-Framework-Win64 ordering in `_locate_aqwa_exe()` has no support in the cited source.
- **The AQWA executable probe targets the wrong binary.** `_locate_aqwa_exe()` glob patterns 1-3 are `Framework/bin/Win64/ansys*l.exe`, `ansys/bin/winx64/ansys*l.exe`, and `ansys*/bin/winx64/ansys*l.exe`. `ansys251l.exe`/`ansys241l.exe` is the ANSYS Mechanical APDL solver, not AQWA. On a real ANSYS install, AQWA's binary lives at `v###/aqwa/bin/winx64/aqwa.exe` (or `aqwa_le.exe` for the workbench launcher). Only probe 4 (`v*/aqwa/bin/winx64/aqwa*.exe`) targets AQWA — but it is listed last and will not be reached because patterns 1-3 will match the unrelated ANSYS solver first. `subprocess.run([ansys251l.exe, "<stem>"])` will not run AQWA on the cited `.dat` input.
- **The proposed `target_machine` pydantic warning channel does not exist.** Plan Files-to-Change row 4b specifies `@field_validator("target_machine")` that "warns (does not raise) ... uses the result.warnings channel via the same pattern as schema_version." Two factual problems: (a) Pydantic's `@field_validator` API only supports `raise ValueError` or returning a value — it has no hook into the external `ValidationResult.warnings` list defined at `validate_manifest.py:48-59`. (b) The `schema_version` warning at `validate_manifest.py:213-219` is **not** inside a pydantic validator — it is a top-level dict check inside the `validate_manifest()` function before pydantic ever runs. The plan's stated "same pattern" doesn't exist where it claims to.
- **Skip-vs-move ordering in `process_job()` is unspecified and will break the stated test.** `process-queue.py:173-174` performs `shutil.move(job_path → completed_job_path)` *and* `output_dir.mkdir(...)` at line 170, both **before** the dispatcher runs. Plan Files-to-Change row (c) says insert the `target_machine` check "after parse, before solver validation" — that is *also* after the file move. Test `test_process_job_skips_when_target_machine_mismatch` (Acceptance §TDD) asserts "job_path not moved" — that will fail unless the skip is placed **before** line 170. The plan does not specify the skip must precede the move.
- **`process_job()` `return None` is counted as failure by the unchanged main loop.** `process-queue.py:485-489` reads `if process_job(job_file): success_count += 1 else: fail_count += 1`. `None` is falsy → skips would be tallied as failures. Files-to-Change row (d) calls for "treat a None return as 'skipped'" but the §Pseudocode does not show the main-loop counter change. Without that explicit edit, the skip path silently corrupts the run-summary log emitted at line 491.
- **`.lis` vs `.mes` error-scrape mismatch.** Plan §Pseudocode reads `<stem>.lis` for error markers. The cited skill `SKILLS_SUMMARY.md:1573` (objective text: *`grep -qi "error|fatal|abort" analysis.mes`*) targets `.mes`, the AQWA messages file, not `.lis` (the listing file). The plan scrapes the wrong artifact.
- **Naive substring matching on `.lis` content will produce false-positive failures.** Pseudocode line 229: `if any(kw in content for kw in ("error", "fatal", "abort"))` after `content = lis_path.read_text().lower()`. Real AQWA `.lis` listings legitimately contain the substring "error" in benign contexts (e.g., "ERROR TOLERANCE", "standard error"). Cited skill uses `grep -qi` (per-line match) — strictly more selective in practice. Plan's whole-file substring match will raise `RuntimeError` on most successful runs.
- **`ANSYS_INSTALL_DIR` semantics are ambiguous.** Plan §Pseudocode error message at lines 198-201 suggests setting `ANSYS_INSTALL_DIR` to "the directory containing 'v241', 'v251', **or** 'Framework/bin/Win64'." Those are at different tree depths — `v251` is a top-level child of `C:\Program Files\ANSYS Inc`, while `Framework/bin/Win64` sits inside `v###/`. The probe globs (relative to `install_dir`) only resolve correctly for one of those root choices. Operator instructions are inconsistent with the glob patterns.
- **Pseudocode for `cadquery.md` quotation cannot be verified at the cited lines.** Plan §LLM Wiki cites `cadquery.md:17,21,47,52` with the quoted phrase "QPPL DIFF requirement for mesh density." Read of `cadquery.md` shows the phrase "remember the `QPPL DIFF` requirement" appears at **line 52**, not 17/21/47. Lines 17 and 21 mention AQWA generally; line 47 is inside an ASCII-art diagram. The line-pin citations are wrong on 3 of 4 line refs.
- **Date drift between r1 review artifacts and revision claims.** Plan header (line 5) says "r1 revision" dated 2026-05-15, but Artifact Map (lines 171-173) cites `2026-05-14-plan-2709-{claude,codex,gemini}.md`. `ls` shows both date stamps exist (`2026-05-14-...` and `2026-05-15-...` review files coexist in `scripts/review/results/`). The plan should pin to the SHA-bound r1 artifact that prompted the revision; instead two distinct review sets are in play and which one drove revisions is ambiguous (relevant to [feedback_issue_2460_approval_binding] precedent on revision-bound approval).
- **`max(matches)` lexicographic sort is described as "latest version" — misleading.** Pseudocode line 258 comment: "latest version by name sort." `max()` of `Path` objects sorts by string representation — works for 2-digit versions (`ansys251l.exe` > `ansys241l.exe`) but breaks for any single-digit/double-digit boundary (e.g., `ansys9...` > `ansys10...`). Comment promises more than the implementation delivers.
- **Acceptance criterion #9 ("Live on-host AQWA smoke run") is unfalsifiable as written.** "with the `.lis` file containing zero error markers" — the plan never defines what an "error marker" is. The cited skill uses `grep -qi "error|fatal|abort"`; the plan's own pseudocode uses a different substring check on a different file. Without specifying the exact grep pattern that will be invoked during smoke validation, "passed" and "failed" are unfalsifiable.
