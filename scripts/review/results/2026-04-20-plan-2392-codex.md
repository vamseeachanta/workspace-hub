### Verdict: MAJOR

### Summary
The plan has multiple blocking correctness gaps: identity handling around missing `doc_key` is not compliant as written, acceptance criteria are not covered by tests, dependency/status claims are unverified, and the review gate conflicts with the repo’s mandatory cross-review policy. I could not affirmatively verify the cited files, issues, or operating-model claims from the plan text alone, so approval is not defensible.

### Issues Found
- [P1] `doc_key` / operating-model §3 compliance is not demonstrated. The plan says the tool is "joined by `doc_key`" and also that "Source with null `doc_key` still emitted but flagged" (`Deliverable`, `TDD Test List: test_missing_doc_key_marked_identity_unresolved`), but nowhere specifies a `sha256:`-namespaced identity fallback or how path-only identity is avoided. This is a blocking correctness gap under the mandatory §3 check.
- [P1] Acceptance criteria are not fully covered by tests. `Acceptance Criteria` requires root-regression pass, runtime `<5 min`, `≥1 gap YAML per wiki domain on first real run`, cron wiring, and review artifacts, but `TDD Test List` covers none of those except dry-run/idempotence. The plan therefore fails the mandatory "every acceptance criterion has a corresponding test" check.
- [P1] The review gate is inconsistent with repo policy. `Adversarial Review Summary` says "Codex | PENDING | Cross-provider review optional-before-approval" and "Gemini | PENDING | Optional", but the workspace instructions require the default 3-agent adversarial review. This is a process-blocking defect.
- [P1] Dependency correctness is unverified and not structured. `Resource Intelligence Summary` cites `#2360` as a blocker, `#2366` as downstream input consumer, and `#2365` as overlapping scope, but the plan has no explicit `Dependencies` section with hard vs soft deps, required statuses, sequencing, or current-state verification. Under the mandatory dependency check, these issue claims are unverified blockers.
- [P1] Cross-machine tier handling is underspecified. The plan claims per `§7` tier classification and includes tests only for `git-tracked` and `shared-mount` (`test_availability_tier_git_tracked`, `test_availability_tier_shared_mount`), while the review note says "tier 3 local-cache excluded explicitly as non-L1/L2 source". There is no test proving exclusion/misclassification behavior for local-cache or mixed-source collisions, so the tier model is incomplete for a correctness-critical rule.
- [P1] Security/threat-model coverage is missing for shared-mount and scheduled execution. The plan reads from `/mnt/ace/` (`test_availability_tier_shared_mount`), scans wiki/report trees, and adds weekly cron wiring (`Files to Change`, `Acceptance Criteria`), but `Risks and Open Questions` contains no threat model for mount poisoning, unsafe path traversal, malformed frontmatter, or cron-time access to external/shared content.
- [P2] The resource-intelligence accounting is internally inconsistent. `Distinct sources consulted: 9 (issue body + 8 above)` does not cleanly reconcile with the enumerated lists in `LLM Wiki pages consulted`, `Documents consulted`, and related issues; the plan appears to count sources ambiguously. That weakens the mandatory check requiring ≥3 distinct concrete sources with findings.
- [P2] The output/storage flow is risky and insufficiently justified. `Pseudocode` reads `docs/reports/*.md` as input and also writes `_summary.md` under `docs/reports/wiki-coverage-gaps/`. The plan does not prove this cannot create self-ingestion, report-feedback loops, or a forbidden durable-flow pattern under operating-model §4.
- [P2] Scope is not kept strictly single-purpose. Beyond detector implementation, `Files to Change` also updates cron scheduling and `docs/plans/README.md`. The latter is administrative churn unrelated to the detector’s core deliverable and should be justified or removed.

### Suggestions
- Add an explicit identity section that defines the exact key scheme for all cases, including missing-`doc_key` entries, and state how `sha256:` namespacing is produced without falling back to path-only identity.
- Expand the TDD matrix so every acceptance criterion has a corresponding test or executable verification step, including performance budget, full-corpus smoke test, cron config validation, and review-artifact generation.
- Do not mark cross-provider review optional; require completed Claude/Codex/Gemini plan reviews before approval, or explicitly amend the plan to match repo policy if an exception was granted.
- Create a dedicated `Dependencies` section listing hard deps, soft deps, required issue statuses, overlap handling for `#2365`, and the exact behavior before/after `#2360` lands.
- Add negative tests for tier classification: local-cache exclusion, conflicting registry entries for the same source, malformed mount paths, and precedence rules when the same artifact appears in multiple registries.
- Add a security section covering shared-mount trust boundaries, path normalization, frontmatter parsing failures, YAML output sanitization, and cron execution constraints.
- Clarify source counting in `Resource Intelligence Summary` and tie each cited source to a concrete finding rather than a bare reference.
- Separate administrative updates (`docs/plans/README.md`) from the detector scope unless they are required by an existing repo standard.
