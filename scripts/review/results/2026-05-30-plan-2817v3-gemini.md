# Plan review artifact — 2817v3 gemini — 2026-05-30 (dispatched via submit-to-{codex,gemini}.sh)

### Verdict: MAJOR

### Summary
The plan successfully identifies the local marker bypass and correctly leverages the server-side label authority. However, there are critical logic flaws in the freshness check that will break the development workflow, and a deployment gap that temporarily removes all enforcement.

### Issues Found
- MAJOR: Workflow-breaking freshness check. The plan requires `applied_at >= pr_head_time`. Because plan approval happens before implementation, the PR head will always post-date the plan approval label. This check would force humans to re-approve the issue after every code push, conflating plan-approval with PR-review.
- MAJOR: Enforcement gap during staging. Retargeting the existing CI job while gating the new logic behind `PLAN_APPROVAL_GATE_ENABLED` creates a window where, if the flag is false (staged rollout), neither the old marker nor the new label is enforced. This fails-open and allows unauthorized merges during the transition.
- MAJOR: Vague plan-to-issue mapping. The function `plan_revision_time(N)` assumes the gate knows exactly which file is the approved plan for issue N. The plan does not specify how this mapping is securely determined. If an agent can spoof which file is considered the plan, it can bypass the plan-revision freshness check.

### Suggestions
- Remove `pr_head_time` from the plan-approval freshness check. The label should only be required to post-date the `plan_revision_time` (the last edit to the plan document).
- To close the enforcement gap, either keep the old `require-plan-approval.sh` active in CI when `PLAN_APPROVAL_GATE_ENABLED` is false, or make the new script fall back to checking the old marker if the flag is disabled.
- Explicitly define how `plan_revision_time(N)` identifies the plan file (e.g., searching for `docs/plans/*-issue-N-*.md` or parsing the issue body for a standardized plan link) and ensure this resolution is resistant to agent spoofing.

### Questions for Author
- How exactly will `plan_revision_time(N)` reliably map an issue number to the correct plan file path in the repository to determine the revision time?
- If an agent force-pushes, does the plan-approval need to be re-evaluated, or only if the plan document itself is modified?
- How does `verified_label_event` handle the GitHub API timeline pagination for issues with more than 100 events?
