## Findings
1. Plan §Files to Change lines 145 and 148 targets nonexistent paths: `scripts/data/document-index/batch-process-standards.py` and `cross-reference-registries.py`. The tracked implementations are under `scripts/document-intelligence/`, as confirmed with `git show HEAD:` and by imports at `tests/document-intelligence/test_marine_standards_batch.py:25-34` and `test_cross_reference.py:17-26`. Those canonical files are also excluded from this sparse worktree. Following the plan literally would either fail or create duplicate, unused consumers.

2. The consumer inventory is materially incomplete. `scripts/data/research-literature/research-domain.py:91-99,138-148` maps ledger states `done`, `reference`, and `in_progress` directly to `available`. `scripts/data/generate-domain-resource-views.py:216-226` equates `gap` with “not yet acquired” and no gaps with downloaded/reference-only resources. `scripts/knowledge/doc-key-lookup.py:100-148,208-228` reads only legacy top-level paths. All contradict Plan §Decision Model lines 71–80, yet none appears in §Files to Change or the TDD list.

3. The plan contradicts the issue’s required semantics. Issue #3533 says: “Prevent `done` or `current` from being inferred when paths, exact edition, amendment, or rights evidence are absent.” Plan lines 80, 119–123, 169, and 185 instead preserve legacy transfer `done`, continue generating transfer rows from implementation/work-item state, and explicitly allow an empty-path `done` row to remain. The batch processor has only one transition—`status = "done"` at `scripts/document-intelligence/batch-process-standards.py:74-79,153-177`—so Plan lines 145 and 171 cannot separately gate “usability/complete.” The plan must resolve this scope deviation and add the issue-required conflicting-chronology and empty-path-completion rejection tests.

4. The schema boundary conflicts with the inherited provenance contract. `docs/document-intelligence/standards-codes-provenance-reuse-contract.md:139-150` requires every tracked document to have `doc_key`, source, path/host, timestamp, and processing status. Plan lines 46, 74, and 182 exclude broad backfill, allow exact identity only “when hashed,” yet require validation of the entire 436-row ledger, where every row lacks `doc_key`. The plan never defines whether legacy transfer-only rows are non-document logical records, grandfathered invalid documents, or subject to #2362. Without that distinction, the validator either cannot pass or silently weakens the canonical contract.

5. DNV-RP-C203 cannot be joined under the specified producer model. The plan confirms no C203 ledger row at lines 18 and 61, assigns holdings ownership to the ledger at line 78, then specifies an enrichment join “by normalized standard identity” at lines 119–123. It does not define curated-only row creation, total/summary effects, or behavior for unmatched-but-valid metadata. Consequently, acceptance criterion line 184 has no deterministic route for recording C203 holding evidence.

6. The deterministic/atomic rebuild acceptance gate is not executable as written. `build-ledger.py:324-329` embeds `date.today()`, `:346-348` produces no dry-run artifact whose bytes can be compared, and `:350-352` writes directly to the canonical file. Plan line 183 demands byte determinism and line 213 demands atomicity, but the TDD list contains no clock-injection, dry-run-output, interruption, or atomic-replacement test.

7. Plan line 181 uses `python -m pytest`, contrary to the repository’s mandatory `uv run` policy. In the active environment, `uv run --no-project python -m pytest` also reports that `pytest` is unavailable; `pyproject.toml:22-31,44-53` places it in the dev dependency group. The acceptance command must name the reproducible dependency-group invocation.
