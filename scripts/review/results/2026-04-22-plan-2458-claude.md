### Issues Found

- **[critical] Mesh-path rewrite math is off-by-one.** The plan asserts the new relative path is `../../../bemrosetta/fixtures/sample_box.gdf` at lines 222 and 346. Walking the path from `digitalmodel/tests/hydrodynamics/diffraction/fixtures/benchmarks/multibody_fpso_turret_v1/`:
  - `..` → `fixtures/benchmarks/`
  - `..` → `fixtures/`
  - `..` → `diffraction/`
  - `bemrosetta/fixtures/sample_box.gdf` then resolves to `diffraction/bemrosetta/fixtures/sample_box.gdf` — **does not exist**.
  Correct value is `../../../../bemrosetta/fixtures/sample_box.{gdf,dat}` (4 ups, not 3). Verified empirically with `realpath -m`:
  - 3 ups → `/…/diffraction/bemrosetta/fixtures/sample_box.gdf` (wrong)
  - 4 ups → `/…/hydrodynamics/bemrosetta/fixtures/sample_box.gdf` (correct, file exists)

  The plan's own reasoning even acknowledges "TWO levels deeper than `fixtures/`" correctly — if original was 2 ups and the new location is 2 levels deeper, the new path needs 2+2=4 ups, not 3. The prose "THREE additional up from new" is ambiguous but the concrete `../../../` string it produces is unambiguous and wrong. This must be corrected before implementation, and the `test_mesh_files_referenced_by_spec_exist_on_disk` TDD guard (good addition — it will catch this) needs the corrected expected path.

- **[important] Mass-assertion tolerance `rel=1e-6` is tight under unit round-tripping.** `OrcaWaveBackend` converts `mass: 250000000.0 kg` → `BodyMass` in tonnes via `kg_to_tonnes` (factor 1000), then the reverse parser multiplies back by 1000. Factor-of-1000 conversions are exact in float64, so rel=1e-6 is usable for the fixture's round-number mass values. But if OrcaWave's native YAML emits `BodyMass: 250000.0` with fewer sig-figs (e.g., `2.5e5`) and the parser's float conversion introduces any ULP-level drift from intermediate string formatting, rel=1e-6 is near the floor. Suggest loosening mass to `rel=1e-4` to match the radii-of-gyration tolerance already in the plan — the engineering claim is "near-equivalent", not "bit-identical".

- **[important] `position` and `attitude` use `abs=1e-6` without justification; values include 0.0.** `pytest.approx([0.0, 0.0, 0.0], abs=1e-6)` is fine but `pytest.approx([100.0, 0.0, 0.0], abs=1e-6)` enforces 1e-8 relative tolerance on the 100.0 component, which is tighter than rel=1e-6. If the OrcaWave backend rounds coordinates to a finite decimal representation anywhere in forward/reverse, this can flake. Prefer `rel=1e-6, abs=1e-9` or match the radii-of-gyration `rel=1e-4`.
