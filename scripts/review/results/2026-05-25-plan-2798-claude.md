# Adversarial plan review — #2798 (Claude r1)

**Reviewer:** Claude (main session, inline r1) · **Date:** 2026-05-25 · **Plan:** docs/plans/2798-completeness-gate.md

## VERDICT: MAJOR

The plan is well-positioned in the existing landscape and reuse-first, but it has two MAJOR defects in the enforcement mechanism and integrity model, plus several MINOR gaps. Not approval-ready as written.

## MAJOR

1. **The "pre-close hook" is technically infeasible as a git hook.** `gh issue close` is a GitHub REST API call from the CLI — a local git pre-commit/pre-push hook does NOT fire on it. The enforcement mechanism is unspecified-but-infeasible as described. Real options: (a) a wrapper/alias around `gh issue close` (bypassable, local-only), (b) a GitHub Action on issue-close webhook that re-opens + comments if no completeness record (server-side, authoritative), or (c) a required `status:completeness-verified` label that a CI check enforces. The plan must pick one; the git-hook framing is wrong.

2. **"Owner-confirmed %" is agent-spoofable.** The plan stores the confirmed value in `hermes kanban complete --metadata`, which is agent-writable — so an agent can write `completeness_pct:95` and "confirmed" itself, defeating the user-in-loop intent. Owner confirmation must be a distinct, attributable, non-agent-writable signal (e.g., a human GH comment matching a pattern, or a label only the owner applies). The "override down-only, never silently up" guarantee is unenforceable when the same actor writes both numbers.

## MINOR

3. **"Based on tests" is undefined for test-less issues.** Most workspace-hub issues are harness/governance/docs with no package and no tests; `quality_score`/`test_source_ratio` (#1629) is per-*package* and won't apply. The ops/rubric fallback is subjective ("live-probe evidence bands") — that is NOT "based on tests" as the requirement states. Define completeness honestly for test-less work, or scope the gate to test-bearing issues only and say so.

4. **Single global threshold (90) is wrong.** Doc/spike/research issues legitimately close below 90. Make the threshold per-issue-class or per-issue-declared, with a default.

5. **#2110 hook collision.** Both this and #2110 add Stop/SessionEnd close-report generation. "Reuse" is asserted but the integration contract (who owns the hook, how the per-issue report composes with the per-session report) is unspecified — risk of double-hooks.

6. **Golden-file HTML test is brittle.** Asserting against the prototype's CSS/layout breaks on any styling tweak. Test the data/score contract, not the rendered markup.

## Recommendation
Address MAJOR #1 (pick a real, preferably server-side enforcement mechanism) and MAJOR #2 (unspoofable owner-confirmation signal) before this is approval-ready. MINOR items can be folded into the plan or the implementation.
