## Findings

### F1 — MAJOR — Fixing D2 re-arms an untested auto-merge that pushes to `main` and deletes remote branches

**Evidence:** `SAFE_BRANCH_RE` is used at **two** sites, not one.

- `scripts/cron/daily-cleanup.sh:139` — step 2, `branch -d` (the site the plan analyses).
- `scripts/cron/daily-cleanup.sh:162` — step 3, "Auto-merge feature branches matching safe patterns", which at `:186` runs:
  ```
  git_q checkout main && git_q merge --ff-only '$branch' && git_q push origin main
    && git_q branch -d '$branch' && git_q push origin --delete '$branch'
  ```

Step 3 pushes to `origin/main` and deletes the **remote** branch. It has never executed, for two independent reasons: `SAFE_BRANCH_RE` matches nothing, and the command is wrapped in `bash -c "..."` (`:185-186`) where `git_q` — a function defined at `:56` and never exported — does not exist, so the subshell exits 127 and the run falls into the `else` branch every time.

The plan's `Pseudocode` covers only `find_branch_disposal_candidates`. Neither the pseudocode, the `Files to Change` reasons, the Acceptance Criteria, nor any of the 20 TDD rows mentions step 3, `--ff-only`, `push origin main`, or `push origin --delete`. The plan's D2 verification row treats `SAFE_BRANCH_RE` as if its only consumer were branch deletion.

**Failure scenario:** the implementation replaces `SAFE_BRANCH_RE` with a policy that matches real fleet prefixes (`feat/`, `chore/`, `fix/`, `worktree-agent-*`). Nothing in the plan tells the implementer to leave step 3 alone. If the new policy is bound to the same variable — the obvious edit — step 3 becomes live simultaneously. On ace-linux-1's workspace-hub, any branch ≤10 commits ahead of `origin/main` authored entirely by `noreply@anthropic.com` (`:173`, which is *every* agent branch) becomes an auto-merge candidate: unattended `push origin main` at 23:00, then remote branch deletion. `main` is the branch #3705 already documents as protected and stranding commits. A failed `--ff-only` mid-run also leaves the shared checkout **on `main`** with the operator's branch abandoned (`:186` `checkout main` is not undone; the loop never `cd`s back).

**Required revision:** the plan must state explicitly that step 3 (auto-merge / push-to-main / remote-branch-delete) is either (a) deleted outright, or (b) left gated behind a separate, explicitly-empty constant that the D2 fix does not touch — with a test asserting no code path in `daily-cleanup.sh` can reach `push origin main` or `push origin --delete`. Add the `bash -c`/`git_q` scoping bug to the defect inventory so the RED-test baseline is not mis-stated.

### F2 — MAJOR — Squash detection matches on branch *name*; `branch -D` will destroy unpushed work

**Evidence:** the plan's pseudocode: `classify squash-merged branches via gh pr list --state merged headRefName` … `return force-delete only for PR-merged squash branches`. The prior art it is copying, `scripts/readiness/reconcile-ecosystem.sh:177-190`, does exactly this and no more:

```
gh pr list --state merged --limit 500 --json headRefName -q '.[].headRefName'
...
grep -qx "$b" <<< "$merged_prs" || continue      # PR merged ⇒ in main
```

`headRefName` is a **name**, not a commit. Nothing compares the local branch tip to the merged PR's `headRefOid`. `worktree_guard.py safe_to_delete_branch` (`scripts/lib/worktree_guard.py:72-74`) only checks whether the branch is checked out in a worktree — it has no unpushed/ahead check whatsoever.

**Failure scenario:** `feat/mooring-lines` had PR #1352 squash-merged in June. In July an agent or the operator recreates or continues `feat/mooring-lines` locally with 6 new commits, never pushed, not currently checked out (the session moved to another worktree). Tonight daily-cleanup sees the name in `merged_prs`, `merge-base --is-ancestor` correctly says "not an ancestor", the guard approves (not checked out), and `git branch -D` destroys the tip. Recovery is reflog-only, on a box where no human is watching at 23:00. This is not hypothetical branch naming — `SOUL.runtime.md` and half a dozen skills instruct agents to reuse per-issue branch names across sessions.

**Required revision:** require `headRefOid` (not `headRefName`) and an explicit check that the local tip is either equal to the merged head SHA or an ancestor of `origin/main`; anything else is surfaced, never deleted. Add a TDD row `test_reused_branch_name_after_merged_pr_is_never_force_deleted` (fixture: merged PR head SHA X, local branch at X+2 unpushed commits → surfaced, not deleted). File a follow-on to apply the same fix to `reconcile-ecosystem.sh:190`, which carries the identical defect today.

### F3 — MAJOR — GitHub failure is fail-**open** today, and no acceptance criterion or test closes it

**Evidence:** `scripts/cron/daily-cleanup.sh:141` and `:202`:

```
OPEN_PR=$(gh pr list --repo "vamseeachanta/$repo" --head "$branch" --state open --json number --jq length 2>/dev/null || echo 0)
if [ "$OPEN_PR" = "0" ]; then   # → proceed to delete
```

Auth failure, secondary rate limit, network partition, `gh` upgrade mid-flight — all produce `0`, which the script reads as *"no open PR, safe to delete."* Note also that step 4's open-PR probe at `:202` is uncapped: it fires once per local branch older than 14 days. On ace-linux-1's five repos that is ~300+ GraphQL calls in a single 23:00 run, well inside the window where GitHub's secondary rate limiter starts returning 403s.

The plan acknowledges this **only in the Risks section** ("The implementation will need bounded calls, cached results per repo, and a fail-closed surface-only fallback"). It appears in **zero** acceptance criteria, **zero** pseudocode lines (`require no open PR` is stated with no error semantics), and **zero** TDD rows. `test_open_pr_branch_never_deleted` uses a well-formed `gh pr list --state open` fixture — it tests the happy path only.

**Failure scenario:** the secondary rate limiter throttles halfway through the run. Every remaining `OPEN_PR` returns `0`. Combined with the F1/F2 fixes now making branches actually deletable, daily-cleanup deletes branches with **open PRs** — the exact set with in-flight human review.

**Required revision:** promote fail-closed to an acceptance criterion and to a TDD row: `test_gh_unavailable_disposes_nothing` (stub `gh` returning exit 1 / empty / rate-limit JSON → zero deletions, run recorded as `errors>0`, and — per F6 — **not** counted as an eligible-backlog no-op). Specify a single bounded `gh pr list --state open --limit N` per repo joined in-process, not one call per branch, and require `timeout` wrapping as `reconcile-ecosystem.sh:178` already does.

**Evidence (three separate problems in one pseudocode block):**

D3 is a one-line "call the helper you already sourced." The plan's Resource Intelligence section never mentions `tier1-repos.sh` or this function, and instead proposes a brand-new `resolve_cleanup_repos(machine_id)` reading `registry.yaml`.

2. The plan's pseudocode says `for each tier1_baseline required/optional repo`. `tier1_baseline:` exists under **exactly one machine** in `config/workstations/registry.yaml` — `dev-primary`. `dev-secondary`, `ace-win-1/2`, `gpu-claw`, `macbook-portable`, and `gali-linux-compute-1` have no such key. `macbook-portable` additionally has no `tier1_repo_root` and no `repo_layout`. The resolver as specified returns nothing on every machine except ace-linux-1 — including ace-linux-2, which the issue says currently carries 7 stashes.

3. `config/tier1-python-repos.txt` states, in its own header: *"NOT the same as `config/workstations/registry.yaml::tier1_baseline.required` — that is per-machine repo *presence* and includes non-Python repos (e.g. llm-wiki)."* Today `daily-cleanup.sh:22` operates on `workspace-hub` + the 4 slugs in that file. Switching to `tier1_baseline.required + optional` changes the destructive job's target set to **8 repos**, newly including `llm-wiki` (private, client/standards content), `aceengineer-strategy`, and `aceengineer-website`. The plan does not name this expansion, does not justify it, and does not seek owner sign-off for it.

**Failure scenario:** implementation follows the pseudocode. On ace-linux-2 and gpu-claw, cleanup silently resolves zero repos and reports a healthy empty backlog forever (the defect this issue exists to eliminate). On ace-linux-1, branch/worktree/stash disposal starts operating on `llm-wiki` and the two aceengineer business repos, which have never been in scope and whose branch conventions have never been audited.

**Required revision:** use `resolve_tier1_repo_path()` from the existing SSOT; if the registry must be consulted, resolve `tier1_repo_root` + `repo_layout` (present on more machines) and fail closed with a named disposition when either key is absent, never silently. State the target repo set explicitly and keep it identical to today's unless the owner approves the expansion in writing.

### F5 — MAJOR — The `.wt-owner` proposal has no writers, no migration, no dirty-tree check, and an unguarded escalation primitive

Four independent problems; each alone makes D4 unfixed.

**(a) There is essentially no worktree-creating automation to modify.** The plan's `Files to Change` says *"Modify: Worktree-creating automation paths discovered by `rg "git worktree add|worktree add"`"*. Running that: the **only** executable that creates a worktree is `scripts/readiness/publish-equality.sh:138` (`worktree add --no-checkout --detach`, a throwaway publish tree). Every other hit is prose in `.claude/skills/**` and `.claude/memory/topics/**` instructing an *agent* to type `git worktree add` by hand — `coordination/parallel-plan-drafting-worktrees`, `software-development/parallel-approved-issue-worktrees`, `workspace-hub-learned/overnight-wave-pack-worktree-isolation`, `git-operation-serialization-preflight`, and others. The ~54 fleet worktrees come from those interactive commands. Marking "automation" fixes nothing; new unmarked worktrees keep accruing at the same rate. The plan does not require updating a single skill file.

**(b) No migration for the ~54 existing worktrees.** The plan states they "will be surfaced and counted as blocked backlog, not removed." Combined with (a), the blocked set only grows. See F6 for why that is worse than inert.

**(c) `mark-owner` is a privilege-escalation primitive with zero validation.** `scripts/lib/worktree_guard.py:102-105`:
```python
if cmd == "mark-owner":
    wt, owner = rest[0], rest[1]
    (Path(wt) / OWNER_MARKER).write_text(owner.strip() + "\n", encoding="utf-8")
```
No check that `wt` is a worktree, that it is not the primary checkout, that a marker does not already exist with a different owner, or that the caller created it. Any script or agent can convert a protected human worktree into a deletable one with one command. The blast radius is larger than deletion: `scripts/maintenance/repo-housekeeping.sh:189-197` gates `git add -A && git commit` on `is-owned "$wt" repo-housekeeping` — writing that owner string into a live session's worktree causes housekeeping to sweep uncommitted human work into an auto-commit. The plan proposes to *rely more heavily* on this marker while modifying `worktree_guard.py` only "if required by marker ownership tests."

**(d) The guard has no dirty/unpushed check, and the plan does not add one.** `safe_to_remove_worktree` (`:67-69`) returns `worktree_is_owned(...)` and nothing else. The plan's `find_worktree_disposal_candidates` requires owner + age + merged-branch; it never requires a clean working tree or an absence of unpushed commits, and there is no TDD row for it. Agent worktrees are precisely where a human intervenes mid-session.

**Required revision:**
- Harden `mark-owner` first, as a prerequisite: refuse a non-worktree path, refuse the primary worktree, refuse to overwrite an existing marker with a different owner, and record `{owner, created_at, creator_pid/script}` rather than a bare string. Add tests for each refusal.
- Add `test_owned_worktree_with_uncommitted_or_unpushed_work_is_never_removed`, and specify `git worktree remove` **without** `--force`.
- Either name the specific skill files that must be updated to emit markers, or drop the marker-writer strategy and replace it with an explicit, owner-approved migration (e.g. a one-time supervised classification pass over the 54 worktrees) — and say which.

### F6 — MAJOR — `CLEANUP_NOOP` will alarm permanently on every box, because "blocked backlog" is never made disjoint from "eligible backlog"

**Evidence:** the plan's `write_cleanup_outcome`: *"update consecutive_noop_counter only when eligible_count > 0 and disposed_count == 0."* The plan's own worktree row: `test_worktree_without_owner_marker_is_not_removed_and_counts_as_blocked_backlog` — *"backlog/outcome will record blocked unowned worktree."* Nowhere does the plan define `eligible_count` as excluding items that policy permanently refuses to dispose. There is no test row asserting `blocked ∌ eligible`.

**Failure scenario:** per F5, all ~54 worktrees stay unmarked indefinitely. Every night: `eligible_count > 0`, `disposed_count == 0`. After N=3 runs, `cron-health-check.sh` exits 1 with `CLEANUP_NOOP` and never returns to green. `cron-health` is a single global exit code (`scripts/monitoring/cron-health-check.sh:397-399`) — one permanently-red task makes the whole daily health signal permanently red, which is exactly the "detection nobody consumes" pathology the issue's through-line names. The plan's paired test `test_true_empty_backlog_noop_stays_healthy` only covers `eligible_count == 0`; it does not cover the case that actually occurs.

Second gaming vector: because `eligible_count` is computed by the same script that decides what to dispose, a conservative classifier trivially keeps the alarm silent by classifying everything as blocked. The health check cannot distinguish "nothing was eligible" from "the classifier declined to call anything eligible."

**Required revision:** define three disjoint counters in the outcome schema — `disposed`, `eligible_but_undisposed` (a real failure), and `blocked_by_policy` (surfaced, never alarms) — and require the per-category reason code for every blocked item. `consecutive_noop_counter` increments on `eligible_but_undisposed > 0` only. Add `test_blocked_by_policy_backlog_alone_stays_healthy` and `test_error_run_does_not_increment_noop_counter` (per F3). Separately, state a ceiling/alert for `blocked_by_policy` so a growing blocked set is visible without wedging the global health exit code red.

### F8 — MAJOR — Stash disposal by `stash@{N}` is a racy destructive reference, and the allowlist matches nothing that exists

**Evidence:** the plan commits to index refs in two places — pseudocode (*"auto-drop only allowlisted automation-owned stash prefixes"*, returning a candidate list) and the TDD row `test_aged_allowlisted_automation_stash_can_drop` — *"specific `stash@{N}` drop candidate will be emitted."* `stash@{N}` is a **position in a stack that renumbers on every push and every drop**.

Also: the plan never names the allowlist. The producers that exist in `scripts/` are `reconcile <ts>` (`reconcile-ecosystem.sh:128` — an `add`-emitted *suggestion*, not an executed stash), `guard-auto-stash-<stamp>` (`return-to-main-guard.sh:85`), `git-safe-auto-stash` (`scripts/cron/lib/git-safe.sh:136`), and `Auto-stash before sync …` (`scripts/coordination/git/sync-all-repos.sh:57`, which pops it again at `:99`). The 15 stashes the issue measured on ace1 were cleared by hand and characterised as "churn" — no evidence links them to any of these prefixes. An allowlist built from these prefixes is a second `SAFE_BRANCH_RE`: correct-looking, matching approximately nothing, and therefore an inert "fix" for D5.

**Failure scenario (race):** candidates computed at 23:00:04 as `stash@{3}` and `stash@{5}`. Either (a) dropping `{3}` first shifts `{5}` to `{4}`, so the second drop destroys the wrong entry; or (b) a human on the box runs `git stash push` at 23:00:06, shifting every index by one, and the drop destroys a stash created seconds earlier. Stashes are repo-wide, not worktree-scoped — the victim need not be near the job.

**Required revision:** resolve each candidate to its **stash commit SHA** (`git rev-parse stash@{N}`), re-verify immediately before dropping that the index still resolves to that SHA, and drop highest-index-first; abort the whole stash pass if the stack changed mid-run. Enumerate the allowlisted prefixes explicitly in the plan and show that each is produced by a named script. If no producer accounts for the observed churn stashes, say so and route D5 to the alert-only branch rather than shipping an inert auto-drop.

Four smaller gaps the plan does not carry:

1. **`--dry-run` is not read-only.** `daily-cleanup.sh:119` (`git fetch --quiet --prune origin`) and `:127` (`git worktree prune --expire=7.days`) are called **directly**, not through the `run` wrapper (`:46-54`). Dry-run therefore prunes remote-tracking refs and deletes worktree administrative records. `docs/plans/2026-06-12-issue-3041-…md` already warned that `daily-cleanup --dry-run` must not be treated as read-only, and the plan cites that document — but files the warning under "Documents Consulted" rather than adding it to the defect inventory. `test_dry_run_does_not_mutate_repos_or_crontab` will go RED for a reason the plan has not identified.
2. **No `runtime:` contract.** `repository-sync` is the only task declaring `runtime: {singleton, max_seconds, state_dir}` (`schedule-tasks.yaml:871`). daily-cleanup's own lock is `LOCK=/mnt/local-analysis/.daily-cleanup-lock` (`:28`) — an absolute path that does not exist on gpu-claw (`/home/undi/ws`) or macOS. Because the script uses `set -uo pipefail` **without** `-e`, the failing `echo … > "$LOCK"` at `:70` does not abort: the job proceeds **unlocked**. The plan never mentions the lock, `cron_runtime.py`, or a singleton contract for a destructive nightly job.
3. **GNU-only builtins.** `stat -c %Y` (`:60`, `:257`) and `date -d` (`:215`, `:230`) are GNU-only; BSD/macOS need `stat -f %m` / `date -j`. The plan's `Acceptance Criteria` promise multi-layout registry coverage and the TDD list includes a macOS-adjacent registry entry, but there is no portability row. Fixture tests authored on the Mac dev box will pass or fail for environment reasons unrelated to the defects.
4. **Hardcoded org.** `gh pr list --repo "vamseeachanta/$repo"` (`:141`, `:202`, `:235`) assumes the org for every slug; the expanded repo set in F4 inherits that assumption unchecked.

**Required revision:** add each to the defect inventory with a corresponding acceptance criterion. In particular, declare a `runtime:` singleton contract for the task and resolve the lock path from the registry.
