## Findings

1. **Pseudocode reintroduces the stale-tail false positive the existing code explicitly guards against (BLOCKER).** Plan §Pseudocode line 264 marks the task ERROR if `recent_tail has /^task=repo-ecosystem-hygiene .*status=ERROR\b/`. But `cron-health-check.sh:235` scans `tail -n 100` of an append-only daily log (audit emits one evidence line per run via `repo-ecosystem-hygiene-audit.sh:744` `print(...)` → crontab `>>`). The plan's OWN reproduction at `docs/plans/...:178-181` shows a tail with `status=ERROR` (13:23) followed by `status=WARN` (13:27, 13:33) — latest state is WARN, yet the proposed regex matches the older ERROR and flips the task red. This directly contradicts the plan's stated intent (Risk line 343: "only treat the final … evidence line") AND the existing append-only-log protection (`cron-health-check.sh:232-234`). No TDD row covers "older ERROR + newer WARN/OK → not flagged." Must parse the LAST matching evidence line, with a test for it.

2. **The executability contract is self-contradicting OR-shaped (BLOCKER).** Deliverable/AC require the crontab to run "without manual WORKSPACE_HUB / LOG edits" (`...:222`, `311`), but TDD rows 296-297 accept *either* concrete command rendering *or* an "emitted env contract," and AC 311 says "or equivalent rendered preview." Current `cron_apply.py:162-166` dry-run returns only `status/preserved/conflicts/selected` — a JSON-only "required env contract" could pass review while applied `new_text` on a clean/no-env crontab still lacks executable paths. The fix must commit to one enforceable mechanism (expand placeholders into the managed command lines is the plan's own recommendation at 341/345) and test the APPLIED `new_text`, not a JSON side-channel. (Consensus with Codex Finding 2.)

3. **Plan's rendering helper derives `WORKSPACE_HUB` and `variant` from DIFFERENT sources than `setup-cron.sh`, so "parity" is not achievable as written (MAJOR).** Pseudocode `cron_env_for_machine` (lines 230-237) reads `machine.workspace_root` from the registry and `variant = machine.schedule_variant or "full"`. But `setup-cron.sh:22` sources `WORKSPACE_HUB` from the live env / script location (`$(cd "${SCRIPT_DIR}/../.." && pwd)`), NOT registry, and `setup-cron.sh:54/62/72` defaults the variant to **"contribute"**, not "full". Two concrete divergences the plan's Risk #1 (line 340) hand-waves: (a) a machine with no `schedule_variant` gets `cron-wrapper.log` from the plan vs `/tmp/workspace-hub-cron.log` from setup-cron; (b) on a host where registry `workspace_root` ≠ the actual checkout path (e.g., ace-linux-2's `~/workspace-hub` sparse overlay per global CLAUDE.md), the plan renders a path setup-cron would never produce. A "shared pure helper" cannot unify these unless setup-cron is also refactored to read the registry — which the plan lists only as optional ("If helper extraction changes the source of truth", Files-to-Change line 279).

4. **`test_status_short_probe_avoids_pathological_untracked_scan_or_uses_safe_timeout` is unfalsifiable (MINOR).** TDD row line 301 passes if "*either* no full untracked scan for expensive path *or* timeout policy prevents git_probe_timeout." An OR over both candidate mitigations means the test cannot distinguish a correct fix from a no-op that merely keeps the existing timeout path — it pins no behavior. Pick the mitigation first (plan recommends tracked timeout defaults, Risk line 342), then write a test that asserts that specific outcome.

5. **No idempotency / second-cutover coverage for the newly-expanded managed block (MINOR).** After the fix, `render_block` emits EXPANDED commands while `catalog_commands` (`cron_apply.py:153`) remains the unexpanded catalog form fed to `plan_cutover`'s uncataloged-abort classifier. The managed block is marker-bounded so a re-run should be safe, but the plan adds no test that a second `run_cutover` over a crontab already containing the expanded block neither aborts as "uncataloged" nor duplicates lines. Given `plan_cutover` aborts fail-closed on classification mismatch, this is worth one explicit idempotency test.

6. **Live-timeout AC only probes 2 of N governed repos (MINOR).** AC line 313 names only `workspace-hub` and `digitalmodel`, but the audit iterates all registry-governed repos (`repo-ecosystem-hygiene-audit.sh` ~674-686; registry lists more). A fix can pass the two named probes while a slower sibling still hits `git_probe_timeout` or exhausts `TOTAL_TIMEOUT_SEC=480`. Probe the full governed set, or justify the two-repo sample as worst-case. (Consensus with Codex Finding 4.)
