### claude

- **Classification mapping ("same logical job across planes") is undefined.** Pseudocode line 60 (`if same logical job exists in multiple scheduler planes`) and TDD row `test_detects_duplicate_logical_job_across_planes` require equating a YAML `id:` (e.g. `gsd-researcher`) with a Hermes job name (e.g. `memory-bridge-daily`, `tier1-indexing-daily`). The plan never specifies how the equivalence is determined — exact-string match? alias table? command-line substring? Without a mapping spec, the duplicate-detection test is testing a fixture-shaped tautology, not a real contract. This is the core deliverable; leaving it under-specified will produce divergent implementations across review/implement cycles.
- **Plan ignores the pre-existing `is_claude_task` flag in schedule-tasks.yaml.** Line 36 of `config/scheduled-tasks/schedule-tasks.yaml` already carries `is_claude_task: true` on `gsd-researcher` (and `false` elsewhere). The plan introduces "native-provider AI bypass" classification (test `test_native_provider_ai_bypass_is_highlighted`) without referencing the field that already encodes this. Either the plan should explicitly consume `is_claude_task` as the source of truth, or it must justify why a new heuristic is needed. As written, two parallel signals will drift.
- **Acceptance criterion #1 contradicts the Files-to-Change and pseudocode coverage.** AC #1 requires reading "all four surfaces". Issue body explicitly names four: YAML, setup-cron dry-run, `crontab -l`, `hermes cron list`. But pseudocode (lines 55-56) collapses to "canonical schedule/config fixtures" + "optional live scheduler evidence", and the Files-to-Change description for `scripts/cron/scheduler-parity-report.py` (line 70) lists "YAML, setup-cron dry-run text, optional crontab text, and Hermes cron list text" — `crontab -l` is "optional" in the script row but "all four" is required in AC #1. Pick one.
- **No TDD test covers the YAML parser surface.** The five TDD rows test setup-cron dry-run parsing, Hermes list parsing, duplicate detection, read-only behavior, and AI-bypass highlighting. The YAML schedule file is the first canonical surface and the issue body's #1 input, yet no test verifies the report parses YAML correctly. AC #5 says "Tests cover parsers" (plural) but only two of three parsers have tests.
- **Risk-vs-AC mismatch on "external crontab lines".** Risks section line 108 states `report must distinguish workspace-hub-managed entries from external cron lines`. No acceptance criterion enforces this, and no TDD row tests it. A risk that is not converted to an AC + test is decorative — implementation will ship without the guardrail.
- **Windows / no-hermes-installed machine path is unaddressed.** `setup-cron.sh:80-86` already shows the script short-circuits on Windows (`contribute-minimal` variant). Issue claims a parity report needs to cover machine state. If the report is invoked on a Windows machine without `hermes`, what should it emit? The plan says "records unavailable surfaces explicitly" in AC #1 but no test covers the unavailable-surface code path. This is a real production scenario, not a hypothetical.
- **Test `test_report_is_read_only` design under-specified for subprocess whitelisting.** The report MUST invoke at least three external commands: `bash setup-cron.sh --dry-run`, `crontab -l`, `hermes cron list`. These are subprocess calls. The TDD description says "Monkeypatch subprocess runner so mutating commands fail if called" — but how does the test distinguish read-only `crontab -l` from mutating `crontab -` (load) / `crontab -r` (remove)? Without an explicit subcommand-arg allow-list, the test is either tautological (monkeypatch fully blocks subprocess and report can't run) or weak (monkeypatch allows everything `crontab*` and a future `crontab -r` ships silently).
- **`#2763` linkage is buried in a single test row, not in the plan body.** Line 84 references `#2763` inside `test_native_provider_ai_bypass_is_highlighted`. The issue body for #2765 references #2762 (parent), #2089, #2291 — not #2763. The plan should either (a) explicitly tie the AI-bypass classification to #2763's migration scope in the Resource Intelligence section, or (b) drop the linkage and let the test cite the broader category. As written, a reviewer cannot tell whether #2763 is an authoritative input or a drive-by attribution.
- **`config/scheduled-tasks/schedule-tasks.yaml` already includes a `weekly-hermes-parity-review` task** (id at line 222, command at line 230 invokes `scripts/cron/weekly-hermes-parity-review.sh`). The plan does not acknowledge or discriminate from this existing parity-review surface. Either the existing weekly-hermes-parity-review covers a different concern (and the plan must say so), or the new report duplicates it. No retrieval section entry addresses this overlap.
- **"Single-lane implementation" justification is weak.** Line 7 declares single-lane because "report schema and tests share parser code". That's true of nearly every TDD project; it does not justify abandoning the documented T2 parallel default. Either justify with a concrete shared-mutation site or run parallel per AGENTS.md T2 default.
- **No reproduction proof captured before planning.** Line 19: "Runtime failure reproduction: N/A". The issue body explicitly cites a `hermes cron list` snapshot showing jobs not in YAML — this IS reproducible live state, not "N/A". The plan should capture the live `hermes cron list` output now (redacted as needed) into a fixture before implementation, per the must-fire-rule "Reproduce alleged failure (Step 1.5)" in workspace-hub CLAUDE.md. Asserting N/A when the issue body provides reproducible evidence is the past-tense / future-tense framing drift `feedback_plan_past_tense_artifact_claims` warns about.
- **`docs/ops/scheduler-parity-report.md` is an "update" but the file does not exist.** Files-to-Change row says `update` for this path. Listing `docs/ops/` confirms no such file exists. `update` implies prior content; this is a `create`. Minor mislabel but the file action verb is wrong.
