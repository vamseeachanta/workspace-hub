### claude

- **MAJOR — Plan misstates the baseline and internally contradicts itself on scheduler filtering.** `grep -nE "scheduler"` across `cron_transaction.py`, `cron_apply.py`, and `cron-audit.py` returns **zero matches**. The current `select_tasks` (lines 205–263) has no `scheduler` check, and `run_cutover` (cron_apply.py:152) passes the full catalog including `windows-task-scheduler` tasks. Yet Files-to-Change (plan line 510) says the extension preserves "existing ... `scheduler=cron` filtering," while the Pseudocode (lines 374–375, 385) *adds* `if task.scheduler exists and task.scheduler != "cron": continue`. The prose says "preserve existing"; the pseudocode says "add net-new." This is a contradiction that can cause under-implementation. The actual reason Windows tasks are excluded today is incidental: `provider-dream-bridge-win`/`hermes-claude-bridge-win` are pinned `machines:[ace-win-1,ace-win-2]` (verified lines 398, 437), so on `dev-primary` they hit the `legacy_excludes` conflict branch (`role-match` control-plane + machine exclusion → `roles_authoritative` unset → not selected, **conflict reported**). A future control-plane Windows task with no `machines` or a Linux machine in `machines` would today be selected into the Linux crontab — that is the latent bug the new filter actually fixes, and the plan never says so.
- **MAJOR (sub-finding of #1) — Untested behavioral delta in conflict reporting.** The plan's own evidence shows `conflicts_count 5` (plan line 177). Adding the scheduler `continue` *before* the conflict branch removes the two Windows control-plane tasks from the conflict list (they currently conflict via legacy-exclusion), so `conflicts_count` will drop to ~3. The negative test `test_cron_apply_filters_non_cron_schedulers_before_role_selection` only asserts these tasks are absent from `selected/new_text`; no test pins the conflict-count/conflict-content change. "Backward compatible … conflict reporting" (plan line 510, AC line 583) is asserted but not falsifiably tested for this delta. Add a regression asserting that scheduler-filtered tasks neither select nor appear as conflicts.
- **MINOR — File-existence evidence is incomplete for the files the plan modifies.** Plan lines 64–74 enumerate 10 EXISTS entries but omit five files the Files-to-Change table modifies: `scripts/cron/cron-audit.py`, `tests/cron/test_cron_audit.py`, `tests/cron/test_a1_preserved.py`, `config/workstations/harness-state-classes.yaml`, `config/workstations/registry.yaml`. I verified all five exist, so "Modify" is correct — but a plan whose entire premise is audit/apply parity (cron-audit.py) and a1 preservation regression (test_a1_preserved.py) must include those in its existence evidence per the must-fire "verify coverage assumptions empirically" rule. Current evidence does not prove the implementer even located the audit-side test surface.
- **MINOR — Timeout change weakens worst-case full-set completion, evidenced only by a warm-cache run.** The plan raises `REPO_TIMEOUT_SEC` 45→120 (verified current default 45 at line 38) while holding `TOTAL_TIMEOUT_SEC=480`. At 45s/repo, 480s allowed ~10 repos at full budget; at 120s/repo it allows only ~4 of the 17 governed repos before `incomplete_due_to_deadline` trips. AC (line 590) *requires* `incomplete_due_to_deadline=false` and zero `git_probe_timeout`, but the only evidence is a single 16.13s run the plan itself flags as possibly cache-warmed (Risk, line 716). The plan defers a cold-cache timing to closeout (line 590), which mitigates but does not close this — the acceptance is structurally satisfiable only if repos stay fast; it is not bounded by `17 × REPO_TIMEOUT`. Not a blocker because closeout cold-cache timing is required, but the per-repo×count vs total tension (flagged by Codex r2 per plan line 617) is still unaddressed in the math, only in the live sample.
- **MINOR — `catalog_commands(catalog, fallback_mode="full-command")` in pseudocode (lines 451–453) names a parameter that does not exist on the current function.** Verified signature is `def catalog_commands(catalog: dict) -> list[str]` (cron_apply.py:119) with hardcoded `cmd.strip()[:60]` (line 129). This is acceptable as proposed new API for the shared builder, but the plan never explicitly states it is adding a `fallback_mode` parameter (or a new function name) in Files-to-Change — it only says "add the canonical shared raw+rendered catalog-key builder." The pseudocode reuses the existing name `catalog_commands` for the new shared builder while `cron_apply.catalog_commands` and `cron-audit.load_catalog_commands` both already exist; the move/rename/signature-change is under-specified for an implementer.
