# Adversarial plan review — #3784 (Claude, r1)

**Plan:** `docs/plans/2026-08-02-issue-3784-tmux-persistence-and-ssh-autoattach.md`
**Date:** 2026-08-02
**Provider:** Claude (main-session inline, r1)
**Stance:** adversarial — hunting defects, defaulting to non-APPROVE

## Verdict: **MAJOR**

The plan is well-evidenced and the scope boundaries are sound, but three defects would produce a
persistence stack that *appears* to work while silently destroying the thing it exists to protect,
and one would let the headline acceptance criterion pass on the wrong mechanism.

---

## F1 — MAJOR: autosave races continuum's restore and can destroy the restore point

`@continuum-restore on` fires when the tmux server starts after boot. The new timer saves on a fixed
schedule with no knowledge of restore state. The interleaving that breaks it:

```
boot → tmux server starts → continuum begins restoring 6 windows
     → timer fires mid-restore → save.sh captures a 2-window partial tree
     → `last` symlink now points at the partial save
     → next reboot restores the partial tree; the good save is no longer `last`
```

The plan treats save and restore as independent. They share one state file. **Required:** the wrapper
must refuse to save while a restore is in progress (resurrect/continuum expose a restore-in-progress
marker; the wrapper must consult it, not assume), and the plan must carry a test for the mid-restore
case. As written, the mechanism that fixes D1 can manufacture a worse failure than D1.

## F2 — MAJOR: `Persistent=true` makes F1 fire on essentially every boot

`Persistent=true` causes a missed 15-minute window to fire *immediately* at boot — which is precisely
the moment continuum is restoring. The plan chose that flag to avoid missing a window, but the
boot-time window is the one where saving is most destructive and least valuable (nothing has changed
yet). **Required:** drop `Persistent=true`, or gate the unit behind the restore-complete condition
from F1. Recommend dropping it — a missed save costs 15 minutes of layout drift; a boot-time save
costs the entire restore point.

## F3 — MAJOR: the plan never verifies that interactive SSH logins actually read `~/.bashrc`

An interactive SSH login starts a **login** shell, which reads `~/.bash_profile` / `~/.bash_login` /
`~/.profile` — **not** `~/.bashrc`. It works on stock Ubuntu only because the default `~/.profile`
contains a block that sources `~/.bashrc`. The plan asserts the `~/.bashrc` placement works and lists
no verification of that chain on any of the three boxes.

This is not hypothetical: gpu-claw runs as a different user (`undi`) with a separately-provisioned
home, and the ace-linux-1 `~/.bashrc` has been appended to by at least two third-party installers.
If any box's `~/.profile` chain is broken or `~/.bash_profile` exists without the source line, the
auto-attach silently never fires — and the acceptance test "interactive SSH login lands in `main`"
would be the *only* thing that catches it, at rollout, per box.

**Required:** add a resource-intelligence step that verifies the `~/.profile` → `~/.bashrc` chain on
all three boxes before implementation, and have `deploy-tmux.sh` detect and warn when the chain is
absent rather than writing a block that will never execute.

## F4 — MODERATE: the `ssh host '<cmd>'` acceptance criterion is protected by the wrong guard

The plan credits `SSH_ORIGINAL_COMMAND` with protecting the remote-command path. **sshd does not set
`SSH_ORIGINAL_COMMAND` for a plain `ssh host 'cmd'`** — it is set only when a `ForceCommand` (or an
`authorized_keys` `command=` restriction) is in play, neither of which this plan uses. The actual
protection for `ssh host 'cmd'`, `scp` and `rsync` is the **interactivity** check.

Consequence: `test_autoattach_skips_remote_command` as specified sets a variable that would never be
set in the real scenario, so it passes whether or not the mechanism that actually protects the path
still works. That is precisely the failure class this repo already burned itself on — a test pinning a
name rather than the property. **Required:** re-specify the test to exercise a non-interactive shell
with `SSH_CONNECTION` set (the true `ssh host 'cmd'` shape), and keep the `SSH_ORIGINAL_COMMAND` case
as a separate, correctly-labelled defence-in-depth test.

## F5 — MODERATE: no test asserts silence on the non-interactive path

Any byte written to stdout by the shell startup chain corrupts `scp`/`sftp`. The guard returns before
warning today, but nothing in the test list *pins* that. A later well-meaning edit adding a status
line to the top of the guard would break file transfer fleet-wide, and every listed test would still
pass. **Required:** add `test_autoattach_emits_nothing_when_non_interactive` asserting both stdout and
stderr are empty.

## F6 — MODERATE: `deploy-tmux.sh` will silently destroy gpu-claw's existing config

`ln -sf "$SRC" "$DEST"` overwrites a **regular file** with no backup. On gpu-claw `~/.tmux.conf` is a
26-line regular file containing local customisation. R5 runs the deploy script there. The local file is
gone with no recovery path, and the plan's own acceptance criteria would report success.

**Required:** back up a non-symlink `~/.tmux.conf` to a timestamped path before linking, and report the
backup location. Cheap, and the plan's rollout table is the only place this would otherwise surface.

## F7 — MINOR: the rename in R2/R4 is not durable until the next save

After `rename-session overnight → main`, the most recent resurrect save still describes `overnight`.
A reboot in the gap between the rename and the next timer tick restores the old name and re-creates the
three-way split the plan set out to eliminate. **Required:** force an immediate save as an explicit
step of R2/R4, and re-verify the saved file names `main`.

## F8 — MINOR: test-harness constraint from `exit`/`return` semantics is unstated

The guard uses `return` (valid only when sourced) and `exit` (terminates the sourcing shell). A pytest
case that sources the guard in-process would terminate the test runner. The prior art the plan cites
uses `subprocess` against hermetic fixtures, which handles this, but the plan should state the
constraint explicitly so an implementer does not reach for a simpler in-process source.

---

## What the plan gets right

- Scope boundary against #3549 is explicit and correct; naming the directory rather than the concept
  makes it enforceable.
- The D3 correction was caught and published before planning rather than propagating — the plan
  addresses the real failure mode (undeployed symlink) rather than the filed one (missing clone).
- Refusing `ForceCommand` and refusing `exec` are both correct calls, and the divergence from the
  approved snippet is flagged rather than silently substituted.
- Honest treatment of the Windows hosts: naming the target unreachable for 2 of 5 boxes is better than
  an acceptance criterion that could never pass.
- Reproduction evidence is real command output with timestamps, not prose assertion.

## Required before approval

F1, F2, F3 are blocking. F4 and F5 must be folded into the test list. F6 must be added to the deploy
script's behaviour. F7 and F8 are plan-text fixes.
