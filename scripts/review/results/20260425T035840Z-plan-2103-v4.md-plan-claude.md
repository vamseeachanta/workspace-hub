### Verdict: MAJOR

### Summary
High-quality v4 plan with strong attestation, explicit r3-defect resolution (file rename, atomic_io consolidation, fcntl.flock concurrency), and a detailed TDD list. However, two real defects remain in the master-index merger design — a schema mismatch on cold start (documented schema includes `supplementary`/`papers` top-level keys that the merger never initializes) and a logically weak concurrency test description — plus several minor pseudocode inconsistencies that should be tightened before approval.

### Issues Found
- [P2] Master-index merger schema mismatch on cold start. The documented contract (lines 135-141) shows top-level `supplementary` and `papers` keys, but `merge_master_index` only does `existing.setdefault('products', {})` and iterates `PRODUCT_KEYS = ['orcaflex','orcawave','orcfxapi','bemrosetta','aqwa']` (no papers, no supplementary). On a cold run with no prior `index.json`, the resulting file is missing those keys — any consumer reading `index['papers']` will KeyError. Either update PRODUCT_KEYS / merger logic to materialize all documented keys, or shrink the documented schema to match what the merger actually writes.
- [P2] `test_update_master_index_flock_serializes_concurrent_runs` description has a logic gap. The text says 'spawn two subprocess merger runs in parallel, each adding a different product index' — but the merger reads whatever per-product `index.json` files already exist on disk; it doesn't 'add' anything itself. Two concurrent runs would read the same set of files and produce the same output, so this test as described would not actually exercise last-writer-wins. The test needs to be redesigned (e.g., interleave per-product index file creation between subprocess starts, or assert via lockfile timing instrumentation) to genuinely demonstrate the flock serialization claim.
- [P3] Helper-name inconsistency: `ingest_bemrosetta.py` defines `extract_title_from_markdown(md_bytes, *, fallback)` but `ingest_aqwa.py` calls `extract_title(md, fallback=url)` — different name, different signature, never declared as a local helper in the AQWA pseudocode. Either reuse the bemrosetta helper (and document import path) or define the local AQWA helper explicitly.
- [P3] `iso_now()` is referenced by all three new modules (`ingest_bemrosetta`, `ingest_aqwa`, `update_master_index`) but is never defined or sourced in pseudocode. State whether it lives in `orcina_common`, `atomic_io`, or each module locally.
- [P3] CLI / argparse interface unspecified. Acceptance criteria call `--output-dir /tmp/wiki-smoke` against all three new scripts, but no pseudocode shows the argparse setup, default for `output_root`, or how `WIKI_OUTPUT_ROOT` interacts with `--output-dir`. Implementers will guess.
- [P3] `test_atomic_io_success_path` asserts no `*.tmp` orphans, but the actual tempfile suffix per pseudocode is `.{pid}.json.tmp` (suffix=`f'.{os.getpid()}.json.tmp'`) and the prefix is `path.name + '.'`. Glob `*.tmp` will catch it — fine — but worth pinning the glob in the test description so future refactors of the suffix don't silently break the test.
- [P3] Lockfile-creation race is benign but not asserted. Two concurrent processes opening `lock_path` with mode `'a+'` is safe (POSIX open(O_APPEND|O_CREAT) is atomic), but the plan doesn't call this out, leaving a reviewer to verify it. One sentence in Risks would close it.
- [P3] `existing.setdefault('products', {})` is called inside the flock window, but the `existing` read happens only if `master_path.exists()` — the cold-start branch sets `existing = {}` then does setdefault. Fine, but combined with the schema gap above it shows the merger isn't carrying the full documented contract.

### Suggestions
- Add an explicit list of top-level master-index keys the merger MUST materialize (`products`, `supplementary`, `papers`, `generated`) and update `merge_master_index` pseudocode to `setdefault` each one. Add an acceptance criterion that the cold-start master `index.json` contains all four top-level keys.
- Redesign `test_update_master_index_flock_serializes_concurrent_runs` to actually exercise the race: have the test fixture write per-product index files in a controlled sequence and use a `fcntl.flock` instrumentation hook (e.g., a sleep injected via env var) to force overlap, then assert both runs' contributions survive in the final master.
- Promote `iso_now()` into `atomic_io.py` (since it's the closest shared utility) or into `orcina_common.py` — pick one and document in pseudocode. Avoids three drifting copies.
- Specify the argparse contract for the three new scripts in a small pseudocode block: `--output-dir` (default = `resolve_wiki_path()`), interaction with `WIKI_OUTPUT_ROOT` env var, exit codes.
- Consider adding a `test_update_master_index_cold_start_schema` test that asserts the four required top-level keys are present after a cold run. This would have caught the current schema mismatch.
- When `update_master_index.py` runs, log the lockfile path and acquire/release timestamps at INFO level — operational debuggability for the eventual ingest→merge automation chain.
- Note in Risks that `fcntl.flock` advisory locks are NOT honored across NFS in some kernels — fine for local workspace, but worth flagging for the eventual cross-machine batch runner.

### Questions for Author
- Is the documented master-index schema (`products`, `supplementary`, `papers`) authoritative, or is it aspirational? If authoritative, the merger needs to materialize all keys; if aspirational, the documented contract should be trimmed to match the merger's actual output.
- Who owns `supplementary` and `papers` writes into the master index? `ingest-orcina.py` (legacy), this plan's new merger, or a future merger extension? The plan should pin ownership.
- For the SLA fallback (#2124 v3 slip > 5 working days), who is the named operator that triggers the 4-helper shim micro-PR? An unowned SLA tends to be ignored.
- When `WIKI_OUTPUT_ROOT` env var is set AND `--output-dir` CLI flag is passed, which wins? The plan assumes `WIKI_OUTPUT_ROOT` for tests but `--output-dir` for smoke acceptance — precedence should be explicit.
- For the registry/priority-queue follow-up issue (filed at PLAN-APPROVAL time per r3 P3), what is the SLA for that follow-up landing? The current text only commits to filing, not to closing — leaving the 'ingested-but-unconsumed' window open indefinitely.
- Will `test_no_new_hyphen_named_python_files_under_llm_wiki` be promoted to a level-2 enforcement script (per `.claude/rules/patterns.md` enforcement gradient) given this is the 5th recurrence? A pytest test catches it at test time; a pre-commit hook would catch it at commit time.
