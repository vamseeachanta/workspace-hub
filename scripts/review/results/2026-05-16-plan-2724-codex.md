## Findings
1. Plan §Rule Texts, rule “Use subagents for parallel work” creates an unconditional cross-provider must-fire rule to “dispatch via parallel `Agent`/`Task` calls” for “2+ independent tasks.” The plan also says provider deltas will not be modified and `SHARED_SOUL.md` is inherited by Hermes, Claude, Codex, and Gemini. That is unsafe as written because not every provider/runtime necessarily exposes or permits `Agent`/`Task`, and the plan contains no provider-capability exception. Add “when the runtime supports and authorizes subagent dispatch; otherwise use the provider’s available parallel/review mechanism and document the fallback.”

2. Plan §Rule Texts, rule “Proactively take up authorized work” says a session with `status:plan-approved` should “proceed without waiting” and that “everything inside an authorized scope is fair game.” This omits existing preconditions from `config/agents/SHARED_SOUL.md`: “Check parallel work before starting” and “Discovery-first on stale `plan-approved`.” As written, the new rule can be read to skip the very stale-state and conflict checks that already exist. The rule needs to say “after checking parallel work and doing stale-plan discovery.”

3. Plan §TDD Test List says “This is text-only + propagation; no new pytest cases. Verification is via the existing drift check.” That does not test the new behavior directly. `scripts/enforcement/check-soul-runtime-drift.sh` only verifies rebuilt runtime artifacts match source concatenation; it does not prove the five intended rule strings were inserted, inserted once, or propagated into each artifact. The plan relies on manual grep for only one string: `grep -c "Promote generalizable" ~/.hermes/SOUL.md ~/.codex/AGENTS.md`. It should add explicit checks for all five rule headings across `SHARED_SOUL.md` and all five rebuilt runtime artifacts.

4. Plan §Deliverable says “applied to all 4 cross-provider runtime artifacts,” but `scripts/agents/build-soul-runtime.sh` emits five artifacts: `hermes/SOUL.runtime.md`, `claude/SOUL.runtime.md`, `codex/SOUL.runtime.md`, `codex/AGENTS.runtime.md`, and `gemini/SOUL.runtime.md`. The plan later says “regenerates all 5 runtime artifacts,” so the deliverable is internally inconsistent and can under-scope verification of Codex’s separate `AGENTS.runtime.md`.

5. Plan §Files to Change says `docs/plans/README.md` will be updated with this plan row, but `docs/plans/README.md` on `main` already contains a `#2724` row for `docs/plans/2026-05-16-issue-2724-soul-must-fire-rules-from-2722-review.md`. The implementation step is stale and risks duplicating the index row unless changed to “verify/update existing row.”

6. Plan §Resource Intelligence Summary says “Standards: Not applicable,” then admits `cat:harness` retrieval applies. GitHub issue `#2724` is labeled `cat:harness`, and `docs/plans/README.md` requires Harness/Infra plans to consult `CONTROL_PLANE_CONTRACT.md`, `config/agents/` settings, and `.claude/rules/`. The plan did consult some of these, so the defect is the false “Not applicable” classification. That should be corrected because this is explicitly a harness/control-plane change.

7. Plan §Rule Texts, rule “Promote generalizable review findings,” cites “26 of 29 distinct findings were generalizable.” The three `#2722` review artifacts verify many findings, but the plan does not provide a durable enumeration or classification showing which 26 were generalizable and which 3 were not. This makes the headline quantitative claim non-reproducible from the cited artifacts without reviewer guesswork. Add a short table or link to a disagreement/classification artifact.

8. Plan §Acceptance Criteria requires `uv run python -m pytest tests/enforcement/` to return “88 passed (or equivalent prior-count + delta),” but I could not verify that count from tracked files via the GitHub connector, and the local shell was blocked. The plan should avoid hardcoding `88/88` unless it records a verifiable command output artifact or uses “current baseline + no regression” with the actual baseline captured during implementation.

## Blockers
- Finding 1: unconditional cross-provider `Agent`/`Task` requirement is unsafe without provider-capability and authorization caveats.
- Finding 2: proactive-work rule must explicitly preserve parallel-work and stale-plan discovery gates.
- Finding 3: verification does not directly prove all five rules propagate to all runtime artifacts.
- Finding 4: deliverable must consistently define whether the runtime artifact set is four provider artifacts or five generated files.
