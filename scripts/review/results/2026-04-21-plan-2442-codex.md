### Verdict: MAJOR

### Summary
The plan does not prove it can deliver a green `python-tests.yml` run. Its phase-2 gate is too weak for the stated deliverable, and its `assetutilities` mitigation omits the checkout/source-resolution step required on a clean Actions runner. The claimed 9-site inventory is therefore incomplete.

### Issues Found
- `docs/plans/2026-04-21-issue-2442-assethold-python-tests.md` — **Deliverable / Acceptance Criteria / Pseudocode mismatch.** The plan promises `"A green python-tests.yml run ... achieved via ... (3) full matrix + docs.yml hardening"`, but phase 2 only gates on `"at least one matrix cell (py3.11 / ubuntu-latest) ... success"`, and the pseudocode even weakens that to `"success or test-only failure"`. That cannot satisfy the actual workflow in `assethold/.github/workflows/python-tests.yml`, where `quality-gate` depends on `test`, `integration-tests`, and `financial-data-tests` and exits non-zero if any upstream job result is not `success`. One green matrix cell is not sufficient to make the workflow green.
- `docs/plans/2026-04-21-issue-2442-assethold-python-tests.md` — **Cross-phase dependency handling for `assetutilities` is underspecified and likely non-functional.** The plan says phase 2 can `prepend install step: uv pip install -e <path-or-git+url>` if needed, but `assethold/pyproject.toml` already declares `[tool.uv.sources] assetutilities = { path = "../assetutilities" }`, while `assethold/.github/workflows/python-tests.yml` only checks out the `assethold` repo. On a clean GitHub runner there is no `../assetutilities` unless the workflow explicitly checks out that sibling repository into that path or switches to a git/url source. The plan identifies the dependency risk but does not include the required checkout/source rewrite, so the 9-site fix inventory is incomplete.
- `docs/plans/2026-04-21-issue-2442-assethold-python-tests.md` — **The proposed default install-path remediation points at a file that declares itself obsolete.** The plan's phase 2 default is to replace `requirements.txt` with `requirements-consolidated.txt`, but `assethold/requirements-consolidated.txt` begins with `"This file is now replaced by pyproject.toml"` and is `"Kept for reference only"`. Treating that file as the primary CI source of truth is not affirmatively justified, especially when the same repo has `uv.lock`, `[tool.uv.sources]`, and a project dependency model in `assethold/pyproject.toml`. This leaves the phase boundary unresolved: the plan has not verified whether the intended fix is `uv sync`/project install or a stale reference manifest.
- `docs/plans/2026-04-21-issue-2442-assethold-python-tests.md` — **Stale Files-to-Change entry.** The plan lists `Update | docs/plans/README.md | Add row for plan 2442 (deferred per constraint — NOT in this session)`, but `docs/plans/README.md` already contains a `2442 | assethold-python-tests` row. That is minor by itself, but it is evidence the artifact map/file inventory was not re-verified end to end.

### Suggestions
- Strengthen the phase gates so they align with the stated deliverable: either reduce the deliverable to a bounded partial-unblock, or require the conditions needed for the whole `python-tests.yml` workflow to conclude `success`.
- Make `assetutilities` resolution explicit in the plan. The workflow must either check out `vamseeachanta/assetutilities` into `../assetutilities`, or stop using the local path source and install from an explicit git/package source that works on hosted runners.
- Choose one install source of truth before approval. If `pyproject.toml` + `uv.lock` are authoritative, say so and remove the `requirements-consolidated.txt` branch from acceptance criteria instead of leaving both paths acceptable.
- Remove stale file-change items and restate the fix-site count after re-verifying every required workflow edit.

### Questions for Author
- Is the intended deliverable really `full workflow green`, or only `startup unblocked + one smoke cell green`? The current plan claims both.
- How is `assetutilities` expected to be made available on GitHub Actions: sibling checkout, published package, or git URL install? The plan needs one concrete mechanism, not a placeholder.
- If `requirements-consolidated.txt` is `reference only`, why is it the default remediation instead of the locked/project-managed install path?
