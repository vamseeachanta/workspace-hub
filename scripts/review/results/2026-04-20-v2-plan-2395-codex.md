### Verdict: MAJOR

### Summary
The plan still contains correctness-critical assertions that are presented as verified without live evidence, especially around dependency status, repo paths, and operating-model compliance. The dominant defect class is unverified resource intelligence and test/acceptance mismatches, which blocks approval under the stated review standard.

### Issues Found
- [P1] Unverified dependency correctness: `## Resource Intelligence Summary` and `### Dependency Matrix (live-verified 2026-04-20)` claim issue states for `#2205`, `#2373`, `#2365`, and `#596`, but the plan includes no evidence payload, snapshot, or reference proving those issues exist at those statuses. Under the mandatory dependency check, this remains unverified.
- [P1] Unverified file-path assertions: `## Resource Intelligence Summary` claims `scripts/data/document-index/phase-a-index.py`, `scripts/data/document-index/provenance.py`, `data/document-index/standards-transfer-ledger.yaml`, and `knowledge/wikis/engineering/CLAUDE.md` were confirmed on `2026-04-20`, but no evidence is attached and several later paths differ (`scripts/data/doc_intelligence/...` vs `scripts/data/document-index/...`). The plan asks the reviewer to trust repo state rather than proving it.
- [P1] Resource-intelligence source count is inflated by unverifiable categories: `Distinct sources: 9` in `## Resource Intelligence Summary` counts broad buckets like `Standards`, `Documents consulted`, and `LLM Wiki pages consulted`, but concrete findings are only attached to a few repo paths. This does not affirmatively satisfy the requirement of `≥3 distinct sources with concrete findings` because the cited external/standards items contain no quoted findings or evidence excerpts.
- [P1] Acceptance criteria are not fully covered by tests despite `## AC ↔ Test Map` claiming complete coverage. `Review artifacts posted` appears in `## Acceptance Criteria` with no corresponding test. `§4 flow map documented in plan + verified by test` is mapped only to documentation, but no test name verifies flow constraints against implementation behavior. `Titles 30 + 33 ingested end-to-end with ≥1000 sections each` is covered only by recorded-fixture count tests, which does not verify live ingestion or mount writes.
- [P1] The plan asserts operating-model §4 compliance without proving that the proposed design avoids forbidden durable-store behavior. In `## Operating-Model Flow Map`, `L1 text → L2 registry` and `L2 registry → L3 wiki overview page` are declared allowed, but there is no evidence from the operating model text that `cfr-registry.yaml` is an allowed L2 index artifact for this use, nor any enforcement test that prevents accidental L3↔L5 or L5-as-store regressions.
- [P1] Frontmatter authority is underspecified for new wiki pages. `## Cross-Machine Tier Assignment` and `## Artifact Map` create `knowledge/wikis/regulatory/CLAUDE.md` and overview pages, and `## Identity Contract` discusses `doc_key`, but the plan never states the exact baseline-floor frontmatter fields for each new page beyond a test name. That is not enough to verify §8.1 compliance for created wiki content.
- [P2] The checkpoint design may not be executable as written across machines. `## Cross-Machine Tier Assignment` makes `/mnt/ace/CFR/.checkpoints/title-XX.yaml` authoritative, while `## Risks and Open Questions` says cron runs on `dev-primary` and resume may happen on machine B. The plan lacks any dependency or preflight check for shared-mount consistency, permissions, clock skew, or concurrent writers, so the cross-machine resume claim is risky.
- [P2] The threat model is incomplete for paths and external writes. `## Threat Model` covers path sanitization and API failures, but the plan modifies `config/scheduled-tasks/schedule-tasks.yaml` and writes to `/mnt/ace/CFR/` without addressing concurrent cron/manual runs, symlink attacks in the mount tree, or secrets/config provenance for the scheduler path.
- [P2] Scope is not fully single-purpose. `## Deliverable`, `## Files to Change`, and `## Acceptance Criteria` mix ingestion, registry design, wiki-domain creation, resume/checkpointing, and scheduler wiring. That is at least four concerns in one issue, which increases blast radius and weakens the claim that the v2 scope reduction solved scope creep.
- [P2] The pseudocode in `## Pseudocode` still has a logic hole: when `prior.doc_key == doc_key`, it `continue`s before `atomic_write_l1(...)` and `update_checkpoint(...)`. If L1 is missing but registry already contains the current hash, the earlier desync check only handles the `already_completed(...)` path, not the `prior exists and hash matches` path, leaving a storage-registry inconsistency unresolved.

### Suggestions
- Attach concrete evidence for every claimed live verification: repo path existence, issue status snapshots, and any registry/domain existence checks. If evidence cannot be attached, downgrade the claims from `confirmed/live-verified` to `to verify during implementation`.
- Replace the `Distinct sources: 9` claim with a table of at least three specific sources, each with a quoted finding and why it matters to this plan.
- Add an explicit AC-to-test row for `Review artifacts posted`, and either remove `§4 flow map ... verified by test` from acceptance criteria or add a real enforcement test that validates no forbidden persistence/flow behavior occurs in code.
- State the exact required frontmatter schema for every new regulatory wiki page in the plan body, including at minimum `title`, `last_updated`, and `doc_key`, instead of relying on a test name as the only specification.
- Add concurrency and mount-safety requirements: single-writer lockfile, symlink-safe path handling, mount reachability preflight, and behavior for concurrent cron/manual invocations across machines.
- Split scheduler wiring and wiki-domain creation into follow-on issues unless they are strictly required for the first ingestion delivery; keep this issue focused on ingest + registry + resume if you want a single-purpose deliverable.
- Fix the pseudocode so that registry/L1 desync is reconciled even when an existing registry entry has the same `doc_key`, and add a dedicated test for `registry-present but L1-missing` recovery.
- Clarify whether `cfr-registry.yaml` is a new authoritative registry or an index derivative, then cite the operating-model rule that permits that exact role; otherwise the §4 compliance claim should be downgraded.
