## Findings (by severity)

### MAJOR

- **M1 — Pseudocode's `diff_report` shape does not match what `semantic_validate.py` actually emits (plan §Pseudocode, lines 119–168).** The pseudocode asserts on `counts["C1"] … counts["C6"]` per section. But `to_json()` at `scripts/semantic_validate.py:1206–1258` emits a dict shaped `{sections: {name: {diffs: [...], missing_in_mod: [...], extra_in_mod: [...], objects: {...}, categories: {...}}, ...}, summary: {...}}` where each `PropertyDiff` has a `significance` field drawn from the `Significance` enum at line 101: `match / cosmetic / minor / significant / type_mismatch / missing / extra`. **The C1..C6 taxonomy is a human classification overlay defined in `SEMANTIC_DIFF_TAXONOMY.md`, not a bucket the tool emits.** The taxonomy doc itself acknowledges this explicitly in lines 256–262 with a "Significance-to-Category" mapping table that is many-to-many and requires judgement (e.g. `MISSING → C1 or C3 or C6 depending on property family`). Asserting `counts["C5"] == []` on the live validator output will fail at `KeyError`. The plan's Risk 2 gestures at "scripts/semantic_validate.py output format for JSON emission has not been verified" and proposes adding a `--json` flag — but `--json` already exists (line 1951), and the gap is not the serialisation format but the taxonomy layer that doesn't exist in the tool at all. This is a load-bearing design defect: every acceptance criterion of the form "zero C5 / zero C6 / every C3 documented / every C4 resolved" is unreachable as written. Resolution requires either (a) authoring a classifier that maps `PropertyDiff.significance + property key` to C1..C6 (new work the plan does not mention), or (b) restating the acceptance criteria in terms of the tool's native significance labels and then citing the taxonomy mapping table in the readiness doc.

- **M2 — `_run_semantic_validator(generated_master, monolithic)` signature is wrong (plan §Pseudocode, line 131).** The pseudocode passes a single `master.yml` path as the modular argument. But `load_modular(modular_dir)` at `scripts/semantic_validate.py:304–334` expects a **directory** that either contains an `includes/` subdir or yml files directly; it iterates `modular_dir.glob("*.yml")`. The pseudocode-computed `_generate_native_from_spec(tmp_path)` helper returns `tmp_path / "master.yml"` (line 129) — if that is then passed as the modular argument, `load_modular` will treat a file as a dir and produce garbage (or fail). The correct argument is `tmp_path` itself (which contains `master.yml`, `includes/`, `inputs/`). This is a mechanical plan defect that implementation will trip over on first run.

- **M3 — L2 claim is unsubstantiated by the proposed tests (plan §TDD Test List line 198; §Risks line 244).** Taxonomy doc line 275: "L2 | Behaviorally equivalent | Statics/dynamics **results** match within benchmark tolerance (no C6 diffs)". L2 requires running statics/dynamics on both models and comparing results. The plan's tests do only (a) generator-runs-without-error, (b) yaml-strict-loads, (c) `OrcFxAPI.Model().LoadData()` — which is **L1 loadability** per plan line 196 itself — and (d) static YAML-level diff classification. No statics/dynamics comparison. The plan's §Risks "Open" paragraph (line 244) admits "A full statics/dynamics comparison ... is NOT in scope" and then the acceptance criteria (line 215) and roadmap-promotion rule (line 179) treat zero-C5-and-zero-C6 on the static diff as sufficient to promote turret-moored FPSO to "Ready now" under an "L2 repo convention". Two problems: (i) there is no repo-wide rule that "zero C5/C6 on static YAML diff" implies L2 — that's a claim the plan invents; (ii) the taxonomy doc explicitly says L2 requires results matching, so promoting the roadmap line on this basis would over-claim. The plan needs to either pin the claim to L1 (loadability) and explicitly defer L2 to a follow-up that runs statics, or add a statics-comparison test to the deliverable set (which changes complexity and scope).

- **M4 — `GROUPS_POLICY` symbol is fabricated (plan §Pseudocode line 156).** The line `documented = _SKIP_GENERAL_KEYS | _SKIP_OBJECT_KEYS | _WIND_SPEED_DORMANT | GROUPS_POLICY` imports four symbols. Verified: `_SKIP_GENERAL_KEYS` and `_SKIP_OBJECT_KEYS` are module-level in `generic_builder.py`; `_WIND_SPEED_DORMANT` is a **class attribute** of `EnvironmentBuilder` (not directly importable the way pseudocode suggests); `GROUPS_POLICY` **does not exist anywhere in the repo**. The intended policy is the `should_generate()` predicate in `GroupsBuilder` that suppresses the Groups section for generic specs. A plan that names a non-existent importable symbol is a factually false claim and a hazard for the executor — who will either stub an empty set (masking real omissions) or waste a cycle deriving the correct source. Fix: either create a constant in the builders package during execution (scope creep) or rewrite the pseudocode to compute the set via introspection (e.g. derive from `GroupsBuilder(spec).should_generate()` result plus a documented justification list in the readiness doc).

### MINOR

On the very first commit the JSON is whatever the live run produced; the test then proves only "the run is deterministic", not "the diff is correct". The reviewer hypothesis flags this; the plan's Risks section does not. The correct framing is: the first baseline is validated by the adversarial review cycle on this plan plus a human inspection of the classified diff during implementation — not by the test itself. That framing belongs in the plan's Risks or in the readiness doc template; currently absent.

Charitable reading: the table describes the downstream execution phase, not the planning agent's own write set. Literal reading: contradiction. The plan should explicitly tag each "Files to Change" row with the phase that produces it (planning vs execution) to avoid the executor interpreting the planning-only clause as forbidding the central deliverables.

## Verdict justification

MAJOR: four independent defects (M1–M4) would each cause the executor to write failing, incorrect, or semantically meaningless code on first attempt. M1 is the largest — the plan's central assertion mechanism (C1..C6 bucket equality) cannot be driven from the validator's actual output shape, because the C1..C6 taxonomy is a manual overlay, not a tool output. M2 is a mechanical signature error that breaks the very first call site. M3 is a category over-claim that would mislead roadmap promotion even if M1/M2/M4 were fixed. M4 names a non-existent importable. The plan's Resource Intelligence evidence-gathering is strong on file existence but did not verify any of the semantic contracts it depends on — which is exactly the failure mode the `feedback_plan_past_tense_artifact_claims.md` memory was written to prevent.

MINOR findings are mostly drafting-hygiene issues (m4/m5 expose that the plan's Risks section was written without reading the file being mitigated; m2 is a scope statement that can be resolved by tagging phases). These do not individually block, but together with the MAJORs they indicate the plan should be revised and re-reviewed before moving to `status:plan-review`.

The plan author should:
1. Read `scripts/semantic_validate.py` end-to-end and re-draft the pseudocode against the real `to_json()` schema.
2. Choose between (a) building a C1..C6 classifier module as part of this deliverable (raises complexity, but honest) or (b) restating assertions in terms of `Significance.SIGNIFICANT`, `Significance.TYPE_MISMATCH`, and property-family skip-lists (keeps T2 but honest).
3. Demote the claim from L2 to L1-plus-static-diff, or add a statics-comparison test and raise complexity.
4. Replace `GROUPS_POLICY` and the class-attribute references with a concrete derivation path.
5. Add a "first baseline validation" paragraph to Risks.
6. Reconcile the "planning-only worker" clause with the deliverables table by phase-tagging.
