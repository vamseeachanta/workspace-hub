## Findings
1. The retrieval pass is below the repo’s required issue-class bundle. Issue [#2487](https://github.com/vamseeachanta/workspace-hub/issues/2487) is labeled `cat:data-pipeline` and `cat:documentation`, and the plan template says multi-class issues must use the union of bundles from `docs/plans/_template-issue-plan.md`. That bundle requires at minimum `registry.yaml`, pipeline config, `resource-intelligence-maturity.yaml`, governance docs in the target dir, `#2209`, and knowledge/intelligence parent docs such as `#2205` and `#2096`. Those sources exist at [data/document-index/registry.yaml](https://github.com/vamseeachanta/workspace-hub/blob/main/data/document-index/registry.yaml), [data/document-index/resource-intelligence-maturity.yaml](https://github.com/vamseeachanta/workspace-hub/blob/main/data/document-index/resource-intelligence-maturity.yaml), [docs/document-intelligence/llm-wiki-resource-doc-intelligence-operating-model.md](https://github.com/vamseeachanta/workspace-hub/blob/main/docs/document-intelligence/llm-wiki-resource-doc-intelligence-operating-model.md), [docs/plans/2026-04-13-issue-2096-intelligence-accessibility-map.md](https://github.com/vamseeachanta/workspace-hub/blob/main/docs/plans/2026-04-13-issue-2096-intelligence-accessibility-map.md), and [docs/plans/2026-04-16-issue-2209-durable-vs-transient-knowledge-boundary.md](https://github.com/vamseeachanta/workspace-hub/blob/main/docs/plans/2026-04-16-issue-2209-durable-vs-transient-knowledge-boundary.md), but the plan’s `Resource Intelligence Summary` does not cite them. That makes the plan’s intel contract insufficient before approval.
2. The canonical machine-readable contract is underspecified. The plan says it will create `config/knowledge/inventory-readiness.yaml`, but `Deliverable`, `Pseudocode`, `Files to Change`, and `Acceptance Criteria` never pin the top-level shape, key names, source-of-truth precedence between YAML and Markdown, nullability/omission rules, issue-reference encoding, or first-run/no-evidence behavior. The strongest schema statement is the pseudocode line `require every row to have source_id, stage statuses, evidence, owning_issue or gap_reason, provider_lane, next_action`, which is not enough for a durable control-plane artifact. That conflicts with `.claude/skills/software-development/approval-stage-plan-hygiene/SKILL.md` rule 4, which explicitly requires the full machine-checkable contract to be pinned in the plan.
3. The plan embeds stale review-process state instead of an implementation contract. The header advertises `Review artifacts: scripts/review/results/2026-04-24-plan-2487-{claude,codex,gemini}.md`, `Acceptance Criteria` includes `Plan-review gate passes...`, and `Adversarial Review Summary` is entirely `pending`. GitHub code search returned no matching `2026-04-24-plan-2487-*` artifacts. That violates `.claude/skills/software-development/approval-stage-plan-hygiene/SKILL.md` rules 1-3: do not cite empty review artifacts, do not keep stale review-state narration in the plan, and do not put workflow-state transitions in acceptance criteria.
4. The TDD contract is conditional enough to permit implementation without a committed test surface. `AGENTS.md` says `TDD mandatory — tests before implementation; no exceptions`, but this plan’s `TDD Test List` is prefaced with `If this issue includes the generator, write tests first` and then says `If plan review scopes this issue as docs/config only, validate with deterministic YAML/schema checks instead of adding a Python generator.` No test file, validator path, or failing-first command is specified for that docs/config branch. For a plan whose primary deliverable is a new machine-readable YAML control-plane artifact, that is a gap, not a detail.
