## Findings

### M1 — `provider_explicit` triggers `ai:` label writes in `--apply`; lane-derived explicitness materializes permanent labels (MINOR)

`scripts/dispatch/route.py:372`: `if p["provider_explicit"] and not any(n.startswith("ai:") for n in existing):` — in `--apply` mode, an explicit provider gets an `ai:<provider>` label written to the issue. Under the plan, `lane:codex` makes the provider explicit, so the first `--apply` run will write `ai:codex` onto every lane-labeled card it routes. Consequence: the dispatch-time `ai:` label then permanently outranks the plan-time `lane:` label; later relabeling `lane:` has no routing effect until the `ai:` label is removed.

This is arguably the *intended* materialization (lane = preference, ai = assignment), but the plan text does not state it, and the reclassification guidance added to the planning skill ("relabel the issue if scope changed") would silently stop working after first dispatch. **Required:** plan must (a) document this materialization explicitly in Risks, and (b) extend the skill text: when reclassifying a lane after dispatch, also remove the stale `ai:` label.

### M2 — lane-over-rule precedence is agent-set, not human-set (MINOR)

`routing-rules.yaml:66`: "A human-set ai:/machine: label on the issue always overrides." The 2026-06-10 lane backfill was agent-classified (codex), not human-set, so granting lane: rule-overriding power slightly extends the documented authority model. Mitigation is acceptable (plan-time relabeling is the correction surface; future lanes are assigned during planning, a human-gated stage), but the plan should state this rationale in the route.py comment so the next reader doesn't assume lane labels are human-set.

### M3 — `apply_wip` consumes resolved provider downstream; verify no cap regression in tests (MINOR)

`route.py:214`: `apply_wip` enforces `auto_routable` and pool caps on the resolved provider. The `{codex, claude}` lane whitelist keeps lane from ever resolving a non-auto-routable provider, and `codex_pool` caps apply unchanged to lane-resolved codex cards. No defect, but the new test file should include one assertion that a lane-resolved provider flows through `apply_wip` identically to a rule-resolved one (cap accounting does not special-case explicitness).
