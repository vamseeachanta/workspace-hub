## Findings

### 1. MAJOR — TDD row 7's RED claim is fabricated. The precedence route it tests does not exist, and the precedence hazard that *does* exist is left unguarded and ordered the wrong way by the design.

**Evidence:** `scripts/cron/cron_line_model.py:130-150`.

```python
def classify_line_detail(line, catalog_commands=None, external_fingerprints=None, ...):
    if _is_ignore_line(line): ...
    if ownership_context is not None:
        identity = ownership_context.get("line_identities", {}).get(line)
        if identity:
            return {"line": line, "class": "cataloged", ...}
        external_fingerprints = ownership_context.get("preservation_fingerprints", [])
    return _classify_preserved(line, external_fingerprints)
```

`catalog_commands` is **never read**. There is no command-token, substring, or fuzzy catalog route in the classifier at all. The plan's row-7 fixture — *"Preserved llm-wiki line plus a deliberately colliding catalog-command token"* — therefore cannot change the outcome. Executed:

```
a) no collision                : preserved_external
b) colliding catalog_commands  : preserved_external   (catalog_commands=['scripts/ingest/cron_ingest.sh', <the full line>])
c) ownership + collision       : preserved_external
```

The row is **GREEN today with zero implementation**, and will remain green after any implementation this plan describes, because the plan explicitly forbids adding a non-exact route (AC #8). It is an unfalsifiable test.

**The real hazard is the opposite ordering.** Exact identity is checked **before** preservation. Injecting the llm-wiki line into `line_identities`:

```
d) exact-identity collision    : cataloged   <-- preservation LOSES
```

That is reachable in production: `harness-state-classes.yaml` `legacy_exact_lines` rows are hand-written exact line texts (3 rows today: `session-curation`, `equality-matrix-refresh`, `notification-purge`). A legacy row whose `line:` matches another repo's live cron line converts `preserved_external` → `cataloged` → deleted by rebuild. `cron_identity._bind_identity` (`cron_identity.py:228-243`) only raises on collisions between two *different catalog task ids*; it performs **no** collision check against `preservation_fingerprints` at all.

The plan's design sentence — *"Preservation fingerprints will be checked before any future non-exact identity branch"* — leaves the **exact** branch ahead of preservation, i.e. it explicitly does not fix (d). r2-on-3708's note that "preservation is checked LAST with no precedence test" is therefore **not** fixed by this plan; it is restated and then tested against a route that does not exist.

**Failure scenario:** an operator adds a `legacy_exact_lines` variant transcribed from a live crontab that happens to be the llm-wiki `cron_ingest.sh` line (or any `preserved_external`/`preserved_local` line). `plan_cutover` classifies it `cataloged`, `_rebuild_lines` drops it from `after`, the render does not re-emit it (it is not a selected task line — it is a legacy variant of a *different* task), and another repo's cron is deleted with no abort, no uncataloged entry, and — under the plan's own pseudocode — **no intent-report acknowledgement**, because cataloged-absent lines are exempt (Finding 4).

**Required revision:** Delete row 7 as written. Replace with (a) a precedence test that asserts `classify_line_detail` returns `preserved_external` when a line matches BOTH a `preservation_fingerprints` entry and a `line_identities` entry, and (b) a `build_ownership_context` guard test asserting that binding an exact identity to a line that matches any preservation fingerprint raises/collides. Either reorder preservation ahead of exact identity in `classify_line_detail` (verified compatible with `derive_cron_classifier_branches` — see Finding 5) or add the bind-time collision guard. State plainly in Resource Intelligence that `catalog_commands` is a dead parameter so no future plan re-derives a fictional command route.

### 2. MAJOR — The "one shared classification path" unifies the loop, not the classifier. Two independent context builders remain, and they are already divergent today. The parity test as specified cannot detect it.

**Evidence:** the classifier's behaviour is determined by `ownership_context` + `external_fingerprints`, which are built by **two separate ~40-line paths**:

- `scripts/cron/cron-audit.py:266-294` `build_audit_context()`
- `scripts/cron/cron_apply.py:291-297` `_load_cutover_context()` + `:157-180` `_selection_context()`

Executed side by side for `dev-primary`:

```
catalog_commands same        : True
selected_task_ids same       : True
ownership line_identities same: True
audit external_fingerprints  : 10 entries
ownership preservation_fingerprints: 11 entries
ext_fp == pres_fp            : False      <-- ALREADY DIVERGENT
```

The two preservation sets differ **today** (the ownership set additionally carries catalog `installed_fingerprint` rows). The divergence is invisible only because `classify_line_detail` **discards** the passed `external_fingerprints` whenever `ownership_context` is not `None` (`cron_line_model.py:149`). A dead parameter is the only thing making the two paths agree.

The plan's shared artifact is `classify_crontab_lines(current_text, classifier)` — it takes the *classifier closure* as an argument. It therefore unifies the iteration and leaves the two context builders, both dead parameters, and the divergence untouched. The issue's own requirement is *"Make the audit and the transaction share one classification path so they cannot disagree. Two independent classifiers over the same input is the root shape of this bug."* Sharing a `for` loop does not satisfy that.

Row 3's test — *"Audit JSON `lines` and transaction preflight records will match by line, location, class, reason, and task id"* — feeds a single fixture context to both consumers, so it passes by construction and can never detect builder divergence. It is a tautology.

**Failure scenario:** a future change adds a preservation source to `build_ownership_context` (or removes one from `load_external_fingerprints`). `cron-audit.py` reports a line `uncataloged` and exits 1; `plan_cutover`, called with `ownership_context`, reports it `preserved_external` and proceeds. The operator sees the advisory fail and the destructive path pass — the exact inversion #3709 exists to close, reproduced one layer up.

**Required revision:** Move the unification seam to context construction. Add a single `build_classification_context(catalog, registry, state_classes, machine_id)` consumed by `cron-audit.py`, `cron_apply.py`, and any test harness, and make `plan_cutover`/`audit_crontab` take that context (not a caller-supplied closure). Delete the dead `catalog_commands` and `external_fingerprints` parameters rather than threading them into the new API. Replace row 3 with a test that calls the two **production** entry points (`build_audit_context()` and `_load_cutover_context()`) for the same machine id and asserts byte-equality of every classification input, plus a mutation test that perturbs one builder and asserts the parity test fails.

### 3. MAJOR — Routing `cron-audit.py` through `parse_crontab` converts the fail-closed audit into a fail-open one for malformed crontabs.

**Evidence:** `cron-audit.audit_crontab` today iterates `crontab_text.split("\n")` (`cron-audit.py:237`) — it never parses markers, so a structurally broken crontab is still fully classified. The plan's pseudocode returns early on parse error:

```python
def classify_crontab_lines(current_text, classify_detail):
    parsed = parse_crontab(current_text)
    if parsed["error"]:
        return {"parsed": parsed, "records": [], "error": parsed["error"]}
```

`parse_crontab` errors on `multiple begin markers found`, `multiple end markers found`, `unbalanced markers`, and `end marker appears before begin marker` (`cron_line_model.py:51-58`). Executed against a crontab with two managed blocks and three unknown live lines:

```
parse error   : multiple begin markers found
TODAY  cron-audit uncataloged=3 -> exit 1   (fail-closed)
PROPOSED shared path: records=0 -> uncataloged=0 -> exit 0   (fail-OPEN)
```

`cron-audit.main()` returns `1 if audit["uncataloged"] else 0` (`cron-audit.py:375`). With zero records it returns **0 — pass**. The plan's pseudocode handles `classified["error"]` in `plan_cutover` (`return abort(...)`) and says nothing whatsoever about the audit consumer.

A duplicated/unbalanced managed block is not a theoretical state: it is precisely what a half-completed or interrupted `setup-cron.sh --replace` leaves behind, and re-enabling `--replace` is the downstream goal (#3708/#3707). The audit is the operator's pre-cutover gate; making it report clean on the one crontab shape that most needs blocking is a direct violation of `.claude/rules/scheduler-mutation-safety.md:8` ("Unsupported indirection, unknown authority, incomplete operations … fail closed").

**Required revision:** Add an explicit `Files to Change` reason and a RED test: `cron-audit.main()` must exit non-zero and print the parse error when `classify_crontab_lines` returns an error, and must never report `ok: true` / `uncataloged: []` on a parse error. Add the same assertion to `plan_cutover` (its abort is already in the pseudocode, but there is no test row for it). Add both to Acceptance Criteria.

### 4. MAJOR — The intent report's acknowledgement design contradicts its own acceptance criterion, and the bypass is a config file that already exists.

**Evidence:** the plan states two incompatible rules.

Acceptance Criteria: *"Any line in baseline `A` and absent from planned `C` will appear in an intent report and **will require explicit acknowledgement** before apply can proceed."*

Pseudocode `build_cutover_intent`: *"require an explicit acknowledgment for every absent **preserved_external or unknown** line"*, and Recommended Design: *"Any absent line **without a catalog-owned exact identity** and explicit acknowledgment token will block."*

Under the pseudocode, a line that classifies `cataloged` and is absent from `C` blocks nothing and needs no acknowledgement. Verified against the captured ace1 crontab: of the 51 absent non-ignore occurrences, **3 classify `cataloged`** and would pass through silently:

```
ABSENT[1] cataloged :: 30 4 * * * cd /mnt/local-analysis/workspace-hub && find logs/notifications/ … -delete …
ABSENT[1] cataloged :: 47 */6 * * * … bash scripts/curation/curate-session-memory.sh …
ABSENT[1] cataloged :: 0 5 * * 0 … catalog_delta.py …
ABSENT[1] cataloged :: 50 */6 * * * … bash scripts/readiness/equality-matrix-cron.sh >> …/equality-refresh-…
```

The acknowledgement bypass the review brief asks for is not a CLI flag — **it is `config/workstations/harness-state-classes.yaml`.** Adding a `legacy_exact_lines` row converts an arbitrary live line into `cataloged`, which (a) exempts it from the uncataloged abort, (b) exempts it from intent-report acknowledgement under the pseudocode, and (c) causes `_rebuild_lines` to delete it. It requires no interaction, no flag, and no operator present — a YAML edit merged in any PR is sufficient. Three such rows already exist. The plan's mitigation is a prose promise ("This issue will not add new legacy rows"), not a mechanism.

Consequently the Deliverable's claim — *"This will make silent deletion impossible by construction"* — is false as designed. The construction has a documented, pre-existing hole.

**Required revision:** Resolve the contradiction in favour of the Acceptance Criterion: **every** absent occurrence, including `cataloged` and `ignore`, must be enumerated in the intent report. Then either (a) close #3709 with no acknowledgement path at all (abort on any absent non-`cataloged` occurrence; report `cataloged` absences and require the report to be non-empty-safe), or (b) specify the acknowledgement token as an occurrence-scoped digest over `(baseline sha256, location, index, exact line)` supplied on the command line only, with an explicit test that no environment variable, config key, or catalog/legacy classification can satisfy it. Add a RED test that a `legacy_exact_lines` row added for a line that is *not* a selected-task variant does not silently authorise its deletion. r1's own Finding 1 asked r2 to force this choice; it must be made before approval, not deferred to the implementer.
