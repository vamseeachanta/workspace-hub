## Findings
1. Plan `Pseudocode > Detection` skips entirely when `.git/MERGE_MSG`, `.git/REBASE_HEAD`, or `.git/CHERRY_PICK_HEAD` exists. That disables the hook during the exact commit where a user resolves a merge and may accidentally stage unresolved markers. This contradicts the deliverable claim that the hook “rejects commits staging files containing unresolved git merge-conflict markers” and issue `#2722`’s failure mode that markers reached `main` through commit/push flow.

2. Plan `Pseudocode > Detection` checks the forensic whitelist with `grep -q "<!-- CONFLICT_MARKER_FORENSIC_OK -->" "$file"` against the working tree, while marker detection is supposed to inspect the staged blob via `git show :"$file"`. This allows staged marker content to be bypassed by an unstaged whitelist edit in the working tree, violating Acceptance Criteria “Stage-aware” and “Forensic whitelist ... works”.

3. Plan `Pseudocode > Cross-repo installer` creates a minimal pre-commit stub when missing, then inserts a snippet that uses `$REPO_ROOT` without specifying that the stub defines `REPO_ROOT`. In repos without an existing hook prologue, the installed check may be a no-op because `"$REPO_ROOT/scripts/enforcement/check-no-conflict-markers.sh"` resolves incorrectly.

4. Plan `Pseudocode > Cross-repo installer` says repo discovery reads `scripts/agents/tier1-repos.yaml -> .repos[]`, but the plan does not define a shell-safe YAML parser dependency, fallback parser, manifest schema, or bootstrap-machine dependency check. This is risky because `scripts/memory/bootstrap-machine.sh` is intended to run on new machines, and `docs/plans/README.md` requires harness/infra plans to inspect control-plane dependencies.

5. Plan `Pseudocode > Drift check` says missing vendored copies only `warn "missing in $repo — run install..."` and `continue`, then can still print `OK: all vendored copies in sync`. Missing vendored copies mean a tier-1 repo is unprotected, so this must fail, not warn.

6. Plan `Deliverable` and `Files to Change` vendor `scripts/enforcement/check-no-conflict-markers.sh` into sibling repos, but Acceptance Criteria only validates local installation on two sibling repos and does not require committing/pushing the vendored copies or preserving/handling dirty worktrees in those sibling repos. That leaves the “all 7 tier-1 repos” propagation non-durable.

7. Plan `Resource Intelligence Summary > Standards` says “Not applicable”, but issue `#2722` is labeled `cat:harness`, and `docs/plans/README.md` says Harness/Infra issues require `CONTROL_PLANE_CONTRACT.md`, `config/agents/` settings, and `.claude/rules/`. The plan read `.claude/rules/patterns.md` but omits the control-plane and provider-adapter implications that matter for cross-repo hook distribution.

8. Plan `Acceptance Criteria` says “T2 → 3-provider review required per `feedback_always_adversarial_review_scale_depth`”, but the cited `feedback_*` memory is not a tracked source verified in this review. The tracked policy `docs/standards/AI_REVIEW_ROUTING_POLICY.md` supports default three-agent review; the plan should cite that durable policy instead of an unverified feedback key.
