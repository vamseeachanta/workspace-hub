### Verdict: MAJOR

### Summary
The plan is well-scoped, evidence-rich, and treats the converter as a diagnostic-only target with clear non-goals. However, several rubric and acceptance-criteria details have internal arithmetic and threshold inconsistencies that will trip the test run on day one, and a few methodological gaps (oracle authorship, fixture provenance enforcement, Jaccard semantics) need tightening before implementation can proceed deterministically.

### Issues Found
- [P1] Acceptance-criteria parametrize math is off-by-20: the plan claims '13 structural tests + 120 parametrized [slug] cases' = 125, but 13 + 120 = 133, and 6 dimensions × 20 topics = 120 parametrized cases (correct), while structural tests in the TDD list count 7 (`test_sample_manifest_loads`, `_stratification`, `_fixture_files_exist`, `test_html_to_markdown_import`, `test_aggregate_rubric_meets_thresholds`, `test_no_network_access`, `test_report_artifact_written`), not 13. The collected-item assertion will fail immediately and there is no agreed denominator.
- [P1] Per-topic + aggregate thresholds are logically inconsistent: an aggregate mean of ≥0.95 cannot be guaranteed when per-topic floors sit at 0.80–0.90. With 20 topics scoring at the per-topic floor, the mean would be the floor itself (e.g., 0.80 for image alt-text), violating the 0.95 aggregate. Either the aggregates need to be reduced, the per-topic floors raised, or the relationship redefined (e.g., 'no more than N topics may sit at the per-topic floor').
- [P1] Stratification axes are over-constrained and may be infeasible: Axis 1 totals 12+5+3=20, Axis 2 totals 4+5+4+3+4=20, Axis 3 totals 6+8+6=20 — but the plan says these are 'orthogonal' and 'intersected.' A 3×5×3 = 45-cell joint distribution cannot be filled with 20 samples while honoring all three marginals exactly; the manifest validator at collection time will likely fail, or the constraints will need to be relaxed to 'marginal-only' (which the text does not say).
- [P2] Oracle markdown authorship is circular: the oracle is being written by humans reviewing the converter's own output (or the source HTML), and the rubric README only requires 'two-reviewer sign-off.' If the oracle is derived from the converter's current output, the test is a snapshot test, not a quality test — it will pass even when the converter is wrong. The plan should specify whether oracle is authored independently from raw HTML or derived-then-corrected, and how reviewers avoid anchoring on current output.
- [P2] Heading-preservation 'Jaccard + order penalty' is under-specified: the formula for combining Jaccard with the order penalty is not given, so two implementers will produce different scores from the same inputs. Same applies to 'tree-edit distance ... normalized' for list nesting (which normalization — by max(|a|,|b|) nodes? by sum?). Determinism is claimed but not provable without the formulas.
- [P2] `test_no_network_access` monkeypatches `urllib.request.urlopen`, but BeautifulSoup ingestion in `html_to_markdown` parses an in-memory string and does not itself fetch — the real network risk is in `fixtures_sampling.py` if it ever resolves URLs, or in any future helper. The test as written will pass trivially. Recommend asserting against `socket.socket` creation or using `pytest-socket --disable-socket` for stronger coverage.
- [P3] The plan asserts cross-review is 'currently blocked' but the acceptance criteria still require posting review artifacts to `scripts/review/results/`. Either the criterion should be marked deferred-conditional or the plan should not enter `status:plan-review` until reviews land, per the user's standing rule that approval gates must be revision-bound (project_issue_2460_approval_binding).
- [P3] Fixture provenance fields (URL + fetch timestamp + content SHA) are mentioned in the Risks section but not declared in the manifest schema. Without them in the YAML schema and the validator, drift detection is informal.

### Suggestions
- Re-derive the acceptance-criteria collected-item count: enumerate the 7 structural tests explicitly, confirm 6×20=120 parametrized cases, and assert exit-0 with exactly 127 collected items (or whatever the recount yields). Pin the number in the plan, not in prose.
- Resolve the per-topic vs aggregate inconsistency by either (a) raising per-topic floors to ≥ aggregate floors (simplest), or (b) replacing the aggregate-mean rule with a stricter 'at most K topics below 0.90 on any dimension' rule, which captures the intent ('hard topics may dip locally') without an arithmetic contradiction.
- Reframe stratification as marginal quotas only: state explicitly that the manifest must satisfy each axis's marginal counts independently, and that joint cells are not constrained. Have `fixtures_sampling.py` validate marginals only, and document this in the schema.
- Add an explicit oracle-authorship protocol: oracle markdown MUST be authored by reading the source HTML and the published target spec, NOT by lightly editing converter output. Require the fixture README to log each oracle's authorship method ('from-source' vs 'reviewed-from-output') so latent snapshot tests are visible.
- Specify the exact scoring formulas for heading preservation, list nesting, and any other composite metric (e.g., `score = 0.5*jaccard(set(actual), set(oracle)) + 0.5*kendall_tau(order)`); cite the normalization denominator for tree-edit distance. Without this, three implementations will produce three different verdicts.
- Replace the urlopen monkeypatch with `pytest-socket`'s `disable_socket` autouse fixture and assert that any attempted socket creation raises `SocketBlockedError`. This catches `requests`, `urllib3`, `httpx`, raw sockets — anything the converter or its imports might add later.
- Move the 'review artifacts posted' acceptance criterion under a 'Deferred / conditional' subsection with an explicit unblock condition (e.g., 'unblocks once cross-review infrastructure restored; plan does not enter status:plan-review until then'). Avoids the appearance of a self-approval shortcut.
- Extend `sample-manifest.yaml` schema with required fields per entry: `source_url`, `fetched_at` (ISO-8601), `html_sha256`, `oracle_authored_by`, `oracle_review_method`. Add a validator test that fails on any missing field.

### Questions for Author
- Where does the oracle markdown come from — is it independently authored from the source HTML against a published rendering spec, or is it the current converter output reviewed and lightly corrected? The rubric's meaning depends entirely on this choice.
- Are the three stratification axes meant to be marginal-only (each axis's counts honored independently) or joint (every product×category×complexity cell that lands in the manifest must be deliberate)? The 20-sample budget cannot satisfy both 3 and 5 and 3 levels jointly without some empty cells.
- Should `test_aggregate_rubric_meets_thresholds` use mean, median, or a percentile? The plan says 'mean' but means are vulnerable to a single outlier on a 20-sample base — is that desired sensitivity, or should it be median/p25?
- Is the 'two-reviewer sign-off' on each oracle file enforced at PR-review time only, or is there an in-repo mechanism (CODEOWNERS, a `oracle_reviewers:` field in the manifest) that the test/CI can verify?
- For dimension 2 (link resolution), should anchor-only links (`#section`), mailto, and external https URLs all be treated identically, or do you want separate sub-scores per link class? Lumping them may hide a regression where internal cross-references regress while external links remain intact.
- Is the gitignore entry for `.artifacts/` global to the repo or scoped to the test module path? The plan says 'add scripts/data/llm-wiki/tests/.artifacts/' — please confirm whether other modules generating similar artifacts should adopt the same pattern (suggesting a repo-wide `**/.artifacts/` rule).
