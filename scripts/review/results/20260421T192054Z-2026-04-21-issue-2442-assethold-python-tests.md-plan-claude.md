### Verdict: MAJOR

### Summary
The plan is thorough, well-evidenced, and the Wave 3 revisions close most of the earlier MAJOR findings — but the proposed P2 sibling-checkout mechanism (`actions/checkout@v4` with `path: ../assetutilities`) uses a `path` outside `$GITHUB_WORKSPACE`, which the action rejects. That is a first-order blocker for the "first green in 7 months" gate and needs to be redesigned before execution. A second concern is direct-to-main execution without a pre-merge CI exercise, which leaves no recovery path if P1 or P2 land badly.

### Issues Found
- [P1] actions/checkout@v4 does not permit a `path:` that escapes `$GITHUB_WORKSPACE`. The proposed `path: ../assetutilities` will be rejected at runtime (the action enforces that the resolved path stays within the workspace). The M1 mechanism as written will not unblock P2. The standard workaround is to give BOTH checkouts explicit workspace-relative paths (e.g., `path: assethold` for the main repo and `path: assetutilities` for the sibling) and then run subsequent steps with `working-directory: assethold` so that `../assetutilities` referenced by `pyproject.toml` resolves correctly. This restructuring cascades into `working-directory` on every install/test/lint step in the 3 dep-installing jobs and is not captured in the Files-to-Change table.
- [P1] The plan has never actually executed M1 end-to-end (it was derived at plan time), yet it is treated as mechanically deterministic. Given the checkout-path constraint above, the claim 'sibling-dep resolution is RESOLVED' is premature. Recommend a smoke validation on a throwaway branch before the direct-to-main P2 commit.
- [P2] Direct-to-main execution creates an irrecoverable state on failure. The plan says 'If P1 CI fails unexpectedly: investigate before P2 commit (do not bundle).' But a failed P1 push already lives on main. With no PR gate and no feature-branch CI pre-check, a bad commit becomes a revert-or-forward-fix scenario. Given this workflow has been red for 7 months, a brief feature-branch exercise costs little and prevents compounding the problem.
- [P2] quality-gate chain semantics across matrix cells are not verified. The acceptance criterion 'Full quality-gate job completes success on a push to main' depends on whether `test` `integration-tests` and `financial-data-tests` jobs require ALL matrix cells green or at least one. If `needs:` requires all cells (the GitHub default for matrix jobs is all must succeed), then P2's 'one smoke cell green' cannot transition to P3 without additional test-red remediation, which widens scope significantly. Plan flags this as an Open Question but ships an acceptance criterion that hinges on it.
- [P2] Cross-OS semantics of the sibling-checkout + `-e ../assetutilities` install on Windows/macOS runners are not validated. Plan defers matrix pruning to P3 but still expects matrix cells to pass in P3 success. Path separators, shell differences, and uv/Python setup on Windows runners may expose additional breakage.
- [P3] Local `python -c 'yaml.safe_load(...)'` pre-push gate verifies PyYAML can parse the file but does not fully match GitHub Actions' workflow schema validation. It is a necessary but not sufficient check. Worth a caveat.
- [P3] TDD assertion for sibling checkout uses `>= 1` but there should be exactly 3 (one per dep-installing job: test, integration-tests, financial-data-tests). Tighten to `== 3` to prevent accidental under-insertion.
- [P3] The claim that `requirements-consolidated.txt` is 'self-declared reference only' justifies not using it, but the plan does not propose deleting or relocating the file — leaving a misleading artifact in the repo that a future reader may still wire up. Consider adding a follow-on cleanup item.
- [P3] `ref: main` coupling is acknowledged as a risk with 'accepted for now' mitigation, but there is no explicit trigger (e.g., 'if assetutilities main breaks assethold CI twice in a month, pin to SHA'). The risk is open-ended.

### Suggestions
- Rework P2 checkout layout: give the main repo `path: assethold` and the sibling `path: assetutilities`, both inside `$GITHUB_WORKSPACE`. Then add `defaults.run.working-directory: assethold` (or set per-step `working-directory`) for the 3 dep-installing jobs so that `pyproject.toml`'s `{ path = '../assetutilities' }` resolves correctly. Document this layout change in Files-to-Change and Pseudocode; it is larger than a one-line checkout insert.
- Validate the P2 fix on a throwaway feature branch (push + CI) before direct-to-main. The assethold repo convention can still be 'merge to main' but a 1-run feature-branch dry run de-risks the never-green unblock. Capture the branch run URL in the acceptance log.
- Before committing P3 acceptance language, read the actual `needs:` clauses on `quality-gate` and confirm whether matrix cells are required-all or any-one. If required-all, either revise P2/P3 scope or plan for test-debt remediation.
- Tighten TDD assertion for sibling checkout from `>= 1` to `== 3` matching the 3 dep-installing jobs.
- Add a one-line follow-on item to mark `requirements-consolidated.txt` as archived (rename or move under `docs/legacy/`) so no future contributor wires it back up.
- Add a pinned-SHA mitigation trigger for the `ref: main` sibling coupling (e.g., 'If assetutilities main breaks assethold CI on 2 consecutive weeks, pin via commit SHA and open a refresh cadence issue').
- Note explicitly that PyYAML-level parse success is necessary but not sufficient vs GitHub's workflow schema; the CI startup gate is the authoritative check.

### Questions for Author
- Has the proposed `actions/checkout@v4 with path: ../assetutilities` been verified on a test branch? GitHub's checkout action rejects paths that resolve outside `$GITHUB_WORKSPACE`. If this has not been exercised live, the M1 mechanism likely needs the workspace-relative checkout layout described above.
- What does the `quality-gate` job's `needs:` array actually look like, and does it succeed when only one matrix cell in an upstream job passes, or does it require the entire matrix? This determines whether the P2→P3 transition is incremental or requires broader test-red remediation.
- Why direct-to-main rather than a short-lived feature branch for P1 and P2? Given 7 months of red CI and irreversible execution risk, is there a repo policy that prohibits branches for infra fixes, or is direct-to-main a convenience choice?
- If P1's push to main causes an unforeseen regression (e.g., a new parse error introduced by the `actions/upload-artifact@v4` API differences for artifact naming), what is the rollback plan? Revert commit? Forward-fix? The plan currently says 'investigate' but does not commit to a recovery path.
- Are the 7 fix sites (5 YAML/action + 2 DATABASE_URL) and 6 P2 sites all in jobs that still use the `ubuntu-latest` runner, or are any on macOS/Windows where path semantics differ? Line ranges given suggest a single file but multiple jobs — confirm per-OS assumption.
- Is there any token/permissions concern with checking out `vamseeachanta/assetutilities` via the default `GITHUB_TOKEN` from inside `vamseeachanta/assethold`? The plan verifies the repo is public (good), but cross-repo checkout with the default token still sometimes needs an explicit `token:` input or permissions grant depending on the repo's Actions settings.
