## Findings

1. **Shell→Python dependency mechanism is unspecified, and the two strategies in the plan do not compose (MAJOR).** The plan says the workflow will "set up Python and install PyYAML" (line 238) — i.e., CI uses system pip — while local/test commands use `UV_CACHE_DIR=… uv run --no-project --with pyyaml` (lines 239, 272–273). But the plan never states *how `scripts/skills/validate-skills.sh` itself invokes the Python helper*. AC line 274 requires `bash scripts/skills/validate-skills.sh` to pass, and the test design (plan lines 204–206) runs `subprocess → bash validate-skills.sh <tmp root>`. In both cases the shell spawns its own Python process; pytest's `uv run --with pyyaml` env does **not** propagate PyYAML into that subprocess. If the helper is invoked as bare `python3 helper.py`, it raises `ImportError` everywhere PyYAML isn't in the system interpreter — which is the exact "CI-doesn't-install-deps" failure class the r1 Claude/Codex reviews already flagged. The plan must pin a single end-to-end invocation (e.g., the shell script calls `uv run --no-project --with pyyaml python scripts/skills/validate_skills_frontmatter.py "$ROOT"` once), or the AC and the test are not implementable as written.

2. **The validator's correctness oracle (PyYAML `safe_load`) is never validated against the actual dispatch-time parser that produced the bug (MAJOR).** Issue #2981 originates from *Codex* failing to load the skill (plan line 38). The plan adopts PyYAML `safe_load` as ground truth (lines 132, 232) and even acknowledges the divergence risk abstractly (lines 310) but takes no step to confirm PyYAML's accept/reject set matches Codex's / Claude Code's skill loader. If the real loader is more lenient, the validator false-fails on the 128 `_internal/` and other files and turns CI red for files dispatch actually accepts; if stricter/different, it false-passes and the next dispatch break slips through. At minimum the plan should state PyYAML is a deliberate conservative proxy and cite *why* it's a safe lower bound for the loaders in question, rather than treating them as equivalent.

3. **A second stale soft-fail block is not covered by the Files-to-Change/AC (MINOR).** AC line 280 and the Files table (line 252) target only the `continue-on-error` comment (workflow lines 31–33). The "Generate skills summary" step (lines 45–46) *also* asserts "Validation runs in soft-fail mode" and "Files under `_diverged/` and `_internal/` may lack frontmatter." `_diverged/` has 0 files and all `_internal/` files parse (verified), so this text is doubly stale and will keep emitting a false CI summary even after the fix. The cleanup AC should name lines 45–46 explicitly.

4. **Soft-fail retention silently defeats the issue's enforcement intent (MINOR / decision-forcing).** The plan leaves `continue-on-error: true` removal as an open question (lines 280, 311) with a "keep soft-fail if code review finds CI risk" fallback. If soft-fail is retained, the workflow never blocks a malformed file — the validator becomes advisory and a future unquoted-colon description re-breaks review dispatch exactly as #2981 did. The plan should state plainly that retaining soft-fail leaves the root cause unguarded, so the reviewer/owner makes that trade-off knowingly rather than as a deferred "open question."

5. **Path-filter AC over-specifies relative to the validator's actual scan scope (MINOR).** AC line 279 requires the workflow `paths:` to include `scripts/skills/*.sh`, `scripts/skills/*.py`, the test file, and `.claude/skills/**/SKILL.md`. Either the workflow must actually invoke the test (currently out of scope), or listing the test file in `paths:` is cargo-cult and misleads a reader into thinking the test gates the PR. Clarify intent.
