### Verdict: MAJOR

### Summary
The plan establishes a clear normalization and gap detection strategy, but the pseudocode fails to enforce the 'degraded' run status contract for domain slug collisions. Additionally, the duplicate wiki key tracking logic fragments reports for keys with more than two duplicates, and there is a semantic error in the document boundary definitions.

### Issues Found
- Domain Slug Collision Degradation Ignored: Section 'Candidate Record Shape' states that domain slug 'collisions must be reported and mark the run degraded.' However, in the pseudocode, `normalize_source_records` does not return collision data or modify `run_status`, meaning a collision will silently fail to degrade the run.
- Duplicate Wiki Key Fragmentation Bug: In the pseudocode, when a wiki key is encountered for the third time (triggering `if key in invalid_wiki_doc_keys:`), it appends a new dictionary `{"doc_key": key, "pages": [page]}`. This fails to group it with the previously identified duplicates for that key, resulting in fragmented diagnostic reports for highly duplicated keys.
- Semantic Confusion in L3 Coverage Boundary: The 'L3 Coverage Boundary' section explicitly states 'The detector may treat only these artifacts as source-side candidates for wiki coverage' but then incorrectly includes 'non-structural wiki markdown' and 'wiki pages with canonical sha256:' (items 4 and 5) in the list. Wiki pages provide the coverage itself; they are not source candidates that require coverage.
- Unused Loaded Data: The pseudocode executes `reporting_data, missing_reporting = load_optional_inputs(...)` but completely discards `reporting_data`. If the intent is merely to identify missing files for reporting, parsing and loading the optional YAML payloads into memory is unnecessary and misleading given the plan claims they are a 'summary/reporting aid'.

### Suggestions
- Update `normalize_source_records` in the pseudocode to return domain slug collisions so they can be evaluated and trigger `run_status = "degraded"`.
- Change `duplicate_wiki_doc_keys` to a dictionary mapping `doc_key` to a list of page paths to correctly accumulate all duplicates for a single key.
- Revise the 'L3 Coverage Boundary' list to clearly separate source-side gap candidates (items 1-3) from coverage-providing artifacts (items 4-5).
- If optional reporting inputs are only used to check for absence, use a fast path-existence check rather than fully parsing their contents in `load_optional_inputs`. If aggregate counts are needed, ensure they are passed to the summary builder.

### Questions for Author

- Should the aggregate counts from `data/document-index/registry.yaml` be extracted and explicitly injected into `_summary.md`, or is its absence just recorded?
