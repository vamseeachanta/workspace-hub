## Findings
1. Plan misses the real batch submit allowlist. `scripts/solver/submit-batch.sh` contains an inline parser that rejects any `solver_type` outside `{'orcawave', 'orcaflex'}`; this is production code, not just a test helper. The plan’s “Files to Change” omits `scripts/solver/submit-batch.sh`, while “Resource Intelligence Summary” only calls out `tests/solver/test_batch_submission.py:132`. An AQWA batch manifest will still fail before reaching `submit-job.sh`.

2. `target_machine` is documented but not made functional. The plan’s “Deliverable” says `target_machine` will be added to `queue/job-schema.yaml`, and the TDD list expects `test_job_schema_target_machine_invalid_value_warns`; however `scripts/solver/validate_manifest.py` has no `target_machine` field in `JobEntry`, no manual validation branch for it, and no warning mechanism for unknown target hosts. The “Files to Change” only mentions `queue/job-schema.yaml` for this field, so the planned implementation cannot satisfy its own target-machine tests.

3. `target_machine` cannot route jobs under the current processor. `scripts/solver/process-queue.py` reads only `solver`, `input_file`, `export_excel`, and `description` inside `process_job()`, then processes every pending YAML found by the local host. The plan’s “GAP: No target_machine field ... needed to route AQWA jobs to the correct licensed Windows host” is not resolved by merely adding schema documentation; without processor-side skip/claim behavior, both Windows hosts can still process or fail the same AQWA job regardless of `target_machine`.

4. The AQWA command pseudocode likely cannot read the input file. The plan’s pseudocode says `subprocess.run(cmd, cwd=output_dir, ...)` and `cmd = [str(aqwa_exe), str(input_path.stem)]`, with a comment that AQWA reads `<stem>.dat` from cwd. But `scripts/solver/process-queue.py` resolves `input_path = REPO_ROOT / input_file` and creates a separate `output_dir = COMPLETED_DIR / job_name`; the plan never copies or links `input_path` into `output_dir`. A normal queued input under the repo will not be present in the AQWA cwd.

5. The executable-location plan contradicts its cited source. The plan’s “LLM Wiki pages consulted” says the Windows install path is typically `%ANSYS_INSTALL_DIR%\Framework\bin\Win64\` or sibling, but the pseudocode probes only `ansys/bin/winx64/ansys*l.exe`, `ansys*/bin/winx64/ansys*l.exe`, and broad default roots. If the cited source is correct, an env-var install at `Framework\bin\Win64` will be missed.

6. The plan treats an unverified invocation as implementable. “Risks and Open Questions” says “ANSYS AQWA command-line invocation shape” is open and “must be validated on-host before the first live job,” while `docs/ops/2026-05-04-multimachine-baseline-inventory.md` §8 defines the AQWA adapter follow-on as “live Windows Task Scheduler + ANSYS/AQWA command proof.” The acceptance criteria are all mock/local checks and do not require any on-host command proof, so the plan can pass while delivering an adapter that has never been validated against AQWA.

7. Acceptance criterion “No hardcoded absolute paths introduced” conflicts with the pseudocode. The plan’s `_locate_aqwa_exe()` explicitly includes `Path("C:/Program Files/ANSYS Inc")` and `Path("C:/ANSYS Inc")`, while acceptance says this is enforced by `scripts/enforcement/check-no-abs-paths.sh`. The plan does not verify whether Windows absolute probe paths are exempted by that script, so it may fail its own hard gate.

## Blockers
- Findings 1, 2, 3, 4, 5, 6, and 7 must be resolved before implementation.
