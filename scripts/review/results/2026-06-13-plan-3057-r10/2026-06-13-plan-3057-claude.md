## Findings

1. **The notification-purge "catalog-owned dedupe" provably trips `cron_apply.py`'s post-cutover preservation guard and rolls back on `--apply`.** The plan keeps the loose `preserved_local` fingerprint (Files-to-Change `harness-state-classes.yaml`, plan line 449) so the out-of-block live line classifies `preserved_external` (fingerprint is checked before catalog at `cron_transaction.py:193-198`). The plan then has `plan_cutover` **drop** that out-of-block line as a catalog-owned duplicate (pseudocode lines 405-407, acceptance line 508). But `run_cutover` runs a second, independent guard after writing — `cron_apply.py:190-193` computes `need = Counter(ln for ln in A.splitlines() if … classify_line(ln, cat_cmds, ext_fps) in ("preserved_external","ignore"))` and rolls back if any such line's multiplicity drops in `after` (194-199). The deduped notification-purge line classifies `preserved_external` in `A`, so it is in `need`; after dedupe it is gone from `after`; the rendered managed line is **not byte-identical** to it (the live form is `cd $WORKSPACE_HUB …` per plan evidence line 146, the managed form expands to `cd /mnt/local-analysis/workspace-hub …` — that expansion is the entire deliverable). Result: `after_counts[live_line] = 0 < 1` → `{"status":"rolled-back","reason":"preserved line lost: …"}`. The plan's `cron_apply.py` Files-to-Change row only says "use shared catalog keys for … the post-cutover preservation recheck" (line 446) — that addresses Claude-r9 Finding 5's key-threading, **not** this exemption. Nothing in the plan exempts a deliberately-deduped catalog-owned line from the `need` guard. The deliverable ("exactly one managed notification-purge line") is unreachable via `--apply` as specified.

2. **The `catalog_task_id` the dedupe depends on has no data path into `plan_cutover`.** The pseudocode (lines 405-407) distinguishes "preserved_local entries explicitly annotated with `catalog_task_id`" inside the cutover, but `plan_cutover(current, selected, roles, catalog_commands, external_fingerprints)` receives only bare fingerprint dicts: `cron_apply.py`'s `external_fingerprints()` returns `fp = entry.get("fingerprint")` and throws away every sibling key (so `catalog_task_id` is lost before `plan_cutover` ever sees it), and `classify_line` (191-199) returns a bare string, never *which* fingerprint matched. The plan asserts the cutover can tell a preserved line is catalog-owned and cross-reference it to a selected task, but the Files-to-Change rows for `cron_transaction.py` (line 447) and `cron_apply.py` (446) never call out changing the `external_fingerprints()` shape to retain `catalog_task_id`, nor the `plan_cutover` signature/logic to consume it. The mechanism is described at the contract level but has no specified plumbing.

3. **The notification-purge TDD test exercises only the dry-run path and so cannot catch Finding 1.** `test_notification_purge_catalog_owned_line_is_deduped_not_preserved_and_duplicated` (plan line 482) asserts "exactly one managed `notification-purge` line appears in `plan["new_text"]`" — i.e. it tests `plan_cutover` output directly. But `run_cutover` returns at `cron_apply.py:164-166` for dry-run **before** the post-cutover guard (188-199) ever runs; the rollback in Finding 1 only fires on `--apply`. So the specified test passes green while real `--apply` rolls back — the exact "validated against a fixture, not reality" trap the review prompt flags. The plan needs an apply-path (or `run_cutover`-level with `_write` shim) test that drives the preservation guard with the duplicated live forms.

4. **`cron-audit.py`'s fingerprint loader has the same `catalog_task_id`-discard gap, so the "shared parity" acceptance is unmet on the audit side.** Acceptance (plan line 507) requires `cron-audit.py` and `cron_apply.py` to classify the placeholder fallback lines identically. But `cron-audit.py:101-116` (`load_external_fingerprints`) merges `preserved_local` and keeps only `entry.get("fingerprint")` — identical discard to cron_apply. If the dedupe relies on `catalog_task_id` metadata, both loaders need the same change; the `cron-audit.py` Files-to-Change row (line 448) mentions only the shared key builder, not fingerprint-metadata retention. (MINOR relative to 1-2, but it undercuts the parity acceptance criterion.)

## Blockers

1. **Finding 1** — Specify how the catalog-owned dedupe avoids the `cron_apply.py:188-199` "preserved line lost" rollback. Either (a) make the deduped notification-purge line classify `cataloged` (which both drops it in `plan_cutover` *and* excludes it from the `need` guard, since `need` only counts `preserved_external`/`ignore`) instead of keeping it `preserved_external`, or (b) explicitly add a `need`-guard exemption for catalog-owned, selected, deduped lines and state it in the `cron_apply.py` Files-to-Change row. As written, the deliverable rolls back on `--apply`.

2. **Finding 2** — Name the concrete plumbing: which function retains `catalog_task_id` from `harness-state-classes.yaml`, what `plan_cutover` parameter carries it, and how the cutover cross-references it to `selected`. Put it in the Files-to-Change rows for `cron_transaction.py` and `cron_apply.py`, not just the pseudocode.

3. **Finding 3** — Add an apply-path test (not a `plan["new_text"]`-only test) that exercises the post-cutover preservation guard with both the `$WORKSPACE_HUB` and absolute-path live forms, asserting `status=applied` (not `rolled-back`) and exactly one managed line survives.

Finding 4 is MINOR and need not block, but should be folded in since it is the same root cause as Finding 2 on the audit path.
