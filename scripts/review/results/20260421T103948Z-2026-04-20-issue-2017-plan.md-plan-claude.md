### Verdict: APPROVE

### Summary
Plan v8 is a rigorous, well-fenced design contract that has survived seven rounds of tri-reviewer adversarial scrutiny. The v8 deltas directly close Codex v7's P1 (spam-path contradiction) and P2 ownership/artifact gaps, Claude v7's P2 stale review summary and revision-specific acceptance gates, and Gemini v7's P3 thundering-herd concern. Remaining observations are polish (missing test row, retry-idempotency clarification, xfail-import plumbing), not blockers.

### Issues Found
- [P2] `test_unknown_sender_fallback` is named in D3/D-section prose (v3 note) but is not present in the TDD Test List table — traceability gap between the contract and the test manifest.
- [P2] xfail tests will live in `tests/email/test_state_machine_contract.py` and must import from `scripts/email/queue_state.py`, which is owned by #2026 and therefore absent at #2017 commit. Pytest will raise ImportError at collection time (error, not xfail) unless the plan specifies either an import-shim/stub in #2017 or `pytest.importorskip` guards. This plumbing detail is load-bearing for the xfail-contract mechanism and is not addressed.
- [P2] Idempotency dedup key is `(account_id, thread_id, from_state, to_state, ts_utc)`. Retries that refresh `ts_utc` will bypass deduplication. Plan states 're-emitting the same transition is a no-op' but does not pin whether retries MUST preserve the original ts_utc or whether the dedup key should drop ts_utc.
- [P2] Sweep batch-append under a single log-lock (new in v8) is unbounded in batch size. At the documented ~18k entries/year / ~50 threads/day, a long-delayed sweep could hold the log lock for many eligible entries, starving inbound processing. No max-batch cap or max-hold-time is specified.
- [P3] D4 says quarterly review runs on 'same cadence as the existing daily-readiness cron `trig_019GWtRosbZ9rw1HxrGpsvy9`' — but that cron is daily and the review is quarterly. Same infrastructure, different cadence. Phrasing is misleading.
- [P3] `test_snapshot_rebuild_double_checked` names 'two threads' but `fcntl.LOCK_EX` is a process-level advisory lock and is a no-op between threads in the same process. The test harness (multiprocessing vs threading) should be named.
- [P3] Pseudocode's `apply_precedence` documents the empty-classifications safety-default branch as reachable, but no TDD test exercises it (e.g., `test_precedence_empty_classifications_safety_default`). Reachability is stated as justification; a test should prove it.
- [P3] File-size attestation '8051 bytes at v1 plan-draft time' for `email-routing.yaml` collides numerically with `batch-unsubscribe.sh` (8051 bytes). Coincidence is fine but worth a one-line disambiguating note so future readers don't mistake it for copy-paste error — and there is no `## Attested Evidence` block in this review payload to independently verify.

### Suggestions
- Add `test_unknown_sender_fallback` row to the TDD Test List table so the fallback behavior has a traceable contract line.
- Pin retry semantics for transition idempotency: either (a) require callers to preserve original `ts_utc` on retry, or (b) drop `ts_utc` from the dedup composite key and rely on `(account_id, thread_id, from_state, to_state)`. Document the choice in D1 concurrency contract.
- Specify a max-batch-size or chunking strategy for sweep's log-lock critical section (e.g., release-and-re-acquire every N transitions) and add a test that bounds worst-case hold time.
- Add `pytest.importorskip('scripts.email.queue_state')` (or an equivalent import shim in #2017) to the xfail contract tests, and document this in the TDD section so #2026 knows to remove the guard when the module lands.
- Rephrase the D4 cron reference as 'same trigger infrastructure, quarterly schedule' to eliminate the daily-vs-quarterly ambiguity.
- Add a `test_precedence_empty_classifications_safety_default` test to exercise the explicitly-reachable v8 branch documented in pseudocode.
- For `test_snapshot_rebuild_double_checked`, name the concurrency primitive — either `multiprocessing` (exercises fcntl) or a deliberately-mocked lock for single-process simulation — so implementers don't land a test that spuriously passes due to thread-local lock semantics.
- Consider renaming `docs/design/email-queue-state-schema.yaml` to `docs/design/email-queue-schemas.yaml` (plural) now that it owns queue-state, snapshot, meta, and learning-log schemas — reduces reader surprise at v8's scope expansion.

### Questions for Author
- Is `scripts/email/queue_state.py` stubbed in #2017 (so xfail tests can import without ImportError), or is there an importorskip guard that #2026 will remove? The plan doesn't say.
- For transition idempotency: on retry, does the caller preserve original ts_utc, or is ts_utc regenerated? This determines whether the current dedup key works as intended.
- What is the expected worst-case sweep batch size? At what point does 'hold log-lock once per run' become unacceptable latency for inbound processing, and should there be a hard ceiling?
- Does the `.pre-commit-config.yaml` hook fire for every committer touching the repo, or only for contributors to `tests/fixtures/email/`? If the former, have parallel work streams been notified so their commits don't surprise-fail?
- Will the quarterly learning review explicitly consume `needs_schema: true` as a schema-backlog input? D4 mentions it as an input candidate, but the acceptance criteria don't require the review output to produce a backlog artifact.
- The v8 user-gate checklist item (confirm grandfathered-β scope interpretation on #2017 before `status:plan-approved`) is correctly deferred to the follow-up session — is the expectation that the user comment references the v8 commit SHA explicitly, and that the transition to `status:plan-review` is blocked until that comment lands?
