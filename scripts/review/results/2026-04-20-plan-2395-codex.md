### Verdict: MAJOR

### Summary
The plan contains multiple correctness-critical claims that are unverified inside the artifact itself, plus at least one direct coverage gap between acceptance criteria and the TDD list. The dominant defects are dependency/resource assertions treated as facts without evidence, and executable-behavior gaps around scheduling, storage tiers, and checkpoint/security handling.

### Issues Found
- [P1] Unverified resource-intelligence claims: the `Resource Intelligence Summary` asserts specific files, issue states, grep results, and memory artifacts (for example `scripts/data/document-index/phase-a-index.py`, closed `#596`, `project_cross_review_policy.md`, and 'no `regulatory` domain exists yet') but provides no evidence beyond prose; under the review requirements these remain blocking-unverified.
- [P1] Unverified dependency status claims: `Resource Intelligence Summary` cites related issues `#2373` and `#2365`, and the header cites issue `#2395`, but the plan does not prove those issues exist at the stated statuses or that no prerequisite work is still open. This fails the mandatory dependency-correctness check.
- [P1] Review-artifact paths are asserted, not verified: header claim `scripts/review/results/2026-04-20-plan-2395-claude.md | ...-codex.md | ...-gemini.md` conflicts with `Adversarial Review Summary`, which says Codex and Gemini are `PENDING`. Listing those artifacts as review artifacts before they exist is a correctness defect in the plan metadata.
- [P1] Acceptance criteria are not fully covered by tests: `Acceptance Criteria` require quarterly cron wiring on 'first Sunday of Jan/Apr/Jul/Oct' and real runs for Title-30/33 with concrete section counts, but the `TDD Test List` contains no test for cron schedule correctness, no integration validation for the generated schedule entry, and no test that verifies section-count expectations or title-specific end-to-end behavior.
- [P1] The resumability design is underspecified and therefore unverified: `Acceptance Criteria` require `--resume`, `TDD Test List` includes `test_resume_from_checkpoint`, but `Files to Change` does not include any checkpoint/state file path or schema, and `Artifact Map` has no checkpoint artifact. The plan cannot be executed as written without defining where checkpoint state lives and which storage tier it belongs to.
- [P1] Cross-machine tier compliance is incomplete: `Artifact Map` declares `/mnt/ace/CFR/...` as 'authoritative copy on shared mount' while also making `data/document-index/cfr-registry.yaml` the git-tracked registry, but `Risks and Open Questions` mention checkpoint state and `Resource Intelligence Summary` cites checkpoint/resume policy without assigning checkpoint data to git-tracked metadata, shared mount, or local cache. This leaves §7 tiering unproven for a correctness-critical stateful feature.
- [P1] §4 flow-rule compliance is not established for durable storage: the `Deliverable` and `Artifact Map` make `/mnt/ace/CFR/` the raw-text store and `knowledge/wikis/regulatory/wiki/` the promoted wiki output, but the plan never specifies the allowed L1→L2→L3 transitions for the registry and promotion steps or how circular refresh/promotion writes are prevented. Given the explicit §4 citation, this is an unverified operating-model claim.
- [P2] `doc_key` compliance is incomplete: `Pseudocode` uses `sha256:` for CFR section content and the wiki overview claims frontmatter includes `doc_key`, but no rule defines how the rendered-page `doc_key` is computed, whether it is content-hash based after frontmatter normalization, or how `source_ref`/`promoted_from` avoid path-only identity. §3 compliance is therefore only partial.
- [P2] §8.1 frontmatter authority is only partially planned: `Files to Change` adds `knowledge/wikis/regulatory/CLAUDE.md` and the test checks only `title/last_updated/doc_key`; the plan does not verify the full baseline-floor schema for every new wiki page, nor whether `knowledge/wikis/regulatory/wiki/index.md` and title pages include all required authoritative fields such as `doc_key` namespace and any domain-specific required metadata.
- [P2] Storage-ignore logic is internally inconsistent: `Artifact Map` places L1 storage at absolute path `/mnt/ace/CFR/...`, but `Files to Change` says modify `.gitignore` to ignore `/mnt/ace/CFR/**` 'if any'. `.gitignore` does not govern files outside the repository, so this action is either useless or evidence that the actual write path is not fully decided.
- [P2] Scope control is weak: `Deliverable` includes API client, normalization, registry, shared-mount raw store, wiki-domain creation, quarterly scheduling, and resumable checkpoints. For a single issue this is more than a single-purpose deliverable and introduces operational concerns (cron, mount durability, checkpointing) beyond pure ingestion.
- [P2] Threat model is missing for mount writes and external API use: `Deliverable`, `Artifact Map`, and `Files to Change` introduce writes to `/mnt/ace/CFR/` and network pulls from the eCFR API, but `Risks and Open Questions` omit path-traversal, malformed content, mount unavailability, partial-write corruption, or secret/config handling for scheduled jobs. The mandatory security check is not satisfied.
- [P3] The plan updates `docs/plans/README.md` in `Files to Change` without a cited need or acceptance criterion. That is adjacent-scope documentation churn not justified by the deliverable.
- [P3] `test_regulatory_claude_md_declares_baseline_floor` says 'grep passes' in `TDD Test List`; that is not a robust authority-schema validation method for a correctness-critical contract file and is too weak for the cited §8.1 requirement.

### Suggestions
- Provide concrete evidence for every resource-intelligence claim inside the plan artifact: exact verified paths, issue URLs with status, and excerpts or command outputs, or downgrade those statements to assumptions needing verification before implementation.
- Remove `...-codex.md` and `...-gemini.md` from `Review artifacts` until those files actually exist, or create them before plan review is requested.
- Add explicit dependency gating: list whether `#2373` and `#2365` are hard, soft, or unrelated dependencies, and state current live status plus why this plan is executable now.
- Add tests for every currently uncovered acceptance criterion: schedule-generation validation for 'first Sunday of Jan/Apr/Jul/Oct', title-specific integration checks, and a deterministic validation of the review-artifact posting step if it remains an AC.
- Define checkpoint storage explicitly in `Artifact Map` and `Files to Change`: path, format, ownership tier, retention policy, and atomicity rules. Then add tests for corruption recovery and tier-correct placement.
- Add an operating-model mapping table showing each artifact’s layer/tier and every allowed flow (`API -> raw L1 -> registry metadata -> wiki promotion`) so §4 and §7 compliance is demonstrated rather than asserted.
- Specify the exact `doc_key` derivation rules for both CFR section documents and rendered wiki pages, including normalization versioning and how frontmatter/content boundaries are hashed.
- Replace the `grep passes` check for `regulatory/CLAUDE.md` with a schema validation test that asserts all required frontmatter authority fields and invariants.
- Drop the `.gitignore` change unless a repo-relative mirror path will actually be created; if a mirror exists, name that path explicitly.
- Add a threat-model section covering network failures, malformed eCFR content, path sanitization for title/part/section-derived filenames, mount unavailability, partial writes, and scheduler environment assumptions.
