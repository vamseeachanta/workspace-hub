# #3549 Implementation Amendment Security Review — Round 1

## Verdict

**MAJOR**

## Findings

1. **[MAJOR] The overlay `OSError` correction has no exact exit or redaction contract.** The amendment says a RED test will cover “an overlay read `OSError`” (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:202-205`), but its implementation rule only says overlay resolution will “preserve its `ConnectionResolverError` exit” and will not flow through registry `OSError` handling (`:210-212`). A raw `OSError` is not a `ConnectionResolverError`, so this does not specify whether the low-level overlay boundary must translate it to exit 4 or 5, whether the command layer must translate it, or which stable field path/error class must be emitted. This ambiguity is security-relevant: the approved design requires stable redacted errors and distinguishes fallback-state failure, integrity failure, and client-launch failure (`docs/superpowers/specs/2026-07-15-3549-registry-connection-helpers-design.md:243-256,267-285`). The current broad boundary demonstrates the risk: `src/workspace_hub/workstations/connection_command.py:167-176` catches every `OSError` from combined registry and overlay resolution as `registry_unavailable`/3. **Blocking change:** specify that every overlay filesystem `OSError` will be translated at the overlay boundary into a named `FallbackUnavailableError`/4 or `OverlayIntegrityError`/5 with a redacted stable field path/class, keep the registry read in a separate block where only registry I/O maps to 3, and name RED tests for both an availability errno and an integrity errno.

2. **[MAJOR] The acceptance command omits the only test file that proves the amendment’s security-critical behavior.** The amendment assigns option parsing, exact launch exits, SIGINT normalization, one-process launch, dry-run redaction, and the executable boundary to `tests/workstations/test_connection_cli.py` (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:178-188,202-220,249`). Yet the authoritative “Focused tests pass” acceptance command at `:376-377` runs `test_connection_resolver.py`, wrapper tests, and enforcement tests without `tests/workstations/test_connection_cli.py`. Consequently, the plan can satisfy its acceptance checklist while abbreviation rejection, ENOEXEC=126, child SIGINT=130, narrow exception boundaries, host-key argv, one-launch/no-retry, and redaction regress. This is not repaired by the prose promise that “focused tests ... will all run” at `:217-220`; the executable acceptance gate contradicts it. **Blocking change:** add `tests/workstations/test_connection_cli.py` to the exact focused acceptance command and to any Windows/Linux CI command that claims CLI contract coverage.

3. **[MAJOR] The launch-error map is narrower than the approved “client-launch failure” contract and leaves other `exec` failures undefined.** The amendment says exit 126 will apply “only for permission/`ENOEXEC` execution failures” and otherwise preserves only a child status (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:207-209`). That leaves pre-child `OSError` cases such as `ETXTBSY`, `E2BIG`, or resource failures with no numeric/redacted result. The approved table defines 126 as “Selected executable cannot run,” 127 as missing runtime, and requires errors to distinguish “missing client or client-launch failure” (`docs/superpowers/specs/2026-07-15-3549-registry-connection-helpers-design.md:243-252,275-282`). An uncaught launch exception may also escape the stable redaction boundary. **Blocking change:** define an errno-complete launch mapping: missing executable/runtime to 127; permission/format and any other selected-executable launch failure to a deliberate documented exit (normally 126 under the approved table); `KeyboardInterrupt` and child `-SIGINT` to 130; nonnegative child status unchanged. Require a redaction assertion for every exception family.

4. **[MINOR] The structural split adds a governed trust-boundary file without explicitly adding it to manifest coverage.** The approved design requires the checked manifest to include “connection core and CLI” (`docs/superpowers/specs/2026-07-15-3549-registry-connection-helpers-design.md:258-261`). The amendment creates `src/workspace_hub/workstations/connection_command.py` as the owner of argv construction, redaction, exit mapping, and process launch (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:178-183,233-235`), but the amendment only promises unspecified “endpoint-literal source scanning” in `test_connection_cli.py` (`:202-205`). It does not require the checked governed-path manifest to name the new module or require the actual staged/head guard to reject its omission. A bespoke source scan is not equivalent to manifest-backed staged-blob coverage. **Required change:** explicitly require `connection_command.py` and `test_connection_cli.py` in the governed manifest with their intended classifications, and add an enforcement test that fails if either path is absent or if a literal is introduced into the staged blob.

5. **[MINOR] The amendment violates the future-tense-only plan rule in its load-bearing justification.** The claim that constraints “became visible,” Slice A/B “established real file sizes,” and Slice C review “exercised the command boundary” is past tense (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:174-176`). The HTML repeats completed-state claims: “implementation review exposed” a conflict and the files “reached 376 and 397 lines” (`docs/reports/2026-07-16-issue-3549-registry-connection-helpers-plan.html:86-88,103-105`). The line counts are empirically correct in the reviewed tree, but the plan rule requires proposed work to remain future tense and completed-state evidence to be clearly separated from authorization. **Required change:** move the observed line counts and review facts into a dated evidence subsection, then phrase the amendment authorization and work exclusively in future tense.

## Verified checks

- The review range changes only the plan, plan index, and human-facing HTML. The amendment’s proposed implementation paths (`connection_command.py`, `test_connection_cli.py`, and `scripts/workspace`) are present in the canonical implementation changed-path map at `docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:233-249`; no implementation-path authority omission was found for those three paths.
- The asserted size pressure is real: the reviewed tree has 376 lines in `connection.py` and 397 lines in `test_connection_resolver.py`; the split files have 196 and 249 lines respectively.
- The approved hostname/fallback trust model is not intentionally changed: canonical hostname remains positional, fallback is explicit, fixed `StrictHostKeyChecking=yes` and canonical `HostKeyAlias` remain required, and no caller-supplied SSH options are authorized (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:151-163,195-198,273-278,350-368`).
- The one-launch/no-retry requirement remains stated in the amendment and parent plan. The acceptance omission in Finding 2 is why that statement is not yet a sufficient gate.
- No `TODO`/`TBD` placeholder was introduced by the amendment. The existing `<completion-date>` navigation placeholder is outside the amendment and denotes a future closeout artifact.
- The human-facing HTML reflects the same three amendment scopes—structural split, command-boundary corrections, and `scripts/workspace` caller migration—but it does not cure the Markdown acceptance and exception-map defects above.

## Blocking changes

1. Define exact redacted overlay-I/O exits and narrow registry versus overlay exception boundaries.
2. Add `test_connection_cli.py` to the authoritative acceptance and CI commands.
3. Complete the pre-child launch `OSError` mapping and test every exception family without raw values.
4. Explicitly bind both split files into governed-manifest enforcement.
