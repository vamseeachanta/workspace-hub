### Verdict: APPROVE

### Summary
Thorough, well-scoped T1 plan with strong TDD discipline, embedded verification evidence, and appropriate adversarial-review gating. Scope is narrow (host-only rewrite), preconditions (xmllint availability, zero normalized collisions, shipped #2391 serving fix) are explicitly verified, and acceptance criteria include both durable regression tests and one-time migration checks. A few SEO-adjacent risks and governance-reconciliation details are under-specified but none are blockers for a content-rewrite of this complexity.

### Issues Found
- [P2] SEO risk surface not addressed: plan assumes www is the canonical host but never confirms that apex→www redirects are configured at the DNS/edge layer. If apex still serves 200 OK, announcing only www in sitemap creates a canonicalization mismatch rather than fixing one. Worth at least a one-line verification step (curl -I https://aceengineer.com/ expecting 301→www) before the rewrite.
- [P2] No post-deploy search-engine notification strategy is mentioned (Google Search Console resubmit, Bing IndexNow, or equivalent). For an SEO chore whose whole purpose is re-crawling, silent deploy may delay the intended benefit; either include it or explicitly defer with a follow-up issue.
- [P3] Governance-drift reconciliation is flagged as a risk but the reconciliation procedure is not specified. The plan says the live `status:plan-approved` label must not be treated as execution authorization, but does not state who clears it, how the local `.planning/plan-approved/2357.md` marker is produced, or how the two are kept in sync on merge.
- [P3] `sitemap_loc_values_are_unique` is described as checking uniqueness 'after normalization' in one place and over 'the full set of <loc> values' in another — the normalization step is undefined (lowercasing? trailing-slash? host-stripping?). Ambiguity here can mask a real duplicate by normalizing it away, or cause a false failure on trivial whitespace.
- [P3] The regression test relies on a regex-based assertion for the absence of apex-host <loc> entries, but the plan does not pin the exact negative-assertion regex. A loose pattern (e.g. missing word boundary or case sensitivity) could miss `https://ACEENGINEER.com` or `http://aceengineer.com` variants. Since the whole point is a durable guard, the regex deserves to be specified in the plan, not left to implementation.
- [P3] The issue body's stale `public/sitemap.xml` reference is only handled via an implementation-summary note. Updating the issue body itself (or adding a pinned comment) would prevent the same confusion from recurring on future readers who don't scroll to the implementation summary.

### Suggestions
- Add a pre-edit apex-host redirect check (e.g. `curl -sI https://aceengineer.com/ | head -1` expecting `301`) as an acceptance criterion so the SEO intent is verified, not assumed.
- Specify the exact negative-assertion regex for the durable `sitemap_has_zero_apex_loc_entries` test (case-insensitive, anchored to `<loc>\s*https?://aceengineer\.com`) inside the plan, so reviewers of the implementation PR can diff against the committed spec.
- Define the uniqueness normalization rule explicitly (recommended: trim whitespace, no other transformation) so `sitemap_loc_values_are_unique` has a single interpretation.
- Add a tiny follow-up step to update the #2357 issue body to reference `aceengineer-website/sitemap.xml` instead of `public/sitemap.xml`, in addition to the implementation-summary note.
- Either include a Google Search Console / IndexNow resubmit step as a manual post-merge task in the acceptance criteria, or file a follow-up issue and link it from the plan so the SEO benefit is not silently delayed.
- Document the governance-drift reconciliation procedure inline (who writes `.planning/plan-approved/2357.md`, when, and with what content) so the live-label vs local-marker mismatch is resolved deterministically rather than ad-hoc.

### Questions for Author
- Is `https://aceengineer.com/` currently returning a 301 to `https://www.aceengineer.com/`, or is it still serving content directly? The answer changes whether this sitemap rewrite is a pure canonicalization fix or whether it introduces a crawl inconsistency until the redirect lands.
- Should search-engine resubmission (GSC / Bing / IndexNow) be part of this issue's acceptance criteria, or tracked as a separate follow-up? The plan is silent on how the re-crawl is actually triggered.
- How will the `.planning/plan-approved/2357.md` marker be created and what does it contain? The plan flags its absence as governance drift but does not describe the reconciliation artifact.
- What exactly does 'unique after normalization' mean for `sitemap_loc_values_are_unique` — trim-only, case-fold, trailing-slash-fold, or something else? The test's strictness depends entirely on this.
- Should the apex-host negative-assertion regex also match `http://` (not just `https://`) and be case-insensitive, to harden the durable guard against future accidental reintroduction via copy-paste from other sources?
