### Verdict: MINOR

### Summary
The plan is well-scoped: it executes a single slice of the #2460 contract without attempting to boil the ocean, and the enforcement sits at the right level of the rules gradient (prose + Level-2 test, no new hook). The remaining concerns are architectural: the plan creates a new top-level `docs/` surface (`ROUTING_INDEX.md`) without stating its lifecycle (who regenerates it? when?), and it treats the discoverability patch to `docs/README.md` as a one-shot edit rather than wiring it into the accessibility-registry-driven generator path that already exists as L2 metadata.

### Issues Found

- [P1] Critical — **`docs/ROUTING_INDEX.md` has no declared owner or freshness cadence.** The plan positions it as the single trusted portfolio-routing surface, but the accessibility registry schema (`data/document-index/intelligence-accessibility-registry.yaml`) requires `freshness_source`, `freshness_cadence`, `owner_issue`, and `discoverability` on every L2/L3 asset. This plan adds a new asset but does not register it. Result: on day one the routing index is trusted; on day 180 it is as stale as the content index it replaces, with no signal to the daily maintenance loop. Fix: add a registry entry to the Files-to-Change table and include a test that every file under `docs/` with a `## Portfolio matrix` header is registered.
- [P2] Important — **Discoverability is patched in markdown, not in the registry.** The plan edits `docs/README.md` directly. That works for today's audit but re-introduces the same structural defect the scorecard complained about: discoverability tracked only in prose. The registry already has a `gaps:` field on every asset; the correct long-term architecture is: (a) update the registry's `gaps:` from "Not linked from docs/README.md" to null, and (b) drive the `docs/README.md` section from the registry. Without that, the next audit finds the same class of defect on newly-added wikis.
- [P2] Important — **No backward-link from `docs/CONTENT_INDEX.md` to `docs/ROUTING_INDEX.md` at read time.** Readers who land on `CONTENT_INDEX.md` via search today will — after this plan — see a banner saying "not a curated routing index" but must know the curated file's path. The plan says "link to `docs/ROUTING_INDEX.md`" in the banner but does not make that a tested requirement. Add an assertion: the banner includes a live relative link to `ROUTING_INDEX.md` (and the link is not broken).
- [P3] Minor — **Plan has no rollback plan for the deletions.** `git revert` of a deletion-only commit is trivial, but the plan does not say what to do if, post-merge, someone reports that a deleted root file was load-bearing. The risk is low given the filenames, but the plan sets a precedent for future tier-1 cleanups where the risk is higher. Add a one-liner: "Rollback: `git revert` the deletion commit; filenames are stable and roundtrip cleanly."
- [P3] Minor — **Test module path `tests/docs/test_tier1_routing_hygiene.py` is fine, but the plan does not say whether the test is repo-scoped or workspace-scoped.** The hygiene rules belong to workspace-hub; if an agent runs them from a sibling repo clone, they should fail fast with a clear message, not a cryptic `FileNotFoundError`.

### Suggestions

- Register `docs/ROUTING_INDEX.md` as an L2 `map` asset in `data/document-index/intelligence-accessibility-registry.yaml` during execution (add to Files-to-Change). That closes the loop between the registry (the "where is everything" surface) and the new routing index (the "what goes where" surface).
- Make the `docs/README.md` discoverability edit structurally minimal and idempotent: one new `### Tier-1 Routing` block with a sentinel comment. This prevents merge conflicts with the many concurrent plans touching README.
- Consider whether `docs/ROUTING_INDEX.md` should be derived from the same registry at build time. A manual markdown table is fine for v1; flag the automation as a #2465 (daily freshness) candidate so the ownership is clear.
- Add a freshness field to the plan: the routing index should be touched at least once per audit cadence (daily, per #2465). Without that, the "trusted" qualifier decays.

### Questions for Author

- Does #2465 (daily freshness) already cover "re-validate routing index sections match the #2460 contract"? If yes, this plan can cite it and skip a self-policing risk. If no, this plan is implicitly creating work for #2465 without declaring it.
- Is there a convention on where tier-1 routing tests live (`tests/docs/` vs `tests/integration/` vs a new `tests/routing/`)? The plan assumes `tests/docs/`; confirm.
