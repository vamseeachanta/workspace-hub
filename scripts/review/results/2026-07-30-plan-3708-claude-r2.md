### 3. MAJOR — The `notification-purge` command-only matcher is unnecessary on the evidence, and adding it weakens the exact-identity invariant the rule mandates.

**Evidence:** the rendered canonical line and the declared legacy line are **byte-identical**:

```
legacy   : 30 4 * * * cd /mnt/local-analysis/workspace-hub && find logs/notifications/ -name "*.jsonl" -mtime +7 -delete 2>/dev/null || true

```

(`config/workstations/harness-state-classes.yaml:178-180` vs `cron_render.render_task` for `notification-purge`, whose `log:` is `null` so `_ensure_log_dir` adds no prefix.) The captured audit reports `reason: legacy-exact-line` only because `_bind_legacy` overwrites the identical canonical binding (`cron_identity.py:241-243, 246-256`) — same task id, so no collision, just a relabel.

Therefore, on ace1: `notification-purge` classifies `cataloged` via **canonical-exact-line** even with the legacy row deleted; both installed copies already classify cataloged; and dedupe to one line already works. Simulation of `plan_cutover` on the captured crontab returns `notification-purge copies: 1`, and existing green tests already assert it — `tests/cron/test_a1_preserved.py:122 test_notification_purge_catalog_owned_line_is_deduped_without_apply_rollback` (`assert state["crontab"].count("find logs/notifications/") == 1`) and `:103 test_recent_a1_catalog_duplicates_are_deduped_into_managed_block`.

**Failure scenario introduced by the fix:** a command-only identity is by construction **schedule-insensitive** — the schedule is not part of the key. Attack-vector 5 answered: yes, dedupe can remove a line that differs only by schedule, and only under the newly proposed matcher. `test_command_only_unknown_find_does_not_match` covers a different *command*, not a different *schedule*.

This also contravenes `.claude/rules/scheduler-mutation-safety.md:5` ("Destructive ownership must use parsed or exact identity") by adding a non-exact destructive branch for a task that needs none.

**Required revision:** Delete the command-only-matcher work item and its Gap. Replace with: (a) an evidence note that `notification-purge` is already canonical-exact and the `harness-state-classes.yaml:167-180` legacy row is redundant, and (b) a decision on removing that redundant row. If a command-only mechanism is genuinely wanted for some other task, it needs its own issue, must include the cron schedule in the identity key, must be checked *after* preservation, and must carry a registry authority branch with a real derivation — none of which this plan provides.

### 4. MEDIUM — The normalization's only stated safety bound is circular, and "renderer-owned" has no mechanical definition.

**Evidence:** plan pseudocode lines 164-170:

```
function canonicalize_log_dir_prefix(line, workspace_hub):
    ...
    require the normalized log dir to equal the selected task's declared log parent
```

The function signature takes no task. At normalization time no task has been selected — the task is only known *after* the normalized line matches. And once a full-line exact match against a rendered line succeeds, log-dir equality is implied. The guard is therefore both unimplementable as written and, once implementable, vacuous. It is the plan's only stated bound on normalization scope, and it constrains nothing.

Worse, "renderer-owned" is not observable in the artifact being classified. `cron_render.py:150-165`:

```python
    if "mkdir -p" in command and log_dir in command:
        return command
    return f"mkdir -p $WORKSPACE_HUB/{log_dir} && {command}"
```

A YAML-authored leading `mkdir -p $WORKSPACE_HUB/<logdir> && …` suppresses the renderer prefix and renders **identically** to a renderer-added one. YAML-authored `mkdir -p $WORKSPACE_HUB/...` is already a live pattern (`drive-index-refresh-ace`, `drive-index-refresh-cad`, `deckhand-api-presence-sync`, the two `email-queue-*` tasks). One YAML edit moving it to the front makes the two indistinguishable, so the plan's central safety story ("only the renderer-owned prefix is normalized") has no test that can be written against it.

Second concrete hole: nothing validates that `$WORKSPACE_HUB` actually expands to the registry `workspace_root`. ace1's crontab sets `WORKSPACE_HUB=/mnt/local-analysis/workspace-hub` (captured line 2), but `_is_ignore_line` (`cron_line_model.py:153-155`) classifies env assignments as `ignore` and nothing ever compares the value. On `gpu-claw` (`workspace_root: /home/undi/ws/workspace-hub`), on a box whose env line is stale, or if the assignment is absent, a line reading `mkdir -p $WORKSPACE_HUB/logs/x && cd /mnt/local-analysis/workspace-hub && …` normalizes to the registry root, matches a rendered line, and is claimed cataloged — granting deletion authority over a line that at runtime creates a *different* directory (or `/logs/x` at filesystem root when unset).

**Required revision:** Replace the vacuous guard with a real one: (i) require the crontab's own `WORKSPACE_HUB=` assignment, when present, to equal the registry `workspace_root`, and fail closed when it is absent or divergent; (ii) make renderer ownership observable — either emit a stable canonical absolute prefix from the renderer (the plan's own preferred option, buried in §Mkdir-Prefix Decision) so no identity-layer normalization is needed at all, or carry explicit per-task canonicalization metadata. Option (i)+(renderer canonical form) removes the normalization surface entirely and is the safer design; the plan should pick it rather than leave both open.

### 6. MEDIUM — The plan claims rollback happens "under the same lock". It does not; the lock is released between write and verify.

**Evidence:** `scripts/cron/cron_apply.py:352-361`

```python
    with _flock(LOCKFILE):
        current = _read()
        if current != A: return {...abort...}
        backup = create_backup(canonical_id, ts, A)
        observation = _write_observation(plan["new_text"], _read, _write)
    transaction = _finish_exact(A, plan["new_text"], backup, observation, _read, _write)
```

`_finish_exact` runs **outside** the `with`, and `_rollback` re-acquires the lock independently at `cron_apply.py:240`. The plan's Cutover Design step 9 says "it will attempt rollback only after a rollback CAS **under the same lock**" — factually wrong about the code, and the plan proposes no fix.

**Failure scenario:** process P1 writes corrupt state C and releases the lock. P2 (`harness-update.sh` → `setup-cron.sh`, a real 6-hourly caller registered at `mutation-surfaces.yaml:229-237`) acquires the lock, reads C as its baseline `A`, CAS-succeeds against it, and writes its own plan. P1's rollback then sees `current != C` and reports `rollback-aborted` (`cron_apply.py:245-250`) — correct fail-closed, but the corrupt intermediate has been laundered into P2's baseline and the durable backup of the *true* pre-transaction state is only recoverable by hand from `logs/cron-backups/`.

Attack-vector 3 sub-questions, answered honestly:
- **Backup succeeds, crontab write partially applies:** `write_crontab` uses `crontab -` on stdin (`cron_apply.py:102-103`), and Vixie `crontab` writes temp+rename, so a torn table is unlikely; if it happens, `observed != B` triggers rollback correctly.
- **macOS/`crontab <file>` empty-table-with-exit-0:** **not applicable and not a defect here.** The code never uses `crontab <file>`. Even if an empty table were installed with rc 0, `read_crontab` returns `""` on the "no crontab" stderr (`cron_apply.py:96-98`), `observed ("") != B` at `_finish_exact:280`, and `_rollback` proceeds because `current == C == ""`. The CAS does catch it. I could not reproduce this on a live host and did not try.
- **Lock held by a dead process:** `fcntl.flock` releases on process death, so this is not a hang risk.
- **Genuine residual:** there is no on-disk intent journal. A SIGKILL (quota death, per `.claude/rules/model-routing.md` corollary 1) between `_write` and `_read` leaves the crontab at `B` with no status ever reported and no marker that a transaction was in flight. The backup exists but nothing points at it.

**Required revision:** Either hold one continuous lock across write → verify → rollback, or state explicitly in the Cutover Design that the lock is re-acquired and add a test for the P1/P2 interleave above. Add an intent-record (write the planned digest next to the backup before the write, clear it on `applied`) so a crash is detectable on the next run. Correct step 9's wording either way.
