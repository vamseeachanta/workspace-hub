## 4. Critical findings (blockers)

### C1. `FORCE_PLAN_GATE=1` is not an actual bypass — plan test is unimplementable as specified

**Claim under review:** Plan §TDD Test List, row `test_commit_gate_emits_bypass_log` states the test verifies "`require-plan-approval.sh` writes to `logs/hooks/plan-gate-bypass.jsonl` when `FORCE_PLAN_GATE=1` is used to bypass."

**Verification:** Read `scripts/enforcement/require-plan-approval.sh` lines 1–123 in full. The script **never reads `$FORCE_PLAN_GATE`**. It reads `$FORCE_PLAN_GATE_STRICT` (the opt-in strict-mode variable, line 12) and accepts `--strict` / `--check` CLI args (lines 14–19). The script's error message (line 105) claims `"To bypass (logged): FORCE_PLAN_GATE=1 git commit"` — but no code path actually honors this variable. Setting `FORCE_PLAN_GATE=1` has zero effect on the gate. In STRICT_MODE=1 the script always `exit 1` after logging a `"plan-gate-blocked"` event; in STRICT_MODE=0 it always `exit 0` with an advisory warning.

**Evidence:**
```
scripts/enforcement/require-plan-approval.sh:105: echo "To bypass (logged): FORCE_PLAN_GATE=1 git commit"
scripts/enforcement/require-plan-approval.sh:(no line): grep -n 'FORCE_PLAN_GATE\b' returned only the STRICT variant
```

**Why this is a blocker:**
- The test cannot pass as written — it tests behavior that does not exist.
- The plan's advisor pseudocode reads `logs/hooks/plan-gate-bypass.jsonl` as its primary commit-gate bypass source. If no mechanism populates that file, the advisor has no commit-gate signal to process.
- The "bypass-logging parity with push gate" Files-to-Change entry (`scripts/enforcement/require-plan-approval.sh` — "Add `log_bypass()` producing `logs/hooks/plan-gate-bypass.jsonl`") silently assumes the *bypass check itself* already exists. It does not.

**Required revision:** The plan must either (a) expand the commit-gate modification to include adding a real `$FORCE_PLAN_GATE=1` check path (parallel to push-gate's `$SKIP_REVIEW_GATE=1` at `require-review-on-push.sh:165`) with an accompanying `log_bypass()` call; OR (b) redefine the commit-gate bypass signal to be something actually observable today — e.g., parse existing `logs/hooks/plan-gate-events.jsonl` (which *is* written at `require-plan-approval.sh:113` on gate-blocked events) to detect attempted-but-not-bypassed commits; OR (c) cover commits made via `git commit --no-verify` (which skips the hook entirely but leaves no log trail — this is the real observability gap).

## 5. High findings

### H1. Pseudocode conflates "no approval marker" with "bypass happened"

Plan §Pseudocode calls `has_post_hoc_approval_marker(commit_sha)`. For a true bypass, the bypass is distinguished *precisely* because no approval existed at commit time. A later marker creation (post-hoc approval) is a meaningful signal, but the function name and check order invite a false-negative class: if the marker is created in a stale or advisory-only fashion (`FORCE_PLAN_GATE_STRICT=0` advisory mode), the bypass would be masked.

**Required:** Pseudocode should distinguish (a) "marker created after commit with explicit approval intent" from (b) "gate ran in advisory mode and marker never existed." The advisor should differentiate these for audit-trail fidelity.

### H2. `auto_revert_proposed` vs `guided_revert` is a muddled distinction

Plan §Key Design Decisions §1 says "Rollback is advisory, not automatic, in this child's scope. The advisor produces a recommendation; the human or a higher-scope tool executes." Yet the two verdicts emitted are `guided_revert` (when pushed) and `auto_revert_proposed` (when local-only). If both are recommendations that a human executes, what operational difference does the verdict make?

**Required:** Either (a) collapse to a single `revert_recommended` verdict with a `pushed: true/false` structured field that downstream tools interpret; or (b) genuinely differentiate — e.g., `auto_revert_proposed` triggers a `git reset HEAD~1` candidate for unpushed commits (agent can exec per TRUST-ARCHITECTURE.md §Rollback Rules line 222) while `guided_revert` generates `git revert` instructions for a human. The plan's current text leaves the distinction decorative.

### H3. Non-zero exit for proposals creates CI coupling not explicitly scoped

Plan §Acceptance Criteria row: "exits non-zero when guided_revert/auto_revert_proposed verdicts are emitted (so it is CI-composable)." Plan §Open Questions asks "should the advisor be wired into CI? Current plan says no." These two statements are in tension: non-zero exit is CI-composable behavior, implying CI use is plausible; but the plan simultaneously says CI integration is out of scope.

**Required:** Pick one. If the advisor exits non-zero on proposals, name where it runs (nightly cron? local only? review-gate hook?) and whether the non-zero exit should actually fail anything today. If the advisor is advisory-only with no blocking surface, a non-zero exit is performative — prefer exit 0 + structured output.

## 6. Medium findings

### M1. "Byte-for-byte schema parity" claim is technically false

Plan §Risks: "commit-gate `log_bypass()` mirrors push-gate schema byte-for-byte; test `test_commit_gate_emits_bypass_log` asserts exact key set." But the push gate's bypass log uses `local_oid` and `remote_oid` (`require-review-on-push.sh:159`), which are push-time hook environment variables. The commit gate has no `remote_oid` at commit time (commit isn't pushed yet). Byte-for-byte parity is impossible; "same schema modulo push-specific fields" is achievable.

**Required:** Rewrite the parity claim accurately. Name exactly which fields transfer (timestamp, user, branch, action) and which are commit-specific (staged_files, commit_sha-if-post-commit).

### M2. `test_advisor_preserves_audit_record_before_any_action` test name conflates proposal with action

The advisor produces recommendations, not actions. "Before any action" is misleading. The correct invariant is "before emitting any revert-implicating verdict" — i.e., the audit record is written before `emit_recommendation()`.

### M3. TRUST-ARCHITECTURE.md §Rollback Rules agent-initiated auto-revert is only narrowly distinguished

Plan §Resource Intelligence cites TRUST-ARCHITECTURE.md's agent-initiated rollback (commit + failing test = auto-revert, line 222) as distinct from bypass-initiated rollback. But the plan doesn't specify precedence when both fire — e.g., an agent commit that bypassed the plan gate AND broke tests. Does the agent's own auto-revert (per TRUST-ARCHITECTURE) run first, or does this advisor run first? Result ordering matters for audit fidelity.

**Required:** Add a §Precedence subsection to the new `BYPASS-ROLLBACK-POLICY.md` explaining order of operations when both rule sets apply.
