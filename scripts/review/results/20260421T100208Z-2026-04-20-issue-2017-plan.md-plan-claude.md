### Verdict: APPROVE

### Summary
Plan v7 is technically sound, well-scoped, and has cycled through six prior review rounds addressing convergent P1/P2 findings from Claude/Codex/Gemini. The grandfathering of existing routing + explicit ownership split across #2017/#2026/#2024, composite-key discipline, atomic snapshot + meta freshness with log_generation, sweep's dual-lock requirement, and fixture redaction standard are all substantive improvements. Remaining issues are doc-hygiene and minor test-naming nits — none should block plan approval, but the stale Adversarial Review Summary and v2-referencing acceptance criteria should be refreshed before merge.

### Issues Found
- [P2] Stale review section: 'Adversarial Review Summary' still shows 'v2 verdicts — pending' and the v2-only table, even though the front matter records Claude APPROVE + Gemini APPROVE + Codex MAJOR at v3 and five subsequent revisions (v4–v7). A reader auditing the doc at merge time cannot reconcile 'pending' with the v7 status.
- [P2] Stale acceptance criteria: 'v2 cross-review artifacts exist' and 'All 3 v2 verdicts are APPROVE or MINOR' reference v2 specifically. As written, the gate is indeterminate at v7 — should be updated to reference the current revision (or be phrased revision-agnostic).
- [P2] Issue-title vs scope reinterpretation: #2017 literally says 'delete when done'. v7 reinterprets this as local-queue-state deletion and punts Gmail-side deletion to follow-on #2423. This is a substantive scope narrowing from the issue's plain reading and needs explicit user sign-off logged as a gate before `status:plan-approved`, not just the inline prose in the header.
- [P3] Evidence-block file-size coincidence: `scripts/email/email-routing.yaml` and `scripts/email/batch-unsubscribe.sh` are both reported as 8051 bytes. Possible copy-paste error in the Resource Intelligence Summary — verify the batch-unsubscribe size independently.
- [P3] Fixture redaction regex is broad: `[\w.]+@[\w.]+\.\w+` will also match canonical placeholders (`test@example.com`, `user@domain.tld`) that fixture authors legitimately want to use. Either document an allowlist of safe placeholder domains or make the pre-commit hook reject only non-allowlisted patterns, otherwise the hook will produce false positives on every new fixture PR.
- [P3] Test-name/behavior mismatch: `test_purged_treated_as_new_if_extraction_missing` does not assert the `extraction_missing_on_reactivation` structured-log event that the v4 pseudocode emits before the fallback. Either rename (e.g., `test_purged_missing_extraction_emits_event_and_treats_as_new`) or split into two tests.
- [P3] Sweep lock-holding time unspecified: daily sweep must hold `fcntl.LOCK_EX` on `queue-state.jsonl` while it appends purged transitions. If the sweep iterates over a large snapshot before appending, the log is held for the full iteration, blocking inbound processing. Specify whether sweep batches appends or releases/re-acquires the lock per transition.
- [P3] Contract test `test_snapshot_atomic_write` is under-specified: 'simulated write failure mid-snapshot' is non-trivial to implement deterministically (kill mid-syscall vs. patched `os.rename` vs. disk-full mock). Name the simulation technique so #2026 can't meet the xfail flip trivially.
- [P3] Grace-boundary tests use day 6 and day 8, but the rule is strict `> 7 days`. No test pins behavior exactly at the 7-day boundary (7d 0s vs 7d +1s). If #2026 implements `>=` by accident, existing tests pass.
- [P3] `apply_precedence` returns `(archive, [])` as a safety default when no classification matches, but the classify_inbound path for unknown senders hard-codes `classifications: [archive]` already. Verify whether the safety default in `apply_precedence` is ever reachable — if not, it's dead code; if so, document when.

- Consider adding a test `test_sweep_batches_or_releases_log_lock` asserting whichever discipline sweep must follow — either batched append within one lock acquisition, or per-transition lock release — so #2024's sweep-cron wiring has a clear contract.
