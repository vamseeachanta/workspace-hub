### claude

- **1. (MAJOR) Acceptance criterion #5 timeout budget is unverified and likely infeasible.** Criterion #5 (plan line 361) requires the audit to complete "across the live governed repo set ... (required, optional, and `non_tier1_machine_access_current`) with zero `git_probe_timeout` under tracked 30/120/480 defaults." The governed set on this host is **17 named repos** (`registry.yaml:73,74,77–86`). The plan's only wall-clock evidence (lines 191–195) measures **2 repos**, and `status-short` *alone* took 11.81s and 10.41s. Each repo runs several sequential probes (`branch-current`, `status-short`, `upstream-ref`, stash list — `cron_transaction.py`/audit `git_readonly` map). `TOTAL_TIMEOUT_SEC=480` with `REPO_TIMEOUT_SEC=120` only covers ~4 worst-case or ~8–16 realistic repos. With 17 repos and per-repo cost plausibly 20–60s, the **total budget can fire before the set completes**, which makes criterion #5 fail by construction. The plan's r2 "resolution" (line 395) only proved the *upper* bound (480 < 600s gap) — it never proved the *lower* bound (480 ≥ actual completion time for the full present set). This is exactly Codex r2's "timeout total budget conflicted with full governed set" finding (line 379), and it remains unaddressed. **Blocker.**
- **2. (MAJOR) `$WORKSPACE_HUB`/`$LOG` expansion can collide with `catalog_commands` substring matching and abort cutovers as "uncataloged."** The plan expands placeholders for *all* selected tasks (`render_catalog_task_for_cron`, pseudocode 264–269). `cron_apply.catalog_commands` (`cron_apply.py:119–130`) keys cataloged-line recognition on a `scripts/*.sh|.py` token *when present*, but **falls back to the raw, unexpanded `cmd.strip()[:60]`** otherwise. `classify_line` matches by `cmd in line` substring (`cron_transaction.py:197`). For any catalog task whose command lacks a `scripts/...` token and begins with `cd $WORKSPACE_HUB && ...`, an *expanded* live line appearing outside the managed block (e.g., written by the legacy non-marker `setup-cron.sh` at line 196, or after marker loss) will no longer substring-match its `$WORKSPACE_HUB`-bearing catalog key → classified **uncataloged** → `plan_cutover` aborts (lines 347–354). The two tasks being fixed (hygiene, cron-health) are script-token-keyed and safe, but the plan changes rendering globally and never audits the catalog for fallback-keyed tasks. The TDD list has no test for "expanded cataloged line outside block is still recognized." **Blocker until the catalog is shown to contain zero fallback-keyed tasks, or a test pins the interaction.**
- **3. (MINOR) Variant resolution parity is asserted at the wrong layer.** `setup-cron.sh` resolves the machine via **alias-aware** matching (`setup-cron.sh:110–116`, iterating `hostname` + `hostname_aliases`) before reading `schedule_variant`. The plan's `cron_context_for_machine` does a **direct key lookup** `registry.machines.get(machine_id, {})` (pseudocode 255). If `machine_id` is a hostname/alias that is not the registry dict key, `cron_render` gets `{}` → `schedule_variant` None → `"contribute"` fallback → `$LOG` resolves to `/tmp/workspace-hub-cron.log`, while `setup-cron.sh` correctly resolves `full` → `cron-wrapper.log`. That is the *same divergence class* the plan claims to eliminate. The parity test `test_setup_cron_and_cron_apply_use_shared_renderer_for_same_task` (plan line 338) asserts identity "for the same task/**context**" — handing both paths a pre-resolved context, so it cannot catch a resolution divergence. The shared module must also share the machine→variant *resolution*, not just rendering.
- **4. (MINOR) 600s schedule-gap margin is thinner than stated.** Hygiene runs `35 5`, cron-health `45 5` (verified `schedule-tasks.yaml:502,521`) = 600s. With `TOTAL_TIMEOUT_SEC=480`, a worst-case hygiene run finishes at 43:00, leaving only **120s** before cron-health reads at 45:00. The plan frames `480 < 600` as comfortable (lines 291, 395); it is a 2-minute buffer with no allowance for cron daemon dispatch jitter or log-flush lag. Acceptable, but should be named as residual risk, not "resolved."
- **5. (MINOR / accurate-claim note) Plan's core claims verified true.** `--json` genuinely lacks `new_text` (confirmed 162–166); ignore-classified env lines (`WORKSPACE_HUB=`, `LOG=`, and incidentally `REPO_ECOSYSTEM_HYGIENE_*=`) **are** preserved verbatim (334–337, 191–193) so acceptance criterion #2 is sound; the `setup-cron` vs `cron_transaction` divergence is real (no `$WORKSPACE_HUB` expansion in `render_block`). The cron-health latest-marker design is internally coherent: the generic `(^|[[:space:]])ERROR:` pattern (line 85) would otherwise re-trip on an older `ERROR: ... execution_failed` marker, so the "filter recognized hygiene markers before generic scan" step (pseudocode 302) is *necessary*, not optional — the plan should state that the filter is load-bearing for criterion #7, not a convenience.
