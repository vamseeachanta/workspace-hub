1. **The plan's own approval gate is currently un-cleanable, and the plan does not say so.** Acceptance criterion line 294 ("Before posting `status:plan-review`, each approval-gate immutable review artifact (fresh post-revision timestamped `*-plan-2488-*.md`...) is non-empty, contains a parseable `## Verdict`...") requires fresh post-revision artifacts. The plan acknowledges Codex/Claude/Gemini may be unavailable in §Adversarial Review Summary line 311 but does not pin a concrete unblock: it does not specify (a) downgrade Codex CLI to 0.123.0, (b) use the GitHub-connector fallback, or (c) record an explicit timestamped UNAVAILABLE artifact for the empty Claude run with `claude.md.err = 0` (no stderr to attach). As written, the gate criterion is satisfiable only by infrastructure work the plan never owns.

2. **`_write_markdown_artifact()` "policy-driven section order" requirement is testable but easily faked.** Plan §Pseudocode line 199 and Acceptance line 283 require `_write_markdown_artifact()` to "consume `ranking_policy.section_order` for exactly these six policy-governed sections". Live code at `weekly_skills_audit.py:809-881` hard-codes every section by literal calls (`_append_finding_section(lines, "New Findings", …)`, `_append_finding_section(lines, "Changed Findings", …)`, plus inline `lines.append("## Suppressed / Carry-Forward Findings")` at line 852 and `lines.append("## Operational Errors")` at line 870). The TDD row `test_policy_section_order_consumes_yaml_for_governed_sections` (line 268) describes a fixture that "reorders the six policy-governed sections" and asserts the rendered Markdown reorders accordingly — that *is* a real consumption test. But the very next TDD row `test_markdown_refactor_preserves_legacy_literal_sections` (line 269) pins the explicit before/after order ("New → Changed → Filesystem-only → Content Quality → Grouping → Oversized → Usage → Follow-up → Unresolved → Suppressed → Errors"). The two together implicitly require the test fixtures to use *different* policy YAML inputs, but neither test row says so. An implementer can satisfy both by (a) running the reorder fixture with a YAML that happens to match the canonical order while (b) running the legacy-section test with a separate YAML — and never wire `ranking_policy.section_order` reads into the rendering path beyond a single fixture-keyed branch.

3. **Acceptance criterion line 282 mandates documenting `filesystem_only_inventory` in `docs/standards/weekly-skills-audit-policy.md` but no TDD row enforces it, and the plan never names a heading or insertion point.** §Files-to-Change line 232 says "Document new inventory summary schema and where `filesystem_only_active` / `filesystem_only_inventory` lives in the existing policy schema", but the existing 2940-byte file is not quoted, no anchor is named, and the TDD list (lines 247-274) contains no row that asserts the doc has been edited. 4. **`scripts/skills/issue_2488_disposition_report.py` has no test row, no defined CLI, and no operator entry point.** §Files-to-Change line 235 introduces this file as a "bounded issue-specific helper that re-runs live inventory and renders the one-time disposition report; not a reusable reconciliation framework, not invoked by cron, and removable/replaceable after #2488 closeout." 6. **The plan does not describe how the `category_alias_families` policy entry interacts with the new `_archive`/`_archived` active filter.** `config/skills/weekly-audit-policy.yaml:299-308` already declares an alias family `id: archive, canonical: _archive, aliases: [_archive, _archived]`. The plan should either (a) wire the active filter through `category_alias_families`, or (b) add a TDD row asserting that the active-filter set equals `category_alias_families[archive].aliases` plus a documented "diverged compatibility" exception.

7. **The "byte-for-byte unchanged" claim for non-description fields in `schedule-tasks.yaml` is brittle and not bracketed.** Acceptance line 287 and TDD rows at lines 263-264 demand byte-for-byte preservation of `label`, `schedule`, `command`, `machines`, `requires`, `log`, and `is_claude_task`. The current YAML uses folded scalars (`command: >-`, `description: >-`) and inline lists (`machines: [dev-primary, ace-linux-1]`). YAML round-trippers (PyYAML default dumper, ruamel.yaml without preserve-quotes) routinely re-flow folded scalars and convert flow-style lists to block style. The plan does not specify the YAML round-trip tooling (e.g., manual edit only, or `ruamel.yaml.YAML(typ='rt')`). An implementer using a naive dumper will fail the byte-for-byte test on non-description fields even when only the description was semantically changed. Pin the editing approach (manual unified-diff edit only, or a specific round-trip library version), or relax the criterion to "semantic preservation under a stated normalizer".

## Blockers

- Finding #1: the approval gate cannot be cleared in the current environment (codex-cli 0.124.0 stdin-hang + empty Claude/Gemini fanout). The plan must either (a) pin the workaround (downgrade Codex CLI, GitHub-connector fallback, or pre-authorized UNAVAILABLE per AI review policy), or (b) acknowledge that gate-clearing is an out-of-band tooling task and not part of the implementation scope.
- Finding #2: the policy-driven section-order requirement needs either an explicit "the reorder fixture must use a non-canonical YAML" clause in the TDD row, or a stronger test that asserts `_write_markdown_artifact()` reads `ranking_policy.section_order` directly (e.g., monkeypatch + assert call).
- Finding #3: the `docs/standards/weekly-skills-audit-policy.md` documentation criterion needs either a TDD row that grep-asserts a named heading or a quoted insertion-point excerpt — otherwise the criterion is unverifiable.
- Finding #4: `scripts/skills/issue_2488_disposition_report.py` needs at least one TDD row asserting the file exists, is invokable, and produces `docs/reports/issue-2488-skills-disposition.md` end-to-end — otherwise the "bounded helper" is structurally undefined and the closeout step has no executable home.
