## Findings

1. **Markdown rendering "refactor" is structurally undefined and silently reorders operator-facing output.** Plan §Pseudocode line 200 and Acceptance Criterion line 310 require `_write_markdown_artifact()` to "consume `ranking_policy.section_order` for the exact six policy-governed sections" while "v2-family legacy sections remain literal." The plan does not specify where the policy-driven loop and the literal calls interleave: if `section_order` iteration replaces the call site, v2-family sections move from their current mid-position to *after* `unresolved_high_confidence_findings`/`suppressed_carry_forward_findings`/`operational_errors_or_skipped_inputs`, materially changing weekly report layout. Tests #287 (`test_policy_section_order_reorders_all_policy_governed_sections`) and #288 (`test_markdown_refactor_preserves_legacy_literal_sections`) demand both behaviors but specify neither's relative position. AC line 311 covers semantic regression, not visible reorderings. This is the load-bearing rendering surface for the entire weekly cron.

2. **Approval-gate review evidence path is unconfirmed and likely unproducible at present.** Plan line 8 records "Approval-gate review artifacts: TBD after fresh post-revision review" and AC line 321 requires "no unresolved MAJOR findings from available reviewers." The latest mutable fanouts at `scripts/review/results/2026-04-25-plan-2488-{claude,codex,gemini}.md` are all 0 bytes with a 70KB `2026-04-25-plan-2488-codex.md.err` sidecar. Workspace auto-memory documents `feedback_codex_cli_0_124_upstream_regression.md` — installed 2026-04-23, blocks all `codex exec` calls regardless of stdin redirection, #2479 filed, workaround = downgrade to 0.123.0. The plan offers no concrete dispatch path for producing the missing approval-gate Codex artifact, no commitment to the documented downgrade workaround, and no fallback statement that names which combination of available providers (e.g., Claude-only or Claude+Gemini) satisfies the gate under AC #321's "remaining required reviewers have no MAJOR findings" carve-out. The plan as written cannot pass its own approval gate.

3. **`informational_namespace` field collides with existing `informational` field — gratuitous schema drift.** Plan §Pseudocode line 177 and AC line 308 introduce `informational_namespace: true` on path objects in `inventory_summary.paths.filesystem_only_active`. But `weekly_skills_audit.py:86` already produces `informational=True` on inventory items derived from `INFORMATIONAL_DIRS = {"_core","_internal"}` (line 33). The plan does not say whether the new field re-uses, mirrors, or duplicates the existing classification, nor whether downstream consumers (baseline carry-forward at `_baseline_finding_sources()`, splitter at `_split_informational_findings()`) get the new key, the old key, or both. This is exactly the "parallel semantic" pattern that creates contributors-since-then drift.

4. **`legacy_diverged_compatibility_total` semantics under-specified vs. existing pruning walk.** Plan §Pseudocode line 173 specifies "de-duplicated union of tracked and filesystem SKILL.md paths containing an exact `_diverged` path segment." But `build_inventory()` at `weekly_skills_audit.py:72` prunes `_diverged` from the dirwalk entirely. The plan's line 163 says "do not reuse the existing duplicate/collision `build_inventory` walk for inventory totals" but does not state whether the duplicate/collision detection pipeline (`_detect_findings`, `_detect_wrapper_pairs` at lines 164-318) now consumes the new non-pruning walk. If it does, `{finding_key, severity, paths}` tuples could include `_diverged` paths, invalidating AC line 311's zero-delta requirement; if it does not, two parallel inventory walks must be maintained without a contract for which classifications use which.

5. **File-hash schema is inconsistent across dispositions and the "rejected legacy fields" set is unnamed.** Pseudocode line 215 enumerates: `reviewed_file_sha256` (promote_commit, ignore_generated_transient), `pre_redaction_sha256`+`final_file_sha256` (redact_then_commit), `original_file_sha256`+`final_consolidated_sha256` (consolidate_then_commit), `original_file_sha256` (archive/delete). Five distinct key names spread across six dispositions with overlapping semantics (e.g., `reviewed_file_sha256` vs. `final_file_sha256` for the same on-disk content). Test #298 (`test_file_hashes_rules_are_disposition_specific`) requires the validator to "reject singular legacy hash fields" but the plan never names what those legacy fields are. Implementation will re-litigate the canonical schema.

6. **Trust-attestation hash inputs lack normalization rules.** Pseudocode line 212 names `git_ls_files_sha256`, `filesystem_walk_sha256`, and `inventory_json_sha256_when_replayed` as gate-critical fields. None of: byte-vs-text mode, line ordering (locale/case sensitivity), `git ls-files -z` NUL handling, line-ending normalization (CRLF on Windows agents), or encoding is specified. The same `git ls-files` output can hash differently across machines/git versions, producing false trust mismatches that block the manual reconcile (exit 3) for unrelated reasons. This is the security-critical check stopping `--inventory-json` replay from bypassing live inventory; spec-by-implementation invites bypass-by-coincidence.

7. **CLI exit-code 4 contract is hand-waved.** Pseudocode line 207 requires usage errors return exit code 4 instead of argparse's default `sys.exit(2)`, "via an explicit `ArgumentParser` subclass or equivalent parser wrapper." Argparse exits 2 from multiple internal sites — `error()`, mutually-exclusive group violations, `type=` callable failures, `BooleanOptionalAction` parsing failures, and `--help` SystemExit are not all routed through `error()` alone. The plan does not pin which override points are required nor name a minimum Python version (`BooleanOptionalAction` requires 3.9+). Test #277 (`test_manual_reconcile_strict_boolean_optional_action`) will pass with a partial implementation that nonetheless leaks default exit code 2 from edge cases, defeating exit-code-4-vs-2-vs-3 disambiguation in operator runbooks.

8. **Mirror-symlink invariance has no integration-level enforcement.** Plan AC line 312 states `.codex/skills` and `.gemini/skills` "remain symlink mirrors; no provider duplicate skill trees are created." Test #268 (`test_inventory_summary_records_provider_skill_mirror_symlinks`) uses a "resolver-injection seam" rather than walking the real on-disk symlinks, by design ("without platform-dependent symlink setup"). Result: a future commit that converts `.codex/skills` from a symlink to a directory passes the unit suite. The plan files no precommit hook, CI step, or runtime check that re-verifies the actual links.

9. **`git add -f` workflow is unprotected against silent no-op staging.** AC line 314 requires "targeted `git add -f`" for ignored-path promotions. No automation gate (precommit hook, CI grep, staging guard) catches an operator who forgets `-f`; the result is silent no-op `git add` for any path under `digitalmodel/`, `memory/`, or `personal-*`. Workspace auto-memory `feedback_retry_loop_reset_hazard.md` documents prior incidents in this repo where staged-state under auto-sync contention was lost. This plan introduces a manual `-f` step in exactly the same risk surface without enforcement.
