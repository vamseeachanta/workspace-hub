## Findings

1. **Family-naming inconsistency between plan §Pseudocode line 197 and existing audit-code/policy convention (Files-to-Change row for `weekly-audit-policy.yaml`).** Plan pins family key `filesystem_only_findings` for `summary_counts` / `_baseline_finding_sources()` integration, while the rule path is `v2.rules.filesystem-inventory.filesystem-only-active`. Existing audit code at `scripts/skills/weekly_skills_audit.py:622-641` follows a `<family-group-with-hyphens>` (in rule path) → `<family_group_with_underscores>_findings` (in JSON arrays) convention: `content-quality` → `content_quality_findings`, `grouping` → `grouping_findings`, `size` → `size_findings`, `usage` → `usage_findings`. Following that convention, the JSON array key would be `filesystem_inventory_findings`, not `filesystem_only_findings`. The plan's chosen name breaks the family-group=first-rule-segment invariant that the rest of the codebase relies on. Pin one form (recommend `filesystem_inventory_findings` for consistency) and update §Pseudocode, §Files-to-Change, and the TDD row at line 283.

2. **Verifier predecessor-check algorithm is under-specified (Files-to-Change line 252).** Plan says `verify_issue_2488_baseline_order.py` must "require a strict predecessor commit (not same commit and not same-second timestamp only)". The parenthetical implies a timestamp-based comparison, but git commit ordering is parent-graph reachability, not committer-timestamp ordering — `git rebase`, `git commit --date`, and CI bots routinely produce commits whose timestamps do not reflect topology. A timestamp-based check can both false-pass (back-dated commits) and false-fail (rebased commits with identical timestamps and a true parent-child relationship). Pin the algorithm to `git merge-base --is-ancestor <fixture_sha> <first_logic_sha> && <fixture_sha> != <first_logic_sha>` and remove the timestamp wording, or explicitly justify why timestamps are authoritative here. TDD row at line 293 (`test_issue_2488_baseline_order_guard_fails_same_commit`) tests one negative case but does not pin the positive algorithm.

3. **`scripts/enforcement/verify-issue-2488-baseline-order.sh` location violates the project's own enforcement-gradient rule (Files-to-Change line 251 vs. `.claude/rules/patterns.md`).** The patterns rule documents `scripts/enforcement/*.sh` as Level-2 bindings ("auditable, testable" exit-0/1 gates called from "skill or CI"); cited examples are `check-no-abs-paths.sh` and `check-harness-file-size.sh`, both exit-status enforcement gates. The plan explicitly downgrades this script to "manual review-package completeness check, not an automated hook/CI hard gate" (line 224), which is Level-0 prose. Putting a Level-0 convention check at a Level-2 path-of-record will mislead future readers expecting hook/CI binding. Either move the helper out of `scripts/enforcement/` (e.g., to `scripts/skills/` next to its `.py` companion) or escalate to Level-2 by binding it in a pre-push hook or CI workflow that the plan also lists as created.

4. **`_diverged` segment treatment in the active filter is internally contradictory (Pseudocode line 163; Acceptance line 308).** Plan says `_diverged` "remains included in #2488 active counts only because #2488's issue-body active-loss contract named `_archive`/`_archived` as non-active" and is also reported as a separate legacy-compatibility count. By the project's own `_diverged` convention (the legacy `EXCLUDED_DIRS` excludes it from duplicate/collision precisely because it is quarantined), counting an untracked `_diverged/.../SKILL.md` as an "active loss-risk" finding contradicts the segment's semantic. Plan acknowledges (line 106) "zero current `_diverged` filesystem-only active SKILL.md paths" — so the rule is harmless today but creates a future false-positive surface. Either exclude `_diverged` from the active-loss filter (matching the segment's semantic) or document a single canonical interpretation and remove the dual "included in #2488 active counts AND reported separately" double-count surface.

5. **Split rendering paths in `_write_markdown_artifact()` are fragile (Pseudocode line 199; AC line 307; TDD row line 284).** Verified at `scripts/skills/weekly_skills_audit.py:809-869`: the renderer issues ten literal `_append_finding_section(...)` calls plus an inline `lines.append("## Suppressed / Carry-Forward Findings")`. Plan promises a refactor where exactly six policy-governed sections (`new_findings`, `changed_findings`, `filesystem_only_inventory`, `unresolved_high_confidence_findings`, `suppressed_findings`, `operational_errors`) consume `ranking_policy.section_order`, while v2-family sections (Content Quality, Grouping, Oversized, Usage, Follow-up Candidates) "remain literal legacy sections unless separately added to policy". After this change, the renderer has *two* rendering paths that an implementer must keep in sync; reordering anything but the six requires a code edit. The TDD row only tests the six-section reorder, so a partial implementation that hard-codes interleaving order between literal and policy-driven sections passes tests but breaks future policy work. Pin: either a single `section_order` walker with literal-fallback for unlisted sections, or list all ten sections under `weekly_summary_sections` now and run them all through the policy loop.

6. **Plan §Implementation Flow line 225 wording is ambiguous against the verifier's strict-predecessor rule.** Line 225 says "capture `tests/fixtures/skills/issue-2488-archived-duplicate-baseline.json` from current pre-change audit behavior and **commit/include it with the first implementation commit**" — but the verifier at line 252 requires the fixture commit to be a *strict predecessor* of the first audit/policy logic commit.
