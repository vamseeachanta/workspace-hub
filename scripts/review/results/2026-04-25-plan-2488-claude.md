## Findings

1. **`_diverged` active-loss semantics are asymmetric and undermotivated.** Plan §Pseudocode line 156 says `_archive` and `_archived` are excluded from active loss-risk counts but `_diverged` "remains included in #2488 active counts." Existing audit semantics treat `_diverged` like `_archive` — `EXCLUDED_DIRS = {"_archive", "_diverged"}` (verified at `scripts/skills/weekly_skills_audit.py:32`) and the existing test is named `test_excludes_archive_and_diverged` (`tests/skills/test_weekly_skills_audit.py:74`). The plan's only justification is "report legacy `_diverged` exclusion separately for compatibility metrics." If `_diverged` is conventionally archive-like, treating a future `_diverged` skill as active loss-risk will generate false positives. Either fold `_diverged` into the loss-risk exclusion alongside `_archive`/`_archived`, or document the convention reason `_diverged` differs.

2. **The new manual-reconcile script's CLI contract is underspecified.** Files-to-Change line 229 creates `scripts/skills/reconcile_filesystem_only_skills.py`, and acceptance line 293 binds it to the exact invocation `scripts/skills/reconcile_filesystem_only_skills.py --disposition-report docs/reports/2026-04-25-skills-disposition-2488.md`. But §Pseudocode line 197 names only an internal function `validate_and_render_dispositions_for_manual_reconcile(disposition_yaml)` — never declaring `--disposition-report`, `--ledger`, default ledger path, or exit-code contract. Plan's own RED-before-GREEN flow (line 213) cannot write tests against an undeclared surface. Add an explicit CLI declaration to §Pseudocode or §Files-to-Change.

3. **Sparse-checkout / partial-inventory detection signal is unspecified.** Acceptance line 297 requires sparse-checkout states to be "detected or warned," and §Pseudocode line 199 says "git errors, sparse checkout, or partial inventory are hard failures in manual reconcile but warning-only in weekly_report." Nowhere does the plan say HOW partial vs complete is distinguished — `git config --get core.sparseCheckout`? `git ls-files | wc -l` below a threshold? Without a defined signal, the corresponding test `test_sparse_checkout_or_partial_git_inventory_is_warned_not_trusted` (line 266) can only be exercised via a mocked adapter return value, which proves nothing about real behavior.

4. **Five of six untracked paths are ignored by parent-directory rules — force-add policy decision is deferred per-skill but is structural.** `git check-ignore -v` confirmed: `digitalmodel/` (line 14) ignores five paths; `personal-*` (line 270) ignores one; `memory/` (line 291) overlaps. The plan's force-add rule "use targeted `git add -f` only after ledger scan/disposition approval" (line 289) treats this case-by-case, but the upstream question — whether `.claude/skills/digitalmodel/`, `.claude/skills/memory/` paths are ever promotable given those ignore rules existed before skill carve-outs — is structural across the entire batch. A reviewer cannot tell from the plan whether `digitalmodel/` line 14 was authored to also exclude `.claude/skills/digitalmodel/` or only the repo-root `digitalmodel/` submodule. The plan should record this disambiguation as a planning-time decision, not leave six identical force-add evidence rows to be re-litigated at review time.

5. **Plan-review gate becomes unreachable when Gemini is UNAVAILABLE for infra reasons.** §Adversarial Review Summary at line 308 records `Gemini | UNAVAILABLE — CLI filesystem scan errors`, and line 310 says "do not move to `status:plan-review` until the next review pass has no MAJOR findings." Per session memory (`feedback_gemini_trust_env_blocks_reviews`, `feedback_gemini_sandbox_overlay_blindness`), Gemini-UNAVAILABLE is a recurring infra failure unrelated to plan content. The plan does not specify which provider's verdict is load-bearing if one provider is permanently UNAVAILABLE — the gate text reads as if all three must be MINOR-or-better, which is unreachable when Gemini's env is broken. Add an explicit "UNAVAILABLE counts as N/A, not blocking" rule.

6. **Acceptance line 293 references `--disposition-report` flag that pseudocode does not declare.** Internal contradiction: line 293 binds implementation to `scripts/skills/reconcile_filesystem_only_skills.py --disposition-report …`, but §Pseudocode line 197 and §Files-to-Change line 229 never enumerate this flag. If the flag name is wrong, every test that asserts the invocation will be wrong too.

For a "machine-checkable" ledger (acceptance line 258 implies it), this matters — string-equality vs timestamp comparisons diverge under non-UTC drift.

If implementation lands on a different date, the filename is misleading. Either bind the date to plan-creation (state this explicitly) or use an implementation-time date.
