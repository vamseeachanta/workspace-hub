## Findings

1. **Hermes-row gitignore citation is wrong, and this propagates straight into the disposition ledger evidence at validation time.** Plan §Tentative Disposition Table line 121 cites `(.gitignore:14 digitalmodel/)` as the ignored-path evidence for `.claude/skills/memory/hermes-memory-bridge/SKILL.md`. Verified live: `git check-ignore -v .claude/skills/memory/hermes-memory-bridge/SKILL.md` returns `.gitignore:291:memory/` — not line 14, and not `digitalmodel/`. Per the plan's own Pseudocode line 216 and acceptance line 309, every promote/redact-of-an-ignored-path entry must record `force_add_attestation_when_ignored.{gitignore_rule, gitignore_line}` matching the actual rule. The previous Claude immutable review (`20260425T125029Z-plan-2488-claude.md` finding #8) flagged this exact mistake and the §Adversarial Review Summary's "Revisions made based on review" list at lines 336-340 does not include a fix for it. The plan currently pre-cites evidence that the implementation must contradict before it can pass validation.

2. **The Markdown section name is specified inconsistently across the three contracts that must agree.** Pseudocode line 199 mandates `append Markdown section "Filesystem-only skill files"`. Acceptance criterion line 305 says the same: `"Filesystem-only skill files"`. But TDD row line 269 (`test_weekly_markdown_surfaces_filesystem_only_active_skills`) asserts the Markdown `includes 'Filesystem-only active skills' section`. As written, an implementation that follows pseudocode/acceptance will fail the TDD assertion; an implementation that follows the TDD will violate acceptance line 305. Pin one literal string and use it in all three places.

3. **The plan's Artifact Map cites three 0-byte mutable fanout files as plan-review evidence.** `wc -l scripts/review/results/2026-04-25-plan-2488-{claude,codex,gemini}.md` returns `0 0 0`. Sibling `.err` files exist (visible in the session's `git status` output). The plan's Artifact Map lines 139-141 list these mutable paths as "Plan review — Claude/Codex/Gemini" without any annotation that they are empty. The plan's narrative at line 335 ("canonical mutable fanout files are not the approval evidence unless they are copied into immutable artifacts after the run") is the *correct* policy, but the Artifact Map itself contradicts that policy by citing them as artifacts. Either drop the mutable rows from the Artifact Map, or annotate each as `(empty/dispatch failed; see immutable timestamped row)`. As written, an operator following the table sees four artifacts, three of which are empty — exactly the failure mode the plan's own acceptance criterion line 316 was added to prevent.

4. **Acceptance line 314 binds `TestScheduleIntegration.test_validate_schedule_still_passes_with_skills_curation_task` to "assert the updated text", but the test as it exists at `tests/skills/test_weekly_skills_audit.py:579` is named `test_validate_schedule_still_passes_with_skills_curation_task` — a structural-validation test, not a description-text assertion.** Plan line 314 commits to "asserts the updated text while preserving schedule/command", which would require modifying the existing test to add a substring/equality assertion on the new description string. That modification is not listed in §Files to Change as an edit-of-this-test (line 240 says "if scheduled YAML description changes" and refers to the same test, but no concrete substring is pinned). Without the new v2 wording fixed in the plan, the implementation can land arbitrary description text and the assertion is unfalsifiable. Pin the v2 description string verbatim in the plan or in a referenced fixture.

5. **The `_diverged` legacy-compatibility-count contract is described in §Pseudocode and §Acceptance but never gets a TDD assertion that it remains a separate, non-zero metric when `_diverged` paths exist.** Pseudocode line 163 and Acceptance line 306 say `_diverged` "remains included in #2488 active counts and is also reported in a separate legacy-compatibility count". TDD row 267 (`test_inventory_summary_excludes_archive_archived_and_reports_diverged_compatibility_count`) only checks that `_diverged` *is* included in #2488 active counts and *is* reported in a separate count — but the plan's verified live data shows zero `_diverged` filesystem-only active paths today (Plan line 107). Keep the row, but add a sub-fixture with at least one `_diverged` SKILL.md and one matching tracked path so the dual-count semantics is exercised, not just declared.
