## Findings

1. **EXCLUDED_DIRS change has hidden blast radius beyond the active filter.** Plan §Risks line 213 says to "extend `EXCLUDED_DIRS` to include `_archived`." But that constant is used in two places: the `os.walk` prune at `scripts/skills/weekly_skills_audit.py:72` (intended target) AND `_skill_counts.excluded` at line 526 (top-level glob). Adding `_archived` will (a) silently drop the 6 currently-tracked `email/_archived/*/SKILL.md` skills from `inventory`, removing them from any duplicate/collision finding they currently participate in; (b) shift the `_skill_counts.excluded` counter; (c) likely break any existing fixture that exercises duplicate detection against `_archived` paths. The plan's TDD entry `test_existing_weekly_audit_behavior_remains_backward_compatible` cannot catch this unless current fixtures already contain `_archived` paths — and they don't appear to. **Recommended:** introduce a separate `ACTIVE_EXCLUDED_DIRS = EXCLUDED_DIRS | {"_archived"}` used only by the new active-filter, leave `EXCLUDED_DIRS` untouched, and add an explicit test that asserts `email/_archived/*/SKILL.md` continue to appear in pre-existing duplicate/collision pipelines.

2. **JSON contract field name drift across the plan.** Pseudocode line 113 returns `missing_tracked_total, missing_tracked_active`. TDD test on line 165 asserts `missing_tracked_active`. But Acceptance Criterion line 185 references `missing_active_tracked_from_fs = 0`, and the live evidence block line 64 prints `missing_active_tracked_from_fs`. The output JSON contract is named inconsistently in the plan itself — implementers will pick one and the other section will be wrong.

3. **`INFORMATIONAL_DIRS = {"_core", "_internal"}` is unaddressed in the active filter.** The script (line 33) treats `_core`/`_internal` SKILL.md files as `informational_only`, not excluded. Both top-level dirs exist on disk. The plan's active-filter spec (Pseudocode line 108, Acceptance line 181) enumerates only `_archive`/`_archived`/`_diverged`. So under the plan's filter, every `_core`/`_internal` SKILL.md still counts as "active" — including for filesystem-only loss-risk accounting. That contradicts the existing script's semantic that those dirs are explicitly *not* operational/active routing material. Plan must either (a) extend the active-filter to also treat informational dirs as non-active, or (b) document why they're counted as active here.

4. **Per-skill disposition for the 6 known files is deferred to implementation, defeating the plan-review surface.** Issue #2488 acceptance criterion lists "All six active filesystem-only skills are individually classified with an explicit disposition" as the central deliverable. The plan punts this to "implementation-time discovery" (Acceptance line 183, Pseudocode line 124). That means the user-in-the-loop reviewer cannot assess the headline disposition decisions during plan-review — they're approving a process that picks dispositions later. At minimum the plan should include a tentative disposition table for the six known paths *as part of plan body* so plan-review approval covers the substantive decisions, not just the audit plumbing.

5. **Acceptance Criterion line 186 (`uv run pytest tests/skills/test_weekly_skills_audit.py -q`) is partially circular.** The plan modifies `tests/skills/test_weekly_skills_audit.py` (Files-to-Change row). After modification, asserting "this test file passes" is tautological — the implementer authored the failing/passing tests. To verify backward-compat, either (a) freeze a list of pre-existing test names at pre-implementation HEAD and assert that subset still passes, or (b) commit the new tests in a separate commit so the diff scope is auditable.

6. **Disposition report has no schema/persistence test.** Plan creates `docs/reports/2026-04-25-skills-disposition-2488.md` (Files-to-Change line 153) but the TDD list only validates *input* (requires reason, valid disposition values). No test asserts the report file is generated at the documented path, has a stable Markdown schema, or that a follow-up audit run reads it back to mark previously-dispositioned skills as resolved. The next weekly run could re-flag the same six skills as loss-risk findings indefinitely.

7. **Symlink mirror test is platform-conditional, leaving Linux production behavior under-protected.** TDD entry `test_inventory_summary_records_provider_skill_mirror_symlinks` (line 167) is hedged: "Linux tmp_path symlinks guarded by platform capability." If this test skips on Windows CI, the symlink-recording feature can silently regress on Linux too because no other test exercises it. Plan should specify deterministic resolver-injection (option A) and drop the platform guard, OR commit to a Linux-only required check in CI.

8. **Wrapper script invariance is not asserted.** `scripts/cron/skills-curation.sh` is not in Files-to-Change, but Files-to-Change adds a new required output artifact (`docs/reports/2026-04-25-skills-disposition-2488.md`). The plan should affirm explicitly that the wrapper needs no change because the new artifact path is computed by the audit script independent of `--output-dir`. Without that affirmation, the cron'd path may drift.

9. **Citation drift — minor but breaks retrieval-skepticism contract.** Plan §Evidence line 51 cites `weekly_skills_audit.py` "line 29" for `EXCLUDED_DIRS = {"_archive", "_diverged"}`. Actual location is line 32. Content matches, but a plan that asks reviewers to trust line citations should not have stale ones.

10. **No commit attestation linking dispositioned skills to a specific audit-run hash.** Per the workspace's own feedback memory `commit_attestation_narrow_scope`, "gates passed" attestation only covers the files in that commit. The plan creates a disposition report and then expects future weekly audits to skip those skills as resolved — but there's no mechanism in the plan tying a disposition entry to the audit-run timestamp/hash that produced it. A future audit re-run with different inventory state (e.g., a skill renamed) would have no way to detect that the existing disposition entry is now stale.
