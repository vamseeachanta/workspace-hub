## Findings

1. **Tentative-disposition vocabulary leaks into a runtime-ledger context (plan §Tentative disposition table, lines 117-122).** Rows use `pending_full_file_scan_and_user_authorization` (line 117) and `pending_full_scan` (lines 118-122) as their `Tentative disposition` value. The runtime allowed-disposition enum at Pseudocode line 216 is `promote_commit | consolidate_then_commit | redact_then_commit | archive_intentionally | ignore_generated_transient | delete_if_junk` — none of those match. Inconsistency between rows is itself a defect: line 117 uses the longer string, lines 118-122 use the short form, so the table is not even self-consistent. Without an explicit disclaimer that "tentative" labels are review-time only, an implementer could (a) try to write `pending_full_scan` into `config/skills/filesystem-only-skill-dispositions.yaml` and have validation fail, or (b) misread the table as a runtime contract. Pin a one-sentence disclaimer that tentative dispositions are review-time placeholders only and do not appear in the runtime ledger.

2. **Baseline-order ancestor check is reflexive in the spec but rejected by the TDD row (Pseudocode line 254 vs TDD line 295).** Pseudocode line 254 says the check is `git merge-base --is-ancestor <baseline_source_commit> <first_logic_sha>` plus tuple-set recompute. `git merge-base --is-ancestor A A` exits 0 — treats a commit as its own ancestor — so a same-commit baseline passes the spec as written. But TDD row at line 295 (`test_issue_2488_baseline_order_guard_fails_same_commit`) requires the implementation to *reject* same-commit baselines. The implementation will need an explicit `<>` check that the spec does not call out. Pin: "the ancestor check must be strict (non-reflexive): `is-ancestor A B` returns 0 AND `A != B`".

3. **`partial_inventory` detection rule is undefined (Pseudocode line 207-208 + Trust attestation schema line 211).** The plan lists trust failures as "git adapter reports a partial/truncated result" and "skills tree is incomplete" and includes `partial_inventory: bool` in trust_attestation. But no deterministic rule says what counts as partial: count of `git ls-files -- <skills_dir>` below some threshold? sparse-checkout pattern fails to include `<skills_dir>/**`? path-count mismatch between `git ls-files` and a sparse-cone reverification? TDD row 282 (`test_manual_reconcile_hard_fails_on_untrusted_or_partial_inventory`) lists triggers but not the boolean rule. Without a pinned definition, two implementations could disagree on whether the same checkout is "partial". Recommend: define `partial_inventory := (git config --bool core.sparseCheckout == true) AND (git sparse-checkout list does not include a pattern that covers <skills_dir>/**)` or an equivalent deterministic check.

4. **`trust_attestation.inventory_json_sha256_when_replayed` lifecycle is undefined for live closeout (Pseudocode line 211).** Schema requires the field on the trust attestation; live closeout writes "a new trust attestation output at --trust-attestation" (line 207). What does the field hold during a live run that has no `--inventory-json` input? If null, replay matching is impossible (because the next run would compare against null). If sha256 of the live-serialized inventory dump, the plan must say so. Pin: "during live closeout, the field is the sha256 of the live-serialized canonical inventory JSON written alongside the trust attestation; during replay, matching requires sha256(--inventory-json bytes) == trust_attestation.inventory_json_sha256_when_replayed".

5. **`verify_issue_2488_baseline_order.py` has no mechanism for running audit code at `baseline_source_commit` to recompute tuple-set hash (Pseudocode line 254 + Files to Change line 254).** The plan says the helper "recompute[s] the tuple-set hash from `baseline_source_commit`". A naïve implementation could (a) checkout the baseline commit (destroys working tree), (b) `git show <sha>:scripts/skills/weekly_skills_audit.py` and run that against the *current* skills tree (semantically wrong), or (c) `git worktree add` (correct but transient). The plan doesn't pin (c). Without a pinned mechanism, the entire baseline-order proof can be a no-op that always passes. Pin: "`verify_issue_2488_baseline_order.py` uses `git worktree add` to materialize a transient checkout at `baseline_source_commit`, runs the audit script as it existed at that commit against the skills tree as of that commit, hashes `{finding_key, severity, paths}` tuples, and removes the worktree". Add a TDD row covering the worktree mechanism.

6. **The 0-byte canonical fanout files (`scripts/review/results/2026-04-25-plan-2488-{claude,codex}.md`) are checked into the worktree at HEAD and remain referenced in §Artifact Map lines 140-143.** Plan disclaims them as "(diagnostic only; not approval evidence)", but a future reviewer following the §Artifact Map link sees zero bytes, with `.err` sibling files (also at HEAD per `git status`). This creates audit-trail noise: a downstream reader cannot tell whether the dispatch was attempted-and-failed, attempted-and-empty, or attempted-and-the-tool-truncated. Recommend: either delete the empty files and let `.err` files alone carry the dispatch-failure signal, or repopulate them after fresh dispatch before posting `status:plan-review`. Acceptance criterion line 328 requires "non-empty" approval-gate artifacts — but the same set of mutable canonical filenames is referenced in two roles (diagnostic vs gate) without a path-naming distinction, so a careless reviewer could miss the disclaimer.
