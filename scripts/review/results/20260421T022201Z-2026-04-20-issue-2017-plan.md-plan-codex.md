### Verdict: MAJOR

### Summary
The plan is materially stronger than earlier drafts, but it still has two unresolved contract-level contradictions and one evidence gap that block approval. The main problems are Gmail-side actions remaining in scope despite the v6 local-only fence, inconsistent ownership for when state-machine tests turn green, and reliance on a missing scope-reference artifact for a key feasibility assumption.

### Issues Found
- [P1] Scope/feasibility contradiction: v6 says #2017 delivers a local queue contract only and does not automate Gmail-side delete/archive, but D6, the state machine, pseudocode, and tests still require `spam_archive` / auto-archive behavior for spam and routing-driven DELETE/REVIEW handling. That is Gmail mutation, so the plan is still partially blocked on `gmail.modify` or equivalent automation.
- [P1] Dependency contract is still inconsistent on who unblocks the contract tests. The ownership table says `tests/email/test_state_machine_contract.py` are xfail pending `#2026` storage implementation, but the TDD section says they cannot pass until `#2024` implements the pipeline and will flip when `#2024` lands. That leaves sequencing and acceptance ambiguous.
- [P2] A key premise is attested through a missing artifact: the plan cites `reference_gmail_mcp_scope.md` as evidence for Gmail scope limits, but the attested file-existence section says that file is missing. A hard scope boundary should not depend on a non-existent reference; the constraint needs to be restated as an explicit contract inside the plan or replaced with verifiable evidence.
- [P2] Acceptance criteria are incomplete around the follow-on boundary introduced in v6. The plan says automated Gmail delete/archive will move to a separate follow-on issue, but there is no acceptance criterion requiring that issue to be created, linked, and scoped before approval. Without that, the renamed behavior can drift back into #2017/#2024.
- [P3] Testing coverage is good on state transitions, but operational edge cases are underspecified: there is no explicit acceptance/test requirement for malformed YAML fixtures, duplicate `account_id::thread_id` keys during snapshot rebuild, or partial/corrupt JSONL recovery behavior after crash/truncation. Those are likely real failure modes for an append-only local queue.

### Suggestions
- Remove all Gmail-mutating behavior from #2017’s executable contract. Replace `auto-archive`, DELETE, and REVIEW effects with local classifications/events only, or explicitly move those behaviors into the follow-on issue and reference them as out of scope everywhere in the plan.
- Choose one dependency boundary for the xfail suite and make every section match it. If `#2026` owns the storage contract and `#2024` only orchestrates it, then the tests should flip on `#2026`; if not, rewrite the ownership table accordingly.
- Inline the Gmail scope constraint as a verified assumption in the design doc/plan itself, and add an acceptance criterion that the follow-on Gmail-mutation issue is filed and linked before `status:plan-approved`.
- Add one small recovery section covering corrupted/truncated JSONL, snapshot/key-collision validation, and invalid fixture/schema inputs, then attach explicit tests for those cases.

- Which issue is the real gate for flipping `test_state_machine_contract.py` from xfail to required pass: `#2026` storage or `#2024` pipeline orchestration?
