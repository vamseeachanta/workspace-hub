### Verdict: MAJOR

### Summary
Not approval-ready. The plan still relies on unverified narrative claims, includes speculative file targets, and leaves core bucket-policy decisions and test contracts too ambiguous for safe approval.

### Issues Found
- `Resource Intelligence Summary` is not evidence-tight. It asserts repo/report behavior without quoted excerpts, line references, or attested data from the cited artifacts, e.g. "current output still mixes generated-site / other-repo paths into actionable workspace-hub drift" and "the refreshed audit now explicitly shows providers with positive_corpus_growth_beyond_recent_activity." In the review packet, only file existence and issue title/state are attested; the underlying report contents are not. That fails item 1 and item 4 because the plan asks reviewers to trust uncited report interpretations rather than verify them.
- `Resource Intelligence Summary` contains a stale/contradictory claim: "there is still no dedicated plan artifact for #2333" while the artifact under review is itself `docs/plans/2026-04-22-issue-2333-provider-audit-drift-classification-expansion.md`. Even if this sentence meant "before this draft existed," that is not what it says. Approval-stage plans cannot carry obviously outdated resource-intel statements.
- `Files to Change` is not aligned with the evidence. `docs/plans/README.md` is listed for update solely to "index this plan," but indexing the plan is not part of the deliverable, acceptance criteria, or defect mechanism. That is unnecessary scope. `docs/ops/legacy-claude-reference-map.md if needed` is speculative for the same reason: the plan cites no verified evidence that the redirect map is wrong today, only that it "must avoid weakening" it.
- The deliverable/acceptance criteria/test table are not fully aligned on output shape. The deliverable promises "deterministic tests and clearer audit interpretation," and the TDD list includes `test_corpus_growth_anomaly_reporting_is_separate_from_recent_event_time_activity`, but the plan never defines the concrete report fields, bucket names, or serialization contract that the test should assert. Without a named schema or exact output surface, the test is non-falsifiable and the acceptance criterion "can explain positive corpus growth" is subjective.
- Core scope decisions are still open in `Risks and Open Questions`: "Should generated-site paths get their own dedicated bucket or be grouped under a broader adjacent-project/non-repo class?" That decision directly changes classifier behavior, report shape, and tests, yet the rest of the plan already assumes a concrete bucket set in the pseudocode, files-to-change table, TDD list, and acceptance criteria. This is an approval blocker, not a post-approval question.
- The plan does not define how to distinguish real recent event-time behavior from historical/backfilled/export-classification noise in an implementation-safe way. It says the audit should keep them separate, but provides no verified source field, timestamp basis, or algorithm for doing so. Because item 4 is central to the issue, this omission is material: the implementation team cannot write TDD-first tests for a distinction that is only described narratively.
- Several test rows are too vague to guarantee they fail for the intended defect classes. Examples: `sample Codex-style path set`, `representative github://... and digitalmodel/... samples`, and `synthetic provider delta input` are placeholders, not concrete fixtures. They do not specify exact paths, counts, or expected report fragments, so they leave room for a passing but incorrect implementation.
- `Acceptance Criteria` includes "Follow-up remediation guidance becomes more precise for Codex/Hermes/Gemini after the classification pass," but the plan does not name the artifact or function where that guidance lives, nor a measurable before/after condition. That criterion is not approval-testable and is unsupported by the listed file targets.
- The plan proposes to modify `docs/reports/provider-session-ecosystem-audit.md`, but does not state whether this report is generated, manually maintained, or a checked-in output derived from rerunning `scripts/analysis/provider_session_ecosystem_audit.py`. If it is generated, editing the report directly is the wrong target; if it is manual, the generation contract needs to be stated. As written, the target is unsupported and potentially incorrect.

### Suggestions
- Replace narrative resource-intel bullets with attested evidence: quote the exact path examples and report snippets that justify each proposed bucket, and cite the source artifact precisely enough for a reviewer to verify.
- Remove or rewrite the stale claim about there being no plan artifact for `#2333`. Approval-stage plans should not contain internally false statements.
- Resolve the bucket-policy decision before approval. State the exact canonical bucket names, precedence order, and one-line rule for each class, including whether generated-site is its own bucket or a subtype of a broader non-actionable class.
- Define the anomaly/event-time contract concretely: what input fields or derived signals indicate recent activity vs historical/backfilled/export-classification growth, and where that distinction appears in the report/output.
- Tighten the TDD table by naming exact fixtures and assertions. Use concrete path samples, expected bucket labels, expected counts, and expected rendered fields so each test can fail for the intended misclassification.
- Trim speculative scope from `Files to Change`. Drop `docs/plans/README.md` unless plan indexing is required by policy, and drop `docs/ops/legacy-claude-reference-map.md` unless the plan cites verified evidence that its current guidance must change.
- Specify whether `docs/reports/provider-session-ecosystem-audit.md` is generated output. If generated, say the implementation must rerun the audit and update the generated artifact indirectly through code/tests rather than manually editing the report.
- Rewrite acceptance criteria into measurable statements tied to named artifacts or functions, for example exact bucket totals, exact report fields, and preserved actionable-path counts for known fixtures.

### Questions for Author

- What concrete data signal will distinguish recent event-time behavior from historical/backfilled/export-classification noise in tests and reporting?
- Is `docs/reports/provider-session-ecosystem-audit.md` a generated artifact from `provider_session_ecosystem_audit.py`, or is part of the intended work a manual report edit?
