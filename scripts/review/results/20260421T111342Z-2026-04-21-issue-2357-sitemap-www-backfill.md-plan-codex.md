### Verdict: MAJOR

### Summary
The core implementation is small and the plan is mostly scoped correctly, but two acceptance/test invariants are underspecified in ways that make them hard to execute or keep as durable regression coverage. There is also an internal contradiction around duplicate handling versus row-count preservation that should be resolved before approval.

### Issues Found
- [P1] The proposed `sitemap_metadata_is_unchanged_row_for_row` check is not operationally specified. After the file is edited, there is no in-repo 'before' snapshot to compare against, so this cannot function as a normal regression test unless the plan defines a fixture/baseline source or limits it to a one-time execution check.
- [P1] The plan contradicts itself on duplicates. In pseudocode step 5 it allows row removal if normalization reveals duplicates, but the acceptance criteria and test list require both unique `<loc>` values and no net `<loc>` count change. Those conditions cannot all hold if any apex/www duplicates already exist.
- [P2] The test strategy mixes durable regression tests with one-off migration verification without clearly separating them. `zero apex entries` and `unique loc values` are stable regression checks, but `before/after metadata preservation` and `before/after loc count preserved` depend on pre-edit state and need either an explicit execution-only verification step or a persisted baseline fixture.

### Suggestions
- Split validation into two classes: durable Jest regression checks that run forever, and one-time implementation verification steps documented in the execution checklist.
- Resolve the duplicate policy explicitly: either assert there are no pre-existing apex/www collisions and keep row count invariant, or allow deduplication and change the acceptance criteria accordingly.
- Define the baseline source for metadata/count comparison if you want those checks automated, for example a committed fixture, a captured pre-edit snapshot in the PR, or a git-based comparison procedure outside Jest.

### Questions for Author
- Do you want `metadata unchanged row-for-row` and `loc count preserved` to be permanent automated tests, or only execution-time verification for this migration?
- Have you verified that the current sitemap contains no apex entries that normalize onto already-existing `www` entries? If not, which invariant wins: uniqueness or preserved row count?
