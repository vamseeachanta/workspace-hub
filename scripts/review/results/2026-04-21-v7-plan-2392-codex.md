### Summary
The plan still leaves correctness-critical behavior unspecified in areas that affect gap counts, domain attribution, scheduler safety, and approval gating. It is not approval-ready.

### Issues Found
- `## Problem Statement` says the detector answers "which indexed or registry-backed sources have no corresponding L3 wiki coverage yet," but neither `## Candidate Record Shape` nor `## Pseudocode` defines any source-side deduplication across `index.jsonl`, `code-registry.yaml`, `standards-transfer-ledger.yaml`, `dde-standards-inventory.yaml`, and `promotions/*.yaml`. The same `doc_key` can appear in multiple source surfaces, which would double-count `gap`/`covered` totals and emit duplicate gap rows for one document.
- `## Problem Statement` and `## Deliverable` make output domain-specific (`"per-domain gap YAML"` / `"which disciplines have the highest uncovered source volume"`), but `## Pseudocode` marks a record covered solely on `if canonical_key in wiki_index:` with no domain check. A wiki page in the wrong domain would suppress a gap for the source domain and corrupt per-domain coverage accounting. The plan needs an explicit contract for cross-domain matches.
- `## Pseudocode` calls `load_required_inputs(required_inputs)` and later `return exit_code_for_run_status(run_status, allow_degraded=True)`, while `## TDD Test List` requires `test_missing_required_input_fails_closed` and `## Manual verification before approval` requires the dry run to `exit 0`. The plan never defines the exit-code contract for clean vs degraded vs missing-required-input runs. Without that, scheduler behavior and approval gating are not testable or reviewable.
- `## Scheduled Task Contract` proposes a command that ends with `git commit ... && git push origin main` on `machines: [dev-primary, ace-linux-1]`, but the plan does not define any precondition for a clean worktree, single-run exclusivity, or protection against concurrent/duplicate scheduled executions. A failover or dirty checkout can publish unrelated changes or race another runner. That is a correctness issue for automated publication, not just an operational nicety.
- `## Resource Intelligence Summary` includes the live-state claim `.planning/quick/review-2408-* artifacts still exist and are unrelated to this issue.` That claim is not covered by the attested evidence block, and the plan does not show why those artifacts are relevant to this issue at all. The review contract requires affirmative verification of correctness-critical claims; this one is both unverified and unnecessary noise in a plan that is supposed to reflect current repo state.

### Suggestions
- Add an explicit source deduplication contract keyed by canonical `doc_key`, including how conflicting metadata from multiple source surfaces is merged and how counts are computed after dedupe.
- Define whether coverage is `doc_key`-only or `doc_key + domain`. If cross-domain matches are allowed, add a separate diagnostic for domain mismatch so per-domain reporting is not silently wrong.
- Specify exact exit codes for at least: clean success, degraded-but-reportable success, and fail-closed missing-required-input/error. Tie those codes to tests and the scheduler contract.
- Harden the scheduled publication contract: require a clean checkout, prevent concurrent runs, and define what happens when the target machine is unavailable or the worktree is dirty.
- Remove unverified repo-state claims that are not backed by attestation, or add them to attested evidence if they are genuinely required for plan correctness.
