The bundle is a truncated 18-line compact proxy — only the title, reviewer instructions, and six acceptance criteria are visible; the entire task breakdown, TDD plan, rollback, dependencies, risk register, workflow file references, and adversarial review evidence are behind the "[truncated for Claude compact bundle]" marker. Cannot approve on what is visible.

### Issues Found
- Truncation blocks correctness review: lines 1–18 are all that is available; the bundle explicitly ends with `[truncated for Claude compact bundle]`. Task list, TDD steps, adversarial review artifacts, rollback, workflow file path(s), and dependency matrix are unreviewable. Per the bundle's own instruction (‘If a risk appears underspecified due to truncation, call that out explicitly’), this alone precludes APPROVE.
- Scope-narrowing mislabeled as ‘hardening’: Criterion 5 replaces `mypy src/ --ignore-missing-imports` with a 2-file target (`src/assethold/signals/watchlist.py`, `src/assethold/modules/reporting/utils/path_utils.py`). Criterion 4 does the same for flake8 (`.` → 6 enumerated paths). New or regressed files outside the tranche will silently escape type and lint checks. The plan title says ‘post-smoke CI hardening’; what is visible is coverage reduction. No criterion requires a compensating guard (e.g., a TODO-tracked expansion plan, a `# type: ignore` budget, a fail-on-new-untyped-file check, or an explicit `exclude` list in config that is reviewed when new files land).
- Enumerated tranche has no governance mechanism. Criterion 4 hard-codes six filepaths in prose. There is no visible single source-of-truth (e.g., a workflow env var or shared text file read by both CI and local verification), so the two flake8 invocations and future additions will drift. A typo in one of the six paths passes CI with `No files matched` semantics depending on flake8 invocation form — no criterion requires `--exit-zero=false`-style proof that each path actually matched at least one file.
- Self-policing evidence clause: Criterion 2 requires adversarial review evidence to ‘[reflect] the real verdicts / any invalid empty-artifact runs honestly,’ but specifies no independent verifier, no required artifact format, no hash/URL of artifacts, and no minimum content per artifact beyond ‘valid.’ ‘Valid’ is undefined. This is exactly the Codex-sandbox empty-artifact failure mode noted in feedback_codex_sandbox_write_blocked.md, yet no machine check is required to detect it.
- `types-PyYAML` criterion lacks a version pin and lacks a drift guard. Criterion 6 says the same package is used in workflow and local verification, but does not require a pinned version, a shared requirements fragment, or a check that the two installs resolved to the same version. A pure string match on ‘types-PyYAML’ will pass while CI and local resolve to different releases.
- Criterion 3 (‘continues to pass … before later gates’) is an outcome statement, not a verifiable gate. No criterion asserts the ordering constraint in the workflow YAML itself (e.g., that the smoke-test job/step is a dependency of flake8/mypy steps). If a future edit reorders steps, Criterion 3 can be satisfied locally while CI breaks the ordering invariant.
- No criterion covers rollback or revert path if the narrowed mypy target surfaces a regression in an unlisted file, or if `types-PyYAML` install fails on the workflow runner image. Plan visibility is zero on how to back out the change without re-broadening coverage in the same PR.
- No criterion references the workflow YAML file path(s) being edited. Reviewer cannot confirm that ‘the workflow’ is a single file or that both flake8 invocations live there. ‘Both flake8 commands’ (Criterion 4) implies two invocations, but their locations (pre-smoke vs post-smoke? matrix entries?) are invisible.
- Project workflow gates missing from acceptance criteria: CLAUDE.md requires `status:plan-review` → user approval → `status:plan-approved` before implementation. No visible criterion binds this plan to that gate, and ‘indexed in docs/plans/README.md’ (Criterion 1) is not equivalent.
- ‘Tranche’ is referenced in Criterion 4 without definition in the visible portion. If the truncated body does not define it precisely (file selection rule, ownership, expansion cadence), the six-file list becomes load-bearing prose with no sustaining process.

### Suggestions
- Resubmit the full plan, not the compact bundle, or confirm that nothing beyond the six acceptance criteria constrains implementation — in which case the gaps above are real, not artifacts of truncation.
- Reframe the change as ‘coverage-narrowing to unblock smoke-gate stabilization’ rather than ‘hardening,’ and add a follow-up issue (linked in the plan) to re-expand mypy/flake8 coverage with a target date. Keeps the scope honest and prevents the narrowed gate from becoming permanent.
- Replace the prose tranche list with a single source-of-truth: e.g., `CI_TRANCHE_PATHS` env var in the workflow, or a `ci/tranche.txt` read by both CI and the local verification script. Add a criterion that both flake8 invocations consume that source.
- Add a machine gate for Criterion 2: require each provider artifact to be a non-empty file ≥ N bytes, committed under a known path, and require the summary table row to match the artifact’s SHA or verdict header. That converts ‘honestly’ from aspiration to exit-code.
- Pin `types-PyYAML` to an exact version in both places and add a CI step that asserts the resolved version matches between workflow install and the local mypy venv (e.g., `pip show types-PyYAML | grep Version`).
- Assert step ordering in the workflow file structurally: make the lint/type steps `needs:` the smoke-test job, or add a workflow-lint unit test (`tests/unit/workflows/test_python_tests_workflow_order.py` is already in Criterion 4 — extend it to assert this invariant).
- Add an explicit rollback criterion: ‘If types-PyYAML install fails on runner image X, revert commit Y and reopen #2459’ — or wire a `continue-on-error: false` + documented revert SHA.
- Include the exact workflow file path(s) in the acceptance criteria so reviewers can diff against the change without reading the plan body.
- Add a criterion binding the plan to the project’s approval gate (`status:plan-approved` present on #2459 before implementation commits land).
