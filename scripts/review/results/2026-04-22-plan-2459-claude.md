### Verdict: MAJOR

### Summary
Plan correctly identifies the post-smoke blockers and the bounded scope, and the resource-intelligence section largely tracks the live workflow file at `assethold/.github/workflows/python-tests.yml` (flake8 at lines 92/94 use `flake8 .`, mypy at line 97 uses `mypy src/`). However, the plan has several real defects that materially weaken its verification story and will likely cause "green local, red CI" or "green CI, weaker gate" outcomes if executed as written. The most important: (1) the local TDD invocations bypass repo conftest/addopts while CI does not, (2) narrowing mypy from `src/` to two files is a coverage regression with no re-expansion mechanism, (3) the persisted workflow verifier is not wired into CI or pre-commit so it can't actually enforce the contract, and (4) the next post-mypy blocker (coverage thresholds 80/70) is not analyzed even though it is the most likely "next exposed surface" the deliverable promises to record.

### Issues Found
- CI/local validation divergence in TDD acceptance criteria. Acceptance lists `uv run python -m pytest ... --noconftest -o addopts= -q` but the workflow's `Run unit tests with coverage` step (lines 108-119) runs pytest with the repo's full conftest/addopts plus `--cov-fail-under=80` and `-m "unit"`. A green local run with conftest/addopts disabled does not prove a green CI run. There is no acceptance criterion that runs the new tests under the exact CI invocation, so the TDD gate can pass while CI still fails.
- Mypy gate coverage regression is undisclosed as a tradeoff. Workflow currently runs `mypy src/ --ignore-missing-imports` (98 source files). Plan changes the workflow gate to only `signals/watchlist.py` + `modules/reporting/utils/path_utils.py`. That removes type-checking enforcement from 96 files indefinitely. The plan defers to assethold#31 but does not commit to (a) a phased re-expansion list, (b) a deny-regression mechanism for currently-clean files, or (c) any signal that newly added files are type-checked. Risk section calls this out only as 'does not solve broad debt' — it does not acknowledge it is also an active reduction of an existing (broken-but-broader) gate.
- The persisted workflow verifier (`assethold/scripts/ci/verify_python_tests_workflow.py`) is not wired into CI or a pre-commit hook. Acceptance criteria only run it locally. A future commit can revert the flake8/mypy narrowing without tripping anything in CI, defeating the 'persisted contract' framing in the Adversarial Review Summary.
- Next-blocker analysis is missing for the most likely successor failures. After flake8/mypy pass, the next workflow steps are `Run unit tests with coverage` (`--cov-fail-under=80`) and `Run all tests with coverage` (`--cov-fail-under=70`). The plan promises to advance the workflow past current first blockers and 'record next exposed failure surface', but does not pre-assess whether the assethold package currently meets 80%/70% coverage. If it does not, the deliverable is technically met (next surface recorded) but the spirit ('CI advances') will be unsatisfied and a follow-up scramble is foreseeable.
- TDD red-state for the workflow verifier is not specified concretely. Plan says 'Before editing workflow/source files, run the persisted workflow-verifier and confirm it fails on current main', but does not specify which assertions must fail (e.g., flake8 target == `.`, mypy target == `src/`, missing `types-PyYAML`). Without that, the verifier could be authored to pass on current main and still appear TDD-compliant.
- types-PyYAML is added only at the package install step in the `test` job; the plan does not state whether it must also be added in the `integration-tests` and `financial-data-tests` install steps (lines 223-227, 273-277). This is fine today because mypy only runs in `test`, but the plan should confirm scope rather than leave it implicit, especially because the plan also exhorts 'use the same package for local targeted mypy verification'.
- Plan claim that `flake8 .` reports E999 in `.agent-os/modules/prompt_enhancement.py` is correct as a current-CI symptom, but narrowing flake8 hides that file forever from the gate without verifying the file is not imported at runtime. I verified there are no imports of `.agent-os` from `assethold/src` or `assethold/tests` (good), but the plan itself does not include that proof — it just defers to assethold#45. Add the no-import evidence to the resource-intelligence section so the deferral is auditable.
- Acceptance criterion 'A post-change CI run proves the workflow clears the current first post-smoke blockers and records the next exposed failure surface explicitly by run ID' is good, but there is no criterion that the post-change CI run must be on the same matrix cells (linux + macos for flake8, windows for mypy) that currently fail. A run that only covers one OS could spuriously satisfy the criterion.

### Suggestions
- Add a CI-parity acceptance command, e.g. `cd assethold && uv run python -m pytest tests/unit/ -m unit --cov=src --cov=. --cov-fail-under=80` — the same shape the workflow uses — alongside the `--noconftest -o addopts=` red/green isolation runs, so local validation cannot pass while CI fails.
- Add a small CI step that invokes `python scripts/ci/verify_python_tests_workflow.py` as part of the `test` job (or a new `verify-workflow-contract` job) so the persisted contract is actually enforced. Otherwise demote the verifier from 'contract' to 'developer aid' in the plan language.
- Either pre-flight `pytest --collect-only ... --cov ... --cov-fail-under=80` against current main to predict whether coverage will be the next blocker, or relax the deliverable language so it does not over-promise 'workflow advances'. If coverage will block, decide now whether to disable `--cov-fail-under` for this tranche (with a tracked follow-up) or absorb minimal additional coverage work.
- Make the mypy narrowing reversible-by-default: include a TODO list inside the workflow comment block enumerating the next files to add back, and add a follow-up issue link or assethold#31 sub-task that specifically tracks restoring `mypy src/` (not just 'broad debt'). Otherwise the gate calcifies at two files.
- Specify the verifier's failing assertions explicitly in the plan: e.g. 'verifier MUST fail when flake8 target tokens contain `.`', 'verifier MUST fail when mypy target equals `src/`', 'verifier MUST fail when `types-PyYAML` is absent from the dependency-install step'. This makes the TDD red-state for the verifier auditable.
- Embed in resource-intelligence the grep-evidence that `.agent-os/modules/prompt_enhancement.py` and `scripts/agent-os/create-spec-enhanced.py` are not imported by `src/assethold/` or `tests/`, so the flake8 narrowing is provably safe at runtime, not just at lint-time.
- Tighten the post-change CI acceptance criterion to require evidence on all three OSes that previously failed (ubuntu, macos, windows) for the flake8 and mypy steps specifically, by linking job IDs in the closeout comment.
