### Verdict: MAJOR

### Summary
The plan is materially stronger than earlier revisions, but it still has one critical requirement mismatch and a couple of contract inconsistencies that would create implementation churn downstream. In its current form, I would not approve it for implementation without tightening the deletion semantics, ownership/test handoff, and schema/test coverage around the state-store contract.

### Issues Found
- [P1] Critical: The plan does not currently satisfy the issue’s core "delete when done" requirement. D3 explicitly says the pipeline never deletes from Gmail and that `purged` is only a local state, which conflicts with both the issue title and the stated deliverable of an extract-first, delete-later workflow. Unless the issue was intentionally re-scoped, this is a requirements miss, not just an implementation detail.
- [P2] Important: There is still dependency/ownership drift in the TDD section. The document says state-machine tests are xfail pending `#2026` storage impl in multiple places, but the state-machine note still says they cannot pass until `#2024` implements the pipeline and will flip when `#2024` lands. That leaves downstream owners unclear on who must satisfy the contract and when.
- [P2] Important: The contract around the state store is incomplete relative to the design decisions. D1/D4 make `queue-state.jsonl`, `queue-state-snapshot.yaml`, `queue-state-snapshot.meta.yaml`, and `queue-learning-log.jsonl` part of the operating model, but the artifact map / acceptance criteria / explicit test list do not fully require schemas and tests for the meta file, learning log, freshness checks, or multi-account collision handling. Those are central correctness constraints, not optional details.
- [P3] Minor: Test coverage still misses a few edge cases that the plan itself elevates as important: same `thread_id` across different `account_id`s, stale snapshot meta triggering rebuild, and lock contention/failure behavior for concurrent writers/sweeps. Given that prior review history already flagged multi-account identity and concurrency, these should be explicit acceptance tests, not implied future work.

### Suggestions
- Either restore actual Gmail deletion/archive semantics to the plan, or explicitly re-scope the issue/plan title and acceptance criteria so the contract is honest about delivering local queue-state only in v1.
- Normalize all ownership references so `#2017` defines the contract, `#2026` satisfies storage semantics, and `#2024` only consumes the storage layer; then align every xfail note, acceptance criterion, and handoff statement to that split.
- Expand the formal contract to include schemas and tests for `queue-learning-log.jsonl`, `queue-state-snapshot.meta.yaml`, snapshot freshness rebuilds, and composite-key isolation across accounts.

### Questions for Author

- Which exact issue is expected to turn the xfail state-machine contract green: `#2026`, `#2024`, or both in sequence?
- Should the schema file be the authoritative spec for both queue-state and learning-log records, or is the learning log intentionally left informal?
