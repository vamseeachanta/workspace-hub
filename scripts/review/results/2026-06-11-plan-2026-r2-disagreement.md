### claude

- **BLOCKER — Missing-extraction reactivation targets a transition the contract forbids.** Plan §Adversarial Review Summary claims the r1 fix "Changed missing-extraction reactivation to return to `inbound`, matching the design contract," and §Pseudocode `reactivate_reply` executes `transition(from_state=prior_state, to_state="inbound")`. But §Pseudocode `transition()` first does "validate from_state -> to_state transition is allowed," and the design contract's State Machine table (`docs/design/email-as-queue.md:57-67`) defines exactly eight edges — **none of which target `inbound`**. `purged -> inbound` (and `awaiting-reply/completed -> inbound`) is an invalid transition under the plan's own validator, so `test_missing_extraction_logs_learning_event_and_returns_inbound` (TDD list) contradicts `transition()` as specified. The design doc's prose at line 43 ("treats the message as new inbound") conflicts with its own transition table, and the plan inherits this contradiction without resolving it: the Files-to-Change entry for `email-as-queue.md` covers only "runtime state path, two-account scope, pending-work semantics" — not transition-table extension. The plan must explicitly add the reactivation-to-`inbound` edge(s) to the state machine and the design doc, or define the missing-extraction path as a non-transition event.
- **Plan header cites review artifacts that are empty at review time.** §Header "Review artifacts" points to `scripts/review/results/2026-06-11-plan-2026-{claude,codex}.md`, which are 0 bytes (their `.err` siblings show in-flight/failed CLI runs); only the gemini file has content. The verdicts the §Adversarial Review Summary table reports actually live in the `-r1-*` files, which the header does not reference. An approver following the header paths finds two of three reviews missing. Update the header to cite the r1 artifacts for the recorded round and ensure r2 artifacts are non-empty before `status:plan-review`.
- **Pseudocode API shape diverges from the frozen contract tests.** `tests/email/test_state_machine_contract.py:18,27,41-44,54-61` call `transition(log, ...)`, `lookup(log, acc, thr)`, `count_entries(log)`, `reactivate_reply(log, ...)` with an explicit JSONL **path as the first positional argument**. §Pseudocode instead resolves the state dir from `EMAIL_QUEUE_STATE_DIR` and operates on a `store`, and D1 says "Tests will use temp directories and `EMAIL_QUEUE_STATE_DIR`" — but the existing contract tests use no env var. Where snapshot/meta/learning-log files land when the caller supplies a bare log path is unspecified. The plan should pin the public signature (path-first, with derived sibling-file locations) so implementation doesn't break the #2017 contract tests it promises to un-xfail.
- **`pending_work_report` return shape misses its own acceptance criterion.** §Pseudocode returns only `(tracked_empty, mailbox_empty, unknown_status)`, dropping `unknown_count` and the **per-account counts** that AC #4 requires ("includes per-account counts"). Additionally, D3's non-pending bucket "`extracted` with no action pending" implies a computable "extracted with action pending" class, but the only pending classes computed are `inbound` and `needs_user_decision` — an extracted thread needing a reply that hasn't yet transitioned to `awaiting-reply` is silently non-pending. Risk of an "empty" report over-claiming.
- **Dedup fallback rule under mixed `triggering_message_id` presence is undefined.** D5 makes `triggering_message_id` "part of the dedup-key contract," yet the existing contract test `test_transition_retry_preserves_dedup_under_fresh_ts` dedups two events that carry **no** triggering id (must keep passing). The mixed case — event A without id, event B with id, same `(account_id, thread_id, from_state, to_state)` — is unspecified: one row or two? The schema's `dedup_key` is a flat required list (`email-queue-state-schema.yaml:60-64`); conditional key membership isn't expressible in that shape, and the plan says "revise dedup semantics" without stating the fallback rule the schema modification must encode.
- **Cosmetic evidence defect:** the gh-issue verification and the pytest reproduction both claim the identical instant `2026-06-11T20:21:48Z` (§Evidence) — copy-paste timestamping. Both facts independently reproduce today, so this is presentation, not substance.

### gemini

- Plan §Pseudocode for `reactivate_reply` invokes `transition(account_id=account_id, thread_id=thread_id, ...)`. This violates the core signature defined directly above it (`def transition(store, event):`), dropping the mandatory `store` parameter and passing kwargs instead of an `event` object, which guarantees a `TypeError` at runtime.
- Plan §Pseudocode for `reactivate_reply` contains a race condition in the `else` block: `append extraction_missing_on_reactivation to queue-state and learning logs`. Appending to the log outside of `transition` bypasses the critical `acquire fcntl LOCK_EX on queue-state.jsonl` safeguard explicitly enforced by `transition`, corrupting the JSONL upon concurrent writes.
- Plan §Pseudocode for `sweep_grace` iterates batches to `append completed -> purged local transitions under log lock` but entirely omits snapshot materialization. Because `transition` relies on an immediate `rebuild snapshot and meta via tmpfile` after every append, bypassing this step during sweep batches causes the materialized snapshot to instantly desynchronize, leading `lookup` to incorrectly return `completed` threads rather than `purged`.
- Plan §Pseudocode defines `def sweep_grace(store, now_utc, grace_days=7, batch_size=100):` and unconditionally appends purged transitions to the log, yet claims to "return dry-run/apply report." It exposes no `dry_run` parameter, making safe, non-destructive sweep simulations impossible.
- Plan §Design Decisions D5 modifies the dedup key by "adding `triggering_message_id` where available." If a thread experiences a second missing-extraction reactivation without a triggering ID, the dedup key falls back to the exact same `account_id, thread_id, from_state, to_state` footprint as its first cycle (`purged` to `inbound`). This causes `transition`'s `append event if dedup key is not already present` check to falsely trigger and silently swallow the valid new reactivation event.
- Plan §TDD Test List covers positive dedup key updates (`test_dedup_preserves_reactivation_cycle` testing "two triggering message IDs") but completely omits verifying the fallback dedup behavior when `triggering_message_id` is missing/null, leaving the critical failure mode in D5 untested.
- Plan §Evidence (embedded verification) claims "EXISTS:" for 7 distinct file paths (e.g., `docs/design/email-as-queue.md`, `tests/email/test_state_machine_contract.py`). Exhaustive `glob` searches of the workspace (`/tmp`) confirm zero of these files exist at HEAD, rendering the plan's architectural assertions and regression baselines unverifiable.

### r1-claude

- **MAJOR — `needs-user-decision` and `unknown` are not states in the #2017 contract, and no contract change is planned.** `docs/design/email-queue-state-schema.yaml:3-8` and the snapshot `state` enum (lines 108-110) define exactly five states: `inbound, extracted, awaiting-reply, completed, purged`. `docs/design/email-as-queue.md:55` confirms the same five. Plan §D3 treats `needs-user-decision` as a durable bucket, the pseudocode `pending_work_report` counts `needs_user_decision` and `unknown`, and TDD test `test_pending_work_report_not_empty_for_needs_user_decision` requires a record in that state. §Files to Change does not touch the schema yaml or the state-machine transition table. As written the test is unimplementable: there is no valid transition that produces a `needs-user-decision` snapshot record. Either extend the contract (schema enum + transition table + dedup implications) or define an explicit mapping onto existing fields (e.g., `primary_classification: actionable` + a flag) — the plan does neither.
- **MAJOR — D5 dedup-key change contradicts the schema the plan itself quotes, and the schema file is not in Files to Change.** Schema `dedup_key` is `[account_id, thread_id, from_state, to_state]` (`email-queue-state-schema.yaml:62-66`); `triggering_message_id` is not even a property of `queue_state_entry` (lines 31-61). Plan §D5 makes `triggering_message_id` part of the dedup key and §Pseudocode writes it into events. Implementing this without updating `docs/design/email-queue-state-schema.yaml` makes the contract artifact false on day one, and validation against the schema (the plan's own evidence base) would reject the new field if `additionalProperties` were enforced. The schema yaml must be added to Files to Change with the D5 semantics, or D5 dropped.
- **MAJOR — "zero unknown/unclassified in-scope threads" is uncomputable from the planned modules.** §D3 defines report-empty as requiring zero "unknown/unclassified in-scope threads", and the §Deliverable claims the module "can tell whether mailbox work is pending." Every module in §Files to Change reads only local state; a thread that was never ingested produces no JSONL row and is invisible to `report.py`. Detecting untracked pending work requires an inbox-enumeration input (Gmail read adapter or an ingest-side thread census) that no planned file provides — `state/labels.py` is a write-side label planner. Either add an inbox-snapshot input interface to `report.py`, or re-scope "unknown" to mean "present in store with unrecognized state" and state explicitly that untracked-thread detection belongs to #2024.
- **MAJOR — acceptance criteria #3 and #7 are jointly unsatisfiable as specified.** Pseudocode `transition` does "validate account alias is allowed" against the hardcoded set `{"ace", "personal"}` (`load_account_scope`), but the existing contract tests the plan promises to keep green (criterion #7, "Existing #2017 contract tests pass") call `transition(log, account_id="user@example.com", ...)` (`test_state_machine_contract.py:18-25`). With allowlist enforcement in `transition`, those tests fail with `AccountOutOfScope`. The plan needs to specify one of: allowlist injectable per store (tests construct a permissive scope), enforcement only at the report/ingest layer, or rewriting the contract tests' account IDs (which changes #2017 contract artifacts and should be called out as such). Related unresolved ambiguity: whether `account_id` persisted in JSONL/snapshot keys is the alias (`ace`) or the literal address — §D2 says tests shouldn't hardcode addresses, yet the contract tests already persist an address as `account_id`.
- **MAJOR — reconciliation scope omits `docs/design/email-as-queue-workflow.md` entirely.** The 29 KB workflow design (also a #2017 artifact, never mentioned anywhere in the plan) declares `~/.hermes/email-state.yaml` as "the authoritative state tracker" (line 236), uses `skestates` account examples (lines 255, 328, 334), and schedules a week-4 "Full pipeline, all accounts" deletion rollout (lines 487-490) — all three contradict this plan's D1 (directory, not single YAML), D2 (two accounts), and the no-Gmail-mutation boundary. Additionally `docs/design/email-as-queue.md:24-29` (the plan's declared contract source) pins all four state files to **repo paths** `scripts/email/queue-state*.jsonl/yaml`, directly contradicting D1; the plan does list that doc in Files to Change but its Resource Intel never surfaces that the contract source itself specifies repo-tracked state paths — a reviewer reading only the plan would think the conflict lives in "old plans," not in the active contract doc. Add the workflow doc to Files to Change (or explicitly mark it superseded) and name the email-as-queue.md State Authority conflict explicitly.
- **MINOR — stdlib `email` shadowing hazard is one plausible edit away.** `tests/conftest.py:9-12` inserts `REPO_ROOT/scripts` into `sys.path`. The plan creates `scripts/email/state/__init__.py` but (correctly) not `scripts/email/__init__.py` — yet never says so. If an implementer "fixes" the asymmetry by adding `scripts/email/__init__.py`, top-level `import email` resolves to the repo directory instead of the stdlib `email` package for the entire test session (regular packages beat the namespace-portion deferral that currently protects stdlib). The plan should explicitly prohibit `scripts/email/__init__.py` and note that `scripts.email.*` imports rely on PEP 420 namespace resolution plus repo root on `sys.path` (via the `tests/` package basedir under pytest's prepend import mode).
- **MINOR — `fcntl` is POSIX-only.** §Pseudocode and `state/store.py` rationale specify `fcntl LOCK_EX`. The workspace convention includes a Windows checkout (`D:\workspace-hub`). Issue is `machine:dev-primary` (Linux), so acceptable, but the plan should state the platform constraint or guard the import so test collection doesn't break on Windows.
- **MINOR — plan presents already-completed work as future.** `docs/plans/2026-04-24-issue-2026-plan.md` already carries the full supersession banner in the working tree, and `docs/plans/README.md` is already modified (git status), while §Files to Change lists both as pending updates on a `Status: draft`, pre-approval plan. This is the inverse of the plan-future-tense rule but hits the same trust surface: the reviewer/approver cannot tell which Files-to-Change rows are real future work. Mark these two rows "already applied in working tree."
- **MINOR — Adversarial Review Summary says "Review not yet run" but the fanout already ran and failed.** All three result files exist as 0-byte placeholders (created 15:24); the codex `.err` is 278 KB (its tail contains the plan's own pytest reproduction output) and a gemini `.err` existed transiently. Per the `scripts/review/results/` convention, failed provider runs should be recorded as UNAVAILABLE with cause, not PENDING. Also note: an active concurrent writer touched these files during this review (gemini `.err` vanished between `ls` and `cat`) — check parallel work before the next fanout wave.

### r1-codex

- Plan D5 requires `triggering_message_id` in the dedup key, but the authoritative schema does not define that field or include it in `dedup_key`. The plan says “adding `triggering_message_id` where available” and the pseudocode says “build dedup key including triggering_message_id” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:232-255`), while `docs/design/email-queue-state-schema.yaml:31-66` has no `triggering_message_id` property and keeps `dedup_key` to `account_id`, `thread_id`, `from_state`, `to_state`. The Files to Change list omits `docs/design/email-queue-state-schema.yaml` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:290-309`), so implementation can pass code tests while leaving the contract artifact stale.
- The plan introduces `needs-user-decision` / `needs_user_decision` as a pending-work state or count without defining it in the state contract. D3 lists `needs-user-decision` as a durable bucket and says empty requires zero `needs-user-decision` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:216-226`); pseudocode counts `needs_user_decision` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:279-281`); the TDD list uses “one needs-user-decision” as test input (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:330-331`). But the schema allows only `inbound`, `extracted`, `awaiting-reply`, `completed`, `purged` for entries and snapshots (`docs/design/email-queue-state-schema.yaml:3-8`, `docs/design/email-queue-state-schema.yaml:34-39`, `docs/design/email-queue-state-schema.yaml:108-110`), and the current design state machine also lists only those five states (`docs/design/email-as-queue.md:53-68`). The plan must either add a schema-backed field/classification for user-decision backlog or stop treating it like a state.
- Missing-extraction reactivation semantics contradict the current contract. The design says if a linked extraction is missing, the system emits `extraction_missing_on_reactivation` “then treats the message as new inbound” (`docs/design/email-as-queue.md:41-43`). The plan pseudocode instead appends the learning event and transitions `prior_state -> extracted` with `reason="missing-extraction"` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:265-270`). The planned test only verifies that a learning event is emitted (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:329`), so it would not catch the wrong final state.
- The plan downgrades live Gmail label work below the issue’s stated verification without getting explicit approval for that scope cut. Issue #2026 body includes “Gmail Labels (visual + API-friendly)” and implementation task “Create Gmail labels via API”; the 2026-06-10 issue comment says verification includes “Labels created.” The plan changes this to “label-operation plan” and “live Gmail label mutation must be off by default” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:228-230`) with acceptance only that a planner exists and mutation is opt-in (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md:353`). That may be a reasonable safety decision, but as written it silently narrows issue scope.
