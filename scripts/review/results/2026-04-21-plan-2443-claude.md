### Verdict: MAJOR

### Summary
Plan is structurally sound for a T1 CI restoration and the evidence chain is unusually thorough (GitHub API probes, sibling-workflow survey, file-existence proofs). However, several defects warrant correction before execution: (1) the acceptance criterion "tune lenient config until 0 violations" combined with disabling MD013/MD033/MD041/relaxing MD025 risks producing a rubber-stamp green CI that catches nothing meaningful; (2) `permissions: issues: write` is granted on link-check.yml with a comment that lychee will "open summary issue on failure" — lychee-action does NOT auto-create issues, so this permission is either dead or silently depends on a non-existent step; (3) minor evidence drift (plan says 13 .py files, actual `git ls-files | grep -c '\\.py$'` = 12); (4) action version pins are floating (`@v2`, `@v16`, `@v4`) rather than SHA-pinned; (5) `fail: true` is redundant on lychee-action v2 (already default in modern versions); (6) "10-20× faster" benchmark vs. node link-checkers is stated without a cited benchmark; (7) no `concurrency:` group on either workflow — rapid successive commits burn Actions minutes duplicating runs; (8) weekly link-check Actions-minute cost contradicts the "negligible burn on non-MD commits" acceptance criterion (scheduled runs cost minutes regardless of diff). Tool selections (markdownlint-cli2, lychee) are defensible against alternatives cited. Verdict: REQUEST_CHANGES — the lint-teeth and permission-vs-behavior issues are correctness-adjacent, not cosmetic.

### Issues Found
- Rubber-stamp CI risk (MAJOR): §Acceptance Criteria bullet 'First triggered markdown-lint run conclusion = success (no pre-existing violations OR lenient config tuned until 0 violations)' combined with pre-disabling MD013/MD033/MD041 and relaxing MD025 defines the success criterion as 'whatever the config is tuned to accept.' This makes the lint effectively unable to fail, defeating its CI purpose. The plan should enumerate a minimum non-negotiable ruleset (e.g., MD034 no-bare-urls, MD042 no-empty-links, MD051 link-fragments, MD011 reversed-link-syntax) that CANNOT be disabled to pass the first run — otherwise the workflow is ceremonial.
- Dead permission / misleading comment (MAJOR): §Pseudocode link-check.yml grants `permissions: issues: write` with comment 'allow lychee to open summary issue on failure (optional)'. `lycheeverse/lychee-action@v2` does not open GitHub issues on its own — it writes a report file (e.g., `lychee/out.md`). Creating a summary issue requires a follow-up step like `peter-evans/create-issue-from-file` reading the report. As written, the permission is unused and the comment implies behavior that will not occur. Either add the issue-creation step, or drop the permission and correct the comment.
- Evidence-drift in §Evidence (MINOR): plan asserts '13 .py files tracked' but `git ls-files | grep -c '\.py$'` on the local achantas-data checkout returns 12. Small, but this is a plan that emphasizes evidence accuracy — discrepancy should be reconciled or the lower count accepted.
- Floating action tags (MINOR): `actions/checkout@v4`, `DavidAnson/markdownlint-cli2-action@v16`, `lycheeverse/lychee-action@v2` are all minor-float pins. Supply-chain best practice for third-party actions (the markdownlint and lychee ones, not first-party) is SHA pinning. The plan's 'Open — which lychee version' item acknowledges this partially for lychee but not for markdownlint-cli2-action.
- Redundant parameter (MINOR): lychee-action v2 defaults `fail: true`; explicit `fail: true` in the target-shape YAML is inert. Not wrong, but signals incomplete tool familiarity — worth dropping or confirming the value matters.
- Uncited performance claim (MINOR): §Tool choice rationale states lychee is '10-20× faster on 495-file repos' and 'node-based link-check tools on 495 MD files routinely timeout.' No benchmark cited; marketing-flavored claim in a plan otherwise strong on citations.
- No `concurrency:` group (MINOR): neither workflow declares a concurrency group. Rapid successive commits to `main` or a PR will queue duplicate markdown-lint runs. For a free-tier personal repo this compounds the cost concern the plan already discusses.
- Internal inconsistency (MINOR): acceptance criterion 'No Actions-minutes burn on non-MD commits' is contradicted by the link-check workflow's weekly `schedule:` trigger, which burns minutes unconditionally of commit content. Criterion should narrow to 'push-triggered runs' explicitly.
- MD025 relaxation on a docs-heavy repo (MINOR): §Files to Change row 3 relaxes MD025 (multiple-h1). On a 495-file markdown corpus, multiple H1s in one file often signal accidentally concatenated documents or broken frontmatter. Disabling this rule hides a class of structural bugs the lint would otherwise catch. Justification in the plan ('personal notes are not published prose') is thin.
- `actionlint` dependency is local-only (MINOR): §TDD Test List and §Acceptance Criteria require `actionlint` passing, but the requirement is enforced out-of-band (developer's machine) rather than in-CI. A workflow that validates `.github/workflows/*.yml` via actionlint-in-CI would make this a gated check rather than a hope.

### Suggestions
- Split the markdownlint config into two layers: a non-negotiable floor (bare-URL detection MD034, empty-link MD042, link-fragment MD051, reversed-link-syntax MD011) that the plan commits to keeping enabled, and a convenience layer (MD013/MD033/MD041) that is disabled. Rewrite the acceptance criterion to forbid disabling the floor rules during tuning.
- Either add a `peter-evans/create-issue-from-file` step to link-check.yml that consumes lychee's output file and opens an issue, or drop `permissions: issues: write` and correct the inline comment so it does not promise behavior that will not occur.
- Reconcile the .py file count to 12 in §Evidence, or show the command that yielded 13 (maybe including untracked or ignored paths).
- Add SHA pins for third-party actions (markdownlint-cli2-action, lychee-action) and call out the pin-update policy as a follow-up maintenance item.
- Remove the redundant `fail: true` from the link-check YAML target shape, or leave it with a comment `# explicit, default in v2+`.
- Replace '10-20× faster' with either a citation (lychee README benchmark) or soften to 'lychee is the faster Rust-based alternative; node-based link-checkers are reported to struggle on large markdown corpora.'
- Add `concurrency: group: ${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress: true` to markdown-lint.yml to dedupe queued PR runs.
- Tighten the 'no Actions-minutes burn' acceptance criterion: scope it to push/PR-triggered markdown-lint runs, and separately budget the expected ≤4 link-check runs/month × ~30s.
- Reconsider relaxing MD025 — on a 495-file corpus this is more likely to surface real defects than noise. Leave it enabled and handle exceptions case-by-case.
- Consider adding a `validate-workflows` job that runs `actionlint` in CI against `.github/workflows/` so the plan's own quality gate is self-hosted rather than a developer-machine ritual.

### Questions for Author
- What is the minimum lint floor you are willing to commit to NOT disabling during tuning? Listing it in the plan converts 'lenient' from a slippery slope into a bounded posture.
- Is the `issues: write` grant on link-check.yml intentional scaffolding for a future issue-creation step, or an error based on misunderstanding lychee-action behavior?
- Do you want SHA-pinned third-party actions (markdownlint-cli2, lychee) to match the security posture of the workspace-hub repo, or is minor-float acceptable given this is a personal docs repo?
- Why is MD025 relaxed? On 495 .md files, multiple H1s usually signal concatenation bugs rather than intentional structure.
- Should link-check.yml also respect a `.lycheeignore` file for per-repo URL allowlisting, and do you want that file created in this plan or deferred?
- If first-run lychee surfaces many dead links in legacy notes, is the intent to (a) fix them in the same PR, (b) bulk-exclude them with dated TODOs, or (c) make the first run warning-only and flip `fail: true` in a follow-up PR? The plan implies (a)/(b) but does not rule out (c).
