## Defect P1-A — `--with pyyaml` will only resolve when uv-managed Python is in use; fails on `--python` override

**Where:** §2 decision and §3.2 edit on `scripts/hooks/pre-push.sh:132,258` and `check-all.sh:506,548`.

**Defect:** `uv run --no-project --with pyyaml python "$SCRIPT"` resolves `pyyaml` against the python `uv` selects. On a clone where the user has set `UV_PYTHON_PREFERENCE=only-system` or has no managed python installed, `uv` falls back to system python — which on this user's setup is miniforge (per issue body: "system python3 is miniforge in this user's setup"). uv writes the `--with` package into a `.venv` overlay only for managed pythons; for `system` python it may use a layered ephemeral path that on some uv versions silently no-ops the `--with`. The issue body itself documents miniforge involvement and `PATH=/home/vamsee/miniforge3/bin:$PATH` not working, suggesting non-trivial python resolution.

**Why P1:** the plan's headline acceptance criterion ("`git push` from fresh worktree without `--no-verify`") may pass on the author's machine and fail on a CI runner or another developer's machine.

**Fix:** the plan must (1) pin python via `uv run --no-project --python 3.11 --with pyyaml python …` so the resolution mode is deterministic, AND (2) the §4.2 cold-cache test must run with `UV_PYTHON_PREFERENCE=managed` and again with `UV_PYTHON_PREFERENCE=only-system` to prove both paths.

## Defect P1-B — Lifting `.git/hooks/pre-push` body into a tracked source is silent corruption risk

**Where:** §3.1 — "CREATE `scripts/hooks/pre-push.sh` — full body of `.git/hooks/pre-push` lines 1-267 lifted into a tracked file."

**Defect:** The plan asserts the body is hand-crafted on this machine but never verifies its provenance. install-hooks.sh appends gates onto **whatever was already there**; the user may have local hand-edits (debug prints, repo-list overrides, the `PRE_PUSH_CHANGED_FILES` test path at line 106-110) that other developers do not have. Promoting one developer's body to "the canonical source" propagates that developer's local quirks to everyone.

The plan's mitigation ("Diff against existing body before promoting") is hand-wavy — diff against what? There is no other copy. `git log -- .git/hooks/pre-push` returns nothing because it's untracked.

**Why P1:** ships untraceable per-machine drift as canonical. Plan #2203 already flagged this exact concern (`docs/plans/2026-04-21-issue-2203-pre-push-worktree-aware-tier1-gate.md:18`) — Team G is duplicating #2203's work and risks merge conflict if both land.

**Fix:** scope this PR to the yaml fix only. Defer the tracked-hook-source migration to #2203 (or a parallel issue that explicitly closes #2203's gap). The yaml fix alone is `sed -i` on `.git/hooks/pre-push` and `scripts/quality/check-all.sh` — the latter IS tracked. For the hook, document the manual one-liner in the issue close-out and accept that until #2203 lands, every developer must apply it locally.

## Defect P2-A — §3.5 enforcement script regex is wrong for inline `python -c` cases

**Where:** §3.5 — "greps for `uv run --no-project [^|]*python\s+(\S+\.py|-c|-)`".

**Defect:** the regex would match `uv run --no-project python -c "import yaml"` only if it sees the heredoc body, but `check-all.sh:189-194` and `:199-203` use multi-line `python -c "<<HEREDOC"` patterns where the imports are on later lines. A naive grep cannot inspect the heredoc body. The script as drafted would either (a) miss yaml imports inside heredocs (false negative) or (b) trigger on benign `python -c "import json"` calls (false positive).

**Why P2:** the enforcement gate is the entire mitigation for the "latent bomb" risk. If it has known FN/FP it will be silenced or removed within a week.

**Fix:** the enforcement script must (1) for `<file>.py` invocations, AST-parse the file; (2) for `-c "..."` invocations, AST-parse the string; (3) for `-c <<HEREDOC` invocations, extract the heredoc body via `bash -n` or shell parser, then AST-parse. Or scope it more narrowly: only check `.py` file invocations and exclude `-c` entirely, accepting the gap.

## Defect P2-B — TDD plan never actually exercises a fresh `uv run --no-project` resolution

**Where:** §4.2 — "creates an isolated `UV_CACHE_DIR=$(mktemp -d)`, runs `bash scripts/hooks/pre-push.sh` with `PRE_PUSH_CONFIG_DRIFT_DRY_RUN=1`".

**Defect:** the proposed `PRE_PUSH_CONFIG_DRIFT_DRY_RUN=1` invokes `... check_config_drift.py --help`. `argparse` `--help` exits **before** any module-level imports run? **No** — module-level `import yaml` (line 29) runs at module load, BEFORE `main()` is called and BEFORE argparse processes `--help`. So `--help` will surface the `ModuleNotFoundError`. Good — the test catches the failure.

But: the test creates `UV_CACHE_DIR=$(mktemp -d)` and assumes uv will populate it on first invocation. On hosts without internet (CI sandboxes, the Codex sandbox per `feedback_codex_sandbox_no_execution.md`), `uv` cannot download pyyaml, the test fails for a reason orthogonal to the fix, and the test is silenced. Per `feedback_mock_vs_live_invocation_divergence.md`, mocking the uv layer to satisfy the test would re-introduce exactly the divergence class the issue exists to fix.

**Why P2:** integration test is fragile; will be flaky in CI; will be marked `@pytest.mark.skip(reason="needs network")` and lose its load-bearing role.

**Fix:** explicitly mark the test as `@pytest.mark.network` and gate it on `UV_OFFLINE` env. Pre-warm pyyaml into a fixture cache used across test runs. Document that this test is the single load-bearing acceptance step; everything else is regex/AST checks.
