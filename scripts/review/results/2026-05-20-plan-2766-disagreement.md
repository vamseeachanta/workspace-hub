### claude

- **§Standards row 2 mis-cites #2731 as authority.** Plan claims `docs/plans/2026-05-19-issue-2731-data-repo-location-contract.md` "establishes adjacent sibling checkout model and forbids inline moves without approved transaction plans." That plan is itself `Status: draft` (line 3) and lists the canonical contract document `docs/standards/REPO_AND_DATA_LOCATION_CONTRACT.md` as `MISSING (new — this plan will create/update via implementation)` (line 69). Treating a still-draft contract-to-be-written as an "applicable" governance source is the past-tense / phantom-counter hazard the project already documents (`feedback_plan_past_tense_artifact_claims`). The sibling-checkout norm currently only exists as a proposed contract, not an enforced one.
- **`tier1_baseline` schema is wholly undefined.** §Gaps identified line 42 and §Files-to-Change line 145 commit to adding a `tier1_baseline` projection to `config/workstations/registry.yaml`, but neither the pseudocode (lines 112-137), the test list, nor the acceptance criteria specify the YAML shape. Is it a flat list, a map `required: [...] / optional: [...] / non_tier1: [...]`, or a per-repo `role:` field on a repo dict? `test_dev_primary_tier1_baseline_matches_user_decision` (line 159) reads a "Registry fixture" without naming a key path. Implementer must invent the schema, which collapses the TDD claim — you cannot write failing tests against an unspecified shape.
- **Pseudocode `discover_checkouts` will self-trip on `workspace-hub/.git`.** Line 129 says "scan workspace_root maxdepth 2 for direct nested .git repos." `workspace_root = /mnt/local-analysis/workspace-hub`, and `find /mnt/local-analysis/workspace-hub -maxdepth 2 -name .git` returns `/mnt/local-analysis/workspace-hub/.git` — workspace-hub's own repo .git at depth 1. No `-mindepth 2` rule, no self-reference exclusion, and no test (`test_no_direct_nested_git_repos_under_workspace_hub` at line 160 only describes a positive nested-repo fixture, not the self-exclusion case). A literal implementation will fail on the clean state the plan claims to defend.
- **Worktree gitlink hazard (`.git` as a file, not a directory) is ignored.** The repo memory carries a specific rule [[feedback_worktree_gitlink_pollution]] and `.gitignore` already accommodates `.claude/worktrees/`. The plan's checker spec only describes "scan ... for .git repos" without distinguishing `.git/` directories from `.git` gitlink files left by parallel-agent worktrees. If a stray `agent-worktrees/<name>/.git` (file) appears under `workspace_root`, the checker either false-positives or false-negatives depending on how `-type` is set. No test case covers this; the hazard is already known and pre-existing per project memory.
- **`data_access_profile.repos` reconciliation is undefined.** Registry line 44 lists `data_access_profile.repos: [workspace-hub, digitalmodel, assetutilities, worldenergydata, assethold, OGManufacturing]` — missing `llm-wiki` and including `OGManufacturing`. The plan reclassifies `OGManufacturing` as `non_tier1_machine_access` and adds `llm-wiki` to required, but neither pseudocode nor TDD list specifies whether `data_access_profile.repos` should be (a) mirrored to the new required set, (b) left as-is, or (c) computed from `tier1_baseline`. `test_registry_repos_reconcile_with_tier1_baseline` (line 164) asserts "no silent drift" without defining the reconciliation policy.
- **Acceptance criterion §5 (line 175) is non-falsifiable.** "Completion leaves a reusable machine-placement pattern for subsequent workstation issues: consistent tier-1 repo folder structure, methodical primary/reference repo placement decisions, and repo harness/file ecosystem handling all routed through the single workstation registry authority." There is no test that can return pass/fail on "reusable pattern," "methodical placement decisions," or "routed through ... authority." Either delete it or convert each clause into a binary check (e.g., "registry contains a `placement_pattern_version: 1` key," "skill `per-machine-repo-placement-outcome-contract.md` cites the registry path").
- **Readiness integration shape is unspecified.** §Files-to-Change line 147 commits to modifying `scripts/readiness/telegram_hermes_readiness.py`, and `test_missing_required_repo_blocks_readiness` (line 162) asserts `dispatchable=false`, but the plan never defines: (a) checker as imported module vs subprocess, (b) the field name added to the readiness payload, (c) the blocker class label that distinguishes placement-blockers from provider/env blockers (§Acceptance criterion line 176), or (d) whether the readiness JSON schema gets versioned. The current readiness script is 22KB; reviewers cannot judge fit without a target call site.
