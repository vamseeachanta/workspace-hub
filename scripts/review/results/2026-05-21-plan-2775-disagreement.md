### claude

- **Local-approval-marker pattern reintroduces a defect class memory already flagged.** Plan §Pseudocode `repair_dry_run` and TDD `test_repair_apply_requires_live_label_and_approval_marker` (line 329) require BOTH a live `status:plan-approved` label AND `.planning/plan-approved/2775.md` for `--apply` to run. Memory feedback `feedback_dispatch_local_marker_rationalization` ("dispatch lanes can write `.planning/plan-approved/<n>.md` rationalizing user instruction; forbid markers AND label") explicitly says the cure is to **forbid** local markers, not to require them in addition to the live label. The "marker is evidence only, never a substitute for the live label" qualifier (line 286) does not address the failure mode: an adversarial dispatch lane can write the marker AND the live label is the only gate that matters anyway. Either remove the marker requirement or cite memory and justify why this case differs.
- **Hermes overlay candidate list is sourced from the stale artifact this plan declares non-authoritative.** §SSoT Strategy §2 (line 236) hard-codes overlay candidates `CAD-DEVELOPMENTS, worldenergydata, achantas-data, assetutilities, digitalmodel` — but `registry.yaml.machines.dev-primary.repos` is `[worldenergydata, digitalmodel, assetutilities, assethold, workspace-hub, OGManufacturing]`. Neither `CAD-DEVELOPMENTS` nor `achantas-data` is in the registry repo list, and `assethold`/`OGManufacturing` are in the registry list but absent from the overlay candidates. The plan picks `registry.yaml` as "authoritative for ... per-machine required repo list" (§SSoT Strategy decision split) and then derives the overlay candidate list from the Hermes template the plan is fixing. This is circular.
- **Registry self-consistency unverified.** Plan declares `registry.yaml` authoritative without checking internal consistency. `dev-secondary.workspace_root: /mnt/local-analysis/workspace-hub` but `dev-secondary.storage.local: /mnt/dde` (registry lines ~54-67). On ace-linux-2 the local partition is `/mnt/dde`, not `/mnt/local-analysis`. The plan's "make harness-config match registry" test (TDD `test_registry_is_authoritative_for_machine_roots`, line 321) will lock in `/mnt/local-analysis/workspace-hub` on a machine whose storage root is `/mnt/dde` — that is exactly the divergence the harness-config originally encoded (`/mnt/workspace-hub`). Neither value is verified against actual checkout location. Add a test that asserts the chosen authoritative value is reachable on the target machine before declaring divergence resolved.
- **`tests/harness/` is a net-new convention not justified.** Plan creates `tests/harness/test_sibling_sso_topology.py`, `tests/harness/test_hermes_config_sibling_paths.py`, `tests/harness/test_sibling_sso_repair_dry_run.py` (lines 296-298). `tests/harness/` does not exist; existing tests live under `tests/architecture`, `tests/cron`, `tests/docs`, `tests/document-intelligence` etc. with no `harness/` precedent. Adding 3 new files in a new subdirectory without pytest collection verification (no `conftest.py` in that path, no mention of `pyproject.toml` `testpaths`) is a TDD-step trap: tests can be "created" yet not discovered by `uv run pytest`. Either route the tests to an existing tier-1 subdir (`tests/cron`, `tests/architecture`, or a new top-level under an existing convention) or specify the pytest-collection change.
- **Shell-wrapper status is internally contradictory.** Artifact Map line 205 marks `scripts/readiness/check-sibling-sso-flow.sh` as "Implementation — optional shell wrapper". Acceptance criterion (line 339) requires `scripts/readiness/check-sibling-sso-flow.sh --machine dev-primary --json` to return PASS. Files-to-Change (line 300) lists it as "Create". An "optional" artifact cannot be load-bearing for an acceptance criterion.
- **Symlink failure test is property-narrow, not class-broad.** TDD `test_provider_symlink_to_missing_parent_skills_fails` (line 324) is keyed to the specific stale realpath `/mnt/local-analysis/.claude/skills` per pseudocode `check_provider_symlinks` line 275: "fail if realpath is /mnt/local-analysis/.claude/skills and target missing". This fails to catch other realpath stales (e.g., a sibling that resolves to `/mnt/dde/.claude/skills`, `~/workspace-hub/.claude/skills`, or any other missing path). Property is *broken-symlink*, not *broken-to-this-specific-path*. Hard-coding the stale value will silently let future drift pass.
- **Registry-required-but-absent path has no test.** §Risks line 383 says "Live absent entries are reported `not_present` unless the registry/check schema marks them required-on-host". `dev-primary.repos` per registry includes `OGManufacturing`, which the topology proof (lines 78-97) shows is NOT under `/mnt/local-analysis/`. No TDD test covers the `not_present` case for a registry-listed repo that isn't checked out. Acceptance criterion does not name it either. Implementation will hit this on day one.
- **`scripts/_core/sync-agent-configs.sh` `--dry-run` behavior not characterized before adding `__TIER1_REPO_ROOT__` requirement.** Plan §Files to Change (line 305) flags `scripts/_core/sync-agent-configs.sh` as "Required: support `__TIER1_REPO_ROOT__`, expose/render a dry-run candidate, and validate no unresolved tokens or stale nested skill paths remain." The script already has `--dry-run` (line 15) and only replaces `__WS_HUB_PATH__` (lines 81, 97). Plan does not document what the current `--dry-run` does, what "expose/render a dry-run candidate" means in delta terms, or whether a path beyond a 1-line token-add is being signed up for. This is exactly the surface area Codex flagged in the first review per §Adversarial Review Summary line 364 ("sync script change cannot be optional") — the plan acknowledged this but did not size or constrain the change.
- **Workspace-hub-self symlink target not covered.** §SSoT Strategy §3 (line 237) and TDD `test_provider_symlink_to_workspace_hub_skills_passes` (line 325) describe the sibling-case relative target `../../workspace-hub/.claude/skills`. But `workspace-hub/.codex/skills` itself is `../.claude/skills` (verified). The plan does not assert that the checker treats `workspace-hub` itself as a separate case from sibling repos; iterating the registry `repos` list and applying the sibling rule to `workspace-hub` will mark its symlink invalid.
- **No reproduction proof for the alleged `IntxLNK` corruption cause.** Plan §Resource Intel line 21 calls them "corrupted NTFS symlink artifacts" but does not state how they arrived — whether they were created by ntfs3-mode mounting (per memory `feedback_ntfs3_symlink_intxlnk`), by a copy across filesystems, or by a sync script. Without a documented cause, the repair manifest could re-corrupt them on the next sync. Add a section identifying the source and adding a guard test (e.g., post-repair `file <path>` does not return `data`).
- **First-review Codex finding "Plan/index not on remote `main` during review" not acknowledged.** §Adversarial Review Summary line 363 lists this as a Codex MAJOR. The "Revisions made" subsection (lines 368-373) does not address it. The plan body itself is at `docs/plans/2026-05-21-issue-2775-workspace-hub-sibling-sso-flow.md` — verify the file is committed and pushed before the next review dispatch (related: memory `feedback_codex_needs_pushed_artifact` and `feedback_reviewer_dispatch_refetch_live_body`).
- **No test for `__TIER1_REPO_ROOT__` resolution failure mode.** TDD `test_sync_agent_config_dry_run_renders_no_nested_paths` (line 330) asserts the *positive* case (token expands). The failure mode — `__TIER1_REPO_ROOT__` referenced in template but missing from machine resolution (e.g., a future machine without `tier1_repo_root` in registry) — has no negative-case test. The sync script must fail closed; the plan should test it does.

### codex

- The plan artifact is not retrievable from `main`. The plan’s Artifact Map names `docs/plans/2026-05-21-issue-2775-workspace-hub-sibling-sso-flow.md`, but fetching that exact path from `vamseeachanta/workspace-hub@main` returned 404. This breaks review reproducibility and contradicts the planning workflow in `docs/plans/README.md`, which requires saving the plan under `docs/plans/` and updating the index before gate progression.
- The target repo scope is still internally inconsistent. Plan §SSoT Strategy says the required repo set comes from `config/workstations/registry.yaml[machine].repos`, but `config/workstations/registry.yaml` `dev-primary.repos` contains only `worldenergydata`, `digitalmodel`, `assetutilities`, `assethold`, `workspace-hub`, and `OGManufacturing`. The same plan’s §Resource Intelligence and §SSoT Strategy include overlay candidates `CAD-DEVELOPMENTS` and `achantas-data`, which are not in that registry set. The plan does not define whether overlay repos may be outside `repos`, where that exception is encoded, or whether the checker/repair command may touch them.
- The plan’s `load_registry()` pseudocode requires `tier1_repo_root` and `repo_layout=sibling` for sibling checks, but `config/workstations/registry.yaml` only defines those fields for `dev-primary`. `dev-secondary` has `workspace_root: /mnt/local-analysis/workspace-hub` but no `tier1_repo_root` and no `repo_layout`. The plan also says harness duplicated roots must match registry roots, while `scripts/readiness/harness-config.yaml` still has `dev-secondary.ws_hub_path: /mnt/workspace-hub`. The plan needs an explicit registry migration for every machine it will validate, not only a failure test.
- The sync-script integration remains underspecified against the actual implementation. `scripts/_core/sync-agent-configs.sh` currently resolves Hermes `ws_hub_path` from `scripts/readiness/harness-config.yaml` in `resolve_ws_hub_path()`, not from `config/workstations/registry.yaml`, and accepts only `--force` / `--dry-run`, not `--machine`. Plan §Acceptance Criteria requires `scripts/_core/sync-agent-configs.sh --dry-run` to prove registry-derived `__TIER1_REPO_ROOT__` expansion and no stale nested paths, but the plan does not specify replacing the harness-based resolver or adding a machine selector. As written, the acceptance test can pass a separate checker while the real sync path still reads stale harness state.
- The plan’s cross-repo source-control strategy is still too vague for writes outside `workspace-hub`. §Files to Change says it will modify target sibling repo `AGENTS.md` files and `.codex/skills` / `.gemini/skills`, but §Acceptance Criteria only requires a final closeout comment and does not require per-sibling repo dirty-state capture, branch/remote verification, commits, pushes, or issue comments in those sibling repos. Issue [#2766](https://github.com/vamseeachanta/workspace-hub/issues/2766) explicitly requires remote URL, branch, ahead/behind, dirty/untracked state, and nested worktree status before repo placement mutations; this plan mutates the consequences of that placement without carrying equivalent safeguards.

### gemini

- Plan references `config/workstations/registry.yaml`, `scripts/readiness/harness-config.yaml`, and `config/agents/hermes/config.yaml.template` as existing authoritative sources — no such files exist at HEAD in the accessible workspace. `glob` returns zero non-test fixture matches. The plan's claims about existing codebase state cannot be verified.
- Plan references `scripts/_core/sync-agent-configs.sh` as an existing script to be modified and `scripts/memory/check-memory-drift.sh` as a memory bridge proof — no such files exist at HEAD. `glob` returns zero matches.
- In the `TDD Test List`, the test `test_rejects_missing_external_skill_root` states the Expected input is: `Missing path /mnt/local-analysis/workspace-hub/worldenergydata/.claude/skills`. This path is nested under `workspace-hub`, which the plan simultaneously claims is a stale topology assumption and must be rejected entirely (as tested by `test_detects_nested_workspace_hub_skill_paths`). A test for a missing valid external root should use a sibling path (e.g., `/mnt/local-analysis/worldenergydata/.claude/skills`). Testing a missing invalid path conflates two distinct failure modes.
- The `Pseudocode` for `repair_dry_run()` and the `Acceptance Criteria` state: "require --apply plus live GitHub label status:plan-approved...". However, the pseudocode fails to specify how the script will securely verify this live label (e.g., executing `gh issue view 2775 --json labels`). Without explicit implementation logic to query the remote state, this requirement risks being bypassed or implemented as a stub.
- The `Risks and Open Questions` section states that a mitigation for cross-repo write risks is to "verify each repo's git state before/after". However, the `Pseudocode` for `repair_dry_run()` completely omits checking if sibling repos are dirty before applying changes. Applying symlink or contract repairs to a dirty working tree could result in untracked data loss.
- The `Pseudocode` states for IntxLNK files: "classify as corrupted_ntfs_symlink and propose delete+recreate only in dry-run manifest". It fails to specify the operational logic when `--apply` is passed. If it is *only* proposed in the manifest, the repair logic will silently fail to actually delete and recreate the symlink during execution.
