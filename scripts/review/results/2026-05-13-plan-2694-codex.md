## Findings
1. Plan P4 contradicts itself on the YAML contract. P4 pseudocode says keep `calculation_type` unchanged and add `edition`, and AC-P4.7a requires the live YAML with `calculation_type: ABS_gn_ships_2018` and no `edition:` to route. But Files to Change says replace the YAML line with `standard:` + `edition:` two-key dispatch, and TDD test `test_yaml_calculation_type_replaced_with_standard_plus_edition` says calculation_type is replaced. The live router currently requires `cfg["inputs"]["calculation_type"]` (`cathodic_protection.py` lines 15-29), and the live YAML uses that key (`cathodic_protection.yml` line 4). This is a blocking implementation ambiguity.

2. P4 router pseudocode calls `digitalmodel.cathodic_protection.run(...)`, but the plan never creates or wires a `run` entry point. The current facade `src/digitalmodel/cathodic_protection/__init__.py` re-exports many functions/classes but contains no `run` function. As written, the thin adapter would fail at runtime.

3. AC-P4.5 imports the wrong public symbol: `from digitalmodel.cathodic_protection import coating_breakdown_factor; r = coating_breakdown_factor('FBE', 10.0, edition='2017')`. Current `__init__.py` exports `coating_breakdown_factor` from `iso_15589_2`, while the DNV function is aliased as `dnv_coating_breakdown_factor`. The plan’s P1 pseudocode changes `dnv_rp_b401.coating_breakdown_factor` from live signature `(a, b, t_years)` in `dnv_rp_b401.py` lines 91-113 to `(category, age_years, *, edition)`, but does not update the facade alias contract. The cited AC will test the wrong function unless the plan explicitly changes exports and migrates callers.

4. P2 test `test_flush_anode_2017_uses_mccoy_2021_uses_dwight` expects `r_2017 = 2 * r_2021 (within 1%)`, but the same plan’s r2 baseline says the ratio at `L=2, r=0.15` is `1.8702`, not 2.0. Live formulas confirm this: `dnv_rp_b401.py` lines 332-334 use McCoy half-space, and `cp_DNV_RP_B401_2021.py` lines 332-339 use Dwight. This test would fail or reintroduce the r1 false numeric claim.

5. `_coating_translation.py` pseudocode regresses the enum-name fix. The plan’s r2 summary says real enum members are `THREE_LAYER_PE`, `THREE_LAYER_PP`, and `CONCRETE_WEIGHT`; live `coating.py` lines 24-33 confirm those names. But P2 translation map uses `"3LPE"`, `"3LPP"`, and `"CONCRETE"`. It also maps to `"CAT_I"`/`"BARE"` while the live 2021 table keys are `"I"`, `"II"`, `"III"`, and `"bare"` in `cp_DNV_RP_B401_2021.py` lines 30-36. This will create a second incompatible vocabulary.

6. AC-P2.2c verifies zinc support through `coating_breakdown_factor(material='zinc', edition='2017')`. Zinc is an anode material capacity concern, not a coating breakdown concern. Live `dnv_rp_b401.coating_breakdown_factor` takes `(a, b, t_years)` and P1 pseudocode takes `(category, age_years, edition)`, neither has `material`. The cited AC is not executable against the planned API.

7. P1 uses `@dataclass class AnodeSizingResult(EditionedResult)` in pseudocode, but live `AnodeSizingResult` is a Pydantic `BaseModel` in `anode_sizing.py` lines 93-119. Replacing it with a dataclass is not a sidecar-only change; it changes validation, serialization, and the `.dict()` behavior that P4 router pseudocode depends on.

8. P3 manifest tests are internally inconsistent. The TDD row says `SUPPORTED_STANDARDS` declares “all 13 (std, edition) pairs” and expects `len == 13`, while P3 pseudocode includes `("DNV-RP-B401", ("2017", "2021"))` plus 12 other standards. That is 13 top-level standards but 14 `(standard, edition)` pairs if editions are expanded. The test name/claim and assertion cannot both be correct.

9. AC-P2.5 says baseline tests still pass as “same 5 tests,” but AC-P1.1 and the P1 baseline table list 6 baseline tests after adding `test_baseline_internal_router_dwight_divergence`. This is a stale acceptance criterion and weakens the no-collapse gate.
