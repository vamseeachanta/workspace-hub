## Findings
1. **Missing source files at HEAD:** Plan §Sources consulted cites `config/agents/SHARED_SOUL.md`, `scripts/agents/build-soul-runtime.sh`, `scripts/agents/install-soul-runtime.sh`, `config/agents/hermes/config.yaml.template`, and `scripts/readiness/harness-config.yaml`. None of these files or directories exist in the current workspace.
2. **Bash vs. Python testing mismatch:** Plan §Files to Change proposes creating a Bash script for validation (`scripts/validation/check-agent-runtime-authority.sh`). However, Plan §TDD Test List proposes testing it with Python (`tests/validation/test_agent_runtime_authority.py`) and expects internal state returns (e.g., "Parser returns normalized registry."). A Python unit test cannot assert against internal state or returned objects of a Bash script without complex wrapping or JSON translation, which the plan omits.
3. **Missing YAML parser dependency:** Plan §Pseudocode for `load_registry(path)` requires a Bash validator to "read YAML registry". Bash cannot natively parse YAML schemas. The plan fails to define how cross-platform YAML parsing (e.g., via `yq` or Python) will be handled without introducing a new unstated dependency.
4. **Validation logic contradicts multi-machine scope:** Plan §Issues That May Arise claims "The validator will compare registry paths against live filesystem observations and existing machine baseline reports". However, Plan §Pseudocode for `inspect_current_machine` only reads live paths for the *current* machine and lacks any logic to ingest or parse the aggregated machine baseline reports from other machines.
5. **Open Question contradicts Acceptance Criteria:** Plan §Open Questions for User Approval asks whether the registry should "include only the four current machines... or should it reserve placeholders...". However, Plan §Acceptance Criteria already mandates "The architecture doc will include a per-provider/per-machine table for Hermes, Claude, Codex, and Gemini across ace-linux-1, ace-linux-2, licensed-win-1, and licensed-win-2." The plan simultaneously leaves the machine scope open for approval while statically enforcing it as a hard requirement.
6. **Vocabulary collision on "canonical":** The stated issue goal is to "Clarify agent/runtime folder architecture to reduce human and agent confusion". However, Plan §2 Placement matrix uses `canonical_path` to refer to the local filesystem mount path of a checkout, while Plan §1 Authority model defines `canonical-repo-source` as human-authored git-tracked files. Reusing "canonical" for both local mount directories and git-tracked source files actively undermines the goal of reducing vocabulary confusion.
7. **Read-only validation vs. Mutating schema:** Plan §Scope asserts validation is "read-only except for test fixtures and documented outputs." However, Plan §2 Placement matrix model defines `last_verified` as a schema field representing a "timestamp emitted by validation, not hand-authored in the plan." If the validator writes this timestamp back into the source-controlled `repo-placement.yaml`, it violates the read-only constraint and will cause a dirty git tree on every run.

## Blockers

- Finding 2: Reconcile the validator implementation language (Python vs. Bash) to enable the specified TDD assertions.
- Finding 3: Define the YAML parsing strategy for the cross-platform validator.
- Finding 7: Clarify whether validation mutates the YAML file (violating read-only constraints) or merely emits a report.
