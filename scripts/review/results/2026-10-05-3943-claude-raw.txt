## MAJOR

### M1. The rewording weakens the separate approval for consequential actions

You authorized removing plan approval. You did not authorize changing the approval rule for consequential actions, but the new wording does change it.

`SHARED_SOUL.md` and all the runtime SOUL copies still say consequential actions need "explicit approval matching the action, destination and current scope". They also say "implementation approval alone does not authorize publication, deployment…".

Many edited surfaces now add a scope qualifier instead:

- `AGENTS.md`: "consequential actions need matching authority **when not already authorized**"
- `engineering-issue-workflow/SKILL.md`: "Consequential actions **outside task scope** require…"
- `gh-work-planning/SKILL.md` (STEP 5 area and overnight rule 7): "outside that scope"
- `issue-planning-mode/SKILL.md`, `docs/plans/README.md`, `data-execution-results-kanban.md`: "outside existing authority"
- `HARD-STOP-POLICY.md` (batch section): "consequential actions outside that authority wait"
- `shared-risk-workflow/SKILL.md`: "matching existing action authority"

Read together with "the task request authorizes implementation", these lines say a consequential action *inside* task scope needs nothing more. "Work issue #N" could then be read as covering push, close and publication, since the route ends in commit/push/close. That contradicts the unchanged SHARED_SOUL table.

The diff also removes the hook's `git push` block. That was the only mechanical check on push, even if a weak one. So the protection is gone both in text and in code.

**Fix:** use one wording everywhere: *"Consequential actions (publication/push, deployment, access changes, destructive actions) require explicit authorization naming that action and destination; task or implementation authority alone does not cover them."* Add a text test that pins this clause in AGENTS.md and the skills, as already exists for SHARED_SOUL. Separately, either say plainly in the PR that the push gate is being removed, or keep a push-only check.

### M2. The completeness change ships in this diff and would enforce the gate on the bulk-labeled backlog

You said the completeness coupling fix is in a separate lane and not in this diff. It is in this diff: `completeness_gate_check.py`, `autoapply-completeness-label.yml` and the matching tests.

There is also a behavioral regression. The removed comment says a one-time bulk-label put `gate:completeness` on the open backlog. The old docstring says the AND with `status:plan-approved` is what kept "the existing backlog… unaffected". Changing `gate_applies` to check only the opt-in label means every bulk-labeled open issue becomes subject to the gate at close. The new header comment claims "Existing unlabeled backlog is not swept", but that only covers *unlabeled* issues. The *labeled* backlog gets enforced retroactively.

Separately, the `opened` trigger enrolls every new issue, including trivial ones. That may be intended, but it is a wider rollout than before.

**Fix:** take these hunks out and leave them to the completeness lane. Or, if they stay here, add something that keeps the backlog out of scope, such as a cutoff date or a marker on new enrollments, plus a test showing a bulk-labeled legacy issue (`gate:completeness` without plan-approved, created before cutoff) is not enforced.
