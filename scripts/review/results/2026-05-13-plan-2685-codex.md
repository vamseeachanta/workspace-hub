## Findings
1. Plan pseudocode will crash because `_resolve_sf_for_condition()` calls `self.repo_root`, but the same plan says not to add a `repo_root` Pydantic field. In `Pseudocode`, `_resolve_sf_for_condition` has `repo_root = _default_repo_root(self.repo_root)`. In `Pseudocode` under `class MooringLineDesign`, the note says “do NOT persist repo_root as a Pydantic field.” Current `src/digitalmodel/orcaflex/mooring_design.py` has no `repo_root` attribute on `MooringLineDesign`. The first `check_mbl_with_safety_factor()` call will raise `AttributeError` before citation resolution.

2. Plan pseudocode constructs `CitationResolutionError` with positional strings, but the actual constructor is keyword-only. In `Pseudocode`, `_default_repo_root()` raises `CitationResolutionError(f"DIGITALMODEL_REPO_ROOT=...")`, and `get_intact_safety_factor()` / `get_damaged_safety_factor()` raise `CitationResolutionError("Cannot emit citation...")`. In `src/digitalmodel/citations/schema.py`, `CitationResolutionError.__init__(self, *, code_id: str, wiki_path: str, reason: str)` requires keyword arguments. These planned paths will raise `TypeError`, not the intended citation error.

3. The plan spans two git repositories while claiming a single-commit rollback. The user-provided project instructions say `digitalmodel/` is a “Separate git repo — cd in before committing.” GitHub verification also found `vamseeachanta/digitalmodel` as a separate repository, while workspace docs/wiki/rules are in `vamseeachanta/workspace-hub`. Plan `Files to Change` modifies `digitalmodel/src/...` and workspace files such as `.claude/rules/calc-citation-contract.md`, `docs/standards/calc-output-citation.md`, and `knowledge/wikis/...`. Plan `Risks and Open Questions` says “Rollback = revert the single commit,” which is false for a cross-repo change.

4. The plan’s standalone warning behavior contradicts the governing citation contract and does not plan a contract update for that exception. Plan `Deliverable` says standalone deployments “gracefully no-op with a one-shot WARNING rather than hard-crashing.” Plan `Pseudocode` returns `citations: []` in standalone mode. But `docs/standards/calc-output-citation.md` §4.1 says resolution failures are “hard errors at calc time, not warnings,” and `.claude/rules/calc-citation-contract.md` step 4 repeats fail-closed behavior. Plan `Files to Change` only adds a changelog-style entry to `docs/standards/calc-output-citation.md`; it does not amend the fail-closed contract to allow a standalone exception.

5. `test_check_mbl_with_sf_fail_closed_on_missing_wiki` cannot verify the code path as planned unless the implementation is changed. The test table says “empty `repo_root=tmp_path` with `DIGITALMODEL_REPO_ROOT=tmp_path` raises `CitationResolutionError`” with `reason == "page_missing"`. But plan `_default_repo_root()` treats any env var path without `knowledge/wikis/` as an invalid env var and raises the incorrectly constructed `CitationResolutionError` before `get_mooring_safety_factor()` can produce `reason="page_missing"`. Even after fixing constructor args, the planned reason would be an env-var misconfiguration reason, not registry `page_missing`.

6. The planned parent-walk sentinel test does not exercise the claimed behavior. `TDD Test List` says “from a deep tmp path, `_default_repo_root()` returns None,” but plan `_default_repo_root()` ignores cwd/tmp paths and always starts from `Path(__file__).resolve()`. Creating a deep `tmp_path` cannot affect the parent walk unless the test monkeypatches `__file__` or refactors the helper to accept a start path. As written, the test can pass or fail based on the actual installed source location, not the deep tmp fixture.

7. The plan says the production wiki frontmatter must match `_DNV_OS_E301_CITATION_TEMPLATE` “byte-for-byte,” but the template is not a file frontmatter block. In `src/digitalmodel/citations/registry.py`, `_DNV_OS_E301_CITATION_TEMPLATE` contains only `code_id`, `publisher`, `revision`, and `wiki_path`. The actual fixture frontmatter in `tests/citations/fixtures/.../dnv-os-e301.md` includes `title`, `tags`, `sources`, `added`, and `last_updated`, and cannot “match byte-for-byte” a Python dict that includes `wiki_path`, which is not wiki frontmatter. The implementer needs exact required fields, not byte-for-byte matching.

8. Plan `Complexity` says “no new public API surface that downstream repos consume,” while `Deliverable` explicitly introduces “a new public-API sidecar return path (`check_mbl_with_safety_factor()`).” That contradiction matters because public API exposure is part of the plan’s T2/T3 justification and review routing.
