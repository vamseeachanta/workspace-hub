## Findings

1. **`cron_apply --apply` silently re-times two a1 cron jobs vs the live crontab — the deliverable makes this reachable, no acceptance check guards it.** The plan scopes schedule parity out as a non-goal (`:294`, risk `:492`) because `setup-cron.sh` honors `schedule_by_machine` while `cron_apply.py` renders `task["schedule"]`. I verified this is not theoretical for a1: `provider-dream-bridge` (`schedule-tasks.yaml:373-377`) has `ace-linux-1: "5 4 * * *"` but fallback `schedule: "0 4 * * *"`, and `hermes-claude-bridge` (`:411-417`) has `ace-linux-1: "25 4 * * *"` but fallback `"20 4 * * *"`. Both are selected on a1 (control-plane role). `setup-cron.sh:118-124` selects by hostname `ace-linux-1` → `:05`/`:25`; `cron_apply.py` renders only `task["schedule"]` (no `schedule_by_machine` lookup anywhere in `cron_apply.py`/`cron_transaction.py`) → `:00`/`:20`. The plan's *own* deliverable — "self-sufficient from the catalog-rendered crontab" with executable `new_text` and second-pass idempotency — is precisely what makes someone run `cron_apply --apply` as the real installer, at which point these two daily jobs silently shift 5 minutes off the staggered slots the catalog comments call intentional. (harness-update is safe: `ace-linux-1` and fallback are both `15 1`.) Documenting a non-goal in prose does not stop the regression; the dry-run JSON the plan adds shows `new_text` that *looks* authoritative but carries the wrong schedule. **Ask:** add an acceptance criterion that `cron_apply`'s dry-run JSON emits an explicit per-task schedule-divergence warning for `schedule_by_machine` tasks (or a test pinning that `cron_apply` stays dry-run-only for them), so the divergence is visible at apply time, not silent.

2. **Double machine-resolution path left unspecified; backup filename uses the unresolved id.** The R4 fix correctly moves alias resolution ahead of role lookup inside `machine_roles` (pseudocode `:322-324`). But the existing CLI already resolves in `main()` at `cron_apply.py:213-216` (`hostname.startswith(host) or m == host`, alias-blind), and the plan's Files-to-Change (`:387`) does not say whether that layer is removed or retained. With both present, `--machine vamsee-linux1` flows through `main()` unresolved → `resolve_machine` catches it → roles work, but `run_cutover` still receives `"vamsee-linux1"` and `cron_apply.py:174` writes backup `vamsee-linux1-<ts>.crontab` while the canonical machine is `dev-primary`. Minor, but the plan should state which layer owns canonicalization and whether `machine_id` is reassigned to the resolved name before `select_tasks` (`:152`) and the backup path (`:174`).

3. **`test_placeholder_fallback_catalog_lines_are_not_uncataloged` asserts the wrong invariant.** The test (TDD list `:414`, criterion `:433`) only checks lines are "cataloged or preserved rather than uncataloged" — i.e., the cutover does not abort. But `plan_cutover._filter` (`cron_transaction.py:360-367`) *drops* any out-of-block `cataloged` line. notification-purge survives only because it is selected on a1 (legacy pin `machines: [dev-primary, ace-linux-1]` → `select_tasks` legacy_match at `cron_transaction.py:234`) and therefore reappears inside the managed block. The test as specified would pass even if the task were dropped — "not aborted" ≠ "preserved." Strengthen the assertion to verify the selected task's command actually appears in `plan["new_text"]`, not merely that `abort_reason` is empty.

4. **Generic-scan filtering of the `execution_failed` marker is correctness-critical and under-specified.** `ERROR: repo-ecosystem-hygiene execution_failed` (`audit:753,764`) *does* match the generic pattern `(^|[[:space:]])ERROR:` (`cron-health:85`), which `grep -Ec`s the whole 100-line tail (`cron-health:236-243`). For "older ERROR cleared by newer OK" (criterion `:438`, test `test_cron_health_latest_status_clears_older_execution_failed_marker`) to hold, the implementation must strip recognized hygiene marker lines from the tail *before* the generic grep — the pseudocode says this (`:371`) but the plan never states the filter is line-exact and must not also swallow a genuine `Traceback`/`ERROR:` emitted on a non-marker hygiene line. Make the filter's precision an explicit test (a hygiene log containing both a stale `execution_failed` *and* a fresh unrelated `Traceback` should stay RED). (`status=ERROR` without a colon is correctly invisible to the generic pattern, consistent with the reproduction at plan `:259`.)

`★ Insight ─────────────────────────────────────`
- The sharpest defects in a heavily-reviewed plan aren't in what it claims — those were already verified across r1–r4 — but in the *seam between its deliverable and its non-goals*. Here, "make the rendered crontab self-sufficient" and "schedule parity is out of scope" are individually defensible but collide: improving executability is exactly what promotes `cron_apply --apply` to load-bearing, which is when the scoped-out schedule gap bites.
- `cmd in line` substring classification + a `[:60]` truncated key is robust only because `$WORKSPACE_HUB` (14 chars) vs the expanded absolute path (33 chars) shifts the 60-char window enough that raw and rendered keys are *both* needed — the R4 union fix isn't belt-and-suspenders, it's load-bearing for the expanded form.
- "Not aborted" and "preserved" are different invariants in a fail-closed cutover: a line can pass classification and still be filtered out of the output. Tests that assert the absence of an error are weaker than tests that assert the presence of the intended result.
