## 5. New v6 defects (MINOR)

### N1. Timestamp comparability across sources is implicit

§Precedence rule compares `T_approval`, `T_revert`, `T_remediation` but the plan doesn't specify they must be in the same timezone/format. Evidence sources differ:
- **Marker file mtime:** filesystem timestamp, may be local tz.
- **GitHub label transition:** API returns ISO-8601 UTC.
- **Revert commit author-date / remediation commit author-date:** git-reported, typically ISO-8601 with tz.

If one is naively compared against another without normalization, precedence decisions become non-deterministic.

**Required:** Add a note in §Audit contract or §Precedence: "All timestamps MUST be normalized to UTC before comparison. Implementation (#2445) responsibility."

### N2. Timestamp tie-breaking undefined

Two evidence sources with identical timestamps (unlikely but possible at second-precision) would cause ambiguous winner. §Precedence doesn't specify a tie-break rule.

**Recommended:** Add tie-break rule: "On tie, prefer `reverted_later` > `approved_later` > `remediated_later`." (Or state explicitly that ties at millisecond precision are acceptable and deterministic via implementation ordering.)

### N3. Discoverability gap after dropping AGENTS.md update

v6 drops the AGENTS.md change to address Codex L1. But this creates a discoverability gap: the existing `FORCE_PLAN_GATE=1` hint in `require-plan-approval.sh` line 105's error message now points to a documented-nowhere-in-AGENTS env var. A reader encountering the hint will not know that the feature is "reserved — pending #2445."

**Recommended:** Either (a) update `require-plan-approval.sh` line 105 to say `"To bypass: see policy docs/governance/BYPASS-ROLLBACK-POLICY.md"` via this plan (small modification), OR (b) accept that the implementation issue (#2445) is the right place to handle discoverability and explicitly note this risk in §Risks.

## 8. Low findings

### L1. `log_only_safe_paths` precedence description slightly contradictory

§Verdict taxonomy lists `log_only_safe_paths` as "(Timeless — not subject to precedence ordering.)" But §Precedence rule then says "When `log_only_safe_paths` applies AND any terminal-state verdict applies, the terminal state wins." That IS precedence ordering for the safe_paths case.

**Recommended:** Remove the "Timeless — not subject to precedence ordering" parenthetical from the taxonomy row OR clarify it as "has no timestamp of its own; loses to any timestamped verdict."

### L2. §Scenario matrix "Bypass → revert → re-approval of plan" simplifies the case

The row says "Approval of PLAN doesn't un-revert the SHA; revert stands." But what if the operator explicitly approves the bypassed commit SHA (not the plan) post-revert as "we want this change after all"? The advisor would still emit `reverted_later` per current policy. That might be wrong in rare cases.

**Recommended:** Clarify the scenario row: "Approval of PLAN or of the bypassed SHA does not un-revert the SHA; revert stands. To restore the change, a new commit (new SHA) is required."
