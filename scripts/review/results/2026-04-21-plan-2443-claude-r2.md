### Verdict: MAJOR

### Summary
Wave-2 revisions closed most of the Wave-1 MAJOR findings, and the AGENTS.md line-7 TDD citation is accurate. However, the central Wave-2 closure mechanism — the "non-negotiable 20-rule floor" with a TDD step-2 assertion script — has a detection gap that re-opens the rubber-stamp risk the plan claims to have sealed. Additional secondary concerns (env dependencies, acceptance-criterion arithmetic, and drift surfaces on floating action tags) warrant tightening before approval.

### Issues Found
- PRIMARY DEFECT (line 202, TDD step 2): the floor-rule assertion `disabled={k for k,v in cfg.items() if v is False}; missing=floor & disabled` only catches rules **explicitly** set to `false`. A markdownlint config of `{"default": false}` (or `{"default": false, "MD051": true}`) silently disables every unlisted rule — including all 20 floor rules — yet the script exits 0 because none of the floor keys equals `False`. This is precisely the rubber-stamp pattern the floor was introduced to prevent; the Wave-2 remediation for the Claude MAJOR does not actually prevent it.
- SECONDARY (line 202): TDD step 2 uses `import json5`, which is not in Python stdlib. No `uv add` / install instruction precedes the gate, and no fallback parser is listed. If absent, step 2 fails with ImportError — a wrong-reason failure that invites developers to skip or disable the gate. The file is `.markdownlint.jsonc` (JSONC, not JSON5); the parser choice conflates two related-but-distinct syntaxes.
- LYCHEE GATE ARITHMETIC (line 224): the two quantitative bounds (`≤25 entries per audit cycle` AND `exclusion list must resolve ≥95% of discovered links`) interact incoherently on a 495-file corpus. If the corpus yields >500 unique URLs, the 5% tolerance alone exceeds the 25-entry cap — the binding constraint is unspecified. The acceptance criterion can silently become either trivially unpassable or dominated by the looser bound. Denominator for ≥95% is also unspecified (unique URLs vs. link instances).
- ACTION-TAG DRIFT SURFACE (lines 152, 179, 268): SHA-pinning was deferred and `DavidAnson/markdownlint-cli2-action@v16` + `lycheeverse/lychee-action@v2` remain on floating tags. The inline comment `fail defaults to true on lychee-action@v2; no explicit override needed` encodes version-specific behavior as plan correctness; a future `@v2.x` whose defaults change (or `@v2` that resolves to a new major) would silently break fail-on-broken-links with no failing gate to catch it. The explicit `fail: true` was redundantly removed, trading belt-and-suspenders for a latent drift surface on a link-rot detector that already runs unattended on a weekly cron.
- ACTIONLINT AVAILABILITY UNGATED (lines 203, 204, 284): TDD steps 3 and 4 require `actionlint` locally; the validate-workflows CI job was deferred on the rationale that actionlint 'runs locally as part of TDD step 3/4'. If a developer lacks actionlint, the gate silently doesn't run — there is no CI-side backstop. The two deferred items (SHA-pin + validate-workflows) mutually depend on local discipline that neither enforces.
- MD025 FIRST-RUN BURDEN UNMEASURED (line 189, 223): acceptance criterion forbids disabling any floor rule to reach green, and MD025 is enabled with `{"level": 1}` (single H1 per file). On 495 legacy markdown notes that were never linted, multi-H1 files are common in knowledge bases. No evidence was gathered on the count of existing MD024/MD025 violations. The Wave-1 Gemini 'first-run failure burden' concern is partially addressed by the lenient convenience layer, but MD025 specifically remains a realistic forcing function for either a large unscoped cleanup pass or quiet erosion of the 'don't disable floor rules' rule.

### Suggestions
- Tighten TDD step 2 assertion to positively verify each floor rule is enabled (truthy) AND that `default` is not set to false. Example: `for r in floor: assert cfg.get(r, cfg.get('default', True)) is not False`, or simpler: `assert cfg.get('default', True) is not False and all(cfg.get(r, True) is not False for r in floor)`. This closes the `{"default": false}` bypass path.
- Declare the Python tooling dependency explicitly in the plan (preferred: `uv run python -c "..."` with `json5` in a dev-deps group; alternative: use `jsonc-parser` npm CLI since the toolchain is already Node-based for markdownlint-cli2). Either way, make the gate's environment reproducible.
- Resolve the lychee arithmetic ambiguity. Pick one binding rule (e.g., 'whichever is tighter: 25 entries or 5% of unique URLs, and the denominator is the unique-URL count reported by `lychee --dump-inputs`'). Commit to a measurement method so the gate is falsifiable at review time.
- Either SHA-pin the lychee-action on the strength of the `fail: true` inlining argument, OR restore the explicit `fail: true` in the YAML as the cheap defense-in-depth. The current combination (float tag + omit explicit fail) optimizes for minimal diff at the cost of a silent regression surface on the one gate whose whole job is to fail on rot.
- Add a one-line preflight check to steps 3/4 — e.g., `command -v actionlint || exit 1` — so a missing local actionlint errors loudly instead of silently skipping. Or: concede the deferral was load-bearing on discipline alone and re-open validate-workflows CI as a T1 follow-up issue with a linked ID in this plan's §Risks.
- Before committing to 'don't disable floor rules to reach green,' collect empirical MD024/MD025 violation counts on the current corpus (single `npx markdownlint-cli2` dry run). If MD025 violations are >30 files, budget the cleanup pass explicitly in acceptance criteria (or formally scope out MD025 with stated rationale — not a silent disable). Otherwise the T1 complexity label understates execution cost.

### Questions for Author
- Does the TDD step-2 script pass or fail against a config of `{"default": false}`? If it passes, what prevents that config from landing as the 'green' end-state?
- What runtime executes TDD step 2 — a `uv`-managed env with json5 declared, a system `python3`, or something else? Where is the dependency installation step in the execution plan?
- For the ≥95% link-resolution acceptance criterion, what is the denominator and how is it measured? What happens when 5% of the corpus's unique URLs exceeds the 25-entry cap — which constraint binds?
- Was SHA-pinning deferred because the cost/benefit is unfavorable for a personal docs repo, or because the template is expected to be copied into production-sensitive repos later (in which case the deferral exports the hardening debt to a future scope)? The rationale bundles two distinct arguments.
- What is the count of MD024 and MD025 violations on the current achantas-data main? Without this number, the 'fix content, don't disable' acceptance criterion has an unknown implementation cost that could dominate T1 scope.
