### Suggestions
- Replace every live-state assertion about issues, file existence, and prior artifacts with explicit verification evidence in the plan: exact checked path, checked issue number/status, and date/time of verification.
- Resolve the `sha256`/`md5` contradiction by choosing one rule set and carrying it through retrieval, rendered markdown, conformance parsing, and tests. If md5 legacy rows are allowed, specify the only pathway by which they can appear.
- Quote or cite the exact operating-model text for the claimed `§3` md5 carve-out; otherwise remove the exception and keep the contract strictly `sha256:`.
- Make the dependency story coherent: either `#2402` is a hard blocker and no stub ships here, or this issue explicitly includes a temporary fallback path with its own acceptance criteria and deprecation plan.
- Extend the `AC ↔ Test Map` so every acceptance criterion has a corresponding automated test or explicit manual verification step, including `Skill SKILL.md updated + template updated` and `Review artifacts posted`.
- Redefine bypass semantics so a skip is recorded as an override outcome, not a synthetic `PASS`. Specify how hooks, logs, and reviewers distinguish pass vs bypass.
- Expand the threat model to cover subprocess execution, hook runtime, path creation, log-write failure modes, timeout behavior, and any data flow from untrusted issue text into retrieval or ranking.
- Clarify `.gitignore` state: either prove the existing `logs/` ignore already covers the new path or keep the `.gitignore` modification and remove the claim that it is already ignored.
- Narrow scope by splitting enforcement/audit concerns from planner retrieval if both are not strictly required for the single deliverable.
- Add a concrete section for manual verification steps on the `3 real open issues`, including who performs it, what constitutes `sensible output`, and how failures are recorded.
