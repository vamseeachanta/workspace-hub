### Verdict: MAJOR

### Summary
v2 fixes some v1 wording and structure defects, but it is still not approval-ready. The new hook split does not actually cover `git commit --no-verify`, the post-commit SHA contract is specified incorrectly, the correlation key is internally inconsistent and collision-prone, `has_approval_intent()` is still not falsifiable, and `git branch -r --contains` cannot support a boolean pushed/not-pushed claim in stale, shallow, or no-remote states.

### Issues Found

- **`git commit --no-verify` is still unhandled despite being claimed as a detected bypass.** Official Git docs say `--no-verify` bypasses `pre-commit`; the plan's event flow depends on a pre-commit record plus a post-commit correlator, so a local commit made with `--no-verify` produces no plan-gate event for the advisor to consume. That means one of the revision rationale's stated bypass mechanisms is not actually specified.
  Sources: `docs/plans/2026-04-21-issue-2289-bypass-rollback-recovery.md` pseudocode/revision rationale; `https://git-scm.com/docs/githooks/2.29.0.html`; `https://git-scm.com/docs/git-commit/2.52.0`.

- **The post-commit SHA capture spec is wrong.** The plan's Log Schema says `commit_sha` comes from `$GIT_COMMIT`, but Git's `post-commit` hook takes no parameters and the official docs do not define a `GIT_COMMIT` input for it. The correct spec would need to resolve `HEAD` after commit, not rely on an undocumented variable.
  Sources: `docs/plans/2026-04-21-issue-2289-bypass-rollback-recovery.md` Log Schema; `https://git-scm.com/docs/githooks/2.15.4`.

- **The correlation contract is internally inconsistent and not collision-safe.** The Log Schema defines `staged_files_digest` as sha256 of staged file names, but the Risks section claims the mitigation is a digest that includes staged-file content hash. Those are different contracts. The 5-second window plus branch plus digest still collides for repeated commits with the same staged set, `git commit --amend`, or concurrent worktrees on the same branch. The TDD only covers different-file concurrent commits, not same-digest collisions.

- **`has_approval_intent()` is still not falsifiable.** The plan says marker contents must contain an 'explicit approval phrase', but it never defines the allowed phrase set, regex, or source-of-truth artifact. That makes the core decision rule non-deterministic and the tests under-specified. The GitHub-label fallback is also acknowledged as degraded when `gh` is unavailable, but the required degradation test is not in the TDD list or acceptance criteria.

- **`pushed` cannot be a reliable boolean under the proposed runtime check.** `git branch -r --contains <sha>` only inspects local remote-tracking refs; official Git docs state those refs are created at clone/fetch time and updated by `git fetch`/`git push`. In shallow, stale, detached-HEAD-without-upstream, or no-remote states, the command cannot prove 'false'; it can only say 'not observed in currently known remote-tracking refs'. The plan needs `pushed: unknown` or an explicit environment precondition, not a bool.

- **The plan reuses the existing commit-gate path classifier as a safety exemption, but that classifier currently excludes `scripts/enforcement/`, `.github/`, `.claude/hooks/`, and tests from plan approval.** Under the proposed advisor logic, bypass commits that modify enforcement infrastructure can therefore be downgraded to `log_only_safe_paths`, which undermines the exact bypass-resistance surface this issue is supposed to protect.
  Source: `scripts/enforcement/require-plan-approval.sh` `needs_plan_approval()` and the plan's `all_paths_in_safe_list()` branch.

### Suggestions

- Add an explicit detection path for local `git commit --no-verify` bypasses, or narrow scope and remove that claim. As written, the two-hook design only covers bypasses that still execute the pre-commit hook.
- Replace the `$GIT_COMMIT` claim with a documented post-commit resolution method such as `git rev-parse HEAD`, and add a test that proves the hook captures the committed SHA without undocumented env vars.
- Define one canonical correlation key. If it is file-name-only, admit the collision risk and add an ambiguity/unknown outcome. If it is content-based, update Log Schema, pseudocode, risks, and tests to the same contract.
- Specify `has_approval_intent()` as an executable rule: exact marker filename set, exact phrase list or regex, precedence versus labels, and what happens when GitHub label history is unavailable.
- Change `pushed` from `bool` to `true | false | unknown`, or declare a strict precondition that the repo has fresh remote-tracking refs and is not operating in a shallow/no-remote mode.
- Do not classify enforcement-path changes as automatically safe. Split 'safe docs-only bypasses' from 'governance/enforcement surface changes' and require the latter to stay rollback-eligible.
- Add TDD coverage for: `--no-verify` local commit, stale remote-tracking refs, shallow clone/no remote, same-branch same-digest correlation ambiguity, and `gh` unavailable during approval-intent resolution.

### Questions for Author

- What concrete event source is supposed to detect a local `git commit --no-verify` that is never pushed?
- What is the exact allowed 'explicit approval phrase' set for `has_approval_intent()`, and where is that contract anchored?
- Should `git branch -r --contains` returning no matches mean 'unpushed' or 'unknown because local remote-tracking refs are incomplete/stale'?
