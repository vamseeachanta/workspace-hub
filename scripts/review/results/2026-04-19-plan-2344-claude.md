## Findings

### F1 — MAJOR: async-font race not mitigated (Google Fonts)
- **Severity:** MAJOR (silent branding regression risk)
- **Evidence:** Plan's "Risks" section flags Google Fonts fetch-at-render-time as a risk and offers mitigation "accept — this machine has internet." That is necessary but not sufficient. Chrome `--print-to-pdf` can race the async `<link>` load; the PDF is written before `@font-face` resolves, silently falling back to system sans-serif **even with network available**. I verified `.claude/skills/data/documents/md-to-pdf/md_to_pdf.py` (grepped) does NOT use `--virtual-time-budget=...` or `--run-all-compositor-stages-before-draw` — so the plan's "reuse the same flag set from md_to_pdf.py:149-161" actively copies a known-incomplete mitigation.
- **Recommendation:** Add `--virtual-time-budget=10000` (10 s budget advances virtual clock until network idle) to the Chrome invocation in the Pseudocode block. Confirmed to work for Google Fonts by Chromium docs. Alternatively, preload Inter WOFF2 into `docs/gtm/website-pages/fonts/` and rewrite the `<link>` — but that is a follow-up, not a v1 gate. For v1, adding the flag is a one-word change.

### F2 — MINOR: 1-page claim is untested in PDF form
- **Severity:** MINOR
- **Evidence:** Plan states "The HTML's print CSS was never actually rendered to PDF before (closed-#2090 skipped the PDF step)." The entire 1-page acceptance therefore rests on an untested CSS. The pseudocode assumes success and moves straight to `cp` and `git add`. If pdfinfo reports 2 pages, the plan says "do NOT commit" — but does not say to do a dry-run **first** before staging. There is a real chance `cp docs/gtm/capability-summary.pdf aceengineer-website/assets/capability-summary.pdf` runs on a 2-page PDF, tempting an operator to stage it.
- **Recommendation:** Explicitly split the Pseudocode into two phases: (a) **render-and-gate** (render → pdfinfo → fail-fast on !=1 page, exit with a loud message before the `cp`), (b) **stage-and-commit** (only reached if gate passed). A 6-line bash guard in the plan would make this unambiguous.

### F3 — MINOR: Letter paper size relies entirely on CSS `@page`
- **Severity:** MINOR
- **Evidence:** Recent Chrome removed the `--print-to-pdf-paper-size` flag; the default differs by locale (US = Letter, most installs = A4). Plan relies on the HTML's `@page { size: letter }` directive. I verified the CSS has it (line 272), so this should work, but there is no fallback if Chrome ignores the directive in a future version. Plan does not document the Chrome version actually used at render time.
- **Recommendation:** Add to the commit body (or acceptance row) the exact `google-chrome --version` captured at render time, plus a post-render `pdfinfo | grep "Page size"` assertion that it reports `612 x 792 pts (letter)`. Cost: one grep line.

### F4 — MINOR: `Content-Type` for PDFs on Vercel is punted to a follow-up
- **Severity:** MINOR
- **Evidence:** Rollback section notes: "Vercel serves PDF with `Content-Type: application/octet-stream` rather than `application/pdf` [...] add an explicit `Content-Type: application/pdf` header for `/assets/*.pdf` in a follow-up." But the acceptance criterion (`public_url_200`) explicitly greps for `application/pdf`. If Vercel ships the wrong MIME, acceptance fails and the stated remediation is a follow-up issue — not a this-PR fix. That is a contradiction between Acceptance and Rollback.
- **Recommendation:** Reconcile. Either: (a) relax the acceptance regex to `application/pdf|application/octet-stream` (browsers sniff anyway), or (b) commit the `vercel.json` `Content-Type` header change in this same PR. Option (b) keeps the acceptance criterion honest and adds ~6 lines to `vercel.json`.

### F5 — MINOR: plan misquotes the issue body on public-asset path
- **Severity:** MINOR (documentation accuracy)
- **Evidence:** Issue #2344 body (confirmed via `gh issue view 2344`) says: "Place at `docs/gtm/capability-summary.pdf` and `aceengineer-website/dist/assets/capability-summary.pdf`." Plan silently substitutes `aceengineer-website/assets/capability-summary.pdf` (which is the *correct* path, given `dist/` is gitignored). But the plan does not call out that it is overriding the issue body. A reviewer reading the plan and the issue side-by-side will think the plan authored the wrong path.
- **Recommendation:** Add a one-line "Deviation from issue body" note in Resource Intelligence: "issue body says `dist/assets/`; corrected to `assets/` because `dist/` is gitignored (build output)." This avoids a future reviewer re-opening the question.

### F6 — LOW: acceptance text accepts em-dash OR `--` for credentials line
- **Severity:** LOW (clarity)
- **Evidence:** TDD row `pdf_has_credentials_line` says "em-dash tolerance: either `—` or `--`". The HTML source uses `&mdash;` (renders as `—`); the markdown uses `---`. `pdftotext` on a Chrome-rendered `&mdash;` will emit U+2014 `—`, not `--`. The tolerance is unnecessary and masks a render defect: if `pdftotext` emits `--`, something is wrong (maybe a font substitution flattened the em-dash). Issue #2344 acceptance explicitly says "Licensed P.E. **—** Houston, TX" — em-dash only.
- **Recommendation:** Tighten the grep to require U+2014: `grep -E 'Licensed P\.E\. — Houston'`. If it ever fails, that's a real signal to investigate.

### F7 — LOW: `--no-pdf-header-footer` flag name
- **Severity:** LOW
- **Evidence:** Chrome 147's correct flag is `--no-pdf-header-footer`. Plan uses this name. Older Chrome (<110) used `--print-to-pdf-no-header`. Plan does not document the version compatibility. Since `/usr/bin/google-chrome` is v147 and verified, this is fine today — noted for future reference only. No change required.
