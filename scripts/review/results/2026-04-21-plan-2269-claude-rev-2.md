### Summary
The v2 revision closes all three Codex v1-rollback MAJORs with concrete plan-level mechanisms (no `python3`, live-probe prerequisite with attested-primary policy, new §Wrapper/Runner Contract with single-owner rule and `--skip-bootstrap` flag). The plan adds enforceable acceptance criteria and two new tests (`test_verify_script_fails_fast_when_uv_missing`, `test_runner_skip_bootstrap_does_not_source_bashrc`) that move the rules from prose to scripts. Residual defects are MINOR — a test-env `uv`-injection seam is under-specified, the attested-path prerequisite has no plan-level fallback if operator lacks dev-secondary access, and the live wrapper script already on disk (`verify-openfoam-baseline.sh`) still embeds the old `python3` fallback until the implementation PR edits it.

### Issues Found

- **MINOR — `uv` absence test seam is underspecified.** `test_verify_script_fails_fast_when_uv_missing` depends on stubbing `PATH` without `uv`. The wrapper currently detects `uv` via `command -v uv`; a `PATH`-stub fixture will work, but the plan does not pin the fixture mechanism (env var vs. temp-PATH wrapper vs. `OPENFOAM_UV_CMD` injection). Two implementers could make incompatible choices. Tighten to: test injects `PATH` via a fixture that excludes `uv`, AND the wrapper must accept no alternative env-var override for `uv` location (no backdoor). Acceptance criterion currently says "no fallback" but does not forbid an alternative-locator env var that would bypass the test.

- **MINOR — attested-path prerequisite has no plan-level fallback.** §Acceptance Criteria #1 requires an attested live probe on dev-secondary, and §Risks acknowledges "if the planning agent lacks that access, implementation must pause for operator confirmation." The plan does not specify what happens if the probe is blocked at implementation time: does the plan get rolled back again? does a placeholder-attested path land with a TODO? The current language leaves implementation without a defined exit from that state. Either (a) require operator attestation as a hard blocker with a clear handoff mechanism, or (b) allow the supported-fallback list to ship with an explicit "no attested primary yet" marker in the workflow doc.

- **MINOR — wrapper-on-disk drift.** The v1-landed `scripts/openfoam/verify-openfoam-baseline.sh` (line 12-16) contains `if command -v uv >/dev/null 2>&1; then PYTHON_CMD=(uv run python); else PYTHON_CMD=(python3); fi`. The new plan's §Files to Change lists this as "Update" (correct) but §Acceptance Criteria says "**no `python3` fallback**" — the on-disk script is currently non-compliant. A reviewer checking the repo state after the plan is approved (but before implementation lands) will see the violation still live. This is not a plan defect per se, but implementation must land quickly or the plan should note "current wrapper is non-compliant pending v2 implementation" to avoid an attested-contradiction between plan and state.

- **MINOR — `uv run python` + heredoc interaction not pinned.** `uv run python - <<'PY' ... PY` works, but `uv run` may insert warnings on stderr or trigger lockfile refreshes that the current `|| true` / stderr-capture patterns in the wrapper would mishandle. The plan references `uv run python` at the contract level but does not call out whether `uv run --quiet`, `UV_NO_SYNC=1`, or a prewarmed venv is required for deterministic stderr capture during failure paths (`write_failure_verdict` captures stdout only; first-run `uv` chatter on stderr would leak into the runner's error_message field via the `runner-failure` branch). Acceptance criterion for deterministic-output could be tightened, though this verges on implementation detail.
