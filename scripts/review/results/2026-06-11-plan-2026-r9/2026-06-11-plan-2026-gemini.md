## Findings
1. **Batch thread state bug.** Plan §Pseudocode for `_append_events_locked` evaluates all `state_events` against an unmodified `snapshot_before` via a list comprehension: `prepared = [prepare_event(...) for event in state_events]`. If a caller passes multiple sequential events for the same thread in a single batch (e.g., `inbound->extracted` and `extracted->completed`), the second event will falsely evaluate its `from_state` against the original `snapshot_before` state instead of the intermediate state. This guarantees a false `StaleStateError`. A batch append helper must thread the mutated intermediate state through the batch sequence.
2. **Legacy delayed retry falsely advances new cycle.** Plan §Pseudocode for `prepare_event` only performs the cycle-agnostic historical dedup candidate search when `current.state != event.from_state`. If a delayed retry of a legacy no-trigger transition (e.g., `extracted->completed` from Cycle 1) arrives when the new cycle happens to be in that same `from_state` (`extracted` in Cycle 2), it bypasses the `candidates` search entirely. It then inherits the current `cycle_id`, misses the exact `dedup_key` match in `historical_dedup_index` (because its inherited `cycle_id` is new), and is falsely appended, thereby applying a stale action to the new cycle. Historical dedup must be checked for legacy events even when `from_state` matches.
3. **ReactivationPrecheck TOCTOU vs Hash Validation.** Plan §Pseudocode for `sweep_grace` requires a `ReactivationPrecheck` object that is valid "for this store/account set/snapshot hash". However, `sweep_grace` uses a `while` loop that acquires the batch lock, appends events, and rebuilds the snapshot once per batch. This creates an impossible constraint: if the precheck hash is validated outside the loop, it creates a TOCTOU race where the snapshot can change before the first lock acquisition. If the precheck hash is validated inside the lock, the second batch will crash `UnsafeSweepOrderError` because the first batch rebuilt the snapshot and invalidated its hash.
4. **Missing learning_event_id schema linkage.** Plan §D11 requires state events to carry a deterministic `transaction_id/learning_event_id` so that snapshot rebuild/recovery can "scan state events for paired learning ids missing from the learning log and backfill them". However, the `queue_state_entry` schema modifications in §Files to Change explicitly omit adding `transaction_id` or `learning_event_id`, making the state row incapable of durably persisting the linkage needed for crash recovery.
5. **TypeError in ensure_labels.** Plan §Pseudocode for `ensure_labels` sets the default parameter `clients_by_account=None`, but then unconditionally evaluates `client = clients_by_account[alias] or gmail_client_factory(alias)`. This will raise `TypeError: 'NoneType' object is not subscriptable` when called with defaults. Must use a safe `.get()` or `None` check.
