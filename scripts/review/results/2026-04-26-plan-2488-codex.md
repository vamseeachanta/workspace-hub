## Findings
1. The plan’s policy-source-of-truth story is internally inconsistent. In `Pseudocode -> run_weekly_audit_extension()` and `Files to Change`, it requires adding `weekly_summary_sections` entry `filesystem_only_inventory` and then claims the canonical Markdown order becomes `New → Changed → Filesystem-only → ...`, but it never requires updating `config/skills/weekly-audit-policy.yaml` `ranking_policy.section_order`, which is the file the repo already documents as locking ranking behavior. Current YAML only lists `new_findings`, `changed_findings`, `unresolved_high_confidence_findings`, `suppressed_carry_forward_findings`, and `operational_errors_or_skipped_inputs`, and [docs/standards/weekly-skills-audit-policy.md](https://github.com/vamseeachanta/workspace-hub/blob/main/docs/standards/weekly-skills-audit-policy.md) explicitly says the YAML locks section ordering. As written, the plan would create a new section id without updating the policy order that is supposed to govern it.

2. The plan leaves `_core` / `_internal` handling contradictory. `Acceptance Criteria` says those filesystem-only skills “remain active loss-risk but carry `informational: true`,” and `Pseudocode -> run_weekly_audit_extension()` also says the Markdown report must list every `filesystem_only_active` path. Current implementation in [scripts/skills/weekly_skills_audit.py](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/skills/weekly_skills_audit.py) routes informational findings through `_split_informational_findings()` into `suppressed_findings`, and `_write_markdown_artifact()` renders family sections from active findings, not suppressed ones. The plan never states whether the new filesystem-only section bypasses that suppression rule or honors it. That is not a stylistic gap; it changes whether `_core` / `_internal` paths appear in the headline section at all.

3. The new family’s baseline identity is underspecified. The plan requires `filesystem_inventory_findings` to participate in `_baseline_finding_sources()`, `_all_active_findings()`, carry-forward logic, and tests such as `test_filesystem_only_family_participates_in_baseline_and_summary_counts`, but `Pseudocode -> run_weekly_audit_extension()` never defines how `finding_key` is computed for this family. Current baseline behavior in [scripts/skills/weekly_skills_audit.py](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/skills/weekly_skills_audit.py) is entirely keyed off stable `finding_key` values. Without a deterministic key recipe for filesystem inventory findings, the plan does not actually specify how weekly “new vs carry-forward vs changed” behavior remains stable.

4. The path-format contract is missing where it matters. The issue body, `docs/reports/issue-2488-planning-inventory-snapshot.json`, and the plan’s own embedded evidence all use repo-relative paths like `.claude/skills/...`, but current `build_inventory()` in [scripts/skills/weekly_skills_audit.py](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/skills/weekly_skills_audit.py) stores paths relative to `skills_dir`, not repo root. `Acceptance Criteria` and `Pseudocode -> inventory_summary.paths` require stable objects `{path, informational}` but never lock whether `path` is repo-relative or skills-dir-relative. That ambiguity breaks the later requirement to reconcile against the snapshot file and to render `issue_body_drift` rows from the original six paths.

5. The plan invents a “structural test” linking `weekly_summary_sections` ids to `v2.rules` family/rule keys, but no mapping contract is specified anywhere. `Pseudocode -> run_weekly_audit_extension()` says a structural test should prove `weekly_summary_sections` entry `filesystem_only_inventory` “agrees with” rule key `filesystem-inventory.filesystem-only-active`, yet current policy YAML uses `weekly_summary_sections` for report sections and `v2.rules` for per-rule defaults; they are different namespaces with no existing canonical transform between them. The plan asserts a validation rule without defining the mapping it wants the code to enforce.

## Blockers
- Finding 1: source-of-truth inconsistency between `weekly_summary_sections` and `ranking_policy.section_order`.
- Finding 2: unresolved contradiction over whether informational `_core` / `_internal` filesystem-only skills surface in the new headline section or are suppressed.
- Finding 3: missing deterministic `finding_key` contract for `filesystem_inventory_findings`.
- Finding 4: missing path-format contract for `inventory_summary.paths`, despite snapshot/issue drift logic depending on exact path identity.
- Finding 5: undefined schema-mapping rule between `weekly_summary_sections` and `v2.rules`.
