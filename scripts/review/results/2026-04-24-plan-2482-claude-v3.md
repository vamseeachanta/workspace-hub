## Findings

### MAJOR

1. **Exercise 8 is hand-waved — pseudo-code has no "not in allow-list shape" branch.** Plan line 268: "linter denies via 'not in allow-list shape' default." Walking the pseudo-code (lines 201–216) for `knowledge/wikis/cross-links.md`:
   - `path.basename = cross-links.md` — not in `SCOPE_BOUNDING_BASENAMES` → carve-out does not apply
   - `knowledge/wikis/` is NOT a deny-listed directory in v3 (only `data/document-index/` is explicitly dir-added; the others in line 211 are inherited from the scoped-surfaces list but `knowledge/wikis/` as a whole is not deny-listed — it's the allow-eligible surface)
   - `frontmatter` is present (title, created, last_updated, total_cross_references, auto_generated, generator) → not caught by missing-frontmatter rule
   - `frontmatter.collection` — absent → not caught
   - `frontmatter.tag` — no `tags` field in the actual file → not caught
   - body scan for firm-copy negatives — cross-links.md body is a link index, no negatives
   - **terminal branch fires: `exit 2 (allow-eligible, sanitization required)`** — not `exit 1` as the exercise expects
   
   The plan's own acceptance criterion (line 282) requires "linter exit codes match expected column." Exercise 8 fails that criterion against the plan's own pseudo-code. Either (a) add a specific rule (e.g., `if frontmatter.auto_generated: exit 1` or `if path is at knowledge/wikis/ top level: exit 1`), (b) re-classify exercise 8 as `exit 2` (allow-eligible pending human sanitization) and let the manual review gate catch it, or (c) acknowledge the exercise is aspirational. As written, the plan asserts a classification the linter cannot produce.

### MINOR

1. **Exercise 3 (sources/001.md) rule-path citation is wrong.** Plan line 263 says the rule path is "`collection` frontmatter → vendor-derivative." Actual 001.md frontmatter does NOT have a `collection` field (confirmed via `head -10`). The deny actually fires on the `sources/` directory rule (line 170: "`sources/` directory match is **absolute deny**"), which is correct. The misattributed rule path is a documentation bug, not a classification bug — linter still returns deny via the path rule. Fix: swap rule-path text in the exercise to "under `sources/` → absolute deny per rule precedence" and pick a different sibling (e.g., one with `collection: NACE`) if frontmatter-driven deny is the intended demo. Grep `knowledge/wikis/marine-engineering/wiki/sources/*.md` for `^collection:` to find a page that actually demonstrates the frontmatter rule.

2. **v2 MINOR #4 (exit-0 aspirational branch) silently carried.** v2 flagged that linter line 215 (`allow-eligible paths with all sanitization boxes ticked: exit 0`) is not mechanical — sanitization steps 1, 2, 4 (client-identifier stripping, numeric generalization, attribution footer) are human judgments. v3's revision history does not mention this. The linter still has an aspirational third branch that no deterministic check can reach without a ledger consultation. Either delete `exit 0` from the mechanical linter and make exit 2 terminal (all allow-eligible paths require ledger signoff to publish, handled outside the linter), or add an explicit `if ledger has signoff-entry for path@sha: exit 0 else exit 2` step that references `docs/governance/gtm-publish-ledger.yaml`. Silent acceptance of a non-mechanical branch is a latent defect in an "acceptance criterion: all 8 exercises classified" regime.

3. **"Wiki root" in the scope-bounding carve-out is undefined.** Linter line 208: `if path.basename in SCOPE_BOUNDING_BASENAMES and path is at a wiki root`. What counts as a wiki root? `knowledge/wikis/engineering/wiki/` (where `overview.md` lives)? `knowledge/wikis/engineering/` (where `CLAUDE.md`, `SCHEMA.md` live)? `knowledge/wikis/`? Without a precise definition, the implementation is ambiguous. Recommended text: "wiki root = `knowledge/wikis/<domain>/wiki/` — the directory immediately containing `overview.md`, `index.md`, and `log.md`. Files named `overview.md` / `index.md` / `log.md` at any other depth fall through to the normal rule chain." This also closes the "attacker creates `personal/overview.md` to shield a page" concern cleanly.

4. **Publisher-name upstream-correction lock-in unaddressed.** v3 line 272 commits the deny-list to match upstream frontmatter verbatim (including "Deepwarter" typo). If upstream corrects the typo in a future ingest, the linter's canonical list desyncs from the live `collection` values and would stop matching. Plan does not describe the update procedure. Suggested amendment: either (a) linter matches on a normalized form (strip trailing dashes/hyphens, case-insensitive, with a small alias table), or (b) the fidelity note states explicitly that upstream-typo fixes require a linter update commit.
