### New v2 defects (blocking)

- **Contradiction in `staged_files_digest`:** Section 'Log Schema' defines it as '(sha256 of staged file **names**)', but Section 'Risks and Open Questions' claims the mitigation for race conditions is that it 'includes staged-file **content-hash**, not just names'. If only names are hashed, the race condition risk remains unmitigated.
- **Flawed precedence logic for pushed commits:** Section 'Precedence vs TRUST-ARCHITECTURE.md' claims that if an agent auto-reverts a commit, the advisor will find 'no resolving commit on the branch'. This is true for local commits (`git reset HEAD~1`), but for pushed commits (`git revert`), the original bypassed commit remains in history. The pseudocode only checks `any_later_commit_has_review_evidence`, which will fail to detect a revert commit, leading the advisor to erroneously recommend reverting an already-reverted commit.
- **Fragile gh auth fallback:** Treating approval-intent as false when `gh` auth is unavailable will lead to false positive `revert_recommended` verdicts. In `--strict` mode, this could break CI/CD pipelines due to transient GitHub API issues or missing credentials.

### Suggestions

- Update the 'Log Schema' to explicitly mandate that `staged_files_digest` includes the content hashes of staged files (e.g., using `git ls-files -s`), rather than just filenames, to truly mitigate the post-commit correlator race condition.
- Update the pseudocode and tests to detect if a commit has already been reverted (e.g., searching for 'Revert "<commit subject>"' in subsequent commit messages) and emit a `log_only_reverted_later` verdict.
- Implement a dedicated fallback state (e.g., `log_only_auth_failed`) when `gh` auth is unavailable, rather than defaulting to `revert_recommended`, to prevent spurious strict-mode failures.

- Should `install-hooks.sh` cleanly handle the case where multiple concurrent git operations attempt to write to `plan-gate-bypass.jsonl` simultaneously? Is lockfile usage required for the hook loggers?
