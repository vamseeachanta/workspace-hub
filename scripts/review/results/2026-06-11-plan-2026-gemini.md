## Findings
1. Plan §Pseudocode for `reactivate_reply` invokes `transition(account_id=account_id, thread_id=thread_id, ...)`. This violates the core signature defined directly above it (`def transition(store, event):`), dropping the mandatory `store` parameter and passing kwargs instead of an `event` object, which guarantees a `TypeError` at runtime.
2. Plan §Pseudocode for `reactivate_reply` contains a race condition in the `else` block: `append extraction_missing_on_reactivation to queue-state and learning logs`. Appending to the log outside of `transition` bypasses the critical `acquire fcntl LOCK_EX on queue-state.jsonl` safeguard explicitly enforced by `transition`, corrupting the JSONL upon concurrent writes.
3. Plan §Pseudocode for `sweep_grace` iterates batches to `append completed -> purged local transitions under log lock` but entirely omits snapshot materialization. Because `transition` relies on an immediate `rebuild snapshot and meta via tmpfile` after every append, bypassing this step during sweep batches causes the materialized snapshot to instantly desynchronize, leading `lookup` to incorrectly return `completed` threads rather than `purged`.
4. Plan §Pseudocode defines `def sweep_grace(store, now_utc, grace_days=7, batch_size=100):` and unconditionally appends purged transitions to the log, yet claims to "return dry-run/apply report." It exposes no `dry_run` parameter, making safe, non-destructive sweep simulations impossible.
5. Plan §Design Decisions D5 modifies the dedup key by "adding `triggering_message_id` where available." If a thread experiences a second missing-extraction reactivation without a triggering ID, the dedup key falls back to the exact same `account_id, thread_id, from_state, to_state` footprint as its first cycle (`purged` to `inbound`). This causes `transition`'s `append event if dedup key is not already present` check to falsely trigger and silently swallow the valid new reactivation event.
6. Plan §TDD Test List covers positive dedup key updates (`test_dedup_preserves_reactivation_cycle` testing "two triggering message IDs") but completely omits verifying the fallback dedup behavior when `triggering_message_id` is missing/null, leaving the critical failure mode in D5 untested.
