## Defects

### D1 [P1] Plan does not assert that current cwd is the digitalmodel repo root — failure mode is silently green

The failing test does `Path("pyproject.toml").read_text(...)`. If pytest runs from a different cwd (e.g., `digitalmodel/` parent, or with a custom `--rootdir`), the file read either succeeds against the **wrong pyproject.toml** (workspace-hub root has its own pyproject.toml) or raises `FileNotFoundError`.

- **workspace-hub root** has its own `pyproject.toml` — confirmed via `ls /mnt/local-analysis/workspace-hub/pyproject.toml`. If pytest is invoked from workspace-hub root, `Path("pyproject.toml")` reads the wrong file. The original literal-substring test would have failed loudly (substring missing). The proposed `tomllib.loads(...)` parse would also fail (no `tool.setuptools.package-data.digitalmodel` key in the workspace-hub pyproject) — this is acceptable as long as the failure is explicit, but the plan should pin the test to read from `digitalmodel/pyproject.toml` resolved relative to `__file__` rather than cwd.
- **Recommended fix:** Read pyproject as `Path(__file__).resolve().parents[2] / "pyproject.toml"` (test is at `digitalmodel/tests/naval_architecture/test_b1528_sirocco_yaw_moment.py`; parents[2] = `digitalmodel/`). The sibling `test_packaged_yaml_in_built_distribution_preserves_existing_package_data` already uses `Path(__file__).parents[2]` — adopt the same pattern for consistency.
- **Severity P1** because it converts a deterministic test into a cwd-dependent one and risks both false-positives (passing because the OTHER pyproject doesn't have the key — wait, that fails) and false-negatives (no-such-file). Either way, the plan should fix this while it's in the file.

### D2 [P2] No KeyError-vs-AssertionError discrimination

The proposed snippet:
```python
package_data = data["tool"]["setuptools"]["package-data"]["digitalmodel"]
assert "naval_architecture/data/*.yml" in package_data
```
If any intermediate key is missing (e.g., someone renames the table to `[tool.setuptools.package_data]` — note underscore vs hyphen variants are both seen in setuptools history), the test raises `KeyError` rather than a meaningful assertion. The test message should distinguish "package-data table missing entirely" from "table present but glob missing". Plan should specify a defensive lookup with `.get(...)` chains and explicit `pytest.fail` / assertion messages, or use a single `assert ... in data.get("tool", {}).get("setuptools", {}).get("package-data", {}).get("digitalmodel", [])` with a meaningful message string.

- **Severity P2** — diagnostic quality, not correctness.

### D3 [P3] Plan claims forward-compat with single-entry layout but does not write a parametrized test to prove it

Acceptance criterion #2 ("test still passes with single-entry layout") is asserted but never tested. A reviewer relying on the plan to implement has no green-bar proof unless they manually mutate `pyproject.toml` — which the plan correctly excludes from scope. Either:
- (a) drop the forward-compat acceptance criterion (it's structurally guaranteed by the `in` operator on the parsed list), or
- (b) add a unit test that imports `tomllib` and parses an in-memory string with both layouts.

Option (a) is cleaner for a T1; option (b) is over-engineering for the scope. Plan should pick one explicitly.

- **Severity P3** — pedagogical/precision; does not threaten correctness.
