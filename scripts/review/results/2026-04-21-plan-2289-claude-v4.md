## 5. New v4 defects (MINOR)

### N1. `--strict` mode not mentioned in v4 policy

v3 had `--strict` as a Key Design Decision (optional flag for non-zero exit on operator-attention verdicts). v4 scope-narrow moved this to implementation detail, which is correct — BUT the policy doc should minimally state the OPERATOR-FACING CONTRACT that implementation must provide. Specifically: "the advisor MUST support a mode where `log_only_observability_gap` and `revert_recommended` verdicts can optionally cause non-zero exit, without this being the default." Without a policy-level requirement, follow-on implementation is free to omit the feature entirely.

**Required:** Add a brief "Operator interface requirements" sub-section to the policy specifying: (a) default non-blocking exit; (b) optional strict mode must exist; (c) strict mode MUST NOT exit non-zero on `log_only_observability_gap` alone if the cause is `pushed_unknown` on an offline-but-local workflow (this honors Gemini v3's finding).

### N2. Follow-on issue number placeholder propagates risk

The plan references `[#NNNN]` in multiple places (top-matter, AGENTS.md update rationale, Acceptance Criteria). If this plan advances to `status:plan-review` before the follow-on issue is filed, readers see unresolved placeholders. Low risk — these are parseable as TBD — but worth either (a) filing the follow-on issue BEFORE v4 review completes and replacing placeholders, or (b) replacing `[#NNNN]` with explicit `(follow-on issue to be filed at plan-approval time)` phrase.

**Required:** Either file the follow-on issue and update placeholders, or make the TBD status explicit rather than templated `[#NNNN]`.
