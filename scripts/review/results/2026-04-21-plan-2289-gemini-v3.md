### Issues Found (MINOR)

- **Revert-of-revert not handled.** The `has_been_reverted_via_revert_commit` logic does not handle 'revert of a revert' scenarios. If a bypass commit is reverted, and then that revert is itself reverted, the original bypassed changes are active again. The current logic will only see the initial revert and erroneously emit `log_only_reverted_later` instead of `revert_recommended`.

- **Offline `--strict` breaks local workflow.** If an operator is working offline, `resolve_pushed_state` will fail to contact the remote and resolve to `unknown`. In `--strict` mode, this results in a non-zero exit, effectively breaking local, offline workflows for unpushed commits.

### Suggestions

- Enhance `has_been_reverted_via_revert_commit` to track the revert chain. If the found revert commit has itself been reverted, the original commit is active and should be treated as unreverted.
- Refine `resolve_pushed_state` for offline scenarios: if a commit is not present in any local remote-tracking branch (`refs/remotes/*`), it can reliably be marked as `pushed: false` even if the remote is currently unreachable, avoiding the `unknown` state.
- Explicitly define the behavior of `synthesize_observer_events` to gracefully handle the absence of `logs/hooks/all-commits-observer.jsonl` during the first run before any commits are made.

### Questions for Author

- How should the advisor handle a scenario where a bypass commit is reverted, but that revert is subsequently reverted?
- Is it the intended behavior to fail `--strict` enforcement for local-only commits when the user is simply offline and cannot verify remote state?
