## Findings

### 1. MAJOR - v3's value-flow predicates still allow a non-abort early return that drops all live lines

**Evidence:** v3 predicate 2 only requires that every live path ends in a `Return`, that exactly one
distinct terminal return is a `Dict`, and that the dict success return flows through `new_text`
(`docs/plans/2026-07-30-issue-3709-managed-block-classification-v3.md:155`). Predicate 1 still scans
for the ordered pipeline statements in `plan_cutover.body` (`:154`) rather than proving every
non-abort terminal path passes through those statements. The reachability engine deliberately treats
non-constant `if` branches as live alternatives (`scripts/enforcement/scheduler_mutation_python_flow.py:39-45`).

I reimplemented the published seven predicates as a scratch AST probe. The exact r2 counter-example
is rejected as v3 claims: the plan's exact result-flow shape has one dict return but no `new_text`
assignment, so `plan-cutover-result-flow` is false, and the classifier/rebuild/intent predicates are
false. Then I constructed this new wrong implementation shape:

```python
def _success_managed_only(classification_context):
    block = ['# >>> workspace-hub managed ...', '0 * * * * run-managed', '# <<< workspace-hub managed <<<']
    return {'new_text': '\n'.join(block), 'preserved': [], 'uncataloged': [],
            'intent': {'absent': [], 'added': [], 'blocking': []}, 'abort_reason': None}

def plan_cutover(current_text, classification_context, *, acknowledged=()):
    if classification_context:
        return _success_managed_only(classification_context)
    classify_detail = _detail_classifier(classification_context)
    selected_tasks = classification_context['selected_tasks']
    roles = classification_context['roles']
    classified = classify_crontab_lines(current_text, classify_detail)
    if classified['error']:
        return _abort(classified['error'], [], None)
    uncataloged = [r for r in classified['records'] if r['detail']['class'] == 'uncataloged']
    if uncataloged:
        return _abort(f'uncataloged live cron line(s): {uncataloged}', uncataloged, None)
    block = render_block(selected_tasks, roles)
    new_lines = _rebuild_from_records(classified['parsed'], classified['records'], block)
    new_text = '\n'.join(new_lines)
    intent = build_cutover_intent(classified['records'], new_lines, acknowledged)
    if intent['blocking']:
        return _abort('planned crontab would omit live line(s)', [], intent)
    return {'new_text': new_text, 'preserved': [], 'uncataloged': [],
            'intent': intent, 'abort_reason': None}
```

The helper is intentionally outside the four inspected functions. Because `classification_context` is
a real non-empty dict in production, this path is taken before classification, rebuild, or intent.
The visible compliant pipeline remains later in the function. My probe result:

```
new_early_success_counterexample True
  plan-cutover-order          True
  plan-cutover-result-flow    True
  render-block-called-once    True
  classify-populates-records  True
  fallback-records-populated  True
  rebuild-retention           True
  intent-derives-blocking     True
```

This is not one of the admitted R1/R2/R3 semantic residues (`docs/plans/...:246-255`). It is another
pure structural bypass of the attestation itself, and it defeats the compensating "counter-example is
a permanent fixture" and arity guards (`:266-274`) because no named predicate is removed.

**Concrete failure scenario:** commit 4 lands a `plan_cutover` with an early helper return like the
above. `python-postwrite-preservation-multiset-v1` passes, the checker records the destructive
crontab owner as compliant, and any non-empty production context returns only a managed block with no
blocking intent.

**Required revision:** strengthen D5 so every terminal return in `plan_cutover` is classified as
either an `_abort(...)` return or the single success dict, and every path to the success dict must pass
through the specific `classified -> uncataloged guard -> render -> rebuild -> intent -> blocking
guard` value chain. Add a named mutation for this early-success helper shape. Do not rely only on
"exactly one terminal Dict"; non-Dict returns can be destructive too.

### 2. MINOR - the fixture sanitisation rule says host provenance stays out of fixtures, but ace1 still contains a host identifier

**Evidence:** the plan says provenance, including host and machine id, lives in the sidecar and
"never in the fixture" because fixture indices are asserted (`docs/plans/2026-07-30-issue-3709-managed-block-classification-v3.md:432-435`);
the README repeats that rule (`tests/cron/fixtures/README.md:6-14`). The committed ace1 fixture still
contains `# Generated: 2026-05-10T12:28:32Z for ace-linux-1` at
`tests/cron/fixtures/ace1-crontab-2026-07-30.txt:7`.

This does not destroy the property under test: the line is a pre-existing ignored comment, the ace1
fixture is byte-equal to live ace1, and preserving it keeps all indices stable. It is still a rule
contradiction and an answer to the prompt's "does any host identifier survive?" check.

**Concrete failure scenario:** a future reviewer reads the sanitisation policy literally and assumes
host identifiers were scrubbed from the fixture body, while tests actually depend on preserving an
existing ignored host comment.

**Required revision:** either redact or normalize the ignored generated-host comment and rebaseline
indices deliberately, or update the sanitisation rule to say pre-existing ignored comments may be
preserved when needed for byte-equal/live-fixture comparison and are not treated as provenance added
by the fixture process.
