## New v2 findings

### F1 — MINOR: plan underspecifies the Inter WOFF2 provenance, license path, and HTML rewrite diff

- **Severity:** MINOR (will surface at implementation, trivial to specify now).
- **Evidence:** Plan line 68 says "*exact family files picked during implementation to match HTML weight usage*". HTML line 9 requests weights `400;500;600;700;800` (five weights) but the Files-to-Change table at 217-219 vendors only three (`Regular`, `SemiBold`, `Bold` → 400, 600, 700). Weights 500 and 800 are missing. Plan line 346 marks this as an "Open question" but it is actually a concrete specification gap: one of {drop unused weights from HTML, vendor all five, subset Inter to the used glyph set}. The user-Q answer on OFL-1.1 LICENSE path (referenced in the review prompt) is not incorporated — plan line 346 says "added during implementation; flagged here for reviewer awareness" without citing the exact license-file path. Plan line 220 says the HTML `<link>` rewrite will use `../../aceengineer-website/assets/fonts/inter/…` — that is a **cross-tree relative path from `docs/gtm/website-pages/capability-summary.html` to `aceengineer-website/assets/fonts/`**; this works for the Chrome `file://` render path but it is *brittle* if the HTML is ever served from the website (which is in fact the stated closed-#2090 outcome — the HTML is a "website page"). Plan should specify: either (a) vendor fonts under `docs/gtm/website-pages/fonts/` for a same-tree relative path, or (b) keep fonts only under `aceengineer-website/assets/fonts/inter/` and copy the HTML into that tree at implementation time.
- **Recommendation:** before approval, plan should name (a) the exact upstream release (rsms/inter version tag), (b) the weight set to vendor (recommend drop 500 and 800 from the HTML since they are not visibly used — verify via grep of `font-weight:` in the HTML), and (c) the LICENSE path and content. 3 lines in Files-to-Change table.

### F3 — MINOR: versioned-filename v-bump policy is implicit only — script hardcodes `-v1`

- **Severity:** MINOR.
- **Evidence:** Plan line 107 hardcodes `PDF_PUBLIC="aceengineer-website/assets/capability-summary-v1.pdf"` and line 192 hardcodes `public_url: https://www.aceengineer.com/assets/capability-summary-v1.pdf`. Plan lines 303, 305, 345 describe the refresh process ("Update the versioned filename in the render script constant + the sidecar + any cold-email template references") as a manual script edit. There is no auto-bump, no `VERSION` variable with a clear contract, no CI check that bumps when content changes. This works, but the "refresh runbook" is prose at 303, not executable code. An operator asked to refresh in 9 months will have to re-derive this. **Not a blocker** — versioned-filename-by-manual-edit is a reasonable T2-level decision. Flag for awareness: the plan should factor `VERSION=v1` to a single constant at the top of the script so the future edit is a 1-line diff, not a 3-site hunt (script constant, sidecar URL, acceptance commands).
- **Recommendation:** plan should add one line showing the script's intended parameterization, e.g. `VERSION="v1"; PDF_PUBLIC="aceengineer-website/assets/capability-summary-${VERSION}.pdf"` — so the bump policy is code-shaped, not prose-shaped.

### F4 — MINOR: sidecar `.meta` path lives in `aceengineer-website/assets/` — will be served publicly

- **Severity:** MINOR (information disclosure is minimal; still worth thinking about).
- **Evidence:** Plan line 67 places sidecar at `aceengineer-website/assets/capability-summary.pdf.meta`. The build copies `assets/` wholesale to `dist/assets/` (verified: plan line 24; `aceengineer-website/build.js` `copyAssets()`). Vercel's `/assets/(.*)` rule applies — the `.meta` file will be publicly fetchable at `https://www.aceengineer.com/assets/capability-summary.pdf.meta` with a 1-year immutable cache. The file contents include the render timestamp, sha256, and Chrome patch version. None of that is secret, but it is operational metadata, and it will be cached immutably for a year even if the `.pdf` is refreshed to `-v2.pdf` (at which point the sidecar contents are stale — the sidecar should then become `capability-summary-v2.pdf.meta` or live outside `assets/`).
- **Recommendation:** either (a) version the sidecar too (`capability-summary-v1.pdf.meta`), or (b) move the sidecar to `docs/gtm/capability-summary.pdf.meta` (kept in-repo, not published). (b) is simpler and avoids the immutable-cache staleness problem. Plan line 67 shows neither option chosen.

### F5 — LOW: `--virtual-time-budget=5000` rationale conflicts with "primary mitigation is vendoring"

- **Severity:** LOW (will work; the rationale is just slightly tangled).
- **Evidence:** Plan line 206: "advances the virtual clock up to 5 s so any remaining async stylesheet/font load (even with vendored-local fonts there is still a `<link rel="stylesheet">` load cycle) completes before rasterization." Once Inter is served from `file://…assets/fonts/inter/*.woff2` via `@font-face` in the HTML's inline `<style>` block (plan line 220 says the `<link>` is rewritten to an `@font-face` block, not another `<link>`), there is **no** async network fetch cycle. The `--virtual-time-budget=5000` is then *defending against nothing*. The flag is harmless, but the pseudocode description is misleading about what it guards. Review-prompt question "5s may be insufficient... or vendoring makes this moot": **vendoring makes this moot**, and the plan text would be more honest saying so.
- **Recommendation:** update plan line 206 to "belt-and-braces; with vendored `@font-face` there is no network fetch, so this is defence against Chrome headless's own compositor pipeline — not network latency." One sentence.

### F6 — LOW: `pdffonts` assertion is weaker than the plan claims

- **Severity:** LOW.
- **Evidence:** Plan line 158: `pdffonts "$PDF_INTERNAL" | awk 'NR>2 {print $1}' | grep -qi Inter`. `pdffonts`'s first column is the *font name*. Chrome will emit names like `ABCDEF+Inter-SemiBold` (with the random 6-char subset prefix), or `Inter`, or `Inter-Bold`. The `grep -qi Inter` matches all of these, which is good — but it does **not** verify the font is *actually embedded* (vs. referenced by name with `emb=no`). The `pdffonts` `emb` column is what would catch a "font name is Inter but the file is not embedded" regression — exactly the scenario the vendoring is designed to prevent. Plan should assert on the `emb` column.
- **Recommendation:** upgrade the gate to `pdffonts … | awk 'NR>2 && tolower($1) ~ /inter/ && $5 == "yes" {found=1} END {exit !found}'`. Two-line change in the script pseudocode.

### F7 — LOW: Chrome major-version pin leaves patch drift unchecked

- **Evidence:** Plan lines 122-127 hard-fail on major mismatch only. Chrome patch versions (147.x.y.Z) can ship print-pipeline changes. The sidecar records the exact patch version (good) but there is no assertion against a pinned patch. Stronger version pinning (e.g. `APPROVED_CHROME="147.0.7727.101"` with exact-match) would detect a silent Chrome auto-update inside the approved major. Not worth escalating — major is the industry norm for Chrome pinning. Noted for awareness; acceptable as-is.
