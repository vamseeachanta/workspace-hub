1. **Miscitation — CONTROL_PLANE_CONTRACT.md does not say what the plan claims.** Standards table row 3 asserts `docs/standards/CONTROL_PLANE_CONTRACT.md` "require[s] repo-owned Windows tooling rather than an undocumented host-local script." The conclusion survives via `scripts/windows/README.md`, but the contract citation is wrong and should be dropped or replaced.

2. **Audit reports land in the current working directory — observed worktree contamination, no mechanism in the plan.** Re-running the Server audit from the repo checkout wrote `RdpMicAudit-Server-ACMA-HOU-RDS02-20260714-054723.json` into the worktree root, and `git check-ignore` confirms nothing ignores it. The plan's AC "No live report containing volatile user/machine detail is committed" states the outcome but specifies no mechanism: no default report path outside the repo, no `-ReportPath` parameter in the pseudocode signature, no `.gitignore` entry, and no TDD row pinning the default report location (only the `-WhatIf` report-claim test exists). One absent-minded `git add -A` commits machine/user identifiers.

3. **Phase 0 execution path to WS014 is unspecified and rests on an untested audit.** Phase 0 runs "locally on WS014," but the only existing diagnostic lives on RDS02 (`D:\ws\Repair-RdpMicrophone.ps1`) and the repo-owned tool is built in Phase 1 — *after* Phase 0. The plan's own evidence says drive redirection is broken (handoff §"Failing, decisive checks") and #2998 rules out SSH/remote management (plan lines 167-169), yet no transfer/distribution mechanism (git clone on WS014, clipboard, share) is named. Additionally, plan line 33-34 records that only the script's parser check, Server audit, and `-Repair -WhatIf` have passed — the **Client** audit that Phase 0 depends on is unexercised, and Phase 2's repair selection inherits whatever that untested code path reports.

4. **`test_rdp_last_property_wins` pins undocumented client behavior with no evidence source.** Pseudocode line "flag duplicates using last-value-wins semantics" and the TDD row "Duplicate RDP keys are parsed with actual last-value-wins behavior" assert a semantic for duplicate `.rdp` properties that the plan's only external source (the Microsoft RDP-properties page) does not document, and no other citation is given. If the actual client resolves duplicates differently (or differently across mstsc/msrdc/Windows App — the very client ambiguity Phase 0 exists to resolve), the fixture test encodes a guess as a contract and the "effective value" the audit reports is wrong. The plan needs an empirical on-host verification step or a citable source before this becomes a test.

5. **Pseudocode contradicts the evidence-selected-repair principle.** `repair_rdp_profile` verifies the candidate against all three of `audiocapturemode=1, audiomode=0, keyboardhook=2` unconditionally, while Phase 2 says "Apply only the repair supported by Phase 0" and `live_two_machine_validation` says "do not apply every possible repair." Writing keyboard-routing (`keyboardhook:i:2`) and playback (`audiomode:i:0`) values during a microphone-capture repair mutates settings the evidence may never implicate — the exact scope creep the plan forbids elsewhere. The property set should be parameterized by Phase 0 evidence, or the plan should explicitly justify the fixed trio.

6. **`tests/windows/` is a new, unwired test surface.** Glob confirms the directory does not exist; the plan neither flags it as new nor wires it to any harness — the native test is only ever run by hand via the AC command. Live precedent (`tests/readiness/test_windows_scheduler_single_source.py`) puts platform-guarded Windows execution tests under `tests/readiness/` where pytest discovers and skips them portably. Either follow the precedent or specify how `tests/windows/` gets discovered (and by what, on which machines).
