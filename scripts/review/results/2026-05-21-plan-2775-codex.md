## Findings
1. The plan artifact is not retrievable from `main`. The plan’s Artifact Map names `docs/plans/2026-05-21-issue-2775-workspace-hub-sibling-sso-flow.md`, but fetching that exact path from `vamseeachanta/workspace-hub@main` returned 404. This breaks review reproducibility and contradicts the planning workflow in `docs/plans/README.md`, which requires saving the plan under `docs/plans/` and updating the index before gate progression.

2. The target repo scope is still internally inconsistent. Plan §SSoT Strategy says the required repo set comes from `config/workstations/registry.yaml[machine].repos`, but `config/workstations/registry.yaml` `dev-primary.repos` contains only `worldenergydata`, `digitalmodel`, `assetutilities`, `assethold`, `workspace-hub`, and `OGManufacturing`. The same plan’s §Resource Intelligence and §SSoT Strategy include overlay candidates `CAD-DEVELOPMENTS` and `achantas-data`, which are not in that registry set. The plan does not define whether overlay repos may be outside `repos`, where that exception is encoded, or whether the checker/repair command may touch them.

3. The plan’s `load_registry()` pseudocode requires `tier1_repo_root` and `repo_layout=sibling` for sibling checks, but `config/workstations/registry.yaml` only defines those fields for `dev-primary`. `dev-secondary` has `workspace_root: /mnt/local-analysis/workspace-hub` but no `tier1_repo_root` and no `repo_layout`. The plan also says harness duplicated roots must match registry roots, while `scripts/readiness/harness-config.yaml` still has `dev-secondary.ws_hub_path: /mnt/workspace-hub`. The plan needs an explicit registry migration for every machine it will validate, not only a failure test.

4. The sync-script integration remains underspecified against the actual implementation. `scripts/_core/sync-agent-configs.sh` currently resolves Hermes `ws_hub_path` from `scripts/readiness/harness-config.yaml` in `resolve_ws_hub_path()`, not from `config/workstations/registry.yaml`, and accepts only `--force` / `--dry-run`, not `--machine`. Plan §Acceptance Criteria requires `scripts/_core/sync-agent-configs.sh --dry-run` to prove registry-derived `__TIER1_REPO_ROOT__` expansion and no stale nested paths, but the plan does not specify replacing the harness-based resolver or adding a machine selector. As written, the acceptance test can pass a separate checker while the real sync path still reads stale harness state.

5. The plan’s cross-repo source-control strategy is still too vague for writes outside `workspace-hub`. §Files to Change says it will modify target sibling repo `AGENTS.md` files and `.codex/skills` / `.gemini/skills`, but §Acceptance Criteria only requires a final closeout comment and does not require per-sibling repo dirty-state capture, branch/remote verification, commits, pushes, or issue comments in those sibling repos. Issue [#2766](https://github.com/vamseeachanta/workspace-hub/issues/2766) explicitly requires remote URL, branch, ahead/behind, dirty/untracked state, and nested worktree status before repo placement mutations; this plan mutates the consequences of that placement without carrying equivalent safeguards.
