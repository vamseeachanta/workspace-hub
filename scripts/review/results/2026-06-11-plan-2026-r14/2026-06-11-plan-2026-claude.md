2. **Old-timestamp guard exempts reactivation-shaped events when states match.** D3 states "non-reactivation events must have `ts_utc >= current.cycle_started_at`" and pseudocode guard `if current is not None and not reactivation and … event.ts_utc < current.cycle_started_at` deliberately excludes reactivations. Consequence: a delayed/replayed reactivation event (e.g., `completed -> extracted`) carrying a **novel** `triggering_message_id` and a `ts_utc` older than the current cycle bypasses every guard when `current.state == event.from_state` — the stale-ts guard (excluded as reactivation), the state-mismatch branch (states match), and the supplied-`cycle_id` branch (reactivation excluded). It mints a new cycle with `cycle_started_at` in the past and regresses `last_seen_message_id`/`last_seen_received_at_utc` to the older message per D3's baseline materialization rules. This is the same "delayed event from a previous lifecycle applied when state names happen to match" class D5 was built to prevent, closed only for non-reactivation events. The failure direction is fail-safe (spurious reactivation → extra pending work; no purge or Gmail mutation can result), and dedup catches true replays of previously applied events — only never-applied stale messages slip through. MINOR, but worth a guard or an explicit accepted-risk note plus a test.

3. **"Non-forgeable `ReactivationPrecheck`" is an overclaim.** D9 calls the precheck object "non-forgeable," but any Python caller can construct the dataclass by hand; the tests only reject booleans (`test_sweep_apply_rejects_forgeable_boolean_precheck`) and raw snapshots. The actual protection is the under-lock validation of `state_log_offset`/`snapshot_hash`/account coverage — which the plan does specify and which makes a hand-built-but-accurate precheck equivalent to a real one. The wording should claim "validated," not "non-forgeable," so implementers don't attempt (and falsely rely on) a forgery-prevention mechanism that Python cannot provide. MINOR.
