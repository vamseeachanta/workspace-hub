## Findings

1. **The byte-for-byte equality contract is unvalidatable under the plan's own test constraints, and the plan's Risks section omits this entirely.** §3 makes `observed_C == planned_B` (including trailing newline) the apply gate; the final acceptance criterion bars any test or verification command from reading or writing the live crontab; every test uses injected `_read`/`_write` fakes. Real `crontab(1)` implementations are known to canonicalize installed content in some builds (trailing-newline handling, install-time header comments on some vixie derivatives). If any fleet host's crontab binary normalizes at all, every `--apply` becomes a **permanent rolled-back loop** — and the hermetic suite is structurally incapable of detecting it, so it ships green and fails live. The Risks section (§Risks and Open Questions) covers shell grammar, migration, collisions, preservation inversion, and diagnostics — but not this. The plan must either (a) define a normalization contract for the comparison, or (b) add a supervised, owner-gated live dry-run/apply verification step per platform class post-merge.

2. **Derived parsed identities must cover ~60 non-fingerprinted catalog tasks, but no test parses the real catalog.** `schedule-tasks.yaml` has 64 task ids; only 3 carry `installed_fingerprint`. §2 says non-fingerprinted tasks "will receive deterministic parsed identities from their rendered catalog command," and §1 says malformed/unsupported grammar fails closed. Catalog commands include env-assignment prefixes (`PATH=$HOME/.local/bin:$PATH;`), `mkdir -p … ;`, cron-escaped `$(date +\%Y\%m\%d)`, and redirects — so a single catalog command the closed grammar rejects makes cutover **abort machine-wide for every machine selecting that task**. The TDD list's only coverage is `test_all_selected_cron_tasks_have_unique_destructive_identity` against a "fixture matrix," not the live `config/scheduled-tasks/schedule-tasks.yaml`. A test that derives identities from the real catalog for every machine context is missing.

3. **§4's registry enumeration omits the transitive rows' substring branches in the same disposition group.** The plan says the registry "will replace the three substring destructive branches with parsed identities [and] remove `catalog-key-fallback`" — that only describes the `cron_apply.py` operation. But `mutation-surfaces.yaml` lines 213–227 give `scripts/cron/setup-cron.sh` (`schedule-and-basename`, `catalog-key-substring`) and `scripts/setup/new-machine-setup.sh` (`delegated-catalog`, `catalog-key-substring`) their own destructive substring branches inside `cron-catalog-migration`. For `test_registry_advances_only_cron_catalog_group` to derive the group compliant, those rows must migrate too — the plan never says how.

4. **Line-citation error with a coverage consequence: physical-host binding is not in `cron_apply.py:220-296`.** Resource Intel attributes host binding to the 220–296 transaction; it actually lives in `main()` (`cron_apply.py:307-319`). `run_cutover()` itself has no host guard — any caller importing it directly bypasses binding. The acceptance criterion "Physical-local host binding … will remain covered" therefore depends on main()-level tests, and the TDD list contains no test naming host binding.

5. **Tightened matching will reclassify previously-cataloged live legacy lines as uncataloged, with no rollout step.** Today the catalog-key substring (`scripts/foo.sh`) matches absolute-path legacy variants; adjacent-token identities derived from rendered commands (`cd $WORKSPACE_HUB && …`) will not match `cd /mnt/local-analysis/workspace-hub && …` variants — this exact divergence is why the `notification-purge` row exists (`harness-state-classes.yaml:150-161`). §Risks acknowledges "unknown variants will abort" but the plan has no per-machine dry-run comparison (pre- vs post-change plan output) and no fleet inventory of which hosts will start aborting on scheduled reconciliation paths (`harness-update.sh` nightly, per registry lines 229–237). Acknowledged risk, unmitigated operationally.

`★ Insight ─────────────────────────────────────`
The interesting structural tension here: the plan's strongest safety property (hermetic tests, zero live-crontab access) is exactly what makes its strongest correctness property (byte-equality with the real scheduler's stored state) unverifiable. Fail-closed designs convert unknown platform behavior into availability outages rather than corruption — safer, but invisible to the test suite. The standard escape is a two-layer contract: hermetic tests prove the logic, plus one supervised "canary apply" per platform class proves the IO boundary assumption.
