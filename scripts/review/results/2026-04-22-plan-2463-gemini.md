### Verdict: MINOR

### Summary
The plan selects the right artifacts and the right enforcement tier for the aceengineer-website slice of the #2460 contract. Architectural concern: the plan creates a one-off `docs/README.md` and operator map without a mechanism for the file/folder enumeration inside them to stay in sync with the actual filesystem as the site evolves. The #2460 contract is about durable routing surfaces; a "correct on day one, stale on day 90" artifact reproduces the exact defect the contract is trying to prevent.

### Issues Found

- [P1] Critical — **Operator map and `docs/README.md` have no freshness mechanism.** The scorecard calls out `docs/CONTENT_INDEX.md`-style drift as a dominant workspace-hub failure mode; this plan creates two equivalent hand-maintained surfaces in aceengineer-website without a refresh cadence, owner, or validator. Fix: either (a) derive the operator map's directory enumeration from `git ls-files`-driven script output (regenerated on each content-sync run), or (b) register both new surfaces in `workspace-hub/data/document-index/intelligence-accessibility-registry.yaml` with `freshness_cadence: weekly` and a validator that cross-checks the filesystem — either way, move off prose-only.
- [P2] Important — **Dependency on #2460 is declared but no merge gate enforces it.** The Risks section names the hard gate (like #2464's sibling plan) but does not attach it to Acceptance Criteria as a checkbox. An executor who does not read the Risks section can still mark the plan complete. Promote the hard gate to an acceptance checkbox.
- [P2] Important — **`AGENTS.md` upgrade does not declare compatibility with the workspace-hub adapter regenerator.** The AGENTS.md file explicitly says "Do not hand-edit policy here. Update workspace-hub/AGENTS.md and regenerate adapters." The plan hand-edits it. Architecturally, the right move is to (i) teach the regenerator to preserve an `<!-- repo-specific:begin --> … <!-- repo-specific:end -->` block, or (ii) add the repo-specific routing block to `CLAUDE.md` / `README.md` / `docs/README.md` instead. The plan's current posture — "add a repo-specific block below the inheritance header" — will fight the adapter on the next sync.
- [P2] Important — **Discoverability of the new operator map is not wired into `workspace-hub/docs/README.md` or the accessibility registry.** The #2464 sibling plan registers its new routing index in the accessibility registry. By symmetry, the aceengineer-website operator map should be registered too, otherwise the workspace-hub routing index (created by #2464) cannot point at it by reliable path.
- [P3] Minor — **Calculator list is enumerated in the operator map; page/blog/case-study lists are not.** The rationale (calculators are small and stable) is reasonable, but the maintenance asymmetry should be documented in the operator map itself ("Calculator list is exhaustive; blog/case-study lists are representative — update this map when the set of calculators changes, but not on every new post").
- [P3] Minor — **No rollback plan for `DEPLOYMENT_GUIDE.md` banner / DNS banner.** Reverting a banner-only edit is trivial, but a single sentence in Risks would close the loop.

### Suggestions

- Register `aceengineer-website/docs/maps/aceengineer-website-operator-map.md` and `aceengineer-website/docs/README.md` in `data/document-index/intelligence-accessibility-registry.yaml` as L2 `map` / `entry-point` assets with `freshness_cadence` and `owner_issue: 2463`.
- Split the `docs/modules/README.md` edit into its own small follow-on if the `.agent-os/` content there is extensive — a modify in this plan that says "remove or correct" invites scope creep at execution time.
- Consider collapsing `PHASE_4_AND_6_PLAN.md` / `PHASE_6_EXECUTION_CHECKLIST.md` / `GITHUB_ORG_SETUP.md` / `GOOGLE_ANALYTICS_SETUP.md` references into the new `docs/README.md` under a `## Strategy & onboarding` sub-section, so they are findable via the canonical entry point rather than only from the marketing README.
