## Findings

1. **§Deliverable / §Acceptance Criteria — fixture-size target is loose.** Plan says "target `spec.yml` ≤ 2 000 lines; if infeasible due to M-profile segment density, justify in the revision wave." The human-authored template `digitalmodel/docs/domains/orcaflex/library/templates/jumper_rigid_subsea/spec.yml` already achieves a full three-LineType + 17-segment PLET-to-PLEM spec in **492 lines**. A 2 000-line ceiling is ~4× the demonstrated working size and is too permissive. Recommendation: tighten to ≤ 700 lines (50% headroom above the template) or require justification for any value > 500 lines.

2. **§TDD Test List / `test_OCS_200V_collet_linetype_ea_te_per_m` — test name and expected-output unit mismatch.** The test name suggests verifying "EA" (axial stiffness) in `te/m`. Issue #1905 lists OCS 200-V as "mass-per-unit-length 2.514 te/m" under the "General" line-type category — that is **mass per length**, not EA. EA elsewhere in the same #1905 table uses units like "EA=100.5 MN" and "EA=261.6 MN" (force). The expected-output column correctly says "mass-per-length `2.514` te/m", but the test identifier `..._ea_te_per_m` is misleading. Rename the test to `test_OCS_200V_collet_mass_per_length_preserved` to align identifier with assertion.

3. **§Pseudocode / §TDD `test_prebend_curvature_values_match_per_segment` — floating-point tolerance is unstated.** Plan asserts "per-segment tuple equality" without specifying whether `==` is safe. `PreBendCurvaturex/y` are YAML floats; round-trip through `yaml.safe_dump`/`yaml.safe_load` is deterministic for finite decimals but the generator may reformat (e.g., scientific notation vs fixed). Specify either `math.isclose(a, b, rel_tol=1e-12, abs_tol=0.0)` or explicitly state that bytewise string preservation is expected and test that claim.

4. **§Pseudocode / §Files to Change — `expected_native.snapshot.yml` pinning has no regeneration procedure.** The plan commits a pinned generator-output snapshot as a regression guard but does not specify a `scripts/validation/regenerate_jumper_snapshot.sh` or an explicit "how to update when the generator is intentionally changed" workflow. Reviewers will routinely ask how to regenerate on a legitimate refactor. Either (a) add a short paragraph under Risks defining the regeneration procedure and its audit trail, or (b) drop the snapshot in favour of the field-by-field assertion list already in the TDD table.

5. **§Acceptance Criteria / §Files to Change `docs/standards/SEMANTIC_DIFF_TAXONOMY.md` — circular acceptance.** Acceptance says the taxonomy doc "exists with five defined categories and at least one worked jumper-family example per category". But the plan is also creating the taxonomy, so the plan defines the scoring rubric that validates itself. Reduce the self-scoring surface: either (a) require the taxonomy doc to pre-date the classifier (a separate commit in the same PR with its own review), or (b) add a concrete example list in the plan itself — e.g., "IGNORABLE: YAML block-style vs flow-style for `MaterialProperties`; ALLOWED: generator injects `LineType.Name` = `''` default; NORMALIZED: `Yes`/`No` ↔ `true`/`false` in `IncludeCoating`; REFERENCE_SAFE: `Lines[0].LineType` string resolves to a `LineTypes` entry; BLOCKING: `CoatingThickness` drifts from 0.0762 to 0.076." — so the taxonomy contract is partially pre-committed.

6. **§Pseudocode / CLI driver — module invocation path may not match `scripts/validation/` layout.** The plan's CLI driver is placed at `digitalmodel/scripts/validation/jumper_plet_to_plem_semantic_diff.py`. The plan acceptance criterion invokes the CLI as "`uv run python -m digitalmodel.scripts.validation...`" in one clause and as a direct script invocation in another. `scripts/` directories are typically not package-installed Python modules; `python -m` would require an `__init__.py` chain. Specify one invocation contract: either (a) `uv run python digitalmodel/scripts/validation/jumper_plet_to_plem_semantic_diff.py --spec ...` (direct), or (b) expose a console-script entry point in `digitalmodel/pyproject.toml` (clean, but more infrastructure).

7. **§Risks — "proprietary content scrubbing" guarantee is grep-only.** Plan asserts committability via `grep -iE 'ballymore|acma|ansys|saipem'` returning empty. This is necessary but insufficient — other provenance strings could remain (internal project codes, document IDs embedded in the extracted YAML comments, vessel names beyond `installation_vessel_01`, or field asset names). Recommendation: extend the scrub check to include a positive allowlist of strings that MAY appear (e.g., the three LineType names, `PLET`, `PLEM`, `OCS 200-V`, generic physical constants) plus a negative denylist beyond the current four tokens. Alternatively: require the fixture `spec.yml` to be authored by hand from the template rather than scrubbed from the extract, which sidesteps the question entirely.

8. **§Pseudocode `classify_diff` — cross-reference resolution is described as "by name" but PLET/PLEM are constraints, not LineTypes.** The pseudocode says "resolve cross-references by name" and the OBJECT_SECTIONS loop iterates "for each section in OBJECT_SECTIONS". The plan does not specify what happens when a `Lines` entry references a `Constraint` (for endpoint anchoring) vs a `LineType` (for material/geometry). If the classifier treats all cross-refs as a flat namespace, a spec with a LineType and a Constraint sharing a name (unlikely but possible) could silently misresolve. Specify that cross-ref resolution is section-scoped (LineType refs resolve against `LineTypes`, Constraint refs against `Constraints`) — this mirrors `post_validator.py` behavior.

9. **§Risks — `spec_upgrader.py` explicit exclusion leaves a follow-up gap.** Plan pins a single entry path `ProjectInputSpec(**data) → ModularModelGenerator.from_spec(spec) → generate` and says the upgrader is out of scope. But some production entry points may run the upgrader implicitly (e.g., CLI flags, file magic). The plan should either (a) add a test that asserts the upgrader is NOT invoked by the pinned path (defensive assertion), or (b) expand scope. Otherwise the claim "this plan proves the forward contract for jumpers" is narrower than it sounds — it proves the contract via one entry point.

10. **§Deliverable vs §Files to Change — classifier must know per-structure-type taxonomy rules, but the only rule set is `jumper`.** Plan introduces `taxonomy_rules[structure_type]` indirection but only defines rules for `structure_type="jumper"`. If another caller (FPSO from sibling #2454, riser) invokes `classify_diff(..., structure_type="riser")`, the classifier will have no rules and all differences will fall into some default bucket. Plan should either (a) specify that unknown structure types default to strict equality (all differences = BLOCKING unless IGNORABLE), or (b) state that the classifier is jumper-only and will ValueError on other structure types until rules are added.
