### F1 — [MAJOR] The plan's central deliverable is already on main; the proposed merge is a no-op
- **Location:** Plan lines 17, 93, 107–109, 175, 179, 210, 252.
- **Defect:** The plan repeatedly proposes "Merge `origin/fix/codex-stdin-hang` (SHA `257b47dd9`) → `main`" as the core deliverable. That work is already on main. Verification:
  - `git log main..origin/fix/codex-stdin-hang | wc -l` returns `0` — the branch tip is an ancestor of main (`git merge-base main origin/fix/codex-stdin-hang` returns `257b47dd9...`).
  - `git log --all --oneline --grep="codex-stdin-hang"` shows commit `ab266cd45` on main with the identical commit-message body as `257b47dd9` (cherry-pick / rebased landing on 2026-04-24).
  - `git diff origin/fix/codex-stdin-hang main -- scripts/review/plan-review-fanout.sh scripts/review/tests/test_plan_review_fanout.sh` returns empty — both files are byte-identical on main and on the fix branch.
  - `grep -n "no-interactive" scripts/review/plan-review-fanout.sh` returns hits only inside comments at lines 17 and 89; the actual `codex exec` invocation at line 94 already reads `codex exec "$combined" > "$out" 2>"$err" </dev/null || rc=$?` — exactly the post-fix state the plan claims it will land.
  - The regression-guard test (`grep -qF -- '--no-interactive'` failing the test) is at `scripts/review/tests/test_plan_review_fanout.sh:172`.
- **Impact:** Acceptance criterion AC#1 ("`git merge --no-ff origin/fix/codex-stdin-hang` lands on `main` cleanly") is unfalsifiable as written — the merge will be empty (fast-forward / already-up-to-date). AC#2 ("regression guard for `--no-interactive` passes") will pass on main today regardless of any plan action. The plan's "Resource Intelligence Summary" (line 17) still describes the wrapper as "currently passes `--no-interactive` and lacks the `</dev/null` redirect on the codex branch" — that reflects pre-`ab266cd45` state, not the current state of main as of 2026-04-26.
- **Recommended fix:** Re-baseline the plan against current main. Drop the merge step. Either (a) close #2479 with a note that the wrapper-side regression is already fixed and only the version-probe / smoke-test scope remains, or (b) keep #2479 open scoped purely to the version-probe + live-smoke deliverables. The Adversarial Review section's claim "the plan will be hardened against these" (line 234) does not pre-empt the most fundamental defect: the plan author did not re-verify the merge state at draft time.

### F3 — [MAJOR] Risk that 0.125.0 has a *latent* bug is not named — and `KNOWN_GOOD` whitelisting it on 4 short artifacts is thin evidence
- **Location:** Plan lines 130, 197–198, 253, and the "Risks and Open Questions" section (lines 252–258).
- **Defect:** The plan's `KNOWN_GOOD` list whitelists `0.125.x` entirely (line 130). The justification is 4 review artifacts, none of which exercise stdin-heavy or large-prompt paths and three of which are <4KB. The original #2406 hang manifested only on "substantial plan files" (per the issue title); a 1117-byte artifact (2487-codex.md) cannot prove the upstream stdin-hang is fixed at the size threshold that triggered the regression in the first place. Line 253's risk entry mentions a "0.126.x release that re-breaks `codex exec` differently" but does not name "0.125.0 has the same hang on a larger plan than we have tested" — the highest-likelihood adjacent failure mode.
- **Impact:** AC#5 ("`bash scripts/review/check-codex-version.sh` returns rc=0 with stdout containing `OK`" on 0.125.0) is trivially satisfied because the probe is *defined* to whitelist 0.125.0. The probe does not actually prove 0.125.0 is hang-free; it just encodes the operator's belief. The opt-in smoke test (AC#6) uses a "90-byte fixture" — explicitly the same lower bound that the plan elsewhere asserts the 0.124.0 hang reproduced on. A 90-byte plan exercises neither size-dependent nor stdin-volume-dependent code paths; passing the smoke test does not refute "0.125.0 hangs on a 40 KB plan."
- **Recommended fix:** Add a risk: "`KNOWN_GOOD = 0.125.x` is asserted on 4 small artifacts. A larger-fixture smoke test (e.g., the 40 KB #2406 plan itself, replayed against 0.125.0) should run before whitelisting." Either widen `smoke_codex_live.sh` to use a multi-KB fixture, or add a second smoke test variant.

### F6 — [MINOR] Acceptance Criterion AC#4 requires a 0.124.0 downgrade with no procedure attached
- **Location:** Plan line 213.
- **Defect:** AC#4: "On a host running codex-cli 0.124.0 (manually downgraded), `bash scripts/review/check-codex-version.sh` returns rc=3…". The plan explicitly rejected version-pinning via npm in pre-empted critique #3 (line 240) on the grounds that "pinning would require a `npm install -g @openai/codex@X.Y.Z` line in machine bootstrap that does not exist today." So this AC requires an operator to perform the very downgrade the plan disclaims as out-of-scope, and there is no procedure for restoring 0.125.0 afterward. Per `feedback_codex_cli_0_124_upstream_regression`, 0.124.0 is the broken version — running it intentionally on a working machine to satisfy AC#4 risks corrupting the operator's review pipeline if the post-test re-upgrade fails.
- **Impact:** AC#4 is testable in principle but operationally hostile; it incentivizes skipping the test or mocking the version output (which is what AC#4 should ask for, given the unit-test mock pattern is already established in tests `test_check_codex_version_known_bad_0_124`).
- **Recommended fix:** Reframe AC#4 as a unit-test-via-mock (which is already covered by `test_check_codex_version_known_bad_0_124` per line 199). Drop the "manually downgraded" wording. Optionally retain a note that operators *can* validate via downgrade if they choose.

### F7 — [MINOR] Pre-empted critique #5 misses an obvious complementary defense
- **Location:** Plan lines 244–245.
- **Defect:** Pre-empted critique #5 considers stderr-token-detection as a defense-in-depth and defers it to v2. But it does not consider the simpler complementary defense: **a wallclock timeout on `codex exec`**. The plan's wrapper integration (line 155) is `codex exec "$combined" > "$out" 2>"$err" </dev/null || rc=$?` — no `timeout N`. If 0.125.0 latently hangs at runtime, the version probe says OK but the live invocation hangs forever. A `timeout 120 codex exec …` is a 1-line addition and a defense layer the plan does not name.
- **Impact:** The probe's WARN-on-untested path (line 142) returns rc=0 and proceeds to invoke `codex exec` — without a wallclock timeout, an unbounded hang is possible on novel versions.
- **Recommended fix:** Add a wrapping `timeout 120` (or similar) around the codex-branch invocation in `plan-review-fanout.sh` as a third defense layer. Add an AC for "wrapper does not block longer than N seconds even when the probe returns OK and the underlying CLI hangs."

### F8 — [MINOR] Source count of "5 distinct sources" is generous
- **Location:** Plan line 84.
- **Defect:** The plan claims 5 sources: issue #2479 body, issue #2406 body, feedback memory file, fix-branch commit metadata, wrapper source code. Two of those (issue body + branch commit metadata) are the same author's framing of the same incident from two surfaces. The retrieval-contract bar of ≥3 distinct sources should mean ≥3 *independent* sources, not 3 self-authored pointers to the same incident.

- **Recommended fix:** Re-count as: "3 independent sources (issue thread / live CLI / wrapper source) plus 2 retrieval-context references (feedback memory, prior plan #2406)."
