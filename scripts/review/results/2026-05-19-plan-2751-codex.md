### Summary
MAJOR

1. `scripts/memory/bootstrap-machine.sh` does not guarantee SOUL runtime installation on a fresh machine, so the G1 fix can still silently fail. The plan claim says Step 10 will run `bash scripts/memory/bootstrap-machine.sh` and that "bootstrap-machine.sh internally calls scripts/agents/install-soul-runtime.sh". In the actual script, that call is guarded by `if [[ -d "${HOME}/.hermes" || -d "${HOME}/.codex" || -d "${HOME}/.gemini" ]]; then bash "${INSTALL_SOUL}"; fi`. On a fresh machine with no provider directories yet, `install-soul-runtime.sh` is skipped. This directly breaks the acceptance criterion requiring `readlink ~/.codex/AGENTS.md` and `readlink ~/.hermes/SOUL.md` after a fresh run.

2. The OS-token inconsistency is not fully fixed. The plan’s `detect_os()` pseudocode says Darwin returns `macos`, and it says this aligns to `scripts/memory/bootstrap-machine.sh`. But the TDD table still says `test_detect_os_darwin` expects stdout `darwin`. That means the first implementation can satisfy either the pseudocode or the test, not both. Citation: `TDD Test List`, row `test_detect_os_darwin`.

3. PowerShell parity is not actually test-gated. The plan acceptance requires `pwsh scripts/setup/new-machine-setup.ps1` to reach functional parity on Windows 10/11, but the TDD section says "PowerShell tests deferred to v1.1 if time permits". That leaves the biggest new surface, native Windows bootstrap, with no required automated test coverage in v1. This is not a minor gap because the plan creates `new-machine-setup.ps1`, `verify-setup.ps1`, `emit-machine-status.ps1`, and claims cross-platform delivery.

4. The Windows plan depends on Git Bash without installing or validating it as a first-class prerequisite. The mapping table says hooks, Codex pin, AI-provider bootstrap, and Hermes config will be reused "via Git Bash subshell". The existing `scripts/windows/setup-scheduler-tasks.ps1` hardcodes `$GitBash = "C:\Program Files\Git\bin\bash.exe"` and exits if absent, proving the dependency is real. But `new-machine-setup.ps1` is presented as native PowerShell parity and does not include a Step 0 that verifies Git Bash, installs Git for Windows, or fails before partial setup. Native Windows without Git Bash cannot execute multiple claimed parity steps.

5. The idempotency claim is false across dates. The plan says rerun should produce zero filesystem changes except baseline timestamp. Actual `scripts/memory/bootstrap-machine.sh` embeds `TIMESTAMP="$(date +%Y-%m-%d)"` into `~/.claude/CLAUDE.md` and rewrites the file when desired content differs. Re-running on a later date mutates `~/.claude/CLAUDE.md`, not just `config/machine-baselines/<hostname>.{md,yaml}`. The plan does not remove that timestamp or exclude home-runtime files from the idempotency contract.

6. The status schema is incomplete for the plan’s own “harness parity” claim. The 13 dimensions omit setup-critical state already handled by `new-machine-setup.sh` / `verify-setup.sh`: submodule initialization, repo hooks, shell profile wiring, npm global prefix/PATH, cron vs Task Scheduler, SSH key presence, `.env` existence, `uv`/Python availability, and Git Bash availability on Windows. A machine can pass the proposed 13 dimensions while failing the existing setup verifier.

7. Secret redaction coverage is under-specified and currently insufficient. The test regex only covers `gh[opsu]_...` and `sk-...`. The plan explicitly tracks status files in git but does not specify coverage for GitHub fine-grained PATs (`github_pat_...`), Anthropic keys (`sk-ant-...`), Gemini API keys (`AIza...`), OAuth refresh-token fields from JSON credential files, or JWT-like bearer tokens. The mitigation says “hard-coded redaction patterns” but does not enumerate modern token formats.

8. Acceptance criterion still says `gemini auth` even though the patched pseudocode says Gemini has no auth subcommand and uses `gemini -p ping`. Citation: Acceptance Criteria: “Real run launches `claude auth login`, `codex auth login`, `gh auth login`, `gemini auth` interactively.” This is internally inconsistent and likely untestable.

MINOR

1. `instantiate-hermes-config.sh` pseudocode says “else python yaml.safe_load”; repo instructions say Python should be run via `uv run`, not bare Python. The plan should specify the exact command and fallback behavior.

2. `scripts/agents/install-soul-runtime.sh` itself only links Hermes/Codex when `~/.hermes` / `~/.codex` already exist and explicitly skips Gemini SOUL. The status schema includes `hermes_soul_symlink` and `codex_agents_symlink`, but no planned step guarantees those parent directories exist before the installer is invoked.

3. The aggregator drift model remains too vague for non-control-plane machines. The plan notes role-aware expectations are deferred, but the deliverable says the control plane can assess fleet harness drift. Without role-aware expected values, worker machines will produce noisy false drift or control-plane-only dimensions will be incorrectly treated as failures.

4. The plan says “All four provider CLIs auto-install via apt/brew/choco when absent,” but Codex is installed through `scripts/install/pin-codex.sh` via npm and Claude/Gemini are npm packages. The acceptance criterion should match the install-channel model already patched into pseudocode.

5. The real macOS and Windows smoke tests are listed as tests, but there is no CI-verifiable mechanism, fixture, artifact format, or required operator command beyond writing session notes. Manual smoke tests are acceptable as acceptance evidence, but they should not be conflated with automated `tests/setup/test_*.sh` coverage.

- Normalize every OS token to `linux|macos|windows` or `linux|darwin|windows` across pseudocode, tests, docs, status schema, and acceptance criteria.
- Require PowerShell tests in v1 for Windows-specific scripts or downgrade Windows parity to explicitly best-effort with follow-up issue.
- Add Git Bash detection/install/early-fail handling to `new-machine-setup.ps1`.
- Remove date-dependent generated content from idempotency-sensitive files or explicitly exclude home-runtime files from the idempotency acceptance criterion.
- Expand status schema to include submodules, hooks, shell profile, PATH/npm, scheduler, SSH, env file, Python/uv, and Windows Git Bash state.
- Enumerate and test token redaction patterns for `github_pat_`, `sk-ant-`, `AIza`, OAuth refresh tokens, and JWT-like secrets.
- Replace `gemini auth` acceptance text with the verified Gemini auth path before approval.
