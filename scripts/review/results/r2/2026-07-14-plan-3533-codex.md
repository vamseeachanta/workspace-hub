## Findings

1. The plan invents “transfer history” that the current data does not establish. Plan §Decision Model lines 80–82 and §Concrete public schema lines 103–105 recast legacy `status: done` as `transfer.legacy_status`. But `scripts/data/document-index/build-ledger.py:2-9,213-238,268-297` defines the ledger as engineering-code porting status and derives `done` from an implemented data-source record or completed WRK item. `scripts/data/document-index/generate-coverage-report.py:104` explicitly defines `done` as “Implemented in codebase.” Calling all 435 values historical transfers creates false provenance rather than preserving semantics.

2. The plan still contradicts its originating issue. Workspace-hub #3533 requires preventing `done` or `current` when rights evidence is absent. Plan §Decision Model line 82 and Acceptance Criterion line 243 explicitly permit a new `done` transition without use permission or technical acceptance. Renaming `done` as transfer completion does not resolve this deviation, and the plan does not identify it as a user decision or amend the issue’s acceptance boundary.

3. The proposed transfer gate has no representable evidence. Plan lines 82, 166–169, 210, 226, and 243 require a destination alias plus content reconciliation, while lines 78 and 282 exclude holdings, fingerprints, paths, permissions, and private evidence from this repository. The concrete schema stores only `transfer.evidence_status`; it has no destination, digest, reconciliation result, attestation reference, or validation source. A validator could only trust a self-asserted `verified` enum.

4. Private authority validation is outside scope but remains a claimed deliverable. Plan lines 78 and 282 defer holdings, permissions, and qualified-review evidence to unplanned llm-wiki #840, which remains `status:needs-plan`. Nevertheless, pseudocode lines 138–164 and tests at lines 215–217, 223, and 227 require validating private holdings and deriving usability. The Artifact Map contains no private schema, adapter, fixture contract, or version boundary. Implementing those tests would pre-authorize an interface owned by #840.

5. The schema and mirror contract are structurally undefined. Plan line 110 promises a closed schema, but lines 90–108 omit the live `codes`/`standards` containers, existing registry fields, ledger fields, and the legacy mirrors required by line 80. Existing `status` uses `current | check | superseded` (`data/design-codes/code-registry.yaml:4-5`), while proposed canonical states use publisher lifecycle and `resolution_gate`; `check` cannot satisfy literal “mirror equality.” Only one generic registry schema is named for two different YAML envelopes, and no schema is assigned to the curated enrichment input.

6. The public disclosure allowlist contradicts the concrete public schema. Plan line 86 says the export will contain only canonical identity, official publisher metadata/evidence, and `resolution_gate`. Lines 99–107 additionally expose internal `implementation_basis`, transfer history/evidence status, and `private_authority_state`. Test `test_public_export_disclosure_allowlist` at line 229 does not reject these extra disclosures.

7. The chronology test cannot be implemented from the proposed fields. Plan line 110 requires chronology based on explicit publisher dates and test line 212 requires rejection of impossible edition dates and amendments without a parent edition. The concrete schema contains only scalar edition/amendment values and the catalog retrieval timestamp; it contains no edition publication/effective date, amendment date, or amendment-parent identity.

8. Future producer runs can bypass the “new completion requires evidence” rule. `build-ledger.py:213-238,268-297` will continue converting newly added `implemented` sources and future completed work items to `done`. The plan provides no migration cutoff or grandfathered-record manifest to distinguish pre-migration historical values from newly synthesized ones. Such rows can therefore be regenerated as `legacy-unverified`, bypassing Plan lines 82 and 243.

9. The producer/consumer inventory remains incomplete. `scripts/data/document-index/mark-exhausted.py:38-40,62-82` and `reclassify-domains.py:412-471` both rewrite the complete canonical ledger directly, bypassing the proposed validator, atomic replacement, and curated merge. `scripts/data/ace_resource_audit.py:164-185` treats ledger counts as disk coverage, while `mkt_a_wiki_unblock.py:68-115` performs a scalar-path join. None appears in §Files to Change or an explicit exclusion analysis.

10. Acceptance remains non-executable as a complete verification contract. Plan line 240 names only three test files and leaves “focused tests for every migrated consumer” unspecified, despite modifying eleven consumers. Existing suites for domain views, research-domain mapping, taxonomy, doc-key lookup, ledger generation, query, and coverage are not enumerated. The sparse preflight at line 239 also omits `scripts/legal`, although line 254 requires the sparse-excluded legal scan.

11. The cross-repository compatibility criterion is circular. Plan line 86 defers the export name/version until implementation, while lines 228 and 250 require compatibility with an unspecified “#837 fixture,” stale-record behavior, and version negotiation. Neither the Artifact Map nor llm-wiki #837 identifies such a fixture or freshness threshold. Implementation would choose its own contract and then test itself against an invented downstream representation.

12. Mandatory resource intelligence is missing. `.claude/skills/coordination/issue-planning-mode/SKILL.md` Step 1 requires a drive-file-search invocation with cited results or an explicit “no relevant drive files” statement for every issue. Plan §Resource Intelligence lines 39–65 cites stale inventory catalogs and filename conclusions but contains neither the required command evidence nor a no-hit statement. This is particularly material because the issue requires empirically verified live holdings.

## Blockers

2. Reconcile the plan with #3533’s rights-gated `done/current` requirement.
3. Define machine-verifiable, disclosure-safe transfer evidence or defer verified transitions.
4. Remove private usability validation from #3533 or define an explicitly approved interface with #840.
5. Specify separate schema envelopes, ownership, legacy mappings, and validation targets.
6. Reconcile the public schema with its disclosure allowlist.
7. Add the fields required to validate edition/amendment chronology.
8. Define a migration cutoff that prevents future `done` synthesis from being grandfathered.
9. Inventory every canonical ledger writer and authority-sensitive consumer.
10. Provide exact sparse-checkout and test commands covering every changed consumer and the legal scan.
11. Define the downstream fixture, version, freshness, and mismatch contracts before claiming compatibility.
12. Complete the mandatory live drive-resource intelligence step.
