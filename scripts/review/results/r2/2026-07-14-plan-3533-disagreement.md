- **The concrete public schema contradicts the plan's own disclosure allowlist, and its target file is ambiguous.** §Decision Model (line 86) states the export "will expose **only** canonical code identity, official publisher metadata, evidence URL/time/type, and `resolution_gate`." The plan creates two schema files (`standards-registry.schema.json` and `standards-authority-public.schema.json`, §Files to Change lines 178–179) but presents one schema block that never says which file it specifies. If the block is the canonical registry schema, the export interface has no concrete spec beyond one prose sentence; if it is the export, it violates its own allowlist, and `test_public_export_disclosure_allowlist` (line 229) as written would not catch `implementation_basis`/`legacy_status` leakage because they aren't in its prohibited list. For a plan whose entire thesis is exact contracts, the central contract is self-inconsistent.
- **Two cross-repo issue references are unqualified and one collides with a different, closed workspace-hub issue.** §Risks/Dependency order (line 283) cites "#839" and "#1588" bare. In a workspace-hub plan, "#1588" resolves to wh#1588 — verified CLOSED and unrelated ("Parametric spec.yml generator — bridge hull_library to DiffractionSpec pipeline"). The intended issue is almost certainly digitalmodel#1588 (OPEN, "Verify DNV-RP-C203 seawater-CP S-N basis and fail-closed citations"). "#839" is llm-wiki#839 but is never qualified or introduced anywhere in the plan. This also violates the repo's inline-issue-URL must-fire rule. A dependency chain that mis-joins its own issue identifiers is exactly the identity defect class this plan claims to eliminate.

### codex

- The plan invents “transfer history” that the current data does not establish. Plan §Decision Model lines 80–82 and §Concrete public schema lines 103–105 recast legacy `status: done` as `transfer.legacy_status`. But `scripts/data/document-index/build-ledger.py:2-9,213-238,268-297` defines the ledger as engineering-code porting status and derives `done` from an implemented data-source record or completed WRK item. `scripts/data/document-index/generate-coverage-report.py:104` explicitly defines `done` as “Implemented in codebase.” Calling all 435 values historical transfers creates false provenance rather than preserving semantics.
- The plan still contradicts its originating issue. Workspace-hub #3533 requires preventing `done` or `current` when rights evidence is absent. Plan §Decision Model line 82 and Acceptance Criterion line 243 explicitly permit a new `done` transition without use permission or technical acceptance. Renaming `done` as transfer completion does not resolve this deviation, and the plan does not identify it as a user decision or amend the issue’s acceptance boundary.
- The proposed transfer gate has no representable evidence. Plan lines 82, 166–169, 210, 226, and 243 require a destination alias plus content reconciliation, while lines 78 and 282 exclude holdings, fingerprints, paths, permissions, and private evidence from this repository. The concrete schema stores only `transfer.evidence_status`; it has no destination, digest, reconciliation result, attestation reference, or validation source. A validator could only trust a self-asserted `verified` enum.
- Private authority validation is outside scope but remains a claimed deliverable. Plan lines 78 and 282 defer holdings, permissions, and qualified-review evidence to unplanned llm-wiki #840, which remains `status:needs-plan`. Nevertheless, pseudocode lines 138–164 and tests at lines 215–217, 223, and 227 require validating private holdings and deriving usability. The Artifact Map contains no private schema, adapter, fixture contract, or version boundary. Implementing those tests would pre-authorize an interface owned by #840.
- The schema and mirror contract are structurally undefined. Plan line 110 promises a closed schema, but lines 90–108 omit the live `codes`/`standards` containers, existing registry fields, ledger fields, and the legacy mirrors required by line 80. Existing `status` uses `current | check | superseded` (`data/design-codes/code-registry.yaml:4-5`), while proposed canonical states use publisher lifecycle and `resolution_gate`; `check` cannot satisfy literal “mirror equality.” Only one generic registry schema is named for two different YAML envelopes, and no schema is assigned to the curated enrichment input.
- The public disclosure allowlist contradicts the concrete public schema. Plan line 86 says the export will contain only canonical identity, official publisher metadata/evidence, and `resolution_gate`. Lines 99–107 additionally expose internal `implementation_basis`, transfer history/evidence status, and `private_authority_state`. Test `test_public_export_disclosure_allowlist` at line 229 does not reject these extra disclosures.
- The chronology test cannot be implemented from the proposed fields. Plan line 110 requires chronology based on explicit publisher dates and test line 212 requires rejection of impossible edition dates and amendments without a parent edition. The concrete schema contains only scalar edition/amendment values and the catalog retrieval timestamp; it contains no edition publication/effective date, amendment date, or amendment-parent identity.

The plan provides no migration cutoff or grandfathered-record manifest to distinguish pre-migration historical values from newly synthesized ones. Such rows can therefore be regenerated as `legacy-unverified`, bypassing Plan lines 82 and 243.

Plan line 240 names only three test files and leaves “focused tests for every migrated consumer” unspecified, despite modifying eleven consumers. Existing suites for domain views, research-domain mapping, taxonomy, doc-key lookup, ledger generation, query, and coverage are not enumerated.
