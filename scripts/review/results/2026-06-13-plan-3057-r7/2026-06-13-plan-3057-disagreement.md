### claude

- **BLOCKER — The plan's selector (§Pseudocode `select_catalog_tasks`, lines 347-352) would render Windows-Task-Scheduler tasks into the Linux crontab.** The pseudocode is `if role_match or machine_match: include`, with no `legacy_excludes` handling and no `scheduler == 'cron'` filter. Simulated against the live catalog for ace-linux-1 (`machine_tokens={dev-primary, ace-linux-1, vamsee-linux1}`, role `control-plane`), this selects four tasks that both `setup-cron.sh` and current `cron_apply.py` correctly exclude: `provider-dream-bridge-win`, `hermes-claude-bridge-win`, `win-repository-sync`, `win-session-state-commit` — all `machines: [ace-win-1, ace-win-2]`, `scheduler: windows-task-scheduler`. They role-match `control-plane` but are pinned to Windows. `setup-cron.sh:118` skips them (`scheduler != 'cron'`) and `:121` skips them (no token overlap); current `cron_apply` drops them via the conflict path. The plan's selector pulls them in via `role_match=True`. This is a direct regression of the alignment the plan claims to deliver (Deliverable line 294, Acceptance line 457), and `render_catalog_task_for_cron` would emit a `powershell`/Windows command as a cron line. No negative test exists to catch it.
- **BLOCKER — The new selector silently drops `select_tasks`' conflict-resolution and `conflicts` reporting, which is live, not dormant.** `cron_transaction.select_tasks` (cron_transaction.py:237-257) resolves role-vs-legacy conflicts via `roles_authoritative` and reports a `conflicts` list that `cron_apply.py` surfaces (`:160`, `:163`, `:222-223`). Live data: 5 conflicts on dev-primary, 8 on dev-secondary. The plan's `select_catalog_tasks` has no conflict concept and the TDD list (lines 421-445) has no test preserving conflict output. The plan never states whether it extends `select_tasks` or replaces it with a `cron_render` selector; §Files-to-Change line 403 ("select tasks by roles plus machine-token pins") and the pseudocode imply replacement, which regresses tested behavior.
- **§Resource Intelligence line 16 mischaracterizes the root cause, risking an incomplete fix.** It states `cron_apply.py` "selects role-matching tasks," implying machine pins are ignored. In fact `select_tasks` already matches `machine_id in machines` (cron_transaction.py:234); the actual defect is that `cron_apply.py:215-216` resolves the host to the canonical registry key `dev-primary`, while catalog pins use `ace-linux-1`, so `'dev-primary' in ['ace-linux-1']` fails (verified: `solver-watch-results`/`solver-dashboard` dropped under `dev-primary`). The conclusion is right but the stated mechanism is wrong; a fix derived from the wrong mechanism is what produced findings #1/#2.
- **MINOR — The "Reproduction proofs" block (plan lines 145-164) is not literal output.** The JSON contains `"... preserved lines elided ..."` and `"..."` placeholders that would not parse, and the current `run_cutover` dry-run result emits no `new_text` key (cron_apply.py:162-166). Presented under a "verify-against-repo-state" header, this is a hand-curated illustration, weakening the empirical claim that the dry-run reproduces the defect.
- **MINOR — Shared-renderer schedule-token precedence diverges latently from setup-cron.** §Pseudocode lines 320-322 use registry `machine.hostname` as the first `schedule_by_machine` precedence token, whereas `setup-cron.sh:126` uses the live `hostname -s`. They coincide on ace-linux-1 and for all current sbm keys, so `test_cron_render_uses_current_ace_linux_1_schedule_golden_values` passes — but it makes the "byte-identical parity" claim (Acceptance line 458) a tautology for the alias case it most needs to cover (a host reached via an alias whose live hostname ≠ registry `hostname` and appears as an sbm key). The parity fixture should exercise the alias-hostname case explicitly.
- **MINOR — Existing live audit evidence does not satisfy its own acceptance criterion.** Acceptance line 459 requires completion across `required` + `optional` + `non_tier1_machine_access_current` buckets, but the live proof (lines 221-243) shows only `repo_count=17` with no demonstration that 17 spans all three buckets. The plan adds a bucket-coverage test (line 436) but the closeout must not treat the 16.13s/17-repo run as proof of the three-bucket criterion.

### codex

- Plan §Pseudocode lines 347-352 changes selection to `role_match OR machine_match` without preserving the current legacy exclusion/`roles_authoritative` conflict semantics in `scripts/cron/cron_transaction.py:215-218` and `scripts/cron/cron_transaction.py:237-257`. That would select role-matching tasks even when their `machines:` list excludes the current machine. Concrete live case: `dev-secondary` has roles `[comms-dispatch, sim-worker]` in `config/workstations/registry.yaml:181-184`; `notification-purge` has `roles: [comms-dispatch]` but `machines: [dev-primary, ace-linux-1]` in `config/scheduled-tasks/schedule-tasks.yaml:311-320`; `solver-watch-results` and `solver-dashboard` have `roles: [sim-worker]` but `machines: [ace-linux-1]` in `config/scheduled-tasks/schedule-tasks.yaml:665-686`. The proposed selector would install these on dev-secondary/ace-linux-2, while current `setup-cron.sh` only selects by machine-token intersection at `scripts/cron/setup-cron.sh:120-122`.
- Plan §Deliverable line 294 says it will “align `cron_apply.py` selection with setup-cron's physical-machine targeting,” but the plan’s `setup_cron_install` pseudocode calls `select_catalog_tasks(catalog.tasks, roles, context.machine_tokens)` at lines 340-343, and that selector includes role matches at lines 347-352. Current `setup-cron.sh` does not select by roles at all; it skips unless `machine_tokens & task_machines` is non-empty at `scripts/cron/setup-cron.sh:120-122`. This is a false parity claim and would make the legacy installer itself broader than the stated “physical-machine targeting” reference.
- The TDD list does not include a negative regression for role-match plus machine-exclusion. The listed selection/parity tests at plan lines 423-428 only cover alias resolution, machine-pinned inclusion, and positive cross-path parity. They do not assert that `notification-purge` stays off dev-secondary/ace-linux-2 or that `cron_transaction.py`’s existing non-authoritative legacy exclusion behavior remains intact.
