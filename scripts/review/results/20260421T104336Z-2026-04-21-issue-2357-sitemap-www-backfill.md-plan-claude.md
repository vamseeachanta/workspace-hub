### Summary
A well-scoped T1 plan to normalize apex-host `<loc>` entries to the canonical `www` host in `aceengineer-website/sitemap.xml`, with a TDD-style regression test added first, deterministic xmllint validation, and clear acceptance criteria. Resource intelligence is solid (real file paths verified, prior issue #2391 context noted, issue-body path mismatch flagged). The plan is ready to proceed once the noted governance drift (missing `.planning/plan-approved/2357.md` vs. any live label) is reconciled and the three adversarial reviews complete.

### Issues Found
- [P3] Minor: The Adversarial Review Summary lists Claude/Codex/Gemini all as PENDING, yet the plan header lists this very file as the planned Claude review output — trivially consistent, but the plan should not be marked ready for user approval until that table is populated and the 'Revisions made based on review' entry is filled or explicitly marked 'no revisions required'.
- [P3] Minor: The 'TDD Test List' includes `sitemap_xml_is_still_well_formed` powered by an external `xmllint` binary, but the existing test file is Jest (`tests/js/demo-links.test.js`). The plan should state explicitly whether xmllint is invoked from Jest via child_process (requiring xmllint on every CI runner), invoked as a separate npm script / CI step, or replaced with a Node-side parser — otherwise this acceptance criterion is ambiguous at implementation time.
- [P3] Minor: `sitemap_loc_count_preserved` as written allows 'identical count OR a documented intentional decrement'. 'Documented' is not a falsifiable test assertion; the plan should specify where the documented decrement lives (commit message, PR body, or a constant in the test) so the check can actually pass/fail deterministically.
- [P3] Minor: Acceptance criterion about adding an issue comment noting the `public/sitemap.xml` vs `aceengineer-website/sitemap.xml` path discrepancy is a governance/documentation task mixed into the implementation acceptance list — consider separating implementation-gates from post-merge comms so the merge criteria stay strictly code-verifiable.

### Suggestions
- Before implementation, decide the well-formedness gate mechanism explicitly (Jest + fast-xml-parser vs. `npm run validate:sitemap` invoking xmllint vs. a GitHub Actions step) and document the choice in the Files to Change table; this removes ambiguity called out in Risks/Open Questions.
- Add a concrete assertion that the full set of expected paths (not just the 5 demo-detail slugs) round-trips after normalization — e.g., snapshot-test the sorted list of path-only (host-stripped) `<loc>` values so reviewers can diff intent vs. actual with one glance.
- Resolve the `status:plan-approved` drift before execution: either create `.planning/plan-approved/2357.md` via the approval path, or strip the label on the issue. The plan correctly flags this — make it an explicit pre-implementation gate, not just a risk bullet.
- Consider a one-line note in the plan about whether the `www`-host rewrite should also bump `<lastmod>` on affected rows. The plan says metadata is untouched, which is defensible, but search engines may re-fetch faster if `<lastmod>` advances — worth an explicit 'intentionally not bumped' statement with rationale.
- Since #2391 already ships `sitemap.xml` to `dist/` via `copySitemap()`, add a smoke check (manual or scripted) that the deployed artifact at `https://www.aceengineer.com/sitemap.xml` shows the normalized hosts post-deploy, separate from the in-repo Jest gate.
