## Defects

### D1 [P2] — "Confirmed cause" decision matrix understates assetutilities risk

§3 routes H2 (editable assetutilities build hook) to "out of scope; file follow-up issue." But §1 hypothesis ranking lists H2 as Medium prior. If H2 actually confirms, declaring it out-of-scope leaves #2606 with no fix and no doc — issue stays open.

**Why it matters:** the plan's escape valve ("inconclusive → document workaround") only fires for H4/H5/H6. If H2 confirms, the matrix sends the plan into limbo: not fixable in digitalmodel, not documentable as a digitalmodel issue, but the digitalmodel `uv sync` hang is real.

**Fix:** add a fall-through row: "H2 confirmed → still document the workaround in digitalmodel/CONTRIBUTING.md AND file follow-up issue against assetutilities AND link both from #2606." Don't let the issue close without at least the workaround landing.

---

### D2 [P2] — strace step requires sudo, unverified availability

§2.2 says `sudo strace -f -p "$UVPID"`. On ace-linux-1 the agent profile may or may not have passwordless sudo for strace. If sudo prompts for password, the strace step silently blocks the investigation.

**Why it matters:** investigation gates the decision point. If 2.2 is unrunnable, the plan is wholly dependent on 2.4 (toggle compile-bytecode), which is fine *if H1 is right* — but 2.4 alone doesn't distinguish H1 from H4 (seed-step hang). Without strace, an inconclusive 2.4 produces an inconclusive plan.

**Fix:** add a fallback — `/proc/<pid>/stack` and `/proc/<pid>/status` (readable without sudo for own processes), or `gdb -p <pid> --batch -ex 'thread apply all bt'` if gdb-without-sudo is allowed for own UID. Document that strace requires `sudo` and may be unavailable; non-blocking.

---

### D3 [P2] — Smoke-test §5 will be flaky on fresh runs (downloads from PyPI)

§5 proposes `timeout 120 uv sync` as a smoke test. Cold-cache run on a slow network would legitimately exceed 120s — that's not a hang, that's just a download. The "120s" threshold conflates two failure modes (real hang vs. slow download) and produces false positives.

**Why it matters:** if the wrapper ever runs in a fresh CI image with empty uv cache, it will fail for the wrong reason and erode trust in the smoke. The plan acknowledges "false positives would burn CI budget" but still picks 120s as the threshold.

**Fix:** Either (a) require a warm-cache precondition in the script preamble (`uv sync` once unconditionally, then time the second run, expect <30s); or (b) raise the threshold to 600s and rename the script `test-uv-sync-no-hang.sh` to make clear it's hang-detection not perf-budget.

---

### D4 [P3] — Plan claims "32k .pyc files present" supports H1 but the same fact is consistent with prior successful sync

§1 cites `~32k .pyc files in venv` as evidence for H1 (compile-bytecode is the hang). But those .pyc files could equally have been written by a *previous* successful sync run — their existence proves only that the venv was successfully populated at some point, not that the *current* hung sync is in the bytecode-compile phase.

**Why it matters:** the evidence chain in §1 is presented as stronger than it is. An adversarial reader (especially user) could call this out as motivated reasoning.

**Fix:** soften §1 row H1 evidence to: "compile-bytecode is double-set; large dep tree typically takes 30-90s for compile pass; the silence-after-Uninstalled signature matches uv's quiet compile phase. ~32k .pyc files exist in venv but are inconclusive for *which* run wrote them." Then call out 2.4 as the disambiguating test.
