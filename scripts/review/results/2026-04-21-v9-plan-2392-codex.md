### Verdict: MAJOR

### Summary
The plan still leaves correctness-critical behavior contradictory or under-specified in ways that can produce different implementations while all listed tests pass.

### Issues Found
- `Identity Join Contract` says every source candidate ends in "exactly one authoritative status" from the enum, and `Cross-domain coverage policy` says a wrong-domain match should classify `domain-mismatch`. But the `Pseudocode` does `add_domain_mismatch(...)` and then immediately `add_gap(...)`. That makes the same record both `domain-mismatch` and a gap, which breaks the claimed single authoritative status model and leaves the per-domain YAML `status` field impossible to specify consistently.
- `Optional semantics` says "`degraded` runs may emit reports, but do not satisfy approval/acceptance gates for full coverage completeness." The `Manual verification before approval` section then says "degraded findings may remain" as long as dry-run exits `0`, and the `Scheduled Task Contract` publishes exit code `2` degraded runs. Those three claims do not define one approval rule. A reviewer cannot tell whether a degraded run is acceptable, rejectable, or publishable-for-approval, so the gate is still ambiguous.
- The `Scheduled Task Contract` command unconditionally runs `git add docs/reports/wiki-coverage-gaps` after `rc=$?`, even when the detector exits `1` fail-closed. That conflicts with the same section's clean-worktree claim and creates a concrete failure mode where a partial/error run leaves the checkout staged and no longer clean for the next publication attempt.
- The `Deduplication contract` says higher-precedence records win for `source_path`, `title`, and `availability_tier`, while the supplemental field contracts also say rows missing authoritative identity/path fields must become `identity-unresolved`. The plan never specifies whether lower-precedence non-empty fields may fill holes from a higher-precedence record. That is a correctness-critical gap: the same duplicate set can become `covered`, `gap`, or `identity-unresolved` depending on an unstated fill policy.

### Suggestions
- Make `domain-mismatch` handling single-path and explicit: either it is its own terminal status that is reported outside gap YAML, or it is serialized as a gap with a different diagnostic field. Do not keep both behaviors.
- Define one normative degraded-run policy covering approval, manual smoke, and scheduled publication. State exactly which degraded reasons are approval-blocking and whether exit `2` outputs are publishable but never approval-satisfying.
- Change the scheduled command so `git add` only executes for `rc=0|2`, or explicitly clean partial outputs on `rc=1` before exit.
- Specify dedupe field resolution precisely: either `winner-takes-all even if empty` or `first-non-empty by precedence`, with tests for sparse higher-precedence records. Include this for `source_path`, `title`, `availability_tier`, and domain/discipline reconciliation.

### Questions for Author
- When a source record has a canonical `doc_key` but only wrong-domain wiki coverage, should a domain YAML entry be emitted, and if so what exact `status` value must that entry contain?
- Is a degraded run ever sufficient for plan approval, or only for operational publication/report refresh? The plan currently says both yes and no in different sections.
