## Findings

### MAJOR (new in r2 — r1 did not flag these)

- [MAJOR] Issue acceptance criterion `daily scheduled job exists` is not satisfied by the plan's Files-to-Change. The GH #2465 body lists `Scheduled local cron job` and `daily scheduled job exists` as required deliverables, and `scripts/cron/crontab-template.sh` declares a HARD RULE: *"all cron/task-scheduler entries must be declared here"* (referring to `config/scheduled-tasks/schedule-tasks.yaml`). The plan at line 169 explicitly punts: `This plan does not create a cron file in this planning-only overnight session; cron creation and registration with the remote scheduler is a morning-operator / status:plan-approved action after this plan is accepted.` That is a scope mismatch — the `status:plan-approved` implementer executes the plan as-written and does not add deliverables. Either add a `config/scheduled-tasks/schedule-tasks.yaml` task-entry row to Files-to-Change, or explicitly narrow the issue body before `status:plan-review`.

- [MAJOR] Placement ambiguity undermines the planning contract. Files-to-Change line 163 says `implementation script (placement: scripts/cron/tier1-indexing-daily.sh OR scripts/automation/tier1-indexing-freshness-audit.py (placement decided by implementation agent))`. A plan that defers script placement also defers the question of which conventions are reused — sourcing `scripts/cron/lib/cadence-common.sh` vs. a Python automation pipeline are structurally different. Two implementation agents reading the same plan will produce incompatible results. Pick one path; recommend `scripts/cron/tier1-indexing-freshness.sh` to match daily-cron convention (`control-plane-drift.sh`, `broken-windows-sweep.sh`, `coverage-drift-report.sh`).

- [MAJOR] No retrieval-contract-union satisfaction for the `cat:harness` + `cat:automation` labels on this issue. Per `docs/plans/README.md`, harness-class issues must cite `CONTROL_PLANE_CONTRACT.md`, `config/agents/`, and `.claude/rules/` at minimum. RIS line 29 cites `CONTROL_PLANE_CONTRACT.md` but neither `config/agents/` nor `.claude/rules/` appears as a Documents-consulted entry with a concrete finding. This is exactly the r6 Codex finding that blocked #2460 for two review rounds; the same gap in #2465 is a direct-evidence defect a Codex fanout WILL flag the first time it runs.

- [MAJOR] Binary exit scheme collapses yellow into green. Pseudocode lines 136–137: `0 if green or yellow; non-zero if red`. This is incompatible with the sibling-cron convention (`control-plane-drift.sh` uses a banded severity where `warn` and `block` thresholds are separable) and it starves the cron-health escalation framework (#2291) of the signal it needs to differentiate "at least one repo has drift" from "nothing wrong." Use `0=green, 1=yellow, 2=red`. This defect is upgraded from r1's MINOR escalation note because the exit-code shape is load-bearing for the entire downstream alerting surface.
