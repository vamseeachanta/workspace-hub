I have enough evidence to write the adversarial review. The key discovery is that `config/workstations/registry.yaml` already exists as a canonical machines registry and the plan proposes a parallel one.

`★ Insight ─────────────────────────────────────`
This plan trips a classic governance anti-pattern: it proposes a "single source of truth" registry in a directory that already contains a file declared as "HARD RULE: all machine identity/capability data lives here." Adversarial review must always grep the proposed directory before approving a new authority artifact — the existence of `registry.yaml` is the kind of finding that flips a plan from MINOR to MAJOR.

## Findings

1. **`config/workstations/registry.yaml` already exists as the canonical machines registry — plan proposes a parallel `config/workstations/repo-placement.yaml` in the same directory without acknowledging the prior art.** `registry.yaml:1-4` reads: *"registry.yaml — Single source of truth for all workstations. Read by: scripts/cron/setup-cron.sh, scripts/operations/workstation-status.sh. HARD RULE: all machine identity/capability data lives here."* The existing file already encodes 6 machines (`dev-primary`/ace-linux-1, `dev-secondary`/ace-linux-2, `licensed-win-1`, `licensed-win-2`, `macbook-portable`, `gali-linux-compute-1`) with `os`, `role`, `workspace_root`, `ssh`, `tailscale_ip`, `capabilities`, `storage`, `repos`, `telegram_hermes`, `data_access_profile`, `readiness_freshness_thresholds`. The plan's §Resource Intelligence Summary (lines 13-23) cites `scripts/readiness/harness-config.yaml` and `config/agents/hermes/config.yaml.template` but never names `config/workstations/registry.yaml`. The plan's own Risk row "Registry becomes another stale authority source" (line 251) is triggered by the proposal itself. **This is the central blocker.**

2. **A pre-existing authority-map artifact at `.claude/skills/workspace-hub/repo-structure/references/agent-runtime-authority-map.md` already defines authority classes for the same domain — plan ignores it.** That file (untracked but present, 48 lines, dated `May 19 10:43` — same day as this plan) defines 5 authority classes (`Canonical source`, `Generated runtime`, `Local runtime/symlink`, `Bridge output`, `Cache/snapshot/state`) with agent behavior rules. The plan proposes `docs/architecture/agent-runtime-folder-authority.md` with 9 classes (lines 75-85), no mention of the existing skill reference or whether the skill is being replaced/extended/duplicated. Two parallel authority taxonomies with different cardinalities and naming will harm, not reduce, agent/human confusion — directly contradicting issue #2758's purpose.

3. **Schema's machine-ID scheme is incompatible with the existing canonical registry.** Plan example (lines 93-111) keys machines by hostname: `machines:\n  ace-linux-1:\n    os_family: linux\n    ...`. Existing `config/workstations/registry.yaml` keys machines by role (`dev-primary:`, `dev-secondary:`) with `hostname:` as a *field*. The plan's Open Question #4 asks "should the registry live under `config/workstations/` as proposed, or should it be folded into `scripts/readiness/harness-config.yaml`" — but the real question (fold into the *existing* `config/workstations/registry.yaml`) is not asked, and the machine-ID scheme mismatch is not surfaced. The plan would silently fork machine naming.

4. **`tier1_repos`/`skill external_dirs`/`registry.yaml.repos` divergence is observed by plan but not reconciled.** `scripts/readiness/harness-config.yaml:22-26` declares 4 tier-1 repos (`assetutilities, digitalmodel, worldenergydata, assethold`). `config/agents/hermes/config.yaml.template:40-45` declares 6 external_dirs (adds `workspace-hub, CAD-DEVELOPMENTS, achantas-data`, drops `assethold`). `config/workstations/registry.yaml` line 27-33 declares 6 repos for dev-primary (`worldenergydata, digitalmodel, assetutilities, assethold, workspace-hub, OGManufacturing`). The plan cites the first two surfaces in §Sources but the proposed registry will become a *fourth* repo list rather than reconciling them. No "supersedes" or "deprecates" statement appears anywhere.

5. **Top-level `workspace-hub/AGENTS.md` — the canonical workflow contract per `SHARED_SOUL.md:6` — is absent from the authority taxonomy.** AGENTS.md exists at repo root and `SHARED_SOUL.md` line 6 calls it the *"Canonical workflow contract."* The plan's class table (lines 75-85) lists `canonical-repo-source` with examples `SHARED_SOUL.md`, provider deltas, scripts, docs — but never names AGENTS.md or its provider-specific siblings (CLAUDE.md, GEMINI.md, the codex `AGENTS.runtime.md` symlink target). A folder-authority contract that omits the load-bearing workflow file is incomplete.

6. **§Scope "read-only validation" conflicts with §Pseudocode and §Tests that require content inspection of user-home secret files.** §Scope line 59: *"Add validation that is read-only except for test fixtures and documented outputs."* But `check_authority_rules` (lines 174-188) verifies "generated header" and "build script reference" — content reads. Tests `test_registry_rejects_secret_like_values`, `test_local_runtime_symlink_target_matches_machine_root`, and `test_report_redacts_home_auth_and_token_paths` (lines 220, 224, 230) imply reading `~/.hermes/.env`, `~/.codex/auth.json`, or scanning for token-like content. The plan must distinguish "doesn't mutate filesystem" from "doesn't read secret files" and explicitly forbid the latter, per `feedback_skill_content_scanner_docs_tension` in your memory (skill scanners trip on `~/.hermes/.env`, `curl ${TOKEN}`).

7. **Cited line ranges paper over precision.** `scripts/agents/build-soul-runtime.sh:1-61` is the entire 61-line file (`wc -l`). `install-soul-runtime.sh:1-87` is the entire 87-line file. `emit-machine-status.sh:1-26` is the entire 26-line file. Citing `1-N` adds no precision over citing the file. Replace with specific function/section line ranges or drop the range.

8. **Schema example shows `users.vamsee.provider_runtime: enabled` but neither the validator nor the field enumeration mentions `provider_runtime`.** Lines 99-103 introduce a `users:` block with `provider_runtime: enabled` — but the per-repo schema field list (lines 115-124) and the validator pseudocode (lines 174-188) never refer to it. The multi-user prose section (§3, lines 127-134) doesn't wire it to anything either. Dead field, or unspecified semantics.

9. **`inspect_current_machine` pseudocode is incoherent with the proposed schema.** Line 163: *"resolve machine entry by explicit flag or hostname aliases"*. But the plan's example registry (lines 93-111) keys machines by hostname-string, not by an alias-resolving structure. The existing `config/workstations/registry.yaml` *does* have `hostname:` + `hostname_aliases:` fields for resolution — another sign the plan should be extending the existing file rather than inventing a new one.

10. **Acceptance criterion #11 ("Plan-stage adversarial review will complete before `status:plan-review` is applied") is a workflow precondition, not a falsifiable acceptance criterion.** Line 245. This belongs in §Status / Gate, not in the test/acceptance list. Trims to padding.

11. **Plan promises report-only vs enforcement modes but specifies no mode flag.** Risk-mitigation row (line 259): *"First implementation will support report-only mode and enforcement mode separately."* §Files to Change names a single script `scripts/validation/check-agent-runtime-authority.sh`. §Pseudocode `emit_report` mentions "enforcement mode" but no flag or env-var contract. Either spec the flag (`--enforce`/`--report-only` plus exit-code semantics) or remove the promise.

12. **`config/machine-baselines/README.md` references `config/agents/machines.yaml`** (per its line 17: *"If `config/agents/machines.yaml` contains `aliases: { <hostname>: <alias> }`, use the alias"*). This is a fourth potential machines-config path adjacent to `config/workstations/registry.yaml`, `scripts/readiness/harness-config.yaml.workstations`, and the proposed `config/workstations/repo-placement.yaml`. The plan must reconcile the alias-resolution surface, or the validator's hostname-alias resolution will diverge from the #2751 baseline emitter's resolution.

## Blockers

1. Reconcile with `config/workstations/registry.yaml`. Either (a) extend that file with the new fields and drop the proposed `repo-placement.yaml`, (b) explicitly deprecate `registry.yaml` with a migration path and update its callers (`scripts/cron/setup-cron.sh`, `scripts/operations/workstation-status.sh`), or (c) document why two registries in the same directory are not duplicate authority. Until this is resolved, the plan creates exactly the failure mode it claims to prevent.

2. Reconcile with the existing `.claude/skills/workspace-hub/repo-structure/references/agent-runtime-authority-map.md`. Either roll the existing 5-class taxonomy into the new doc verbatim and migrate the skill to point at it, or justify why two divergent authority taxonomies (5-class skill vs 9-class doc) are intended.

3. Add `AGENTS.md` and provider-specific workflow files (`CLAUDE.md`, `GEMINI.md`, codex `AGENTS.runtime.md`) to the authority class examples in lines 75-85, or explicitly mark them out-of-scope with a reason.

4. Reconcile the 3–4 competing repo lists (`harness-config.tier1_repos`, `hermes/config.yaml.template.skills.external_dirs`, `registry.yaml.machines.<m>.repos`, `machine-baselines/README → machines.yaml`) by naming the canonical list and the derived/supersedure relationship for each.

5. Disambiguate "read-only" in §Scope: explicitly forbid the validator from reading inside `~/.hermes/.env`, `~/.codex/auth.json`, and any path classified `local-secret-auth`. Use path-class allowlists, not content scans.

6. Replace blanket `:1-N` whole-file citations with function/section-scoped ranges; cite `config/workstations/registry.yaml` and the existing authority-map skill explicitly in §Sources.
