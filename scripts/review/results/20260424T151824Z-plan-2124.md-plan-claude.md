### Verdict: MAJOR

### Summary
Plan is well-scoped and evidence-backed, with strong TDD coverage and appropriate security focus on ZIP extraction. However, two material concerns need addressing before implementation: (1) a Python-import contradiction — the plan proposes `from ingest_orcina import ...` but the source file is `ingest-orcina.py` (hyphen, not underscore), which is not a valid Python module name and will fail at import; (2) ZIP size protection covers compressed size (Content-Length ≤ 50 MB) but the pseudocode and test list do not enforce a decompressed-size cap, leaving a zip-bomb vector even though risks section mentions the mitigation.

### Issues Found
- [P1] Import path is broken: pseudocode says `from ingest_orcina import html_to_markdown, fetch_page`, but Files-to-Change lists the source as `scripts/data/llm-wiki/ingest-orcina.py` (hyphen). Hyphenated filenames are not valid Python module identifiers and the import will raise `SyntaxError`/`ModuleNotFoundError`. Either rename the existing file to `ingest_orcina.py` (breaking change — callers must be checked), or use `importlib.util.spec_from_file_location` to load it, or duplicate the helpers into the new script. Plan must specify which path and record the breaking-change scope.
- [P1] Zip-bomb exposure: `download_and_extract_zip` only pre-checks HTTP `Content-Length` (compressed ceiling). Risks section mentions a `hard cap on total extracted bytes`, but the pseudocode doesn't implement it and the TDD list has no `test_training_zip_extract_rejects_decompression_bomb`. A 50 MB ZIP can decompress to gigabytes. Add an explicit cumulative-decompressed-bytes check inside the extraction loop and a matching fixture test.
- [P2] Content-Length is advisory: servers can omit or misreport `Content-Length`. `test_training_zip_size_guard` only asserts behavior when the header is present and large. Plan should also specify streamed-read size enforcement during download (accumulate bytes, abort past the 50 MB ceiling) and test the header-missing path.
- [P2] Pagination not addressed for release-notes and news crawlers. `parse_release_notes` and `crawl_news_feed` fetch a single index and iterate its links, but Orcina's `/releases/` and `/news/` indexes likely paginate. Without an explicit pagination loop and a fixture test, ingestion silently truncates to page 1. Spec the pagination strategy (follow next-page links, cap depth) and add a fixture.
- [P2] Master-index merge contract unverified: plan asserts the merged master gains an `orcina.extended` key alongside `orcaflex`, but the Resource Intelligence does not show the actual existing `index.json` shape/top-level schema. Test `test_master_index_merge_extended` uses a hypothetical `orcaflex` key. Verify against the real index produced by `ingest-orcina.py` before coding, or the merge may collide with or shadow existing keys.
- [P2] No polite-scraping policy: plan crawls ~54 example pages, an unknown number of release pages, and all news posts, but specifies no robots.txt check, User-Agent string with contact info, or inter-request delay. Orcina could rate-limit or block the crawler. Add explicit User-Agent, `robots.txt` consultation, and a minimum inter-request sleep (e.g., 1s).
- [P3] Review artifacts are TBD. Adversarial Review Summary rows and `Overall result` are placeholders. Per the user's planning workflow (`status:plan-review` → user approves → `status:plan-approved`), the plan cannot move forward until Claude, Codex, and Gemini verdicts are captured. Note this is a workflow gate, not a content defect — but it blocks implementation.
- [P3] Examples smoke-test threshold (`≥ 20`) is arbitrary and weakly tied to the claim of 54 examples. If the enumerator silently miscounts (e.g., picks up only a sidebar), 20+ can pass while the catalog is half-captured. Consider a tighter bound (`≥ 40`) plus a log-summary assertion, or sanity-check the count against a fixture-derived expected minimum.
- [P3] Concurrent-run race on `data/llm-wiki/index.json`: the user's workflow explicitly runs parallel agents, and the merged master index is shared state. No lockfile, atomic-rename, or single-writer convention is specified. Add `tempfile + os.replace` atomic write at minimum, and document whether concurrent ingesters are supported.
- [P3] ZIP content-type not validated: if the training-bundle URL redirects to HTML (maintenance page, WAF challenge), downloader will write HTML to a `.zip` and `zipfile.ZipFile` will raise a bare `BadZipFile`. Validate `Content-Type` includes `application/zip` (or probe magic bytes) and surface a clear error.
- [P3] Heading-text fragility in release-notes parser: extracting version sections by matching literal `What's new` / `Bug fixes` strings breaks silently if Orcina renames to `New features` / `Fixes`. Plan flags fragility broadly but doesn't specify fallback behavior or a test that asserts graceful degradation (write the full page, emit WARN) when expected headings are absent.

### Suggestions
- Resolve the import question up front by extracting shared helpers (`html_to_markdown`, `fetch_page`) into a module with a legal Python name — e.g., `scripts/data/llm-wiki/orcina_common.py` — and have both `ingest-orcina.py` (via importlib or a tiny shim) and the new extended ingester import from it. This also prepares cleanly for #2103's `llm_wiki_common.py` landing.
- Add a concrete decompressed-size ceiling constant (e.g., `MAX_EXTRACTED_BYTES = 200 * 1024 * 1024`), accumulate `ZipInfo.file_size` pre-extract plus running total mid-extract, abort with `ValueError` on overflow, and add `test_training_zip_extract_rejects_decompression_bomb` using a fixture whose per-member `file_size` is inflated.
- Spec a `respect_robots()` helper that consults `urllib.robotparser` against Orcina once per run, and a `POLITE_DELAY_SECONDS = 1.0` applied between each HTTP fetch. Include a `USER_AGENT` constant identifying the crawler and a contact email.
- Before finalizing the master-index schema change, run `ingest-orcina.py` once and paste the top-level keys of the produced `index.json` into the Resource Intelligence section, then base the merge test on the real shape.
- For pagination, add `iter_paginated(index_url, max_pages=N)` and drive both release and news crawls through it; add one fixture with `rel='next'` and assert two pages are fetched.
- Either populate the three review verdicts or explicitly mark the plan as not ready for `status:plan-review` handoff. The workflow rule forbids self-approval, so leaving TBD until reviews land is correct — but the handoff itself should be deferred.
- Consider adding a category-independent `--dry-run` flag that crawls without writing, for CI smoke-checks that don't want to pollute disk.
- Document the breaking-change blast radius if `ingest-orcina.py` is renamed: grep for `ingest-orcina.py` across the repo (CI, cron, docs, other plans) and list callers in Risks.

### Questions for Author
- Is there a reason to keep the hyphenated filename `ingest-orcina.py`? If yes, does the new script use `importlib` to load helpers, or does it duplicate them? The plan should commit to one path.
- What is the expected decompressed-size ceiling for the training bundle, and should extraction abort hard or extract-then-truncate when a single member exceeds it?
- Does Orcina's robots.txt permit crawling `/resources/`, `/releases/`, `/news/`, and the 54 example sub-pages? If not, how should the ingester behave — skip-with-WARN, or fail-fast?
- Should the ingester's output be reproducible (same corpus → same index.json) across runs, or is crawl-order-dependent ordering acceptable? This affects whether `index.json` writes need sorted keys.
- Is the `orcina.extended` master-index key nested under an existing `orcina` object, or sibling to `orcaflex`? Test fixture suggests sibling, but the dotted name implies nesting — which is it?
- For news ingestion, do you want a default date cutoff (e.g., last 5 years) to keep the corpus bounded, or explicit ingest-all with a documented growth-review trigger?
- Should the training ZIP be preserved on disk for audit (reproducibility of source-of-record), or is the per-file markdown conversion sufficient given the upstream URL is captured in each file's source header?
