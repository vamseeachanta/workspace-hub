### Verdict: MAJOR

### Summary
The plan establishes a solid architectural approach to resolving identity ambiguity and avoiding false gaps, but contains critical defects regarding report distribution from the scheduled task and an asymmetric normalization bug that will cause the exact false gaps it aims to prevent.

### Issues Found
- **Stranded Reports in Scheduled Task**: The cron command in `Scheduled Task Contract` executes the script, which writes YAML and Markdown files to `docs/reports/wiki-coverage-gaps/`. However, the command lacks any step to stage, commit, and push these changes. As a result, the reports will sit as unstaged files on the local worker node (`dev-primary` or `ace-linux-1`) and will not be visible to the team.
- **Asymmetric Normalization Causes False Gaps**: Section 'Mixed-state behavior' specifies that source-side bare hex values are normalized to `sha256:<hex>` to prevent false gaps. However, the pseudocode comment (`# sha256 only; bare hex stays warning-only`) and the 'L3 Coverage Boundary' rule ('include pages with a conforming doc_key') indicate that wiki pages with bare hex keys are treated as non-conforming and are NOT normalized into the wiki index. This means normalized source records will fail to match wiki pages with bare hex keys, generating false gaps.
- **Unexpanded Glob in Inputs Array**: The `optional_inputs` list in the pseudocode contains the string `"data/document-index/promotions/*.yaml"`. Unless `load_optional_inputs` is specifically implemented to expand globs for mixed lists of literals and patterns, standard file-existence checks will treat this as a literal filename and silently skip all promotion manifests.

### Suggestions
- Update the scheduled task command to include a `git add docs/reports/wiki-coverage-gaps/` and `git commit` / `git push` sequence, or explicitly document an alternative artifact distribution mechanism.
- Ensure the wiki-side parsing logic (`normalize_wiki_doc_key_for_coverage`) normalizes bare hex values to `sha256:<hex>` for the join index (mirroring the source-side logic) while still emitting a `wiki-schema-warning`.
- Explicitly handle glob expansion when parsing `optional_inputs` in the implementation.

### Questions for Author
- The plan states 'The detector reads only git-tracked metadata', but relies on `data/document-index/index.jsonl` as its primary required input. Is `index.jsonl` actually committed to source control, or is it a generated artifact that requires the scheduled task to run an indexing build step first?
- If the scheduled task is intentionally not committing the generated reports to the repository, what mechanism is responsible for distributing them to the team?
