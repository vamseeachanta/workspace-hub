### Verdict: MAJOR

### Summary
The v2 plan substantively addresses r1 feedback (helper extraction, decompression-bomb caps, pagination, robots.txt policy, attested-evidence block) and the TDD list is thorough. However, the same root-cause defect v2 diagnosed for v1 — hyphenated filenames breaking Python imports — recurs in the newly-created `ingest-orcina-extended.py` and its companion test module, and the `CATEGORIES` dict in the pseudocode would execute crawlers at import time, bypassing the robots.txt gate. These are structural blockers that merit a fix before approval.

### Issues Found
- [P1] Hyphenated filename recurrence: `ingest-orcina-extended.py` cannot be `import`ed by `test_ingest_orcina_extended.py` for the same reason v2 fixed for v1 (the rejected `from ingest_orcina import ...`). The plan doesn't say how tests reach the code — either rename the new script to `ingest_orcina_extended.py` (underscore), or move testable logic into a legally-named module (e.g., `orcina_extended.py`) with the hyphenated file being a thin CLI shim.
- [P1] Pseudocode `CATEGORIES = {...}` eagerly invokes `crawl_resources_sub_pages(...)`, `enumerate_examples(...)`, `download_and_extract_zip(...)`, etc. at module top level. Taken literally, this would (a) crawl Orcina at import time, (b) bypass the `respect_robots` gate that runs inside `ingest_extended`, and (c) defeat tests that monkeypatch `fetch_page` after import. Must be a lazy mapping (category → callable) or constructed inside `ingest_extended`.
- [P2] The extraction list includes `_convert_element` and `_convert_table`, but the Attested Evidence block only verifies `html_to_markdown` at line 98 and `fetch_page` at line 286. The existence and exact names of the private converter helpers are unattested — if they don't exist or are spelled differently, Build Sequence step 1 fails silently.
- [P2] `BeautifulSoup` is introduced as a new external dependency (used in `iter_paginated`, `parse_release_notes`, `crawl_news_feed`, `enumerate_examples`) but not declared in Files to Change or in any dependency manifest update. Existing `ingest-orcina.py` reportedly uses stdlib `html.parser`; this adds `bs4` without calling it out.
- [P2] Monkeypatch-target ambiguity for `fetch_page`. `ingest-orcina-extended.py` does `from orcina_common import fetch_page`, which binds a local name. Tests that monkeypatch `orcina_common.fetch_page` will not affect the imported binding unless the test targets the consuming module's namespace. The plan says only 'monkeypatch of fetch_page' without specifying target — a common source of silently-passing tests that actually hit the network.
- [P2] No cross-page de-duplication in `parse_release_notes`. Each paginated index page is parsed for `/releases/` links independently; if the same version appears on multiple pages (common on CMS archives), it gets re-fetched and the output file gets overwritten, wasting polite-delay budget and potentially tripping rate-limit heuristics.
- [P3] Idempotency/rerun policy undefined. Master-index merge is additive on the `extended` key, but individual markdown files under `orcina/extended/**` are silently overwritten each run, and there's no 'skip if already fetched' path. Worth stating explicitly.
- [P3] `crawl_resources_sub_pages` is referenced in the CATEGORIES dict and in Build Sequence step 10, but no pseudocode signature or behavior is shown — its fan-out, stop conditions, and polite-delay behavior are unspecified.
- [P3] robots.txt token handling: `rp.can_fetch(USER_AGENT, ...)` passes the full UA string including the contact-email segment. Some robots parsers match on the first whitespace-delimited token; consider passing only `workspace-hub-llm-wiki` to avoid over-strict disallow.

### Suggestions
- Rename the new script to `ingest_orcina_extended.py` (underscore) so tests can `import` it directly. This is the same fix v2 chose for the v1 `from ingest_orcina import ...` problem — apply it consistently.
- Declare the `beautifulsoup4` dependency explicitly in the Files to Change table (and whatever uv/pip manifest applies), or rewrite pagination/link extraction against `html.parser` to avoid introducing a new dep.
- Add a fixture `tests/fixtures/orcina_robots.txt` and a test that exercises the specific UA-token match path, so future UA changes don't silently change allow/disallow decisions.
- Add an acceptance criterion for idempotency: a second immediate rerun with the same output dir produces zero new HTTP fetches beyond the robots.txt consultation (implement via an on-disk content-hash side table, or explicitly state 'always re-fetch' as the policy).
- Promote the `--dry-run` flag out of the deferred list — it makes CI schema-regression checks nearly free and would directly cover the `test_master_index_merge_extended_real_shape` acceptance path in a live (non-mocked) context.
- Specify in the test plan which module the monkeypatch targets (e.g., `monkeypatch.setattr('ingest_orcina_extended.fetch_page', ...)`) so tests don't accidentally hit the live network.

### Questions for Author
- How do tests import `ingest-orcina-extended.py` given the hyphenated filename? If via `importlib.util.spec_from_file_location`, doesn't that reintroduce exactly the dynamic-load friction Option B was rejected for?
- Are `_convert_element` and `_convert_table` actually defined in `ingest-orcina.py` at HEAD, and do they have those exact names? If not, what's the fallback plan for the helper extraction?
- Is `beautifulsoup4` already a declared dependency of workspace-hub or the llm-wiki subproject? If adding a new dep, does it need separate approval under the project's dependency-governance policy?
- On rerun, should already-fetched pages be skipped (incremental) or re-fetched and overwritten (idempotent)? This affects both polite-scraping etiquette and what 'second run exits 0' means as an acceptance check.
- Should the atomic master-index merge take a process-level advisory lock (e.g., `fcntl.flock`) when there's any chance `ingest-orcina.py` and `ingest-orcina-extended.py` run concurrently, or is the 'single-writer convention' enforced elsewhere (lockfile, queue)?
- For the news feed, is there a date cutoff or retention policy you want baked into the plan before merge, or is 'ingest-all, revisit later' the intended ship condition?
