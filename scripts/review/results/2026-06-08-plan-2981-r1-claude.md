`★ Insight ─────────────────────────────────────`
The sharpest defects in CI-gate plans are rarely in the logic being added — they're in the **execution environment** the gate runs in. A validator that parses YAML perfectly is worthless if the CI job that invokes it has no YAML library and no `uv`. Always trace the new dependency all the way to the runner that must satisfy it.

## Findings

1. **MAJOR — The new YAML dependency has no execution path in CI; `skills-validation.yml` adds no Python/uv/PyYAML setup.** The plan's deliverable is "a test-covered validator path that YAML-parses" running through `.github/workflows/skills-validation.yml`, but that job is only `actions/checkout@v4` + `run: bash scripts/skills/validate-skills.sh` — no `setup-python`, no `setup-uv` (verified by `grep`). Sibling enforcement workflows (`enforcement-gate.yml`) explicitly add `actions/setup-python@v5` + `astral-sh/setup-uv@v4` first. If the upgraded validator calls `uv run --with pyyaml` (as the plan's own test guidance suggests, plan line 228), `uv` is absent in this job and the step errors. If it calls bare `python3 -c "import yaml"`, it relies on the ubuntu runner's system Python silently shipping PyYAML — an undocumented, unstated assumption (the local `yaml 6.0.3` proves nothing about the runner). The "Files to Change" table lists the workflow only under **"Consider"** for the `continue-on-error` toggle and never mentions adding a setup step. This is the load-bearing gap.

2. **MAJOR (compounding) — Removing `continue-on-error: true` while finding #1 is unresolved produces a hard-red CI.** The plan's Risks/Open recommendation (lines 289) is to remove the soft-fail "immediately after the validator passes live inventory." Combined with finding #1, removing the safety net before the runner can satisfy the new dependency converts a silent no-op into a blocking CI failure on an unrelated cause (missing interpreter/lib, not a malformed skill). Sequence and dependency must be pinned before this toggle flips.

3. **MEDIUM — 3111 files under a 10-minute CI timeout: the plan never pins single-process parsing.** `skills-validation.yml` sets `timeout-minutes: 10`. The pseudocode (lines 216-223) says "for each SKILL.md under root: parse extracted frontmatter with yaml.safe_load" without specifying that all files are parsed in **one** Python process. A per-file shell-out — especially `uv run --with pyyaml` per file (3111 dependency-resolution startups) — would blow the timeout. The implementation must iterate the whole tree inside a single interpreter invocation; the plan should state this as a constraint, not leave it to implementer discretion.

4. **MEDIUM — Two divergent frontmatter-extraction methods in the plan's own evidence; none is pinned, and none is tied to the real consumer's parser.** The live-inventory probe (lines 126-131) uses `text.find('\n---', 4)` + `text[4:end]`; the reproduction probe (line 156) uses `text.split('---', 2)[1]`; the existing bash uses `awk` matching `^---[[:space:]]*$`. These differ on edge cases (no trailing newline, `---` inside the body, trailing chars after `---`). More importantly, the validator's verdict is only meaningful if it mirrors what Claude Code's / Codex's skill loader actually does — the plan asserts "Strict YAML parsers reject this file" (line 17) but never identifies the parser the real consumers use. Pin one canonical extraction and justify that it matches the loader, or the gate can diverge (false-pass or false-fail) from real load behavior.

5. **MINOR — The new regression test has no demonstrated CI wiring.** `skills-validation.yml` triggers only on `scripts/skills/*.sh` and `.claude/skills/**/SKILL.md` (not `*.py`, not `tests/**`). The plan adds `tests/enforcement/test_validate_skills_frontmatter.py` and all RED/GREEN acceptance criteria run it via local `uv run pytest`, but nothing in the plan shows which CI workflow collects `tests/enforcement/`. If the intent is durable enforcement (not a one-time local check), the plan should name the CI path that runs the new test, or add it.

6. **MINOR — The workflow's soft-fail justification comment is already factually false and the plan doesn't flag its removal.** Lines 90-92 of the workflow claim files under `_diverged/` and `_internal/` "do not yet have YAML frontmatter," justifying soft-fail. The live inventory proved `missing_frontmatter=0` (and my strict re-run found 0 missing). When the plan edits this file it must delete this stale false comment, not just toggle the flag — otherwise a disproven justification persists in-tree.
