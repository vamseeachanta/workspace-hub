## New v3 findings

### V1 — LOW / observational (non-blocking): `_parse_owner_overrides_from_tos_review()` semantics are underspecified

The override mechanism is the load-bearing reconciliation between Q11 (KEEP LinkedIn) and U1 (robots.txt enforcement). Plan line 193 says:

> `_OWNER_OVERRIDE_SOURCES: set[str] = _parse_owner_overrides_from_tos_review()`

…parsed at import time. But the plan never specifies the parse grammar. Questions the plan leaves open:

- What exact marker does the parser grep for? `"Owner override:"`? `## Source: <name>` header plus `Owner override` block? A fenced code block?
- What if a source section is commented-out / behind an HTML comment? Does that count?
- What if the doc has a typo (e.g. `linkedin` vs `LinkedIn`)? Is the match case-insensitive? Is the source name normalised?
- The test `test_linkedin_override_parser_round_trips` (line 245) asserts "returns `{"linkedin"}` iff override block present" — but "present" is not mechanically defined.

**Why this matters:** if the parser is loose, a stray mention of "Owner override" in prose (e.g. in a historical note or a removed-sources appendix) could silently enable override for a source that wasn't meant to have one. If it's too strict, a trivial formatting drift revokes an override the owner intended to keep.

**Recommendation (non-blocking — can be resolved at implementation time):** Before Commit 2 lands, the plan should add a micro-spec for the parser: "one source = one H2 header of form `## Source: <name>`; override is active iff that section contains a line matching regex `^Owner override:` AND a line matching `^Owner approved: \d{4}-\d{2}-\d{2}` within the same section." Or similar. This is a clarification, not a plan revision — noting for the implementing session.

### V2 — LOW / observational (non-blocking): LinkedIn ToS-update-post-acceptance is not addressed

The reviewer prompt asked specifically: "does plan include what happens when LinkedIn ToS updates post-acceptance?" Plan v3 does NOT have an explicit answer.

What the plan does have:

- Line 338: "Risk: `TOS_REVIEW.md` is a compliance record, not a legal opinion. Mitigation: owner sign-off is explicit" — acknowledges the record is static.
- Line 333 R3: "if override becomes untenable, does a separate issue track API procurement? Not opened automatically in v3" — open question on the escalation side, but not on the detection side.

Missing: a process for **detecting** that LinkedIn's ToS or robots.txt changed after owner sign-off. The override is a committed doc block with a date — nothing in the plan re-validates that ToS content 6 months later. If LinkedIn tightens its ToS post-acceptance, the owner-override becomes stale silently.

**Why this matters:** the whole compliance-posture argument (fail-closed default, public repo, forged UA) implies ongoing compliance, not point-in-time. A sign-off dated 2026-04-20 tells us the owner evaluated the risk *on that date* but not that the acceptance is still valid six Mondays later.

**Recommendation (non-blocking, can be a follow-up issue):** add one line to §Residual Open Questions — "R4: ToS re-validation cadence for signed sources — unspecified; consider a quarterly re-check reminder or a robots.txt drift-detection step (if cached robots.txt content changes, flag for owner re-review)." This is a genuine gap but does not block approval of v3 because:
  1. The override is revocable via single PR (owner can revoke at any time when they notice drift).
  2. Fail-closed default means that if LinkedIn tightens robots.txt, the scanner auto-DENIES until owner explicitly re-signs.
  3. This is arguably out of scope for #1707's baseline fix; it's a governance-cadence question better tracked as a separate issue.
