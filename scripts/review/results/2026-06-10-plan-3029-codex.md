### Verdict: MAJOR

### Summary
The plan is not approval-ready. The proposed precedence and `provider_explicit` semantics change existing dispatch behavior and the planned tests do not cover the dangerous paths.

### Issues Found
- MAJOR: `lane:` over `rule` breaks an existing specific routing rule. Plan Step 1/2 says precedence is `ai:` > `lane:` > rule > default, and Step 4 would classify “orchestration/review/light” as `lane:claude`. But `.claude/memory/kanban/routing-rules.yaml:89-92` explicitly routes `needs:cross-review` to `codex` because “Codex strong on adversarial cross-review.” A card with `needs:cross-review` plus `lane:claude` would match the codex rule, then be overridden by lane. That is a behavior change against an existing routing intent, not just a new default signal.
- MAJOR: The plan’s `provider_explicit = bool(existing_ai or accepted_lane or assign.get("provider"))` changes `--apply` label writes despite claiming “No change to `--apply` write behavior.” In `scripts/dispatch/route.py:356-373`, `labels_for()` writes `ai:<provider>` whenever `p["provider_explicit"]` is true; the current code defines provider explicit as only human/rule choice at `scripts/dispatch/route.py:155-157`. Treating lane as explicit would cause lane-only cards to get sticky `ai:` labels, including `ai:claude`, and later `existing_ai` wins over changed lane at `scripts/dispatch/route.py:152-157`. This contradicts Acceptance Criteria 4 and can freeze plan-time labels into dispatch-time overrides.
- MINOR: The test plan does not pin the highest-risk precedence case. Step 1 test 5 only says “Rule-assigned provider + `lane:` present → `lane:` wins over rule”; it does not test the live `needs:cross-review -> codex` rule from `.claude/memory/kanban/routing-rules.yaml:89-92` against `lane:claude`. Without that fixture, the suite can pass while silently inverting the one provider rule that currently exists.
- MINOR: The test plan does not cover the downstream `provider_explicit` consumer. The only downstream use I found is label writing in `scripts/dispatch/route.py:372`; `apply_wip()` uses `provider` for auto-routable/capacity at `scripts/dispatch/route.py:210-223`, not `provider_explicit`. Tests need to assert whether lane-derived provider selection should or should not make `labels_for()` emit `ai:` labels.

### Suggestions
- Decide whether `lane:` is a default preference or a hard issue-level override. If it is a default preference, use `ai:` > rule provider > lane > default, or make specific rules like `needs:cross-review` override lane.
- Split provider selection from label-write explicitness. For example, return `provider_source` (`ai`, `lane`, `rule`, `default`) and let `labels_for()` write `ai:` only for the intended sources.
- Add tests for `needs:cross-review + lane:claude`, `lane:claude` with no `ai:` through `labels_for()`, no-lane behavior, and unknown lane fallback.

### Questions for Author
- Should `lane:claude` intentionally override the existing `needs:cross-review -> codex` rule, or should that rule remain stronger than lane?
- Should `--apply` convert lane-derived routing into persistent `ai:` labels, or should lane remain a separate non-sticky planning signal?
