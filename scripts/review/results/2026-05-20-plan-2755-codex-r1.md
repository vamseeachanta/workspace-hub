### Verdict: MAJOR

### Summary
The plan is not approval-ready. It mostly blocks repo mutation and correctly treats `/mnt/remote/ace-linux-1/ace` as data input, but it under-gates missing provider/runtime PATH findings and cites repo-placement alternatives that are not supported by the cited registry/baseline files.

### Issues Found
- Runtime blockers are scoped too narrowly. Resource Intel says `claude`, `codex`, `gemini`, and `hermes` were missing from the non-interactive SSH PATH, but Acceptance Criteria only requires they be blockers “before provider dispatch,” and `test_runtime_probe_missing_provider_clis_blocks_provider_dispatch` only disables provider dispatch. For a Telegram/Hermes worker lane, missing `hermes` and missing provider CLIs/auth should block `dev-secondary` dispatchability until fixed or explicitly scoped out. This conflicts with `docs/ops/telegram-hermes-multimachine-control-plane.md` Minimum safe enablement path, which requires the worker to install Hermes CLI/gateway, configure env names, generate host-local readiness evidence, and pass readiness before dispatch.
- Tier-1 path policy invents unsupported placement alternatives. The plan’s `Tier-1 Repo Placement Baseline` allows `digitalmodel`, `assetutilities`, and `worldenergydata` under “registry-declared primary under `/mnt/dde/repos/...`,” but `config/workstations/registry.yaml` only declares `storage.local: /mnt/dde`, `workspace_root: /mnt/local-analysis/workspace-hub`, and repo names `digitalmodel` / `worldenergydata`; it does not declare `/mnt/dde/repos` or per-repo primary paths. The baseline inventory cites `/mnt/local-analysis/<repo>` as the preferred ace-linux-2 target. Make `/mnt/dde/repos/...` an explicit proposed registry addition with tests, or remove it from the accepted baseline.
- TDD does not cover the live SSH findings as acceptance-critical evidence. The TDD table uses fixtures for `workspace-hub` only, remote mount handling, and missing provider CLIs, but it does not require a captured live SSH probe fixture with timestamp, hostname, exact local repo discoveries, non-interactive PATH results, and `/mnt/remote/ace-linux-1/ace` classification. Acceptance Criteria says live-probe missing repos and missing provider commands must be recorded, but no test proves the readiness integration consumes that live evidence rather than hardcoded/stale fixture assumptions.
- Registry citation is plausible but stale/conflicting runtime evidence is not reconciled. `config/workstations/registry.yaml` declares `dev-secondary.capabilities.agent_clis: [claude]` and tools including `hermes`, while Resource Intel says `claude` and `hermes` are not found in non-interactive SSH PATH. The plan notes this as a risk, but Implementation Scope only says “Record provider/runtime gaps as dispatch blockers,” without requiring the registry/readiness output to distinguish declared capability from observed executable/auth readiness. That distinction is required to avoid dispatching from declarative registry state alone.

### Suggestions
- Change all dispatch gates from “provider dispatch disabled” to “host dispatchable=false” whenever required runtime, Hermes, auth, or non-interactive PATH evidence is missing for the selected lane.
- Replace the `/mnt/dde/repos/...` allowance with exact declared paths, or add a planned `tier1_baseline.required[].allowed_paths` schema to `config/workstations/registry.yaml` and tests proving arbitrary `/mnt/dde/tmp/...` and remote NFS paths fail.
- Add a captured live-probe fixture test that asserts the exact 2026-05-20 findings: only local `workspace-hub`, missing tier-1 repos, remote `/mnt/remote/ace-linux-1/ace` as data input only, and missing `claude/codex/gemini/hermes` in non-interactive PATH.
- Add an acceptance criterion requiring the issue comment/readiness artifact to show both declared registry capability and observed runtime status, with observed status winning for dispatch decisions.
