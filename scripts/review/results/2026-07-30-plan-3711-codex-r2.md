## Findings

1. **MINOR - The enforceability argument overclaims what the contents check can prove.**

   Evidence:
   - Plan D2 defines the declared-root guard as only "absolute, already-normal POSIX path" validation
     (`docs/plans/2026-07-30-issue-3711-host-independent-identity-inventory.md:270-288`).
   - Plan D4 says the checker recomputes rows from git-index bytes and compares `identities` and
     `machines` (`...md:297-301`).
   - The enforceability table says "It cannot be satisfied by a self-consistent lie" (`...md:325`).
   - I staged a fully source-consistent poison: changed `gpu-claw.workspace_root` to
     `/System/Volumes/Data/home/undi/ws/workspace-hub`, regenerated the inventory, and refreshed
     `mutation-surfaces.yaml` `source_digest`. Result: `contents_check.py` exit 0,
     `check-scheduler-mutation-surfaces.py` exit 0, with three wrong rows relative to the clean
     Linux baseline: `equality-report`, `equivalence-sentinel`, `repository-sync`.

   Failure scenario:
   A commit changes the trusted source (`config/workstations/registry.yaml`) to the macOS firmlink
   target, refreshes the inventory and `source_digest`, and passes the proposed contents check. This is
   no longer the silent artifact-only Mac bypass, but it is still a self-consistent wrong identity
   inventory relative to the real Linux machine.

   Required revision:
   Narrow the claim. State explicitly that the contents check validates inventory consistency against
   trusted index sources, not physical truth of registry roots. Preferably add a structural guard for
   the known Darwin firmlink prefix (`/System/Volumes/Data/...`) on `os: linux` rows, or record why
   registry-source truth is intentionally left to code review. This does not block the plan's main fix.

2. **MINOR - The `tests/cron` baseline did not reproduce at the stated base commit.**

   Evidence:
   - Plan records `[ace1] uv run pytest tests/cron -q -> 1 failed, 283 passed`
     (`...md:575`, `...md:641-642`; verification log lines 257-259).
   - On current ace1 `main` (`05da65cc`), I measured `284 passed in 33.27s`.
   - In a temporary ace1 clone checked out to the plan base `3fe934da9`, I also measured
     `284 passed in 29.45s`.
   - The other two baseline suites matched the plan: `scripts/cron/tests` was
     `1 failed, 65 passed` on `test_validate_schedule.py::test_windows_tasks_have_windows_scheduler`;
     `tests/enforcement` was `2 failed, 417 passed` on
     `test_check_skill_index_coherence.py::test_real_repo_passes` and
     `test_soul_auto_load.py::test_drift_script_returns_zero_in_clean_state`.

   Failure scenario:
   The acceptance criterion could whitelist a new `tests/cron` failure as "pre-existing" even though I
   could not reproduce that failure on either current ace1 `main` or the stated plan base.

   Required revision:
   Update the baseline to `tests/cron: 284 passed` or explicitly mark
   `test_signal_keeps_lock_until_child_exits` as a flaky/non-reproduced historical failure that must
   not be allowed to hide a new regression.

   refreshing `source_digest`; see Finding 1. That is a source-truth boundary, not a failure of the
   artifact-consistency check.

4. **Fake resolver: acceptable.**

   The fake maps `/home/X` to `/System/Volumes/Data/home/X`, matching the measured Mac behaviour for
   `gpu-claw`. It produced exactly the three poisoned rows on both hosts and none under the proposed
   lexical render. This is not merely a test of the mock because the Mac run independently measured
   the same three rows without the fake.

5. **Second host dependency: verified.**

   `expanduser()` on `cron_render.py:87` is a separate defect. `~/ws/workspace-hub` expands to the
   running user on both hosts, and `~undi/ws/workspace-hub` raises uncaught `RuntimeError`. The proposed
   absolute-normal POSIX guard closes both by rejecting roots that do not start with `/`.

6. **Lexical normalisation: no blocking consumer found.**

   `workspace_hub_path` has only its definition and one internal use in `build_context`. The consumer
   joins paths and stringifies; no repo caller relies on symlink resolution of a declared root. The
   no-override branch still returns concrete `REPO_ROOT`. Windows-shaped `D:\...` roots were reasoned,
   not measured, but the proposed `startswith("/")` guard rejects them for `os: linux` rows, while
   Windows rows are excluded at `build-cron-identity-inventory.py:70`. I judge this gap acceptable.
