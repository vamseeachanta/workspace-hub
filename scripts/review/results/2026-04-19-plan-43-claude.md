## Findings

### Finding 1 — MINOR — Plan pseudocode for `emit_signals` contradicts its own idempotency claim
- Plan claim: "# idempotency: skip records whose (event, provider, date) tuple already appears / in any file under .claude/state/session-signals/ for the same date / write_jsonl(path, dedupe(records, against=scan_existing_signals(date)))" (Pseudocode, lines 125-127)
- Location: Pseudocode `emit_signals`, and TDD test `test_emit_signals_idempotent` ("second run with same (event,provider,date) writes nothing / file size unchanged")
- Evidence: The filename schema is per-session `{date}-{HHMMSS}.jsonl` (line 119). Because `now.strftime('%H%M%S')` always produces a new path on re-run, the SECOND run writes to a NEW empty file (0 records after dedupe). The test asserts "file size unchanged" — on a brand-new 0-byte file that's vacuously true, but it does NOT verify idempotency against the existing data. Worse, an empty file is still CREATED each run, littering `.claude/state/session-signals/` with 0-byte artifacts.
- Why it matters: Silent corruption of the signals store (many empty files) and a test that passes without verifying the property it names. Also bloats `session-analysis.sh`'s file scan.
- Suggested fix: Either (a) write to a deterministic per-day filename in this store (e.g., `{date}-compliance.jsonl`) and dedupe-append in place, or (b) in the emitter, skip writing ANY file when dedupe removes all records, and add an explicit assertion in `test_emit_signals_idempotent` that no new file was created.

### Finding 5 — MINOR — No rollback story for corrupt writes to `.claude/state/session-signals/`
- Plan claim: "Risk — log volume / log-format drift … Mitigation: treat log-format contract as a first-class output with its own tests." (Risks)
- Location: Risks section (232-236). No rollback procedure is specified anywhere in the plan.
- Evidence: The emitter writes into a store that `session-analysis.sh` auto-consumes on cron. If the first emission contains a malformed event type or a wrong `provider` value, nightly analysis reads it as fact. Plan has no "delete/quarantine" procedure, no dry-run flag, and no file-naming convention that would let you identify-and-delete just this issue's output.
- Why it matters: Writes to a live production state store (per `project_daily_readiness_cron.md`) without a revert path.
- Suggested fix: Add `--dry-run` to the emitter (defaults ON), and use a filename prefix (e.g., `43-compliance-{date}.jsonl`) so rollback is `rm .claude/state/session-signals/43-compliance-*.jsonl`. Add an acceptance bullet: "emitter supports `--dry-run`, and malformed output can be removed in one glob."

### Finding 6 — MINOR — `routing-rules.yaml` is content-free in this plan

- Location: Q2 decision; Output 3 row in Files to Change.
- Evidence: Nowhere does the plan specify the schema for this new YAML — no keys, no example block, no schema-validation test. In contrast, `routing-config.yaml` has a concrete shape (tiers, weighted dimensions). "Policy-only" tells the reader nothing.

- Suggested fix: Add a `routing-rules.yaml` schema block in the plan (at least top-level keys and one representative entry) and a new TDD test `test_routing_rules_schema` that validates the artifact against a documented JSON Schema.

### Finding 7 — MINOR — Codex sandbox write-block risk is acknowledged (via Q6) but not hedged against for THIS implementation
- Plan claim: "Q6 — Plan authored by Claude; implementation dispatched to Codex via `codex:rescue`. Codex writes the code; Claude only orchestrates and verifies the plan landed." (Design Decisions)
- Location: Q6 Design Decision; acceptance criterion "Implementation commit authored by Codex (via `codex:rescue`), not Claude, per `agent:codex` label".
- Evidence: `feedback_codex_sandbox_write_blocked.md` documents that Codex rescue subagent runs in a sandbox that blocks `apply_patch` and shell-write operations ("bwrap: loopback"), observed twice on issue #2342 (2026-04-17 and 2026-04-19). The same failure mode would block Codex from creating `scripts/session-analysis/*.py`, `tests/session-analysis/*.py`, `config/agents/routing-rules.yaml`, or modifying `behavior-contract.yaml`.
- Why it matters: The acceptance criterion "Implementation commit authored by Codex" is likely unachievable. Plan will land in a "Codex returned text but could not write" state and Claude will have to transcribe manually — contradicting the acceptance contract.
- Suggested fix: Change the acceptance criterion to "Implementation authored primarily by Codex via `codex:rescue`; manual transcription by Claude is permitted when sandbox write is blocked, and the commit message attributes Codex as the author." Or: pre-flight a sandbox-write smoke test before accepting the label.

### Finding 8 — MINOR — Emitter consumability by `session-analysis.sh` is not proven
- Plan claim: "`scripts/analysis/session-analysis.sh` ingests the new events in a dry-run against the emitted file without schema-change errors" (Acceptance Criteria bullet 8) and "consumed automatically by the nightly cron with no pipeline schema change" (Deliverable)
- Location: Acceptance criterion 8; Deliverable summary.
- Evidence: `session-analysis.sh` only filters by `select(.event == "session_end")` at line 101 (per grep). Other event types (including `stage_exit`, `codex_session` per the plan's precedent claim) are passed through to downstream jq filters whose behavior on NEW event types like `gate_compliance_score` / `provider_capability` is unverified. The TDD test `test_emit_signals_pipeline_compat` only asserts "all events parseable" — that's JSON parseability, not pipeline semantic compatibility.
- Why it matters: "Parseable JSON" ≠ "consumed correctly by the cron"; a net-new event type may silently drop out of downstream reports without an error.
- Suggested fix: Add an acceptance test that runs `session-analysis.sh --date 2026-03-15` against a fixture directory containing ONLY `gate_compliance_score` + `provider_capability` events, and verify a designated output (e.g., `ANALYSIS_DIR/2026-03-15.md`) contains a new section for the new event types. If the cron has no handler for the new types, that is itself an implementation gap this plan must cover.

### Finding 9 — MINOR — `scripts/session-analysis/` is a brand-new directory (no siblings)
- Plan claim: "Create scripts/session-analysis/parse-session-logs.py … score-gate-compliance.py … emit-session-signals.py" (Files to Change)
- Location: Files to Change rows 2-4.
- Evidence: `scripts/session-analysis/` does not currently exist. The existing canonical location is `scripts/analysis/session-analysis.sh`. Creating a new parallel directory `scripts/session-analysis/` (different name, different convention) fragments the harness.
- Why it matters: Two near-identically-named script roots (`scripts/analysis/session-analysis.sh` vs `scripts/session-analysis/*.py`) will confuse future readers and cron authors — the very kind of drift the CONTROL_PLANE_CONTRACT is meant to prevent.
- Suggested fix: Put the new Python modules under `scripts/analysis/lib/` or `scripts/analysis/session/` so they live next to their shell caller, not a sibling directory with a suggestively-different name.

## Summary
The plan is well-researched and structurally complete (pseudocode, TDD list, files-to-change, explicit Q&A log of 7 resolutions). Most high-risk claims — `session-analysis.sh` path, closed-predecessor state, MEMORY feedback file existence, `.claude/work-queue/` layout — check out. But the idempotency story for the emitter is broken by its own filename schema (Finding 1), the Q4 log-format contract does not yet produce the violation list that acceptance bullet 6 demands (Finding 2), a resource-intel claim is incorrect (Finding 3), and the Codex execution acceptance criterion is likely unachievable under the documented sandbox constraint (Finding 7). None of these rise to MAJOR because they are fixable with localized edits, but the plan should not proceed to implementation without addressing at least Findings 1, 2, 6, 7, and 8.
