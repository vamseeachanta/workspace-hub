## Findings

1. **[BLOCKER] The contract's applicability layer binds to a capability authority that does not exist, inside a roster file that competes with a declared hard rule.** Plan §Resource Intel calls `scripts/readiness/harness-config.yaml` "the live roster authority"; AC-9 enumerates roster coverage from it; pseudocode `grade_interaction_evidence` requires "explicit roster capability; never infer it from hostname"; tests `test_roster_semantics_are_explicit_and_fail_closed` and `test_applicability_is_not_inferred_from_hostname` require an "explicit authority". But (a) no GUI/headless capability field exists in `harness-config.yaml` — `gpu-claw` carries `role: linux-execution`, identical to GUI-capable `dev-secondary`, so today's roster cannot distinguish an "explicitly declared headless role" from a GUI machine; (b) `config/workstations/registry.yaml:3` declares "HARD RULE: all machine identity/capability data lives here" and already carries a distinct per-machine capability taxonomy (`role: gpu-executor`, `harness_profile.roles: [sim-worker]`). The plan never reconciles the two authorities, never names the new field/enum, and assigns its creation to no one: §Files to Change contains no roster mutation, the parent forswears modifying "equality collectors/renderers", and §Risks only says "#3567 will require an explicit roster capability" while §Documents-consulted scopes #3567 as not mutating behavior — leaving the load-bearing capability declaration unowned. The contract YAML (the parent's core deliverable) cannot specify fail-closed applicability against an authority whose surface and shape are undefined.

2. **The freshness gap and AC-13 mischaracterize the publish mechanism as a "fingerprint".** §Gaps: "No interaction-evidence freshness policy reconciles evidence timestamps with the equality report fingerprint. Excluding the observation time from all hashing could prevent refreshed HITL evidence from publishing." AC-13: "`observed_at` will affect the persisted interaction-evidence/report fingerprint so refreshed HITL evidence publishes." The actual equality publish gate is `scripts/readiness/publish-equality.sh` lines 60-61/104: a lexical `generated_at` newer-than comparison ("nothing newer than $REMOTE/$BRANCH; no commit needed") — no content hashing exists in that path. The only "fingerprint" scripts (`scripts/monitoring/equivalence-fingerprint.sh`, #3059) are a separate drift-sentinel surface the plan never cites. The requirement's substance (a refresh must publish) is sound, but the contract will encode a constraint against a mechanism that doesn't exist as described; #3567 could design to the wrong gate. Cite `publish-equality.sh:60-104` and pin the requirement to `generated_at` semantics, or explicitly specify the new fingerprint the contract expects #3567 to introduce.

3. **Template header nonconformance.** The plan header omits the `> **Project:**` line required by `docs/plans/_template-issue-plan.md` line 8 (the field is optional to *populate*, but the header line is part of the template and Rule E consumers key off it). All other header fields and `##` sections conform.

4. **The Codex CR→LF normalization claim is an unverified upstream assertion baked into the paste contract.** §Documents-consulted: "Current Codex normalizes CR to LF before composer insertion" — cited to openai/codex#17103 "and source". The issue exists and matches the paste-event/key-event split topic, but its title/body do not establish the normalization behavior, and no pinned Codex commit or version-specific source citation is given. `validate_paste_fixture` then hard-codes "normalize CR and CRLF to LF exactly as the Codex composer contract specifies". `canonicalization_version` in the fixture schema partially mitigates, but the plan should require #3566 to empirically re-verify normalization on the pinned codex-cli (0.144.5) before the contract's canonical-equality policy is treated as fact.

5. **Pre-existing review-artifact residue contradicts the PENDING table and risks being committed as evidence.** `scripts/review/results/2026-07-17-plan-3568-claude.md` and `-codex.md` already exist as 0-byte files with `.err` companions (failed dispatches: untrusted-workspace for Claude; Codex run died), and `-gemini.md` is an UNAVAILABLE stub (no non-interactive auth). The plan's §Adversarial Review Summary says PENDING ×3, which is consistent with intent but not with the tree. Zero-byte files must never be committed as review evidence; the Gemini outage means the T3 review degrades to T2 per the cross-review routing rules and that depth reduction must be disclosed at the HITL gate (the plan promises this generically but does not record the already-observed Gemini auth failure).

6. **AC-16's `check-no-abs-paths.sh` gate is vacuous for two of the three created artifacts.** The scanner's target set is `git ls-files '*.sh' '*.py'` (`check-no-abs-paths.sh:63`), so `docs/architecture/interaction-ux-parity-contract.yaml` and the HTML manual — the artifacts most likely to carry gesture-doc paths like `/home/...` — are outside its file-type scope; only the test `.py` is covered. Private-path exclusion for YAML/HTML rests solely on `legal-sanity-scan.sh --diff-only` and the contract test's own denylist; the AC should state that division of labor rather than implying scanner coverage.
