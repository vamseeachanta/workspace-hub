## Findings

### Finding 1 — MAJOR — Parser ignores fixture paths
- Plan claim: `test_parse_logs_nominal` tests "parser reads contract-compliant JSONL" using `tests/.../fixtures/claude-stage2-sample.jsonl`
- Location: Pseudocode (`parse_session_logs`) and TDD Test List
- Evidence: `function parse_session_logs(start_date, end_date, signal_roots):` iterates over hardcoded `walk([".claude/state/session-signals/", "state/session-signals/"])` instead of using the `signal_roots` parameter.
- Why it matters: The TDD test will fail because the parser ignores the passed fixture path and scans the hardcoded real directories instead.
- Suggested fix: Update the `walk()` call to use `signal_roots` instead of hardcoded paths.

### Finding 2 — MAJOR — Race condition in latest-wins emitter
- Plan claim: "Emitter: latest-wins replace-by-key. Mid-day reruns overwrite stale records."
- Location: Pseudocode (`emit_signals`)
- Evidence: The logic reads the file, filters existing records, and writes the combination (`existing = read_jsonl_if_exists(path)`). There is no file lock (`flock`) specified.
- Why it matters: If multiple pipeline jobs (e.g., for Claude and Codex) run concurrently and emit to the same date file, one process will overwrite the other's records (read-modify-write race).
- Suggested fix: Implement a file lock (e.g., `fcntl.flock`) around the read-modify-write block.

### Finding 3 — MAJOR — `next_gap_seconds` is used but never computed
- Plan claim: `user_review_adherence = (sum(1 for e in review_evts if e.next_gap_seconds >= 60) ...)`
- Location: Pseudocode (`score_provider`)
- Evidence: The `stage_exit` event shape in the Resource Intelligence Summary only contains `(wrk, stage, date, timestamp)`. The parser pseudocode does not compute inter-event gaps.
- Why it matters: The scorer will crash with an `AttributeError` when accessing `e.next_gap_seconds` on parsed events.
- Suggested fix: Add logic to the parser to sort events by timestamp and calculate `next_gap_seconds` before passing them to the scorer.

### Finding 4 — MAJOR — Fabricated `gate_bypass` attribute
- Plan claim: `if e.stage in {5, 7, 17} and e.type == "gate_bypass":`
- Location: Pseudocode (`find_hard_gate_violations`)
- Evidence: The known event corpus does not contain a `type` attribute or a `"gate_bypass"` value.
- Why it matters: The hard-gate violation detection will always return an empty list because it relies on non-existent data, leading to a false sense of compliance.
- Suggested fix: Define how a gate bypass is explicitly inferred from the existing event corpus, or add it to the `insufficient_corpus` deferred list.

### Finding 5 — MINOR — Unjustified scope reduction for `tool_skill_invocation`
- Plan claim: "tool_skill_invocation: {"status": "insufficient_corpus", "missing_events": ["skill_invoke"]}"
- Location: Pseudocode (`score_provider`)
- Evidence: The Resource Intelligence Summary states that the `session_tool_summary` event contains a `tool_calls` attribute.
- Why it matters: The plan falsely claims `tool_skill_invocation` cannot be derived without a new event, missing the opportunity to approximate it using the existing `tool_calls` metric.
- Suggested fix: Derive `tool_skill_invocation` from the existing `session_tool_summary` data instead of deferring it.

### Finding 6 — MINOR — Fixture filename lacks required date for parser
- Plan claim: "date filter works" with `tests/session-analysis/fixtures/claude-stage2-sample.jsonl`
- Location: Pseudocode (`parse_session_logs`) and Files to Change
- Evidence: The parser explicitly evaluates `date_in_name = extract_date(file.name)`. The fixture filename `claude-stage2-sample.jsonl` contains no date.
- Why it matters: `extract_date` will fail or return null, causing the fixture to be silently filtered out during tests.
- Suggested fix: Rename the fixture to include a valid date, e.g., `claude-stage2-sample-2026-03-10.jsonl`.

### Finding 7 — MINOR — `git apply` patch provenance fails on concurrent edits
- Plan claim: "Claude applies via git apply after SHA-256 verify"
- Location: Acceptance Criteria
- Evidence: Validating the SHA-256 of the patch artifact only proves the patch file itself is intact.
- Why it matters: If the target files are modified by another process between patch generation and application, `git apply` will fail due to context mismatch.
- Suggested fix: Use `git apply --3way` to handle concurrent drift, or utilize `git am`.

## Summary
The v3 plan introduces several critical functional defects in its pseudocode and test alignment. The emitter contains a read-modify-write race condition that threatens data integrity during concurrent runs. The scorer relies on uncomputed metrics (`next_gap_seconds`) and fabricated attributes (`gate_bypass`), which will cause crashes or silent failures. Furthermore, the TDD strategy is disconnected from the parser's hardcoded logic. These implementation flaws undermine the entire compliance scoring mechanism and must be fixed prior to approval.
