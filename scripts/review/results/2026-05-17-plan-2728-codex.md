## Findings
1. The plan’s retrieval is insufficient for the issue class. GitHub issue `#2728` is labeled `cat:harness`, `domain:workflow`, and `domain:infrastructure`, but `docs/plans/README.md` requires Harness/Infra plans to consult `CONTROL_PLANE_CONTRACT.md`, `config/agents/` settings, and `.claude/rules/`. The plan’s “Documents consulted” section lists only `#2728`, `#2726`, `docs/DATA_RESIDENCE_POLICY.md`, `data/document-index/mounted-source-registry.yaml`, `docs/content-pipeline/README.md`, and `docs/WORKSPACE_HUB_CAPABILITIES_SUMMARY.md`.

2. The plan does not satisfy the issue’s required inventory scope. Issue `#2728` says: “Inventory current execution entry points across tier-1 repos: scripts, packages, prompts, review runners, legal scans, report builders, content pipelines.” The plan’s Files to Change only creates three docs and one test file under `workspace-hub`; it has no inventory artifact, no tier-1 repo traversal step, and no source list for `digitalmodel`, `assetutilities`, `worldenergydata`, `llm-wiki`, `assethold`, `aceengineer-website`, or `aceengineer-strategy`.

3. The plan omits a requested deliverable from `#2728`. The issue requires a “Follow-up issue list for missing runners, registries, validators, or adapters.” The plan’s Artifact Map and Files to Change do not include a follow-up issue list, issue-tree artifact, or GitHub issue creation step.

4. The routing-matrix plan risks duplicating canonical workstation data. `config/workstations/registry.yaml` states: “HARD RULE: all machine identity/capability data lives here.” The plan proposes `docs/architecture/execution-routing-matrix.md` to “map tools/machines/providers to allowed source classes and outputs,” while `config/workstations/registry.yaml` already contains machine capabilities, repos, storage roots, and data access profiles. The plan only says `config/workstations/registry.yaml` will be “Cross-link only if needed,” so it does not require the routing matrix to derive from or explicitly defer identity/capability facts to the canonical registry.

5. The plan misses the issue acceptance criterion for regeneration commands. Issue `#2728` requires: “Required run metadata and regeneration commands are specified.” The plan’s Acceptance Criteria mention command manifests, checksums, tests, legal scan, and review artifacts, but not regeneration commands. The TDD Test List likewise has no test for regeneration command fields.

6. The TDD strategy is too weak for the core publication-safety claim. The plan’s test `test_no_execution_direct_publication` verifies “direct publish wording absent/blocked.” Absence of wording in `docs/architecture/execution-layer-contract.md` does not prove the contract forbids execution-to-public/report bypasses required by issue `#2728` Acceptance Criteria: “Execution cannot directly publish public/client-facing outputs without validation/promotion gates.”

7. The plan claims `llm-wiki/` presence was “detected via filesystem search” in the “LLM Wiki pages consulted” section, but no retrieval evidence gives the command, output, path list, or whether this came from local worktree state versus tracked GitHub state. This is not verifiable from the embedded evidence and should not be used as a factual basis for architecture decisions.
