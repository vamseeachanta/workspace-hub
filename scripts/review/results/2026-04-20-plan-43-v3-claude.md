## Findings

### Finding 1 — MAJOR — `session-analysis.sh` "conceptual patch" is semantically incoherent with the actual script
- Plan claim: "BEFORE: `jq 'select(.event == "session_end") | .signals.skill_invocations[]?'` / AFTER: `jq '(select(.event == "session_end") | .signals.skill_invocations[]?), (select(.event == "gate_compliance_score") | {event, provider, score, date}), ...'`"
- Location: Pseudocode block labelled "Pipeline handler for scripts/analysis/session-analysis.sh, near line 101"
- Evidence: Lines 96–103 of the real script wrap that jq in `while IFS= read -r skill; do skill_usage["$skill"]=$(( ... + 1 )); done`. The existing jq emits skill NAMES (plain strings); adding `{event, provider, score, date}` JSON objects makes the loop treat the JSON blob as a "skill name" and corrupt `skill_usage`. Adding new events at line 101 cannot be a jq-union inside the existing pipeline — it requires a second jq pipeline and a second downstream handler, OR an upstream filter that routes events to different consumers. The plan's pseudocode would break the skill scorer.
- Why it matters: The entire integration test (`test_pipeline_integration`) is predicated on this patch landing cleanly. If implementation follows the plan's pseudocode literally, the morning cron's skill-scoring corrupts `skill-scores.yaml` and Codex's patch either fails CI or silently regresses production behavior.
- Suggested fix: Pseudocode should add a NEW parallel jq loop below line 105 (after `N_SKILLS_SCORED=...`) that handles the new events into a separate data structure, not union them into the existing skill-invocation pipeline. The test list should include `test_existing_skill_scoring_unchanged` as a regression guard.

### Finding 2 — MAJOR — Provider inference is undefined for the actual data shape
- Plan claim: `infer_provider(file, event_attr="session_id" | path_pattern)` (pseudocode line 126) and "For each provider in {claude, codex, gemini}: EITHER `provider-assessment.md` has per-dimension scores OR `insufficient_data` sentinel" (AC)
- Location: Pseudocode `parse_session_logs`, AC zero-data disjunction
- Evidence: `session_tool_summary` fields in `.claude/state/session-signals/2026-03-15.jsonl` are `[edits, event, reads, session_id, tool_calls, ts, wrk]` — NO provider field, and `session_id` is a UUID (e.g. `1d7f1a63-b593-4976-93fc-0bc4440a43de`). `codex_session` events have `session_id` prefixed `rollout-2026-03-10T...` which is self-identifying, but `session_tool_summary` has no such marker. The "per-session timestamped JSONL" store (`2026-02-20-091148.jsonl`) has all events emitted by Claude's Stop hook (note the `hook_event_name:"Stop"` fields). No Codex or Gemini session_tool_summary data exists in either store for the window — so `log_completeness` is either Claude-only (provider==claude) or uniformly zero/insufficient for codex+gemini.
- Why it matters: If `infer_provider` can only label Claude data, then the final assessment has two providers on `insufficient_data` and one on real scores. The "EITHER…OR" AC is technically satisfied, but the Deliverable promises a cross-provider assessment that the corpus cannot actually support. The plan does not disclose this.
- Suggested fix: Add an explicit Resource-Intel row enumerating distinct `session_id` prefixes per event type and which providers each store carries data for. If the 2026-03-08..15 window only contains Claude `session_tool_summary` and Codex `codex_session` (no Gemini session data), either shrink the Deliverable to "Claude + Codex assessment" or add a per-provider `insufficient_data` row to the Deliverable (not just the AC).

### Finding 3 — MAJOR — `user_review_adherence` references a field that does not exist
- Plan claim: `user_review_adherence = (sum(1 for e in review_evts if e.next_gap_seconds >= 60) / len(review_evts)) if review_evts else None`
- Location: Pseudocode `score_provider`
- Evidence: `stage_exit` events in `state/session-signals/2026-03-*.jsonl` have exactly these keys: `date, event, stage, timestamp, wrk`. There is no `next_gap_seconds` field. Computing a 60-second gap requires joining consecutive `stage_exit` records by `(wrk, timestamp)` ordering and differencing timestamps — which the pseudocode does not describe.
- Why it matters: This is the dimension v3 claims IS derivable; if the derivation is actually more complex than stated and the field cited doesn't exist, TDD `test_score_user_review_adherence_gap` cannot be written against the plan as-is.
- Suggested fix: Replace the pseudocode with the actual derivation: `sort events by (wrk, timestamp); for each stage in {5,7,17}, compute seconds between e.timestamp and next_event.timestamp; adherence = count(gap >= 60) / count(stage ∈ {5,7,17})`. Add `test_score_user_review_adherence_computation` that asserts the sort+diff is correct.

### Finding 4 — MAJOR — `routing-rules.yaml` precedence chain is fictional
- Plan claim: "precedence `behavior-contract.yaml` > `routing-config.yaml` > this file" and the header comment `# Precedence chain (higher overrides lower)…`
- Location: Pseudocode `emit_routing_rules`, §Routing-Rules Schema, Design Decisions Q2
- Evidence: `grep -rn 'routing-rules.yaml' config/ scripts/ docs/` returns only references inside v2 plan, v3 plan, v2 review artifacts, and `docs/plans/README.md`. No runtime code, no script, no policy consumer reads `routing-rules.yaml`. With no consumer, precedence is a literal no-op: there is nothing to override anything. The behavior-contract + routing-config precedence claim is a paper declaration that cannot be enforced.
- Why it matters: A DERIVED file with no consumer is deliverable bloat — the v3 resolution to Codex F5 ("either define consumer, precedence, and ownership boundaries") said "if derived, say so and do not make humans edit it." V3 says derived, but it never names a consumer. Codex F5's second half is unsatisfied.
- Suggested fix: Either (a) add a concrete consumer to the plan (e.g. `scripts/coordination/routing/select-provider.sh` reads this file and merges atop routing-config) with a TDD test proving the merge happens, or (b) mark the file `# ADVISORY SNAPSHOT ONLY — NO RUNTIME CONSUMER` and drop the precedence-chain language entirely. Current state is the worst of both.

### Finding 5 — MAJOR — Latest-wins atomic-write is claimed but not tested for the actual crash mode
- Plan claim: AC "a rerun with changed scores REPLACES matching `(event,provider,date)` tuples and leaves others intact" and test `test_emit_atomic_write` — "crash mid-write leaves file intact | simulated interrupt | no partial JSONL; `.tmp` cleaned up"
- Location: AC, TDD Test List
- Evidence: The pseudocode says `atomic_write_jsonl(path, retained + new_records)      # tmp → fsync → rename`. `.tmp` cleanup on crash is NOT implied by tmp+rename — if the process dies between write-to-tmp and rename, the `.tmp` file is orphaned. Python's `os.replace` is atomic on POSIX, but the plan's pseudocode calls `atomic_write_jsonl(path, retained + new_records)` with no mention of wrapping in a `try/finally: unlink(tmp)` for the crash path. The test "crash mid-write… .tmp cleaned up" can only pass with a cleanup-on-startup routine (not tmp-and-rename), which is not specified.
- Why it matters: The test as written cannot be satisfied by the pseudocode as written — implementation will either (a) fail the test or (b) silently diverge from the plan. Either way the latest-wins semantic is not actually proven.
- Suggested fix: Either drop the "`.tmp` cleaned up" assertion (tmp+rename is atomic for the committed-file guarantee; orphan cleanup is a separate concern) and rename the test to `test_emit_atomic_no_partial_committed_file`, or add a startup-sweep `cleanup_orphan_tmp_files()` function to the pseudocode and test it.

### Finding 6 — MINOR — Reopen-comment-reclose may be over-correction for `gh issue comment`
- Plan claim: "GitHub reopen→comment→reclose | #798, #871, #826, #950"
- Location: Files to Change, AC
- Evidence: `feedback_gh_issue_close_silent_comment_drop.md` names the bug as `gh issue close --comment "..."` (single command) silently dropping the comment when already CLOSED. Plain `gh issue comment NNN --body` on a closed issue posts normally. The plan's cross-ref step is 4 separate issues × (reopen + comment + reclose) = 12 gh calls vs 4 gh calls if the simpler path works, and each reopen creates audit noise (open/close events in issue timeline).
- Why it matters: Memory rule is correct but applied to the wrong command. Needless timeline churn on 4 closed issues.
- Suggested fix: Verify by dry-run that `gh issue comment 798 --body "test"` succeeds on a CLOSED issue (it does today per `gh 2.86.0`). Downgrade AC to plain `gh issue comment` unless the silent-drop bug can be reproduced on CLOSED issues in the current gh version.

### Finding 7 — MINOR — Fixture at `tests/session-analysis/fixtures/claude-stage2-sample.jsonl` is unspecified
- Plan claim: "Create | `tests/session-analysis/fixtures/claude-stage2-sample.jsonl` | Committed fixture (gitignore-safe)" and 9 tests reference it
- Location: Files to Change, TDD Test List
- Evidence: The plan says the fixture replaces `logs/claude-stage2-t1.log` but never states what SHAPE the fixture must have. Tests like `test_parse_logs_nominal` expect "N events in order"; `test_score_lifecycle_complete` expects "all 20 `stage_exit` stages present"; `test_score_insufficient_corpus_shape` needs "nominal cohort". A single sample fixture cannot simultaneously be "one session with 20 stages" AND "a multi-provider cohort" AND "an `insufficient_corpus` input" AND "pipeline-integration fixture with only new events". The plan needs either multiple fixture files or explicit fixture-factory description.
- Why it matters: Without fixture contract specified in the plan, implementation drifts and tests become tautological (pass with whatever the implementer happens to emit).
- Suggested fix: Expand the "fixture" row into a fixture MANIFEST listing each fixture file, its contents (event count, stages present, providers represented), and which tests consume it. Minimum: `nominal-cohort.jsonl`, `insufficient-corpus.jsonl`, `empty.jsonl`, `gate-violations.jsonl`, `pipeline-integration.jsonl`.

### Finding 8 — MINOR — Codex patch-provenance SHA-verify has no rebase/drift story
- Plan claim: AC "Claude applies via `git apply` after SHA-256 verify, and the commit message attributes Codex as original author"
- Location: AC, Q6 Design Decision
- Evidence: The plan describes SHA-256 checksum on the PATCH ARTIFACT itself but not on the files the patch targets. If Codex generates the patch at revision X, but workspace-hub's `scripts/analysis/session-analysis.sh` drifts at revision X+N (active repo), `git apply` either (a) succeeds but produces a semantically wrong merge, or (b) fails with conflict and the plan has no recovery step. SHA-on-patch proves the patch wasn't tampered with; it does not prove the patch still applies cleanly.
- Why it matters: With active churn on `session-analysis.sh` (see git log — recent `chore(session)` commits), the patch window between Codex generation and Claude application is a realistic drift risk.
- Suggested fix: Add to Q6: "patch artifact filename includes the base-commit SHA Codex generated against (e.g. `2026-04-19-codex-patch-43-@<shortsha>.diff`); Claude runs `git apply --check` first and on conflict, dispatches a re-rescue with current HEAD instead of fuzzy-merging."

## Summary

V3 is a meaningful improvement on v2 — scope reduction, derived routing-rules, replace-semantics, patch provenance, and the `insufficient_corpus` machinery all close real v2 defects. However, v3 introduces or fails to surface five fresh MAJOR issues: the pseudocode patch to `session-analysis.sh` would break the existing skill scorer (F1); provider inference is undefined for the actual event-field shapes (F2); `user_review_adherence` references a nonexistent `next_gap_seconds` field (F3); the routing-rules precedence chain is a paper declaration with no runtime consumer, violating the letter of Codex F5's resolution (F4); and `test_emit_atomic_write` as specified cannot be passed by the pseudocode as specified (F5). Two minor issues: overly broad application of the gh silent-drop workaround, and an under-specified fixture contract that 9 tests depend on. Not yet approval-ready.
