## Findings
1. Plan has a contradictory re-review gate. Acceptance Criteria says “Revised plan receives Claude, Codex, and Gemini re-review before approval request,” but §Adversarial Review Summary says “Gemini may be recorded as `UNAVAILABLE` during quota exhaustion” and only “Claude/Codex must return substantive artifacts.” This makes the approval gate ambiguous: either Gemini is required or it is degradable.

2. Plan makes verification-critical claims about cited files without embedding evidence. §Resource Intelligence Summary says `docs/DATA_RESIDENCE_POLICY.md`, `data/document-index/mounted-source-registry.yaml`, `docs/content-pipeline/README.md`, and `docs/WORKSPACE_HUB_CAPABILITIES_SUMMARY.md` contain specific facts, but the plan includes no command output, line references, or quoted excerpts. Because local, connector, and raw GitHub retrieval all failed in this review, those claims remain unverified assertions.

3. The structured source of truth is internally inconsistent. §Client data handling model says “Structured inventory source of truth for this packet is `tests/fixtures/architecture/data_source_inventory.yaml`,” but the TDD row `test_data_inventory_required_seed_sources` uses `data-source-inventory.md` as expected input. That permits the markdown view and YAML fixture to diverge while tests still pass the wrong artifact.

4. The YAML schema is underspecified. §Files to Change creates `tests/fixtures/architecture/data_source_inventory.yaml` and `tests/fixtures/architecture/data_promotion_cases.yaml`, and §Contract Logic says tests validate “machine-readable YAML fixtures,” but the plan only defines required columns for `docs/architecture/data-source-inventory.md`. It does not define required YAML keys, enum values, cross-link format, or how markdown is generated/curated from YAML.

5. The boundary-violation inventory has no discovery method. The TDD row `test_boundary_violation_inventory_present` requires “Existing artifacts that violate or blur boundaries are listed or explicitly marked none-found with search evidence,” but the plan gives no grep/find commands, path scope, deny patterns, or evidence format for `docs/architecture/data-boundary-violations-and-gaps.md`. That makes a false “none found” easy to pass.

6. Redaction is declared but not testable enough. §Client data handling model says tracked public docs must not publish raw client-identifying path names and literal mappings must stay in a private-only appendix, but §TDD Test List has no explicit test that scans the created docs/fixtures for forbidden literal client roots or validates that only `client_present_###` / `client_planned_###` IDs appear in tracked files.

7. The plan references a “private-only appendix outside public docs” in §Client data handling model but does not specify whether that appendix is created, where it lives, how it is protected from git, or how implementation verifies it was not accidentally tracked. That is a data-leak risk for the exact client-path problem the plan is trying to control.

## Blockers
- Finding 1: Resolve the Gemini-required vs Gemini-degradable gate contradiction.
- Finding 2: Add verifiable evidence or line references for cited source claims before approval.
- Finding 3: Make YAML the single tested source of truth or explicitly test markdown/YAML consistency.
- Finding 4: Define the YAML schema and validation contract.
- Finding 5: Add concrete discovery commands/evidence requirements for boundary violations.
- Finding 6: Add explicit redaction tests for tracked docs and fixtures.
- Finding 7: Define or remove the private appendix mechanism before implementation.
