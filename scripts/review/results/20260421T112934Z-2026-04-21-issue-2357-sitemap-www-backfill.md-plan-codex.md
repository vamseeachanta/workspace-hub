### Verdict: MAJOR

### Summary
The plan is mostly scoped correctly for a small sitemap host-normalization change, and it incorporates TDD plus XML validation. It still needs changes before approval because it does not verify the production-relevant build artifact, and its one-time migration evidence is underspecified enough to make the acceptance criteria hard to audit consistently.

### Issues Found
- [P1] Important: The plan stops at editing `aceengineer-website/sitemap.xml` and running tests plus `xmllint`, but it never requires rebuilding and verifying the copied output in `dist/`. Since attested evidence confirms #2391 was specifically about production serving from the build output, this plan should prove the deployed artifact also contains only `https://www.aceengineer.com/...` entries, not just the source file.
- [P2] Important: The one-time verification steps depend on a pre-edit snapshot and a row-for-row metadata comparison, but the plan does not define how that snapshot is captured, where it is stored, or what comparison method is authoritative. That makes the acceptance criteria difficult to reproduce and easy to satisfy inconsistently.
- [P3] Minor: The plan adds several structural assertions to `demo-links.test.js`, but it does not say whether the XML will be parsed structurally or checked with regex/string matching. For checks like 'each `<url>` has exactly one `<loc>`' and metadata-preservation comparisons, a regex-only approach is brittle and could miss malformed structure while still passing.

### Suggestions
- Add an explicit post-build verification step: run the site build, then assert `dist/sitemap.xml` exists and matches the normalized source sitemap content or independently passes the same host/uniqueness checks.
- Specify the migration-evidence mechanism up front: define the exact snapshot path or temp-file convention, the comparison command/script, and what evidence must be recorded in the implementation summary.
- Use an XML-aware parser or DOM-based test helper for the new Jest coverage so the structural assertions are robust and not dependent on formatting.

### Questions for Author
- Should the acceptance criteria require verifying `dist/sitemap.xml` after a real build, given that the production incident in #2391 was in the build/copy path rather than only in the source file?
- What exact command or script will perform the before/after row comparison for metadata preservation, and where will its snapshot/output be stored during implementation?
