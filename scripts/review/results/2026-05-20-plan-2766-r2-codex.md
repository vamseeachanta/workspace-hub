## Findings
1. The plan omits the required `Artifact Map` section. `docs/plans/README.md` says every plan must include `Artifact Map — paths to plan, tests, implementation, review files`; `docs/plans/_template-issue-plan.md` also has an `## Artifact Map` section. The reviewed plan jumps from `## Resource Intelligence Summary` to `## Deliverable` and never maps the plan, tests, implementation, report, or R2 review artifacts. This weakens the review gate because implementers and reviewers do not have one canonical artifact list.

2. The plan claims `docs/plans/README.md` has an existing `#2766` row, but the fetched index does not. Acceptance criterion says ``docs/plans/README.md` existing #2766 row is updated only after the re-review result is known`; `Files to Change` says to “refine the existing #2766 row.” `docs/plans/README.md` Plan Index lines read around the current issue cluster with `#2762`, `#2763`, `#2764`, `#2765`, then `#2760`, `#2758`, etc.; no `#2766` row appears in the fetched lines 1-280. The plan should say to add the missing row, not update an existing one.

3. The `historically_moved_not_currently_present` schema is contradictory. The plan’s live evidence says issue-comment-only repos such as `acma-projects`, `client_projects`, `doris`, `frontierdeepwater`, `OGManufacturing`, `rock-oil-field`, `saipem`, `sd-work`, and `seanation` “were not present in the latest top-level git inventory” and “must reconcile them as `historically_moved_not_currently_present` or equivalent.” But the proposed schema sets `historically_moved_not_currently_present: []` and instead lists those absent repos under `non_tier1_machine_access`. That will make the checker warn on missing non-tier-1 repos rather than recording the historical reconciliation the plan requires.

4. The readiness payload insertion point is underspecified against the current schema. The plan says `readiness_projection(result): append readiness.repo_placement = {...}` and the acceptance criterion says readiness output contains a `repo_placement` section. But `scripts/readiness/telegram_hermes_readiness.py` currently returns `{"overall_status": ..., "hosts": {hid: entry}, "errors": []}` and computes `entry["dispatchable"]` per host. The plan does not say whether `repo_placement` is top-level or under `hosts[hid]`, nor how `repo_placement.dispatchable` combines with the existing host-level `dispatchable`. A top-level field would be ambiguous for multi-host output; a host field would need explicit integration into the current status computation.

5. The proposed registry schema still leaves `machines.dev-primary.repos` semantics inconsistent. `config/workstations/registry.yaml` currently uses `repos` as a machine repo list for `dev-primary`, and the plan’s reconciliation rule says `data_access_profile.repos` must be classified, but the proposed schema’s `repos` includes required/optional tier-1 plus only `OGManufacturing` while `non_tier1_machine_access` lists many additional machine-access repos. The plan never defines whether those additional non-tier-1 repos must also be added to `machines.dev-primary.repos`, intentionally excluded from it, or discovered live only. That makes `test_registry_repos_are_classified_or_explicitly_ignored` incomplete because it can pass without resolving the role of `repos`.

6. The plan does not include a test for unknown top-level sibling repos. The deliverable says it will “classify non-tier-1 machine-access repos affected by #2766,” and issue `#2766` comment `4497956095` lists many moved sibling repos. The TDD list covers missing required, missing optional, missing registered non-tier-1, dirty/ahead, and nested git repos, but it does not include a fixture where `/mnt/local-analysis/<unexpected-git-repo>` exists and is absent from all registry buckets. Without that test, the checker can silently ignore new drift while satisfying the listed tests.

## Blockers
- Finding 3: the proposed schema contradicts the plan’s own historical reconciliation rule.
- Finding 4: readiness integration target and dispatchable/status merge semantics are ambiguous against the current implementation.
- Finding 5: registry `repos` vs `non_tier1_machine_access` semantics are undefined.
- Finding 6: unclassified sibling checkout drift is not tested, despite being central to the issue.
