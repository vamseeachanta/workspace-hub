## Findings

1. **The Windows scheduler action contract is not implementable as specified.** Plan §“Windows task materialization” says to “construct action from the YAML command,” but `config/scheduled-tasks/schedule-tasks.yaml:137-141` contains a folded compound shell command using `$WORKSPACE_HUB`, `$(date)`, cron-specific `\%` escaping, PATH mutation, and redirection. The current scalar reader at `scripts/windows/setup-scheduler-tasks.ps1:90-108` would read `command: >-` as the literal `>-`, while the action builder at lines 247-249 expects a simple script path. The plan does not define folded-scalar parsing, how `$WORKSPACE_HUB` is injected, how cron escaping is translated, or whether a wrapper replaces the compound command. `test_windows_sentinel_action_comes_from_yaml` is too vague to resolve those design choices. A task can therefore render successfully under `-WhatIf` yet fail when scheduled.

2. **The promised “schema validation” is only field-presence validation.** Plan §“Atomic fingerprint generation” requires five keys and only says `machine_id` and `role` must be nonempty; §“Exact state publication” checks object shape and machine equality. This accepts values such as `fingerprint_version: null`, non-string `hostname`, invalid/future `ts`, boolean identifiers, and Python’s non-standard `NaN`. The TDD list at plan lines 254-259 covers missing, malformed, non-object, mismatch, and unsafe keys, but no wrong-type, version, timestamp, or non-finite-value cases. That is insufficient for the claims “schema-validated fingerprint” and “strict publisher validation,” especially because `scripts/monitoring/equivalence_compare.py:179` expects parseable timestamps and relies on identity fields for fleet labeling.

3. **Publish-health persistence failure is absent from the fail-closed exit contract.** Plan §“Sentinel failure contract” says health is “always” written atomically, but defines no required nonzero exit when temporary-file creation, serialization, flush, or replacement fails. `test_publish_health_write_is_atomic` only asserts “prior valid record or complete new record”; it does not assert that inability to publish the new health record fails the cycle. Consequently, a successful comparison can return zero while `scripts/readiness/collect-equality.sh:376-390` continues reading an old health record, contradicting the deliverable’s fresh-evidence guarantee.

4. **The validation command violates the repo’s own runtime rule.** Acceptance criterion line 287 invokes `python scripts/cron/validate-schedule.py`, while the supplied AGENTS.md requires `uv run` and this plan specifically addresses unreliable bare Python resolution. The acceptance command must use the verified resolver or the canonical `uv run --no-project python ...` form.

## Blockers

- Finding 1: specify and test the complete YAML-to-Windows action translation, including folded scalar handling, environment binding, quoting/escaping, and execution from Task Scheduler.
- Finding 2: define an exact fingerprint schema and add wrong-type/version/timestamp/non-finite tests at both generation and direct-publisher trust boundaries.
- Finding 3: make publish-health persistence a required stage whose failure returns nonzero, with an injected write/replace-failure test.
