### Verdict: MAJOR

### Summary
v2 is a substantial improvement that closes most v1 P1/P2 findings: TF-IDF is now fully specified, the cross-link schema is inlined as source-of-truth for #2068, the readiness drift is downgraded from assert to warn, and a malformed-record sidecar plus performance budget land. However, the classifier ranked-output contract (R5) is internally inconsistent with the test fixtures it must satisfy: tests 7 and 8 cannot pass under the documented tie-break rule, which means either the spec or the tests must change before code is written. A handful of smaller drift items (placeholder stopwords_sha, schema enum admits an unreachable value, undefined "reference machine") should also be tightened.

### Issues Found
- [P1] Classifier spec vs. test fixture contradiction. Per the §Classifier ranked-output contract, scoring counts keyword hits in the lowercased title and ties are broken by deterministic alphabetical on domain name. Test 7 ('VIV fatigue in deepwater risers' → primary=VIV, secondary=structural) and Test 8 ('VIV fatigue on pipelines' → primary=pipeline, secondary=VIV) both produce three-way ties at score 1 (VIV, structural, and either pipeline or none depending on whether matching is exact-token or substring). Under the documented alphabetical tie-break, primary becomes 'pipeline' (or 'structural' if exact-token excludes 'riser'/'risers'), not 'VIV'; and the lexical second place is 'structural', not 'VIV'. Either the keyword lists need weights, the matching mode (exact-token vs substring) needs to be made explicit and chosen so the fixtures pass, or the test expectations need to be rewritten. Without resolution, AC1 fails on day one.
- [P2] `TFIDF_PARAMS['stopwords_sha']` is a literal placeholder string ('<computed at first commit; pinned in code constant>'), and Test 12 (`test_tfidf_stopwords_sha_pinned`) asserts the code constant equals sha256(file). The plan does not specify when/how the placeholder is resolved (pre-commit hook? first-run script? manual?). Risk: tests are red until someone manually computes and substitutes the SHA, and the substitution step is not in the Files-to-Change table or the TDD list.
- [P2] Appendix A `secondary_domain` enum admits the value 'misc', but the classifier contract explicitly returns `secondary=None` when no keywords match (the only path to misc primary). 'misc' as a secondary value is unreachable — the schema should be tightened to {pipeline,subsea,VIV,hydrodynamics,marine,structural} or null, otherwise a future maintainer will write code that emits 'misc' as secondary and break downstream consumers without any test catching it.
- [P2] Terminology drift between AC3 ('len(classified) + len(skipped) == 14180') and the pseudocode invariant ('len(papers) + len(skipped) == 14180'). After classification, 'classified' could be read as 'len(papers) - len(misc_bucket)' since misc has separate semantics in some readings. Pin one term and use it in both places, or define `classified := all rows that loaded successfully, including misc` explicitly.
- [P3] AC14 references a 'reference machine' for the <5 min / <15 min performance budget but never defines it (CPU, RAM, disk, OS, Python build). Test 23 (`test_omae_subslice_perf_budget`) is therefore non-portable — it will pass or fail depending on CI runner specs. Either pin a CI runner class (e.g., GitHub Actions `ubuntu-latest`, 2-core, 7GB) or convert the budget to an operation-count assertion instead of wall-clock.
- [P3] `assert path_guard_never_reads('/mnt/ace/docs/conferences/')` in the pseudocode is a runtime invariant that is not trivially implementable as a literal `assert`. The plan should specify the mechanism (e.g., a context manager that monkey-patches `open`/`pathlib.Path.open`, or a static check that the runner imports no module that reaches that path), since Test 5 will need a concrete implementation surface to assert against.
- [P3] Single-pass farthest-first seeding + one assignment pass (no k-means iteration) is fully deterministic but can produce poor cluster quality on a 7,292-paper bucket like OMAE — first-seed bias dominates. Acceptable for stub generation, but the plan should call out that downstream consumers (#2068) should not treat cluster boundaries as authoritative.
- [P3] AC11 conflates two invariants: 'no wiki pages promoted' AND 'no files under config/**, .claude/** modified'. These are independent; bundling them means a single failure mode is harder to localize. Split into AC11a/AC11b.
- [P3] R7 footnote scope assumes both upstream docs have the named sections (`§5.2` of the queue doc, `§3.2` of the batch-packs doc). The Evidence block confirms the files exist but does not confirm those section headings exist; if the section numbers have drifted, the footnote insertion is undefined. Verify section anchors during execution and fall back to end-of-doc with explicit '(was: §5.2)' note.

### Suggestions
- Resolve the P1 classifier contradiction by (a) introducing per-domain weights so VIV and pipeline-keywords don't naturally tie at 1, or (b) declaring exact-token matching and rewriting the keyword lists to win on the intended fixtures, or (c) revising Test 7/Test 8 expected outputs to match the alphabetical tie-break. Whichever path you take, add a worked-example block in the §Classifier section showing the score matrix for both fixtures so the next reviewer can audit the math.
- Add a pre-commit step or a one-line make target (e.g., `make pin-stopwords-sha`) that computes sha256 of the stopwords file and rewrites the constant in code, plus add this step to the Files-to-Change table or to the runner's first-time setup README.
- Tighten the Appendix A enum: split `engineering_domain` (allows misc) from `secondary_domain` (does not allow misc). Round-trip parser test in Test 16 should reject 'misc' as a secondary value.
- For AC14, either pin a concrete CI runner class with `pytest.mark.skipif(not on_reference_runner)`, or replace wall-clock with `assert tfidf_ops_counter <= BUDGET` so the test is reproducible across machines.
- Specify the path-guard mechanism inline (e.g., `runner monkey-patches builtins.open at module load with a deny-list prefix check`) so Test 5 has a concrete API to assert against.
- Add a Test 25 covering the boundary case `len(papers_in_domain) == 1` — current `cluster_count_min=2` would attempt 2 clusters from 1 paper; either guard with `k = min(k, N_d)` or assert N_d ≥ 2 before clustering.
- Consider documenting the `stub_id` collision policy: if two runs against different inputs produce overlapping `bp2-pipeline-001` ids (for example after a future re-run with corrected DOT data), what happens? A `generated_at` + `stub_id` composite key in the JSONL header would harden #2068's consumer.
- Add an explicit acceptance criterion that the runner's exit code is non-zero if `len(papers) + len(skipped) != 14180` (the pseudocode `assert` is currently silent on whether the runner crashes vs. returns).

### Questions for Author
- Is the keyword-matching mode exact-token or substring? The plan reads as substring ('keyword hits in lowercased title'), but the inclusion of both 'pipeline' and 'pipelines' as separate keywords reads as exact-token. The answer determines whether Test 7/Test 8 are fixable by adjusting fixtures or whether the contract itself needs rewriting.
- When #2068 lands, who arbitrates schema drift — does this issue's `schema_version: 1.0` freeze the contract, or can #2068 propose a 1.1 with a migration shim that lives in this issue's runner? The Risks section says '#2068 will adopt this schema' but does not specify the governance.
- Should the misc bucket be clustered at all? Lumping uncategorized papers into TF-IDF clusters can create stubs with no real engineering coherence; an alternative is to write misc papers to a flat appendix in the report and skip stub generation for that bucket.
- For the ISOPE re-index follow-on (AC13: 'filed or flagged for user to file'), is there a preference? The Open Questions defaults to leaving it to a human, but a single-line `gh issue create` invocation would make this fully self-completing and removes one human gate.
- Test 23 (OMAE perf budget) — is the intent to fail CI on regression, or to be a soft canary? If CI-blocking, the 'reference machine' question above is load-bearing; if canary-only, mark with `pytest.mark.benchmark` and exclude from the AC1 'all tests pass' bar.
