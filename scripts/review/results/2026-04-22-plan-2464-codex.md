### Verdict: MINOR

### Summary
The deletion set and evidence are rigorous; that is where this plan is strong. Weaknesses cluster in three places: (1) the file the plan creates depends on a contract that is not yet final; (2) two acceptance criteria are satisfiable by a trivial artifact, making the regression test less adversarial than it reads; (3) an important execution hazard — the `docs/CONTENT_INDEX.md` regenerator — is acknowledged but not prevented.

### Issues Found

- [P1] Critical — **`scripts/search/build_content_index.py` will silently clobber the raw-inventory banner.** The plan says so itself ("Mitigation: place the banner outside the generator's write window…with a sentinel comment telling the generator to preserve it"), but neither the sentinel nor the generator change is in the Files-to-Change table. That means execution can land a green build (banner present at commit time) and the very next nightly index rebuild erases the acceptance criterion. Either add a minimal generator-side guard to the Files-to-Change table (treat this plan as a doc+generator pair) or move the banner to a separate file that the generator never writes (e.g., `docs/CONTENT_INDEX.header.md` + include directive) and update the test to check the composed artifact.
- [P2] Important — **`test_content_index_declares_raw_inventory` checks two substrings on the first 10 lines.** An executor can satisfy the test with a single-line comment that nobody reads and still claim compliance. Tighten the test to require (a) a visible Markdown `> **⚠ Raw inventory**` style callout, (b) an explicit link to `docs/ROUTING_INDEX.md`, and (c) the sentinel comment the regenerator will respect.
- [P2] Important — **No authority lock on the "ten banned filenames" between this plan and the scorecard.** The plan copies the list verbatim. If the scorecard is edited (to add, say, `**Deliverable:**`) later, the test still passes. Make the test read the hygiene set from a canonical machine-readable YAML (new, one-line list) and have the scorecard and plan both cite it. That converts a prose-locked rule into a Level-2 enforcement per `.claude/rules/patterns.md`.
- [P2] Important — **Deletion safety check is asserted but not operationalized.** The plan says `git log --follow + grep -r <filename>` each candidate before deletion. It does not say who runs it, with what tool, and what command exits non-zero on a hit. For files named `-`, `**Issue:**`, etc., shell-quoting is non-trivial. Provide the exact commands in a code block so the executor cannot vary them.
- [P3] Minor — **Out-of-scope list mentions ~25 tail-end root artifacts but does not link a follow-on issue.** That is a well-known anti-pattern: the mess re-appears on every audit because no one owns the cleanup. Open (or link) a single "tier-1 root-hygiene Pass 2" issue and reference it in the Out-of-scope line.
- [P3] Minor — **#2460 alignment clause is aspirational.** "Rebase the section list before merge" is a promise, not a gate. Add a pre-merge check — e.g., a CI rule that `docs/ROUTING_INDEX.md`'s section headings equal the section list in the #2460 contract file — or explicitly accept that this is a prose-only rule and downgrade the claim.

### Suggestions

- Move the regression test out of `tests/docs/` if it is the only file there that touches `git ls-files`; otherwise confirm with a sibling pattern. Fast test files that shell out to git tend to grow flaky in CI without a rate-limited skip.
- The plan's "Authority": make `docs/standards/TIER1_INDEXING_AND_CODE_PLACEMENT_CONTRACT.md` (the deliverable of #2460) the single source of required sections. This plan's test would then assert equality against that source, not against a hand-copied list.
- Consider renaming `docs/CONTENT_INDEX.md` → `docs/RAW_CONTENT_INVENTORY.md` with a redirect stub. The Open Question defers it; closing it one way or the other unblocks the banner-text lock.

### Questions for Author

- Will the executor have write access to `scripts/search/build_content_index.py`? If not, the P1 finding is blocked until a separate PR touches that generator — say so in Dependencies.
- Is a follow-on issue already open for the ~25 non-scorecard tail-end artifacts? If not, what is the rule the author wants enforced: "remove nightly", "archive to `_archive/`", or "triage into owning repos"? The plan's silence means the answer gets re-invented each time someone audits.
- Should the new regression test be part of the mandatory `uv run pytest tests/docs/` hook, or opt-in via a marker? The plan does not touch CI wiring; that should be called out.
