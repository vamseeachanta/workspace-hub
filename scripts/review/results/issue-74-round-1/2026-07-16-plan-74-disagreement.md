### claude

- **Shared dataset — sibling `field-economics-sensitivity` regression is unaddressed (MAJOR).** The plan scopes only `field-explorer`, but `config/capabilities.yaml:102` shows `field-economics-sensitivity` (`status: live`) reads the *same* `hf_dataset: aceengineer/worldenergydata-explorer` via the floating datasets-server (`hf-fetch.js`). Producer #1045 will republish that dataset as a relational browser snapshot (its contract lists `fields/wells/countries/parametric_economics`). Any config/schema change to `parametric_economics` on republish silently breaks a live sibling capability the plan never mentions. §Resource Intelligence and §Risks say nothing about this coupling. Nothing verifies the republish preserves the `parametric_economics` schema the floating path still consumes.
- **Route collision on `/capabilities/field-explorer.html` is not explicitly resolved (MAJOR).** The existing renderer emits `/capabilities/${cap.id}.html` (`render-capabilities.js:117,123`) for `id: field-explorer`. The plan's §Registry Contract line 91 and §Template/Route lines 113–115 emit the *same* path for the *same* id. The plan's validator "rejects duplicate template/route ownership" (line 96) but that governs *new* relational entries — it does not state that the legacy `render-capabilities.js`/`build.js` path must skip `mode: relational-snapshot` entries. Absent an explicit "legacy renderer yields this route" step in §Files to Change (line 157 only says build.js will "orchestrate validated relational rendering transactionally"), the build risks double-writing `dist/capabilities/field-explorer.html`.
- **Silent coverage regression: 56→10 fields, 84→56 wells (MAJOR).** §Resource Intelligence line 29 records the current live page as "Showing 50 of 56 rows" and "Showing 50 of 84 rows" (fields=56, wells=84). §Verified baseline line 47 and #1045's body both fix V1 at "10 fields and 56 wells." So pinning the relational snapshot *reduces* visible fields from 56 to 10 and wells from 84 to 56. §Risks/Fixed-Decisions (lines 297–305) frames static-output size and pinning as strictly positive and never discloses that the replacement drops ~46 field entries and ~28 wells from what is currently live/indexed. This is an SEO/coverage regression that needs an explicit disclosure and transition decision (e.g., retain the old table view until parity), not silence.
- **Hard dependency on an unplanned, unpublished producer (MAJOR blocker for implementation).** The entire Registry Contract hinges on `revision: <exact-40-character-hf-sha>` (line 73), `browser/manifest.json`, and the committed V1 fixture at `data/hf-cache/pinned/<dataset>/<sha>/` (line 166). Producer #1045 is `status:needs-plan` and OPEN — it has no approved plan, no implementation, no HF commit, no receipt. The manifest, shards, stable IDs, and the SHA the fixture directory is named after do not yet exist. The plan concedes "production pinning will wait for a verified #1045 receipt" (line 18), but the *fixture the plan proposes to commit and TDD against* is equally blocked. Implementation cannot begin beyond scaffolding until #1045 is planned, approved, and published.
- **Acceptance test hardcodes counts the plan elsewhere insists must be discovered (MINOR).** §Failing-First line 235 asserts "V1 route counts are discovered as 1 parent + 10 fields + 56 wells," while §Verified baseline line 47 says "Production code will discover counts from the validated manifest rather than hardcoding them," and #1045 explicitly warns "counts are discovered from inputs, not hardcoded." Baking `10`/`56` into a website test recouples it to a producer output that #1045 has not frozen (a zero-well field gaining data, or completeness changes, flips the count). Assert *manifest total == route count*, not the literals.
- **The plan advertises a round-1 adversarial pass that produced zero signal (MINOR).** The header (line 12) cites three "Round 1 artifacts." In fact `*-claude.md` and `*-codex.md` are 0 bytes and `*-gemini.md` is `UNAVAILABLE` (no non-interactive auth). No adversarial review has actually run. §Adversarial Review Summary (lines 289–295) does honestly mark all three PENDING, but the header presents the artifacts as substantive. State plainly that round 1 yielded no usable review and this is the first real pass.
- **HF one-hop redirect policy is an unverified behavioral assumption (MINOR).** §Immutable-read evidence line 36 asserts raw Git blobs "may redirect once to a same-origin `/api/resolve-cache/.../<exact-sha>/...`" and the fetcher will permit exactly that shape. This is stated as fact but not empirically demonstrated in the plan. It fails closed (LFS/Xet/off-origin rejected), so it is not a correctness hazard, but the plan should mark it as an assumption to verify against live HF during implementation rather than a settled fact — HF's Xet migration can move blobs off the same-origin cache form.

### codex

- The plan violates the mandatory planning evidence contract. It asserts runtime behavior in §Resource Intelligence lines 24–29 but supplies no embedded commands, timestamps, output, file-existence evidence, or reproduction proof. It also omits the required Standards, Gaps Identified, and Artifact Map sections. `docs/plans/_template-issue-plan.md:22-118` and the issue-planning skill explicitly require this evidence and make missing runtime reproduction a default-MAJOR defect.
- The registry contract cannot implement the generic requirement in [issue #74](https://github.com/vamseeachanta/aceengineer-website/issues/74). Plan lines 68–94 hardcode field/well semantics but omit registry-declared config, value column, label column, slug column, URL parameter, and duplicate-label disambiguation. The renderer therefore cannot derive selector text or slugs generically, nor prove that another compatible hierarchy works without code changes.
- The plan does not define dispatch away from the legacy renderer. `build.js:58-66,152-163` hydrates and renders every capability through the legacy path, which already owns `/capabilities/field-explorer.html`; `scripts/render-capabilities.js:64-94,292-360` expects `hf_dataset`, `tables`, and floating refresh metadata. The proposed entry instead uses `dataset` and `mode`. Files to Change omits `scripts/render-capabilities.js`, `scripts/hf-fetch.js`, `scripts/verify-capabilities-online.js`, and their tests, leaving a route collision and a CI gate that can incorrectly PASS after treating `dataset: undefined` as a transient online failure.
- The local browser-data contract is undefined. Plan lines 59 and 201 say local data will be emitted but specify no output path, revision-bearing filename, URL, HTML binding, or receipt entry. `vercel.json:19-26` applies one-year immutable caching to `/assets/*`; a stable JSON URL would allow R2 or rolled-back R1 pages to read stale cached data. Content-addressed URLs and a stale-client rollback test are required.
- The promised atomic promotion is not implementable as described. Plan lines 135–138 and 153 require replacing a populated `dist`; the Node probe returned `ENOTEMPTY`. Meanwhile `build.js:109-137,154-175,201-209` writes directly to global `dist`, and CSS mutation occurs afterward at `build.js:249-327`. The plan defines neither a parameterized output root nor backup/journal/recovery semantics and has no crash-point tests between promotion operations.
- The receipt timeline is circular. Plan line 167 creates the build receipt before deployment, but lines 257–259 require every receipt to bind a live Vercel deployment ID. The parent correctly treats `build_receipt`, `browser_receipt`, and `deployment_receipt` as separate inputs at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:217-219`. The website plan must define separate schemas and trust boundaries.
- The protected release infrastructure assumed by lines 259–281 does not exist and has no owner. Live GitHub environment inspection found no required-reviewer protection on the website environments and no `field-explorer-publish` environment in worldenergydata. Neither child plan assigns repository-setting changes, reviewer allowlists, `prevent_self_review`, branch policy, or a preflight verifying those settings.
- No plan defines the production workflow required by the parent. Parent pseudocode lines 240–253 requires candidate-bound Vercel create/query/reconcile/rollback operations. Website line 156 creates only a verification workflow, while line 258 declares production collection read-only; its file list contains no deployment-intent client or production workflow. The parent file list likewise owns verification/state code, not the deployment implementation.
- Generated route integration is incomplete. Nested field/well pages require depth-sensitive `rootPath`, while `content/partials/head-common.html:1-4`, `content/partials/nav.html:9-19`, and `build.js:152-161` only support the existing one-level detail route. Sitemap generation is also unresolved: `build.js:178-186,241-244` copies the static root sitemap after page generation, and `tests/js/build.test.js:173-213` requires byte-identical copying, so a generated relational sitemap can be overwritten.
- The browser/accessibility verification toolchain is absent from Files to Change. `package.json:16-97` discovers an explicit list of Jest files; arbitrary new tests will not run. `package.json:112-120` and `package-lock.json` contain no Playwright or axe dependency. The plan omits `package.json`, `package-lock.json`, test-discovery changes, and reproducible scripts for the browser, accessibility, legal, link, receipt, and evidence commands promised at lines 249–259 and 284.
- Stable canonical URLs conflict with the producer contract. Website lines 90–93 put mutable slugs in canonical paths, while `docs/plans/2026-07-16-issue-1045-wed-hf-browser-snapshot.md:127` declares slugs mutable. Acceptance line 283 promises URL stability, but the website plan contains no slug-history input, redirect generation, stable-ID route design, or cross-revision slug-change test.
- The child plan does not enforce the parent’s P0 dependency. Parent lines 143–149 require the parent contract to be reviewed and user-approved before child implementation. The parent remains `status:needs-plan`, and its lines 344–348 record unresolved Round-3 MAJOR verdicts. Website line 18 and acceptance line 266 mention only the child approval gate; implementation could therefore begin without the approved contract and receipt schemas it must conform to.
