## Findings

1. The plan violates the mandatory planning evidence contract. It asserts runtime behavior in §Resource Intelligence lines 24–29 but supplies no embedded commands, timestamps, output, file-existence evidence, or reproduction proof. It also omits the required Standards, Gaps Identified, and Artifact Map sections. `docs/plans/_template-issue-plan.md:22-118` and the issue-planning skill explicitly require this evidence and make missing runtime reproduction a default-MAJOR defect.

2. The registry contract cannot implement the generic requirement in [issue #74](https://github.com/vamseeachanta/aceengineer-website/issues/74). Plan lines 68–94 hardcode field/well semantics but omit registry-declared config, value column, label column, slug column, URL parameter, and duplicate-label disambiguation. The renderer therefore cannot derive selector text or slugs generically, nor prove that another compatible hierarchy works without code changes.

3. The plan does not define dispatch away from the legacy renderer. `build.js:58-66,152-163` hydrates and renders every capability through the legacy path, which already owns `/capabilities/field-explorer.html`; `scripts/render-capabilities.js:64-94,292-360` expects `hf_dataset`, `tables`, and floating refresh metadata. The proposed entry instead uses `dataset` and `mode`. Files to Change omits `scripts/render-capabilities.js`, `scripts/hf-fetch.js`, `scripts/verify-capabilities-online.js`, and their tests, leaving a route collision and a CI gate that can incorrectly PASS after treating `dataset: undefined` as a transient online failure.

4. The local browser-data contract is undefined. Plan lines 59 and 201 say local data will be emitted but specify no output path, revision-bearing filename, URL, HTML binding, or receipt entry. `vercel.json:19-26` applies one-year immutable caching to `/assets/*`; a stable JSON URL would allow R2 or rolled-back R1 pages to read stale cached data. Content-addressed URLs and a stale-client rollback test are required.

5. The promised atomic promotion is not implementable as described. Plan lines 135–138 and 153 require replacing a populated `dist`; the Node probe returned `ENOTEMPTY`. Meanwhile `build.js:109-137,154-175,201-209` writes directly to global `dist`, and CSS mutation occurs afterward at `build.js:249-327`. The plan defines neither a parameterized output root nor backup/journal/recovery semantics and has no crash-point tests between promotion operations.

6. The receipt timeline is circular. Plan line 167 creates the build receipt before deployment, but lines 257–259 require every receipt to bind a live Vercel deployment ID. The parent correctly treats `build_receipt`, `browser_receipt`, and `deployment_receipt` as separate inputs at `docs/plans/2026-07-16-issue-3559-field-explorer-cross-repo-program.md:217-219`. The website plan must define separate schemas and trust boundaries.

7. The protected release infrastructure assumed by lines 259–281 does not exist and has no owner. Live GitHub environment inspection found no required-reviewer protection on the website environments and no `field-explorer-publish` environment in worldenergydata. Neither child plan assigns repository-setting changes, reviewer allowlists, `prevent_self_review`, branch policy, or a preflight verifying those settings.

8. No plan defines the production workflow required by the parent. Parent pseudocode lines 240–253 requires candidate-bound Vercel create/query/reconcile/rollback operations. Website line 156 creates only a verification workflow, while line 258 declares production collection read-only; its file list contains no deployment-intent client or production workflow. The parent file list likewise owns verification/state code, not the deployment implementation.

9. Generated route integration is incomplete. Nested field/well pages require depth-sensitive `rootPath`, while `content/partials/head-common.html:1-4`, `content/partials/nav.html:9-19`, and `build.js:152-161` only support the existing one-level detail route. Sitemap generation is also unresolved: `build.js:178-186,241-244` copies the static root sitemap after page generation, and `tests/js/build.test.js:173-213` requires byte-identical copying, so a generated relational sitemap can be overwritten.

10. The browser/accessibility verification toolchain is absent from Files to Change. `package.json:16-97` discovers an explicit list of Jest files; arbitrary new tests will not run. `package.json:112-120` and `package-lock.json` contain no Playwright or axe dependency. The plan omits `package.json`, `package-lock.json`, test-discovery changes, and reproducible scripts for the browser, accessibility, legal, link, receipt, and evidence commands promised at lines 249–259 and 284.

11. Stable canonical URLs conflict with the producer contract. Website lines 90–93 put mutable slugs in canonical paths, while `docs/plans/2026-07-16-issue-1045-wed-hf-browser-snapshot.md:127` declares slugs mutable. Acceptance line 283 promises URL stability, but the website plan contains no slug-history input, redirect generation, stable-ID route design, or cross-revision slug-change test.

12. The child plan does not enforce the parent’s P0 dependency. Parent lines 143–149 require the parent contract to be reviewed and user-approved before child implementation. The parent remains `status:needs-plan`, and its lines 344–348 record unresolved Round-3 MAJOR verdicts. Website line 18 and acceptance line 266 mention only the child approval gate; implementation could therefore begin without the approved contract and receipt schemas it must conform to.
