### Verdict: MAJOR

### Summary
The plan is a well-scaffolded design-issue plan with strong resource intelligence, but it explicitly defers the adversarial review, leaves six open decisions unresolved, and has not verified the existence of a file (`scripts/email/email-routing.yaml`) that the plan's core routing-modification task depends on. Before approval the author must close the open decisions, re-verify file existence at HEAD, and complete the cross-provider review pass the plan itself describes as prerequisite.

### Issues Found
- [P1] Critical: The plan is explicitly a scaffold — the Adversarial Review section is empty (Claude/Codex/Gemini verdicts all `pending`), yet downstream acceptance criteria reference review artifacts at specific paths. Approving the plan in this state would violate the project's own `status:plan-review → plan-approved` gating rule.
- [P1] Critical: File existence of `scripts/email/email-routing.yaml` is not verified at HEAD — the plan admits this (see Risks). The 'Modify' task for that file could silently turn into a 'Create' task, changing both scope and test semantics (e.g., `test_routing_yaml_sandsig_unchanged` becomes meaningless). Verify with `ls`/`git cat-file` before locking the plan.
- [P1] Critical: Gmail MCP scope is read+compose only per cited memory, but the state machine requires Gmail-side label writes (`queue/extracted`, `queue/awaiting-reply`, `queue/completed`, `queue/reactivated`). The plan flags this as a risk but does not commit to a mechanism (browser automation vs. re-auth with `gmail.modify`). Without resolution, the design doc cannot specify the label-transition implementation that #2024 will consume.
- [P2] Important: Six 'Open' questions remain in Risks and Open Questions (deletion safety, extraction format, versioned schema, rule-file placement, plus two inherited). Tentative recommendations are listed but the plan's own Deliverable statement says the design doc 'resolves the 4 open decisions' — the plan must resolve them before execution, not during.
- [P2] Important: Re-activation transition in the state machine is ambiguous. Pseudocode shows `deleted → re-activated (restored from Trash)` but Gmail's Trash auto-purges at 30 days. The plan does not specify behavior when a reply arrives on a thread already purged from Trash, which is a real failure mode for the queue's re-activation guarantee.
- [P2] Important: `queue-state.jsonl` is append-only but there is no specification for how to derive current state from the log (scan-to-end? snapshot? compaction?). For a queue with unbounded thread volume, this becomes an O(n) read per lookup without a defined index strategy.
- [P2] Important: TDD test list omits state-machine tests. Since the state machine is the plan's central semantic contract, absence of tests like `test_reactivation_from_awaiting_reply`, `test_grace_period_boundary`, `test_duplicate_transition_idempotent` means the contract is asserted but not verified.
- [P2] Important: `test_spam_rules_letstok_no_false_positive_on_real_inquiry` uses 'a fabricated real inquiry sample.' A single fabricated negative is insufficient; false-positive rate requires a corpus of real legitimate inquiries, otherwise the test is purely confirmatory of the rule's author's bias.
- [P3] Minor: Acceptance Criterion 'no new issue created for follow-on items (use existing backlog)' conflicts with normal practice of filing narrowly-scoped follow-ups; rationale not given and may block legitimate decomposition.
- [P3] Minor: Artifact Map lists `.planning/INDEX.md (if present)` — conditional modification targets make the plan non-deterministic. Decide now whether the file exists and whether it must be touched.
- [P3] Minor: Complexity rating of T2 may be understated given (a) unresolved Gmail-scope mechanism, (b) state-machine semantics, (c) three config files plus design doc plus tests plus three review artifacts. Worth re-evaluating after open decisions are closed.
- [P3] Minor: Plan does not state what happens when classification precedence ties occur (e.g., a thread matching both `data_extract` and `drive_doc`) — precedence list is cited but tie-breaking semantics are not explicit.

### Suggestions
- Resolve all six open decisions inline with a short rationale before transitioning to `status:plan-review`; move 'Tentative recommendation' lines into 'Decision' lines with explicit tradeoffs.
- Run `ls scripts/email/email-routing.yaml` and capture the output (or `git cat-file -e HEAD:scripts/email/email-routing.yaml`) in the Evidence section before any further work. Update the Files-to-Change action from 'Modify' to 'Create or Modify' contingent on the check.
- Add a dedicated 'Gmail Label Mechanism' subsection under the state machine that commits to one of: (a) re-auth with `gmail.modify`, (b) browser automation via Playwright, (c) local-only state with no Gmail-side labels. Each has distinct security and reliability consequences for #2024.
- Add state-machine tests to the TDD list — at minimum: reactivation from `completed`, reactivation from `deleted` post-Trash-purge, grace-period boundary, idempotent re-entry, and log-derivation correctness.
- Specify a minimum viable false-positive corpus for the Letstok rule (e.g., ≥10 legitimate form submissions from prior triage artifacts) rather than one fabricated sample.
- Document the state-log read strategy (snapshot file vs. periodic compaction vs. full scan) — even if the v1 choice is 'full scan,' making the choice explicit prevents a silent performance regression later.
- Dispatch the cross-provider review as described in 'What a follow-up session needs to do' and fill in the Adversarial Review Summary before requesting approval. Current draft should carry `status:draft`, not be circulated as a reviewable plan.
- Consider splitting the routing-config update and the spam-detection rule into separate follow-on issues — they are mechanically independent of the design doc and may be executable before the design decisions are final.
