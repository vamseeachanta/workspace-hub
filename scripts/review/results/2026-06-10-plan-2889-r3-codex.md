## Findings

1. MAJOR: The verdict model does not implement the issue’s core “vs Claude-on-same-machine” contract. Issue #2889 says Codex/Hermes are graded against Claude on the same box. Plan pseudocode `provider_capability_verdict(provider_record, capability)` maps a target provider’s own status directly to `PARITY/DIVERGES/EXPECTED-DIVERGENCE/ABSENT` without reading the Claude reference record. This can report `PARITY` for Codex when Claude is absent/unknown, or `DIVERGES` when both Claude and Codex lack the same capability. The plan needs a reference-aware verdict function and tests for reference absent/unknown/present combinations.

2. MAJOR: Provider presence is too broad and will create false non-ABSENT cells. Plan pseudocode sets `provider_present = command_exists(provider) or provider_runtime_state_exists(provider)`, while the current collector’s provider presence is CLI-based via `prov() { have "$1" ... }` in `scripts/readiness/collect-equality.sh`. Because repo-tracked runtime files like `config/agents/codex/AGENTS.runtime.md` exist in every checkout, a machine with no Codex CLI can still be marked `present` and then get `PARITY` for `memory:read`. That violates “on box N” provider capability measurement.

3. MAJOR: `workflow:gates` still measures static repo text, not whether the provider is actually subject to the gates. The plan checks `config/agents/codex/AGENTS.runtime.md` and `config/agents/hermes/SOUL.runtime.md` for phrases, but `scripts/agents/install-soul-runtime.sh` shows the operational condition is local runtime symlink/install state (`~/.codex/AGENTS.md`, `~/.hermes/SOUL.md`). Static repo files prove the contract exists, not that the provider on that machine loads it. This can falsely report `PARITY` on boxes with stale or clobbered provider runtime files.

4. MAJOR: Collector coverage is under-specified for the 3x3 provider schema. The planned collector test only requires `schema_version == 4` and `dimensions.provider_harness.schema_version == 1`; that can pass with missing providers or missing capabilities. Given prior pseudocode regressions already emitted only one provider, the plan needs a live `collect-equality.sh --stdout` test asserting all three providers and all three exact capabilities exist with valid statuses/reasons.

## Blockers

- Define parity relative to Claude-on-same-machine, not target-provider status alone.
- Split provider installation/presence from repo runtime artifact presence.
- Make `workflow:gates` verify the active provider runtime path/symlink state, or explicitly downgrade static repo text to evidence rather than parity.
- Add live collector tests that fail unless `dimensions.provider_harness.providers.{claude,codex,hermes}.{memory:read,skills:invoke,workflow:gates}` are all populated.
