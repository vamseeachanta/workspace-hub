### Verdict: MAJOR

### Summary
The plan is directionally solid, but it still has a few contract-level inconsistencies that would cause implementation drift across #2017, #2024, and #2026. The main problems are a new Gmail mutation sneaking back into scope, an ownership contradiction around the xfail contract tests, and missing specification/enforcement for artifacts the plan treats as required.

### Issues Found
- [P1] The spam path is internally inconsistent and likely infeasible as written. Scope v7 says the spam layer adds 'no new Gmail action beyond classification', but D6, the state machine, and pseudocode all require spam to 'auto-archive'. Given the stated Gmail scope limits and the explicit deferral of new Gmail-side mutations to follow-on work, the plan needs one authoritative rule for spam handling.
- [P2] The dependency contract for the xfail state-machine tests is contradictory. The owner matrix says those tests are blocked on #2026 storage implementation, but the TDD section says they 'cannot pass until #2024 implements the pipeline'. That creates ambiguity about which downstream issue must satisfy the contract and when the xfails are removed.
- [P2] The plan requires behavior that it does not fully specify. D4 introduces `queue-learning-log.jsonl`, and D1 introduces a fixture redaction pre-commit hook, but neither artifact is included in the artifact/files-to-change contract. Acceptance criteria also reference schema tests for the learning log and snapshot meta format without clearly pinning where those schemas or enforcement hooks live.
- [P3] The plan still mixes review-version bookkeeping with acceptance criteria. It requires 'v2 cross-review artifacts' dated `2026-04-20` even though the document is now at v7, which makes the acceptance contract harder to evaluate and easy to satisfy with stale review outputs rather than reviews of the current text.

### Suggestions
- Make spam handling explicit in one place: either classify-only in #2017 and defer archive behavior to #2423/#2024, or state that archive is already covered by grandfathered existing routing and name the exact mechanism.
- Choose a single unblocker for the xfail contract tests. If #2026 owns the storage module under test, say they turn green with #2026 and #2024 only consumes that API.
- Expand the artifact contract to include the learning-log schema and the PII-enforcement mechanism, or remove those requirements from this issue if they are intentionally deferred.
- Update the review acceptance criterion so it requires fresh review artifacts for the current plan revision instead of hard-coding 'v2' artifacts from April 20, 2026.

- Should `docs/design/email-queue-state-schema.yaml` also define `queue-learning-log.jsonl`, or is a separate schema artifact intended?
- Where is the pre-commit redaction rule meant to live: existing repo hook config, a new script, or only as a pytest check?
