## VERDICT: CHANGES-REQUESTED

## Findings (severity-ranked)

- [BLOCKER] `docs/plans/2026-06-01-issue-2931-deckhand-message-lifecycle-poc.md:POC boundary` — POC excludes Layer 3 per-scope PATs while allowing write execution through Layer 2 only; the governance doc itself says command hooks are bypassable. — Make the POC read-only, or require per-scope GitHub credentials for every GitHub operation before any write-capable POC ships.

- [BLOCKER] `docs/governance/2026-06-01-deckhand-scope-routing-orthogonality-decision.md:Decision`; `docs/plans/...:Diagram 3` — “origin chat is always allowed” is unsafe for shared Telegram groups. A private `acma` command from a shared origin can leak repo names, PR URLs, branch names, or denial reasons to everyone in that group. — Origin should be allowed only for DMs or channels whose clearance matches the scope sensitivity; otherwise reply with a generic “continue in DM” message.

- [BLOCKER] `docs/plans/...:Diagram 2`; `docs/governance/...orthogonality...:Consequences` — origin-bound default permits repo resolution from “operator named it,” which reintroduces prose-based privilege routing and weakens channel→repo binding. — For writes, require either explicit scope or a registered channel→repo binding; a named repo in prose should not establish default write scope.

- [MAJOR] `docs/plans/...:Diagram 1`; `docs/plans/...:Diagram 2` — TOCTOU is not handled between scope resolution and `git/gh` execution. The plan passes “requested action(s) + active scope,” then executes in an unspecified cwd/env where remotes, `GH_REPO`, aliases, or worktree state can drift. — Use an immutable command manifest: operator id, scope id/version, repo node id, canonical worktree, action class, token id; revalidate immediately before each command.

- [MAJOR] `docs/governance/2026-06-01-deckhand-scope-enforcement-below-model-decision.md:Decision`; `docs/plans/...:Diagram 2` — Layer 2 is underspecified and bypassable by direct GitHub API calls, `gh api`, `curl`, PyGithub/Octokit, libgit2, MCP tools, shell subprocesses, git aliases, gh extensions, or absolute binary paths. — Define one mandatory execution substrate and block all outbound GitHub mutations except through it; include bypass tests for each path.

- [MAJOR] `CONTEXT.md:Language`; `docs/governance/...enforcement...:Rationale` — destructive-vs-write boundary is enforceable only narrowly, not safely. A normal commit can delete every file, remove CI protections, expose secrets, or alter deployment workflows. — Add write-risk gates: PR-only for POC, no direct protected-branch pushes, diff budgets, deny mass deletion/CI/security-sensitive edits without explicit elevated approval.

- [MAJOR] `docs/governance/...enforcement...:Decision`; `docs/plans/...:Worked example` — audit and response content can leak sensitive identifiers. “Redacted, ID-free” is insufficient if scope/repo/action/PR URL/title remains public or goes to uncleared origin chat. — Treat repo names, PR URLs, branch names, titles, and error specifics as sensitive for private scopes; public summaries should use counts, hashes, or scope-class buckets only.

- [MAJOR] `docs/plans/...:Diagram 2` — not every deny path audits despite the text claiming every deny is audited; `D2[Reject write — ask for explicit scope]` omits audit. Also execution is audited only after success, so crash-after-mutation loses the record. — Add `PENDING` audit before execution and `FINAL` audit after; every reject node must explicitly include audit.

- [MINOR] `docs/plans/...:What the POC needs before build` — operator identity model is missing. Gateway allowlist plus per-scope allowlist is not enough unless identities are stable platform IDs, not usernames/display names, and are mapped across platforms intentionally. — Specify canonical operator IDs and fail-closed identity normalization.

## What's missing for a safe POC

- A mandatory command-runner threat model: allowed APIs, forbidden APIs, env sanitization, cwd control, alias/extension disabling.
- Per-scope token plan or a read-only POC constraint.
- Origin chat clearance rules for shared channels.
- Atomic scope/action manifest with pre-exec revalidation.
- Diff-risk policy for dangerous-but-non-destructive writes.
- Audit-before-execute plus redaction rules for private scope metadata.
- Tests proving bypass attempts fail, not just happy-path authorization tests.
