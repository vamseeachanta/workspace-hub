### claude

- **"Three landed fix PRs" claim is FALSE** (plan §Resource Intelligence Summary, lines 35-39). Plan asserts the three PRs are "landed" and uses them in §Evidence/Reproduction proofs (line 117) as "the audit + 3 landed fix PRs serve as the empirical evidence." Live state: `worldenergydata#415`, `aceengineer-website#15`, `assethold#51` are **all OPEN**. This is a load-bearing factual error — the plan's forward-validation assumes the sibling repos are clean, but if the fix PRs haven't merged, the markers may still be on `main` in those siblings. Installing the new hook on those repos via §Acceptance criterion 12 ("hook installed on ≥2 sibling repos…verified to block a deliberately constructed marker-containing commit") would *also* block legitimate work until those PRs merge.
- **"40 existing + 16 new = 56" is WRONG** (plan §Acceptance Criteria, the no-regression criterion ~line 342). Actual `grep -c "^def test_" tests/enforcement/*.py` total = **36** test functions, not 40. Math becomes 36 + 16 = 52, not 56. Replace the magic number with a delta-form invariant (e.g., "existing test count + 16 new").
- **Self-exclude is a blanket file-level exemption — exploitable defense bypass** (plan §Pseudocode line 174). `if "$file" == "scripts/enforcement/check-no-conflict-markers.sh": continue` permanently whitelists the entire script from marker detection. Any future modification to that script — including a malicious one that adds conflict-marker text outside the documentation block — would land silently. The mitigation should be per-line sentinel matching (`# CONFLICT_MARKER_FORENSIC_OK` end-of-line tag, as `check-no-abs-paths.sh:28` does with `# abs-path-allowed`), NOT per-file exemption.
- **Forensic-whitelist sentinel reads working tree, but marker scan reads staged blob — TOCTOU divergence** (plan §Pseudocode lines 172, 178-179). Marker scan uses `grep ... (staged blob via git show :"$file")`; sentinel check uses `grep -q "<!-- CONFLICT_MARKER_FORENSIC_OK -->" "$file"` (working tree). An attacker can place the sentinel ONLY in the working tree (not staged), defeating the whitelist gate while landing markers in stage. Both reads must come from the same source — the staged blob.
- **TIER1_REPOS path resolution unspecified — installer is non-deterministic** (plan §Pseudocode line 210). `REPO_PATH = "$HOME/$repo" OR "$WS_ROOT/../$repo" OR configured base` defers a critical decision. On this machine `~/workspace-hub` is a sparse overlay (per CLAUDE.md `Sparse overlay`); siblings exist at both `/mnt/local-analysis/<repo>` and possibly under `~/<repo>`. The installer needs a single resolution order (preferably `${WORKSPACE_HUB:-…}/../$repo` then fallback) with a test of `-d "$REPO_PATH/.git"` to confirm. Without it, installer behavior on this user's actual layout is undefined.
- **GNU sed `i\` insert-before-pattern is non-portable to BSD/macOS** (plan §Install-hooks.sh wiring, lines 272-278). The `sed -i '/^exit 0$/i\...'` form is GNU-specific. BSD sed (macOS default) requires `-i ''` (empty string) and a different newline-escaping form for `i\`. `bootstrap-machine.sh` claims cross-OS support (lines 22-27 detect Linux/macOS/Windows). This sed invocation will fail silently or destructively on macOS. Either gate on `[[ "$(uname -s)" == "Linux" ]]` or rewrite using Python/awk for portability.
- **#2411 issue title contradicts the plan's characterization as "7-repo audit"** (plan §Documents consulted, line 34). The issue's actual title is "feat(release-readiness): tier-1 provider entrypoint and parity surface inventory" — the 7-repo audit is a *comment* deliverable that satisfies that issue, not the issue itself. Re-cite as "#2411 audit comment ([issuecomment-4467824635](...))" without conflating issue and comment scope.
- **Pseudocode `^>>>>>>> ` trailing-space requirement misses git's lower-bound** (plan §Pseudocode line 179, §Acceptance Criteria 3). Plan claims "git always writes that form" (with trailing space). True for the standard merge writer, but `recursive`/`diff3` styles, custom merge drivers (`git config merge.<driver>.recursive`), and external tools can emit `<<<<<<<\n` with no trailing space when the ref name is empty or when output is generated mechanically. False-negative consequences listed in §Risks acknowledge a "stray `=======`" case but not the "no trailing space" case. Either weaken the anchor to `^<<<<<<<\b` / `^>>>>>>>\b` or document why this risk is accepted.
- **`docs/governance/**` pattern semantics undefined** (plan §Pseudocode line 172). `matches pattern "docs/governance/**"` reads as a glob but the script is bash. `[[ "$file" == docs/governance/* ]]` (single `*`) matches one level; `**` requires `shopt -s globstar`. Pseudocode should disambiguate; otherwise implementer guesses and gets either too-broad or too-narrow scope.
- **Cadence-helper "pattern lifted" comparison overstated** (plan §Pseudocode line 238). The cadence-helper sync at `install-hooks.sh:158-178` is a `cat >> pre-push` append for installation + a separate `sync-cadence-helper.sh` byte-compare. The plan's drift-check pseudocode uses `sha256` comparison — that is *similar in spirit* but is NOT the same idiom. Either inspect `scripts/sync/sync-cadence-helper.sh` and adopt its actual mechanism (likely `cmp -s` or `diff -q`, not sha256) or drop the "lifted from" wording, which falsely implies a verified-to-work pattern.
- **`docs/plans/README.md` row addition is named but not specified** (plan §Artifact Map line 137, §Files to Change). No format, no column ordering. README rows typically have a strict shape; the implementer must guess. Either pin the row format or remove the "Update" entry.
- **Acceptance criterion 12 ("hook installed on ≥2 sibling repos") is unverifiable from inside this plan** (line ~343). Sibling repos are git-independent — there's no way for a workspace-hub CI/test to attest the install state of `digitalmodel/.git/hooks/pre-commit` without writing to those repos. The criterion needs an explicit verification command (e.g., `bash check-pre-commit-hook-drift.sh && grep -q "check-no-conflict-markers" $sibling/.git/hooks/pre-commit`) or it becomes self-attestation.
- **No mention of how the new hook interacts with the existing dead-code state** (plan §Resource Intelligence Summary line 22 identifies it; §Install-hooks.sh wiring lines 268-280 patches around it but does not remove it). The plan correctly notes the state-file size guard at `.git/hooks/pre-commit:51-54` is dead code, but the wiring block inserts BEFORE `exit 0` without removing the dead code below. This is fine for the marker check, but leaves the state-file size guard broken — an in-scope cleanup the plan should either commit to OR explicitly defer with citation.

### gemini

- **Self-blocking plan file.** Plan §Pseudocode (`check-no-conflict-markers.sh`) exempts `docs/governance/**`, but this plan itself is located at `docs/plans/2026-05-16-issue-2722-pre-commit-conflict-marker-hook.md` and contains bare `<<<<<<< ` strings in its own pseudocode blocks. The hook will block the commit adding this very plan, as it is not covered by the whitelist pattern or the self-exclude rule.
- **Worktree incompatibility (Detection).** Plan §Pseudocode (`check-no-conflict-markers.sh`) checks for active merges using `exists .git/MERGE_MSG OR .git/REBASE_HEAD`. In git worktrees, `.git` is a file containing a reference pointer, not a directory. The check for `.git/MERGE_MSG` will fail, causing the hook to incorrectly block legitimate merge resolution commits inside worktrees. It must resolve the git directory via `git rev-parse --git-dir`.
- **Working-tree state leakage.** Plan §Pseudocode (`check-no-conflict-markers.sh`) evaluates the forensic whitelist by running `grep -q "<!-- CONFLICT_MARKER_FORENSIC_OK -->" "$file"`. This reads the unstaged file from the working tree. If a user adds the sentinel but forgets to stage it, the hook will read the working tree, see the sentinel, and improperly allow the commit of unresolved markers without the sentinel included in the commit. It must evaluate the staged blob via `git show :"$file"`.
- **False positive on nested blockquotes.** Plan §Pseudocode (`check-no-conflict-markers.sh`) triggers a violation if `lines_lt is non-empty OR lines_gt is non-empty`. The claim "require co-occurrence with either anchor" is violated by the `OR` condition. The anchor `^>>>>>>> ` is valid Markdown syntax for deeply nested blockquotes (7 levels). Because it does not strictly require co-occurrence with `<<<<<<< `, this logic will incorrectly block valid markdown files.
- **Undefined `$REPO_ROOT` in minimal stub.** Plan §Pseudocode (`install-pre-commit-hook-cross-repo.sh`) states `if not exists PRE_COMMIT: create minimal stub`, and then immediately appends a block executing `bash "$REPO_ROOT/scripts/enforcement/check-no-conflict-markers.sh"`. Because a newly created minimal stub does not define `$REPO_ROOT`, the path will evaluate to `/scripts/enforcement/...` and fail to execute.
- **Worktree incompatibility (Installer).** Plan §Pseudocode (`install-pre-commit-hook-cross-repo.sh`) defines the hook target as `PRE_COMMIT = "$REPO_PATH/.git/hooks/pre-commit"`. In git worktrees, `.git` is a file and the `.git/hooks` directory does not exist. The installer will fail to wire the hook for sibling repos checked out as worktrees. It must determine the hooks directory via `git -C "$REPO_PATH" rev-parse --git-common-dir` or `--git-dir`.
- **Invalid hashing command.** Plan §Pseudocode (`check-pre-commit-hook-drift.sh`) generates hashes using `CANONICAL_SHA = sha256(CANONICAL)`. The command `sha256` does not natively exist on standard Linux or macOS systems (the standard is `sha256sum` or `shasum -a 256`), which will cause the drift check to fail unconditionally.
- **Unsafe space handling in filenames.** Plan §Pseudocode (`check-no-conflict-markers.sh`) iterates over staged files with `for file in STAGED`. If `STAGED` is expanded in bash natively, word-splitting will break filenames containing spaces into invalid partial paths, causing `git show` to fail or evaluate the wrong files. Iteration must use a `while IFS= read -r` loop or `git diff -z`.
