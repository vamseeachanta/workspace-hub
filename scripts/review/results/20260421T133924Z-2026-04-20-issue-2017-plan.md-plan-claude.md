### Verdict: MAJOR

### Summary
A mature, thoroughly-reviewed plan (v9 after 8 adversarial rounds) with strong scope fencing, clear ownership split across #2017/#2024/#2026, and comprehensive TDD coverage. However, two specific v9 changes introduce plausible correctness regressions: (1) dropping `ts_utc` from the dedup key can suppress legitimate repeat transitions after reactivation cycles, and (2) the module-level `pytest.importorskip` shim conflicts with the acceptance gate that requires state-machine tests to appear as XFAIL (not SKIPPED) under `--runxfail`. Both should be resolved before plan-approval.

### Issues Found
- [P2] Dedup key correctness regression (v9 §D1 Idempotency + `test_transition_retry_preserves_dedup_under_fresh_ts`): the new log dedup key `(account_id, thread_id, from_state, to_state)` — with `ts_utc` dropped — cannot distinguish legitimate repeat transitions from retries. A thread can legitimately traverse `extracted → completed` multiple times across the state machine (e.g., completed → reactivated → extracted → completed again after purge-reactivation, or via the awaiting-reply loop). Under v9 dedup, the second legitimate `extracted → completed` would be silently dropped, corrupting snapshot replay. Consider adding a reactivation-cycle counter or sequence number to the key.
- [P2] Module-level `pytest.importorskip` conflicts with the xfail acceptance gate (v9 §TDD import-shim plumbing): `pytest.importorskip('scripts.email.queue_state')` at module level produces SKIPPED tests when the module is missing, not XFAIL. The acceptance criterion explicitly requires `uv run pytest tests/email/ --runxfail` to list these tests as failing (xfail), but `--runxfail` doesn't affect skipped tests. The shim and the gate are mutually incompatible. Fix: move the import inside each test (or use a fixture) so `@pytest.mark.xfail` catches the ImportError directly — pytest's xfail catches any exception by default.
- [P3] `writer_identity.boot_id` cross-platform specification gap (§D1): the schema pins `boot_id: str` but Linux derives this from `/proc/sys/kernel/random/boot_id` while macOS has no canonical equivalent (typical workarounds: `sysctl kern.boottime` parse, `ioreg` UUID, or synthesize from uptime). Plan should specify the cross-platform derivation or explicitly declare Linux-only scope. Otherwise, CI runs on non-Linux hosts will produce inconsistent or empty `boot_id`.
- [P3] `test_letstok_no_false_positive_on_corpus` statistical weakness: passing on ≥10 fixtures provides weak evidence against false positives in production. Either raise the threshold (≥50-100), document the accepted FP-rate boundary, or reframe as a regression gate rather than correctness proof.
- [P3] Fixture-redaction regex `[\w.]+@[\w.]+\.\w+` misses RFC 5321-valid local-parts containing `-`, `+`, `!`, `%`, etc. Real PII with e.g. `first.last+tag@domain.com` or `support-team@domain.com` would pass the hook undetected. The allowlist check also doesn't specify subdomain handling (does `news.aceengineer.com` match allowlist entry `aceengineer.com`?).

### Suggestions
- Add a `cycle_id` or reactivation counter field to queue-state.jsonl entries. This cleanly separates retry-dedup (same cycle, same transition = dedup) from legitimate repeat transitions across reactivation cycles (different cycle = new entry). It also makes the quarterly learning review more informative — FP override patterns can be correlated with cycles.
- Replace module-level `importorskip` with a pytest fixture or per-test import: either `@pytest.fixture def queue_state(): return importlib.import_module('scripts.email.queue_state')` and let xfail tests consume it (ImportError → XFAIL), or import inside each test body under the `@pytest.mark.xfail` decorator. This satisfies the acceptance gate cleanly.
- Specify an explicit platform-compatibility matrix for `writer_identity.boot_id` — either (a) Linux-only v1 with an explicit gate (`pytest.skip` on non-Linux), or (b) a documented fallback hierarchy (Linux boot_id → macOS kern.boottime → synthesized UUID persisted at `.locks/instance-id`).
- Add a `test_transition_distinguishes_reactivation_cycles` test to pin the dedup-vs-legitimate-repeat boundary concretely. This will catch regressions on any future dedup-key refactor.
- For the fixture-redaction hook, use a well-tested email regex (e.g., the one from `validate_email` or similar) rather than `[\w.]+@[\w.]+\.\w+`. Add explicit tests for edge cases: `+tag` addresses, `-` in local-part, subdomain allowlist matching semantics.
- Consider pinning the `time.sleep(10ms)` between sweep chunks with a rationale (why 10ms, not 1ms or 100ms?) or make it configurable. A test proving that inbound processing CAN interleave during sweep's yield window would strengthen the concurrency claim more than the current `test_sweep_chunks_at_batch_cap`, which only verifies the chunk boundary.
- Document the user-facing trigger mechanism for `spam_false_positive_override`. The plan describes the log entry format but not how the user signals reclassification — CLI command? Gmail label? Manual edit? This gap affects #2024's pipeline design.

### Questions for Author
- After reactivation, a thread can legitimately traverse `extracted → completed` more than once. With v9's dedup key `(account_id, thread_id, from_state, to_state)`, how does the system distinguish the second legitimate completion from a retry of the first?
- The acceptance criterion requires `uv run pytest tests/email/ --runxfail` to list state-machine tests as failing. If `pytest.importorskip` skips the entire module when `queue_state.py` is absent at #2017 commit, won't those tests be reported as SKIPPED rather than XFAIL, failing this gate?
- How is `writer_identity.boot_id` derived on macOS/Windows CI runners? Is #2017 implicitly Linux-only, or is there a fallback specification?
- What is the user-facing interface for reclassifying a spam-matched message? A CLI command on queue-learning-log.jsonl? A Gmail label the pipeline polls? Manual JSONL append? The override path is specified end-to-end in the log-format sense but the trigger boundary is unspecified.
- When a Letstok rule is tightened due to quarterly-review FP analysis, is there a mechanism to re-evaluate historical messages that were spam-classified under the old rule? Or is the rule change strictly forward-looking?
- The `test_snapshot_rebuild_double_checked` test uses `multiprocessing` because `fcntl.LOCK_EX` is process-level. On macOS with `spawn` start method vs Linux with `fork`, are there expected behavioral differences, and has the test been verified on both? If CI runs only on Linux, that should be an explicit test gate.
- The scope fence says `gmail-archive-extract.py` is grandfathered, but the synthetic DELETE path in D6 v9 explicitly adds a NEW routing action injection point (pipeline decides effective_action when sender is unmapped). Doesn't this constitute a new mutation point of the routing logic, even if the downstream Gmail action is grandfathered? Is there a test that pins the grandfathered archive-script's behavior given a synthetic DELETE?
