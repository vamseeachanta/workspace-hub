### Verdict: MAJOR

### Summary
The plan has multiple blocking correctness gaps: several live-state claims are unverified or internally inconsistent, the proposed fallback preserves the original buggy argv path, and acceptance criteria do not fully satisfy the mandatory TDD coverage requirement for exit-code behavior. As written, the plan cannot be approved without tightening dependency verification, removing the unsafe fallback, and adding missing tests for stated invariants.

### Issues Found
- [P1] blocking: the plan leaves correctness-critical dependency claims unverified. In `Resource Intelligence Summary -> Evidence (embedded verification)` it asserts live GitHub states such as `#2406 — OPEN`, `#2405 — CLOSED`, `#2403 — OPEN`, and `#2402 — OPEN`, but no durable artifact, command transcript, or repo-tracked evidence is cited beyond prose; under the review contract, issue-number/status claims must be verified, not narrated.
- [P1] blocking: the proposed `runtime codex-version compatibility probe` in `Pseudocode` explicitly falls back to the old argv path: `fall back to the old argv path and log a one-time WARN`. That reintroduces the exact mechanism identified earlier in `Resource Intelligence Summary` as the bug (`codex exec "$prompt_text"` on argv), so the stated deliverable of `reliably dispatches any prompt ... without hanging on stdin` is not true for older installs.
- [P1] blocking: TDD coverage is incomplete for declared acceptance criteria. In `Acceptance Criteria ↔ Test Traceability`, the plan states `Exit-code semantics for 3/5/6 paths preserved ... manual spot-check (closeout)`, while `Acceptance Criteria` says those semantics are preserved. That is a correctness claim about behavior, but it has no automated tests and only a vague manual check, violating the requirement that every acceptance criterion have corresponding test coverage for failure modes.
- [P1] blocking: `Files to Change` says `Update | docs/plans/README.md | add index row for #2406 (already landed in v1 commit a73ec66f6)`. If the change is already landed, this is not a pending file change; if it is not landed in current repo state, the plan depends on an external commit not otherwise declared as a dependency. Either way, the dependency state is not executable as written against current repo state.
- [P1] blocking: the plan claims operating-model compliance but does not verify the cited authority. In `Operating-model compliance (explicit N/A rationale)`, assertions such as `§2 ownership ... No`, `§3 identity ... No`, and `§4 flow rules ... No` are unsupported by citations to the actual operating-model source file/section. Given the mandatory checks, these are assertions about policy scope, not verified facts.
- [P2] risky: `Resource Intelligence Summary` claims `Found: tests/review/test-submit-scripts.sh (320 lines)` and `Existing test-case count: 22`, but the artifact map and TDD plan later rely on adding `T26/T27/T28/T29/T30`. The numbering implies prior existence through T25, which conflicts with the stated count of 22 and leaves the current numbering scheme ambiguous.
- [P2] risky: the plan treats `Issue #2405 ... related context, not a dependency` in `Documents consulted`, but the manual acceptance criterion later requires a live repro against `docs/plans/2026-04-20-issue-2405-cross-review-sandbox-repo-access.md`. That makes #2405 plan availability a practical dependency for closeout, contradicting the earlier non-dependency claim.
- [P2] risky: in `T27`, the expected output is `stdin equals the constructed FULL_PROMPT exactly`, but the table also says `ignoring trailing newline`. That weakens the byte-for-byte guarantee the plan relies on to prove transport fidelity; the acceptance condition is underspecified for a newline-sensitive prompt channel.
- [P2] risky: the threat model in `Risks and Open Questions -> Threat model` claims `Argv exposure ... Improvement` and `stdin pipe content ... eliminated`, but if T30 fallback is exercised the prompt returns to argv exposure and the old dispatch shape. The security analysis therefore does not match the proposed implementation under all branches.
- [P2] risky: `Resource Intelligence Summary -> Existing repo code` asserts that fixing `run_codex_exec()` fixes both initial and retry paths because both call the same function, but `Pseudocode` adds probe logic and PIPESTATUS handling inside that function without showing how per-call state is isolated across first call and retry. The interaction between one-shot probe caching and retry behavior is not specified or tested.

### Suggestions
- Replace the version-probe fallback with a hard failure or explicit unsupported-version exit code; do not route older installs back through the known-buggy argv path if the deliverable claims reliability.
- Add automated tests for every stated exit-code invariant, especially the preserved `3/5/6` paths; remove the manual-only exemption for correctness-critical behavior.
- Resolve the `docs/plans/README.md` state ambiguity: either mark it as already complete and remove it from `Files to Change`, or declare the missing upstream commit as a hard dependency and verify its presence before approval.
- Cite the actual operating-model source file and section for each claimed N/A determination, or remove the compliance claims until they are backed by concrete references.
- Tighten dependency statements around #2405: if the live repro and referenced plan file are needed for closeout, declare that explicitly as a soft or hard dependency instead of calling it non-dependent.
- Make T27 newline handling strict and explicit. Either require exact byte equality including newline semantics or define a normalized construction rule and test that exact normalization.
- Document and test the probe-cache behavior across both first dispatch and compact retry so the retry path cannot silently diverge from the initial dispatch logic.
- Provide repo-tracked evidence for issue statuses and file existence claims, or downgrade those statements to unverified assumptions and exclude them from approval criteria.
