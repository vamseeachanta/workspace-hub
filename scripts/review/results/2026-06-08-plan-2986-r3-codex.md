## Findings
1. `docs/plans/2026-06-09-issue-2986-cron-uv-resolution.md` lines 187-191 sources `scripts/lib/uv-env.sh` and `scripts/lib/uv-resolver.sh` before computing `SCRIPT_DIR` or `REPO_ROOT`. That makes the revised direct entrypoint still cwd-sensitive: `source scripts/lib/uv-env.sh` works only when the caller is already at repo root. Existing `scripts/skills/validate-skills.sh` lines 5-6 currently computes `SCRIPT_DIR` and `REPO_ROOT` before path-sensitive work, so the plan regresses the wrapper’s location-independent script resolution unless it explicitly sources via `"$REPO_ROOT/scripts/lib/..."` or a path derived from `SCRIPT_DIR`.

2. `docs/plans/2026-06-09-issue-2986-cron-uv-resolution.md` lines 176-177 uses `"$HOME/.local/bin/uv"` / `"$HOME/.cargo/bin/uv"` and only says to skip when `HOME` is empty. Under `set -u`, an unset `HOME` aborts before the skip logic can run; I verified `env -i PATH=/usr/bin:/bin bash -c 'set -u; for candidate in "$HOME/.local/bin/uv" ...'` fails with `HOME: unbound variable`. The current validator returns exit 2 under `env -i PATH=/usr/bin:/bin`; the proposed resolver can become a shell crash unless the plan requires `${HOME:-}` handling and an unset-`HOME` test, not just an empty-`HOME` test.

3. `docs/plans/2026-06-09-issue-2986-cron-uv-resolution.md` lines 245-246 acceptance commands rely on `uv` being on the caller’s `PATH`. The issue is specifically about cron/direct callers with minimal PATH and `uv` discovery, yet the test commands do not exercise the new `UV_BIN` or common-path fallback for running the test suite itself. That is not fatal for implementation, but it leaves the primary verification path dependent on the same ambient condition the plan is trying to harden.

## Blockers
- Finding 1: fix the pseudocode ordering/pathing so sourced libraries are resolved from `SCRIPT_DIR`/`REPO_ROOT`, not caller cwd.
- Finding 2: require unset-`HOME` safety under `set -u` and add/adjust a test or acceptance probe for it.
