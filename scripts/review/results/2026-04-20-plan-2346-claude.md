## Findings

### MAJOR M1 — Gating mechanism is hand-waved; website repo has no disallow/noindex plumbing

- **Evidence:** Plan line 118 promises "Crawler-blocked via `robots.txt` + `X-Robots-Tag: noindex, nofollow`." Current `aceengineer-website/robots.txt` lines 1-2 read `User-agent: *` / `Allow: /` (no disallow for `/prospects/`). Current `aceengineer-website/vercel.json` headers (lines 20-46) set only `X-Content-Type-Options`, `X-Frame-Options`, `X-XSS-Protection` — no `X-Robots-Tag`. There is no `/prospects/` directory. `vercel.json` line 3: `"public": true`. No basic-auth mechanism (no `netlify.toml`, no `_headers`, no edge middleware). The "Gating mechanism" comparison table at plan lines 117-121 asserts "Low complexity — static file publish, no auth server" for hash-URL — but the as-written deployment would index the file publicly.
- **Severity:** MAJOR. This is the security contract for NDA-bearing prospect data. "Gated" without any of the three mechanisms actually wired up = the gated URL is public.
- **Recommendation:** Add to Files-to-Change:
  - `Modify aceengineer-website/robots.txt` — add `Disallow: /prospects/`
  - `Modify aceengineer-website/vercel.json` — add `headers` entry for `source: /prospects/(.*)` with `X-Robots-Tag: noindex, nofollow`
  - Add acceptance criterion: `curl -I https://aceengineer.com/prospects/<hash>/index.html` returns `X-Robots-Tag: noindex, nofollow`.
  - Add acceptance criterion: unit test verifying `robots.txt` contains `Disallow: /prospects/`.
  - Acknowledge that if the website is cloned/forked/mirrored, the gated dir IS indexable there — list this as residual risk.

### MAJOR M2 — JSON-Schema `not: {required: ["vessel"]}` does NOT forbid a property; Q6 "FORBIDDEN for demos 1/2" is not actually expressed

- **Evidence:** Plan lines 186-189 propose:
  ```
  - if:   target_demo enum [demo_01, demo_02]
    then: { not: { required: ["vessel"] } }
  ```
  In JSON-Schema draft-07, `not: { required: ["vessel"] }` is satisfied when `vessel` is absent OR any OTHER non-vessel-required constraint fails. More critically: `required` does not mean "must be present" in the "schema rejects if present" sense; `not required` does NOT prohibit presence. To actually FORBID the `vessel` key on demos 01/02 the schema must use `properties: { vessel: false }` or `not: { properties: { vessel: {} }, required: [vessel] }` with additionalProperties logic, or the cleanest form: a `propertyNames` or an `allOf` branch that sets `properties: { vessel: { type: "null" } }` combined with an absent constraint.
  The plan's snippet will accept an intake that has `target_demo: demo_01` AND a `vessel:` block — the exact case Q6 says must be refused (and acceptance criterion line 456 promises will be rejected).
- **Severity:** MAJOR. This is the central Q6 contract from the user's answer. The test on line 440 (`test_e2e_demo_01_with_stray_vessel_rejected`) will pass only by coincidence (caught by the `assert "vessel" not in intake` guard at plan line 235), NOT by the schema. That means the schema does not enforce what the plan says it enforces, and the defense-in-depth the plan claims at line 234 is actually single-line-of-defense.
- **Recommendation:** Rewrite the `allOf` branch using one of:
  - `then: { properties: { vessel: false } }` (draft-07 supports `{property: false}` meaning "this property is forbidden"), OR
  - `then: { not: { type: "object", required: ["vessel"] } }` + `additionalProperties: false` at root (requires enumerating every other allowed property), OR
  - Move the forbid-logic into a top-level `oneOf` over a demo-specific schema set (cleaner: one schema per demo).
  Pick one and update the pseudocode at line 184-193. Then the Python `assert` becomes true defense-in-depth, not the primary gate.

### MAJOR M3 — Cross-plan collision with #2342/#2343 is likely but unanalyzed

- **Evidence:** Plan line 62 says the prospect pipeline "can be rendered as a one-off derivative page on the same template." #2342/#2343 is status `plan-approved` (per the 2026-04-19 self-approval noted in plan). ### MINOR m2 — Fallback matrix has at least two under-specified rows

Similarly row "Numerical failure": `F2 ALLOWED (if pre-auth AND root cause is vessel)` — but there's no protocol for determining "root cause is vessel" inside a NaN-at-solver-blowup.
