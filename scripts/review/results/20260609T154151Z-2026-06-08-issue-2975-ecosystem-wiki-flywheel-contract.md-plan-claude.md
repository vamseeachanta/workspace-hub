### Verdict: MAJOR

### Summary
A genuinely strong, deeply-iterated T3 contract plan that composes (rather than forks) existing manifest/report/wiki-routing schemas, fails closed by default, and ships a TDD-first validator with a clear MVP boundary. It is not yet APPROVE-clean: the publication-state classifier omits the worldenergydata-wiki public-federal output residency that its own flagship BSEE fixture targets, the public-projection allowlist checks key names but not value-level leakage (e.g. private tokens embedded in run_id), and at least one acceptance criterion (staged publishing order) has no backing test.

### Issues Found
- [P2] Output-residency gap in publication-state classifier: classify_publication_state() (pseudocode lines 345-371) branches only on `public_llm_wiki`, `private_llm_wiki`, and `private_client_wiki`. But the flagship `valid-public-bsee/` fixture (line 244) and AC line 597 ('public BSEE/federal first') target public federal data, which per `.claude/rules/codes-standards-data-routing.md` §6 and `wiki-sibling-routing.md` routes to the separate `worldenergydata-wiki` repo with `visibility: public-federal-data`. There is no `public_federal_wiki`/worldenergydata output residency in the classifier. Either the BSEE path is silently treated as `public_llm_wiki` (wrong repo/visibility semantics) or it falls through to `blocked`. This is the primary staged-publishing target and must be modeled explicitly.
- [P2] Public-projection allowlist is key-scoped, not value-scoped: the projection schema (lines 377-389) and `test_public_projection_is_allowlist_only` reject forbidden KEYS (client, project, private URLs, paths), but `run_id` is an allowed public key described only as 'Public-safe run identity' with no validator check that its VALUE does not embed a client slug, project slug, or private issue number. Same concern applies to `event_id` and `destination`. Given the workspace's documented leak incidents (feedback_verify_subagent_firewall_claims), a value-level pattern check (deny-list scan over emitted string values) is needed, or the contract must constrain run_id/event_id construction to provably-public tokens.
- [P2] Acceptance criterion without a backing test: AC line 597 requires the staged publishing order to be 'encoded' (BSEE/federal first; FDAS after classification+citation; HSE/marine after segregation/redaction/legal). No blocking test or hardening test in the TDD list verifies ordering enforcement — `scheduler_state` enum exists but no test asserts the sequence. This is the AC/blocking-test mismatch class r4 flagged; it appears to persist for this AC. Either add a test or explicitly downgrade the AC to documentation-only.
- [P3] Self-blocking-safety test is not in the blocking floor: `test_self_artifacts_are_validator_safe` (line 496) and `test_invalid_fixtures_are_sentinel_scoped` (line 497) are in the inventory but excluded from the non-cuttable blocking subset (lines 517-551), while the workspace SOUL carries an explicit must-fire rule that 'Enforcement scripts must not block their own artifacts.' Even though #2975 ships manual-only (no hook), promoting at least the self-artifact safety test to blocking would harden the eventual hook follow-up and align with the rule.
- [P3] Fragile array-index source reference: the flywheel wrapper example uses `wrapped_source_ref_id: sources[0]` (line 327-332). An ordinal index into the report-evidence `sources[]` array breaks silently if source ordering changes between manifest generation and wrapper authoring. A stable per-source id (matching report-evidence-bundle source identity) is safer and should be the contract.

### Suggestions
- Add an explicit `public_federal_wiki` (worldenergydata-wiki) output-residency branch to classify_publication_state with its own public-safe gating, and add a blocking test that the valid-public-bsee fixture resolves to that residency with `visibility: public-federal-data` frontmatter — not to `public_llm_wiki`.
- Add a value-level deny-list/pattern scan over every string emitted into the public ledger projection (run_id, event_id, destination, freshness) so embedded client/project/issue tokens fail closed, and extend `test_public_projection_is_allowlist_only` with a fixture whose run_id embeds a client slug.
- Either add a `test_staged_publishing_order_encoded` test (asserting the BSEE→FDAS→HSE ordering and its preconditions are machine-checkable in the standard's fenced block) or rewrite AC line 597 to state the order is documentation-only and not validator-enforced in #2975.
- Specify the fenced machine-readable enum block format in the standard (YAML vs JSON inside the fence) so `test_standard_enum_table_matches_config` has an unambiguous parse target rather than deferring the format entirely to test-authoring time.
- Replace `sources[0]`-style ordinal references in the wrapper with stable source identifiers and add a test that a reordered sources[] array does not silently re-bind a wrapper to the wrong source.

### Questions for Author
- What output_residency value does a BSEE/federal-data public bundle carry, and does the validator route it to worldenergydata-wiki (public-federal-data) rather than the llm-wiki pointer/index layer? The classifier pseudocode does not show this path.
- How is `run_id` guaranteed public-safe at the value level — is there a construction rule or a deny-list scan, or is it assumed safe by convention?
- Is the staged-publishing order (BSEE→FDAS→HSE) intended to be machine-enforced in #2975, or is it standard-documentation only? The AC says 'encoded' but no test covers it.
- Given the validator already carries 35 blocking tests across many policy surfaces, would splitting the legal-scan attestation surface (or the projection-allowlist surface) into its own follow-up issue reduce review risk without weakening public-output gating?
- Since this is the r6 submission after five MAJOR rounds, is there a specific prior-round finding you consider still open that you want this review to adjudicate, versus net-new findings?
