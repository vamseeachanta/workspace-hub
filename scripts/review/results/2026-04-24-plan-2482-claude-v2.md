## Findings

### MAJOR

1. **MAJOR 5 partial repeat — `data/document-index/` leakage surface still unscoped.** v1 MAJOR 5 explicitly called out "`data/document-index/conference-*` — registry/manifests referencing licensed conference papers; a doc-index → wiki → GTM chain is the primary leakage path not just wiki → GTM." v2 claims to have addressed v1 MAJOR 5 (see v2 line 28), but only expands wiki-adjacent surfaces (dark-intelligence, seeds, health-reports, .planning/research). The registry surface remains out of scope. Verification: `data/document-index/conference-registry.yaml` contains `total_files: 27735, total_collections: 30` with per-collection file counts keyed to the exact 30 publisher collections the plan's own deny-list now enumerates (SPE, OMAE, OTC, NACE, ISOPE, …). An allow-list promotion path that reads from document-index manifests can bypass the entire wiki boundary. Either explicitly scope `data/document-index/` and `data/llm-wiki` (symlink to external digitalmodel llm-wiki source) into the deny-list, or explicitly out-of-scope them with a rationale. Dismissing this twice after v1 flagged it is the repeat-MAJOR.

2. **`knowledge/wikis/engineering/wiki/overview.md` is the allow-eligible exemplar but has NO YAML frontmatter.** Plan classification exercise #2 expects the linter to return `exit 2 (allow-eligible, sanitization required)`. The linter logic (line 192) says `read frontmatter` and the risk section line 287 says `linter treats missing frontmatter as deny (conservative default)`. Actual file begins with `# Overview: Engineering Wiki` — no `---` delimiters anywhere. Under the conservative default, the overview page would be **denied**, not allow-eligible, contradicting the classification exercise. This is a spec bug: either the overview page must be re-tagged with frontmatter before the linter lands, or the conservative-default rule must carve an exception for `overview.md`-style scope-bounding pages, or the expected classification in exercise #2 is wrong. Any of those three is a plan change; silence is a linter-vs-exercise contradiction that fails the acceptance criterion "`check-gtm-boundary.sh` exists and correctly classifies all 6 exercise pages." The engineering wiki CLAUDE.md mandates frontmatter as required, so the overview being non-compliant is itself a wiki-hygiene gap this plan should surface.

### MINOR

1. **Publisher name cosmetic drift — "Unlocking Deepwater Potential – Mumbai".** Plan line 98 spells "Unlocking Deepwater Potential – Mumbai" with an en-dash. Live frontmatter value is "Unlocking Deepwarter Potential- Mumbai" (typo "Deepwarter" preserved from source data, hyphen not en-dash). If the linter matches `frontmatter.collection` exactly against a canonical list, the respelled name would fail to match the real value. Fix: either quote the raw string verbatim (including typo) or state the linter uses a normalized/case-insensitive publisher match.

2. **Quarantine archive convention `knowledge/_archive/` is invented; plan does not state directory creation.** `ls knowledge/` returns `dark-intelligence/, seeds/, wikis/` — no `_archive/`. Sibling `_archive/` directories exist elsewhere (`./_archive`, `./scripts/_archive`, `./worldenergydata/_archive`, `./CAD-DEVELOPMENTS/_archive`, `./.claude/skills/_archive`), so the naming convention is consistent with repo norms, but the target path inside `knowledge/` is new. Files-to-Change line 227 writes the Move target as `knowledge/_archive/...` without an explicit `mkdir` step or `README.md` explaining the archive's scope. Add an explicit create-directory line and a one-paragraph README to prevent the archive from becoming an opaque dumping ground.

3. **Allow-list line 149 — "Methodology explainers for public-domain or fair-use standards (ASCE, API public RPs, ISO general-audience material)" contradicts deny-list line 160 when the methodology page is itself ingested under `knowledge/wikis/*/wiki/sources/`.** `engineering/wiki/standards/dnv-rp-c203.md` (and siblings) live under `standards/`, not `sources/`, so are not blanket-denied. But if a methodology explainer lands in `knowledge/wikis/marine-engineering/wiki/sources/` (where `001.md` today is a publisher-derivative), the deny-list wins and the allow-list intent is overridden. The plan should explicitly state that allow-list eligibility is evaluated on `standards/` and `concepts/` paths only, and that `sources/` is always deny regardless of content. Without that rule precedence, two reviewers applying the same doc can disagree.

4. **Acceptance criterion "correctly classifies all 6 exercise pages (verified by `bash -x` invocation)" is not fully mechanical while the linter allows an escape hatch.** Linter step (line 198) says "if page passes above: exit 2 (allow-eligible, sanitization required)"; step (line 199) says "allow-eligible paths with all sanitization boxes ticked: exit 0". The "with all sanitization boxes ticked" clause is not yet mechanical — sanitization steps 1, 2, 4 are human-judgment operations (strip client identifiers, generalize numerics, attribution footer). The linter cannot actually return exit 0 without a ledger check. State clearly that exit 0 requires consulting `gtm-publish-ledger.yaml` for a recorded signoff, otherwise the linter's third branch is aspirational.

5. **Top-level `knowledge/wikis/cross-links.md` is in scope by proximity but unmentioned.** This is a cross-wiki registry file sitting at the root of `knowledge/wikis/` (outside any domain subtree). It would not be reached by a directory-rooted deny-list pattern like `knowledge/wikis/*/wiki/sources/`. Explicitly say whether top-of-tree wiki registry files (cross-links.md, per-wiki CLAUDE.md, per-wiki SCHEMA.md, per-wiki SOURCE_INVENTORY.md) are allow / deny / not-in-scope; silent defaults are a gap.
