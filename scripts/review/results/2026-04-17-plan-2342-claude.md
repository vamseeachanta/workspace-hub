The plan gets the low-level mechanics mostly right (file counts, line numbers, demo-card positions, jumper-installation.html frontmatter pattern) but is built on an **incorrect deployment model** (GitHub Pages vs. Vercel) and omits several production-visible artifacts (sitemap.xml, head-common include for analytics/nav parity, title rewriting). ## Findings

### Defect 1 — Deployment target is Vercel, not GitHub Pages
**Severity:** blocker
**Evidence:**
- Plan line 36: *"No `.github/workflows/` dir. Deploy is GitHub Pages on push to main with `dist/` served."*
- Repo has a `vercel.json` with `"buildCommand": "npm run build"` and `"outputDirectory": "dist"`, plus host-based redirects from `aceengineer.com` → `www.aceengineer.com`.
- `.github/workflows/` directory EXISTS but is empty (plan's wording "No .github/workflows/ dir" is literally wrong; `ls` returns the dir).
- `dist/` is **gitignored** (`.gitignore` line 2: `dist/`) and `git ls-files dist/` returns zero entries.
**Impact:** The Artifact Map lists `dist/demos/*` and `dist/demos/index.html` as commitable artifacts and instructs "Commit aceengineer-website/" as the deploy trigger. This is wrong in two ways:
  (a) `dist/` contents will not be committed (ignored) — no point regenerating them.
  (b) The trigger is Vercel's git-integration build on push, not GitHub Pages serving pre-built `dist/`.
**Recommendation:** Rewrite the Resource Intelligence paragraph. Drop all "dist/" rows from the Artifact Map and Files to Change. State the deploy mechanism is Vercel (`vercel.json`), which runs `npm run build` on each push and serves `dist/` it produces. Clarify that `node build.js` locally is only for **local verification**, not for committing dist/.

### Defect 2 — New pages will have no analytics, nav, or site CSS (parity gap)
**Severity:** major
**Evidence:**
- `content/partials/head-common.html` contains the Google Analytics config (`G-K31E51DQ47`), favicon, and `assets/css/styles.min.css` link.
- `jumper-installation.html` (the "reference pattern" the plan copies) does NOT `<include>` head-common — it ships with only inline `<style>`, no GA, no navbar.
- Plan treats this as an "Open question" (line 180) and also proposes publishing verbatim (pseudocode step 2 in workstream A), which would continue the gap for 4 more pages.
**Impact:** GTM campaign landing pages with no GA tracking defeat the plan's own purpose (per `docs/gtm/gtm-plan-30day.md` references). Users landing from cold emails hit a page with no nav bar back to the site — high bounce.
**Recommendation:** The "open" question about head-common parity is NOT safe to defer. The plan must commit to including `<include src="partials/head-common.html"></include>` in all 4 new pages BEFORE first deploy, and retrofit `jumper-installation.html` as part of the same change (single "fix analytics gap on detail pages" atomic commit). Otherwise every cold-email click is an untracked landing.

### Defect 3 — Source reports' `<title>` tags do not match plan's promised branding
**Severity:** major
**Evidence:**
- Plan pseudocode line 84: *"ensure `<title>` tag reads 'A&CE — `<Demo Title>`' for brand consistency"*
- Actual source `demo_01_freespan_report.html` line 6: `<title>DNV Freespan / VIV Screening Analysis — digitalmodel</title>`
- Plan also says "copy remainder of source verbatim" (line 86) — these two directives contradict: "verbatim" and "ensure title reads X" are incompatible when the source title is different.
**Impact:** Whichever directive the implementer follows, the other fails. Acceptance criterion `local_dist_titles_match_source` (line 131) literally says "Each dist page `<title>` matches 'A&CE — `<Demo Title>`'" but that test name contradicts itself ("match source" vs. hardcoded prefix).
**Recommendation:** Resolve the verbatim vs. rebrand contradiction. Either (a) rewrite `<title>` in each new page and drop "verbatim" language, or (b) accept source titles and drop the A&CE prefix promise. Rename the test to something unambiguous.

### Defect 4 — sitemap.xml omission
**Severity:** major
**Evidence:**
- `sitemap.xml` is hand-maintained and has zero entries for any `demos/` page (not even the already-live `jumper-installation.html`).
- Plan touches 0 sitemap entries.
**Impact:** Four new pages invisible to search engines — undermines the GTM campaign's organic-discovery angle. The pre-existing absence of `jumper-installation.html` is a latent defect the plan fails to flag.
**Recommendation:** Add `sitemap.xml` to Files to Change. Add 5 `<url>` entries (4 new + 1 backfill for jumper). Add an acceptance criterion and test.

### Defect 5 — Link-check script not wired to CI or pre-commit
**Severity:** minor
**Evidence:**
- Plan proposes `aceengineer-website/scripts/check-demo-links.sh` as "regression guard" (line 118, 149).
- `.github/workflows/` is empty. No pre-commit config in `aceengineer-website/`. No mention of invoking this script from `package.json` test command or a hook.
- Acceptance criterion only says "exits 0 locally" — a one-time check, not a regression guard.
**Impact:** Write-only guard. Next time someone reshuffles card anchors, no one runs the script.
**Recommendation:** Wire into `package.json` scripts (e.g., `"test:links": "bash scripts/check-demo-links.sh"`) and add to the Jest test invocation OR add a GH Actions workflow that runs it on PR. Otherwise delete the script — it adds maintenance weight with no enforcement.

### Defect 6 — CSP / Plotly remote-CDN risk is acknowledged but unverified
**Severity:** minor
**Evidence:**
- Plan risk line 176: "verify CSP headers before deploy."
- `vercel.json` has a `headers` block (I saw the top of it); plan does not report whether a CSP exists or what it allows.
- Source reports load `https://cdn.plot.ly/plotly-2.32.0.min.js` — a specific version. Version pinning against CDN availability is its own risk the plan misses.
**Impact:** Detail pages could silently render without charts if CSP blocks cdn.plot.ly, or break when plotly-2.32.0 is removed from CDN.
**Recommendation:** Do a concrete CSP audit (read `vercel.json` headers section) and record findings in Resource Intelligence. Consider vendoring Plotly under `assets/js/` with a specific version — removes both CSP and CDN-availability risks in one shot.

### Defect 8 — 118 KB inline Plotly pages have no performance budget
**Severity:** minor
**Evidence:**
- Source demo 1 is 116 KB of HTML that includes inline Plotly JSON. Plus it fetches `plotly-2.32.0.min.js` (~3 MB uncompressed).
- `vercel.json` has immutable cache headers only for `/assets/(.*)` — demo detail HTML under `/demos/` gets no explicit caching policy in the snippet I saw.
**Impact:** Mobile users on flaky connections hit 3+ MB per page. GTM campaign click-to-bounce will spike.
**Recommendation:** At minimum, add a cache-control header rule for `/demos/*.html`. At best, lazy-load the Plotly script with `<script async>` and render a static fallback image above the fold. Treat as blocker for mobile GTM traffic, not as follow-up.

### Defect 9 — TDD test list skips two acceptance criteria
**Severity:** minor
**Evidence:**
- Acceptance criterion "`content/demos/*.html` exist with correct frontmatter and `<title>`" — no test checks frontmatter (`rootPath: "../"`) is correct. Missing frontmatter is a common build-breaker.
- Acceptance criterion "Browser validation: desktop + mobile, Plotly charts interactive" is `manual` only. Not reproducible; not a test.
- No test checks head-common include is present (ties to Defect 2).
**Recommendation:** Add `local_frontmatter_has_rootPath` (grep `^rootPath: "../"`). Add `local_pages_include_head_common` (grep for `<include src="partials/head-common.html"`). Replace "browser manual mobile" with a Playwright/Puppeteer check of Plotly chart presence, or explicitly note it as out-of-scope manual QA rather than a test.

### Defect 10 — No plan for the broken/missing `demos/` entry in sitemap vs. robots.txt
**Severity:** minor
**Evidence:**
- `robots.txt` exists in the repo. Plan does not check whether `/demos/` is disallowed.
- If robots disallows `/demos/`, deployed pages won't be indexed regardless of sitemap.
**Recommendation:** Verify `robots.txt` allows `/demos/*` and document in Resource Intelligence.

## Open design questions — my position

### Q1: "publish verbatim vs. strip to summary-style like jumper-installation.html"
**My position: NEITHER option is correct as written. Publish with head-common include.**

The plan frames this as a binary. Evidence shows a third option is required:
- "Verbatim" loses GA tracking (source reports have no GA).
- "Strip like jumper-installation.html" also loses GA (jumper has no GA).

Correct answer: publish the full Plotly-embedded source **plus** inject `<include src="partials/head-common.html"></include>` into `<head>`, and adjust `rootPath` frontmatter. This gives the rich report + site analytics/nav. Anything else sends GTM campaign traffic to pages that don't track. Do not defer this.

### Q2: Demo 2 CTA — keep calculator, add detail, or replace?
**My position: ADD detail CTA alongside calculator. Plan's current stance is correct here.**

Evidence: `content/calculators/wall-thickness.html` exists (23 KB, production-served). The calculator is valuable lead-capture. Removing it to add a detail-report button trades a proven CTA for an unproven one. Both fit in the same card (`.card-actions flex-direction: column` on mobile, line 242 of gallery CSS). Plan's direction to keep both is fine; the "open question" can close with that decision.

### Q3: head-common include parity — defer?
**My position: DO NOT DEFER. Blocker for first deploy.**

See Defect 2 above. Without head-common, these pages have no GA beacons — the GTM campaign measurement dies. Without navbar, users can't navigate back to the site. The plan's own rationale for the pages is "cold email → landing page → conversion." Untracked landing pages break that rationale. Fix in the same commit that authors the 4 pages; also retrofit `jumper-installation.html`.

## Summary

Verdict MAJOR. The plan's mechanics (file counts, line numbers, frontmatter pattern) are correct, but the top-of-plan deployment model is wrong (Vercel, not GitHub Pages), four acceptance-visible gaps are unaddressed (head-common include, sitemap, title rewriting vs. verbatim contradiction, CSP/Plotly audit), and the "link-check regression guard" has no wiring to fire automatically. At least one "open question" (head-common parity) is a blocker disguised as a deferral. Fix Defects 1-4 and Q3 before implementation; Defects 5-10 can roll into the same revision.
