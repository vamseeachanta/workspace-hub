# Plan Review — Issue #1878 (Claude)

**Reviewer:** Claude (Opus 4.7) | **Date:** 2026-04-16

## Verdict

**MAJOR**

## Retrieval Adequacy

**adequate.** Nine sources cited with specific file paths, line numbers, and concrete record counts (649,564 / 717,141 / 543,994). Diagnosis is reproducible; #2208 contract satisfied (≥3).

## Key Findings

1. **[blocking] Pseudocode `hash_key = record["content_hash"]` is wrong.** Phase-A stores `content_hash` as `"sha256:<64hex>"` or `"md5:<32hex>"` (phase-a-index.py:130-134), but summary filenames on disk are bare 16-hex (e.g. `000021e9241944bd.json`) — verified via `ls /mnt/ace/data/document-index/summaries/`. Lookup will miss 100% of content_hash records and silently report `summary_done=False`. **Fix:** strip prefix and slice to the actual length used by `summarise-worker.py` — read that script and mirror its filename derivation exactly. Add `test_hash_key_strips_sha256_prefix` and `test_hash_key_strips_md5_prefix` to TDD list.

2. **[blocking] Plan ignores diagnosis evidence of 46.1% summary-match rate for content_hash records.** Diagnosis §2 reports only 78,268 / 169,815 sha256-prefixed records have summaries — a 54% miss. Plan does not explain the gap nor whether enrichment will reproduce 83.7% or 46.1% on that segment. **Fix:** add a pre-flight reconciliation step that materializes hash-key → summary-file mapping for a 1K sample and asserts match-rate ≥ projection before touching the real index.

3. **[blocking] No `--resume` / `--workers` / chunked I/O.** Existing pattern (`enrich-readability.py:152-170`, `ProcessPoolExecutor`, `--resume` skipping records that already have the field, `.jsonl.tmp` → `.jsonl.bak` rotation) is the established idiom. Plan only mentions "atomic rename" abstractly. 649K records with per-record `os.path.exists` + `json.load` on NFS will be slow without parallelism, and a mid-run abort will require a full restart. **Fix:** mirror `enrich-readability.py` skeleton — `--resume`, `--workers`, `ProcessPoolExecutor`, `.tmp`/`.bak` rotation.

4. **[minor] Threshold drift unexplained.** Diagnosis Phase 3 says `<50%` summary_done rejects; plan tightened to `<60%`. With projected 83.7% there is headroom, but the change is undocumented. **Fix:** state rationale or revert to 50%; either way make the threshold a CLI flag with the default written in `validate-index-metadata.py`'s `--help`.

5. **[minor] Atomic-rename test is unobservable as written.** `test_enrichment_atomic_rename` says "simulated mid-run failure → original file intact." Without a specific injection point (e.g., monkeypatch `os.rename` or kill between `.tmp` write and rename), this is untestable. **Fix:** specify the injection seam.

6. **[minor] `summary_title` / `summary_discipline` inflate row size by ~65 MB; no downstream-impact check listed.** Risk-section ack but no acceptance criterion. **Fix:** add an AC: "no downstream consumer (list scripts in `scripts/data/document-index/`) errors on the enriched index" — run them once with the new file.

7. **[nit] Skill GOTCHA edits should land *after* enrichment is verified, not in the same PR.** Otherwise docs claim a feature that may still be 0% if the run aborts. Sequence: enrich → validate → flip GOTCHAs.

## Pseudocode Soundness

Logic is **structurally** sound (load map, iterate, derive ext-based content_type, lookup summary, write). It is **operationally broken** on the content_hash path (Finding #1). Empty-summary handling via `bool(data.get("summary","").strip())` is correct. Atomic-rename mention is too thin (Finding #5). No handling of corrupt/partial JSON in summary files — must `try/except json.JSONDecodeError` and treat as `summary_done=False`.

## Test Coverage Adequacy

15 tests cover the happy paths but miss: (a) `content_hash` prefix-stripping (Finding #1), (b) corrupt summary JSON, (c) summary file present but `summary` key absent (different from empty string), (d) unicode/non-UTF8 paths (487K records include CAD with mixed encodings), (e) concurrent run safety — two enrichments racing the same `.tmp`, (f) very large index memory footprint (649K records × dict will be ~2GB resident; needs streaming write or confirmed RAM ceiling), (g) `--resume` semantics (skip records that already have `content_type`). **Add 5-7 tests covering b–g.**

## Acceptance Criteria Quality

`≥90% content_type` is trivially satisfied because the `other` fallback guarantees 100% — the threshold is meaningless as written. Either tighten to "≥90% non-`other`" or drop. `≥60% summary_done` is reasonable given 83.7% projection but should match the validator's threshold (currently 60% in plan vs 50% in diagnosis — see Finding #4). Backup-file AC is good. Missing: "no record loses an existing field" (regression guard against accidental key deletion).

## Scope and Risk

In-scope items (enrichment, validation, phase-a carryover, GOTCHA updates, maturity YAML) are all causally tied to #1878. **Scope creep risk:** maturity-YAML refresh and skill edits broaden blast radius — recommend splitting into a follow-up so the data-fix PR is reviewable in isolation. **No rollback plan stated** beyond the dated backup file — add: "to roll back, `mv index.jsonl.backup-2026-04-16 index.jsonl`" and confirm backup is git-ignored (file is 200+ MB). **Blast radius:** any consumer reading `index.jsonl` sees new keys mid-deploy; survey consumers via `grep -r "index.jsonl" scripts/` before merge.

## Recommendation

**Do not approve as-is.** Required changes:
1. Fix the content_hash → filename derivation (Finding #1) and add tests.
2. Add `--resume` / `--workers` / `.tmp`+`.bak` per `enrich-readability.py` (Finding #3).
3. Pre-flight match-rate reconciliation on a sample (Finding #2).
4. Clarify threshold (Finding #4) and tighten content_type AC (Acceptance section).
5. Add corrupt-JSON / streaming / resume tests (Test Coverage section).
6. Split maturity-YAML + skill edits into follow-up issue, or sequence after enrichment verified.

After these revisions, plan is approval-ready.
