## Scope completeness

Open question in plan (line 186): "should Demo-1–4 detail pages (shipped by #2342+#2343 Commit 2 — `freespan.html`, `wall-thickness.html`, `mudmat.html`, `pipelay.html`) also carry the Download-PDF CTA? ... **Recommended:** file a follow-up issue after this one deploys if GTM asks; do not expand scope here."

**Review position:** the recommendation to defer is *defensible* (issue #2367's scope in its own body is "gallery page + 4 methodology pages" verbatim), but the plan's framing understates the cost of not expanding scope here:
- The 4 new detail pages (verified present via `ls content/demos/`: `freespan.html`, `jumper-installation.html`, `mudmat.html`, `pipelay.html`, `wall-thickness.html`) are the *most conversion-likely prospect-facing pages on the site* — a visitor reading freespan.html is a warmer lead than a methodology-page reader.

Still T1 by the plan's own T1/T2 criteria (line 193: "no new code paths, no new config"). The marginal cost is trivial; the marginal GTM value is non-trivial.
- **Also:** `content/demos/jumper-installation.html` exists and is not in either bucket. If the user later expands scope, that page gets forgotten unless explicitly named.

**Recommendation (MINOR):** re-open the open question rather than pre-answering "file a follow-up". Present the user with a binary choice: (a) ship 5 pages only, file follow-up for 5 detail pages; (b) expand scope now to 10 pages, same T1 complexity. Don't pre-decide.

## New findings — claim-vs-code drift

**Finding 1 (MINOR): methodology pages do not use `{{ rootPath }}` templating in body content.**

Plan pseudocode (line 88) prescribes for each methodology page:
```html
<a href="{{ rootPath }}assets/capability-summary-v1.pdf" ...>
```

Verified: `grep -c 'rootPath' content/methodology/*/index.html` returns `1` for each file (the frontmatter only; 0 in body). The existing `method-cta` block uses raw relative paths: `<a class="btn btn-primary btn-lg" href="../../contact.html">Talk to ACE Engineering</a>` (e.g. `content/methodology/compound-engineering/index.html:79`). Posthtml-expressions will still render `{{ rootPath }}` correctly — it is wired in `build.js` lines 57–63 — but introducing `{{ rootPath }}` here will be the *first* body use in any methodology page and creates an inconsistency future maintainers will need to explain.

**Either:** prescribe `../../assets/capability-summary-v1.pdf` (matches surrounding code style in these 4 files); **or** prescribe `{{ rootPath }}` here *and* note that the plan is deliberately upgrading methodology pages to use templated paths. Pick one; don't let the inconsistency sneak in silently.

**Finding 2 (MINOR): line-number claims drift from git state.**

Plan line 20: "`content/demos/index.html` (468 lines)". Actual: 472 lines (`wc -l`). Plan line 20: "demo cards at lines 289–393" / "`<section class="demo-cta-section">` at lines 451–463". Actual: `demo-cta-section` starts at line 456 (`grep -n 'demo-cta-section'`).

Plan line 21: "`content/methodology/compound-engineering/index.html` (78 lines)". Actual: 80 lines. More importantly: the plan describes this file as having a "template ... `rootPath: "../../"` frontmatter; inline `<style>` block; `<article class="method-shell">` body with `method-toc`, section H2s, `method-cta` block at the end (line 78...)". **All four methodology pages are effectively single-line-minified HTML** — lines 1–4 are frontmatter, lines 5–6 are a giant `<style>`, and the entire body (hero, TOC, article, method-cta, footer include) is on one unbroken line (verified: `head -5` on each returns `<!DOCTYPE html>...method-hero{...}` on line 6 with no line breaks). Line 78 is not meaningful for these files; the `method-cta` is at the *end* of line 79 embedded inside that single HTML line. Call the files what they are (minified, one-line body) so the implementer doesn't open them expecting a readable layout.

**Finding 3 (MINOR): issue body says "hero or footer"; plan silently picks footer-only.**

Issue #2367 body (fetched via `gh issue view 2367`): "Add `<a href=\"/assets/capability-summary-v1.pdf\">Download capability summary (PDF)</a>` CTA to: `aceengineer-website/content/demos/index.html` (gallery page, **hero or footer**)". Plan picks footer (`.demo-cta-section`) without acknowledging the hero option. The gallery hero block is verified at line 252 (`<section class="demo-hero">`) and the KPIs block at lines 259–276 is a natural download-CTA placement slot *with higher visibility* than the footer.

**Pick explicitly.** Plan's rationale "This final CTA section is the natural placement slot for the new Download-Capability-Summary button" (line 20) is ipse dixit. Hero placement is plausibly higher-conversion. Present both as alternatives in the Risks/Open-Questions section, not silently prefer one.

**Finding 4 (MINOR): acceptance wording mismatch against issue acceptance.**

Issue #2367 acceptance checkbox: "Live URL returns 200 on `www.aceengineer.com`". Plan acceptance (line 147): "all 5 pages return HTTP 200; all 5 pages' rendered HTML contains `/assets/capability-summary-v1.pdf`; the PDF URL itself returns 200 with `Content-Type: application/pdf`".

The PDF URL is `https://www.aceengineer.com/assets/capability-summary-v1.pdf`. The plan prescribes `{{ rootPath }}assets/capability-summary-v1.pdf` which after posthtml-expansion becomes `../assets/capability-summary-v1.pdf` from `dist/demos/index.html` and `../../assets/capability-summary-v1.pdf` from `dist/methodology/*/index.html`. **The rendered URL is relative; the issue acceptance says the live URL must 200.** Browsers resolve the relative URL against the page URL, which yields the correct absolute URL, so the behaviour is fine — but the plan's acceptance test `prod_cta_in_rendered_html` (line 133) tests for the literal string `/assets/capability-summary-v1.pdf` in rendered HTML. The literal will **not** match because the rendered anchor is `../assets/…` or `../../assets/…`. **This test, as written, will fail.** Either change the test to match the actual rendered relative URL, or change the anchor to use a site-absolute `/assets/…` path.

**Finding 5 (MINOR): accessibility / screen-reader anchor text is not discussed.**

Plan anchor text: `"Download capability summary (PDF)"`. The `(PDF)` suffix is good for assistive tech. Missing: a file-size hint (`"(PDF, ~300 KB)"`) — this is a WCAG 2.1 best practice for download anchors so users on metered connections know what they're committing to. The #2344 parent plan constrains PDF size (see its risks); this plan should inherit the final size from #2344 and include it in the anchor text. Not blocking, but flag it as a pre-implementation dependency: "final anchor text pending #2344 PDF size measurement".

**Finding 6 (LOW): `download` attribute behaviour on iOS Safari.**

Plan line 91: "browsers that ignore the [`download`] attribute will still render the PDF inline in their built-in viewer — both behaviours satisfy the issue's acceptance criterion." True on desktop; on iOS Safari the `download` attribute is entirely ignored AND the PDF opens in Safari's inline viewer with no "save to Files" affordance above the scroll fold. For a capability-summary leave-behind, that's acceptable (user can still share the URL), but the plan claiming "both behaviours satisfy the issue's acceptance criterion" is too strong. The issue says "downloads ... (or opens in-browser PDF viewer)" — so iOS is in-spec. Downgrade the plan's claim from "both behaviours satisfy" to "acceptable by issue's acceptance ('downloads or opens in-browser viewer')".

**Finding 7 (MINOR): "Open Questions" flagged for user are defaults, not TBD.**

Plan Risks section has 3 user-facing open questions (line 184–186): CTA button copy, methodology-page placement, detail-page scope. A T1 plan with `status:plan-review` should have **concrete defaults** that the user can approve with a single "yes", not multiple "please decide" forks. Each open question is well-framed but pushes decisions onto the user in a way that makes `status:plan-approved` harder to stamp cleanly. Either promote each default (`"Download capability summary (PDF)"`, `.method-cta` placement, scope=5-pages-only) from "flagged for decision" to "default assumption; flag for objection" — or split the plan into two approval rounds, which is overkill for a 5-file T1.

**Finding 8 (LOW): `btn-default` choice unverified against methodology CSS.**

Plan line 182 says "use `btn-default` (not `btn-primary`) for the new button to visually subordinate it". The methodology CSS block (`.method-cta{margin-top:30px;background:linear-gradient(135deg,#2d3436 0%,#4a5568 100%);color:#fff;...}`) has a *dark gradient background* with white text. Bootstrap `btn-default` is traditionally *white background + dark text* — which would render a white-on-dark pill that visually dominates the primary CTA rather than subordinating it. Plan's subordination logic may be backwards. Needs a real render check, not an assumption. Flag as manual-visual-QA before claiming it subordinates.
