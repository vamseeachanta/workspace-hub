## Findings

1. **MAJOR — `needs-user-decision` and `unknown` are not states in the #2017 contract, and no contract change is planned.** `docs/design/email-queue-state-schema.yaml:3-8` and the snapshot `state` enum (lines 108-110) define exactly five states: `inbound, extracted, awaiting-reply, completed, purged`. `docs/design/email-as-queue.md:55` confirms the same five. Plan §D3 treats `needs-user-decision` as a durable bucket, the pseudocode `pending_work_report` counts `needs_user_decision` and `unknown`, and TDD test `test_pending_work_report_not_empty_for_needs_user_decision` requires a record in that state. §Files to Change does not touch the schema yaml or the state-machine transition table. As written the test is unimplementable: there is no valid transition that produces a `needs-user-decision` snapshot record. Either extend the contract (schema enum + transition table + dedup implications) or define an explicit mapping onto existing fields (e.g., `primary_classification: actionable` + a flag) — the plan does neither.

2. **MAJOR — D5 dedup-key change contradicts the schema the plan itself quotes, and the schema file is not in Files to Change.** Schema `dedup_key` is `[account_id, thread_id, from_state, to_state]` (`email-queue-state-schema.yaml:62-66`); `triggering_message_id` is not even a property of `queue_state_entry` (lines 31-61). Plan §D5 makes `triggering_message_id` part of the dedup key and §Pseudocode writes it into events. Implementing this without updating `docs/design/email-queue-state-schema.yaml` makes the contract artifact false on day one, and validation against the schema (the plan's own evidence base) would reject the new field if `additionalProperties` were enforced. The schema yaml must be added to Files to Change with the D5 semantics, or D5 dropped.

3. **MAJOR — "zero unknown/unclassified in-scope threads" is uncomputable from the planned modules.** §D3 defines report-empty as requiring zero "unknown/unclassified in-scope threads", and the §Deliverable claims the module "can tell whether mailbox work is pending." Every module in §Files to Change reads only local state; a thread that was never ingested produces no JSONL row and is invisible to `report.py`. Detecting untracked pending work requires an inbox-enumeration input (Gmail read adapter or an ingest-side thread census) that no planned file provides — `state/labels.py` is a write-side label planner. Either add an inbox-snapshot input interface to `report.py`, or re-scope "unknown" to mean "present in store with unrecognized state" and state explicitly that untracked-thread detection belongs to #2024.

4. **MAJOR — acceptance criteria #3 and #7 are jointly unsatisfiable as specified.** Pseudocode `transition` does "validate account alias is allowed" against the hardcoded set `{"ace", "personal"}` (`load_account_scope`), but the existing contract tests the plan promises to keep green (criterion #7, "Existing #2017 contract tests pass") call `transition(log, account_id="user@example.com", ...)` (`test_state_machine_contract.py:18-25`). With allowlist enforcement in `transition`, those tests fail with `AccountOutOfScope`. The plan needs to specify one of: allowlist injectable per store (tests construct a permissive scope), enforcement only at the report/ingest layer, or rewriting the contract tests' account IDs (which changes #2017 contract artifacts and should be called out as such). Related unresolved ambiguity: whether `account_id` persisted in JSONL/snapshot keys is the alias (`ace`) or the literal address — §D2 says tests shouldn't hardcode addresses, yet the contract tests already persist an address as `account_id`.

5. **MAJOR — reconciliation scope omits `docs/design/email-as-queue-workflow.md` entirely.** The 29 KB workflow design (also a #2017 artifact, never mentioned anywhere in the plan) declares `~/.hermes/email-state.yaml` as "the authoritative state tracker" (line 236), uses `skestates` account examples (lines 255, 328, 334), and schedules a week-4 "Full pipeline, all accounts" deletion rollout (lines 487-490) — all three contradict this plan's D1 (directory, not single YAML), D2 (two accounts), and the no-Gmail-mutation boundary. Additionally `docs/design/email-as-queue.md:24-29` (the plan's declared contract source) pins all four state files to **repo paths** `scripts/email/queue-state*.jsonl/yaml`, directly contradicting D1; the plan does list that doc in Files to Change but its Resource Intel never surfaces that the contract source itself specifies repo-tracked state paths — a reviewer reading only the plan would think the conflict lives in "old plans," not in the active contract doc. Add the workflow doc to Files to Change (or explicitly mark it superseded) and name the email-as-queue.md State Authority conflict explicitly.

6. **MINOR — stdlib `email` shadowing hazard is one plausible edit away.** `tests/conftest.py:9-12` inserts `REPO_ROOT/scripts` into `sys.path`. The plan creates `scripts/email/state/__init__.py` but (correctly) not `scripts/email/__init__.py` — yet never says so. If an implementer "fixes" the asymmetry by adding `scripts/email/__init__.py`, top-level `import email` resolves to the repo directory instead of the stdlib `email` package for the entire test session (regular packages beat the namespace-portion deferral that currently protects stdlib). The plan should explicitly prohibit `scripts/email/__init__.py` and note that `scripts.email.*` imports rely on PEP 420 namespace resolution plus repo root on `sys.path` (via the `tests/` package basedir under pytest's prepend import mode).

7. **MINOR — `fcntl` is POSIX-only.** §Pseudocode and `state/store.py` rationale specify `fcntl LOCK_EX`. The workspace convention includes a Windows checkout (`D:\workspace-hub`). Issue is `machine:dev-primary` (Linux), so acceptable, but the plan should state the platform constraint or guard the import so test collection doesn't break on Windows.

8. **MINOR — plan presents already-completed work as future.** `docs/plans/2026-04-24-issue-2026-plan.md` already carries the full supersession banner in the working tree, and `docs/plans/README.md` is already modified (git status), while §Files to Change lists both as pending updates on a `Status: draft`, pre-approval plan. This is the inverse of the plan-future-tense rule but hits the same trust surface: the reviewer/approver cannot tell which Files-to-Change rows are real future work. Mark these two rows "already applied in working tree."

9. **MINOR — Adversarial Review Summary says "Review not yet run" but the fanout already ran and failed.** All three result files exist as 0-byte placeholders (created 15:24); the codex `.err` is 278 KB (its tail contains the plan's own pytest reproduction output) and a gemini `.err` existed transiently. Per the `scripts/review/results/` convention, failed provider runs should be recorded as UNAVAILABLE with cause, not PENDING. Also note: an active concurrent writer touched these files during this review (gemini `.err` vanished between `ls` and `cat`) — check parallel work before the next fanout wave.
