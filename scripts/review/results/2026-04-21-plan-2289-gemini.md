### Verdict: MAJOR

### Summary
The plan contains critical logic flaws regarding Git hook lifecycles and event processing. It falsely assumes a pre-commit hook can log a commit SHA, and it fails to deduplicate bypass events for the same commit across multiple gates, which would lead to duplicate revert proposals.

### Issues Found

- **Git Lifecycle Impossibility:** The plan states `require-plan-approval.sh` is a 'pre-commit' gate, yet `test_commit_gate_emits_bypass_log` explicitly demands the bypass log includes a 'SHA'. A pre-commit hook runs before the commit object is created and therefore cannot know or log the commit SHA. The pseudocode's `commit_sha = event.commit_sha or resolve_from_local_oid(event)` will fatally fail for these events.

- **Duplicate Revert Proposals:** The pseudocode iterates over `bypass_events` sequentially without deduplication. If a user bypasses the commit gate and subsequently bypasses the push gate for the exact same commit, two separate events are logged. The advisor will process both independently, resulting in duplicate audit records and multiple revert proposals for the same SHA.

- **Schema mismatch in pseudocode:** The pseudocode conditionally checks `if event.pushed` to determine the verdict. However, the schema excerpted for `require-review-on-push.sh` (lines 149-167) does not contain a 'pushed' boolean; it contains `local_oid` and `remote_oid`. The definition of `event.pushed` is undefined and unmapped.

### Suggestions

- Refactor the commit-gate logging mechanism. Either use a `post-commit` hook to log the actual SHA if a bypass was flagged during `pre-commit`, or log the working tree state/branch and resolve it dynamically in the advisor.
- Add a deduplication phase in the `bypass_rollback_advisor` pseudocode that groups bypass events by `commit_sha` before applying the evaluation rules.
- Modify `test_commit_gate_emits_bypass_log` to accurately reflect the data available at the hook's execution time, removing the expectation of a commit SHA if run at pre-commit.
- Determine the `pushed` state by actively checking if the resolved `commit_sha` exists on the remote branch (e.g., `git branch -r --contains <sha>`), rather than relying on a non-existent `event.pushed` field.

- If a single commit bypasses both the plan gate and the push gate, generating two distinct log entries, how does the proposed advisor prevent duplicate revert proposals and redundant audit logs?
- Where is `event.pushed` derived from in the pseudocode, given it does not exist in the referenced JSONL schema?
