# Adversarial Review — Plan #2024 (Codex)

Date: 2026-04-14
Issue: #2024
Plan: docs/plans/2026-04-13-issue-2024-gmail-extract-and-act-pipeline.md
Reviewer: Codex CLI
Reviewer mode: adversarial
Overall verdict: MAJOR
Ready for user approval: No
Retrieval adequacy: insufficient

Top blockers
1. The plan does not resolve the core design decisions it claims as gaps: canonical unit of work, state schema, deletion semantics, attachment persistence policy, and replacement strategy for gmail-archive-extract.py are still open.
2. Resource intelligence is too thin for approval on a stateful data-pipeline rewrite. It cites a few local files, but not the governing workflow/policy artifacts, parent issue decisions, Gmail label constraints, or the downstream repos/data contracts the pipeline will write into.
3. The migration/backfill scope is materially underspecified. Backfilling previously archived emails is potentially a separate issue with different legal, quality, and data-reconciliation risks, but the plan leaves it bundled without acceptance boundaries.
4. TDD scope is not approval-ready for the risky behaviors: idempotency, partial failure recovery, duplicate extraction prevention, cross-account state isolation, concurrent runs, label drift, and commit/write ordering around legal scan are all missing.
5. Acceptance criteria are process-oriented rather than outcome-oriented. They do not make the implementation falsifiable on safety, state transitions, deletion protection, or no-raw-body persistence.

Critical findings
- The plan leaves the canonical lifecycle model undecided. It explicitly asks whether state should be per message or per thread, but that is the highest-risk design choice in the whole issue.
- The deletion model is unsafe as written. It does not define trash vs permanent delete, mixed-state thread handling, or the metadata needed to prove a thread is safe to delete.
- The legal-scan step is wrongly abstracted. The plan does not define whether scan happens before repo write, before git add, before commit, or before any attachment persistence.
- The migration scope is internally contradictory: it says build new script, replace old script, and modify gmail-archive-extract.py via slim/deprecate/wrap, which are materially different execution paths.
- The plan has no explicit rollback/failure model for a stateful workflow touching Gmail labels, local state, repo writes, and deletions.

High findings
- Retrieval is inadequate for plan-stage review under this repo’s contract. The plan should have pulled in and summarized the actual planning policy/hard-stop requirements and parent issue decisions from #2017.
- The downstream write contract is missing: per-template destination schemas, file naming/idempotency keys, update-vs-create behavior, and dedupe rules when the same thread is reprocessed.
- Attachment handling remains an open question even though attachments are first-class in the current script and likely essential for invoices and CRE data.
- Reactivation semantics are too vague and do not define whether any inbound message reactivates, how outbound-only replies are treated, whether labels are removed atomically, or whether reactivation creates a new extraction event.
- The state file contract is missing: no schema, versioning, locking/concurrency strategy, corruption recovery, or account namespacing.
- The proposed CLI is not backed by plan decisions; actions like triage, delete-completed, check-replies, and state-report imply a state machine/operator model the plan never concretely defines.

Medium findings
- The TDD list misses idempotency and replay safety.
- The TDD list misses mixed-policy routing cases, such as delete/review routing colliding with structured extraction.
- The TDD list misses account isolation.
- The plan does not define how labels are bootstrapped or validated if they do not already exist.
- “Standards: N/A” is too loose for this repo; workflow/governance standards and email/legal-scan docs should have been consumed.
- The backfill phase lacks success criteria.
- Acceptance criteria do not mention observability, dry-run guarantees, or auditability.
- The plan does not state whether commits occur per email, per thread, per batch, or per repo.

Low findings
- tests/email/ is too vague for a T3 rewrite.
- The risk section is too short relative to the destructive nature of deletion/reactivation behavior.
- Review-artifact placeholders are still pending.
- The pseudocode collapses multiple irreversible operations into one loop and hides ordering decisions that should be explicit.

Required revisions before user approval
1. Decide and document the canonical unit of work; if thread-based, specify exactly how per-message events roll up into thread state and how reactivation works.
2. Define the state schema for ~/.hermes/email-state.yaml, including account keying, thread/message ids, current state enum, timestamps, extracted artifact refs, last-seen marker, schema version, and locking/update strategy.
3. Make deletion semantics explicit and safe: trash vs permanent delete, required preconditions, mixed-state handling, operational definition of noise, and operator-visible dry-run output.
4. Define exact legal-scan sequencing, including cleanup behavior on scan failure.
5. Resolve replacement scope: either full replacement with a deprecation shim or staged coexistence, but not replace/wrap/slim ambiguously.
6. Split or narrow migration scope; backfill likely needs a separate follow-on issue unless this plan adds explicit data source, validation, and rollback details.
7. Expand resource intelligence to include governing workflow/policy artifacts and parent issue decisions, plus any existing email/Gmail/label/state-management docs or skills.
8. Upgrade TDD coverage for idempotent reruns, concurrent/locked state updates, duplicate prevention, label bootstrap/failure, mixed routing outcomes, attachment policy branches, legal-scan failure cleanup, and cross-account isolation.
9. Replace process-only acceptance criteria with falsifiable behavioral criteria for extraction, state transitions, no raw-body persistence, safe deletion, reactivation, and rollback/recovery behavior.

Conclusion
- The earlier MAJOR verdict stands. The current plan is directionally useful, but it is not approval-ready because the risky design decisions are still deferred into implementation.
