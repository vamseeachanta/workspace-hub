## Findings
- The 30-second performance target for parsing ~35 MB across 15 files has no profiling evidence; reasonable for streamed parse but should be a soft goal, not acceptance criterion, until measured.
- Log retention is 15 days per `ls` output, so the `invocations_90d` column cannot be fully satisfied without an archival story — the plan flags this as a risk but doesn't propose a resolution; v1 should either drop the 90d column or add an archive-ingestion step.
- The proposed tier-demotion rule (`invocations_90d == 0 → COLD`) can conflict with the existing `skill-usage-report.py` HOT criterion ("referenced by 5+ other skills OR recent git"), producing contradictory states; the plan should specify whether invocation-signal overrides reference-signal and in which direction.
- The plan lists three Skill-tool aliases (`Skill`, `activate_skill`, `skill`) but does not specify the exact JSON path to extract the skill name per provider — the scanner parser needs a concrete mapping (e.g., `.toolInput.skill` for Claude Code, something else for Codex/Gemini sessions) or it will silently under-count.
- PII risk in session logs is unaddressed — emitted JSON should confirm it carries only skill names and timestamps, never tool input bodies or file contents.
- The `fixture sample_session.jsonl` should include at least one event per provider format, not just one synthetic Skill event.
