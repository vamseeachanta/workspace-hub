## Verdict
MAJOR

## Retrieval adequacy
insufficient — plan sampled only `logs/orchestrator/hermes/session_20260415.jsonl` (Hermes format) while proposing to handle Claude Code, Codex, and Gemini session formats. No fixture or schema pin for the other three formats exists.

## Findings
- **Correctness — pseudocode cannot work as written.** The pseudocode uses flat `event.tool_name` and `event.tool_input.skill` lookups. Real Claude Code session jsonl nests tool calls inside `message.content[].tool_use` with `name` and `input` fields, not `tool_name` / `tool_input`. The parser would produce zero invocations against real data.
- **Correctness — 90-day window is a false promise.** `Acceptance Criteria` row 1 produces `invocations_90d` but `ls logs/orchestrator/hermes/` shows ≤15 days retained. The metric is unachievable as specified; "best-available" is not documented anywhere in Deliverable or Pseudocode.
- **Correctness — tier-demotion rule contradicts existing classifier.** `Pseudocode` integration clause demotes to COLD on `invocations_90d == 0`, but `scripts/skills/skill-usage-report.py` HOT criterion is "referenced by 5+ OR recent git". A skill with 5 incoming references and no invocations would oscillate between HOT and COLD depending on which signal is last applied. Merge rule is unspecified.
- **Correctness — "Every SKILL.md appears in output" acceptance cannot be satisfied by the pseudocode.** `defaultdict(list)` only produces keys for invoked skills. The acceptance requires a prior `discover_skills(skills_root)` walk, which the pseudocode does list — but the CSV writer iterates `rows` built from `invocations`, not from `all_skills`. Inconsistency between pseudocode blocks.
- **Correctness — `<30s` performance acceptance has no budget evidence.** Python json.loads on 35 MB spread across 15 files is routinely 20-60s depending on implementation. Plan does not commit to streaming (`for line in f`) vs bulk parse, and no profiling fixture exists.
- **Scope — PII risk unaddressed.** Session logs can contain file contents, tool inputs including paths, user messages. Plan has no output-content-redaction clause. `Acceptance Criteria` row 3 writes "Every .claude/skills/**/SKILL.md appears in output" but doesn't constrain WHAT appears — only `skill_name` + counts should be emitted, never raw event bodies.
- **Scope — MCP tool calls not considered.** `mcp__*` invocations are heavy tool use but are NOT Skill invocations. Plan conflates "tool telemetry" with "skill telemetry" — unclear which.
- **Scope — dashboard integration acceptance unbacked by test.** `Acceptance Criteria` row 6 requires `skill-health-dashboard.sh` end-to-end run to include the new audit, but `TDD Test List` has zero dashboard integration tests.
- **Scope — log-rotation timestamp derivation unspecified.** `session_YYYYMMDD.jsonl` filename encodes one date, but events inside span midnight. The 30/90d windows need event timestamps, not filename dates. Pseudocode doesn't specify which.

## Blockers
- Pin the actual JSON schema for Skill-tool invocations in each supported session format (Claude Code, Codex, Gemini, Hermes) with concrete fixture files, OR narrow v1 to one format and update Deliverable / Acceptance.
- Reconcile 90-day promise with 15-day retention: pick one — narrow window, add archive ingestion, or explicitly label `invocations_90d` as "best-available within retained logs" in Deliverable, Pseudocode, and Acceptance.
- Specify merge rule when invocation-signal and reference-signal disagree for tier classification; add a TDD test for the contradiction case.
- Add a TDD test for `skill-health-dashboard.sh` integration; or drop that acceptance row.
- Add an explicit output-schema clause: "only skill_name, counts, last_used are emitted; raw event bodies are never written."
- Change pseudocode to derive counts from the `discover_skills` walk, not from the `invocations` dict, to satisfy zero-invocation-row acceptance.
