### Verdict: MAJOR

### Summary
The plan has correct general direction but contains factually wrong line-number citations in its own "embedded verification" block, treats the only non-mechanical risk (assetutilities sibling-dep resolution — actually a `{ path = "../assetutilities" }` declaration in pyproject.toml) as a flagged risk rather than a phase-2 blocker, leaves the phase-1/phase-2 gate ambiguous (nothing forces a separate push + CI validation between them), and proceeds despite a documented governance violation (`status:plan-approved` applied before the plan artifact existed). These are MAJOR defects for a never-green 7-month CI, because the plan will either fail on phase-2 CI (assetutilities unresolvable on a clean runner), or the executor will edit line 136 (which is actually a YAML comment) instead of line 138. Diagnosis of the YAML root cause is also unproven.

### Issues Found
- MAJOR — Line-number error inside the plan's own 'Line excerpts (sed)' evidence block (plan §Evidence): plan claims line 136 is the second `DATABASE_URL: sqlite:///:memory:` site, but actual line 136 is the YAML comment `# Environment variables for testing`. The second DATABASE_URL is at line 138 (verified by `grep -n DATABASE_URL`). An executor following the plan verbatim will quote the wrong line or fail to find a match.
- MAJOR — Second line-number error in §Risks and Open Questions: 'codecov/codecov-action@v3 at line 343' — actual occurrence is at line 144 (verified). Undermines confidence in the plan's 'embedded verification' discipline and will misdirect any later bump decision.
- MAJOR — The 9-site inventory is incomplete/mis-scoped for the stated deliverable. `assethold/pyproject.toml` line 222 declares `assetutilities = { path = "../assetutilities" }` and `requirements-consolidated.txt` line 43 lists bare `assetutilities` with no source. A GitHub Actions runner has no `../assetutilities` path and `assetutilities` is not on PyPI — so phase-2 as written (swap requirements.txt → requirements-consolidated.txt) will fail at install step. The plan labels this a 'Risk' but phase-2 acceptance (one matrix cell green) depends on it — it belongs inside the fix list, not in a mitigation footnote.
- MAJOR — Phase-1 → Phase-2 gate is not enforceable. The plan says phase-1 acceptance is 'jobs register, matrix executes (install may fail)' and phase-2 is 'one cell green' — but there is no instruction that phase-1 must be pushed and CI-verified before phase-2 commits, and no separate PR/commit boundary. An executor could bundle both into one commit, skipping the gate. The plan calls this a 'phased' remediation but does not mechanically enforce the phasing.
- MAJOR — The acceptance criterion 'run locally: cd assethold && uv run pytest tests/test_smoke.py -v must pass before pushing phase-2 fix' is not equivalent to CI validation. A local fresh venv still has `../assetutilities` on the filesystem and in pyproject.toml; a CI runner does not. The plan's pre-push gate cannot detect the sibling-dep failure mode it claims to protect against.
- MAJOR — Root-cause diagnosis for the 0s startup pattern is unproven. Plan asserts `DATABASE_URL: sqlite:///:memory:` 'triggers YAML mapping error' but offers no yamllint/parser output. Trailing `:` before newline is ambiguous in YAML 1.2 but is accepted by many parsers. The more likely 0s-reject cause is `actions/upload-artifact@v3` (hard-rejected by GitHub since Jan 2025) and `codeql-action@v2` (retired). The plan bundles both fixes into phase-1 without differentiating, so it may 'work' without proving which change unblocked parsing — a problem if only deprecated-action fixes are needed and DATABASE_URL quoting is benign noise.
- MAJOR — Label-drift governance violation proceeds with only a flag. The plan notes `status:plan-approved` was pre-applied before any plan existed, acknowledges this 'violates the plan-approval gate semantics,' and mitigates only by posting a governance comment. The user's explicit memory entry `feedback_never_offer_to_self_label_plan_approved.md` says 'never self-approve in chat, never pre-authorize downstream agents via handoff-prompt language; user-in-loop gate is load-bearing across session boundaries.' The plan should block execution pending fresh explicit approval, not merely document the drift.
- MINOR — Plan TDD assertion 'phase-1: upload-artifact step exists as v4 — `rg @v4 ... 3+ hits`' is ambiguous. Line 57 already has `actions/checkout@v4` and line 207, 254, 297 have more checkout@v4, so `@v4` grep already returns >=4 hits before any fix. The test doesn't discriminate the 3 upload-artifact changes from pre-existing v4 usage.
- MINOR — Missing enumeration of other stale action pins: `actions/setup-python@v4` (4 occurrences: 62, 210, 257, 302; v5 is current), `astral-sh/setup-uv@v1` (4 occurrences: 68, 216, 263, 307; docs.yml already uses @v4 — so same repo has inconsistent pins). Plan lists codecov-action as an open question but silently omits setup-uv@v1, which is the much older pin.
- MINOR — Acceptance criterion 'Update docs/plans/README.md (deferred per constraint — NOT in this session)' contradicts itself: it's listed as an acceptance checkbox but explicitly excluded from the session. Either drop it from the checklist or resolve the contradiction.
- MINOR — T2 classification is suspect. Phase-3 includes 'diagnose docs.yml zero-jobs' with the root cause 'hypothesized' but unverified, and phase-2 requires a non-mechanical decision between `uv sync --frozen` vs. requirements-consolidated.txt that depends on sibling-dep behavior. That's T3-shaped work labeled T2.

### Suggestions
- Re-run `grep -n` against the current workflow file and replace every cited line number in §Evidence and §Pseudocode. Add a pre-commit gate in the plan: 'executor MUST re-verify each line number before editing.'
- Move `assetutilities` resolution from §Risks into the phase-2 fix list. Pick one explicit path (either `pip install git+https://github.com/vamseeachanta/assetutilities.git@main` as a CI-only step, or clone via a second `actions/checkout` with `repository: vamseeachanta/assetutilities` + `path: assetutilities`) and bake it into the workflow edit inventory. Update phase-2 acceptance to verify the sibling-dep install log shows success, not just that one matrix cell is green.
- Separate phase-1 and phase-2 into distinct commits (or distinct PRs). Add an acceptance gate between them: 'phase-1 commit pushed, one CI run observed with `jobs[] != []` before phase-2 commit is authored.'
- Replace the local smoke-test pre-push gate with either (a) a clean Docker container test that does not have `../assetutilities` on the filesystem, or (b) a 'run workflow against a feature branch first, observe CI result, then promote to main' step. Local `uv run pytest` on the developer workstation cannot validate the CI install path.
- Prove or disprove the YAML-parse diagnosis with `python -c 'import yaml; yaml.safe_load(open(...))'` or `yamllint` before execution. If the file parses clean, drop the DATABASE_URL edits from phase-1 (they're noise) and document the actual cause (deprecated actions). If it fails, record the parser error verbatim in the plan.
- Block execution on the `status:plan-approved` label drift. Add an acceptance criterion: 'user has explicitly re-confirmed approval in-thread after reading this plan artifact' — do not rely on the pre-applied label as approval authority.
- Tighten the TDD assertion to `rg 'upload-artifact@v4' --count` == 3 (exact count, specific action) rather than generic `@v4` grep with 3+ hits.
- Enumerate all version-pin decisions (`setup-python@v4`→v5, `setup-uv@v1`→v4, `codecov-action@v3`→v5) as explicit in-scope or out-of-scope items in §Files to Change, not as footnote flags.
- Remove the self-contradictory `docs/plans/README.md` checkbox or resolve it (either do the update or drop the checkbox).
- Reconsider T2 vs T3. If phase-3 is diagnostic-first with unknown root cause, split it into a separate issue rather than carrying an unbounded phase inside a T2 plan.
