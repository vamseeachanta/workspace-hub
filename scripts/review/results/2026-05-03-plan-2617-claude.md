## P1-1 — `xdist_group` does NOT serialize across worker boundaries when `--dist loadscope` is in effect

The plan claims `@pytest.mark.xdist_group("digitalmodel-wheel-build")` will serialize the three sibling tests within a single `pytest -n auto` run. This is partially true and partially wrong:

- `xdist_group` requires `--dist loadgroup` (or `--dist worksteal` in newer xdist) to take effect.
- The repo's `Makefile:23` runs `pytest -n auto --dist loadscope`. **`loadscope` ignores `xdist_group`**: it groups by file/module scope only.
- Result: the marker is silently inert in the canonical CI invocation. The plan's "belt-and-suspenders" layer provides zero in-session protection in practice.

**Fix:** either (a) drop the `xdist_group` claim entirely and rely on per-test `cwd` alone — which the plan already says is sufficient — or (b) document that the marker requires `--dist loadgroup` and propose a `Makefile` change. The current plan asserts both layers are active without verifying `--dist` compatibility.

**Severity:** P1 — the plan documents a defense layer that does not exist under the project's actual test invocation.

## P1-2 — Source-tree copy may break `--no-isolation` build because `[tool.uv.sources] assetutilities = { path = "../assetutilities", editable = true }` resolves relative to `cwd`

Plan §Risks #2 acknowledges this risk and waves it off ("setuptools reads `pyproject.toml` for project metadata only, not for uv sources"). That is wrong on two counts:

1. The copied `pyproject.toml` lands in `tmp_path/src_copy/pyproject.toml`. `../assetutilities` from `tmp_path/src_copy` resolves to `tmp_path/assetutilities` — which does not exist. uv WILL parse this file when `--no-isolation` runs `python -m build` because `build` invokes the configured backend (`setuptools.build_meta`), and the wrapper command is `uv run --no-sync ... python -m build`. uv resolves sources at command entry, not at backend dispatch.
2. Even if `uv run` itself doesn't trip on the missing path because of `--no-sync`, `setuptools.build_meta:get_requires_for_build_wheel` may invoke `pip` or read `[build-system].requires`, and any tool that re-reads `pyproject.toml` for the project metadata will see a `requires-python` and `dependencies` block referencing assetutilities by name (line 26: `"assetutilities>=0.0.7,<1.0.0"`) — which is a registry name, fine — but `[tool.uv.sources]` overrides that to local path during the active `uv run` process scope.

The copy strategy needs an explicit verification step (the plan says "Verify by single-test smoke run before claiming fix complete" — that is verification, not mitigation). If the smoke run fails, the plan has no fallback design.

**Fix:** plan must either (a) include a fallback "if the source-tree copy breaks, switch to filelock on `<repo_root>/build/` instead", or (b) preemptively scrub `[tool.uv.sources]` from the copied `pyproject.toml`, or (c) copy `assetutilities/` into `tmp_path/` alongside `src_copy/` so the relative path still resolves.

**Severity:** P1 — without a fallback, the recommended fix may not work at all and the plan would need to restart from the option-comparison table.

## P2-1 — Plan's recommended fix does NOT explain WHY the test is special to a future maintainer

The plan adds a `conftest.py` fixture and a marker but does not specify a **comment in the test itself** explaining the trap. A future maintainer copy-pasting this test as a template (which is exactly what happened — `test_yaw_moment_sweep.py` and `test_turning_circle_estimator.py` are clones) needs a load-bearing docstring/comment block at the test function:

> "DO NOT change `cwd=wheel_build_workspace` to `cwd=repo_root`. Setuptools' build dir is hardcoded at cwd; running `--no-isolation` with `cwd=repo_root` from multiple parallel pytest workers races on `<repo_root>/build/` and produces ENOENT from the build_wheel backend. See #2617."

Without this, the next person to add a fourth wheel-build test will copy from the unfixed test_turning_circle_estimator.py (if not yet updated) or skip the fixture, and the flake returns.

**Fix:** add to TODO checklist: "Add docstring + ABOUTME-style hazard comment to all three test functions naming #2617."

**Severity:** P2 — the plan covers the technical fix but not the social/maintenance contract.

## P2-2 — Acceptance criterion for cross-session vector is under-specified

Plan acceptance says: "Cross-session simulation (two parallel `pytest` invocations on the same checkout) passes 5/5." But the simulation command shown is:

```bash
( uv run pytest tests/naval_architecture/test_yaw_moment_sweep.py & ) ; \
  uv run pytest tests/naval_architecture/test_rudder_stock_torque_sweep.py
wait
```

This runs the YAW test ONCE alongside the RUDDER test ONCE. It does NOT exercise:
- Three-way concurrency (yaw + rudder + turning_circle simultaneously).
- The realistic `/whats-next` scenario (the issue's actual reproducer): two FULL pytest sessions, not just one test file each.

Also, "5/5" is too few iterations for a race condition with the observed flake rate (issue body shows ~50 % failure rate under contention; 5 reps gives p ≈ 0.03 of all-green by luck even without a real fix).

**Fix:** acceptance must require:
1. Three-process simulation (all three sibling tests, each in its own `pytest` invocation, started within a 1-second window).
2. Loop count ≥ 20 to give ≥ 99 % statistical confidence the flake is gone.
3. Run on ace-linux-1 specifically (issue body names that host as the reproducer).

**Severity:** P2 — green on the plan's acceptance does not statistically guarantee the cross-session race is fixed.
