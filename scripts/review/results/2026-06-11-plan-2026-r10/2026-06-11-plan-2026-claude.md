## Findings

1. **False `mailbox_empty: true` survives for newer replies on tracked `extracted` threads (the exact defect class R4/R8/R9 treated as blockers).** Plan §D7: "A newer message on a tracked `completed`, `awaiting-reply`, or `purged` thread is counted as `reactivation_pending`" — `extracted` is excluded. §D3 buckets "`extracted` with no action pending" as durable non-pending, but the snapshot carries no field distinguishing "no action pending" from "action pending", and `reactivation_candidates()` pseudocode iterates only "completed/awaiting-reply/purged tracked thread[s]". Consequence: an in-scope Gmail thread tracked as `extracted`, with a stored baseline and a strictly newer `latest_message_id` in the supplied inbox snapshot, contributes to no pending bucket — the report returns `mailbox_empty: true` while an unprocessed reply sits in the inbox. The asymmetry is internally incoherent: an extracted thread with a *missing* baseline blocks empty (`baseline_missing` rule, §D7), but an extracted thread whose baseline *proves a newer message exists* does not. The #2017 contract (`docs/design/email-as-queue.md:41-43`) limiting reactivation transitions to awaiting/completed/purged justifies the *state machine* edge set, not the *report* semantics — the plan never states or defends this exclusion. Either count newer-message-on-`extracted` in `reactivation_pending` (or a new pending bucket), or document the exclusion with rationale in D3/D7.

2. **Raced distinct no-trigger reactivations dedup against each other, contradicting D5's own invariant.** §D5 historical-retry rule: "If the caller lacks `cycle_id` and current state differs from `from_state`, search historical keys with the same `(account_id, thread_id, from_state, to_state, dedup_event_id)` and then filter candidates to the current snapshot `cycle_id`." In `prepare_event`, this branch runs *before* reactivation cycle assignment, and `reactivation_id` does not feed `dedup_event_id` (it stays `legacy:no-trigger`). So: checker A plans `reactivate_reply(reactivation_id=R2)` from a stale read; meanwhile R1's reactivation applied and current state advanced to `extracted` with cycle `reactivation:R1`. R2's event matches exactly one current-cycle candidate (R1's row, same `legacy:no-trigger` dedup_event_id) and is silently swallowed as an "idempotent retry" — despite carrying a distinct `reactivation_id`. The test `test_no_trigger_distinct_reactivation_cycles_require_distinct_reactivation_id` only covers the sequential path (state returned to `purged` first), so an implementation passes all listed tests while violating "Mixed no-id/id events do not dedup against each other" in spirit. Fix: when the incoming event carries `reactivation_id` or `triggering_message_id`, the historical match must also require candidate `cycle_id` equality with the *incoming event's derived* cycle id, not only the current snapshot's.

3. **`scripts/review/results/2026-06-11-plan-2026-r10/` already exists and is not in the plan's artifact list.** The plan header and Artifact Map enumerate "failed review rounds" through `...-r9/` only, and demand "a fresh R10 adversarial review" — but an r10 results directory containing a failed fanout (two zero-byte verdict files plus a `gemini.md.err`) already sits on disk from 18:18 today. Recording the fresh R10 into that directory silently mixes a failed run's residue with live verdicts; the plan's review-artifact ledger is already stale at draft time. Document/clean the failed r10 artifacts or advance the counter.

4. **The existing contract test `test_transition_retry_preserves_dedup_under_fresh_ts` (tests/email/test_state_machine_contract.py:31) appears nowhere in the TDD table.** The table lists `test_transition_retry_preserves_legacy_dedup_without_triggering_message` instead, and Files-to-Change says "Expand contract tests and remove xfail markers." If implementation renames the existing test, traceability to the #2017 contract (and the plan's own reproduction proof, which names the original test) breaks; if it keeps it, the TDD table is incomplete. State explicitly that the four existing test names are preserved verbatim.

5. **The scheduled-task entry is underspecified against the file's own conventions.** `config/scheduled-tasks/schedule-tasks.yaml` header mandates fields (`machines`, `requires`, `command`, `log`, `is_claude_task`) and existing entries are machine-scoped. The plan (D11, D10 task 4) says only "add a daily dry-run `email-queue-state.py sweep --dry-run`/report entry." The runtime state dir `~/.hermes/email-state/` exists (if at all) only on dev-primary, and the issue is labeled `machine:dev-primary` — without `machines: [dev-primary]` scoping the cron job fails or creates empty state dirs on other machines. `test_schedule_adds_daily_email_queue_dry_run` as specified ("schedule config | daily dry-run sweep/report entry") would not catch a missing machine scope.

6. **`sweep_grace` durability is asymmetric with snapshot durability.** Pseudocode specifies "tmpfile + fsync + os.replace" for snapshot/meta rebuild but says nothing about fsync on the JSONL append itself. A crash after snapshot rebuild but with the appended purge rows still in the page cache can yield a snapshot ahead of the durable log — the meta hash/offset checks (D11 freshness contract) would then fail closed on next read, which is recoverable, but the plan should state whether log appends are fsynced or that the freshness contract is the designated recovery path. One sentence resolves it; silence leaves the implementer to guess.
