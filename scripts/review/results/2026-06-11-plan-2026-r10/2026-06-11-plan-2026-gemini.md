## Findings

1. Plan §Pseudocode for `sweep_grace` apply mode creates an infinite loop. The code loops `while eligible completed records remain:` and fetches `up to batch_size still-completed records`. If a record is selected but skipped due to `reactivation_precheck` (e.g., pending replies or missing baselines), the plan states it "skips selected records" and does not append the purge event. Because no state transition is appended, the rebuilt snapshot will still represent the thread as `completed`. The loop will perpetually see this same record as eligible and re-select it, spinning infinitely. The logic must explicitly exclude known-skipped threads from its query or exhaust a pre-calculated candidate list.
2. Plan §Pseudocode for `ensure_labels` introduces a `TypeError` crash. To resolve an R9 subscripting defect, the plan uses `client = clients_by_account.get(alias) or gmail_client_factory(alias)`. However, the function signature defaults to `gmail_client_factory=None`. If the CLI runs with `apply=True` and no factory is supplied, this evaluates to `None(alias)`, which will crash with `TypeError: 'NoneType' object is not callable` before the `require client` safety check can ever trigger. The factory must be checked for callability.
3. Plan §D7 (Inbox Snapshot Contract) fails to define comparison behavior when the supplied inbox snapshot lacks baselines. The plan correctly specifies that if the *local tracked state* lacks a baseline, the report increments `baseline_missing_count`. However, the contract defines `latest_message_id` and `received_at_utc` as "optional" in the inbox snapshot itself. If the local state *has* a stored baseline but the supplied inbox snapshot record lacks both fields, `pending_work_report()` and `reactivation_candidates()` cannot determine if the snapshot represents a "newer message." The plan leaves this comparison undefined, risking exceptions or silent false-negatives in the mailbox-empty check.
