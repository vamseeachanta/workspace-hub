### Verdict: MAJOR

### Summary
Solid MVP-narrowed plan with strong resource intelligence, explicit identity contract, and good scope discipline — but several defects warrant changes before implementation: a referenced config file is never listed in Files to Change, the `domain-unresolved` status has no TDD row, wiki-side non-canonical `doc_key` (e.g. `md5:`) behavior is untested, and the "commit `_summary.md` as baseline" acceptance criterion conflicts with weekly scheduled overwrites.

### Issues Found
- [P2] Config-file contract is undefined: pseudocode calls `load_config(args.config)` for domain map, slug rules, and suggested-page template, but `Files to Change` does not list any config file to create, nor does it specify that defaults are baked in. The detector cannot be implemented deterministically from the plan as written.
- [P2] Status enum lists `domain-unresolved` but the TDD Test List has no row covering this branch — untested classification path.
- [P2] Wiki-side non-canonical `doc_key` values (e.g., a wiki page carrying `doc_key: md5:...` or `doc_key: <bare-hex>`) are not enumerated in tests. Pseudocode sends all non-`sha256:` into `wiki_schema_warnings` but the per-branch behavior (esp. `md5:` vs bare-hex vs missing) is not separately verified.
- [P2] Dedup precedence (`index > ledger > dde > online`) and the conditional 'online-resource-registry contributes source candidates only for entries carrying canonical `doc_key`' rule have no explicit tests.
- [P2] Acceptance criterion says `docs/reports/wiki-coverage-gaps/_summary.md` is committed from the first run as baseline evidence, but the same file is regenerated by the weekly scheduled task — the plan does not specify whether subsequent runs overwrite the tracked baseline, append history, or are redirected elsewhere. As written, the scheduled task will dirty the working tree every week.
- [P3] `derive_domain_slug` logic is hand-waved in pseudocode; only one normalization test (`test_domain_slug_kebab_case`) covers it. Edge cases (unknown domain, ambiguous path, frontmatter-vs-path conflict) are untested — precisely the cases that produce `domain-unresolved`.
- [P3] The 5-minute runtime acceptance criterion has no measurement methodology specified — whether it is enforced in CI, measured once manually on the 19K-page `marine-engineering` tree, or asserted via a perf test is not stated.
- [P3] Open questions on git-tracking of `<domain>.yaml` and the top-500 truncation default are deferred to approval — acceptable, but the plan should explicitly name these as blockers of final lock rather than soft 'flag for user' items if the implementation PR will need them resolved.
- [P3] `_summary.md` schema lists `skipped_inputs` alongside integer counts, but skipped_inputs is a list of paths, not a count — the shape of `_summary.md` is ambiguous (table of counts vs. mixed structure).
- [P3] `scripts/cron/validate-schedule.py` is cited in acceptance criteria but is not attested as existing in the Evidence block; if the script is absent or uses a different name, this criterion cannot be met.

### Suggestions
- Add a 'Create: scripts/knowledge/config/wiki-gaps.yaml' (or equivalent) row to Files to Change with the exact schema for domain map, slug rules, and suggested-page template — OR explicitly state that defaults live in-module and `--config` is optional.
- Add TDD rows for: (a) `domain-unresolved` (valid sha256 but unresolvable domain), (b) wiki page with `doc_key: md5:...` (legacy identity on wiki side), (c) dedup precedence when the same `doc_key` appears in `index.jsonl` and `standards-transfer-ledger.yaml`, (d) online-resource entry without canonical `doc_key` (expected: not a source candidate).
- Resolve the `_summary.md` overwrite conflict: either (i) commit baseline to a dated path like `_summary-2026-04-23.md` and let the scheduled task rewrite a `_summary.md` pointer, or (ii) gitignore `_summary.md` and commit a separate `BASELINE.md` that is stable.
- Specify perf-verification path: e.g., `test_runtime_under_5min_on_real_corpus` as an opt-in slow test gated by an env var, or a one-shot measurement recorded in the PR description.
- Lock the two open questions (git-tracking of `<domain>.yaml`; top-500 truncation default) before status:plan-approved — they change both Files-to-Change and acceptance criteria.
- Attest `scripts/cron/validate-schedule.py` existence in the Evidence block (same treatment as the other file-existence checks) so the scheduled-task acceptance criterion is verifiable at plan time.
- Consider splitting the `_summary.md` acceptance criterion into structured YAML (`_summary.yaml`) plus a human-readable markdown wrapper — YAML is easier to assert against in tests and matches the ecosystem's YAML-first convention for agent-facing structured data.

### Questions for Author
- Where does the config come from? Is there a file to create, or are all defaults (domain map, slug rules, suggested-page template) baked into the module?
- Is `_summary.md` intended to be overwritten by every scheduled run, or is the first run's copy meant to be a pinned baseline that later runs write elsewhere?
- Should `<domain>.yaml` gap reports be committed, gitignored, or published to a separate artifact sink (e.g., GitHub Issues, an index repo)? The implementation PR cannot merge without this answer.
- What is the exact classification when a wiki page carries `doc_key: md5:<hex>` — `wiki-schema-warning` (plan text suggests yes) or a distinct `wiki-identity-legacy` bucket? Test coverage depends on this choice.
- How will the 5-minute runtime budget be verified before merge — manual measurement against the live 19K-page marine-engineering tree, or a synthetic perf test?
- Does `scripts/cron/validate-schedule.py` currently exist? If not, is writing/fixing it in scope for this plan or a separate prerequisite?
- If the detector runs weekly and produces updated `_summary.md`, who commits the update — the scheduled runner, a follow-up agent, or is the file gitignored after baseline commit?
