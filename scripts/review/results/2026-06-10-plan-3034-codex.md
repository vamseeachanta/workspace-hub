### Verdict: MAJOR

### Summary
The plan is not approval-ready. It misidentifies the cron source of truth, does not model the statusline’s actual quota-file fallback behavior, and leaves existing statusline tests in conflict with the proposed missing-timestamp semantics.

### Issues Found
- MAJOR: The scheduling root cause and edit target are wrong. The supplied plan says to add `provider-utilization-refresh.sh` to `scripts/cron/crontab-template.sh`, but that file is explicitly legacy/read-only and says to edit `config/scheduled-tasks/schedule-tasks.yaml` instead (`scripts/cron/crontab-template.sh:2-10`). The canonical YAML already declares `provider-utilization-refresh` every 4h at `20 */4 * * *` for `dev-primary`/`ace-linux-1` (`config/scheduled-tasks/schedule-tasks.yaml:243-256`). `setup-cron.sh` reads that YAML, not the legacy template (`scripts/cron/setup-cron.sh:21-24`, `scripts/cron/setup-cron.sh:94-120`). The plan should diagnose why the existing scheduled task is not keeping the cache fresh: live crontab convergence, host targeting, logs, or script failure.
- MAJOR: The proposed single `quota_file_age_ok` computed from “first existing quota file” is incorrect for the current source logic. `extract_pct` reads `.week_pct` from `quota_primary`, but falls back to `.pct_remaining` from `quota_cache` (`.claude/statusline-command.sh:65-78`). `reset_days` separately scans both files for reset metadata (`.claude/statusline-command.sh:120-131`). A single age for the first existing file can mark a provider fresh while its actual value came from a stale fallback file, or stale while its actual value came from a fresh fallback file. The implementation needs provider-level source tracking, not one global freshness boolean.
- MAJOR: The plan’s “missing timestamp is stale” requirement conflicts with the stated “existing statusline suites unchanged” regression path. Existing fixtures in `tests/statusline/test_weekly_reset.bats` and `tests/statusline/test_combined_wrapper.bats` omit a top-level `timestamp` (`tests/statusline/test_weekly_reset.bats:26-33`, `tests/statusline/test_combined_wrapper.bats:12-18`). If missing timestamps render `?`, those tests either need fixture timestamps added or assertions updated. The plan claims fresh output is byte-identical and existing suites are unchanged, but it does not account for these timestamp-less fixtures.
- MAJOR: The supplied plan calls `provider-utilization-refresh.sh` “lightweight: one app-server RPC + report regeneration,” but the script runs five additional generators after `query-quota.sh --refresh --log` (`scripts/cron/provider-utilization-refresh.sh:21-32`). Two of those perform live GitHub issue list calls (`scripts/ai/provider-work-queue.py:38-44`, `scripts/ai/provider-kanban.py:454-462`) and the script has no flock or non-overlap guard (`scripts/cron/provider-utilization-refresh.sh:1-48`). A 4h cron change must either use the already-canonical task with an explicit safety review, or schedule a slim quota-only command. The current plan does not prove the full refresher is safe for that cadence.
- MINOR: The Claude “live-sourced stays unmarked” claim is incomplete. The percentage is live when `.rate_limits.seven_day.used_percentage` exists (`.claude/statusline-command.sh:163-169`), but `c_days` can still fall back to file-sourced `reset_days claude` when `week_resets_at` is absent (`.claude/statusline-command.sh:196-197`). If a stale quota file carries Claude reset metadata, the segment can mix live percent with file-sourced countdown without a stale marker. The plan should either forbid that fallback when `week_used` is live, or mark any file-sourced suffix component stale.
- MINOR: `STATUSLINE_QUOTA_MAX_AGE_HOURS` is proposed without validation or bounds. The plan should specify behavior for empty, nonnumeric, zero, negative, and very large values, and add tests. Otherwise a local env override can silently disable the warning by setting an enormous threshold, which is the same class of policy-bypass concern the prompt asks to scrutinize.

### Suggestions
- Replace the cron step with a discovery step: inspect `config/scheduled-tasks/schedule-tasks.yaml`, `scripts/cron/setup-cron.sh --dry-run`, live `crontab -l`, and `logs/quality/provider-utilization-refresh-*.log` before proposing a schedule change.
- Make `extract_pct` return both value and source file, or add provider-specific freshness helpers that evaluate the exact file used for each displayed value/suffix.
- Update existing statusline fixtures with explicit fresh timestamps if byte-identical fresh regression is required.
- If the goal is only cache freshness, schedule `scripts/ai/assessment/query-quota.sh --refresh --log` via the canonical YAML rather than the full report pipeline.
