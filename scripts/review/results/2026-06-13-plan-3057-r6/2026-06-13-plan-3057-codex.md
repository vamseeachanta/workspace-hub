## Findings
1. Plan leaves a destructive selection mismatch in `cron_apply.py`. The plan says `setup-cron.sh` and `cron_apply.py` will share rendering while preserving existing selection behavior (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` lines 337-354, 395, 443, 508-509). Current `setup-cron.sh` selects cron rows by hostname/alias machine tokens (`scripts/cron/setup-cron.sh` lines 109-122), but current `cron_apply.py` selects by roles plus a single `machine_id` (`scripts/cron/cron_apply.py` lines 148-153; `scripts/cron/cron_transaction.py` lines 205-263). On `ace-linux-1`, `setup-cron.sh` will select `solver-watch-results` and `solver-dashboard` because both are pinned to `machines: [ace-linux-1]` (`config/scheduled-tasks/schedule-tasks.yaml` lines 665-693), while the planned canonical `dev-primary` role path will not select them because their role is `sim-worker`, not `control-plane` (`config/workstations/registry.yaml` lines 7-18). `plan_cutover` drops cataloged out-of-managed-block lines instead of preserving them (`scripts/cron/cron_transaction.py` lines 340-343, 360-367), so a transactional cutover can silently remove catalog tasks that setup-cron would install.

2. The cross-path parity test is too narrow to catch finding 1. `test_setup_cron_and_cron_apply_use_shared_renderer_for_same_task` only uses “a fixture task selected by both setup-cron's `machines` path and cron_apply's role path” (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` line 415). That explicitly avoids the real mismatch class where a task is selected by setup-cron’s alias-machine path but not by cron_apply’s canonical-role path, such as `solver-watch-results` / `solver-dashboard` (`config/scheduled-tasks/schedule-tasks.yaml` lines 665-693).

3. The full governed repo-set regression is not pinned by automated tests. Acceptance requires the live governed set from `required`, `optional`, and `non_tier1_machine_access_current` (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` line 444), and source currently enumerates those three buckets (`scripts/cron/repo-ecosystem-hygiene-audit.sh` lines 292-305). But the existing test helper only reads `tier1_baseline.required` (`scripts/cron/tests/test_repo_ecosystem_hygiene_audit.py` lines 67-69), and the plan’s TDD additions for hygiene cover timeout defaults and probe timeout behavior only (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` lines 423-424). A live closeout proof is not a durable regression test for the bucket coverage claim.

## Blockers
1. Resolve the setup-cron vs cron_apply selection mismatch before implementation approval. Either make cron_apply selection alias-token aware for legacy `machines` pins, or explicitly preserve cataloged-but-unselected machine-pinned lines instead of dropping them.
2. Add a parity/regression test for a task selected by setup-cron via `ace-linux-1` machine pin but not by `dev-primary` roles, using the real `solver-watch-results` / `solver-dashboard` shape or an equivalent fixture.
3. Add an automated hygiene test proving `governed_repo_names()` includes required, optional, and `non_tier1_machine_access_current`, not only required repos.
