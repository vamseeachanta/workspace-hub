### claude

- **(MAJOR — load-bearing) The shared renderer's `schedule_by_machine` token-precedence order contradicts both setup-cron and the plan's own AC#6, and will *cause* the silent retiming AC#6 exists to prevent.** The registry has `dev-primary` (canonical name), `ace-linux-1` (hostname), `vamsee-linux1` (alias) as **one machine** (`registry.yaml:7–9`). `provider-dream-bridge` defines *different* schedules per key: `dev-primary: "0 4 * * *"` vs `ace-linux-1: "5 4 * * *"` (`schedule-tasks.yaml:374–375`); `hermes-claude-bridge` likewise `dev-primary:"20 4"` vs `ace-linux-1:"25 4"` (`:412–413`). Resolution order is therefore outcome-determining:
- **setup-cron.sh** (the plan's named parity reference) iterates `[hostname, *sorted(machine_tokens)]` (`setup-cron.sh` schedule block) → `ace-linux-1` is matched first → **"5 4 * * *"** / **"25 4 * * *"** — these are what is *currently installed* on this host.
- **Plan renderer pseudocode** builds `tokens = lower([machine_name, machine.hostname] + machine.hostname_aliases)` = `[dev-primary, ace-linux-1, …]` and takes "first … where token in machine_tokens" (plan `:320, :330`) → `dev-primary` is matched first → **"0 4 * * *"** / **"20 4 * * *"**.
-    Since the plan refactors setup-cron to *consume* this renderer (Files-to-Change `:395`; AC `:443`), the refactor would silently change ace-linux-1's installed bridge schedules from `5 4`/`25 4` to `0 4`/`20 4` — directly violating AC#6's literal text: "*provider-dream-bridge and hermes-claude-bridge keep their **ace-linux-1** `schedule_by_machine` values … preventing silent 5-minute retiming*" (`:442`). The plan pins the *wrong* precedence.
- **(MAJOR — the parity test cannot catch Finding 1.)** `test_setup_cron_and_cron_apply_use_shared_renderer_for_same_task` (`:415`) asserts setup-cron-via-renderer == cron_apply-via-renderer are "byte-identical." After the refactor **both** call the same renderer, so both produce the same (wrong) `0 4`/`20 4` and the test passes green. `test_cron_render_matches_setup_cron_context_semantics` (`:413`) only asserts `schedule_by_machine` "resolves from canonical/hostname/alias tokens" — it tests *that* resolution happens, not *which key wins when canonical and hostname are both present with different values*. No test pins a golden pre-refactor schedule. **Blocker fix:** the renderer must reproduce setup-cron's current precedence (hostname/`sorted`-prioritized, not canonical-name-first), and add a regression test with hardcoded golden values (`provider-dream-bridge → "5 4 * * *"`, `hermes-claude-bridge → "25 4 * * *"` for this host) asserted against the renderer output — not against the other renderer-consuming path.
- **(MINOR) Cron-health hygiene-marker logic is under-specified for its interaction with the existing STATUS/counter flow.** The current script guards generic-error escalation with `if [[ "$STATUS" == "OK" ]]` before doing `STATUS=ERROR; PROBLEM_TASKS++` (`cron-health-check.sh:244–254`), precisely to avoid double-counting when a log is already `STALE`/`MISSING`. The plan's pseudocode `if latest_hygiene_marker == "ERROR": mark task ERROR` (`:378`) carries no equivalent guard and the TDD list has no case for "hygiene `status=ERROR` on an already-STALE log." A literal implementation risks double-incrementing `PROBLEM_TASKS` or clobbering a `STALE` STATUS. Specify the precedence (STALE/MISSING vs hygiene-ERROR) and add a combined-state test.
- **(MINOR) `TOTAL_TIMEOUT_SEC < 600` is asserted as an invariant but the "600s gap" is an un-pinned property of the catalog.** `test_repo_hygiene_timeout_defaults_are_production_safe` (`:423`) hardcodes "total < 600s gap," and `test_validate_schedule_repo_hygiene_contract` (`:431`) checks hygiene-before-cron-health ordering but the plan does not add an assertion tying the literal `35 5`/`45 5` interval to the 480s budget. If the catalog schedule is later edited, the 480/600 relationship silently rots with no failing test. Add a schedule-derived assertion (compute the actual gap from `schedule-tasks.yaml`, assert `TOTAL_TIMEOUT_SEC < gap`) rather than a magic `600`.
- **(MINOR, verify-only) Fallback-key `[:60]` collision risk for the rendered `notification-purge` key is unaddressed.** `catalog_commands` truncates to 60 chars (`cron_apply.py:127`). The rendered key becomes `cd /mnt/local-analysis/workspace-hub && find logs/notif…` — the host-path prefix consumes ~38 of the 60 chars, leaving little task-discriminating tail. With only one fallback-keyed task today (Claude r4 confirmed) this is latent, but the plan's raw+rendered union should note that a second long-path fallback task could collide; at minimum the test should assert the rendered key is non-empty and distinct from the raw key.

### codex

- Plan leaves a destructive selection mismatch in `cron_apply.py`. The plan says `setup-cron.sh` and `cron_apply.py` will share rendering while preserving existing selection behavior (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` lines 337-354, 395, 443, 508-509). Current `setup-cron.sh` selects cron rows by hostname/alias machine tokens (`scripts/cron/setup-cron.sh` lines 109-122), but current `cron_apply.py` selects by roles plus a single `machine_id` (`scripts/cron/cron_apply.py` lines 148-153; `scripts/cron/cron_transaction.py` lines 205-263). On `ace-linux-1`, `setup-cron.sh` will select `solver-watch-results` and `solver-dashboard` because both are pinned to `machines: [ace-linux-1]` (`config/scheduled-tasks/schedule-tasks.yaml` lines 665-693), while the planned canonical `dev-primary` role path will not select them because their role is `sim-worker`, not `control-plane` (`config/workstations/registry.yaml` lines 7-18). `plan_cutover` drops cataloged out-of-managed-block lines instead of preserving them (`scripts/cron/cron_transaction.py` lines 340-343, 360-367), so a transactional cutover can silently remove catalog tasks that setup-cron would install.
- The cross-path parity test is too narrow to catch finding 1. `test_setup_cron_and_cron_apply_use_shared_renderer_for_same_task` only uses “a fixture task selected by both setup-cron's `machines` path and cron_apply's role path” (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` line 415). That explicitly avoids the real mismatch class where a task is selected by setup-cron’s alias-machine path but not by cron_apply’s canonical-role path, such as `solver-watch-results` / `solver-dashboard` (`config/scheduled-tasks/schedule-tasks.yaml` lines 665-693).
- The full governed repo-set regression is not pinned by automated tests. Acceptance requires the live governed set from `required`, `optional`, and `non_tier1_machine_access_current` (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` line 444), and source currently enumerates those three buckets (`scripts/cron/repo-ecosystem-hygiene-audit.sh` lines 292-305). But the existing test helper only reads `tier1_baseline.required` (`scripts/cron/tests/test_repo_ecosystem_hygiene_audit.py` lines 67-69), and the plan’s TDD additions for hygiene cover timeout defaults and probe timeout behavior only (`docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md` lines 423-424). A live closeout proof is not a durable regression test for the bucket coverage claim.
