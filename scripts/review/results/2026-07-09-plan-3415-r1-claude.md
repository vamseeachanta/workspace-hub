## Findings

1. **Resource-intel enumeration is inaccurate (plan line 21).** The plan states `county_reference.py` "contains reference rows for Texas, Oklahoma, and three eastern Colorado counties." At the pinned commit `SUPPORTED_STATES` covers **seven** states (TX, NM, OK, ND, CO, WY, LA), and the three CO counties are Weld (northeastern DJ Basin) and Adams/Arapahoe (Denver metro) — not plainly "eastern Colorado." The load-bearing negative (no Rio Blanco, no Garfield) is verified true, but the understated coverage mildly flatters the "Colorado county coverage is unproven" narrative. Correct the sentence. MINOR.
2. **Scorecard is circular with the test suite — comparison cannot change the outcome.** Acceptance criterion 4 and `test_exact_candidate_set` / `test_county_cluster_marks_conditional_members` (TDD table) hardcode Colorado/Piceance + Rio Blanco-primary. Once those tests exist, the TX/OK/CO weighted scorecard (AC 3, `build_candidate_scorecard`) can never select a different winner without failing the suite — the "comparison" documents a pre-made decision rather than making one. The plan does disclose this ("**Approval decision:** Approving this plan will accept Colorado/Piceance…"), so it is a transparent design, but AC 3 reads as if declared weights drive the selection. Add one sentence stating the scorecard is decision *rationale documentation* locked at plan approval, not a live decision procedure. MINOR (disclosed), would be MAJOR if undisclosed.
3. **The anti-drift test has no automated enforcement.** No workflow references `tests/docs/` (`baseline-check.yml` runs only `tests/test_deduplication_fix.py` + `tests/ci_smoke/`; `skills-validation.yml` runs enforcement/cron tests). `test_html_matches_yaml_decision`'s promise that "human and machine artifacts cannot drift" holds only when someone manually runs `uv run pytest tests/docs/...`. Per `.claude/rules/patterns.md` this is Level 2 advisory at best; either say so in the plan or name the workflow that will run it. MINOR.
4. **Identical-to-the-second evidence timestamps.** Issue statuses and federal counts both claim `2026-07-09T22:57:00-05:00` — two distinct verification acts stamped with one identical round-number timestamp, in a plan whose whole thesis is claim-level provenance (`reject claims without … observed timestamp`). Use actual observed timestamps. Cosmetic but on-thesis. MINOR.
5. **Header inconsistency: `Project: landman-project-desk` with `Client: N/A`.** Per the template, `Project:` exists to be consumed by `check-wiki-sibling-frontmatter.py` Rule E and is meaningful only under a client; wiki-sibling-routing Rule D forbids `project:` outside client wikis. The plan touches no wiki content, so `Project:` should be blank/N/A or clearly marked as an informal tag. MINOR.
