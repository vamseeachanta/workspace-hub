## Findings

### MAJOR-but-non-blocking

1. **False-positive risk under unexpected `CLAUDECODE` exports.** If a developer manually exports `CLAUDECODE=1` in their `~/.bashrc` (or a wrapper script does for unrelated reasons), the fanout's codex leg becomes silently unusable — UNAVAILABLE with a "running under Claude-Code Bash" reason that may not be true. Mitigation in plan's Risks section says "the override (`CLAUDECODE= bash plan-review-fanout.sh ...`) is documented." But the *guard's INCOMPATIBLE message* doesn't mention this override path — operators reading the codex artifact won't know they can unset the var.

   **Suggested resolution:** extend the INCOMPATIBLE message to read `"...; dispatch fanout from a plain terminal OR unset CLAUDECODE (e.g., 'env -u CLAUDECODE bash scripts/review/plan-review-fanout.sh ...') for Codex review)"`. One-line change to the guard's `echo` statement.

### MINOR

2. **Test mechanism subtlety not documented.** The new test uses `CLAUDECODE=1 run_wrapper_under_mocks "$td"`. This pattern works in bash (the env var propagates into the function's `()` subshell and reaches the wrapper), but it's not obvious why — and the existing `PLAN_REVIEW_CODEX_VERSION="..." run_wrapper_under_mocks` test uses the same idiom without comment. A drive-by reader could mistake the prefix-assignment for a no-op if they don't know bash function-call env semantics.

   **Suggested resolution:** add a brief inline comment in the new test (one line): `# CLAUDECODE=1 prefix-assignment propagates into the function's () subshell and reaches the wrapper.` Cosmetic but reduces future-reader confusion.

3. **Open question about process-tree defense-in-depth lacks a trigger.** Plan's Risks section says "env-var only for v1; revisit if env-var proves insufficient" but provides no observable that defines "insufficient." Could be tighter.

   **Suggested resolution:** name the trigger explicitly: "Revisit if a fresh-fanout failure attributable to a missed Claude-Code-Bash environment surfaces (e.g., CLAUDECODE not set but codex still hangs). Track via [follow-up issue]."

4. **`INCOMPATIBLE` message length (~200 chars).** Consistent with existing version-guard messages (which are also long). Cosmetic; not a blocker.
