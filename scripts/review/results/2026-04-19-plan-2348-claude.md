### F2 — HIGH (scope gap contradicting plan's own analysis) — LinkedIn should be removed from `SOURCE_ALLOWLIST` in this plan, not deferred

**Evidence:**
- Plan line 188-191: "linkedin.com — ToS: prohibits scraping; history of enforcement (hiQ remand 2022) ... **Decision: ELEVATED RISK. Consider removing or replacing with a lawful alternative**".
- Plan line 212-213 §C: "(Optional, deferred) Remove LinkedIn from allowlist — Not in this plan's scope — flagged as a follow-up issue."
- Plan line 311 Q2: "Should LinkedIn be removed from `SOURCE_ALLOWLIST` given elevated enforcement risk? Out of scope for this plan."

The plan argues LinkedIn is materially more enforcement-risky than the other three sources (Supreme Court remand, active enforcement program, explicit CFAA theories), then defers the one action that directly reduces that risk. The plan's own TOS_REVIEW.md template escalates LinkedIn to "ELEVATED RISK" in writing. Shipping a document that says "this source is elevated-risk" while the source stays in the allowlist is worse than either acting on it or not writing the document — it establishes knowledge without mitigation, which is the classic shape of a documented-but-unremediated liability.

**Why this matters:** the entire urgency frame of #2348 (pause the cron, "legal exposure is ongoing every Monday") justifies in-scope removal of the single highest-risk source. The 1-line diff (`SOURCE_RATE_LIMITS.pop("linkedin")` or equivalent) is cheaper than the robots.txt fix the plan is already doing.

**Recommendation:** Either (a) remove LinkedIn from `SOURCE_ALLOWLIST` and `SOURCE_RATE_LIMITS` in Commit 2, document the removal in `TOS_REVIEW.md`, and note the loss-of-coverage in `dashboard.md` header; or (b) downgrade the `TOS_REVIEW.md` LinkedIn language from "ELEVATED RISK" to match whatever the user actually wants. The current state — document the risk, leave the source in — is the worst of both paths.

### F3 — HIGH (wrong default) — "default ALLOW on robots unreachable" contradicts the plan's stated posture

**Evidence:**
- Plan pseudocode line 150: `print(f"  [WARN] robots.txt unreachable for {netloc}: {e}; defaulting to ALLOW")`.
- Plan acceptance criterion line 268: "robots.txt fetch failures default to ALLOW with `[WARN]` (don't hard-fail the scan)".
- Plan adversarial-review section line 335 already flags this exact question: "Is 'default ALLOW on robots unreachable' the right choice, or should it be 'default DENY'?"

The plan asks this question then pre-answers it "ALLOW" in the code. Given the plan's framing — "legal exposure is ongoing", cron paused, public repo, forged UA — the posture is compliance-first. The correct default under compliance-first posture is DENY: if we cannot verify the site allows us, do not fetch. The plan's justification ("don't hard-fail the scan") prioritizes scan completeness over the compliance posture it claims to establish.

**Why this matters:** robots.txt unreachable is not a rare edge case on a forged-UA scraper. A site that detects the scraper may serve 403/404 specifically for `/robots.txt` (or for the scraper's UA). Under the current plan's rule, that triggers the "unreachable → ALLOW" branch — exactly the path an adversary would want. DENY-on-unreachable collapses this.

**Recommendation:** Change default to DENY. If the scan ends up with near-zero results because a source blocks robots.txt reads, that is a *correct* signal that the source does not want us; handle it by filing a follow-up issue, not by defaulting to fetch. If the user explicitly rejects DENY, document the choice in `TOS_REVIEW.md` under "Residual risk acknowledgement" so the decision is visible.

### F4 — MEDIUM (unverifiable legal artifact) — "cease-and-desist runbook" is beyond the agent's authoring scope without legal review

**Evidence:**
- Plan line 208-209 TOS_REVIEW.md template: "Any cease-and-desist email from any listed source terminates use of that source immediately and triggers an allowlist removal PR within 24 hours."
- Plan acceptance criterion line 269: "`TOS_REVIEW.md` created, listing all four sources with ToS URL + decision + residual risk + C&D runbook".
- Plan line 315-317 known risks: "ToS review is inherently a legal-judgment call; the agent is not a lawyer ... residual-risk acknowledgement is not a legal shield. Noted."

The plan acknowledges it is not a legal document but then specifies a legally-consequential runbook (what to do on C&D receipt, within what SLA, who owns response). A C&D is a legal demand — recommending a fixed 24h response window without counsel review is itself a risk (too short could be harmful if investigation is needed; too long is obvious). An author-by-agent runbook here creates an artifact that looks authoritative but has no legal weight, which is the shape of an expert-impostor document.

**Why this matters:** this is the one part of the plan that actively creates new liability surface rather than reducing it. If a real C&D arrives and someone follows this runbook literally, the response may be worse than an ad-hoc response with counsel.

**Recommendation:** Reframe the section as "Observed-exposure response — operational only". Keep the allowlist-removal PR step (that is an operational, non-legal action: git commit to turn off a scraper). Strip the 24h SLA. Add an explicit line "On receipt of any legal notice, do not respond without counsel; operational action in this runbook (removing the source from the allowlist) is a separate decision from any legal response." Flag to user that the legal-response portion needs counsel review.

### F5 — MEDIUM (rollback confusion) — "rollback" after cron pause is un-pausing; plan's three-commit structure makes un-pausing a new commit, not a revert

**Evidence:**
- Plan line 281: "Three-commit structure (Commit 0 is conditional on user approval)". Commit 0 pauses. Commits 1-2 do docs + robots.txt. Commit 3 un-pauses.
- Plan line 284: "Rollback: `git revert <commit0-sha>` restores the weekly Monday schedule." — but if the goal of this work is to land robots.txt FIRST and then resume cron, a straight revert of commit 0 would resume cron *without* the robots.txt fix landed if commits 1-2 failed.
- Reviewer prompt observation: "the cron is already paused; the 'rollback' question is actually 'roll forward to what state?'" — plan does not address the state machine explicitly.

The plan has four possible terminal states (paused, paused+docs, paused+docs+robots, unpaused+docs+robots), but the "rollback plan" treats each commit as independently revertible without defining which state is the safe resting state on failure. If commit 2 (robots.txt code) fails testing, the right action is NOT `git revert commit1` — that would leave cron still paused but docs gone. The resting state should be "cron stays paused until robots.txt lands green" — that is a policy rule, not a revert rule.

**Why this matters:** the plan will be executed across multiple sessions; whoever resumes does not necessarily have the four-state mental model.

**Recommendation:** Add a state-machine note to §Rollback:
- Safe resting states: (paused), (paused+docs+robots), (unpaused+docs+robots).
- Unsafe resting states: (paused+docs), (unpaused+docs-only), (unpaused+docs+partial-robots).
- Rule: never commit un-pause (commit 3) unless commits 1 and 2 are both green and tests pass. On test failure between commits 1 and 2, resting state is (paused+docs) — explicitly documented as "OK temporarily but not OK as a ship state".

Since the cron is already paused, the "Commit 0 (optional)" framing is moot — drop it and renumber to Commits 1/2/3. Commit 3 (resume cron) becomes the conditional one.
