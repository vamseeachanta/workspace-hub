## Findings
1. The execution interface is internally contradictory. Plan lines 159-168 and 214-217 require the runner to accept a command and execute it with argv preservation, without `shell=True` or command-string interpretation. The actual repository-sync command in `config/scheduled-tasks/schedule-tasks.yaml:847-850` is a shell program containing `cd`, `&&`, and `>>`; `scripts/cron/cron_render.py:164-171` preserves that compound command as a string. The plan never defines a structured argv schema or moves working-directory/redirection handling outside the command. The proposed runner therefore cannot execute the canonical command under its own security rules.

2. Signal handling can reintroduce the exact overlap defect. Plan lines 169, 208, and 255 require lock release “on signal” and test only that the next run can acquire it. They do not require forwarding the signal to the child/process group, waiting for the mutator to terminate, or retaining the lock while a descendant remains alive. If the runner exits while `scripts/repository_sync` continues, the next cron tick can acquire the released lock and start a second mutator. This conflicts with acceptance criterion line 272 and with the mutation boundary at `scripts/cron-repository-sync.sh:18`.

3. The state machine marks normal completed runs as failures. Plan lines 166-168 say the record retains an exit result, but inspection at lines 175-182 returns `stale_pid` whenever the recorded PID is absent. A successfully completed runner necessarily leaves an absent PID unless its state is deleted, yet no completed-success/completed-failure/never-started branch or deletion protocol exists. Cron-health then maps stale identity to exit 1 at lines 192-195. The issue explicitly requires distinguishing successful completion, but neither Task 4 nor the TDD list contains that state.

4. Contention evidence has an unresolved lost-update race. The single `state_file` in plan lines 147-152 is used for active-run identity, results, and contention. Lines 163-168 and 216-217 require the lock loser and owner to perform independent atomic whole-file replacements. Atomic rename prevents torn files, not logical lost updates: the contender can overwrite the owner record, and the owner’s later result can erase the overlap evidence. The inspection rule “if contention evidence is newer than the run” at line 180 does not specify a locked merge, separate contention journal, or monotonic sequence. Acceptance criterion line 273 therefore is not established.

5. Lock scope is unresolved at the mutation boundary. Plan line 222 says the rendered catalog command will contain the runner, while line 306 admits that direct wrapper invocation may bypass it and only says behavior will be “explicit.” The actual mutation occurs through `scripts/cron-repository-sync.sh:18`. Tests that invoke the rendered runner do not prove that another caller invoking the wrapper or `scripts/repository_sync` cannot overlap. This contradicts the unqualified deliverable at line 139 and acceptance criterion line 272. The plan must name the closest enforced boundary and test guarded and bypass paths.

6. A required runtime-health state from issue #3463 is omitted. The issue requires cron health to distinguish “filesystem wait,” and its evidence specifically records wait channels. Plan lines 175-195 define only stale PID, reused PID, overlap, excessive runtime, active-within-budget, and unavailable probe. Although the runbook will capture `wchan` at line 244, no runtime record, inspection result, JSON field, test, or acceptance criterion classifies filesystem wait. The implementation could satisfy every listed plan test while failing the issue acceptance criterion.

7. Installed-crontab reconciliation is broader than the defined ownership mechanism supports. Task 5 lines 236-238 promises detection/reconciliation of stale same-schedule commands, old schedules, and “exact duplicate unmanaged entries.” Yet `scripts/cron/cron_transaction.py:215-253` classifies unknown live lines as `uncataloged`, and `scripts/cron/cron_apply.py:202-214` aborts on any such line. The plan does not specify how an unmanaged duplicate becomes safely attributable to the catalog rather than remaining fail-closed. “Detect” and “reconcile” need separate expected outcomes and fixtures; otherwise Task 5’s claimed replacement behavior is not implementable without weakening ownership safety.

8. The security contract defers a correctness-critical bound to implementation. Plan line 154 leaves the maximum accepted `max_seconds` to be chosen in a failing test. That makes the canonical schema non-reviewable and allows a value large enough to defeat bounded-runtime health. The plan must state the numeric bound and its rationale before approval.

## Blockers
1. Resolve the shell-command versus argv-only runner contradiction with an explicit executable/argv/cwd/logging interface.
2. Define signal propagation, child reaping, and lock retention so no live mutator survives lock release.
3. Define complete runtime states, including successful completion, failed completion, never-started/missing evidence, and filesystem wait.
4. Replace the racy single-file owner/contention update protocol with a lossless, testable evidence design.
5. Put singleton enforcement at a named mutation boundary and test bypass attempts.
6. Specify a safe ownership rule for stale and duplicate installed entries without weakening fail-closed handling.
7. Fix the numeric `max_seconds` validation bound in the plan.
