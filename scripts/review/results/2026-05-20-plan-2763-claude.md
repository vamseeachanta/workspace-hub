## Findings

1. **`setup-cron.sh` installer is absent from Files-to-Change.** Plan §Files to Change (L66-74) lists `schedule-tasks.yaml`, the script, the test, the runbook, and the plans README — but omits `scripts/cron/setup-cron.sh`. That installer is what currently renders the `gsd-researcher` YAML entry into the live system crontab (issue #2763 body and #2762 plan L14 both confirm). If the migration lands without modifying the installer (or adding a `runtime: hermes` / `scheduler: hermes-gateway` skip rule), `setup-cron.sh` will keep rendering the system cron entry on its next install, producing exactly the "Dual-running system cron and Hermes cron would duplicate research output and spend provider credits twice" risk that §Risks (L107) names. Either modify the installer or explicitly assert in TDD that the installer's dry-run no longer emits this job — neither is in the plan.

2. **YAML schema-extension surface for Hermes-managed tasks is undefined.** Test `test_schedule_yaml_metadata_matches_runtime` (L82) requires "YAML metadata no longer says only `requires: [claude]` when the runtime is Hermes-managed" — but (a) the live YAML at line 34 already says `requires: [claude, python3, uv]` (multi-valued, not `[claude]`-only), so the test's stated baseline is incorrect; and (b) the plan never names the *positive* schema fields the migrated entry must carry (`runtime: hermes`? `scheduler: hermes-gateway`? `is_hermes_task: true`?). Without the schema spec, the test cannot be written and the migration target is unspecified. The test as worded would pass against the unchanged YAML — a false-green.

3. **`ALLOW_NATIVE_CLAUDE_GSD_RESEARCHER` env-var is invented with no governing definition.** Test `test_native_exception_requires_explicit_flag` (L81) gates the native path on this env-var, but the plan does not specify (a) where the flag is declared, (b) what justifies setting it (operator decision tree), (c) whether it lives in YAML metadata, an `.env`, or shell-only, or (d) how operators discover it. Without a definition of "what counts as a documented exception," the test is checking a string, not a contract. Also: the documented-exception path is *one of* the two acceptance outcomes, but the plan provides no rubric for which outcome is correct — both tests are written as if both outcomes will simultaneously materialize.

4. **Pseudocode (L54-64) describes a parity classifier, not a migration.** Lines like "classify each scheduled job by scheduler plane" and "if same logical job exists in multiple scheduler planes: emit duplicate warning" are the contract of the `#2765` parity-report plan, not of a single-job migration. A migration plan's pseudocode should describe: read current job → assemble self-contained prompt → register Hermes Gateway cron entry → remove (or guard) system cron rendering → verify post-state. The borrowed classifier shape suggests this plan was templated from a different one and never re-grounded to its actual scope.

5. **§Reproduction proofs marked `N/A` despite concrete reproducibles in the issue body.** Plan L19 says "N/A — governance/scheduler contract plan; no single failing runtime claim to reproduce." But issue #2763 body explicitly cites `bash scripts/cron/setup-cron.sh --dry-run` and live `crontab -l` as the evidence trail. Step 1.5 of the workspace-hub planning workflow (CLAUDE.md "Planning Workflow") requires *reproducing the alleged failure* — here the "failure" is "this job bypasses Hermes" and is trivially reproduced. Skipping reproduction means the plan's baseline-state evidence is never captured, so the post-migration diff cannot be proven.

6. **Self-contained prompt artifact is named as a risk but never created.** §Risks (L105): "Hermes cron jobs run in fresh sessions, so prompt/context currently assembled by the shell script must be made self-contained." The current script assembles `CONTEXT` from on-disk research staleness, weekday rotation, and budget — none of which a fresh Hermes session would inherit. But §Files to Change has no entry creating this self-contained prompt (e.g., `config/agents/hermes/prompts/gsd-researcher.md` or similar), and the TDD list has no test asserting prompt-completeness. The Hermes migration path cannot be proven to work without this artifact; the plan ships the risk without retiring it.

7. **Upstream dependency on #2762 routing contract is not gated.** Parent #2762 ("Hermes-vs-system cron scheduler routing contract") is still `status:needs-plan` (verified via `gh issue view`). That issue is what defines the rule for *which* plane owns a job — i.e., the classification rule this plan's tests would need to consume. Implementing #2763 before #2762's contract is approved means the migration target is being defined ad-hoc per-job rather than against a stable rule. The plan does not state whether implementation blocks on #2762 landing.

8. **Runtime-equivalence gap: `TIME_BUDGET=300` budget enforcement.** Current script (L24, L295-301) enforces a 5-minute timeout per `claude -p` call and retries with reduced context on failure. The plan's §Deliverable promises a "tested migration path" and §Acceptance Criterion #2 says "Existing cadence and output locations are preserved" — but cadence ≠ budget. Hermes Gateway cron has no documented equivalent of the per-call `timeout` + context-reduction retry pattern. Without specifying how the budget/retry contract survives the migration, the migrated job could either run unbounded (silent overspend) or terminate without the retry safety net (silent skips). Add a test or design statement for budget-equivalence.

9. **TDD coverage is process-level only.** All four tests (L80-83) stub `claude`/`hermes` on PATH or use fixture files — none verifies that a Hermes Gateway cron entry actually exists post-migration (`hermes cron list` parse + assertion) or that a tick execution produces the expected output file under `.planning/research/`. The plan §Risks names "Removing native Claude too quickly could break a useful nightly signal" but provides no positive assertion that the Hermes path produces equivalent output. A unit-level mocks-only test list cannot prove the migration; add at least one fixture-backed integration assertion against `hermes cron list` output.

10. **`docs/plans/README.md` update is already done (bookkeeping no-op).** Files-to-Change row 5 lists this as an `update` action, but `grep 2763 docs/plans/README.md:204` shows the row is already present. The row is dead and clutters the change list; either remove it or restate as "verify index entry" (which is a no-op as a "change").

11. **"Out of scope" omits implementation-time scheduler mutation.** §Out of scope (L47-50) names "Mutating live crontab or Hermes Gateway cron during planning" but does not extend this guardrail to *implementation tests*. TDD tests for `cronjob(action='create')` must run against fixtures/stubs, never against the live Hermes runtime — otherwise the test suite installs a real recurring job each run. State the constraint explicitly.

12. **Plan §7 (Acceptance Criteria) #6 cites `scripts/review/results/` but does not require a per-provider artifact set.** "Adversarial plan review artifacts are saved under `scripts/review/results/`" is true of the directory but does not specify Claude+Codex+Gemini coverage matching the §Adversarial Review Summary (L98-101). Without an explicit "all three or a documented UNAVAILABLE per missing provider" criterion, #6 can be satisfied by a single review file — collapsing T2/T3 coverage to T1.

- **Finding 4** — Pseudocode must be rewritten to describe migration mechanics, not parity-report classification.
