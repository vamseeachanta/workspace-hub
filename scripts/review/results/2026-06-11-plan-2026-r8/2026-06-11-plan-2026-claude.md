## Findings

1. **D5's historical-retry rule violates D5's own stated idempotency guarantee in any second lifecycle.** D5: "treat the event as an idempotent retry only when **exactly one candidate exists** and that candidate's `cycle_id` equals the current snapshot `cycle_id`; otherwise raise `StaleStateError`," followed by the claim "This keeps delayed duplicates in the same lifecycle idempotent." It does not. Concrete trace: cycle `initial` records `extracted -> completed` (no trigger); thread is reactivated into cycle `reactivation:R1`; cycle R1 records its own `extracted -> completed` (no trigger); a delayed duplicate of that R1 event arrives. The 5-field search `(account_id, thread_id, extracted, completed, "legacy:no-trigger")` now returns **two** candidates (one per cycle), "exactly one" fails, and a legitimate same-cycle retry raises `StaleStateError`. The candidate-uniqueness test must be scoped to candidates **within the current snapshot cycle**, not across all history. No test in the TDD list covers a no-trigger retry of a non-reactivation transition in a second cycle (`test_multicycle_without_trigger_can_extract_complete_and_purge_twice` covers distinct events, not retries), so an implementer following the spec literally ships the defect green.

2. **Missing-baseline tracked threads can produce a false `mailbox_empty: true` — the exact failure class R4/R5 blocked on.** D11 specifies `baseline_missing` behavior only for the reactivation **checker** ("If no baseline exists, the checker reports `baseline_missing`"). The `pending_work_report()` pseudocode counts `reactivation_pending_count` as threads "newer than stored message baseline" and its return schema has no `baseline_missing` field. A tracked `completed` thread with no stored `last_seen_message_id` (the plan never specifies *which events write* the baselines — `received_at_utc` appears nowhere in the transition inputs, and `triggering_message_id` is optional, so legacy/no-trigger threads will systematically lack baselines) that appears in the supplied inbox snapshot with a new reply is: not unknown (it's tracked), not reactivation-pending (no baseline to compare), not inbound — so `mailbox_empty: true` is reported while a reply sits unhandled. The report must surface baseline-missing tracked threads as a blocking or warning status, and the plan must specify the baseline write rule. Only `test_reactivation_checker_requires_message_baseline` exists, and it covers the checker, not the report.

3. **Spec/test contradiction on bootstrap prior-state bounding.** TDD test `test_bootstrap_reactivate_rejects_unbounded_prior_state` expects "empty log + `prior_state='inbound'`" to raise. Per the `prepare_event` pseudocode, `current is None` + `from_state == "inbound"` takes the initial-transition `pass` branch, and `inbound -> extracted` is a valid edge — the event **appends successfully** instead of raising. Neither the `reactivate_reply` pseudocode nor D11 validates `prior_state` at the wrapper level. The spec needs an explicit wrapper-level bound (`prior_state in {awaiting-reply, completed, purged}`) or the test as written fails against the spec'd behavior.

4. **`pending_work_report()` return contract is inconsistent on `noise_excluded`.** The `config_missing` early-return dict includes `noise_excluded: None`, and tests `test_pending_work_report_excludes_noise_label_from_unknown` (`noise_excluded: 1`) and `test_pending_work_report_config_missing_uses_unknown_noise_sentinel` treat it as part of the report contract — but the function's final return dict (both evaluated and not-evaluated paths) omits the key entirely.

5. **D6 misattributes `list_threads` to the existing contract.** D6: "must keep the path-first API used by `tests/email/test_state_machine_contract.py`" and then lists `list_threads(log_path, account_scope=None, include_out_of_scope=False)`. The test file (read in full) uses only `transition`, `lookup`, `count_entries`, `reactivate_reply`. `list_threads` is a new surface whose signature is a design choice, not a locked contract; the plan presents it as externally constrained.

Pseudocode: `event.completed_at = None` unconditionally for non-completed. No mechanism, argument, or test defines the "unless" path.

The guard as pseudocoded is weaker than the guarantee D9 states; either specify the token (e.g., a value only `reactivation_candidates()` returns) or downgrade the D9 prose.

Sweep preselects distinct threads, limiting practical exposure, but D11's invariant ("Dedup keys are checked against a historical dedup index rebuilt from the append-only log") does not hold within a batch.
