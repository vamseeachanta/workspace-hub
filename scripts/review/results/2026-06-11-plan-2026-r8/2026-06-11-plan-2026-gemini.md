## Findings
1. Plan §Pseudocode for `sweep_grace` explicitly allows proceeding without an inbox snapshot via `if not dry_run and not (inbox_snapshot or reactivation_prechecked): raise UnsafeSweepOrderError`. However, the batch loop unconditionally executes `skip any selected record with newer inbox_snapshot message`. If `reactivation_prechecked=True` is passed without an `inbox_snapshot`, this line will crash trying to evaluate a `None` type.
2. Plan §D11 requires: "The reactivation checker compares inbox snapshot latest_message_id/received_at_utc against these stored baselines. If no baseline exists, the checker reports baseline_missing rather than claiming a newer reply." However, the §Pseudocode for `reactivation_candidates` unconditionally maps `latest_message_id` to a `reactivate_reply` call and completely omits the baseline check. It will falsely reactivate threads that lack a baseline instead of reporting them.
3. Plan §Pseudocode for `_append_events_locked` rebuilds `historical_dedup_index` outside the loop, but never updates it when a new event is appended during the `for event in prepared:` loop. If a batch contains two identical retry events, the second event will bypass dedup because the index is stale, resulting in both events being appended and corrupting the state log.
4. Plan §D11 mandates storing `last_seen_message_id` and `last_seen_received_at_utc` in snapshots to avoid false reactivations. However, neither the pseudocode for `prepare_event` nor the design sections specify how these fields are actually captured from incoming transitions (e.g., mapped from `optional_fields` or `triggering_message_id`). Without a defined path to persist these fields on inbound/extracted events, all threads will permanently report `baseline_missing`.
5. Plan §Pseudocode for `reactivate_reply` passes a `QueueLearningEvent` as a separate `learning_events=[learning_event]` list to `_append_events_locked`. But `_append_events_locked` iterates over `prepared` state events and vaguely checks `if event has paired learning row`. Since they are separate, parallel lists, there is no deterministic pairing mechanism. A crash recovery relying on loosely associated lists is prone to misassigning transaction IDs across events.
