## Findings

### F1 — Option B rejection overclaims Vercel Rewrites incapability

**Claim:** Plan v2's rejection of Option B (Vercel rewrite) reads as an impossibility argument — it says rewrites "cannot serve paths outside `outputDirectory`". This is imprecise. Per the [Vercel Rewrites docs](https://vercel.com/docs/routing/rewrites), rewrites support two distinct modes: same-application rewrites within the deployed app, and rewrites to external origins. Neither mode reaches arbitrary repo-root files outside `outputDirectory`, but that constraint is different from "cannot serve" — the underlying fitness argument is correct, but the language loses precision.

**Drift scenario:** a future reviewer or implementation agent reading the v2 plan might conclude that Vercel rewrites are fundamentally limited in ways they are not, and either (a) over-trust the v2 rejection as a blanket rule applicable to future rewrite decisions, or (b) discover the overclaim and lose trust in the plan's other technical claims.

**Remediation:** rewrite the Option B rejection paragraph to articulate the fitness argument precisely. Rewrites support (i) same-app rewrites, (ii) external-origin rewrites. To serve `sitemap.xml` via Option B, the plan would need to either (a) include it in `outputDirectory` — which is Option A, (b) proxy to a Vercel Function that returns the XML body, or (c) rewrite to an external origin hosting the sitemap. All three add operational complexity for a single static XML file. Option A is strictly simpler. Rejection stands on fitness, not on technical impossibility.

### F2 — "same-day back-to-back" sequencing is not operationally bounded

**Claim:** Plan v2 commits to landing #2391 and #2357 "same-day back-to-back" to minimise the crawler-canonicalization window. This language is aspirational, not enforceable — it assumes both PRs will be ready within a day of each other, which is not under the plan's control. If #2357 slips, the v2 plan provides no concrete merge predicate for a reviewer to check.

**Drift scenario:** #2391 ships green on day 1; #2357 stalls in review and slips a week; the apex-host 34 `<loc>` entries are indexed by Googlebot every crawl during that week, inflating the redirect-hop count and the canonicalization window. The v2 plan has no gate to prevent this.

**Remediation:** replace the "same-day back-to-back" language with a concrete deploy-gate predicate: #2391 shall not merge to main until #2357 is also approved-and-ready. At the merge-ready moment, both PRs enter the deploy queue together. If #2357 is not approved-and-ready when #2391 is otherwise merge-ready, #2391 is deferred. This converts an aspirational clock-based commitment into a binary predicate a merge reviewer can verify in 10 seconds.

### F3 — Review-artifact citations in plan header overclaim file presence

**Claim:** Plan v2's header review-artifact section lists review file paths without distinguishing which are verified-on-disk vs which are projected from the session. This introduces a subtle past-tense drift — a reader might assume all cited artifacts are in git when in fact at least one (the v2 Codex review artifact, produced in a sandbox that blocks filesystem writes) is not.

**Drift scenario:** a v3 reviewer or an audit cron reading the plan header would try to `cat` a path that doesn't exist; trust in the plan's traceability breaks. This is exactly the G1 pattern that Claude caught on plan #2367 and on this plan's subsequent v3 review (which flagged the same missing file Codex is flagging now).

**Remediation:** correct the plan header to list only paths verified to exist via `ls` at edit time. For the round-2 Codex artifact specifically, annotate transparently: "findings applied from dispatching agent's summary; artifact file not yet written to disk at v3 edit time" so downstream reviewers understand the provenance gap and can reconstruct the artifact later if needed.
