### Verdict: MAJOR

### Summary
A thorough, well-structured T3 governance/enforcement plan with strong TDD-first test design, a clear MVP boundary, and explicit fail-closed publication gating. It is close to approvable, but has a concrete schema-regression coverage gap, a fixture-hash brittleness hazard that conflicts with the team's own documented line-ending pitfalls, and a residual private-slug leak vector in public-projection identity minting that the denylist-based validation cannot positively close.

### Issues Found
- [P2] The plan modifies two shared schemas (execution-manifest.schema.yaml and report-evidence-bundle.schema.yaml) by adding output_residency: public_federal_wiki, and names tests/architecture/test_report_layer_contract.py as the EXISTING validator of those schemas, but the Acceptance Criteria verification commands run only the new flywheel test and the wiki-sibling frontmatter test. There is no AC to run test_report_layer_contract.py after modifying the schemas it covers — a regression-coverage gap on the exact files being changed.
- [P2] Public-projection identity (run_id, event_id) leakage is enforced via legal deny-list regex + private-path/URL scans, but the plan also claims these IDs are 'minted only from public tokens.' Denylist scanning cannot positively prove public-token provenance: a novel private client/dataset slug not yet on the deny-list would pass. The stated property (public-token-only) is stronger than the validation that backs it.
- [P3] Legal-scan attestation hashes raw file bytes with explicit 'no newline normalization.' The team's own operating memory documents recurring CRLF/LF corruption in committed data files (verification-queue mixed line endings). Committed fixtures that carry recorded SHA-256 hashes will break on any editor/git autocrlf/whitespace touch, producing false-positive forgery/stale failures unrelated to actual tampering.
- [P3] test_two_clean_manual_runs_required_before_scheduling and test_clean_run_requires_reviewed_generated_diff appear both in the main TDD table and in the 'follow-up hardening, not blocking' list; ensure the standard's clean-run/scheduler acceptance criteria do not imply these are enforced in #2975 when they are explicitly deferred.
- [P3] Six consecutive review rounds (r1–r6) returned MAJOR/NO_OUTPUT, each surfacing new defect classes (output residency, value-level leakage, staged-order tests, destination schema, path hardening). Findings are narrowing, but the leak/forgery threat-model surface is large enough that its completeness is asserted rather than demonstrably exhausted.

### Suggestions
- Add an explicit Acceptance Criterion and verification command to run tests/architecture/test_report_layer_contract.py (and any other existing consumer tests of the two modified schemas) so the additive public_federal_wiki enum change is proven non-breaking.
- Either reframe the public-projection identity guarantee as 'denylist-clean + structurally constrained' rather than 'public-token-only,' or add a positive structural validator (e.g., run_id must match a regex composed solely of known public source-authority codes, an allowlisted public dataset-slug registry, ISO date, attempt integer, and a short hash) so unknown private slugs cannot pass.
- For committed fixtures bearing recorded hashes, either store fixtures with enforced LF via .gitattributes (e.g., *.yml/*.jsonl text eol=lf and the fixture dir marked binary-safe) and add a test asserting the on-disk bytes match the recorded hash at checkout, or compute attestation hashes over a normalized canonical form for committed-fixture mode while keeping raw-byte hashing for live runs.
- Add a single 'threat-model completeness' checklist to the standard enumerating every private-data egress path (run_id, event_id, destination.repo, destination.path, freshness fields, supersession refs, frontmatter) with the test that closes each, so future rounds can verify coverage against a fixed list rather than rediscovering vectors.
- Given the validator carries nearly every AC behavior in one 'MVP,' confirm the helper-module split has a per-module test file mapping in the plan so the reviewer of the implementation PR can review each policy surface independently.

- How does the validator positively prove that a public-projection run_id/event_id was minted only from public tokens, as opposed to merely failing the deny-list? Is there an allowlisted public-dataset-slug registry, or is a novel un-denylisted private slug an accepted residual risk?
- How will committed fixtures with recorded byte-exact SHA-256 hashes be protected from line-ending/whitespace drift across machines and editors, given the documented CRLF/LF corruption history in this repo's data files?

Is the follow-up 'repo-qualified plan attestation' issue a blocking prerequisite for trusting this evidence at r7, or is the manual transcript accepted as sufficient given the decoupled implementation gate?
