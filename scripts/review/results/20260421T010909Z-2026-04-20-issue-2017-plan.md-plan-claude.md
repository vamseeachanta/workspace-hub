### Verdict: APPROVE

### Summary
The v4 plan is well-scoped, locks all 6 previously-open design decisions, and cleanly separates #2017 (schemas/contracts/fixtures/xfail tests) from #2024 (pipeline) and #2026 (storage). The composite `(account_id, thread_id)` key, single-writer fcntl lock, atomic snapshot rewrite, and explicit trash-purge recovery path directly address prior P1/P2 findings; xfail state-machine tests resolve the scope vs. coverage tension. Minor polish opportunities remain around meta-file concurrency, sweep-lock path creation, and a few acceptance-criteria gaps.

### Issues Found
- [P3] Minor: `queue-state-snapshot.meta.yaml` is not written atomically alongside `queue-state-snapshot.yaml`. A crash between snapshot rename and meta rewrite could leave readers with a stale meta pointing at the old offset, masking real staleness. Specify a two-file atomic protocol (write snapshot.tmp + meta.tmp, fsync both, rename meta last, or combine into one file).
- [P3] Minor: The plan moves the sweep lockfile to `<repo_root>/.locks/` but does not specify who creates the directory, whether it is in `.gitignore`, or the lock-file cleanup policy on stale PIDs. Worth one line to avoid a first-run failure when `.locks/` does not exist.
- [P3] Minor: Acceptance Criteria does not include an assertion that `tests/fixtures/email/` redaction has been reviewed for PII (real email addresses, names, subject lines). Given this is a committed corpus, a redaction-review checkbox would prevent accidental PII leak in git history.
- [P3] Minor: The `apply_precedence` pseudocode returns `(archive, [])` as a safety default when no classifications match, but `archive` is a valid classification in the precedence list — the silent fallback could mask a classifier bug. Consider logging `classifications_empty_fallback` to the learning log.
- [P3] Minor: `writer_identity` includes `boot_id` for uniqueness, but the plan does not specify where `boot_id` is sourced (`/proc/sys/kernel/random/boot_id` is Linux-only). If the pipeline may run on macOS dev boxes or CI runners, specify the fallback (e.g., `uname -a` hash or process start-time).
- [P3] Minor: The 7-day grace boundary tests (`day_6`, `day_8`) don't cover the exact boundary at `day_7 + 1 second` vs `day_7 - 1 second`. Given `freezegun` is already in use, an off-by-one boundary test is cheap insurance.
- [P3] Minor: The quarterly learning review schedule names specific dates (Jan 1, Apr 1, Jul 1, Oct 1) but the existing daily-readiness cron runs 6am CT; the plan does not specify the time-of-day or cron expression for the quarterly trigger.

### Suggestions
- Add a one-line acceptance criterion that `tests/fixtures/email/` has been reviewed for PII redaction before merge (checklist item, reviewer signoff).
- Consider collapsing `queue-state-snapshot.yaml` + `queue-state-snapshot.meta.yaml` into a single YAML file with a top-level `meta:` key — one atomic rename covers both, eliminating the cross-file consistency window.
- Document the `.locks/` directory in `.gitignore` and add a bootstrap step (either in the design doc or as a module init) that creates it with `os.makedirs(exist_ok=True)`.
- Specify the cron expression and machine for the quarterly learning review trigger (e.g., `0 9 1 1,4,7,10 *` on ace-linux-1), parallel to the existing daily-readiness trigger reference.
- In `apply_precedence`, emit a learning-log event when the classifications set is empty — the silent `archive` default is correct behavior but worth observability for drift detection.
- For the xfail state-machine tests, add an acceptance criterion that the xfail reason string uniformly references `#2024` (or `#2026` for storage-specific tests) so a reader can `grep` the reason and map each xfail to its unblocking issue.

### Questions for Author
- When the user eventually decides skylineseven routing (open gate), is that decision recorded in the plan doc, in the GitHub issue, or in a separate decision log? The plan is conditional on it but does not specify where the resolution is captured.
- `account_id` is described as the Gmail account email (e.g., `vamsee.achanta@aceengineer.com`). What happens if the primary account email is aliased or changes? Is the composite key stable across email-address rename events, or should `account_id` be a stable opaque identifier (e.g., a hash or UUID) mapped to the current address?
- The plan estimates ~18k JSONL entries/year and defers compaction. What is the threshold (file size, snapshot-rebuild time) that will trigger the v2 compaction follow-on — is it tracked as an issue now or only when observed?
- For the bootstrap quarterly review on 2026-07-01 covering 2026-04-20 → 2026-06-30: who dispatches it (manual vs cron), and does the cron trigger exist at plan-merge time or is it created as part of this plan?
- The dependency contract says #2017 owns the xfail contract tests and #2026 flips them green — what happens if #2026's implementation reveals a contract flaw? Is the expected flow to file a follow-up to #2017, or can #2026 amend the tests in the same PR with a cross-reference?
- Is `freezegun` already a declared dev dependency, or does this plan implicitly add it? The TDD list assumes it for time-boundary tests.
