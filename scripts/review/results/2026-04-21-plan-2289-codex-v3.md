### Issues Found

**High:**
- **`synthesize_observer_events()` can suppress a real `--no-verify` bypass** by treating any nearby `plan-gate-events` record as a match. Blocked pre-commit attempts do not produce a commit and therefore are not Git-valid correlates for a later post-commit event. The helper contract says to match `plan-gate-events` generically and skip synthesis on any match (lines 225-229), while the same plan states that `plan-gate-events.jsonl` contains both `plan-gate-blocked` and `plan-gate-bypass-attempted` actions (lines 275-279). That creates a false-negative path for the core v2 `--no-verify` defect.

- **`has_approval_intent()` remains internally inconsistent and still not fully falsifiable.** The revision rationale defines only two approval sources (line 28), the helper contract implements only those two (lines 232-239), but the open-questions section says `.planning/phases/*/REVIEWS.md APPROVE` is now part of the rule (line 358). The marker-file rule uses `mtime within 24h of commit timestamp` rather than proving approval occurred before or after the bypass event (lines 234-237), so a stale or pre-existing marker can still mask an unapproved commit.

- **all-commits observer semantics are undefined for detached `HEAD`.** The observer schema requires `branch` on every record (lines 273-280) and synthesis correlates on `(branch, staged_files_digest, time)` (lines 225-229), but the plan never defines what `branch` means in detached-HEAD state. `git commit --no-verify` is valid in detached HEAD, so this omission leaves a coverage gap in exactly the path v3 claims to close (line 25).

**Medium:**
- **`has_been_reverted_via_revert_commit()` is both incomplete and over-broad.** The revision rationale describes one grep contract (line 34), but the helper contract changed it to `^Revert` plus a second grep for the SHA anywhere in later commits (lines 250-255). That second branch can false-positive on unrelated mentions of the SHA, while the plan itself admits hand-crafted reverts will be missed (line 354).

- **`resolve_pushed_state()` still rests on an ungrounded 7-day freshness heuristic.** The plan states `false` only when remote refs were fetched within the last 7 days (line 29, lines 242-247), but provides no justification for 7 days, no boundary behavior, and no test for day-7/day-8 transitions.

- **Dual safe-list split still has undefined policy edges.** The plan only exempts `docs/plans/`, `docs/reports/`, `docs/standards/`, and `.planning/` (line 30, line 146, lines 193-194), while separately creating `docs/governance/BYPASS-ROLLBACK-POLICY.md` as a new policy file (line 290). The plan never states whether documentation paths not in either list are intentionally rollback-eligible or accidental omissions.

- **The 20-test suite is under-specified in the wrong places.** It does not include a detached-HEAD observer test, a blocked-pre-commit-then-later-successful-commit correlation test, a `.planning/phases/*/REVIEWS.md` approval-intent test, a path-outside-both-safe-lists classification test, or a 7-day freshness boundary test (lines 304-330). The count is not the issue; the missing boundary cases are.

### Suggestions

- Tighten `synthesize_observer_events()` so it only correlates observer commits against bypass-attempt records that can legitimately lead to a commit. Do not treat generic `plan-gate-blocked` events as a suppressing match.
- Rewrite `has_approval_intent()` as a single canonical contract in one place, and make the timing falsifiable. If `.planning/phases/*/REVIEWS.md` counts, put it in the normative helper contract and add a dedicated test. Require evidence ordering relative to the commit, not just `mtime within 24h`.
- Define observer behavior for detached `HEAD` explicitly. Either record `branch=null`/`HEAD` and make synthesis branch-agnostic in that state, or use a correlation key that does not depend on branch at all.
- Narrow revert detection to evidence that actually proves reversal of the target SHA. Do not treat arbitrary later mentions of the SHA as a revert. Add tests for default `git revert`, edited revert messages that keep `This reverts commit <sha>`, and unrelated SHA mentions.
- Replace or justify the 7-day pushed-state threshold. If it stays, document why 7 days is the policy boundary and add explicit tests for fresh/stale edges.
- State the intended disposition for paths not in either safe-list. If they are rollback-eligible by default, say that plainly and justify the governance consequence for non-enforcement docs like `docs/governance/*.md`.
- Rebalance the test plan. Add boundary tests for detached HEAD, blocked-attempt correlation, approval via REVIEWS artifacts, mixed safe/non-safe commits, and freshness cutoff transitions.

### Questions for Author

- When a user commits in detached `HEAD`, what exact `branch` value will `all-commits-observer.sh` log, and how will `synthesize_observer_events()` correlate it against pre-commit records that were captured on a named branch?
- Why is a blocked pre-commit event a valid suppressor for later observer synthesis, given that Git does not run `post-commit` for an aborted commit?
- Do you intend `docs/governance/BYPASS-ROLLBACK-POLICY.md` and other non-enforcement governance docs to be rollback-eligible by default, or should some of them be in `ADVISOR_SAFE_PATHS`?
