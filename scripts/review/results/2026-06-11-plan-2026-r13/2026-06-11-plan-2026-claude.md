## Findings

1. **Unrecorded R13 artifacts — the ledger defect class flagged at R12 has recurred.** `scripts/review/results/2026-06-11-plan-2026-r13/` exists on disk with two zero-byte files (`2026-06-11-plan-2026-claude.md`, `.err`) and appears in git status as untracked. The plan's "Review artifacts" header, Artifact Map row, and Adversarial Review Summary all stop at r12 and state the next round must be "fresh." R12 itself flagged "review ledger did not yet record the attempted R12 artifacts" — the identical omission now exists for an attempted r13. Either record r13 as an attempted/failed round or remove the empty directory; as written, the next reviewer inherits a ledger that is provably incomplete against the filesystem.

2. **D5 prose and pseudocode disagree on caller-supplied `cycle_id` for mid-cycle non-reactivation events, leaving an unvalidated write path.** D5 prose: "Non-reactivation transitions **inherit** the current snapshot `cycle_id`," with supplied `cycle_id` meaningful only as an exact-historical-replay exception. Pseudocode (`prepare_event`, non-reactivation branch): `event.cycle_id = event.cycle_id or snapshot_before.get(...)` — caller-supplied wins unconditionally. When `current.state == event.from_state` and `ts_utc >= cycle_started_at`, neither the stale-timestamp guard nor the state-mismatch branch fires, so a non-duplicate event carrying a stale/wrong `cycle_id` appends tagged to a cycle the thread is no longer in. That row then enters the historical dedup index, where the D5 exact-six-field-replay exception would later treat genuine stale replays of that key as idempotent duplicates. No test in the TDD list covers "supplied `cycle_id` ≠ current snapshot cycle, states match, fresh timestamp" (the closest, `test_supplied_cycle_id_same_ts_historical_retry_dedups_before_stale_timestamp_guard`, only covers the replay-exists case). This is the same prose-vs-pseudocode defect family that R11 flagged on the incoming-cycle gate. Fix: require supplied `cycle_id` on non-reactivation events to either match the current snapshot `cycle_id` or be an exact historical duplicate; otherwise reject. (Initial-record `cycle_id` supply per D5 bullet 2 is a legitimate carve-out and should be stated as the only one.)

3. **Blocked-label-setup evidence is incomplete: it ignores the `claude_ai_Gmail` MCP label surface.** The Runtime credential/config probe checks only filesystem OAuth paths (`~/.gmail-mcp/oauth-env.json`, `~/.gmail-ace/...`, `~/.gmail-personal/...`) and the Risks section marks live label setup "Resolved … blocked unless credentials are provisioned or the user approves a split." `config/agents/claude/SOUL.runtime.md` §MCP Tool Scope documents `claude_ai_Gmail` with label scope, and `mcp__claude_ai_Gmail__create_label`/`list_labels` are live in this environment. For a one-time setup task (issue task 1: "Create Gmail labels via API (one-time setup)"), an interactive MCP path exists for at least the connected account. The plan presents the user a blocked-or-split decision without this third option; the "Resolved" claim overstates the blockage.

4. **Dual source of truth for alias→email mapping with no reconciliation requirement.** `scripts/email/gmail-archive-extract.py:71-74` already hardcodes `ace`/`personal`/`skestates` → literal emails in tracked code; D2 introduces a second mapping in `~/.hermes/email-state/accounts.yaml`. D4 splits ownership ("accounts.yaml remains the queue-state normalization config; credential discovery remains owned by the existing Gmail helper pattern") but never requires the two mappings to agree. A divergence (e.g., `accounts.yaml` remaps `personal`) would have the label adapter mutating one mailbox while the report normalizes snapshot records against another, silently. No test or acceptance criterion checks cross-consistency.
