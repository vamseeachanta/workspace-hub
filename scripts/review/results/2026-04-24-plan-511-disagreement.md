### claude

- **Plan §Pseudocode line 143 redefines `combinations()` as `Iterator[dict]` but existing code returns `list`.** Actual signature at `schema/campaign.py:90` is `def combinations(self) -> list[dict[str, float | str]]:` and the function ends with `return [dict(zip(keys, combo)) for combo in product(*value_lists)]`. Critical downstream callers depend on list semantics: `CampaignSpec.generate_run_specs` at `campaign.py:285` does `limit = self.max_runs if self.max_runs else len(combos)` — `len()` does not work on iterators. `CampaignGenerator.preview` at line 374 returns this value, and `cli.py:330,334-340` calls `len(combos)` and iterates twice (`for i, combo in enumerate(combos, 1)`). Switching to an Iterator silently breaks `--preview`, `max_runs`, and `validate()` (which iterates combos to check duplicate names). The plan's "**Reuse as-is**" framing for `CampaignMatrix.combinations()` is false.
- **Plan §Pseudocode line 145–149 has a single-pass-iterator bug that would cause silent under-generation.** The pseudocode does `sweep_combos = itertools.product(*(s.values for s in self.sweeps))` *before* the outer `for typed in typed_combos` loop, then iterates `sweep_combos` inside the outer loop. `itertools.product` returns a one-shot iterator; on the second outer iteration `sweep_combos` is exhausted and yields nothing. The result: only the first typed combo would be crossed with sweeps; subsequent typed combos would emit zero sweep variants. This is the kind of off-by-one logic error that would pass a 1×N "single typed axis" test and fail silently on N×M. The pseudocode needs `list(itertools.product(...))` or recomputation per outer iteration. No test in §TDD exercises N×M typed × sweep crossing in a way that would catch this.
- **Plan §TDD `test_campaign_matrix_single_sweep_only` is unimplementable without an unacknowledged schema change.** `CampaignMatrix.water_depths: list[float] = Field(..., min_length=1, ...)` at `campaign.py:70` makes `water_depths` a *required* field. A "sweeps-only campaign with no typed axes" cannot construct a `CampaignMatrix` instance. The plan must either (a) make `water_depths` optional (backward-incompatible — affects the existing `validate_output_naming_coverage` validator and `from_legacy_config`) or (b) drop this test. Neither is acknowledged. This propagates: the integration test at acceptance criterion line 228 ("two dotted sweeps … produces exactly `len(h) * len(d)` `spec.yml` files") implies no `water_depths` axis, which is currently impossible.
- **Plan §Pseudocode line 150 produces combo dict keys that break `output_naming.format()`.** Existing code at `campaign.py:292-294` does `self.output_naming.format(base_name=spec.metadata.name, **combo)`. Python's `str.format()` interprets `{a.b.c}` as *attribute access* on argument `a`, not as a string-key lookup of `"a.b.c"`. With `combo = {"environment.waves.height": 3.5}` and template `"{environment.waves.height}"`, `format()` would attempt `combo["environment"].waves.height`, raising `KeyError: 'environment'` (or returning a wrong result if the typed `environment` axis is also present). The plan acknowledges the placeholder issue at line 278 ("require alias when template references the sweep; otherwise slug") but the pseudocode at line 150 yields the *raw dotted path* as the combo key. The aliasing/slugging must be applied at combo-construction time, not as a downstream concern. Two §TDD tests (`test_sweep_naming_template_with_alias`, `test_sweep_naming_template_without_alias_slug_fallback`) reference this behavior but the pseudocode does not implement it.
- **Plan §Pseudocode line 159–165 misrepresents `_apply_overrides` signature and contract.** Actual signature at `campaign.py:298-302` is `def _apply_overrides(spec: ProjectInputSpec, combo: dict[str, float | str], matrix: CampaignMatrix) -> None:` — it *mutates `spec` in place* and returns `None`. The plan's pseudocode shows `def _apply_overrides(base, combo): … return spec`, treating it as a functional transform with rebinding (`spec = apply_dotted_override(spec, ...)`). The plan also references `matrix.sweeps` without `matrix` being in its declared signature. A reviewer can guess the intent, but the pseudocode does not match the code it claims to extend, which means the actual implementation strategy is undefined: do you mutate `spec` (matching existing pattern, but `apply_dotted_override` returning a new model breaks that) or refactor `_apply_overrides` to return a new spec (breaking the existing callsite at `campaign.py:291` which discards the return value)?
- **Plan §Files-to-Change does not include `validate_output_naming_coverage` (campaign.py:257-277), but adding `sweeps:` will break it.** This `model_validator` iterates the typed axes and `raise ValueError` if any varying axis is missing from `output_naming`. As written it doesn't know about `sweeps:`. After the schema extension, two failure modes:
- If the validator is *not* updated: a sweep with no `{alias}` placeholder in `output_naming` produces non-unique run names (every combo writes to the same dir). Currently the typed-axis check prevents this; sweeps would silently regress it. The §TDD `test_sweep_naming_template_*` tests likely won't catch this without explicit duplicate-name assertions.
- If the validator *is* updated to also check sweeps: the plan must add the change to "Files to Change" and add a test. Neither is present.
- **Plan §Risks line 269 names overlap risk only for `environment.*` (vs `EnvironmentVariation`), missing the more severe `environment.water.depth` ↔ `water_depths` collision.** `water_depths` is a *required* typed axis and `_apply_overrides` at `campaign.py:304-307` mutates `spec.environment.water.depth` for every combo. A user-defined sweep on `parameter: environment.water.depth` would get *overwritten* by the typed-axis pass that always runs first. The plan's mitigation "dotted applied after typed (dotted wins)" handles this by ordering, but only works if `_apply_overrides` is refactored as in finding #5 — and the current mutate-in-place pattern means the typed axis writes first, then the sweep writes second, which the pseudocode does. Still, the plan should explicitly call out `environment.water.depth` and `equipment.tensioner.tension_value` as known shadow paths and add tests for both.
- **Plan §Acceptance Criteria line 229 ("byte-identical to pre-change baseline") is brittle as written.** Generated YAML files contain ordered keys, comments, and (depending on writer) timestamps in headers; "byte-identical" is rarely a stable contract for code that may unrelatedly change YAML serialization. The acceptance criterion should require *structural* equality (load both, compare via `model_dump()` or normalized YAML) — not byte-identical. As written, an unrelated dependency bump to PyYAML or Ruamel could fail this gate.
- **Plan §Resource Intel line 38 cites `cli.py:293-358` for `cmd_campaign`; actual range is 293-369.** Off-by-11 on the upper bound. Minor in isolation, but combined with the `root.py:21-80` mis-citation (actual class spans 21-228) it suggests the line ranges were transcribed from intel without spot-checking the file. This matters because the `cmd_campaign` body at lines 354-358 contains the existing call `gen.generate(output_dir=..., force=..., resume=...)` — no `spec_only` kwarg yet — and the plan's CLI integration depends on knowing this surface exactly.
- **Plan §Pseudocode line 153–157 (`apply_dotted_override`) under-specifies the Pydantic walk.** The plan says "walk Pydantic model by attribute, not dict-mutation" and "use model_copy(update=..., deep=True) at each level" but `model_copy(update=...)` only updates *top-level* fields — it does not descend into nested models. Doing `model_copy(update={"environment.waves.height": 3.5})` is not a valid Pydantic operation. The realistic implementation is `model.environment.waves.height = 3.5` (Pydantic v2 allows assignment if `model_config = ConfigDict(validate_assignment=True)` is set on every nested model in the chain). Plan needs to verify whether `validate_assignment` is enabled on `Environment`, `Waves`, etc., or describe the actual walk — `model_dump()` → mutate dict at dotted path → `ProjectInputSpec.model_validate(...)`. The §Risks-line-274 mitigation references `model_validate(model_dump())` round-trip but the pseudocode contradicts it.
