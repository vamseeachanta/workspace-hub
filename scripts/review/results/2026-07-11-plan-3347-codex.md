## Findings
1. The proposed “exact” Deckhand ownership predicate cannot be implemented by metadata alone using the current matcher. Plan pseudocode lines 133–136 requires an “exact command token,” a workspace-hub cwd basename, and rejection of similar commands. But `scripts/cron/cron_transaction.py:154-180` implements substring matching, and lines 172–176 accept either `$WORKSPACE_HUB` token regardless of the requested `cwd_basename`. The Files to Change table, plan lines 143–153, omits `scripts/cron/cron_transaction.py`. Adding `installed_fingerprint` to YAML therefore cannot satisfy the stated safety contract or its negative test.

2. Delegating default setup to `cron_apply.py --apply` without supplying a unique `--ts` will overwrite backup history. Plan pseudocode lines 121–124 forwards no timestamp. `scripts/cron/cron_apply.py:280` defaults the timestamp to `"manual"`, while lines 237–249 write `<machine>-manual.crontab` using `Path.write_text`, which replaces an existing file. Repeated compatibility-entrypoint runs would destroy the preceding recovery point—the exact scenario covered by the issue’s repeated-run report. The plan has no unique-backup test or acceptance criterion.

3. The claimed entrypoint-level repeat-run regression is absent. Plan line 44 identifies the gap as invoking the compatibility entrypoint twice against an injectable crontab, but tests at lines 161–171 only stub delegation at the wrapper and separately run the transaction twice. This can pass even if wrapper argument construction, environment selection, or invocation behavior makes the second real entrypoint run non-idempotent.

4. `--machine` routing is under-specified and untested for the Windows safety branch. Plan lines 118–124 says the wrapper will resolve a supplied machine and preserve contribute-minimal guidance. Existing `scripts/cron/setup-cron.sh:40-80` decides the variant from the physical hostname before delegation. The proposed tests at plan lines 161–171 contain no `--machine licensed-win-*` case. A wrapper that retains current ordering could invoke Linux cron reconciliation for a Windows target or ignore the override while still passing every listed test.

5. The validation test contract is too weak for ownership-critical metadata. Plan line 170 only requires rejection of “unknown or empty fields.” It does not require field-type validation, non-empty list members, or a minimum conjunctive identity. `scripts/cron/cron_transaction.py:154-180` will accept values whose types are not the documented string/list contract and will treat a single broad substring as ownership. A schema could pass while still permitting `command_contains: "deckhand"` or malformed values that overclaim live lines.

6. The acceptance suite deliberately hides a known failing relevant cron test. Plan line 21 acknowledges `tests/cron/test_a1_preserved.py` is stale, while acceptance line 183 excludes it. Running that file currently fails at `tests/cron/test_a1_preserved.py:96-100`: it expects 4 `preserved_external` entries, but the live YAML contains 8. This plan modifies the same ownership catalog behavior and cannot establish a green relevant baseline while omitting the existing real-catalog regression suite.

7. The review-artifact declaration is not durable evidence as currently written. Plan line 9 and Artifact Map line 104 name three provider artifacts; on disk, the Claude and Codex files are zero bytes, while the Gemini file is only 338 bytes. The plan-review hardening contract forbids treating zero-byte provider files as evidence. The current `PENDING` summary is truthful, but these paths cannot support promotion until regenerated against the final revision.

8. Acceptance line 184 says “ShellCheck” will pass but provides no executable command, target, or configuration. This is not a reproducible acceptance gate; it should name the exact invocation, such as the repository’s canonical wrapper or `shellcheck scripts/cron/setup-cron.sh`.
