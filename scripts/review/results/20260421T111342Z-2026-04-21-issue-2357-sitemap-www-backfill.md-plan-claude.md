### Verdict: APPROVE

### Summary
Tight, well-scoped T1 plan for a host-normalization rewrite of aceengineer-website/sitemap.xml with TDD coverage, before/after invariants, and an explicit xmllint gate. Resource intelligence is concrete (real file paths, line excerpts, prior-issue context) and risks (governance drift on label, stale issue body path) are surfaced rather than hidden. Adversarial review is correctly marked PENDING, which is the appropriate state for a draft entering plan review.

### Issues Found
- [P3] Minor: Acceptance criterion requiring "Regression test ... is written before the sitemap edit" is a process claim that cannot be verified from the resulting artifact diff — there is no scripted check (e.g., commit ordering or test-fails-first capture) that would prevent the criterion from being silently satisfied even if TDD ordering was skipped.
- [P3] Minor: The 'before/after row-for-row metadata comparison' acceptance criterion is described in prose but the TDD test list does not pin down where the pre-edit snapshot lives (committed fixture vs. git-show of HEAD vs. in-test string constant); without that, the test is under-specified and could be implemented in a way that trivially passes.
- [P3] Minor: Plan asserts `xmllint --version` exits 0 in the current environment but does not commit a CI/hook check that fails the plan if a future executor lacks xmllint — the stated mitigation ('stop before editing') is purely advisory.

### Suggestions
- Add a small fixture or use `git show HEAD:aceengineer-website/sitemap.xml` inside the Jest test to anchor the before-snapshot used by `sitemap_metadata_is_unchanged_row_for_row`, so the comparison is reproducible and not dependent on an in-memory pre-edit string.
- Consider extending the regression test to also assert there is no `<loc>http://...` (plain HTTP) variant and no trailing-slash inconsistency between rows, since both are common drift modes when sitemaps are hand-edited.
- When updating `docs/plans/README.md`, add a one-line note pointing to issue #2391 so the historical split between serving fix and content fix is discoverable from the index, not only from the session handoffs.
- Capture the exact `xmllint` invocation and exit-code expectation in a short shell snippet inside the plan (or in `scripts/`), so the executor and any reviewer run the identical command rather than reconstructing it from prose.

### Questions for Author
- Should the regression test also enforce a canonical trailing-slash policy (e.g., `https://www.aceengineer.com/` vs. `https://www.aceengineer.com`) for the apex/root entry, or is whatever the current row uses considered authoritative?
- If the rewrite surfaces a true duplicate (apex and www variants of the same path both present today), what is the deterministic resolution rule — keep the row with the newer `<lastmod>`, keep the apex row's metadata, or keep the www row's metadata?
- Is there an expectation to also touch `robots.txt` or any `<link rel="canonical">` tags in the same change, or is this strictly sitemap-only and those are tracked under a separate issue?
- Given the noted GitHub label/local-marker drift risk, do you want the implementation step to refuse to start until `.planning/plan-approved/2357.md` is created, or is the existing batch-agent rule ('only act on status:plan-approved') considered sufficient enforcement here?
