### Verdict: MAJOR

### Summary
The dominant defect class is unverified correctness-critical assertions. The plan makes many live-state claims about files, issue statuses, CLI behavior, and prior artifacts, but none can be affirmatively verified from the plan itself, and several mandatory operating-model checks are either omitted as "not applicable" or lack any evidence of compliance.

### Issues Found
- [P1] Unverified resource-intelligence claims: the plan asserts live existence/status for `scripts/review/submit-to-codex.sh`, `tests/review/test-submit-scripts.sh`, issue `#2406/#2405/#2403/#2402`, and multiple memory/docs artifacts in `Resource Intelligence Summary` and `Evidence (embedded verification)`, but provides no independently verifiable evidence beyond self-reported command outputs; per the review contract, these remain unverified blocking claims.
- [P1] `doc_key` / operating-model §3 compliance is not checked at all. The plan creates `docs/plans/2026-04-20-issue-2406-codex-stdin-hang-fix.md` in `Artifact Map` but nowhere declares a `doc_key`, let alone a `sha256:`-namespaced identity; this fails a mandatory check.
- [P1] Operating-model §2 ownership compliance is unverified. `Standards` says "Not applicable — infrastructure script bug fix" and no section checks whether the plan invents forbidden ownership classes such as between-layer or `L<n>-adjacent`; mandatory check missing.
- [P1] §4 flow-rules compliance is unverified. The plan touches durable docs (`docs/plans/...`, `docs/plans/README.md`), tests, scripts, review artifacts, and memory files, but nowhere analyzes whether any forbidden flows are introduced; mandatory check missing.
- [P1] §7 cross-machine tier-rule compliance is unverified. `Documents consulted` explicitly relies on `memory/feedback_codex_needs_pushed_artifact.md` and discusses Codex sandbox/GitHub behavior, but the plan does not classify artifacts into git-tracked metadata vs shared-mount vs local-cache tiers or prove the proposed tests respect those boundaries.
- [P1] Acceptance-criterion coverage is incomplete. `Acceptance Criteria` includes `Manual live repro ... fixed script completes within CODEX_TIMEOUT_SECONDS` and `All three review artifacts ... posted to scripts/review/results/`, but `TDD Test List` has no automated tests covering the live timeout behavior, artifact creation/posting, or README index update. Mandatory test-to-acceptance traceability is missing.
- [P1] Dependency correctness is not established. `Documents consulted` states `Issue #2405 ... Both must land before cross-provider review is trustworthy again`, but the plan does not model this as a hard or soft dependency in a dependency section, does not state whether #2406 is executable independently, and does not resolve the implication that review reliability depends on another issue's state.
- [P1] The compact-retry reasoning is internally inconsistent. `Resource Intelligence Summary` claims the retry "inherits the argv-vs-stdin hazard, but only for prompts large enough to first defeat the 120 000-char initial guard at line 216," while `Files to Change` and `T28` target the compact-retry path using `CODEX_COMPACT_RETRY_CHARS`. If prompts exceeding the 120000-char guard are rejected before dispatch, the stated trigger condition for retry is suspect and needs proof against current code.
- [P2] Security/threat-modeling is underspecified. The plan modifies a script that shells out to `CODEX_BIN`, pipes large untrusted prompt content, writes to `$raw_file/$err_file`, and depends on PATH-mocked binaries in tests, but `Risks and Open Questions` does not address injection/path spoofing/log poisoning risks or any threat model for external CLI invocation.
- [P2] Scope creep is present. `Files to Change` includes `docs/plans/README.md` and `Acceptance Criteria` requires posting three provider review artifacts, which are process/documentation concerns adjacent to the single-purpose bug fix in `scripts/review/submit-to-codex.sh`; the plan does not justify why these are in-scope for a dispatch-hang fix.
- [P2] The plan relies on a quoted CLI contract from `codex exec --help` in `Gaps identified` / `Evidence`, but does not account for version skew despite also noting `Risk: if CODEX_BIN is an older codex version that doesn't support stdin`. This leaves the core fix contingent on an unpinned tool contract.
- [P2] `Resource Intelligence Summary` does not satisfy the “≥3 distinct sources with concrete findings” requirement in a rigorous way because one category is explicitly `LLM Wiki pages consulted: No relevant wiki pages` and `Standards: Not applicable`; the source count is asserted in an HTML comment rather than evidenced through distinct, correctness-critical findings tied to the proposed change.

### Suggestions
- Add an explicit verification table that marks each cited file, issue, and artifact as `verified existing`, `to be created`, or `unverified`, and remove any live-state claim you cannot prove.
- Add frontmatter/identity handling for the new plan artifact, including a `doc_key` using the required `sha256:` namespace, and cite the operating-model section that requires it.
- Add a dedicated operating-model compliance section covering §2 ownership, §4 flow rules, §7 cross-machine tiers, and §8.1 frontmatter authority, even if the outcome is “no impact”; right now those checks are absent.
- Create a test-to-acceptance matrix mapping every acceptance criterion to one or more tests, and either add tests for missing criteria or downgrade those criteria from acceptance requirements to manual follow-ups.
- Clarify dependency semantics for `#2405`: state whether it is a blocker, a related issue, or irrelevant to implementation of `#2406`, and remove contradictory wording about trustworthiness if not a real dependency.
- Re-check the compact-retry path against current code and rewrite the trigger explanation so it is consistent with the `120000` initial guard and `CODEX_COMPACT_RETRY_CHARS` behavior.
- Add a minimal threat model for shelling out to `CODEX_BIN`: PATH trust assumptions, prompt-content handling, temp/log file handling, and why the stdin pipe does not introduce new injection or leakage risks.
- Reduce scope to the bug fix plus regression tests unless there is a hard policy requiring README/artifact updates; if required, cite that policy explicitly.
