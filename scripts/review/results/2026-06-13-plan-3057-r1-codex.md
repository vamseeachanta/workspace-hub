## Findings
1. Plan §Pseudocode lines 261-268 will create stale-tail false positives. It says to mark hygiene ERROR if `recent_tail has /^task=repo-ecosystem-hygiene .*status=ERROR\b/`, while `cron-health-check.sh` scans `tail -n 100` at lines 226-255. The plan’s own evidence at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:178-181` shows an append-only hygiene log tail containing an older `status=ERROR` followed by newer `status=WARN` lines. This plan would keep cron-health red after a later successful/non-error run if the older ERROR remains in the last 100 lines. It must parse the latest hygiene evidence line for that task, not any matching line in the tail.

2. The crontab executability contract is internally inconsistent. The deliverable and acceptance criteria require the generated crontab to run without manual `WORKSPACE_HUB` / `LOG` edits (`docs/plans/...:220-222`, `311`), but the TDD rows allow either concrete command rendering or an “emitted env contract” (`docs/plans/...:296-297`). Current `cron_apply.py` dry-run returns only `status`, `preserved`, `conflicts`, and `selected` at lines 162-166, so a JSON-only “required env contract” could pass review while the applied `new_text` still lacks top-level env definitions in a clean/no-env crontab. The plan needs one enforceable path: expand placeholders in managed command lines, or generate env lines into `new_text` and test the applied crontab.

3. The planned setup-cron parity test misses half the stated defect. `docs/plans/...:299` only requires no unresolved `$LOG`; the live issue and plan scope repeatedly name both `$WORKSPACE_HUB` and `$LOG` (`docs/plans/...:42-44`, `311`). Existing setup-cron expansion handles both at `scripts/cron/setup-cron.sh:135-140`, but the proposed test could pass while `$WORKSPACE_HUB` regresses.

4. The live timeout acceptance is too narrow for the script’s actual iteration surface. `docs/plans/...:313` only names live `workspace-hub` and `digitalmodel`, but `repo-ecosystem-hygiene-audit.sh` iterates all governed repo names from the registry at lines 674-686, and `config/workstations/registry.yaml:73-87` includes more required/current repos. A fix can pass the named two-repo probe while still producing `git_probe_timeout` or deadline-driven incomplete status elsewhere in the real daily audit.

## Blockers
1. Finding 1: cron-health must evaluate only the latest hygiene evidence line, with a test where an older `status=ERROR` is followed by newer `status=WARN` or `status=OK`.
2. Finding 2: the plan must choose and test one concrete crontab executability mechanism for clean/no-env crontabs.
