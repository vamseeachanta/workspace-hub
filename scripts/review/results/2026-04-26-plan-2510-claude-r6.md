## Findings

1. **Determinism Contract demands a two-run byte-diff probe but none is embedded; the only "evidence" probes a flag default, not bytes.** Plan §Determinism Contract line 335: *"Execution must include a two-run byte-diff probe for `chip_package_demo.gds`."* The §Evidence (embedded verification) probe at lines 92-101 only inspects `inspect.signature(gf.Component.write_gds)` and `getattr(opts, "gds2_write_timestamps", None)`. That confirms the API surface and the timestamp default — it does **not** observe `sha256(gds_a) == sha256(gds_b)` across two runs. GDSII has additional non-determinism sources beyond timestamps (cell-reference ordering, library-record ordering, vertex ordering inside polygons, rounding when shapes cross dbu grid). Pinning `gds2_write_timestamps=False` does not by itself prove byte-equal output. The plan should embed an actual two-run probe in §Evidence, OR demote the determinism claim to "guarded at runtime, blocker if unequal" and remove AC #6 from the closeout list until proved.

2. **Transitive-dep pinning is incomplete; byte-determinism is not actually falsifiable.** §CLI and Dependency Contract line 169 pins `gdsfactory==9.40.2 --with kfactory==2.4.7 --with klayout==0.30.8` but not Python itself, not `numpy`, not `shapely`, not `kdb` patch level. `gf.Component` geometry math is numpy-backed; numpy version drift can shift floating-point rounding for shapes near dbu boundaries and thus shift GDS bytes. `uv run` will resolve a new numpy whenever pip publishes one. AC #5 (manifest re-validation by `sha256sum -c`) becomes silently fragile on any future date. Either pin `--python 3.X` plus `--with numpy==N --with shapely==M`, or commit a `uv.lock`/`requirements.txt` for the demo, or scope the determinism guarantee to a frozen instant and document the expected expiry.

3. **`90bfa08d3` is stale review-traceability evidence.** Plan line 74 says: *"docs/plans/2026-04-26-issue-2510-python-layout-cad-automation-demo.md exists locally and is pushed to main in commit 90bfa08d3 for review traceability."* That commit is the **initial draft**. The current `origin/main` is `1830d17` ("docs: harden layout CAD plan after r4 review") and the working copy contains uncommitted r5 patches on top. A reviewer following the cited SHA will retrieve the pre-r4 plan and grade against an outdated artifact. Update the line to `1830d17` (or whichever SHA carries the version under review), or delete the SHA reference entirely and let `@main` resolve to the tip.

4. **Polygon-count upper bound `* 4` is arbitrary and admits 4× reader misbehavior.** §TDD Test List line 254 (test #4) accepts `generated_count <= readback_count <= generated_count * 4`. For axis-aligned rectangles + bumps, GDSFactory + GDS round-trip is essentially lossless; flatten typically produces equality, not a 4× explosion. A reader that erroneously fractures one rectangle into four pieces — a real failure mode for poorly-implemented boolean/clip operations — would pass. Tighten to equality (justified by "all shapes are axis-aligned rectangles, flatten preserves count") OR specify per-layer bounds derived from the geometry generator (e.g., bump-array layer expects exactly `pad_count` polygons). The current bound exists only because the author was uncertain; that uncertainty is itself a finding.

5. **`pinned reader version` JSON key is required by a test but never named in the CLI contract.** Test #4 (line 254) requires `gds_readback_metadata.json` to contain "pinned reader version." Pseudocode `import_exchange_artifact` (lines 213-217) says *"extract read-back cell name, layer/polygon counts, bbox, and labels/ports where available"* — does not list a writer/reader version key. Pseudocode `write_metadata` (lines 219-221) writes `layout_metadata.json`, not `gds_readback_metadata.json`. The implementer can satisfy the test with any key shape (`reader_version`, `gdsfactory_version`, `tool.version`); the test then has to match whatever the implementer chose. Pin the exact JSON keys in the CLI Contract: e.g., `gds_readback_metadata.reader.package == "gdsfactory"` and `…reader.version == "9.40.2"`.

6. **Manifest path semantics under arbitrary `--report` invocation are still undefined.** AC #5 (line 269) walks the canonical case where the report sits at `docs/reports/...` and the manifest sits at `data/semiconductor/layout_cad_demo/`; the relative key is `../../../docs/reports/...`. Determinism Contract line 333: *"Manifest entries must be relative to the manifest file parent directory."* This works **only** when `os.path.relpath(report_path, manifest_dir)` is well-defined. If a user runs the CLI with `--output /opt/foo --report /home/me/r.md` (not under repo root, not siblings), `relpath` still resolves to a `..`-traversing string but the resulting manifest is brittle and hash-divergent across machines (different absolute prefixes shorten differently). Either restrict `--output` and `--report` to be under `--output`'s parent (or an explicit `--manifest-root`), or document `relpath` cross-machine assumptions explicitly. The current "the same relative-to-manifest rule applies" hand-wave is not enough for `test_outputs_are_deterministic_across_runs` to be meaningful across CI environments.

7. **`test_outputs_are_deterministic_across_runs` does not assert manifest equality.** Lines 244, 256: the test runs in two temp dirs and checks "equal content hashes for manifest-covered artifacts." The manifest itself is the file whose **text** depends on the path-resolution policy in finding 6. If the test only diffs covered artifacts (svg, csv, json, gds, readback json, report), it cannot catch a manifest writer that emits non-deterministic ordering, mixed line endings inside the manifest, or an unstable path-resolution shortcut. Add `sha256(manifest_a) == sha256(manifest_b)` explicitly, OR add `manifest_a.read_text() == manifest_b.read_text()`.

Line 12: *"Review artifacts (r5 current/canonical): scripts/review/results/2026-04-26-plan-2510-{claude,codex,gemini}.md"*. Line 13: *"Review artifacts (r5 archive after run): …-r5.md"*.
