### gemini

- **Python tests validating Markdown prose.** Plan §Files to Change proposes creating `docs/architecture/execution-manifest-schema.md` and `docs/architecture/execution-routing-matrix.md`. Plan §TDD Test List proposes `tests/architecture/test_execution_layer_contract.py` to verify required fields and columns in these documents. Writing Python tests to parse and validate unstructured Markdown prose or tables is brittle and non-standard. If these definitions require programmatic validation, they must be backed by a machine-readable format (e.g., JSON Schema, YAML), not just `.md`.
- **Contradiction in E-L2 tooling scope.** Plan §Proposed Execution Layer Levels defines E-L2 (Tools/code execution) as exclusively "Python via `uv run`". However, Plan §Standards explicitly cites `scripts/legal/legal-sanity-scan.sh` as an applicable standard. Restricting E-L2 to Python breaks the ability to use the repository's existing shell scripts for validation gates.
- **Pseudocode proposes unimplemented automation.** Plan §Pseudocode outlines a `function execute_pipeline(execution_manifest)` that routes work, runs tools in isolated workdirs, and collects artifacts. However, Plan §Files to Change contains no actionable code changes to implement this pipeline orchestrator—only Markdown files and one test file. The plan conflates documenting the architecture with building the runtime orchestrator.
- **Open question blocks test implementation.** Plan §Risks and Open Questions states: "Open: Should execution manifests be markdown, YAML, or both?" If the manifest format is unresolved, the TDD tests (specifically `test_execution_manifest_required_fields` against the "schema doc") cannot be implemented, as the parser implementation depends entirely on this decision.
