### Verdict: APPROVE

### Summary
The v3 plan is thorough, internally consistent, and convincingly addresses the prior review rounds — locked design decisions D1–D6 with explicit counter-options, a clean state machine with declared states separated from classifications, a concurrency contract (fcntl + atomic rename + UTC pinning), and a dependency contract mapping #2017 outputs to downstream consumers. The scope fence (design doc + config files + xfail'd pipeline tests) is coherent, and the acceptance criteria are falsifiable. A handful of minor tightenings would strengthen it, but nothing rises to a blocker.

### Issues Found
- [P3] Minor — Pseudocode/spec drift on extraction-missing reactivation: D3 says emit a structured `extraction_missing_on_reactivation` event AND treat as new inbound, but the `on_inbound_reply` pseudocode just calls `classify_inbound(message)` in that branch without the log event. Similarly, the acceptance test `test_purged_treated_as_new_if_extraction_missing` only checks 'treated as fresh inbound' and does not assert the structured log event was emitted — the very behavior D3 was strengthened to provide will silently regress without a test.
- [P3] Minor — Snapshot freshness protocol has an ambiguity: the reader protocol says rebuild from log if `snapshot.mtime < latest jsonl_entry.ts`, but readers generally cannot cheaply read 'latest jsonl_entry.ts' without scanning the log (defeating the snapshot). Specify how readers cheaply determine staleness (e.g., a tiny `snapshot-meta.yaml` with `last_log_offset`, or comparing against log file size/inode).
- [P3] Minor — `writer_identity` is required on transitions and the learning log, but the state-schema acceptance criterion (`docs/design/email-queue-state-schema.yaml`) does not include a test asserting the schema actually declares and rejects missing `writer_identity`. Absent a schema-validity test that checks required fields, drift between D1/D4 prose and schema is likely.
- [P3] Minor — `test_snapshot_atomic_write` describes a crash-injection test (`simulated write failure mid-snapshot`) but does not specify the injection mechanism (monkeypatch on `os.rename`? fault injection in `fsync`?). Without a named technique the test risks becoming a tautology.
- [P3] Minor — Quarterly review cadence binds to calendar quarters (Jan/Apr/Jul/Oct 1) but the system goes live mid-quarter (Apr 20, 2026). First review on Jul 1, 2026 will cover only ~10 weeks — plan should either call that out explicitly or specify a bootstrapping rule.
- [P3] Minor — Precedence rule currently stores `secondary_classification` but the pseudocode's `apply_precedence` is not defined elsewhere (what happens with 3+ matches? is ordering stable?). A one-line deterministic rule would close the ambiguity for #2024 consumers.
- [P3] Minor — The 'Dropped from scope' line says `.planning/INDEX.md is dropped` but the Files to Change table still lists `docs/plans/README.md` as modified; confirm these are distinct indices (appears to be, but a reviewer glancing at both will double-take).

### Suggestions
- Add a test `test_extraction_missing_on_reactivation_emits_learning_event` that asserts both the JSONL entry and the `queue-learning-log.jsonl` event are written when a reply arrives on a purged thread whose extraction has been deleted — closes the spec/pseudocode/test gap in one move.
- Fix the pseudocode's `else` branch in `on_inbound_reply` to emit the structured log event before calling `classify_inbound`, matching D3's prose exactly. This is a ~2-line edit but eliminates a future-you footgun.
- Introduce a tiny `queue-state-snapshot.meta.yaml` (or trailer in the snapshot) with `last_log_byte_offset` / `last_log_sha`; readers compare against `os.stat(log).st_size` to decide freshness in O(1).
- Specify the fault-injection approach for `test_snapshot_atomic_write` — e.g., 'monkeypatch `os.rename` to raise after `fsync` returns; assert final snapshot path unchanged and `.tmp` left behind or cleaned per policy'.
- Add an explicit bootstrap clause for the learning-review cron: 'first review dispatched 2026-07-01 covering the partial Q2 window' — avoids ambiguity for the cron author.
- Define `apply_precedence` formally: 'iterate classifications in the fixed ordering [actionable, data_extract, drive_doc, unsubscribe, archive, noise]; first match → primary; remaining matches → secondary list in the same ordering'. This makes #2024's implementation mechanical.
- Consider whether `xfail` pipeline tests should be `skip(reason='#2024 not yet landed')` instead — `xfail` will count as 'unexpected pass' noise if someone partially implements the pipeline out-of-band; `skip` gated on a `HAS_PIPELINE` marker is typically cleaner.
- For the 'v2/v3 verdicts pending' table: once v3 is dispatched, make sure the plan commit and the review-results commit are paired so reviewers always see matching `plan_sha` — the review artifacts at `scripts/review/results/...` should include the plan SHA they reviewed.

### Questions for Author
- The reader protocol rebuilds from log when snapshot is stale — what is the bound on acceptable rebuild time? You mention 1s as a compaction trigger; is that the same threshold, or does staleness-rebuild have its own SLO that should appear in acceptance criteria?
- D1 says the daily sweep takes a separate lockfile `/tmp/email-queue-sweep.lock` — is `/tmp` acceptable given cross-host execution? If the sweep runs on a different machine than the inbound handler, the lock provides no mutual exclusion. Should this be `<repo>/.locks/` or a systemd mutex?
- `writer_identity` includes PID + host — are PIDs ever recycled within the retention window of the log (the JSONL appears to be kept indefinitely given 18k entries/year)? If so, consider adding a boot-id or monotonic counter for true uniqueness.
- The plan accepts the Gmail 30-day Trash auto-purge as a data-loss boundary, but the trash-purge recovery path in D3 assumes you can `lookup thread_id → linked_extraction_path` — what happens if a reply arrives after Gmail has purged the thread from Trash and Gmail assigns a new `thread_id` for the resumed conversation? Is thread identity actually stable across that boundary?
- For the `letstok_web_form_abuse` rule's ≥10-sample legitimate-inquiries corpus — are those samples drawn from real inbound mail (redacted) or synthesized? If real, is there a redaction checklist committed alongside the fixtures to prevent PII leakage in future additions?
- The skylineseven routing decision is user-gated and labeled as blocking implementation but not plan approval — if the user picks 'keep DELETE', does the conditional test `test_routing_yaml_skylineseven_present_per_user_decision` simply not exist, or does it assert the absence? The current wording ('conditional — only if user chose CRE route') suggests test-existence is mutable, which complicates CI reproducibility.
- v3 revision note mentions 'replace "treat as new" with structured log event' — is the prior 'treat as new' path fully removed, or (per pseudocode) still the fallback after the log event is emitted? The changelog wording and the pseudocode appear to disagree.
