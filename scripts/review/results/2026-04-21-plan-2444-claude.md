### Verdict: MAJOR

### Summary
Plan is close to shippable but has a load-bearing internal contradiction (Deliverable uses `uv sync`, Spec uses `uv pip install -e`), a HIGH risk that is not evidence-backed yet is also left unmitigated while acceptance criteria demand a GREEN first run, and some template-fidelity drift that is not called out in the substitutions list. Not approvable as-is.

### Issues Found
- Deliverable/Spec contradiction: line 105 says the workflow runs `uv sync --extra test --extra dev`, but the Detailed CI Workflow Spec step 5 (line 211) says `uv pip install -e ".[dev,test]"`. These are different commands with different semantics — `uv sync` expects a uv-managed project (with a lock file and typically a `[tool.uv]` config), while this pyproject.toml uses the `setuptools` build backend and has no `uv.lock`. The plan must pick one and make Deliverable and Spec agree; otherwise the reviewer cannot know which command the implementer will write.
- HIGH-risk mitigation is deferred to the reviewer while acceptance criteria require GREEN: Risks section (line 228) says `tests/knowledge/` may fail-import and leaves two options 'open for reviewer'. Acceptance Criteria (line 145) says 'First GitHub Actions run ... is GREEN on both py3.11 and py3.12'. A plan cannot ship with an unresolved HIGH risk whose non-resolution would violate an acceptance criterion. Pick a mitigation in the plan itself (install `[knowledge-semantic]`, or `--ignore=tests/knowledge`, or a `-m 'not semantic'` marker) before approval.
- HIGH risk is speculative and not verified: I grepped `aceengineer-admin/src/aceengineer_admin/knowledge/` and `aceengineer-admin/tests/knowledge/*.py` — there are no top-level imports of `sentence_transformers` or `numpy`. The matches that exist are string literals (e.g. `test_code_scanner.py:67 "import numpy as np\n"` inside a test fixture payload). If the imports are actually done lazily inside functions, the collection-time failure mode the plan worries about may not occur. Either (a) cite the specific file/line that will fail on first CI run, or (b) downgrade the risk level.
- Template fidelity drift not disclosed in Pseudocode substitutions: Source template (`workflow-automation-tests.yml` lines 23-33) runs `actions/setup-python@v5` BEFORE `astral-sh/setup-uv@v5`. Plan's Detailed Spec (lines 207-209) reverses them (setup-uv first, setup-python second). Plan's Pseudocode section (line 111) enumerates the substitutions made but does not disclose this ordering change. Either preserve the source order or call out why it was swapped.
- Template fidelity drift — dropped verification steps not in substitution list: Source template has a `Verify package installation` step (lines 60-62 `python -c "from digitalmodel..."`). Plan replaces it with `compileall`, which verifies bytecode-compilability but NOT that `aceengineer_admin` is importable from the installed package. For a 'minimal viable' CI whose point is to surface install/import regressions, dropping the import-smoke while also skipping the CLI smoke (`aceengineer --help`) leaves no step that actually exercises the installed package. Either add `python -c 'import aceengineer_admin'` or justify why compileall is sufficient.
- `workflow_dispatch` is listed as Open, self-described as zero-cost and recommended (line 233), then omitted from the Detailed Spec (lines 206-215). Open questions should be resolved in the plan, not carried forward as runtime surprises.
- Acceptance criterion 'Summary comment posted back to issue #2444 with the Actions run URL' (line 150) has no corresponding implementation in the Detailed Spec — there is no `actions/github-script` step or equivalent. This is either (a) a manual step that should be moved to a post-merge checklist, or (b) a missing workflow step. As written it's ambiguous and likely to be silently dropped.
- No `concurrency` group is specified. For a `push` + `pull_request` workflow that will be triggered on every merge and every PR update, lack of `concurrency: {group: ..., cancel-in-progress: true}` will burn minutes on superseded PR commits. Minor but easily fixed before first run.
- `paths-ignore` list includes `docs/**` and `**/*.md` (lines 193-194) — this skips CI when the only changed files are docs or markdown. That is fine in isolation, but the plan's own artifact `aceengineer-admin/.github/workflows/ci.yml` lives under `.github/`, which is NOT in `paths-ignore`; any workflow-only edit would still run. That's correct. However, the plan also claims (line 134) 'commit that only edits `.claude/**` does NOT trigger CI' — verified, `.claude/**` is in the list — so that part checks out. Flagging only because it's worth ensuring `.github/**` is intentionally absent from ignore.
- Matrix narrowing (single OS, drop 3.13) partly justified but not cost-quantified: aceengineer-admin's real invoice/xlsx workflows almost certainly run on Windows in production. The source template ran `[ubuntu-latest, windows-latest]`. Dropping Windows is defensible for T1 minimal-viable, but the plan should explicitly note that Windows-specific regressions (path separators, openpyxl behaviors, locale) will not be caught and add a follow-up issue reference. Right now it's dropped without a tracked follow-up.

### Suggestions
- Resolve the `uv sync` vs `uv pip install -e '.[dev,test]'` inconsistency. Given the pyproject.toml uses setuptools and has no `uv.lock`, `uv pip install -e '.[dev,test]'` is the correct command. Update the Deliverable paragraph to match the Spec.
- Commit to a concrete mitigation for `tests/knowledge/` before approval: either (a) add `knowledge-semantic` to the install line (`uv pip install -e '.[dev,test,knowledge-semantic]'`), or (b) add `--ignore=tests/knowledge` to the pytest invocation and open a follow-up issue to re-enable it with proper extras. Record the chosen option in Detailed Spec step 8.
- Before finalizing the HIGH risk, run `uv pip install -e '.[dev,test]'` locally in a clean venv and `uv run pytest tests/knowledge/ --collect-only` once — that takes 60 seconds and converts the risk from speculation to evidence. If it collects cleanly, downgrade the risk and drop the open-for-reviewer question.
- Preserve the source template's `setup-python` → `setup-uv` ordering or explicitly document the reason for swapping. `astral-sh/setup-uv@v5` does cooperate either way, but the plan should not silently diverge from the adopted template.
- Replace the `compileall` step (or augment it) with an explicit import smoke: `uv run python -c 'import aceengineer_admin; print(aceengineer_admin.__version__)'`. This costs one line and is the single best regression check for a packaging-heavy repo.
- Add `workflow_dispatch:` and a `concurrency` block to the Detailed Spec rather than leaving them as Open questions.
- Either add an `actions/github-script` step that comments the run URL back to issue #2444, or move that bullet from Acceptance Criteria into a separate 'Post-merge governance' checklist so it isn't confused with the workflow's internal behavior.
- Open a follow-up issue for Windows matrix + Python 3.13, and reference its ID inline in 'Not included (deferred to follow-ups)' so the deferral is tracked rather than implicit.
