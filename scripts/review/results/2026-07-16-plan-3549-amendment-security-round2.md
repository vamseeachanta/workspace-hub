## Blocking findings

1. **[MAJOR] The overlay 4-versus-5 contract is prose-only and still lacks the exact two RED cases required by round 1.** The revised amendment names only “an overlay read `OSError`” without an expected exit, field path, error class, or injected errno (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:202-207`). The next paragraph says availability errors will remain 4 while integrity/digest and otherwise-unclassified local overlay I/O will return 5 (`:215-218`), but it does not define an executable test for either side of that boundary. This is not a theoretical distinction: the current overlay boundary maps parent lookup `OSError` to `FallbackUnavailableError`/4 (`src/workspace_hub/workstations/connection.py:227-233`), maps non-`ENOENT` file-open `OSError` to `OverlayIntegrityError`/5 (`:241-247`), and leaves `stream.read()` `OSError` untranslated (`:256-257`), after which the command's combined catch reports `registry_unavailable`/3 (`src/workspace_hub/workstations/connection_command.py:167-176`). The existing resolver test proves only a missing overlay returns 4 (`tests/workstations/test_connection_resolver.py:390-397`); it does not exercise a read error or the command boundary. The round-1 requirement for one availability errno and one integrity/I/O errno, with stable redacted diagnostics and proof that neither becomes registry exit 3, therefore remains open. **Blocking change:** require exact command-level RED cases such as overlay file `ENOENT` → exit 4 with `overlay.file`/`unavailable`, and post-open `EIO` read failure → exit 5 with a named stable overlay I/O class; assert exit is not 3 and stderr contains neither the path, rejected data, nor exception text.

2. **[MAJOR] The launch mapping is specified, but the TDD contract still cannot prove “127 only for `ENOENT`” or stable redaction for every pre-child failure family.** The normative correction says `ENOENT` alone maps to 127 and every other pre-child `OSError` maps to 126, with diagnostics containing only stable classes (`docs/plans/2026-07-16-issue-3549-registry-connection-helpers.md:211-214`). However, the named RED/negative controls cover only `ENOEXEC`, an unspecified “missing executable,” and normal child status (`:202-210`); they do not require errno-bearing constructions for `ENOENT`, `EACCES`, `ENOEXEC`, and an unrelated error such as `E2BIG`/`ETXTBSY`, and they do not require exact stderr field/class plus raw-message canaries for each family. The current test uses bare `FileNotFoundError()` and `PermissionError()` objects and asserts only numeric return values (`tests/workstations/test_connection_cli.py:168-177`), so it is green even though current `_launch` catches the exception subclasses rather than inspecting errno and lets `ENOEXEC`/`E2BIG` escape (`src/workspace_hub/workstations/connection_command.py:128-139`). A direct probe at the reviewed commit confirmed bare `FileNotFoundError(errno=None)` returns 127 while `OSError(ENOEXEC, ...)` and `OSError(E2BIG, ...)` escape. The global redaction acceptance sentence (`docs/plans/...:388-391`) does not make these missing RED assertions executable. **Blocking change:** require a parameterized RED matrix using exact errno-bearing exceptions—`ENOENT` → 127; `EACCES`, `ENOEXEC`, and at least one unrelated pre-child errno → 126—plus exact stable field/error-class assertions and secret/path/message non-disclosure for each. Retain the already specified `KeyboardInterrupt` and child `-SIGINT` → 130 controls.
