## Verdict: REQUEST-CHANGES

Two findings. Both require plan text changes before implementation. Neither is a defect in the produced work (there is no produced work yet); both are gaps in the v2 TDD + acceptance coverage that would allow a wrong-result implementation to pass every gate.

## Findings

### F1 — CTAs hardcode "1 page" but v2 TDD only checks asset existence / file type / size

**Claim:** The v2 plan prescribes a literal CTA copy of `"Download Capability Summary (PDF, 1 page)"` across all 5 anchors. The v2 TDD row `pdf_asset_exists_at_target` verifies the asset is a non-trivial PDF (size > 10KB + magic bytes), but does **not** verify it is actually 1 page.

**Drift scenario:** if #2344 implementation (which this plan depends on) renders a 2-page PDF — e.g., a late-stage copy edit pushes content past the Letter-page boundary — #2344's own render-side gate would catch it, but this plan has no independent check. If #2344's gate regressed or was bypassed, every one of this plan's 5 CTAs would mislabel the artifact undetected. The copy couples to a physical attribute of the asset; the asset's physical attribute is not independently verified here.

**Remediation:** add a pre-commit TDD row `pdf_is_one_page` that runs `pdfinfo aceengineer-website/assets/capability-summary-v1.pdf | awk '/^Pages:/{print $2}'` and hard-fails on any value other than `1`. Add a matching acceptance criterion. The test runs BEFORE the CTA-wiring Edits are accepted, so a drift in #2344 surfaces at this plan's implementation time, not in production.

### F2 — Placement tests grep only basename / counts, so an implementation in the wrong container would still pass

**Claim:** The v2 plan's placement tests (`cta_anchor_in_gallery`, `cta_anchor_in_4_methodology_pages`) verify that each page contains exactly one anchor to the versioned PDF basename. They do not verify **where** in the page the anchor sits.

**Drift scenario:** an implementation agent that placed the gallery CTA in the footer `.demo-cta-section` (v1's silent default, reversed by v2's hero placement) would still pass `cta_anchor_in_gallery`. An agent that placed the methodology CTA in the `.method-toc` sidebar instead of the `.method-cta` block would still pass `cta_anchor_in_4_methodology_pages`. The plan's placement decisions (hero for gallery, `.method-cta` for methodology) are asserted in prose but not tested in code.

**Remediation:** add three structural-placement TDD rows:
1. `cta_in_gallery_hero` — positive: extract the span between `<section class="demo-hero">` and its matching `</section>`; assert exactly one match for `capability-summary-v1\.pdf` in that span.
2. `cta_in_methodology_method_cta` — positive, parameterised per slug: for each of 4 methodology slugs, extract the span from `<div class="method-cta text-center">` up to and including its matching closing `</div>` on the minified body line; assert 1 match per page.
3. `cta_NOT_in_gallery_footer` — negative: extract the span between `<section class="demo-cta-section">` and its matching `</section>`; assert 0 matches for `capability-summary-v1\.pdf`. Prevents accidental dual-placement.

Add matching acceptance criteria summarising both positive and negative directions.

## Claims verified

- Plan v2 TDD rows `cta_anchor_in_gallery` / `cta_anchor_in_4_methodology_pages` rely on `grep -c` over the whole file — no section scoping.
