## Findings
### Finding 1 — MAJOR — The claimed idempotency is not correct if scores change mid-day
- Plan claim: "`# idempotency: read existing file, keep records with new (event, provider, date) tuples`"
- Location: `emit_signals` pseudocode; Files to Change says "`emit-session-signals.py` ... with cross-file dedupe scan"
- Evidence: The dedupe key is only `(event, provider, date)`. If the scorer is rerun the same day after fixing a bug, ingesting more logs, or recalculating a score, the updated record is discarded as a duplicate. The pseudocode also only reads `existing` from the current file, not a "cross-file dedupe scan."
- Why it matters: This makes the per-day deterministic filename stale-by-design. A bad morning run cannot be corrected later that day without manual file surgery.
- Suggested fix: Define replace-by-key semantics for same-day reruns, e.g. rewrite the day file with latest records by `(event, provider, date)`, or add a run/version field plus explicit latest-wins logic. Align Files to Change with the actual algorithm.

### Finding 2 — MAJOR — The plan still does not prove automatic pipeline consumption
- Plan claim: "emits `gate_compliance_score` + `provider_capability` events into `.claude/state/session-signals/` ... consumed automatically by the nightly cron with no pipeline schema change"
- Location: Deliverable section
- Evidence: [session-analysis.sh](https://github.com/vamseeachanta/workspace-hub/blob/main/scripts/analysis/session-analysis.sh) extracts skills only from `select(.event == "session_end") | .signals.skill_invocations[]?`. It has no reader for `gate_compliance_score` or `provider_capability`. The plan's own acceptance criterion later weakens this to "`OR the drop behavior is documented with a warning log`," which concedes non-consumption.
- Why it matters: Output 4 is presented as a live pipeline input, but the only verified consumer ignores it. That is a core scope contradiction, not a polish issue.
- Suggested fix: Either add a concrete `session-analysis.sh` handler to the plan and Files to Change, or remove the "consumed automatically" / "no pipeline schema change" claim and scope Output 4 as archival-only.

### Finding 3 — MAJOR — The scoring contract is under-specified and not derivable from the verified corpus
- Plan claim: "`docs/standards/session-log-format-contract.md`" will define the parser/scorer contract; pseudocode scores `verify-gate-evidence`, `test_write_event`, `impl_write_event`, `skill_invoke`, and `gate_bypass`
- Location: Design Decision Q4; `score_provider` and `find_hard_gate_violations` pseudocode
- Evidence: `session-log-format-contract.md` does not exist in the repo. The verified signal corpora I fetched show `session_tool_summary`, `stage_exit`, and `codex_session` events, not the events the scorer requires. The plan does not specify how raw logs map to those derived events.
- Why it matters: Most of the six dimensions are not independently computable from the verified repo artifacts as currently specified. The parser/scorer contract is still aspirational.
- Suggested fix: Inline the minimum event grammar in the plan itself: exact required fields, which source files produce them, and how each metric is computed from real log lines. If some dimensions cannot be derived, cut or defer them.

### Finding 4 — MAJOR — The TDD list references a missing fixture
- Plan claim: "`test_parse_logs_claude_nominal` ... Expected input `logs/claude-stage2-t1.log`"
- Location: TDD Test List
- Evidence: Fetching `logs/claude-stage2-t1.log` returned 404. I also checked another plausible log path and did not find a repo-tracked log file at the named location.
- Why it matters: A named first-line parser test cannot run against a non-existent fixture. That makes the test plan non-executable as written.
- Suggested fix: Replace the test input with an existing committed fixture, or add fixture creation to Files to Change with the exact path and schema.

### Finding 5 — MAJOR — `routing-rules.yaml` creates a third routing policy source with no precedence
- Plan claim: "`routing-rules.yaml` = declarative static policy; `routing-config.yaml` continues as the dynamic smart-router runtime config"
- Location: Design Decision Q2; Routing-Rules Schema; Output 3
- Evidence: [routing-config.yaml](https://github.com/vamseeachanta/workspace-hub/blob/main/config/agents/routing-config.yaml) already contains tiers, fallbacks, dimensions, and cross-review switches. [behavior-contract.yaml](https://github.com/vamseeachanta/workspace-hub/blob/main/config/agents/behavior-contract.yaml) already contains `provider_assignment.task_type_matrix` plus a `provider_assessment` model. The plan does not name any consumer of `routing-rules.yaml` or define precedence between the three files.
- Why it matters: This is policy drift waiting to happen. Future routing changes can disagree across three files with no authoritative resolver.
- Suggested fix: Either extend one existing source of truth, or explicitly define consumer, precedence, and ownership boundaries for each file. If `routing-rules.yaml` is derived output, say so and do not make humans edit it.

### Finding 6 — MINOR — The sandbox-fallback hedge is auditable only by narrative, not by artifact
- Plan claim: "when the Codex sandbox blocks `apply_patch` ... Claude transcribes Codex's emitted patch manually and the commit message attributes Codex as the original author"
- Location: Design Decision Q6; Acceptance Criteria final bullet
- Evidence: [AI_REVIEW_ROUTING_POLICY.md](https://github.com/vamseeachanta/workspace-hub/blob/main/docs/standards/AI_REVIEW_ROUTING_POLICY.md) keeps Claude as orchestrator and Codex as worker, which is fine. The problem is narrower: the plan relies on a manual transcription path but defines no patch artifact, no checksum, and no provenance record beyond a commit-message note. The cited `feedback_codex_sandbox_write_blocked` string is not repo-tracked.
- Why it matters: Manual transcription introduces race and attribution ambiguity. A commit message alone does not prove the landed patch matches what Codex actually produced.
- Suggested fix: Require a committed or attached intermediate patch artifact from Codex, then have Claude apply that exact artifact. Make provenance verifiable from repo/GitHub state, not memory.

### Finding 7 — MAJOR — The absent-provider / zero-data case contradicts the acceptance criteria
- Plan claim: "`test_score_zero_sessions` returns explicit `insufficient_data` sentinel"
- Location: TDD Test List
- Evidence: The Acceptance Criteria also require `provider-assessment.md` to contain 6-dimension scores for `claude/codex/gemini` and require the signal file to contain at least one `gate_compliance_score` and one `provider_capability` event for each of those providers. The plan does not define what happens if any provider has zero sessions in 2026-03-08→15.
- Why it matters: The plan simultaneously allows `insufficient_data` and requires complete per-provider outputs. Those cannot both be true without an explicit sentinel/output policy.
- Suggested fix: Define one behavior for missing-provider windows: fail the issue, emit explicit `insufficient_data` records, or mark the report as incomplete. Then update the acceptance criteria to match.
