## Findings
1. Plan still has the OR-shaped dry-run executability contract it claims to have removed. `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:270` says “include rendered `new_text` or `managed_preview`”, test row `:320` expects “`new_text` or `managed_preview`”, and acceptance criterion `:335` repeats “rendered `new_text` or managed preview”. That contradicts the revision claim at `:360` that the OR-shaped path was removed. A preview can diverge from the actual `plan_cutover(...)[new_text]` path in `scripts/cron/cron_apply.py:156-166` and `scripts/cron/cron_transaction.py:356-380`, so this remains an approval blocker.

2. The latest-evidence-line plan does not address older generic execution failures in the same append-only hygiene log tail. The plan promises at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:305` that newer `status=WARN`/`status=OK` clears task-level failure, and tests only older `status=ERROR` followed by newer WARN/OK at `:326-327`. But `scripts/cron/repo-ecosystem-hygiene-audit.sh:752-764` emits `ERROR: repo-ecosystem-hygiene execution_failed...` on execution failure, and `scripts/monitoring/cron-health-check.sh:83-92` plus `:226-254` will still scan the last 100 lines for `ERROR:` and mark the task red. The plan needs explicit semantics and tests for “older `ERROR:` execution_failed followed by newer machine-readable OK/WARN”.

3. Timeout acceptance is internally inconsistent with the live governed repo set. The plan sets per-probe/per-repo defaults to 30/120 at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:274-279` and acceptance `:338` requires completing across the live governed repo set, but current code keeps total timeout default 480 seconds at `scripts/cron/repo-ecosystem-hygiene-audit.sh:12` and `:39`. The governed set is built from required, optional, and `non_tier1_machine_access_current` buckets in `scripts/cron/repo-ecosystem-hygiene-audit.sh:292-305`; `config/workstations/registry.yaml:65-86` defines 17 total governed repos for `dev-primary`. A 120-second per-repo budget across 17 repos cannot be reconciled with a 480-second total budget without an explicit scheduling/bounding policy. The fallback clause “or justifies any remaining timeout” at plan `:338` is also too loose to prove the fix.

4. The setup-cron parity test does not cover the actual selection-contract divergence. The plan calls `setup-cron.sh` the “semantic parity reference” at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:323`, but `scripts/cron/setup-cron.sh:117-122` selects tasks only by `machines`, while `scripts/cron/cron_transaction.py:205-263` selects by role and legacy machine pin with conflict behavior. The proposed test only checks a hostname alias emits hygiene/health entries; it does not include a role-vs-machine conflict fixture proving transactional rendering and setup-cron rendering are being compared over the same selected task set.
