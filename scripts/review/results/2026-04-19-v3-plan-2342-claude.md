## New v3 findings

### Finding 1 — npm `dist.shasum` is SHA-1, but plan labels it "SHA256"
**Severity:** minor
**Evidence:**
- Acceptance criterion line 278: "`assets/js/plotly-2.32.0.min.js` committed with a concrete SHA256 recorded in commit message (v3: obtained via `npm view plotly.js-dist-min@2.32.0 dist.shasum`)"
- Verified (via live command `npm view plotly.js-dist-min@2.32.0 dist.shasum`): returns `2977d2cd974a15bab1442b2c472d999b79d83e9a` — a **40-char hex string**, which is SHA-**1**, not SHA-256. npm's `dist.shasum` field stores the tarball SHA-1 hash.
- For SHA-256, npm uses `dist.integrity` (e.g., `sha512-...` or `sha256-...` subresource-integrity format), not `dist.shasum`.
- Known Minor Debt table row D (line 370) carries the same mislabel.
**Impact:** Operator follows the command literally, commits a 40-hex SHA-1 under the label "SHA256", and the commit message becomes provably wrong. Cross-review catches it; deploys anyway; confusion in audit.
**Recommendation:** Either (a) rename the label to "SHA-1" (matches what `dist.shasum` actually returns — honest but weaker security guarantee), or (b) keep "SHA256" and update the command to `npm view plotly.js-dist-min@2.32.0 dist.integrity` (returns `sha512-...` base64) or compute `sha256sum assets/js/plotly-2.32.0.min.js` locally after download. Option (b) is stronger.

### Finding 2 — `link_check_project_registered_in_npm_test` grep target doesn't match real Jest output
**Severity:** minor
**Evidence:**
- Plan TDD line 247: "`npm test 2>&1` output contains the line `RUNS demo-links` or equivalent Jest project marker"
- Verified by running `npm test` in `aceengineer-website/`: actual output format is `PASS <displayName> <path>` (e.g., `PASS npv-calculator tests/js/npv-calculator.test.js`) or `FAIL <displayName> <path>` on failure. There is no `RUNS demo-links` line in Jest's default reporter.
- Plan line 194 (pseudocode) is more defensible: "`npm test 2>&1 | grep 'demo-links'`" — this would match both `PASS demo-links` and `FAIL demo-links`. But TDD pass-criterion (line 247) mentions `RUNS demo-links` specifically, which won't appear.
**Impact:** The test as specified will always fail because `grep RUNS demo-links` returns no lines, even when the project runs correctly. Either the test gets tweaked at implementation time (defect lives in spec only) or the operator misreads the output format and erroneously reports the wiring as broken.
**Recommendation:** Change TDD line 247 pass criterion to: "output contains `PASS demo-links` OR `FAIL demo-links`" — both prove the project was discovered and executed. Alternatively, keep the broader `grep demo-links` phrasing already used at pseudocode line 194.

### Finding 3 — `sitemap_uses_www_host` test doesn't handle pre-existing apex entries
**Severity:** minor
**Evidence:**
- Plan TDD line 245: "All 5 new entries use `https://www.aceengineer.com/` (not apex)" with pass criterion "5/5 match".
- Verified `sitemap.xml` has **>20 existing entries** on the apex host (`<loc>https://aceengineer.com/...</loc>`). Lines 5, 13, 21, 29, 37, 45, 53, 59, etc. — all use apex.
- Plan explicitly defers the apex→www fix for existing entries to a follow-up (line 156: "Existing 20+ apex entries remain as pre-existing debt").
- If `sitemap_uses_www_host` is implemented naively as "every `<loc>` in sitemap.xml starts with `https://www.`", it fails because of 20+ pre-existing apex entries. If it's implemented as "exactly 5 entries match `https://www.aceengineer.com/demos/*`", the test is scoped correctly — but the plan's 1-line description doesn't distinguish.
**Impact:** Implementer writes the test the naive way, it fails with 20+ reported mismatches, operator either (a) widens scope to fix all apex entries (scope creep into deferred work), or (b) narrows test to `demos/*` and re-runs — wasted iteration.
**Recommendation:** Specify the test scope precisely: "only `<loc>` entries containing `/demos/` must use `https://www.aceengineer.com/`" — not "all entries in sitemap.xml". This matches the Pseudocode D intent.

### Finding 4 — Pseudocode B head-include injection will not parse with `posthtml-include`
**Severity:** minor (potential build-time failure)
**Evidence:**
- Existing jumper file (read, line 6): `<head><meta charset="UTF-8"><title>A&CE — Subsea Jumper Installation Analysis Demo</title>` — all on one line, no newlines between elements.
- Pseudocode B (line 132): "insert `<include src="partials/head-common.html"></include>` as the first child of `<head>`"
- "First child of `<head>`" is ambiguous in a single-line `<head>` — the injection point could land before `<meta charset>` or after `<title>`. `posthtml-include` doesn't care about position, but cache-control headers and Google Analytics beacon ordering can differ if the nav/style CSS loads before `<meta viewport>`.
- Content at line 6 is a single-line `<head>`. Plan does not specify whether to reformat to multi-line or keep inline.
**Impact:** Low; `posthtml-include` is tolerant. But the Acceptance criterion at line 270 expects "page still renders static report identically" — if implementer reformats `<head>` for readability, the file diff balloons from 1 line to ~5 lines, complicating the Commit 1 "single file, one-line change" revert premise.
**Recommendation:** Pseudocode B should specify: "after the existing `<title>` element" (matches Pseudocode A ordering for Demos 1-4). Keep `<head>` single-line or reformat — explicit choice avoids inconsistent retrofit.

### Finding 5 — Commit 2's gallery edit creates anchor-to-head inconsistency window
**Severity:** minor
**Evidence:**
- Commit 1 modifies only `jumper-installation.html`. Gallery `index.html` line 383 already has `<a href="{{ rootPath }}demos/jumper-installation.html" class="btn btn-info">View detailed report</a>` — verified.
- Commit 2 adds 4 more "View detailed report" CTAs for Demos 1-4 (pseudocode C, Files to Change line 216).
- Between Commit 1 deploy and Commit 2 deploy, the gallery still has only **1** detail-CTA (Demo 5 → jumper). This is correct — not a defect.
- But: if Commit 2 is reverted (Rollback line 310 "demos 1-4 disappear from site but jumper retrofit remains live"), the gallery index.html *also* reverts — removing the 4 new CTAs. Correct.
- However, `sitemap.xml` in Commit 2 includes the jumper backfill entry (Pseudocode D line 153). Reverting Commit 2 removes the jumper sitemap entry too. So after a Commit 2 revert: jumper retrofit is live (good), jumper page serves GA (good), but jumper is **not** in sitemap.xml (regression from intended state).
**Impact:** Edge case. Post-revert, jumper page loses sitemap visibility that existed briefly. Not a deploy blocker; a cleanup follow-up commit can re-add the jumper sitemap entry.
**Recommendation:** Either (a) move the jumper sitemap backfill into Commit 1 (clean — jumper-only commit handles jumper sitemap too), or (b) document explicitly in Rollback Plan that a Commit 2 revert drops the jumper sitemap entry and requires a tiny follow-up commit to re-add it.
