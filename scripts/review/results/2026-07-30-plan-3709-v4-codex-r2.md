## Findings

### 1. MAJOR - v4 accepts a success-path mutation that clears `intent["blocking"]` after intent construction and before the pinned abort guard

**Evidence:** Predicate 9 only requires the success path to traverse the ordered chain through `intent = build_cutover_intent(...)` and then `if intent['blocking']:`; it does not require adjacency or forbid mutation of `intent` between those steps (`docs/plans/2026-07-30-issue-3709-managed-block-classification-v4.md:103`, `scripts/review/prototypes/3709-v4/preservation_prototype.py:323-348`). Predicate 10's assigned-name closure allows this because assigning through `intent['blocking']` still contributes only the allowed `intent` name (`preservation_prototype.py:115-129`, `:351-366`). Predicate 19 proves that the original `build_cutover_intent` comprehension contains the managed-location blocking condition, but it does not prove the value survives to the guard (`preservation_prototype.py:564-582`).

I built this new case by starting from admitted residue `r01_detail_classifier_constant` and inserting one statement after the intent assignment:

```python
def plan_cutover(current_text, classification_context, *, acknowledged=()):
    ...
    intent = build_cutover_intent(classified['records'], new_lines, acknowledged)
    intent['blocking'] = []
    if intent['blocking']:
        return _abort('planned crontab would omit live line(s)', [], intent)
    return {'new_text': new_text, 'preserved': [], 'uncataloged': [],
            'conflicts': [], 'intent': intent, 'abort_reason': None}
```

The committed behavioural harness reports it as destructive:

```text

```

This is not just accepted; it is accepted-and-destructive under the author's required bar. The shape also invalidates the residue table's RES-1 safety argument: `r01_detail_classifier_constant` is non-destructive only because the intent guard still sees the absent cataloged records. Clearing the success object before the guard removes that protection while preserving all 19 predicates.

**Concrete failure scenario:** commit 4 lands a source shape that classifies too broadly as cataloged, rebuilds only the managed block, computes a correct blocking report, then clears `intent["blocking"]` before the pinned guard. `python-postwrite-preservation-multiset-v1` passes, the checker certifies the destructive crontab transaction, and a cutover returns `abort_reason: None` while dropping live lines.

**Required revision:** add a named mutation/case for this exact accepted-and-destructive shape and strengthen D5 so every path from `intent = build_cutover_intent(...)` to the success return proves the same unmodified `intent["blocking"]` value is tested. Viable fixes include making the blocking guard immediately follow the intent assignment with no intervening statement, forbidding all subscript/attribute writes to `intent` on success paths, or returning a fresh success object only after a pinned no-mutation guard. Re-run `run.py` and `behaviour.py` with the new case.
