### Verdict: MAJOR

### Summary
Plan v2 is well-structured and addresses visible r1 gaps (acceptance-vs-scope reconciliation, exit-code Unix convention, side-cache/locking/YAML decisions). However, several design elements are under-specified in ways that will bite during implementation: the forward-emitter pseudocode does not actually branch on `action`, the cross-registry atomicity story conflicts with the tightened "BOTH surfaces" acceptance criterion, the side-cache has its own concurrency and git-tracking questions that are not answered, and a handful of edge cases (delete semantics, duplicate-key sources, batch+emitter concurrency) have no test coverage despite being easy to introduce.

### Issues Found
- [P1] Forward-emitter pseudocode does not use the `action` parameter. For `action="delete"` the page file is gone, so `parse_frontmatter(wiki_page_path)` will fail and `new_keys` cannot be computed; the spec needs delete to short-circuit to `new_keys = set()` (forcing all old_keys into `removed`). As written, delete paths will crash or silently no-op, contradicting `test_emit_removes_wiki_ref_on_page_deletion`.
- [P1] Cross-registry atomicity approach contradicts the v2-tightened acceptance criterion. The acceptance criterion now says BOTH L2 surfaces store `wiki_refs`, but the atomicity strategy openly accepts transient drift between surfaces with a stderr warning and manual reconciliation. This gap is not covered by any test — there is no `test_emit_rolls_back_surface_A_if_surface_B_fails` or equivalent, and no evidence showing reconciliation is actually idempotent.
- [P2] Side-cache (`wiki-refs-cache.jsonl`) is declared `git-tracked` but has no rationale for tracking a file that mutates on every emit. Git-tracked + frequent-mutation + parallel ingesters on different machines is a well-known merge-conflict pattern. If the cache is repopulable from scratch via `--reconcile`, it should probably be `.gitignore`d — otherwise the plan needs to explain the tracking decision.
- [P2] Side-cache has no lock of its own. `read_cached_keys_for_page` and `update_cached_keys_for_page` are described as a read-mutate-write cycle around the registries, but registry locks protect the registries, not the cache. Two concurrent emitters on different pages can both read stale cache state and race on the atomic-rename cache write. `test_portalocker_serializes_concurrent_writers` targets registry YAML only.
- [P2] Pseudocode uses `find_row(registry_path, doc_key)` and `registry_row_for_doc_key(registry, doc_key)` without specifying the indexing. If registries are large YAMLs and each emit walks them linearly, nightly batch will be O(pages × rows). The plan mentions the 19K-page marine-engineering domain but does not quantify the per-emit cost or propose an index.
- [P2] Acceptance criterion wording "BOTH L2 surfaces ... store `wiki_refs`" is ambiguous. Does each citing page path appear in both surfaces (implies every doc_key is duplicated across registries), or is it only the FIELD that must exist in both? The scope section calls them "two L2 surfaces — first wave" without saying whether they index the same doc_keys.
- [P2] `test_batch_mode_groups_locks` only verifies lock-acquire count for `--batch`. There is no test for batch running concurrently with a regular emitter invocation, nor for the `--reconcile` path's lock behavior. Open-question #3 (silently skip vs warn vs stub row for missing registry row) has no corresponding test either.
- [P3] Exit-code table conflates "reconcile found gaps" with "runtime error" (both return 1). Callers cannot distinguish a clean gap report from a crash. `grep` uses 0/1/2 for match/no-match/error; this tool could use 1 vs 2 differently (e.g., 1 = gaps, 3 = runtime error) or at least document the ambiguity.
- [P3] `emit_wiki_refs` is declared to be imported into `llm_wiki.py` and invoked from ingest/update/delete paths, but the plan does not identify the specific call-sites in the 1,465-line file. Without those line references, reviewers cannot verify the emitter actually fires on every relevant code path (especially delete).
- [P3] Plan states registry mutations ship as "a separate PR from the tooling PR so review surface is clean" but does not actually add an acceptance criterion or gating check enforcing that split. This is a convention, not a guarantee; easy to regress.
- [P3] Backfill report at `docs/reports/wiki-refs-backfill-<date>.md` will accumulate one file per run. No retention policy, no index, no cross-linking from the runbook.

### Suggestions
- Tighten the emitter pseudocode: explicitly branch on `action`, with `delete` setting `new_keys = set()` and skipping frontmatter parse. Add a targeted test `test_emit_delete_when_page_file_absent` that removes the page from disk before invoking the emitter.
- Resolve the atomicity-vs-acceptance tension: either (a) relax the criterion back to "at least one L2 surface, with reconciliation closing the loop" (matching the current design), or (b) commit to true cross-registry atomicity (e.g., stage both writes, fsync both, then rename both) and add a test that asserts no half-state is observable.
- Either gitignore `wiki-refs-cache.jsonl` and call it a derived artifact (repopulable via `--reconcile`), or document why git-tracking is desirable despite the merge-conflict surface area on parallel ingests.
- Add a cache-level lock (`wiki-refs-cache.jsonl.lock` via `portalocker`) covering the read-mutate-write cycle, and a concurrent-writers test analogous to `test_portalocker_serializes_concurrent_writers` but for the cache.
- Quantify lookup/emit cost against `registry.yaml` and `standards-transfer-ledger.yaml` size today (row count, file size). If linear walks are acceptable, state that; if not, propose a small in-memory index keyed by doc_key built on load.
- Rephrase acceptance criterion 4 as: "Both L2 surfaces define the `wiki_refs` field schema and are written to by the emitter when the cited doc_key exists as a row; a given page path appears only in the surface(s) whose row matches its doc_key."
- Add tests: (a) concurrent `--batch` + single emit, (b) the open-question #3 behavior (log-and-skip as proposed), (c) duplicate `sha256:` entries in a single page's `sources:` dedupe to a single ref.
- Reassign exit codes so runtime errors are distinguishable from expected-negative results: 0=success/no-hits-is-valid, 1=gaps-found-on-reconcile, 2=usage/format, 3=runtime error — or clearly document that CI gates must parse stderr to disambiguate.
- Cite the specific functions in `llm_wiki.py` (by name or approximate line) where `emit_wiki_refs()` will be invoked on add/update/delete so reviewers can confirm no code path is missed.
- Add a small "Backfill report retention" subsection: keep the latest N, link the newest from the runbook, or date-prefix and list under a dated index.

### Questions for Author
- Why do BOTH `registry.yaml` and `standards-transfer-ledger.yaml` need `wiki_refs` populated? Do they index overlapping `doc_key` sets, or are they disjoint views of different document populations? This answers whether the cross-registry atomicity story matters at all.
- Is `wiki-refs-cache.jsonl` intended to be git-tracked (as Files-to-Change says) or derived (as the corruption-recovery note suggests — 'delete the cache, run backfill')? These are incompatible.
- For the `action="delete"` case, is the emitter invoked BEFORE the file is removed from disk (so frontmatter is still parseable) or AFTER? The pseudocode implies 'after', but that requires short-circuiting the frontmatter read, which the pseudocode doesn't do.
- Open Question #3 (missing registry row) — you proposed (b) log-and-skip. Will that also record the orphan doc_key to the backfill report so operators can fix the registry later, or is it fire-and-forget to stderr?
- What is the ingest volume you expect the emitter to absorb per nightly run (pages × canonical-doc_keys per page)? If it's >100, the in-place YAML round-trip for two registries per emit may dominate; batching addresses it, but the plan's fallback path still iterates per-row.
- Does `find_row(registry_path, doc_key)` require the registry to be indexable by `doc_key` as a top-level key, or is it a scan over a list of entries? The registry schema is not excerpted in the plan.
- Will the reverse-lookup CLI acquire the same `portalocker` lock as the emitter, or read without a lock and rely on atomic-rename? If the former, concurrent lookups will serialize unnecessarily; if the latter, state that explicitly in the runbook.
