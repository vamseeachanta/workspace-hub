### Verdict: MAJOR

### Summary
The plan still contains blocking correctness defects: multiple live-state assertions are unverified, and the stdin-compatibility fallback design is internally contradictory across sections. The dominant problem class is trust in unverified repo/issue state plus inconsistent implementation requirements that would let the patch diverge from its stated deliverable.

### Issues Found
- [P1] Unverified dependency/resource claims: the plan treats live GitHub issue states and file existence as established facts in `Resource Intelligence Summary -> Evidence (embedded verification)` (`#2406` OPEN, `#2405` CLOSED, `#2403` OPEN, `#2402` OPEN; `EXISTS/MISSING` file claims), but this review packet provides no verifiable evidence beyond prose. Under the stated review standard, those are correctness-critical claims and remain unverified.
- [P1] Internal contradiction on unsupported Codex versions: `Pseudocode` says older CLIs must hard-fail with exit 7 and "No silent fallback to the old argv path," but `Files to Change` for `scripts/review/submit-to-codex.sh` still says "add one-time codex-version probe and argv-path fallback," which reintroduces the forbidden path.
- [P1] The same fallback contradiction persists in `Risks and Open Questions`: "Mitigation: runtime version probe + argv-path fallback (T30)." That directly conflicts with the v3 claim that argv fallback was removed and makes the intended behavior non-executable as written.
- [P1] Acceptance-criteria/test traceability is incomplete despite claiming full coverage. `Acceptance Criteria` includes manual checks for `docs/plans/README.md` row presence, `scripts/review/results/...` artifact count, and live repro completion, but `TDD Test List` and the traceability table do not provide automated coverage for those acceptance criteria. This fails the mandatory check that every acceptance criterion have a corresponding test or verified mechanism.
- [P1] Resource-intelligence source quality is overstated. `Resource Intelligence Summary` claims distinct sources "count ≥ 10," but several are memories/skills/handoff notes rather than direct evidence for the bug mechanism. The mandatory check requires concrete findings from distinct sources; the critical claims about issue state, file existence, and CLI contract are still only asserted, not independently substantiated in the plan artifact.
- [P2] `Files to Change` marks `docs/plans/README.md` as already done and "not counted in v3's to-do work," yet `Acceptance Criteria` still requires `docs/plans/README.md` to contain a `| 2406 |` row. That mixes prior-state validation with implementation scope and creates an execution dependency on a preexisting commit (`a73ec66f6`) that is not otherwise verified here.
- [P2] Operating-model compliance is asserted as N/A in `Operating-model compliance (explicit N/A rationale)` without proving that no wiki/domain artifacts are affected by the README/index and plan-file updates. The plan names the canonical operating-model file but does not verify the claimed non-applicability against actual ownership/flow rules; this is especially weak given the mandatory stance on `doc_key` / `sha256:` and §7 tier compliance.
- [P2] Threat-model coverage is incomplete. `Threat model` only discusses argv/stdin/temp-file privacy, but the plan also adds version probing via `"$CODEX_BIN" exec --help` and extensive PATH-based mocking. There is no analysis of malicious `CODEX_BIN`, help-output spoofing, or shell-escaping risk around probe/log handling even though the user explicitly required security review for paths/mounts/secrets/external APIs.
- [P2] The test strategy around `PIPESTATUS[1]` is underspecified. `Pseudocode` says the final implementation detail "lives in code," but the exact function contract is left unresolved while `T29` depends on that behavior. For a correctness-critical shell fix under `set -euo pipefail`, leaving the exit-propagation mechanics informal is avoidable risk.

### Suggestions
- Replace every live-state assertion in `Evidence (embedded verification)` with either a reproducible artifact embedded in the plan package or downgrade the statement to "unverified" and remove it from dependency reasoning.
- Resolve the unsupported-version behavior in one place and propagate it everywhere: either hard-fail with exit 7 or use fallback, but do not describe both. Update `Files to Change`, `Risks`, `T30`, and the exit-code map to the same rule.
- Tighten acceptance criteria so each item has a matching executable check. If README/artifact-count/live-repro remain manual, label them as manual release checks rather than test-backed ACs, and do not claim complete AC↔test coverage.
- Separate already-landed state from planned work. Move the `docs/plans/README.md` row verification to a precondition section or remove it from this issue's acceptance criteria unless this issue actually changes that file.
- Expand the security section to cover the version-probe path, PATH/CODEX_BIN trust assumptions, and how mocks/probe output are prevented from altering control flow unexpectedly.
- Specify the exact shell structure for `run_codex_exec` exit propagation, including how `${PIPESTATUS[1]}` is captured and returned under `set -euo pipefail`, so T29 is testing a concrete design rather than an informal note.
