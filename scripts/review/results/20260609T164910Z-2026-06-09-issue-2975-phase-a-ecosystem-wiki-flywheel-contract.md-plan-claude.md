### Verdict: MAJOR

### Summary
A well-structured Phase A contract-surface plan with strong TDD coverage and explicit scope-blocking into Phase B (#3013). The one genuine technical gap is that the highest-risk change — broadening the public-egress guard from `const public_llm_wiki` to an enum across two JSON Schemas — is specified by intent but not by an exhaustive, per-occurrence enumeration, which is what makes a fail-open public-egress boundary safe. Plan is self-marked FAIL-through-r4 awaiting r5; close, but needs the schema edit tightened.

### Issues Found
- [P2] Schema guard exhaustiveness is under-specified. The plan broadens `output_residency const public_llm_wiki` -> `enum [public_llm_wiki, public_federal_wiki]` across conditional predicates in BOTH execution-manifest.schema.yaml and report-evidence-bundle.schema.yaml (top-level + nested outputs[] + source/source-mix constraints). The pseudocode describes intent but does not require enumerating EVERY `public_llm_wiki` occurrence and assigning each an explicit broaden/leave-unchanged disposition. A single missed predicate yields a silent fail-open public-egress hole; an over-broadened one weakens the existing `public_llm_wiki` guard. For a public-egress security boundary this needs a deterministic enumeration step (e.g., grep all occurrences, table each with disposition) plus a test asserting the count of guarded predicates.
- [P2] Negative-fixture coverage proves rejection but the positive full-gate acceptance path for `public_federal_wiki` is thin. `test_public_federal_wiki_is_public_guarded_residency` proves incomplete gates/private-source inputs FAIL, and `test_public_federal_wiki_in_*_schema` proves the enum is accepted, but no test explicitly proves a FULLY-gated `public_federal_wiki` output (all promotion gates, legal scan, audience, sanitization present) is ACCEPTED. Without it, a guard that rejects all `public_federal_wiki` regardless of gates would still pass the suite — masking a guard that is too strict to ever be usable by Phase B.
- [P3] Evidence section asserts issue states (#2975 OPEN, #3013 OPEN) and file existence/missing-state as verified locally, but no `## Attested Evidence` block is present in this review payload. The plan itself defers verification to a label-time attestation run (`scripts/review/attest-plan-claims.sh`), so these are pending-attestation claims, not yet independently verified at review time.
- [P3] Review-numbering provenance is confusing: line 9/15/270 reference `r1-r8` (prior omnibus draft) while the Adversarial Review Summary table only covers Phase A r1-r4. A reader could mistake the omnibus r1-r8 history as applying to this narrowed plan. The plan states they are historical/non-approving, but the dual numbering invites confusion.
- [P3] Gemini returned NO_OUTPUT in all four Phase A rounds. T2 is satisfied by Claude+Codex, and the plan documents the outage, but four consecutive NO_OUTPUT rounds warrant an explicit UNAVAILABLE note per scripts/review/results convention rather than inline table cells, to avoid reading as a skipped gate.

### Suggestions
- Add an explicit enumeration step to the schema-edit task: grep both schemas for every `public_llm_wiki` literal, render a disposition table (broaden-to-enum vs leave-as-const-with-rationale), and add a regression test asserting the number of public-output guard predicates that include `public_federal_wiki` equals the enumerated count. This converts a narrative edit into an auditable, fail-closed one.
- Add a positive-path acceptance test: a fully-gated `public_federal_wiki` execution manifest and report-evidence bundle (all promotion gates, legal scan, audience classification, sanitization, review verdict present) MUST validate successfully — proving the guard is usable, not merely strict.
- Consolidate review-history provenance: in the Adversarial Review Summary, add a one-line note distinguishing the omnibus r1-r8 (different artifact, blocked) from Phase A r1-r4 (this plan), so the numbering is unambiguous.
- Document Gemini's persistent NO_OUTPUT as a single explicit UNAVAILABLE degradation note (T3->T2) rather than four separate table rows, matching the existing results convention.
- Confirm the auto-derived completeness class expectation: because this plan ships a Python sync script (scripts/knowledge/sync-...py) plus test files, the changed-files->package mapping will likely auto-derive `code` (threshold 90). Worth stating the expected class so the closeout does not surprise on threshold.
