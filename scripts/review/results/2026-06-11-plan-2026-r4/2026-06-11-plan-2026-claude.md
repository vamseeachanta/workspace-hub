## Findings

1. **MAJOR — D2 x D7 interaction permits a false `mailbox_empty: true` when account config is absent.** D2: "If the local config is absent, the default scope enables aliases `ace` and `personal` only; literal email normalization is unavailable." D7: "Out-of-scope records are counted separately and never make `mailbox_empty` false." Pseudocode: `mailbox_empty = tracked_empty and unknown_count == 0`, where `unknown_count` counts only *enabled in-scope normalized* threads. A realistic #2024 snapshot carries literal email addresses (D7 schema: "canonical alias, or email that maps to one"). With no config, every literal-email record fails normalization, lands in `out_of_scope_count`, `unknown_count` stays 0, and the report answers `mailbox_empty: true` while real in-scope inbox threads are untracked. This inverts the user's core requirement from the 2026-06-11 issue comment. No TDD entry covers "literal-email snapshot + absent config" (`test_pending_work_report_normalizes_literal_email_snapshot` uses a temp config; `test_account_config_defaults_to_aliases_only` supplies no snapshot). Fix: unmappable-due-to-missing-email-mapping records must fail closed — e.g., `unknown_status: "config_missing"` and `mailbox_empty` forced to non-true — and a test must pin it.

2. **MAJOR — `transition()` never validates `from_state` against the current snapshot state.** Pseudocode `prepare_event` validates only that the edge is table-allowed. A table-valid event with a stale `from_state` (e.g., a delayed retry of `inbound -> extracted` arriving after the thread reached `completed`) passes validation, is NOT caught by dedup (different from/to than the latest event, and per finding 3 the dedup substrate is unspecified), appends, and — under last-event-wins snapshot materialization (D3) — silently regresses the thread to `extracted`. The entire D5 cycle/dedup apparatus exists because retried/out-of-order events are expected, yet stale-from_state ordering is unaddressed by any design decision, pseudocode line, or TDD entry. The plan must state the policy (reject stale from_state vs. accept event-sourced semantics) and test it.

3. **MINOR — dedup-check substrate unspecified.** `_append_events_locked`: "if event.dedup_key already exists: skip" — exists *where*? The snapshot holds one latest record per `{account_id}::{thread_id}`, so historical dedup keys are not in it: a delayed duplicate of an earlier same-cycle transition (dup of `inbound -> extracted` after `extracted -> awaiting-reply`) would not match the snapshot's latest record. Correct dedup requires a full-log scan or a maintained dedup index; the plan specifies neither, and the choice has lock-hold-time implications that D9 batching cares about.

4. **MINOR — no-trigger reactivation retries are not idempotent, breaking the asymmetry silently.** D5: no-trigger reactivations get `cycle_id = "reactivation-ts:" + ts_utc`. A *retried* no-trigger reactivation under a fresh timestamp creates a new cycle and a duplicate row — the existing contract guarantee (`test_transition_retry_preserves_dedup_under_fresh_ts`: retry idempotency under fresh ts) intentionally does not extend to this path, but the plan never says so. Document the asymmetry or key the fallback cycle on something retry-stable.

The underlying facts verify (workflow doc lines 96, 236, 364, 487-490), but the formatting blurs verified-quote vs. summary — the same evidence-hygiene defect class the plan's own r2 summary criticizes Gemini for.
