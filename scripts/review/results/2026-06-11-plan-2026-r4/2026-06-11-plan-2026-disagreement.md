### claude

- **MAJOR — D2 x D7 interaction permits a false `mailbox_empty: true` when account config is absent.** D2: "If the local config is absent, the default scope enables aliases `ace` and `personal` only; literal email normalization is unavailable." D7: "Out-of-scope records are counted separately and never make `mailbox_empty` false." Pseudocode: `mailbox_empty = tracked_empty and unknown_count == 0`, where `unknown_count` counts only *enabled in-scope normalized* threads. A realistic #2024 snapshot carries literal email addresses (D7 schema: "canonical alias, or email that maps to one"). With no config, every literal-email record fails normalization, lands in `out_of_scope_count`, `unknown_count` stays 0, and the report answers `mailbox_empty: true` while real in-scope inbox threads are untracked. This inverts the user's core requirement from the 2026-06-11 issue comment. No TDD entry covers "literal-email snapshot + absent config" (`test_pending_work_report_normalizes_literal_email_snapshot` uses a temp config; `test_account_config_defaults_to_aliases_only` supplies no snapshot). Fix: unmappable-due-to-missing-email-mapping records must fail closed — e.g., `unknown_status: "config_missing"` and `mailbox_empty` forced to non-true — and a test must pin it.
- **MAJOR — `transition()` never validates `from_state` against the current snapshot state.** Pseudocode `prepare_event` validates only that the edge is table-allowed. A table-valid event with a stale `from_state` (e.g., a delayed retry of `inbound -> extracted` arriving after the thread reached `completed`) passes validation, is NOT caught by dedup (different from/to than the latest event, and per finding 3 the dedup substrate is unspecified), appends, and — under last-event-wins snapshot materialization (D3) — silently regresses the thread to `extracted`. The entire D5 cycle/dedup apparatus exists because retried/out-of-order events are expected, yet stale-from_state ordering is unaddressed by any design decision, pseudocode line, or TDD entry. The plan must state the policy (reject stale from_state vs. accept event-sourced semantics) and test it.
- **MINOR — dedup-check substrate unspecified.** `_append_events_locked`: "if event.dedup_key already exists: skip" — exists *where*? The snapshot holds one latest record per `{account_id}::{thread_id}`, so historical dedup keys are not in it: a delayed duplicate of an earlier same-cycle transition (dup of `inbound -> extracted` after `extracted -> awaiting-reply`) would not match the snapshot's latest record. Correct dedup requires a full-log scan or a maintained dedup index; the plan specifies neither, and the choice has lock-hold-time implications that D9 batching cares about.
- **MINOR — no-trigger reactivation retries are not idempotent, breaking the asymmetry silently.** D5: no-trigger reactivations get `cycle_id = "reactivation-ts:" + ts_utc`. A *retried* no-trigger reactivation under a fresh timestamp creates a new cycle and a duplicate row — the existing contract guarantee (`test_transition_retry_preserves_dedup_under_fresh_ts`: retry idempotency under fresh ts) intentionally does not extend to this path, but the plan never says so. Document the asymmetry or key the fallback cycle on something retry-stable.
- **MINOR — evidence block presents paraphrase as excerpt.** Plan "Line excerpts" section, the `docs/design/email-as-queue-workflow.md` block ("Older workflow text still references...") is reviewer prose inside a code fence formatted identically to the genuine quoted excerpts above it. The underlying facts verify (workflow doc lines 96, 236, 364, 487-490), but the formatting blurs verified-quote vs. summary — the same evidence-hygiene defect class the plan's own r2 summary criticizes Gemini for.
- **MINOR — round bookkeeping is already stale.** Plan line 9 says "this r3-patched draft requires a fresh r4 review" and lists artifacts only through r3, but `scripts/review/results/2026-06-11-plan-2026-r4/` already exists containing a Codex MAJOR verdict and empty claude/gemini placeholders. ### gemini

- **MAJOR: No-trigger reactivation bypasses dedup idempotency.** Plan §Pseudocode `prepare_event` specifies `event.cycle_id = "reactivation-ts:" + event.ts_utc` for reactivations lacking a message ID. Because a retry inherently provides a fresh `ts_utc` from the caller, retrying a no-trigger `reactivate_reply` will generate a novel `cycle_id` each time. This forces a different `dedup_key`, causing duplicate `inbound` transitions to append. This contradicts the §D5 guarantee that "existing retry tests without a message id still dedup across fresh timestamps."
- **MAJOR: `sweep_grace` race condition with dynamic state.** Plan §Pseudocode `sweep_grace` reads the snapshot unlocked ("find completed snapshot records..."), yields, and then submits batches to `_append_events_locked`. If a thread is concurrently reactivated (transitioning to `inbound` or `extracted`) after the snapshot is read but before its batch is processed, the sweep will blindly attempt to append a `completed -> purged` transition. This will either silently corrupt the thread's state or trigger an unhandled validation crash that aborts the sweep mid-execution.
- **MAJOR: Dynamic state validation omitted in `prepare_event`.** Plan §Pseudocode `prepare_event` specifies "validate event.from_state -> event.to_state transition is allowed." This describes a static graph edge check. It critically omits verifying that the thread's CURRENT state under the lock (`snapshot_before.get(event.key).state`) actually matches `event.from_state`. Without this dynamic check, the state machine cannot reject invalid transitions submitted by callers operating on stale views.
- **MAJOR: `noise` routing threads force false-positive pending work.** Plan §D4 establishes that "noise remains a routing/labeling class, not a queue-state enum," meaning noise threads are intentionally excluded from local state. However, §D3 defines unknown threads as "present in the supplied in-scope inbox snapshot but absent from local state." When `pending_work_report` evaluates an inbox snapshot containing safely routed noise threads, it will see they are absent from local state, count them into `unknown_count`, and permanently prevent `mailbox_empty` from returning `True`. The logic must explicitly exclude threads labeled `wh-email/noise` from the unknown count.
- **MAJOR: Default account config nullifies unknown-thread evaluation.** Plan §D2 states that absent a config file, the default "email mapping is empty." Plan §D7 mandates that unknown-thread detection "only considers enabled aliases." If `pending_work_report` evaluates an inbox snapshot containing literal Gmail addresses without a pre-existing `accounts.yaml`, the empty mapping will fail to normalize them. It will drop all untracked literal emails into `out_of_scope_count` rather than `unknown_count`, resulting in a false `mailbox_empty = True` even if the inbox is full of genuine pending work.
