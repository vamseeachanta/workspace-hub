## Findings
1. Plan claims issue task 1, “Create Gmail labels via API,” is in scope, but does not specify any real Gmail credential/client integration path. The issue body task list requires “Create Gmail labels via API”; plan D4 only says `ensure_labels(..., apply=True)` should work “when a Gmail client/credential surface is available” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md` lines 281-300), and the only label-apply test uses a fake Gmail client (`test_ensure_labels_creates_missing_labels_with_apply_flag`, lines 643-645). Existing scripts expose Gmail search/get/delete/trash helpers but no label-create/modify helper (`scripts/email/gmail-archive-extract.py` lines 102-139; `scripts/email/batch-unsubscribe.sh` lines 114-122, 217). This can pass tests while never satisfying the issue’s API setup task.

2. Plan defers cron wiring for the grace checker even though the issue explicitly includes it. Issue #2026 task 4 is “Grace period checker (runs in daily cron)”; plan D10 says the checker command is in scope but “actual scheduled-task/cron wiring is deferred to #2024” (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md` lines 381-389). The current dependency table only says “Pipeline orchestration and scheduled sweep wiring” belongs to #2024 (`docs/design/email-as-queue.md` lines 70-77), but the plan does not update #2026 acceptance or issue disposition to make the scope reduction explicit. This leaves the issue task incomplete while allowing the plan to close without daily execution.

3. Reactivation detection cannot reliably determine “newer messages” from the planned state model. D10 and acceptance require a snapshot-driven checker to identify completed/awaiting/purged threads with newer messages (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md` lines 387, 675), and D7 defines an inbox snapshot with `latest_message_id`/`received_at_utc` (`lines 340-353`). But the schema update scope only adds `cycle_id`, `triggering_message_id`, `dedup_event_id`, `needs_user_decision`, and warning metadata (`lines 596, 670`), and the existing snapshot schema has no `latest_message_id`, `last_seen_message_id`, or `received_at_utc` field (`docs/design/email-queue-state-schema.yaml` lines 95-123). Without storing the prior message baseline, “newer” is underdefined and can produce false reactivations or missed replies.

4. The locking pseudocode contradicts the path-first/nonstandard-log contract. D6 requires arbitrary log paths to derive non-colliding sibling files (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md` lines 330-338), but `_append_events_locked()` says it acquires `fcntl LOCK_EX on queue-state.jsonl` (`line 454`). For `custom.jsonl`, that wording either locks the wrong file or leaves the lock target ambiguous, undermining the non-collision guarantee tested by `test_nonstandard_log_path_derives_noncolliding_siblings` (`lines 616-617`).

5. The plan defines last-event-wins clearing for pending metadata but has no test that clears pending flags. D3 says absent boolean metadata on a later state event clears prior `needs_user_decision` and `needs_schema` (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md` line 277). The TDD list only tests that `needs_user_decision: true` and `needs_schema: true` make reports non-empty (`lines 641-642`); it does not test that a later event without those flags clears the pending condition. That is a mailbox-empty correctness gap.

6. The plan’s review-artifact state is stale against the live repo. The plan header says this “r3-patched draft requires a fresh r4 review” and the Artifact Map lists failed rounds only through r3 (`docs/plans/2026-06-11-issue-2026-email-state-tracking.md` lines 9, 216), while `scripts/review/results/2026-06-11-plan-2026-r4/` already exists with Claude/Codex/Gemini artifacts and `.err` files. Before status movement, the plan must reconcile whether this review is the r4 source of truth or whether the live r4 artifacts are stale/failed.
