## Findings
1. **MAJOR: No-trigger reactivation bypasses dedup idempotency.** Plan §Pseudocode `prepare_event` specifies `event.cycle_id = "reactivation-ts:" + event.ts_utc` for reactivations lacking a message ID. Because a retry inherently provides a fresh `ts_utc` from the caller, retrying a no-trigger `reactivate_reply` will generate a novel `cycle_id` each time. This forces a different `dedup_key`, causing duplicate `inbound` transitions to append. This contradicts the §D5 guarantee that "existing retry tests without a message id still dedup across fresh timestamps."

2. **MAJOR: `sweep_grace` race condition with dynamic state.** Plan §Pseudocode `sweep_grace` reads the snapshot unlocked ("find completed snapshot records..."), yields, and then submits batches to `_append_events_locked`. If a thread is concurrently reactivated (transitioning to `inbound` or `extracted`) after the snapshot is read but before its batch is processed, the sweep will blindly attempt to append a `completed -> purged` transition. This will either silently corrupt the thread's state or trigger an unhandled validation crash that aborts the sweep mid-execution.

3. **MAJOR: Dynamic state validation omitted in `prepare_event`.** Plan §Pseudocode `prepare_event` specifies "validate event.from_state -> event.to_state transition is allowed." This describes a static graph edge check. It critically omits verifying that the thread's CURRENT state under the lock (`snapshot_before.get(event.key).state`) actually matches `event.from_state`. Without this dynamic check, the state machine cannot reject invalid transitions submitted by callers operating on stale views.

4. **MAJOR: `noise` routing threads force false-positive pending work.** Plan §D4 establishes that "noise remains a routing/labeling class, not a queue-state enum," meaning noise threads are intentionally excluded from local state. However, §D3 defines unknown threads as "present in the supplied in-scope inbox snapshot but absent from local state." When `pending_work_report` evaluates an inbox snapshot containing safely routed noise threads, it will see they are absent from local state, count them into `unknown_count`, and permanently prevent `mailbox_empty` from returning `True`. The logic must explicitly exclude threads labeled `wh-email/noise` from the unknown count.

5. **MAJOR: Default account config nullifies unknown-thread evaluation.** Plan §D2 states that absent a config file, the default "email mapping is empty." Plan §D7 mandates that unknown-thread detection "only considers enabled aliases." If `pending_work_report` evaluates an inbox snapshot containing literal Gmail addresses without a pre-existing `accounts.yaml`, the empty mapping will fail to normalize them. It will drop all untracked literal emails into `out_of_scope_count` rather than `unknown_count`, resulting in a false `mailbox_empty = True` even if the inbox is full of genuine pending work.

## Blockers
- Finding 1: No-trigger reactivation bypasses dedup idempotency.
- Finding 2: `sweep_grace` race condition with dynamic state.
- Finding 3: Dynamic state validation omitted in `prepare_event`.
- Finding 4: `noise` routing threads force false-positive pending work.
- Finding 5: Default account config nullifies unknown-thread evaluation.
