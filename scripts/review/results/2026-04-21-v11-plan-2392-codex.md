### Verdict: MAJOR

### Summary
The draft still leaves correctness-critical behavior undefined or internally unsafe. It is not approval-ready because the scheduler contract is not single-run across the declared machines, domain resolution is not specified tightly enough to verify correctness, the dedupe contract can suppress real gaps, the publication command can dirty the checkout outside the staged report set, and a required input prerequisite used by the approval gate is not affirmatively verified by the attested evidence.

### Issues Found
- `Scheduled Task Contract` is not actually single-run across the declared fleet. The plan says `machines: [dev-primary, ace-linux-1]`, `prefer: dev-primary`, and `single-run lock: shell-level only via flock -n $WORKSPACE_HUB/.locks/wiki-coverage-gap-detection.lock`. That lock path is checkout-local, so it prevents only same-machine concurrency. It does not prevent both machines from running and publishing independently, which makes the claimed single-run publication behavior incorrect and risks duplicate commits/push races.
- `Scheduled Task Contract` and `Mapping expectations` rely on config fields that are named but not normatively specified. The plan cites `source_root_domain_map`, `design_code_domain_defaults`, and `wiki_domain_rules`, then claims the detector will derive authoritative `domain` / `domain_slug` and classify `covered` vs `domain-mismatch`. There is no concrete schema for overlapping path prefixes, normalization rules, tie-breaking, or invalid-config handling. Without that, domain assignment correctness cannot be affirmatively verified.
- `Candidate Record Shape` introduces a lossy contradiction between deduplication and coverage semantics. It says `one canonical doc_key yields at most one normalized source candidate in coverage accounting`, but `Cross-domain coverage policy` says coverage is `doc_key + domain`, not `doc_key` alone. If the same canonical source legitimately maps to more than one wiki domain, the current rule collapses that into one record or forces `domain-unresolved`, which suppresses real per-domain gaps instead of reporting them. The plan never proves the necessary invariant that one canonical source can belong to only one output domain.
- `Scheduled Task Contract` can violate its own clean-worktree publication rule. The command writes `>> "$WORKSPACE_HUB"/logs/knowledge/wiki-coverage-gap-$(date ...).log` before the commit logic, but the precondition check is only `test -z "$(git status --porcelain)"` before execution, and the commit stages only `docs/reports/wiki-coverage-gaps`. If `logs/knowledge/**` is tracked or not ignored on any target checkout, the task leaves the repo dirty while still claiming `publishes ... from a clean target checkout only`. The plan does not constrain or verify log-path ignore status.
- The approval gate depends on a required input that is not affirmatively verified by the attestation. `Authoritative source inputs` and `Manual verification before approval` both require `data/document-index/index.jsonl`, but the `## Attested Evidence` block does not verify that path exists. Because your review contract requires affirmative verification before APPROVE, this draft is not approval-ready on its own evidence set.

### Suggestions
- Replace the local `flock` claim with a real single-publisher contract: one machine only, or a shared lock / leader-election mechanism, or explicitly mark secondary machines as non-publishing observers.
- Specify the exact config schema and precedence rules for domain mapping: key format, prefix matching order, normalization algorithm, duplicate-rule handling, and fail-closed behavior for ambiguous mappings.
- Either prove and state the invariant `one canonical source belongs to exactly one domain`, or change normalization so one `doc_key` can emit multiple domain-scoped candidates when the source truth says so.
- Make log handling non-mutating to the repo state used for publication: write outside the checkout, or require/verify that the log path is gitignored, or restage/clean it explicitly under a safe contract.
- Add attested evidence for `data/document-index/index.jsonl` on the approval target, since the current evidence set is insufficient for the stated manual gate.

### Questions for Author
- Is the detector intended to have exactly one publishing host, or do you actually expect both `dev-primary` and `ace-linux-1` to run the schedule?
- What is the authoritative rule when a single canonical document legitimately belongs to multiple wiki domains: duplicate rows, a primary domain, or a hard error?
- What is the exact matching/precedence schema for `source_root_domain_map` and `wiki_domain_rules` when multiple rules match the same record or page?
