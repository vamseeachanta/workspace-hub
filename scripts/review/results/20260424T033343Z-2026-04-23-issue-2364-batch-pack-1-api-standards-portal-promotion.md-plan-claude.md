### Verdict: MAJOR

### Summary
The plan is well-structured, grounded in concrete evidence, and correctly scopes the deliverable as a stub-generation report rather than direct wiki promotion. However, the unresolved forbidden-path tension (runner under `scripts/**` and tests under `tests/**`) and the undecided registry-write strategy are material to execution and should be pinned down before approval, not deferred into plan review.

### Issues Found
- [P1] Forbidden-path conflict is unresolved: Batch Pack spec §3.1 lists both `scripts/**` AND `tests/**` as forbidden, yet Files-to-Change creates `scripts/knowledge/run-batch-pack-1.py` and `tests/knowledge/test_batch_pack_1.py`. The plan acknowledges `scripts/**` but silently adds a `tests/**` write without addressing the same prohibition. Either both exceptions need user sign-off before implementation or the artifacts must move.
- [P1] The rationalization that 'forbidden-path rule governs runtime-execution write scope, not whether a committed helper tool may exist' is the planner's interpretation, not a quote from the spec. Without explicit language in `docs/reports/llm-wiki-staged-batch-packs.md` supporting this carve-out, the plan is at risk of re-litigating scope during execution. Cite the spec clause that permits committed helpers or treat the forbidden-paths clause as binding.
- [P2] Domain classifier is specified at pseudocode level but `MARINE_TAGS`, `NAVAL_ARCH_TAGS`, `NAVAL_HOSTS`, `MARINE_TERMS` lists are never enumerated. Two of the ten TDD tests depend on these sets, so the tests cannot be written until the sets are defined — this defers a design decision into TDD instead of locking it in the plan.
- [P2] The 120-char + capability-indicator threshold is introduced as the minimum-evidence rule, but the plan does not show how many of the actual 40 entries would land in the insufficient bucket under that rule. Without a dry-run count, the plan cannot demonstrate that the threshold produces a reasonable split (e.g., risk of sending 35/40 to follow-on catalog, making the deliverable largely empty).
- [P2] Acceptance criterion 'Each generated stub has target_wiki_domain ∈ {engineering, marine-engineering, naval-architecture}' conflicts with the possibility that some `standard_portal` entries may legitimately belong to `maritime-law` (the plan explicitly notes maritime-law is out of scope). There is no acceptance check that a standards-portal entry about, e.g., IMO conventions isn't force-misclassified into `engineering` as the default fallback.
- [P3] 'Additive-only registry write' risk mitigation relies on `ruamel.yaml`, but this dependency isn't listed anywhere (pyproject, requirements) and the plan doesn't confirm it's available in the `uv run` environment.
- [P3] The duplicate-check strategy (build `source-id → page` map across 19,191 marine-engineering pages) has no cost estimate. If frontmatter parsing is slow, this could dominate run time; mitigation is asserted without benchmark.
- [P3] Test `test_duplicate_check_detects_existing_wiki_page` references fixture entry id `noaa-ndbc` but the plan does not confirm that id actually exists in the committed registry. If it does not, the fixture is fabricated and the test verifies nothing about live data.
- [P3] The Adversarial Review Summary table is PENDING and the plan is labeled draft v1 with 'no revisions yet' — per the user's workspace rules, `status:plan-approved` is gated on completed adversarial review, so the plan cannot advance until those slots are filled.

### Suggestions
- Resolve the forbidden-path question before plan approval by either (a) quoting the spec clause that exempts committed helpers, (b) landing the runner as an inline Python block in `docs/reports/batch-pack-1-api-portal-metadata-stubs.md` with the report generated by a one-shot inline runner, or (c) requesting an explicit spec amendment in `docs/reports/llm-wiki-staged-batch-packs.md` via a separate micro-issue.
- Enumerate the full keyword lists (`MARINE_TAGS`, `NAVAL_ARCH_TAGS`, `NAVAL_HOSTS`, `MARINE_TERMS`) in the plan or pin them to an explicit sidecar config file before tests are written — otherwise TDD is writing tests against a moving target.
- Run a dry-pass count against the live registry (no writes, just the partition) and embed the expected sufficient/insufficient split in Evidence so reviewers can sanity-check the threshold before implementation.
- Add `maritime-law` as a fourth allowed `target_wiki_domain` OR add an explicit 'unclassifiable → follow-on' escape hatch in the classifier so standards-portal entries that don't fit the three target wikis aren't silently forced into `engineering`.
- Prefer the sidecar `online-resource-registry.processed.yaml` option from the Open Questions — it eliminates the additive-write risk entirely and is reversible without a registry diff. Recommend defaulting to sidecar and promoting to inline only if a downstream consumer requires it.
- Verify `ruamel.yaml` availability in the project's uv environment and add it to dependencies explicitly if missing; or document the fallback (e.g., pure-text patching of just the two new keys) if the dependency is undesirable.
- Replace the `noaa-ndbc` fixture reference with an id verified to exist in `online-resource-registry.yaml` (or make the duplicate-check test use a synthesized-in-memory fixture with no live-data dependency).
- Add one acceptance criterion: 'A Classifier Trace section lists the rule that matched for every one of the 40 entries, with zero entries in an Unclassified bucket, OR the plan explicitly accepts an Unclassified bucket and the bucket is accounted for in the 40-total invariant.'
