### Issues Found

- **[minor] Dependency on sibling #2458 for `benchmarks/__init__.py` is sound but the "idempotent co-create" resolution could be tighter.** The plan says whichever of #2457/#2458 lands first creates `__init__.py`, and the other is a no-op. This is correct if and only if BOTH plans emit a byte-identical empty file. #2458's plan specifies an empty package init; this plan specifies the same. But a git-level race is still possible if both land in the same commit window — one commit's `git add benchmarks/__init__.py` could collide with the other's staging. Mitigation: the plan's Risks section already addresses this; suggest adding a specific "if this file already exists, do not overwrite" guard in the implementation commit so that ordering is truly irrelevant at the filesystem level too.
- **[minor] The `test_preserves_load_rao_method_both` test relies on enum-to-enum equality, but `LoadRAOMethod` is imported implicitly by the DiffractionSpec machinery — not directly by the test.** The plan shows the test as `assert parsed.solver_options.load_rao_method == orig.solver_options.load_rao_method`. This is fine IF both sides deserialize to the same enum. If the reverse parser stores it as a string `"both"` rather than the enum member, the comparison may coerce or raise TypeError, depending on how `LoadRAOMethod` is declared. Suggest the test also assert `isinstance(parsed.solver_options.load_rao_method, LoadRAOMethod)` AND `parsed.solver_options.load_rao_method.value == "both"` to pin the type and value separately. Belt-and-braces; not a correctness blocker.
- **[minor] Claim-boundary language citation is right but could double-down.** The plan asserts the manifest's `claim_boundary` field contains "near-equivalent for key engineering inputs" AND "not guaranteed 100% semantically equivalent" — both substring-tested. Good. But the README's full sentence includes additional context ("…and tested round-trip pathways"). The manifest-language test should also include "tested round-trip pathways" in its substring check, because the plan's own Risks section warns against "claim-boundary paraphrase drift". Tightening the assertion closes the drift gap fully.
- **[minor] The `bridge_candidates` manifest field declares a future OrcaWave → OrcaFlex handoff validation but does not bound the scope.** The plan's string reads "future OrcaWave -> OrcaFlex handoff validation (extends delivered #1592/#1768 handoff primitives with a QTF-enabled ship case)". Reader could interpret this as "already tested against #1592/#1768" rather than "extends them in a future issue". Suggest rephrasing to "**pending**: extends delivered #1592/#1768 handoff primitives to a QTF-enabled ship case in a future issue (not validated under #2457)" to preserve the temporal boundary. Same clarification was applied to #2458 in r2; apply consistently here.
