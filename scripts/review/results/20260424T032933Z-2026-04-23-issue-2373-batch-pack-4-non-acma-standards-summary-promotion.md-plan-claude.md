### Verdict: MAJOR

### Summary
Thorough, well-scoped T2 plan with clear exclusions, TDD gates, and provenance contract. Blocking gaps: (1) topic-clustering is described as "editorial" but produces deterministic per-domain structure with no specified rule source, threatening reproducibility; (2) the post-filter row count is left as "≤145" with no concrete target, so the pre-run gate and acceptance criterion can't fail cleanly; (3) the design-code-registry exclusion depends on `data/design-codes/code-registry.yaml` whose existence is never verified in the evidence block.

### Issues Found
- [P1] Topic-clustering rule is undefined and marked 'editorial' (risk section), but drives the per-domain report structure for 145 entries across cathodic-protection/pipeline/structural. Without a locked clustering table (e.g., in a fixture YAML or inline in this plan) the output is not reproducible and cross-provider review cannot reason about correctness.
- [P1] Pre-run count gate in pseudocode Step 2 says 'len(slice_entries) must equal 145 minus the excluded/CSA/OCIMF rows' — but that subtraction is never computed. Acceptance criterion mirrors this with '≤145'. A gate with an unbounded range cannot detect under-inclusion (e.g., filter bug drops rows silently).
- [P2] Exclusion of design-code-registry entries depends on `data/design-codes/code-registry.yaml`, but that file's existence is NOT in the evidence block (only standards-transfer-ledger.yaml, maturity YAML, shards, wiki dirs, and staged-batch-packs design doc are listed). If the registry file is missing or empty, `load_design_code_registry_ids()` returns an empty set and the exclusion silently no-ops — no test catches this.
- [P2] `propose_target_page(entry)` is pseudocode with no slug-normalization rule. Whether 'API 579-1/ASME FFS-1' maps to `api-579-ffs.md` vs `api-579-1.md` determines extend-vs-create verdict per row. Without a normalization spec, the extend-vs-create map is non-deterministic and the `post_run_all_extend_pages_exist` test becomes tautological (it only checks whatever the author wrote).
- [P2] `post_run_no_source_reads` claims to verify zero filesystem access to `/mnt/ace/**` during execution, but no mechanism is described (no strace, no mount unbinding, no process audit). As written this is an unfalsifiable assertion.
- [P2] Provenance sample is fixed at 10 of 145 rows (~6.9%). The plan acknowledges this as a 'smoke-check' and defers full coverage to #2039, but there's no stratification rule — e.g., at least N rows per domain, at least one 'extend-only' and one 'create'. A random 10 could miss a domain entirely.
- [P3] Parallel Lane B1 conflict on `docs/plans/README.md` is mitigated by 'serialized commit through main session' — but no concrete mechanism (lock file, commit ordering, rebase protocol) is named. Given KNOWLEDGE.md on multi-agent commit serialization and merge-race silent revert, this deserves a named protocol.
- [P3] `cathodic-protection` domain (19 entries) is filtered by org-exclusion (OCIMF/CSA) — but the plan never states whether any cathodic-protection entries are tagged OCIMF/CSA. If none are, the exclusion is a no-op for that slice and the stated post-filter count becomes tighter; worth pre-computing.
- [P3] Acceptance criterion says 'Zero files under `knowledge/wikis/**` modified by this plan's commits' but the out-of-scope list says `knowledge/wikis/**` is 'read-only'. Reads are fine; the test checks writes. Wording consistent, but consider adding a pre-commit hook assertion rather than only a post-run grep for defense-in-depth.
- [P3] `post_run_only_owned_paths` regex `grep -v -E '^(docs/reports/\|docs/plans/)'` — the escaped pipe `\|` inside `-E` (ERE) would match a literal `|`, not alternation. Likely a markdown-escaping artifact, but will silently pass if implemented as written in a script.

### Suggestions
- Commit the topic-clustering rule to a fixture: either inline a table in each per-domain report (e.g., `pipeline-design-inspection-corrosion-materials` with explicit keyword→cluster rules) or pre-land `data/document-index/standards-topic-clusters.yaml` as part of this plan. The open question at line 258 should be resolved before plan-approval, not deferred.
- Run the `in_slice` filter during plan-approval (dry-run, no commit) and pin the exact expected post-filter row count (e.g., 'expected = 141' or '138'). Make that number the acceptance criterion, not '≤145'.
- Add `ls -la data/design-codes/code-registry.yaml` to the Evidence block, or state explicitly 'file does not exist → exclusion is a no-op for this wave' so the assumption is visible.
- Specify the slug-normalization rule for `propose_target_page()` — at minimum: lowercase, hyphen-separated, strip org prefix if it matches wiki convention, and include a table of the ~7 existing engineering-wiki pages with their canonical slugs so readers can verify mapping determinism.
- Replace the `post_run_no_source_reads` assertion with a falsifiable check: either (a) run under a PID with `/mnt/ace` unmounted or bind-mounted read-only with audit, or (b) add a pre-commit grep that fails if any new file path in the diff references `/mnt/ace/`.
- Stratify the 10-row provenance sample: at least 3 rows per domain, at least 1 'extend-only' and 1 'create' verdict, at least 1 with multiple shard summary refs. State the selection rule.
- For the Lane B1 `docs/plans/README.md` conflict, name a concrete serialization mechanism (e.g., 'main session appends plan row last, after both lanes finish; if other lane already merged, rebase and re-append') with reference to KNOWLEDGE.md feedback on multi-agent commit serialization.
- Fix the `grep -v -E` regex in `post_run_only_owned_paths` by verifying in a throwaway shell that the alternation actually works as intended — or replace with two `grep -v` invocations chained.
- Consider adding an explicit `ledger_id` collision check: if two ledger rows normalize to the same target page slug, both get 'extend-only' verdict pointing at the same file — worth asserting that in the extend-vs-create map.
