## Findings

1. **MAJOR - #3712 does not make #3709's Layer 2 live.**

   Evidence:
   - #3712's required set is limited to `Run Tests`, `Scheduler Mutation Surface Guard`, `Review Evidence Check`, and `Plan Approval Check` (`docs/plans/2026-07-30-issue-3712-required-status-checks.md:198-207`, `:237-243`, `:277-282`).
   - #3709 v6 says its primary CI control will be a future `Cron Cutover Preservation` job (`docs/plans/2026-07-30-issue-3709-managed-block-classification-v6.md:177-181`). It says making that control genuinely required means required-check contexts `Cron Cutover Preservation` **and** `Scheduler Mutation Surface Guard` (`...managed-block-classification-v6.md:191-196`). It repeats that Layer 2 stays inert until an owner adds required status checks (`...managed-block-classification-v6.md:227-232`).

   Failure scenario:
   #3712 lands exactly as planned. The repository now blocks merges on the four named checks, but #3709 later adds `Cron Cutover Preservation` only as a visible CI job. A PR can still merge with that future preservation test red unless a second ruleset change happens. That leaves #3709's Layer 2 inert after the issue that the ecosystem is citing as the required-check fix.

   Required revision:
   Add an explicit dependency-direction section. Either include `Cron Cutover Preservation` as a required context once #3709's job lands, with the same staged/migration treatment as the initial four checks, or state that #3709 needs its own follow-on owner ruleset update and that #3712 does not satisfy #3709 Layer 2. Without that, the enforceability claim remains false for #3709.

2. **MAJOR - No concrete rollback/backout path is stated for a bad ruleset rollout.**

   Evidence:
   - The rollout plan stages checks one at a time and records evidence (`docs/plans/2026-07-30-issue-3712-required-status-checks.md:237-243`).
   - The acceptance criteria verify that checks become required (`docs/plans/2026-07-30-issue-3712-required-status-checks.md:277-285`).
   - There is no step describing what owner action to take if a newly-required context is red, missing, duplicated, or intermittently frozen across the 18 open PRs.

   Failure scenario:
   A context is added to required status checks and GitHub treats stale/missing check-runs as blocking on several open PRs, or a job starts failing due to GitHub Actions/network/tooling variance. Maintainers then have no pre-approved backout procedure and either freeze the repo while debating policy or bypass the intended governance manually.

   Required revision:
   Add a rollback section before approval: record the exact owner action to remove the last-added required context or set the new status-check rule back to the previous known-good required-context list; require capturing pre-change and post-rollback `gh api repos/vamseeachanta/workspace-hub/rulesets/<id>` evidence; define the decision trigger, e.g. any newly-added required context blocks an otherwise-mergeable PR for reasons unrelated to the PR's diff.

## Ordering judgment

The proposed first step, repairing `LEGAL_SCAN_AUTH_CURRENT` / `AUTH_ENVELOPE`, is correct. The reusable workflow fails before audit logic if the secret is absent, so making `strict-scan / authority` required now would freeze affected same-repo PRs.

Requiring `Run Tests` alone does **not** appear to freeze the current 18 PRs. I checked each current PR head via `GET /repos/vamseeachanta/workspace-hub/commits/{head_sha}/check-runs?per_page=100`; `Run Tests` was present and successful on all 18. The latest `Baseline Testing` workflow runs on `main` today were also successful. This check is not the ace1 `tests/enforcement` or `tests/cron` baseline: `.github/workflows/baseline-check.yml:51-64` runs `tests/test_deduplication_fix.py` and `tests/ci_smoke/` only, so the ace1 baseline failures do not imply `Run Tests` is red in CI.

Requiring the full proposed set immediately would freeze or force migration work. `Scheduler Mutation Surface Guard` is red on #3583, #3569, #3563, #3546, and #3520, and absent on older heads that predate the context. The plan correctly says to handle red PRs before enabling that context, but it should also preserve the missing-context/rerun requirement as an explicit migration gate.

## Advisory/gating split

Leaving `Code Quality`, `Governance Checks`, `Model-ID Sourcing Guard`, and `Compliance Dashboard` advisory is sound for this rollout. The first two are advisory by implementation (`continue-on-error` / warn mode), `Model-ID Sourcing Guard` is documented advisory in the workflow, and `Compliance Dashboard` has `continue-on-error: true`. Leaving `claude` and `claude-review` advisory is also correct: they are interactive or external AI automation, not deterministic merge gates.

The four proposed-required checks are mostly deterministic and do not depend on repository secrets. `Plan Approval Check` depends on repo variables and protected-label prerequisites, and the plan correctly puts it last with prerequisite verification. `Scheduler Mutation Surface Guard` is currently the riskiest required context because it is already red on several open PRs and uses generated report freshness; it is appropriate only after explicit PR triage/rerun.

## 18-PR migration impact

- All 18 current heads have `Run Tests` present and green.
- `Review Evidence Check` and `Plan Approval Check` are present and green on the sampled/current inventory.
- `Scheduler Mutation Surface Guard` is green on #3590, #3543, #3540; red on #3583, #3569, #3563, #3546, #3520; absent on older heads including #3471, #3468, #3465, #3425, #3411, #3410, #3379, #3378, #3363, #3327.
- `strict-scan / authority` is red on the seven newer heads where it exists and absent on older heads. It must stay outside the required set until the secret is repaired and current heads are rerun.

On rollout day, stale or older branches with missing contexts need a synchronize/rerun path before those contexts can be required for them. The plan's inventory step is directionally right; it needs to make missing contexts a first-class bucket, not only red contexts.

## Rule amendment judgment

There is no direct conflict between #3711's proposed amendment and #3712's preferred path. #3711 changes the fail-closed/source-artifact clause to say source attestations/content checks fail closed when artifacts disagree with trusted git-index sources, while not certifying physical registry-root truth (`origin/plan/3711-host-independent-identity-inventory-v2:.claude/rules/scheduler-mutation-safety.md:8-11`). #3712's preferred path makes the existing pre-merge scheduler command true by requiring `Scheduler Mutation Surface Guard` (`docs/plans/2026-07-30-issue-3712-required-status-checks.md:224-231`). Those are additive.

Potential conflict only appears if #3712 uses its fallback and weakens the pre-merge scheduler rule to advisory/manual language. That would undermine #3709's and #3711's reliance on the scheduler-mutation rule as a mandatory local gate. The plan should state that the fallback requires owner approval and a dependency review against #3709/#3711 before amendment.

## Final judgment

Do not approve as-is. The sequencing for the initial four checks is mostly sound, and `Run Tests` alone should not freeze the current repo. The plan needs targeted revision for #3709 dependency direction and rollback/backout before a ruleset change is safe to approve.
