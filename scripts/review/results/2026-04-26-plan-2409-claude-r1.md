### F2 — `RUBRIC.yaml` weights are named, never numbered (specificity gap, defect-checklist item 7)

No sample RUBRIC.yaml is shown, no enumerated weight categories beyond what pseudocode names, and no rule for resolving the case where a `forbidden_substring` and a `required_section` co-occur (does the section credit survive the forbidden-substring penalty?).

### F3 — Scoring asymmetry in the verdict path (consistency defect, defect-checklist item 11)
- Pseudocode line 198: `if expected.has("verdict"): score += rubric.weights.verdict_match if matches else -X`. The literal `-X` is unspecified. What's the verdict-mismatch penalty?
- Acceptance criterion line 283 says "Adversarial-review class fixtures cover all three verdict classes (APPROVE / MINOR / MAJOR)" — but it does not say the **scoring is verdict-aware** beyond the binary `matches`. A MINOR predicted-as-APPROVE should plausibly cost less than MAJOR predicted-as-APPROVE (severity-graded penalty), which is the standard pattern for ordinal-verdict graders. The plan's binary match treats every mismatch identically, which silently encodes a model-quality bias toward "guess MINOR every time" as a low-cost neutral position.
- **Fix:** either explicitly justify binary verdict scoring, or specify a confusion-matrix penalty table in RUBRIC.yaml (e.g., `verdict_penalty: {APPROVE_predicted_as_MINOR: 1, APPROVE_predicted_as_MAJOR: 2, MAJOR_predicted_as_APPROVE: 3, ...}`). Defect-checklist item 11 was answered with a checklist criterion ("cover all 3 verdicts") but not with a normalization rule.

### F5 — Validator/CI enforcement-tier label is misaligned with `.claude/rules/patterns.md` (defect-checklist item 9)
- Adversarial Review pre-empt #7 (line 312) declares: *"Tier 2 (script) per `.claude/rules/patterns.md` enforcement gradient: a CI workflow runs the validator on every fixture-path change. Tier 3 (commit hook) is deferred to a follow-up..."*
- Read literally against `patterns.md` (verified at `/mnt/local-analysis/workspace-hub/.claude/rules/patterns.md`):
  - Level 2 — Script: "Shell/Python, called from skill **or CI**, Reliability: High — auditable, testable" ✓ (CI is named here)
  - Level 3 — Hook: "pre-commit / stop-hook, Reliability: Strongest — fires automatically"
- So the table itself does mention "or CI" under Level 2, which gives the plan partial defensibility. But the plan **also** delivers a `.github/workflows/validate-battery-fixtures.yml` that runs on every PR — that's auto-firing on push, which is operationally indistinguishable from a Level-3 enforcement guarantee for paths under `tests/fixtures/model_release_battery/**`. The plan's label of "Tier 2" is **technically defensible but understates the actual enforcement strength**, and a future reader looking at "Tier 2, follow-up if friction appears" will assume a weaker guarantee than they actually get.
- This isn't a blocker — the table genuinely lists CI under Level 2 — but the plan's framing should be sharpened.
- **Fix:** rephrase pre-empt #7 as "Tier 2 via CI per `.claude/rules/patterns.md`; this provides Tier-3-equivalent automatic firing on PRs touching fixture paths, but a true pre-commit hook is deferred until friction is observed."

### F6 — "Validator enforces identity block in first 500 bytes" is partially specced but quietly underspecified (defect-checklist item 8)
- Acceptance criterion (line 277), TDD test (line 253), and pseudocode (line 208) all assert the validator enforces the 500-byte identity block. The validator script is named (`scripts/release_readiness/validate_battery_fixtures.py`, line 113), and TDD tests are listed for it. ✓

### F7 — Repo-navigation negative case test is too loose (defect-checklist item 5/12)
- Acceptance criterion line 284: "at least one negative case (the right answer is 'not found / does not exist')." TDD test (line 257) accepts either `expected.verdict == NOT_FOUND` **or** empty `required_substrings_any` + non-empty `forbidden_substrings`.
- The disjunction is loose. An empty `required_substrings_any` means "no substring required" — that's how every fixture would look if a fixture author forgot to populate it. The OR clause turns a forgotten-field bug into a passing negative-case fixture.
- **Fix:** require `expected.verdict == NOT_FOUND` (or equivalent positive marker) for negative-case fixtures, not the disjunction.
