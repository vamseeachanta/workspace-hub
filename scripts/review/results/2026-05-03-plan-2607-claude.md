## Defects found

### R1 — P2 (MAJOR-leaning) — Promised platform support exceeds verification

**Defect:** Plan §4 commits to documenting Debian/Ubuntu, Fedora/RHEL (`dnf`), and macOS (`brew`) commands. Plan §6 only validates on Docker `python:3.13-slim` (Debian-based). Documenting a `dnf install libxml2-devel libxslt-devel` line we never ran is exactly the failure mode the user asked us to AVOID — it accidentally promises system support that's not tested. This recurs the issue we are nominally fixing for clean-venv installs.

**Evidence:** `feedback_naive_secret_scan_false_positive_cascade` and `project_github_workflow.md` precedent: untested commands in user-facing docs are defects, not "best effort."

**Required fix:** Plan §4 will scope the documented platform to **Debian/Ubuntu only** (the platform reported in the issue). For macOS/Fedora/RHEL, README will say: *"Other platforms: install the equivalent libxml2 and libxslt development headers for your distro; not verified by maintainers."* No copy-pasteable command for unverified platforms.

**Status:** Plan must be amended before implementation. (Folding into A.C.3 narrowing.)

### R2 — P3 (MINOR) — Doc location matches convention but skips a precedent check

**Defect:** Plan §2.3 asserts README is canonical. Verified — true. But §2.4 cites the `pygmt` precedent ("requires GMT system lib") as an *inline pyproject comment*, while the plan proposes a **README subsection**. These are different surfaces. The plan does not justify why the lxml requirement merits a README upgrade while `pygmt` lives only in pyproject. Inconsistency invites bikeshedding in review.

**Evidence:** `pyproject.toml:138` for pygmt; `pyproject.toml:62` for lxml — both inline comments only. README has zero system-deps mentions today.

**Required fix:** Either (a) Plan will add an inline `# requires libxml2-dev/libxslt1-dev system libs` to `pyproject.toml:62` AS WELL as the README block (consistency with pygmt), or (b) Plan will explicitly justify why README escalation is warranted for lxml-but-not-pygmt (lxml broke a real reported smoke install on a supported Python; pygmt's GMT is a heavier opt-in extra). Recommend (a) — minimal extra cost, kills the inconsistency.

**Status:** Adopt (a). Add `pyproject.toml:62` inline comment update to plan §4.

---

### R3 — P3 (MINOR) — Smoke-script TDD claim oversells the test value

**Defect:** Plan §6 frames `scripts/bash/check-install-prereqs.sh` as a TDD substitute. It is not. It checks for `libxml2-config`/`xslt-config` binaries — these are proxies, not the actual `pip install lxml` operation. A system could have those binaries from a partial install yet still fail to compile lxml (e.g., missing `python3-dev` headers, incompatible compiler). The plan presents a proxy-check as a guarantee.

**Evidence:** `lxml`'s actual build dependency chain on Debian/Ubuntu also requires `python3-dev` (for `Python.h`) and a C compiler (`gcc` or `build-essential`). The plan's package list is incomplete.

**Required fix:** Plan §4 README block will list the **complete** apt set: `build-essential python3-dev libxml2-dev libxslt1-dev`. Plan §6 will downgrade the smoke-script claim from "test surface" to "advisory pre-check" and document its limits inline. Acceptance criterion A.C.5 will be revised to "the script's PASS exit MAY still be followed by a pip-install failure if compiler/headers are absent; it is a hint, not a gate."

**Status:** Adopt. Update README package list and rewording of A.C.5.
