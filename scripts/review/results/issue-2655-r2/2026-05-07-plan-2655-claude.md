## Findings

1. **The plan's prose risk-acknowledgement does not match its TDD coverage — `match_remediation_rule` already mis-routes `sitemap.xml.gz` and `…issue-334….md.bak` today.** §Resource Intel line 21 says "implementation should not generalize `docs/plans/*` or `sitemap.xml` without new evidence because those paths may collide with legitimate workspace-hub artifacts," and §Risks line 282 says "`sitemap.xml` is a collision-prone singleton if workspace-hub ever gains a real sitemap. Mitigation: keep the rule exact and evidence-bound." But the rule is **not exact** in source: `scripts/analysis/provider_session_ecosystem_audit.py:200` uses `path == pattern or path.startswith(pattern)` for *all* patterns, so `sitemap.xml.gz`, `sitemap.xml.template`, and `docs/plans/2026-04-21-issue-334-annual-operator-disclosures-dataset.md.bak` empirically all match `nested_repo_context_drift` right now (verified). The plan's negative TDD test #4 (`test_unrelated_missing_workspace_hub_path_stays_actionable`) uses `docs/real-missing-workspace-doc.md` — a path that obviously shares no prefix with any rule and would pass trivially. The plan needs either (a) a TDD test that fixes a `sitemap.xml.gz`-style collision in red-then-green form, or (b) an explicit acknowledgement that the existing prefix semantics are accepted and that the "keep the rule exact" mitigation in §Risks is not actually implemented. Without one of those, the §Risks claim is aspirational, not load-bearing.

2. **Adversarial Review Summary misrepresents r1 provenance — the "Claude r1 | MAJOR" and "Gemini r1 | MAJOR" rows are not backed by provider artifacts.** Plan §Adversarial Review Summary lines 261-263 list three providers with verdicts and key findings. The on-disk artifacts show: `scripts/review/results/2026-05-07-plan-2655-claude.md` = 0 bytes, `claude.md.err` = 0 bytes (no error trail — review-runner did not even invoke Claude), `gemini.md` = 0 bytes, `gemini.md.err` = 5660 bytes (capacity error), `codex.md` = 395 bytes (`UNAVAILABLE` stub due to codex-cli 0.124+ regression #2479). The Claude/Gemini "findings" the plan summarizes actually live in the `disagreement.md` (7921 B) file authored by a different process. Per `feedback_permission_gate_blocks_cross_review.md` and `feedback_permission_gate_blocks_cross_review.md`, single-author/surrogate review provenance must be transparently labeled — the plan's frontmatter line 7 ("r1 review returned MAJOR/UNAVAILABLE/MAJOR") and §Adversarial Review Summary table both flatten this. Acceptance criterion #9 (line 253) anticipates the unavailability case but applies it to the *next* review wave; the table at lines 261-263 still presents the prior wave as if three providers reviewed.

3. **TDD test #3 (`test_issue_334_plan_path_routes_to_worldenergydata_docs_plans_without_generalizing_all_docs_plans`) does not exercise the brittleness the plan claims it does.** The test gives a positive example (issue-334 plan path) and a negative example (`docs/plans/2026-05-07-issue-2655-codex-nested-repo-context-drift.md`). Under the existing `path == pattern or path.startswith(pattern)` semantics, the negative case passes trivially because the issue-2655 plan path shares no prefix with the issue-334 pattern. The actual generalization risk the plan flags ("issue-334 plan path is exact and not a generic `docs/plans/*` mapping," §Risks line 283) would require a test like `docs/plans/2026-04-21-issue-334-annual-operator-disclosures-dataset.md.draft` (would WRONGLY match) or `docs/plans/2026-04-21-issue-334-something-else.md` (would correctly NOT match). Plan §Pseudocode line 204 ("`unrelated docs/real-missing-workspace-doc.md` returns no nested_repo_context_drift rule") echoes the same trivial coverage. Either tighten the test to exercise the prefix-collision boundary, or rename the test to admit it only verifies the existing prefix behavior, not the generalization claim.
