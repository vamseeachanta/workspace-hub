## Findings

1. **[MINOR] TDD t02b — `systemctl show` property name** — The property is `EnvironmentFiles` (plural) — but `systemctl show -p EnvironmentFiles` returns lines like `EnvironmentFiles=/home/vamsee/.hermes/.env (ignore_errors=no)`. The grep pattern in t02b should match the path substring (which it does). However, when the operator runs the test, they should be aware that the same property is also available as `EnvironmentFile=` (singular) in systemd 252+ — confirm output format on the host (`systemd 254` ships on Ubuntu 24.04+) before treating an empty grep as a real failure.
   - **Evidence:** TDD row t02b — `systemctl show hermes-gateway -p EnvironmentFiles | grep -c '/home/vamsee/.hermes/.env'`.
   - **Fix:** Add a fallback: `systemctl show hermes-gateway -p EnvironmentFile -p EnvironmentFiles | grep -c '/home/vamsee/.hermes/.env'`.

2. **[MINOR] TDD t05b — race window on `~/.bash_history` flush** — Bash writes to history on shell exit by default (or per-command if `PROMPT_COMMAND='history -a'` is set). The verification grep can pass simply because the operator hasn't logged out yet, then the token can land in history later when the shell exits. The Wave 1 step (e) snippet does use `set +o history` inside a subshell — that does the right thing — but t05b's grep alone is not sufficient evidence of permanent absence.
   - **Evidence:** TDD row t05b — `grep -E "[0-9]{8,10}:[A-Za-z0-9_-]{30,}" ~/.bash_history | wc -l`.
   - **Fix:** Add a note that t05b should be run AFTER `history -a` (force-flush) or AFTER the operator's shell session ends; OR add t05c that greps `/proc/<curl-pid>/cmdline` for a more direct probe (acknowledged race is fine — that's what t05c implicitly accepts). Alternatively, the residual-risk note in Risks already covers this; just lift the caveat into the test row.

3. **[MINOR] Phase 2 toolset enumeration is still soft** — Wave 2 step (b) lists "memory, session_search, cronjob, send_message, file (read-only-ish), kanban" as the mobile-safe set, but the runbook deliverable doesn't bind this with a concrete `config.yaml` snippet. The reviewer (and the operator weeks from now) cannot tell whether `terminal` is gated by approvals.mode alone or also requires explicit `tools.terminal.enabled: false` in the gateway block of `config.yaml`.
   - **Evidence:** Pseudocode Wave 2 step (b) — "Document mobile-safe set: …" with no `config.yaml` excerpt.
   - **Fix:** During Wave 2 execution, paste the actual relevant `config.yaml` excerpt into `docs/runbooks/telegram-hermes-mobile.md#phase-2-guardrails` so reviewers have a config-level diff to verify, not just a prose claim.

4. **[MINOR] Recovery path for failed override** — If `sudo systemctl edit hermes-gateway` produces a malformed override.conf (typo, wrong section header), `systemctl daemon-reload` will warn but `restart` may then fail. The plan does not prescribe a rollback step.
   - **Evidence:** Pseudocode Wave 1 step (c) — daemon-reload + restart with no rollback if restart fails.
   - **Fix:** Add: "If `restart` fails, `sudo systemctl revert hermes-gateway` removes ALL drop-ins and reverts to the base unit; re-run `systemctl edit` to retry." This is one line and saves real recovery time.

5. **[MINOR] No explicit test that the rotated token replaced the old one** — t05 confirms the **current** token in `.env` validates with Telegram. It does not prove the operator actually performed the rotation step (Wave 1 step a–b) versus accidentally re-installing the old token. If the original BotFather token wasn't actually revoked, both tokens still work and t05 passes either way.
   - **Evidence:** TDD row t05 — only validates that whatever token is in `.env` is accepted by Telegram.
   - **Fix:** Add a manual checklist item in the runbook: "After `/revoke` in @BotFather, attempt `getMe` with the OLD token (held briefly in operator memory) and confirm `401 Unauthorized`. Then update `.env` with the new token and retest." This is a **secret-aware** step that cannot be a CI command but should be in the operator runbook.
