## Pseudocode Soundness

The 1-line addition in `enrich_one()` is correct for the straightforward case and the edge case raised:

- `summary_file_exists = summary_path is not None` is computed **before** `summary_done_from_file(summary_path)` is called, so even if the latter raised, `summary_file_exists=True` would persist on the record. Good.
- However, `summary_done_from_file()` (lines 64-77 of current source) cannot raise — it catches `FileNotFoundError / UnicodeDecodeError / OSError / JSONDecodeError` internally and returns False. So the edge-case concern is defused at the callee, not the caller. This means the two fields correctly diverge when a file exists but is corrupt/binary: `summary_file_exists=True`, `summary_done=False`.
- One latent fragility: if a future maintainer narrows the `except` tuple in `summary_done_from_file` (e.g., drops `OSError`), an IOError could surface and the call site would crash **after** setting `summary_file_exists=True` but **before** setting `summary_done`. The record would then be missing `summary_done` entirely and `_is_already_enriched()` would return False on next resume. Worth a defensive try/except in `enrich_one()` or a test that asserts both keys are always present on return.

## Test Coverage Adequacy

Eleven tests cover the nominal paths well, but three critical scenarios are missing:

- **(a) Unreadable-file divergence.** Tests 1-4 cover "file exists with empty/missing summary key" — but no test asserts `summary_file_exists=True` AND `summary_done=False` for **corrupt JSON** or **unicode-decode error**. Given that the existing test suite already has fixtures for these (lines 81-93 of the test file), add two: `test_summary_file_exists_true_on_corrupt_json` and `test_summary_file_exists_true_on_unicode_decode`. These are the tests that prove the split was worth doing.
- **(b) `--resume` on pre-split records.** `_is_already_enriched()` at line 98 currently tests `"content_type" in record and "summary_done" in record` — both pre-split records satisfy this. After deployment, an interrupted re-enrichment resumed with `--resume` will **skip** every pre-split record and never write `summary_file_exists`. The plan does not address this. Either (i) extend `_is_already_enriched` to require all three fields, or (ii) document that initial re-enrichment must run without `--resume`. Preferred: (i) with a test.
- **(c) Asymmetric carryover.** `extract_enriched_fields` + `apply_carryover` already handle partial field sets cleanly (setdefault on each key present). Plan's test 10 covers the happy path; add a test for a record that has `summary_file_exists` but not `summary_done` (and vice versa) surviving a Phase A/C/E rewrite without one field clobbering the other.

## Validator Threshold Reasonableness

12.8pp headroom (0.75 default vs 87.8% projection) is tight but defensible. However, note that the existing `summary_done_min=0.55` default is already inconsistent with the production 16.1% observation (the validator would reject today's index), suggesting defaults in this file are aspirational rather than current-floor. Recommend **0.70** for `summary_file_exists_min` to match the pattern of round-number floors with ~15pp headroom, and document the observed 87.8% in the script's docstring so future maintainers know the gap is intentional slack.

## Scope Boundary

Batching YAML updates into the same PR is correct here. The maturity YAML's `summary_file_exists_percent` is empirically derived from the re-enrichment run, so splitting would require the code PR to merge, re-enrichment to run against `main`, then a follow-up PR — creating a window where the registry declares a field the maturity YAML doesn't report. Single-PR closure is the right call.

## Ops Flow

Live re-enrichment mid-PR is the main sequencing risk: if edge cases surface in production that weren't caught in tests, the PR is half-merged (code landed, YAML not yet updated). Mitigation: run a **dry-run against production** as an acceptance-criteria gate **before** the first commit, so the ~87.8% projection is validated on real data before any code is pushed. The plan mentions a dry-run check but does not sequence it before the code commit — tighten this.

## Recommendation

Approve with three fixes before implementation: (1) extend `_is_already_enriched()` to include `summary_file_exists` and add a resume test; (2) add corrupt-JSON and unicode-decode tests asserting the `True/False` divergence; (3) move the production dry-run check to occur **before** the first commit, not after. Consider dropping the validator default to 0.70. YAML batching and ops flow are otherwise correct.
