### Summary
Not approval-ready. The plan still leaves the core replacement contract undefined, misses required harness retrieval, and proposes speculative edits/tests that are not anchored to verified current surfaces or measurable outcomes.

### Issues Found
- `docs/plans/2026-04-17-issue-2312-lifecycle-script-authority-cleanup.md` is missing the central implementation contract. The plan itself says `No canonical replacement evidence paths have been defined yet` in `Resource Intelligence Summary > Gaps identified`, and repeats the same blocker in `Risks and Open Questions` (`What should the canonical issue-specific evidence path be for the final close/archive stages`). Until the exact `evidence:` replacements for `.planning/templates/stage-evidence-template.yaml` are specified, the deliverable, tests, and acceptance criteria cannot be verified.
- The resource-intelligence section is not evidence-tight for this issue class. `docs/plans/README.md` requires `cat:harness` plans to consult `CONTROL_PLANE_CONTRACT.md`, `config/agents/` settings, and `.claude/rules/`; the plan cites none of those. That omission already caused a blind spot: `config/agents/codex/state-snapshots/default.rules` still contains legacy lifecycle-script references, but the plan never classifies it as current guidance, fixture, or out-of-scope.
- `Files to Change` contains speculative targets that are not supported by verified stale hits. `docs/work-queue-workflow.md` already states `Do not invoke any legacy local closure helper as a live workflow step` and is already covered by `tests/docs/test_banned_stale_references.py`. `notes/agent-work-queue.md` already declares GitHub issues as the `Source of truth` and the refresh scripts as the regeneration path. The plan gives only `tighten wording if needed` / `document ... if the template needs` rationale, not a verified defect in either file. `docs/plans/README.md` is also already indexed for issue `2312`, so `add this plan to index` is stale metadata, not work still to be planned.
- The TDD section is too vague to fail for the real defect classes. `test_current_workflow_docs_use_github_planning_refresh_authority_not_deleted_lifecycle_scripts` relies on an undefined `curated current-file list`; `test_analytical_fixture_files_are_not_treated_as_current_workflow_docs` relies on an undefined `selected fixture file list`; and no test asserts the exact approved replacement contract or that the replacement evidence targets are real canonical anchors rather than placeholders. As written, a meaningless substitution could satisfy `zero deleted lifecycle-script matches`.
- The plan does not resolve scope/classification boundaries needed for safe approval. Its pseudocode says to decide whether each reference is `current guidance, historical evidence, or analytical fixture`, but verified files outside the listed scope still contain lifecycle-script references, including `config/agents/codex/state-snapshots/default.rules` and `scripts/knowledge/tests/test-knowledge-scripts.sh`. Without an explicit classification/allowlist decision for these surfaces, the bounded test strategy is underspecified.
- The audit-refresh acceptance criterion is not approval-grade and does not handle historical-vs-event-time noise. The plan requires only `Post-implementation audit refresh is run and linked from the issue`, but `docs/reports/provider-session-ecosystem-audit.md` explicitly separates `Recent activity since previous audit` (event-time) from `Corpus change since previous audit` (export/reclassification noise). The plan never states what audit outcome would count as success, or how to interpret unchanged counts if historical/allowlisted references remain.

- Expand `Resource Intelligence Summary` to satisfy the harness/documentation retrieval bundle from `docs/plans/README.md`, then explicitly classify every verified lifecycle-script reference you intend to include, exclude, or defer. At minimum, address `config/agents/codex/state-snapshots/default.rules` and `scripts/knowledge/tests/test-knowledge-scripts.sh`.
- Remove unsupported `modify if needed` targets from `Files to Change` unless you can cite a concrete stale reference or wording defect in those files. `docs/plans/README.md` should be dropped from the cleanup deliverable unless the plan index is actually missing.
- Rewrite the TDD table so each test has a fixed protected-surface set or an explicit directory rule plus allowlist, and add a test that asserts the approved replacement anchors themselves, not just the absence of banned strings.
- Tighten the audit criterion to a measurable statement, such as verifying that the refreshed audit still maps lifecycle-script reads only to intentional historical surfaces, or explicitly demote audit refresh to a post-implementation observation rather than a pass/fail acceptance gate.
- If the canonical close/archive evidence contract is still undecided, split that decision into a prerequisite issue instead of approving this cleanup plan as if it were already settled.
