## Findings

1. **Factual error: `MooringCondition` enum description is false** (plan §Resource Intelligence Summary L17). The plan states: "`MooringCondition` enum (INTACT_QUASI_STATIC=1.67, DAMAGED_QUASI_STATIC=1.25) at lines 21–24". Actual `registry.py:21–23`:
   ```
   class MooringCondition(str, Enum):
       INTACT_QUASI_STATIC = "intact-quasi-static"
       DAMAGED_QUASI_STATIC = "damaged-quasi-static"
   ```
   The numeric 1.67 / 1.25 values live in the separate `_MOORING_SAFETY_FACTORS` dict at lines 35–38, which the plan never references. An implementer following this plan would expect `MooringCondition.INTACT_QUASI_STATIC` to *be* the float and write incorrect dereference code.

2. **`_default_repo_root()` is unspecified ellipsis** (Pseudocode L156–160 is `...`). The Adversarial Review §2 lists the desired fallback order (kwarg → env var → parent walk → sentinel → raise) but the implementation is not pseudocoded. More importantly: pip-installed `digitalmodel` lives under `site-packages/digitalmodel/...` where the parent walk *never* hits `knowledge/wikis/` — the walk falls through to the sentinel and raises `CitationResolutionError` on every mooring calc. The plan must explicitly state that pip-installed deployments require `DIGITALMODEL_REPO_ROOT` env var or explicit kwarg, and define the bounded sentinel (e.g., stop at filesystem root or after N levels). Without this, CI/CD pipelines running pip-installed digitalmodel silently fail-closed.

3. **`test_grep_count_meets_target` is a fixture test, not a behavior test** (TDD Test List row 5, L221). The plan's own prompt template (`scripts/review/plan-review-prompt.md` lines 40–46) flags exactly this anti-pattern in "Bad findings": "Acceptance criterion is circular: weak-fixture → non-APPROVE regardless of wrapper correctness. This tests the fixture, not the code." A `grep -c` test passes if someone writes a docstring containing the word "Citation" three times; it does not exercise `validate_citation()`, does not trigger `CitationResolutionError`, and does not assert SFs are applied. Delete this row and AC1; rely on AC2/AC3/AC4 behavior tests.

4. **AC6 escape hatch contradicts the plan's own rejected option** (Acceptance Criteria L235 vs. Gaps L54). Gaps L54 explicitly rejects "(c) accept fail-closed behavior in prod and only emit at test/fixture time" as "defeats the rule's purpose". AC6 then permits exactly this: "OR Risk row below explicitly documents accepted fail-closed behavior with deferred follow-up issue". Either the pilot ships with a production wiki page (make AC6 unconditional) or it isn't a pilot — pick one.

5. **Persisting `repo_root: Optional[Path] = None` on `MooringLineDesign` is a portability footgun** (Pseudocode L164, Adversarial Review #4 L251). `MooringLineDesign` is a `BaseModel` (verified `mooring_design.py:259`). YAML-serialized configs that capture `repo_root` will embed the absolute repo path of the machine that wrote them, then fail on every other machine. This violates `.claude/rules/coding-style.md` "Path Handling" rule (no hardcoded absolute paths). Mitigation belongs on the *method* or a service object, not on the persisted Pydantic model.

6. **Pseudocode emits only one citation per call but a complete DNV-OS-E301 safety check needs both** (Pseudocode L178–195). `check_mbl_with_citations(max_tension_kn, *, condition="intact")` returns `{"citations": [sf_cv.citation]}` — a single-state assessment. A complete §2.2.3 mooring check evaluates BOTH intact AND damaged factors. The pilot as planned forces callers into two separate method calls and two separate sidecar dicts, which is awkward and a fertile ground for callers checking only the intact case and missing damaged.

7. **Adversarial Review #3 mitigation contradicts Open Q L264** (L249 vs. L264). The Adversarial Review says: "Mitigation: deprecate the literal fields in this PR (mark with `Field(..., description="DEPRECATED — use get_intact_safety_factor()")`) and add a `@model_validator` that warns if the field value doesn't match the registry." Open Q L264 then says: "Recommend follow-up to keep this PR tightly scoped." Pseudocode L162–167 shows neither deprecation nor validator. An executor following Pseudocode will leave the shadow fields silently divergent from the registry — exactly the failure mode flagged in Adversarial Review #3. Pick one path and reflect it in Pseudocode.

8. **AC5's `grep -c 'PENDING' .claude/rules/calc-citation-contract.md` returns 0 is brittle** (L234). Verified currently 1 occurrence at line 19. AC5 enforces an absence test that punishes any future legitimate use of the word PENDING in the rule file (e.g., "(PENDING MCP migration #2400)"). A stronger AC asserts the specific paragraph is rewritten to reference the actual implemented pilot — not a word-presence check.

9. **AC8 mandates three-provider review, contradicting the plan's own T2 complexity rating** (Complexity §L286 vs. AC8 L237). The plan cites `feedback_always_adversarial_review_scale_depth` which (per MEMORY index) prescribes "T2=Codex+Gemini, T3=add Claude code-reviewer". The plan rates itself T2 (L286) but AC8 requires three providers (Claude + Codex + Gemini) — that's T3 review depth. Either upgrade complexity to T3 with justification or drop Claude from AC8.

10. **`check_mbl_with_citations()` return shape is an undocumented heterogeneous dict** (Pseudocode L192–195). The existing `check_mbl()` returns `Dict[str, float]`. The new method returns a nested dict with `results` (mapping str → dict) + `citations` (list). No `TypedDict`, dataclass, or Pydantic model is specified. Sidecar-pattern rule (`.claude/rules/calc-citation-contract.md:6` — "Citations emit to a sidecar, not the primary numeric payload — preserves downstream-consumer compatibility") suggests an explicit return type that downstream consumers can `isinstance`-check. The plan should pin the shape — e.g., `class MblCheckResult(TypedDict): results: dict[str, SegmentUtilisation]; citations: list[Citation]`.

11. **AC7 references "CHANGELOG entry in `docs/standards/calc-output-citation.md`" but the plan doesn't show that file's structure** (L236). File exists (verified) but the plan never quotes its current contents to confirm there's a CHANGELOG section to append to. If the file has no CHANGELOG, AC7 is unachievable without first creating one — which the plan doesn't enumerate in Files to Change.

12. **Off-by-one line-count claims throughout §Resource Intelligence Summary** (L15, L16, L17, L18). Plan reports `__init__.py` 21 / actual 20, `schema.py` 133 / actual 132, `registry.py` 59 / actual 58, `mooring_design.py` 455 / actual 454. Likely `wc -l` vs editor-trailing-line discrepancy. Minor on its own; combined with finding #1 it suggests the Resource Intelligence section was assembled from notes rather than direct re-verification.

13. **The vendored fixture's frontmatter matches the registry template, which is the validator's happy path — not surprising — but the plan never explicitly confirms the production-side validator will likewise succeed once `knowledge/wikis/engineering/wiki/standards/dnv-os-e301.md` is created.** The frontmatter on the production page must include `revision: 2021-07` (registry.py:29). If the production page is created with a different revision string, every prod call fail-closes with `reason=frontmatter_mismatch:revision:...`. The plan §Files to Change row "Create | knowledge/wikis/.../dnv-os-e301.md" mentions `revision: 2021-07` (L207) but doesn't propose a smoke test that runs `validate_citation()` against workspace-hub repo root before merging.
