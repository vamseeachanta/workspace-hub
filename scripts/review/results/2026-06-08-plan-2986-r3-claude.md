## Findings

1. **(MAJOR — blocker) Pseudocode sources lib files via relative path, before `SCRIPT_DIR` exists — reintroduces the exact CWD-fragility this plan exists to eliminate.** Plan §Pseudocode lines 187-195 order the body as:
   ```
   source scripts/lib/uv-env.sh        # line 188 — RELATIVE path
   source scripts/lib/uv-resolver.sh   # line 189 — RELATIVE path
   set SCRIPT_DIR from BASH_SOURCE     # line 190 — computed AFTER the sources
   ```
   The current real script (`validate-skills.sh:5-6`) deliberately computes `SCRIPT_DIR`/`REPO_ROOT` *first* so it is CWD-independent. As written, a direct caller invoking `bash /abs/path/scripts/skills/validate-skills.sh` from any CWD other than repo root hits `source scripts/lib/uv-env.sh` → file-not-found → under the script's `set -euo pipefail` the `source` builtin returns non-zero and the script aborts with bash's terse error — **not** the actionable resolver diagnostic the plan promises. The plan's stated beneficiary is "agent sessions or other automation" (Gaps §line 54) with unknown CWD, so this is a correctness break on the deliverable's own target path. Fix: compute `SCRIPT_DIR` first, then `source "$SCRIPT_DIR/../lib/uv-env.sh"` / `"$SCRIPT_DIR/../lib/uv-resolver.sh"` with absolute paths. Note the plan already uses `$SCRIPT_DIR/validate_skills_frontmatter.py` at line 195 — the asymmetry (absolute for the py file, relative for the sources) is the tell.

2. **(MINOR) Workflow path-filter update is under-specified — `paths:` is duplicated in both `pull_request` and `push` blocks.** Plan §Pseudocode lines 206-210 and Files-to-Change line 221 say "add path filters for scripts/lib/uv-resolver.sh, scripts/lib/uv-env.sh, and tests/cron/..." but `skills-validation.yml` carries two independent `paths:` lists (lines 7-12 for `pull_request`, 16-21 for `push`). If the implementer updates only one, CI coverage is asymmetric (e.g., a push to main touching only `uv-resolver.sh` would skip validation). AC line 250 should require both blocks be updated.

3. **(MINOR) `test_validate_skills_uses_uv_env_cache_default` tests the passthrough branch, not the default.** TDD table line 237 sets an *explicit* `UV_CACHE_DIR=<tmp-cache>` and asserts the fake `uv` receives it. But `uv_env_setup` (`uv-env.sh:19`) only *derives* the default (`$repo_root/.claude/state/uv-cache`) when `UV_CACHE_DIR` is **unset** — `${UV_CACHE_DIR:-...}`. By setting it explicitly the test never exercises default derivation, despite the name. Either rename to `..._honors_explicit_cache` or add a separate case with `UV_CACHE_DIR` unset asserting the repo-relative default.

4. **(MINOR) Minimal-PATH success/failure probes must scrub the inherited environment or the real CI `uv` leaks in.** Tests `test_validate_skills_resolves_uv_from_home_local_under_minimal_path` (line 233) and the empty-HOME failure case (line 236) rely on `PATH=/usr/bin:/bin` to force the candidate-loop/diagnostic path. In CI, `astral-sh/setup-uv@v4` (workflow line 34-35) puts `uv` on PATH; if the test subprocess inherits the parent env instead of passing a clean `env=` dict, `command -v uv` (resolver step 2) succeeds via the leaked CI uv and the test asserts nothing meaningful. The plan should state the probes launch with a scrubbed env, not just an overridden `PATH` string.
