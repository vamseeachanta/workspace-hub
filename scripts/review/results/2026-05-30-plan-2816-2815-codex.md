# Plan review artifact — 2816 2815 codex — 2026-05-30 (dispatched via submit-to-{codex,gemini}.sh)

### Verdict: MAJOR

### Summary
Plan is not approval-ready. The thin PowerShell-to-Bash delegation is a sound direction, but the plan relies on false existing behavior and under-specifies Windows runtime guarantees that will fail closed in the matrix.

### Issues Found
- MAJOR: The plan claims commit-on-change comes from the canonical collector, but origin/main `collect-equality.sh` only writes the state file and exits; it does not commit or push anything. See `scripts/readiness/collect-equality.sh:250-261` and the scheduled YAML action at `config/scheduled-tasks/schedule-tasks.yaml:35-40`, which only runs collector + matrix build. Failure scenario: Task Scheduler produces `.claude/state/equality-licensed-win-1.yaml` locally, but the report never reaches `origin/main`; the central matrix keeps using stale/missing Windows evidence while the live-validation checklist falsely says “commit-on-change fired.”
- MAJOR: Windows `python` is treated as a safe replacement for `uv`, but both the YAML renderer and matrix builder depend on PyYAML. `build-equality-matrix.py` imports `yaml` at `scripts/readiness/build-equality-matrix.py:22`, while the YAML entry currently declares `requires: [bash, python3, uv]` at `config/scheduled-tasks/schedule-tasks.yaml:34`. Failure scenario: licensed-win has system Python but no PyYAML outside the uv environment; `python -c` YAML parsing or `python scripts/readiness/build-equality-matrix.py` fails with `ModuleNotFoundError: yaml`, so no task registration or no matrix output. The plan needs an explicit Windows Python environment contract or a parser approach that does not depend on undeclared packages.
- MAJOR: Provenance freshness mitigation is not real enough for an approval gate. The collector intentionally never fetches, per `scripts/readiness/collect-equality.sh:152-157`, and `is_stale()` fails closed when `behind_main != 0`, `ahead_main != 0`, or `origin_ref_age_h` is outside 0-12h at `scripts/readiness/build-equality-matrix.py:139-161`. The plan says “ensure RepoSync” or “OR add git fetch,” but does not make either a required implementation/acceptance item for the wrapper. Failure scenario: Sunday 23:30 RepoSync fails, credentials expire, origin/main advances after sync, or FETCH_HEAD is older than 12h; Monday 04:30 EqualityReport runs successfully but every Windows cell grades `STALE-CHECKOUT`.
- MAJOR: The `ram_gib_min` restoration is not implementable as written. The plan lists `scripts/readiness/harness-config.yaml` as a #2816 file to modify and acceptance requires `ram_gib_min` restored, but the only valid value is deferred until “owner runs once.” Origin/main currently has no Windows RAM floor at `scripts/readiness/harness-config.yaml:56-87`. Failure scenario: implementer reaches the approved implementation step with no owner-confirmed value; either they guess and create false BELOW-BASELINE/false CONFORMS behavior, or they cannot satisfy the approved acceptance criteria. Split this into a two-step gate or mark the floor change as a follow-up after captured evidence.
- MINOR: The EQ override seam needs numeric allowlisting, not just happy-path tests. The YAML emitter writes `cores`, `ram_total_mib`, `ram_avail_mib`, and `disk_avail_gb` as unquoted scalars at `scripts/readiness/collect-equality.sh:215-217`. Failure scenario: a null/failed CIM query or inherited `EQ_*` value becomes `0`, empty, or malformed YAML rather than cleanly falling back to `unknown`; matrix grading then reports `BELOW-BASELINE` or parse failure instead of `MISSING-EVIDENCE`. Add explicit shell-side validation such as integer-only for counts/MiB/GiB and fallback to `unknown`.
- MINOR: The proposed Linux-runnable scheduler tests are mostly static string checks and do not cover cron-to-TaskScheduler translation semantics. The source schedule is cron day-of-week Monday at `config/scheduled-tasks/schedule-tasks.yaml:30-33`, while current Windows registration only supports daily `-At` triggers at `scripts/windows/setup-scheduler-tasks.ps1:41-65`. Failure scenario: renderer prints `04:30` but registers a daily task, wrong day, or wrong timezone interpretation; `test_ps1_no_hardcoded_equality_schedule` and `test_ps1_reads_schedule_yaml` still pass. Add a parser-level contract test for generated trigger metadata, not just absence/presence of strings.

### Suggestions
- Make commit/push behavior explicit in `equality-report.ps1` or add a separate state-commit step, with tests/assertions that the wrapper invokes it after collector + matrix success.
- Either use `uv run python` on Windows too, vendor a stdlib-only YAML extraction path for the small fields needed, or document/install the exact Python environment containing PyYAML.
- Require the wrapper to fetch before collection, or make freshness preflight fail fast before writing a report, then include `origin_ref_age_h` and `behind_main` checks in owner-run acceptance.
- Split RAM floor restoration into a follow-up issue after the first real `.ps1 -Stdout` evidence is pasted, unless the owner provides the value before approval.
- Add tests for bad `EQ_*` values: empty, non-numeric, newline, negative, and unit-suffixed values.

### Questions for Author
- Should the Windows scheduled run be responsible for committing/pushing equality state, or is another scheduled commit task intended to pick up `.claude/state` and `docs/reports` changes?
- Is PyYAML guaranteed in the system `python` on licensed-win-1/2, or should the plan preserve `uv`/managed Python for the matrix build?
