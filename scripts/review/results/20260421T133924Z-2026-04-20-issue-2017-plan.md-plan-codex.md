### Verdict: MAJOR

### Summary
The plan is materially stronger, but two core execution gates are still unsound: the transition dedup contract can erase legitimate repeat events, and the proposed `importorskip`/`xfail` strategy does not actually validate the state-machine contract at the current repo state. There is also a smaller scope/verification mismatch in how the xfail suite is supposed to be checked.

### Issues Found
- [P1] Critical: The v9 dedup key `(account_id, thread_id, from_state, to_state)` is too coarse for a queue that can legitimately revisit the same transition multiple times. A thread can cycle `awaiting-reply -> extracted -> awaiting-reply -> extracted` across multiple replies; under the current rule, later valid transitions would be dropped as duplicates. This is a behavioral correctness bug, not just a logging detail.
- [P1] Critical: The test strategy is internally inconsistent with the attested repo state. The plan now requires `pytest.importorskip('scripts.email.queue_state')` at module scope, but attested evidence shows `scripts/email/queue_state.py` is currently missing. That means `tests/email/test_state_machine_contract.py` will be skipped at collection time, not registered/executed as xfail, so the acceptance criterion claiming the contract tests exist as xfails is not actually satisfiable as written.
- [P2] Important: The acceptance check `uv run pytest tests/email/ --runxfail` is the wrong mechanism for proving the contract-test set is present. `--runxfail` turns xfails into normal tests; once the module exists, expected failures become hard failures, and before it exists the module-level `importorskip` skips the file entirely. This does not provide a stable pre-implementation gate for plan approval.
- [P3] Minor: Scope ownership is still slightly muddy in the prose. The Resource Intelligence section says the extract-first/delete-later pipeline is “this issue's deliverable,” while the Deliverable and Dependency Contract sections say pipeline orchestration belongs to #2024 and #2017 only ships contracts/config/tests. That should be normalized so downstream execution does not inherit the wrong scope boundary.

### Suggestions
- Replace transition dedup with an event identity that distinguishes true retries from later legitimate repeats, such as `(account_id, thread_id, from_state, to_state, triggering_message_id)` or a monotonic transition sequence derived from the triggering inbound/reply artifact.
- Choose one contract-test strategy and make the gate match it. If #2017 must ship executable xfail tests now, add a minimal importable stub for `scripts.email.queue_state`; if no stub is allowed, then mark the file as intentionally skipped until #2026 and stop claiming current xfail registration.
- Replace the `--runxfail` acceptance check with a collection/reporting gate, for example `pytest --collect-only`, a marker count assertion, or `pytest -rxXs` plus an explicit expected-skips/xfails contract.
- Tighten the scope wording so every section consistently states that #2017 delivers schemas/design/tests/config only, while #2024 owns orchestration and #2026 owns storage implementation.

### Questions for Author

- Do you want #2017 to ship an importable `queue_state` stub solely so the contract tests can exist as xfails now, or should the plan explicitly treat those tests as skipped-until-#2026 instead?
