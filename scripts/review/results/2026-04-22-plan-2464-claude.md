### Verdict: MINOR

### Summary
The plan delivers a clear curated/raw separation, a machine-checkable regression test, and a locked deletion list backed by independently verified evidence. Core weakness: the curated artifact it creates (`docs/ROUTING_INDEX.md`) depends on #2460's in-flight contract that has not yet landed, and the plan does not pre-commit the exact banner text for `docs/CONTENT_INDEX.md` nor the generator-side protection for that banner. These are tightenable — not disqualifying — hence MINOR.

### Issues Found

- [P2] Important — **Contract coupling without a merge gate.** The plan says `docs/ROUTING_INDEX.md` must include every section "required by #2460's final contract." #2460 is OPEN on the same nightly branch. If #2460 lands a new required section after this plan starts execution, the regression test `test_routing_index_exists_and_has_required_sections` will still pass (its heading list is hardcoded here), silently hiding the contract drift. Fix: either pin the required-sections list as a shared constant consumed by both plans, or require the #2460 contract file to be merged to `main` before this plan executes (not just to the shared nightly branch).
- [P2] Important — **Exact banner text for `docs/CONTENT_INDEX.md` is not locked.** The plan specifies two substrings (`"machine-generated"` and `"not a curated routing index"`) but not the banner's full wording, header level, sentinel marker, or position relative to the generator's write window. Without a locked block, the executor has free rein, the test is satisfied by trivially-weak banners, and the "generator-side check in a follow-on" risk mitigation is not auditable.
- [P3] Minor — **`test_root_has_no_routing_noise` is pattern-blind.** It tests that the ten banned filenames are absent. It does NOT catch the analogous failure mode — someone committing a new `**Deliverable:**` or `**Source**` fragment. The plan explicitly locks the list to avoid scope creep (defensible), but the residual risk of re-introducing the same class of noise under a new name should be acknowledged in Risks.
- [P3] Minor — **`docs/plans/README.md` is not updated by this plan.** The plan is intentionally silent on the plan index update because write boundaries forbid editing it. That is correct under the worker's constraints but leaves a knowable gap: the newly-created plan will not appear in the canonical index until a follow-on commits it. The plan should acknowledge this and name the follow-on step (or pre-seed the line for the orchestrator to add).
- [P3] Minor — **Evidence count correct but thinly cross-linked.** The Evidence section names ≥3 distinct sources, but the scorecard line-number excerpt uses `sed -n 86,100p` without re-asserting the file SHA. If the scorecard is later edited, the excerpt no longer validates. Cheap fix: cite `git log -1 --format=%H docs/reports/2026-04-22-tier-1-indexing-scorecard.md` alongside the excerpt.

### Suggestions

- Lock the exact `docs/CONTENT_INDEX.md` banner in the plan as a fenced block so reviewers can diff it directly at execution time. Include an HTML comment sentinel like `<!-- tier1-raw-inventory-banner: do not regenerate -->` that `scripts/search/build_content_index.py` can grep for.
- Extend `test_root_has_no_routing_noise` with a second assertion: root filenames should not match a pattern like `^\*{2,}` (stray markdown-header fragments). This does NOT broaden the deletion set in this plan — it only prevents regression of the class.
- Add a plan-file entry to the Risks section: "If #2460 contract changes required sections mid-flight, this plan must rebase the heading list in `test_routing_index_exists_and_has_required_sections`."
- State explicitly whether `docs/RAW_CONTENT_INVENTORY.md` rename (Open Question) is deferred to a follow-on or closed as "won't do." Open questions without dispositions drift.

### Questions for Author

- Is the #2460 contract expected to merge to `main` before this plan executes, or will they land together via the same nightly merge? The plan hedges; the answer determines whether the contract-drift test needs shared-constant enforcement.
- Are the ~25 non-scorecard root artifacts (`draft_*.md`, `gmail_*.md`, `issue-1839-*`, etc.) tracked in any follow-on issue? If yes, link it in "Out of scope." If no, create one and link it to avoid re-raising the cleanup request on every future tier-1 audit.
- For the regression test, should it skip cleanly if `docs/BUSINESS_BRAIN.md` changes the tier-1 repo set, or fail-closed? Fail-closed is safer for contract enforcement; the plan is silent.
