## MINOR findings (would not block approval but improve plan quality)

### MINOR-1: Row-count target is poorly grounded

**Evidence:** Plan claims target = 2,159 rows = "2,211 baseline – ~52 dedup overlap". The 52 overlap number is invented (8 of 48 vendor rows are Noble names also in WAR ≠ 52).

**Correction:** Target should be derived empirically: run the existing script, observe row count, that's the target. Don't pre-commit to a number the plan can't justify.

### MINOR-2: Validator-tolerance worry is speculative

**Evidence:** Plan §"Risks" worries the validator may reject WAR rows missing hull dimensions. But `bsee_war=1` precedence in dedup means vendor rows (with hull dims) win on collision; non-colliding WAR rows have no dims and need their own validator tolerance. The plan should read `validator.py` and answer this empirically, not speculate.

### MINOR-3: "OPERATOR field semantic mismatch" risk is real but mitigation is wrong

**Evidence:** Plan correctly identifies that WAR's `OPERATOR` is lease-holder, not rig contractor. But mitigation says "Setting `OWNER = WAR.OPERATOR` is semantically incorrect but consistent with the prior baseline." That's begging the question — the prior baseline may itself have been semantically wrong. Correct mitigation: set `OWNER=None` for WAR rows OR add a new field `LEASE_HOLDER` and leave `OWNER=None` for WAR-only rows.
