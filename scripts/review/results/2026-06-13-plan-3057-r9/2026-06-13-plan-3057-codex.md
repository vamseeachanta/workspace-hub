## Findings
1. Plan has an unresolved setup-cron selection contradiction. `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:347` says setup-cron will call `select_tasks(..., roles=[], machine_id_or_tokens=context.machine_tokens)`, which is machine-token-only. But `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:462` requires cross-path parity “through role and machine-token paths,” and line 590 claims selection is centralized in the shared renderer/selector. Current `scripts/cron/setup-cron.sh:117-122` only selects tasks whose `machines:` intersect machine tokens. The plan does not specify whether setup-cron should remain machine-pin-only or gain role selection, so the parity test is ambiguous and could either fail or silently widen setup-cron’s install surface.

2. The `notification-purge` dedupe plan is under-specified against existing classifier ordering. `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:434` says to “Remove or narrow” the preserved-local exception, but `cron_transaction.classify_line` checks external/preserved fingerprints before catalog commands at `scripts/cron/cron_transaction.py:191-198`. Current `config/workstations/harness-state-classes.yaml:120-130` still matches `notification-purge` by `find logs/notifications/` and `-delete`, and current `tests/cron/test_a1_preserved.py:60-63` asserts that line classifies as `preserved_external`. The planned test wording at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:441` only says “remain non-uncataloged,” which would still pass if the line remains preserved instead of catalog-owned. That is insufficient for acceptance line 492, which requires the out-of-block duplicate to be deduped and exactly one managed `notification-purge` line to remain.

3. The plan modifies `cron-health-check.sh` but ignores an existing hardcoded user-local `uv` path in the same script. `scripts/monitoring/cron-health-check.sh:53` and `scripts/monitoring/cron-health-check.sh:101` invoke `/home/vamsee/.local/bin/uv`, despite the script already exporting `$HOME/.local/bin` into `PATH` at line 16. The plan’s cron-health changes at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:437` and shell acceptance at lines 502-508 do not require removing or testing this hardcoded path. That leaves the health check non-portable across the very machine/cron context the plan is hardening.
