### claude

- **The notification-purge fingerprint removal rests on an unverified byte-exact-match premise, and the plan presents no live-crontab evidence to close it.** Files to Change row for `config/workstations/harness-state-classes.yaml` plus Acceptance Criterion "exactly one managed `notification-purge` line appears in `plan['new_text']`" require *removing* the `preserved_local` fingerprint so the out-of-block line classifies `cataloged` instead of `preserved_external` (necessary because `classify_line` checks `preserved_external` before `cataloged` at `cron_transaction.py:193-198` — keeping the fingerprint yields a preserved copy **plus** a managed copy = two lines). But that fingerprint was deliberately written loose: its own note (`harness-state-classes.yaml:122-128`) says it matches only "the find target + the `-delete` action, **not the cd path or stderr redirect**," and that the line "Appears DUPLICATED in a1's crontab." Replacing a loose ownership fingerprint with strict full-command substring matching only works if the live line is a byte-exact superstring of the raw or rendered catalog command. The plan's reproduction probe (lines 135-142) greps for `WORKSPACE_HUB|LOG|REPO_ECOSYSTEM_HYGIENE_|repo-ecosystem-hygiene|cron-health` — it **never shows the live notification-purge line(s)**. The only evidence the line matches is the hand-built fixture at `tests/cron/test_a1_preserved.py:42-45` — i.e., the acceptance is validated against a fixture, not reality (the exact trap the review prompt flags). If either live copy diverged from that fixture (different stderr redirect, schedule, `-mtime`, quoting, or a trailing `# comment`), it classifies `uncataloged` → `plan_cutover` aborts fail-closed → Acceptance Criterion #1 (`--json` includes non-abort `new_text`) fails against the real crontab. Blast radius is bounded (cron_apply is manual, not auto-scheduled, and fails closed safely), but the plan removes a working safety net on the unproven assumption that the live line is byte-stable.
- **The mandated "shared raw+rendered catalog-key builder" has no designated home module in the Artifact Map or Files-to-Change.** Acceptance Criterion "`cron-audit.py` and `cron_apply.py` use the same shared raw+rendered key builder and agree on cataloged vs preserved/external classification" and the `cron-audit.py` Files-to-Change row ("Use the same shared raw+rendered catalog-key builder as transactional cutover") require a single canonical key builder. But the Artifact Map describes `scripts/cron/cron_render.py` only as "machine context, hostname-first effective `schedule_by_machine` selection, `$WORKSPACE_HUB`, `$LOG`" — *rendering*, not *catalog-key building* — and the `cron_transaction.py` Files-to-Change row lists only `select_tasks` extension + env-line preservation. No row assigns the key builder a home. The natural home is `cron_transaction.py` (already imported by both `cron_apply.py:45-49` and `cron-audit.py:56`), but the plan never says so, leaving the implementer free to re-duplicate the very divergence this issue is meant to remove.
- **Resource-intel mis-frames the catalog-key status quo: the two builders already diverge today.** The plan's Gaps section (line 47) and resource-intel frame `[:60]` truncation as *the* catalog-key behavior. In fact `cron_apply.py:129` uses `cmd.strip()[:60]`, but `cron-audit.py`'s `stable_command_fragment` (`scripts/cron/cron-audit.py:72-80`) already "Falls back to the whole single-spaced command when no script path is present." So `cron-audit` and `cron_apply` produce **different** fallback keys for `notification-purge` *right now* — the audit path already full-command-matches it while the apply path truncates. The plan's premise (uniform `[:60]`) understates the existing inconsistency; the intel should state that audit already uses full-command and only `cron_apply` truncates.
- **`cron_context_for_machine`'s hostname selection predicate is underspecified for non-current-host rendering.** Pseudocode line 325: "`hostname_short = live hostname when rendering for the current host, else machine.hostname`." The plan never defines how the renderer decides "rendering for the current host." For cron_apply's real use (it only ever writes *this* host's crontab) this is always the current host, so it's benign in practice — but the contract as written is ambiguous, and a future caller passing `--machine <other-host>` would get a different precedence token than setup-cron would on that host. Should be pinned to "cron_apply always renders for the live host; `machine.hostname` is the fallback only when the live hostname is unavailable."
- **The post-cutover preservation recheck site is not explicitly threaded with the new union keys.** `cron_apply.py:190-193` recomputes `need` via `ct.classify_line(ln, cat_cmds, ext_fps)` using the same `cat_cmds`. After the fallback-key change, this site must use the identical raw+rendered union as `plan_cutover`, or the post-write assertion could disagree with the plan. The `cron_apply.py` Files-to-Change row implies it ("use shared full fallback command keys") but does not call out this specific recheck site, which is easy to miss since it lives outside `plan_cutover`.

### codex

- Plan has an unresolved setup-cron selection contradiction. `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:347` says setup-cron will call `select_tasks(..., roles=[], machine_id_or_tokens=context.machine_tokens)`, which is machine-token-only. But `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:462` requires cross-path parity “through role and machine-token paths,” and line 590 claims selection is centralized in the shared renderer/selector. Current `scripts/cron/setup-cron.sh:117-122` only selects tasks whose `machines:` intersect machine tokens. The plan does not specify whether setup-cron should remain machine-pin-only or gain role selection, so the parity test is ambiguous and could either fail or silently widen setup-cron’s install surface.
- The `notification-purge` dedupe plan is under-specified against existing classifier ordering. `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:434` says to “Remove or narrow” the preserved-local exception, but `cron_transaction.classify_line` checks external/preserved fingerprints before catalog commands at `scripts/cron/cron_transaction.py:191-198`. Current `config/workstations/harness-state-classes.yaml:120-130` still matches `notification-purge` by `find logs/notifications/` and `-delete`, and current `tests/cron/test_a1_preserved.py:60-63` asserts that line classifies as `preserved_external`. The planned test wording at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:441` only says “remain non-uncataloged,” which would still pass if the line remains preserved instead of catalog-owned. That is insufficient for acceptance line 492, which requires the out-of-block duplicate to be deduped and exactly one managed `notification-purge` line to remain.
- The plan modifies `cron-health-check.sh` but ignores an existing hardcoded user-local `uv` path in the same script. `scripts/monitoring/cron-health-check.sh:53` and `scripts/monitoring/cron-health-check.sh:101` invoke `/home/vamsee/.local/bin/uv`, despite the script already exporting `$HOME/.local/bin` into `PATH` at line 16. The plan’s cron-health changes at `docs/plans/2026-06-13-issue-3057-cron-hygiene-hardening.md:437` and shell acceptance at lines 502-508 do not require removing or testing this hardcoded path. That leaves the health check non-portable across the very machine/cron context the plan is hardening.
