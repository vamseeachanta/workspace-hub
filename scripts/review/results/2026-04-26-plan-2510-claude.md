## Findings

1. **GDSFactory import-path is pinned in §Round-Trip but contradicted in §Scope and §Pseudocode.** Line 148 (Round-Trip): "Read-back must use GDSFactory 9.40.2 with primary API `from gdsfactory.read import import_gds`; if that import path is unavailable in the pinned version, implementation must stop and revise the plan rather than guessing a new API surface." Line 121 (Scope): "Import/read-back of the generated GDS using an open reader (`gdsfactory.import_gds`, KLayout Python, or another explicitly documented open dependency)…" Line 183 (Pseudocode): "read chip_package_demo.gds back through `gdsfactory.import_gds` or another named open reader". `gdsfactory.import_gds` is a public re-export whose stability across 9.x is not part of the pinned-API rule; `from gdsfactory.read import import_gds` is the qualified path. The pseudocode also adds an "or another named open reader" escape hatch that directly contradicts the Round-Trip contract's stop-as-blocked rule. An implementation following the pseudocode will satisfy the plan while violating the pinned-surface contract. r3 Claude Finding 4 and Codex r3 Finding-equivalent demanded a pinned API; the patch only pinned it in one section.

2. **Round-trip count rule is internally inconsistent.** Line 152: "Imported geometry must be flattened or recursively traversed before counting; tests must state which mode was used. Per-layer **flattened** polygon counts must be at least the generated counts for required layers: substrate, die, bump/pad, route/keepout." The first sentence permits two modes (`flattened` OR `recursively traversed`). The second sentence then asserts a count rule expressed only in flattened terms. If the implementation picks `recursively traversed`, the count rule has no defined semantics. Codex r3 Finding 5 explicitly said "GDS read-back counting needs an explicit flatten/recursive traversal policy **before implementation**"; the patch left the choice to implementation and added a count rule that only works in one of the two permitted modes.

3. **§Acceptance Criteria line 241 closeout policy uses "valid review" without definition.** "closeout requires no unresolved MAJOR from any provider that returns a **valid review**". The plan does not define what counts as valid: 0-byte canonical file (the current state for all three providers), an empty `.md` plus a non-empty `.err`, an UNAVAILABLE verdict, or a structurally non-conforming output that lacks the four required sections. Without a definition, closeout is not falsifiable. r3 Claude Finding 12 demanded a non-circular AC; the new wording replaces circularity with vagueness — both fail the "Bad findings" criterion in the review prompt.

4. **§Files to Change line 210 places review-artifact backfill in the implementation phase.** "Create/update `scripts/review/results/2026-04-26-plan-2510-{claude,codex,gemini}.md` plus archived `-r1/-r2/-r3` snapshots — Adversarial plan-review artifacts with stale/empty outputs either replaced by valid content or explicitly marked UNAVAILABLE". This row sits in the same Files-to-Change table as `scripts/semiconductor/layout_cad_demo.py` and `tests/semiconductor/test_layout_cad_demo.py` (lines 206–207), implying review backfill is part of implementation. It is not — review backfill must complete before `status:plan-approved`. Mixing planning-phase and implementation-phase artifacts in one table lets a downstream batch agent treat the review backfill as a normal implementation TODO.

The plan does not state where r4 outputs land — `*-r4.md` archive only, the canonical `*.md` path only, or both — and does not state whether the canonical 0-byte files (which Claude r3 Finding 1 flagged for r2) are filled now (during r4) or later. 9. **`test_outputs_are_deterministic_across_runs` (line 224) does not gate on the new "stop as blocked" pinning rule.** The Determinism Contract (line 293) says implementation must stop if pinning fails. But the test description says "repeat runs produce identical deterministic artifact hashes under the **pinned GDS timestamp policy**". If pinning silently fails (e.g., kfactory writer ignores the timestamp argument), the test will detect the hash mismatch only at test time, not at implementation time. There's no test that explicitly verifies the pinning hook took effect, e.g., reading the GDSII header bytes back and asserting `BGNLIB == fixed UTC tuple`. 10. **§Risks line 302 commits to a CI-cost policy that pytest cannot enforce.** "execution should run the full test suite once per validation stage, not spawn repeated per-test `uv run --with` processes". `uv run --with gdsfactory==9.40.2 pytest tests/semiconductor/test_layout_cad_demo.py -q` spawns a single resolution event for that invocation, but if the test file imports `gdsfactory` lazily inside fixtures and tests, pytest will not re-spawn `uv run` per test. The "policy" is true by default — but if any test module is moved or split, or if `pytest -k` invocations are issued, the wording does not prevent multi-resolve cost. The "decision" is policy advice, not a contract check.
