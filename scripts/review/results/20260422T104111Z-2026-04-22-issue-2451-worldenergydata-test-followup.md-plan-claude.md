### Verdict: MAJOR

### Summary
Strong evidence-first plan with well-integrated adversarial feedback across three failure clusters, but still carries a self-acknowledged Wave 3 MAJOR verdict and draft status. Cluster A has an internal tension — if `--all-extras` already installs `pytest-benchmark` (plan's own evidence), A1a workflow edit is near-impossible to justify, yet A1b (default) is under-specified relative to A1a. Entry-point discovery for C-repoint should have been completed in planning rather than deferred, and the cross-repo execution contract (workspace-hub plan → worldenergydata fix) needs a more explicit two-branch/two-PR description.

### Issues Found
- [P1] Cluster A internal contradiction: plan proves `dev` extra includes pytest-benchmark AND CI uses `--all-extras`, which together make A1a (workflow edit) almost certainly a no-op. A1b should be promoted from 'preferred starting branch' to the near-exclusive path, and A1a should be demoted from a peer branch to an edge-case fallback that fires only on explicit install-log evidence of absence.
- [P1] A1b path is under-specified for something designated the default executable branch. It enumerates three diagnostic surfaces to inspect but does not name concrete remediation options comparable in specificity to A1a. If A1b is the default, it needs at least one concrete commit-level remediation example, not just 'diagnose.'
- [P1] The plan's own Acceptance Criteria includes 'Adversarial review ... returns APPROVE or MINOR,' and the plan self-reports Wave 3 = MAJOR. Status=draft is consistent with that, but the gate should be satisfied (Wave 4 APPROVE/MINOR) before seeking plan-review label, otherwise the approval path is circular.
- [P2] Duplicate pytest-benchmark declaration (`[project.optional-dependencies] dev` at line 68 AND `[dependency-groups] benchmark` at line 215) is itself a strong candidate A1b root cause (plugin-registration collision or env-isolation conflict) but is not listed among A1b's three diagnostic surfaces. Should be called out explicitly.
- [P2] Cluster C entry-point discovery is deferred to execution Step 0d when it belongs in resource intelligence. The production docstring literally says 'use the financial module at...' — planning should have resolved that path (grep for `src/worldenergydata/**/financial*` or equivalent) so the owner can make an informed C-skip-vs-C-repoint call at approval time rather than during implementation.
- [P2] Cross-repo execution contract is sketched but not locked. The plan says fixes land on a worldenergydata branch 'recommended nightly/2451-worldenergydata' and 'merges independently of workspace-hub planning commits' — but does not explicitly spell out: two separate PRs, which PR gates what, how #2433's landed state is verified at rebase, and how review artifacts pinned at SHA 0f8ac026 remain valid if worldenergydata main has advanced.
- [P2] TDD Test List mixes real verification tests with diagnostic steps (e.g., `verify_benchmark_root_cause_confirmed` and `verify_local_all_extras_provenance` are pre-implementation diagnostics, not post-implementation verifications). This confuses the GREEN check — diagnostics belong in Pseudocode Step 0, not in the test list.
- [P3] `verify_ci_residual_failure_set` has a non-mechanical pass criterion ('any remaining failures are explicitly outside this issue's scope'). As stated, it requires human judgment to pass. Either narrow to a concrete grep-for-three-signatures check or move to Acceptance Criteria as a review-time assertion.
- [P3] Unverified claims (no `## Attested Evidence` block provided): SHA `0f8ac026`, issue states for #2451/#2433/#2452/#2424, CI run id `24757842396`, existence of listed files under `/mnt/local-analysis/worktrees/worldenergydata-2433`, and the live pytest plugin list. Dispatcher should run `scripts/review/attest-plan-claims.sh` before the next review wave.
- [P3] README.md deferral is mentioned in Files to Change and Risks, but the plan does not name the downstream run/issue that owns the consolidation edit. Risk of orphaned deferral if that tracking is not explicit.
- [P3] B1 fixture body is listed as 'verbatim' from lines 105-117 with specific constant values recorded inline. If the source fixture changes between planning and execution, that inline snapshot silently drifts from source. Either hash-capture or explicitly direct the implementer to re-read from file at edit time (the plan does both partly — could be tightened).

### Suggestions
- Rewrite Cluster A decision matrix with A1b as the primary path and A1a as a narrow conditional-fallback, not co-equal branches. Add the duplicate-declaration hypothesis to A1b's diagnostic surface list.
- Complete NPV-entry-point discovery during this planning pass (grep for `financial` under `src/worldenergydata/`, inspect the docstring truncation, record result) so the C-skip vs C-repoint decision can be made at approval rather than execution.
- Add an explicit 'Cross-Repo Execution Contract' subsection under Deliverable that spells out: (a) workspace-hub PR content (plan + approval marker only), (b) worldenergydata PR content (fix), (c) rebase protocol if worldenergydata main has advanced past `0f8ac026`, (d) how review artifacts remain valid.
- Move diagnostic steps (`verify_benchmark_root_cause_confirmed`, `verify_local_all_extras_provenance`, `verify_cashflow_fixture_consumers`) out of the TDD Test List into Pseudocode Step 0. Keep only post-implementation green checks in the test list.
- Narrow `verify_ci_residual_failure_set` to a mechanical check — grep-count of the three exact failure signatures in CI log should be zero. Judgments about 'scope' belong in the plan-review artifact, not in automated verification.
- Run `scripts/review/attest-plan-claims.sh` at the current commit before the next adversarial review wave so subsequent reviews can stop flagging the same unverified issue/file claims.
- Name the downstream consolidation run/issue that owns the `docs/plans/README.md` row add, so the deferral doesn't become orphaned.
- Resolve the Wave 3 → Wave 4 gate before labeling `status:plan-review`. Current self-verdict of MAJOR and draft status is internally consistent but means the plan's own APPROVE/MINOR acceptance criterion is not yet satisfied.
