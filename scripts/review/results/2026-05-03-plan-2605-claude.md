## Defect 2 — `test_overwrite_when_requested` is under-asserting; removing `get_ship` cements the gap (MINOR)

**Claim under attack:** The plan flags this as "Open Q2" and defers, but doesn't assess whether deferring is correct.

**Defect:** Read the test carefully:
```python
def test_overwrite_when_requested(self):
    from digitalmodel.naval_architecture.ship_data import (
        register_fleet_vessels,
        get_ship,    # ← about to be removed
    )
    register_fleet_vessels([THIALF_RECORD])
    added, skipped = register_fleet_vessels([THIALF_RECORD], overwrite=True)
    assert added == 1
    assert skipped == 0
```
The test name is `test_overwrite_when_requested` but the assertions only verify the **return-value counters** of the second call. Nothing verifies that the underlying `_SHIPS` dict actually got mutated. If `register_fleet_vessels(overwrite=True)` were buggy and silently no-oped while still returning `added=1, skipped=0`, this test would pass green. The unused `get_ship` import is **the fingerprint of an abandoned assertion** — the author was about to write `assert get_ship("THIALF")[...] == ...` and didn't.

**Once we ruff-fix this away,** future maintainers reading the cleaned test won't even see the breadcrumb that someone was going to verify post-overwrite state. The test's name will continue to lie.

**Severity:** MINOR for the lint PR (the lint PR's job is not to fix coverage). But this fact MUST be captured in a follow-up issue, not lost.

**Recommended fix:** Plan must add an acceptance criterion: "File a follow-up issue titled 'test_overwrite_when_requested under-asserts post-overwrite state' before closing #2605." The plan currently says "Recommendation: file a separate follow-up issue" but does not commit to it as a gate.
