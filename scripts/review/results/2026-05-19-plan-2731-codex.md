## Findings
1. Plan omits required `#2731` named-path classifications. Issue `#2731` requires inventory and decisions for `/mnt/ace/rock-oil-field`, `/mnt/ace/client_projects`, `/mnt/ace/doris`, `/mnt/ace/acma-projects`, `/mnt/ace/frontierdeepwater`, `/mnt/ace/saipem`, `/mnt/ace/llm-wiki`, `/mnt/ace/llm-wiki-archive`, `/mnt/ace/digitalmodel/llm-wiki`, and planned private wiki repos. The plan’s `TDD Test List` only asserts generic classes like raw source, standards/reference, repo overflow, staging, alias, and legacy, so implementation could pass without classifying the issue’s concrete required paths.

2. Plan fails the issue’s naming-mismatch acceptance criteria. Issue `#2731` explicitly requires resolving or deferring `client_projects` vs `client-projects` and `frontierdeepwater` vs `frontier-deepwater`. The plan’s `Acceptance Criteria` do not mention either mismatch, and the `TDD Test List` has no test for these path-name decisions.

3. Plan delegates too much of `#2731` into `#2732`. The plan’s `Documents consulted` says `#2732` is the sibling for canonical first/second-level mount and folder taxonomy and that this plan will avoid duplicating that full taxonomy. But `#2731` itself requires concrete inventory/classification of active repos, private/public `llm-wiki` repos, raw/client/source roots, aliases, and transformation/promotion transactions. The current plan can satisfy a high-level contract while leaving required `#2731` path-level decisions unresolved.

4. Plan’s `docs/CONTENT_INDEX.md` premise is not verified against pushed state. The plan claims `docs/CONTENT_INDEX.md` contains stale nested path examples for `digitalmodel`, `worldenergydata`, and `assetutilities`; GitHub fetch returned empty content for `docs/CONTENT_INDEX.md`, and GitHub searches for those exact nested paths returned zero results. The planned update and test target may therefore be a false or local-only premise.

5. Plan’s validation does not actually “block future docs from reintroducing nested checkout references.” The `Gaps identified` section says no validation currently blocks future nested checkout references, but `test_selected_docs_do_not_reintroduce_unannotated_nested_repo_paths` only scans selected docs. The plan does not require a CI-enforced checker, pre-commit hook, or broad scan over future documentation paths, and the scanner is marked optional in `Artifact Map` / `Files to Change`.

6. Plan does not satisfy `#2731` deliverable for an inventory report. Issue `#2731` required `docs/reports/YYYY-MM-DD-data-location-inventory.md` or equivalent with runtime evidence and examples. The plan substitutes `docs/reports/issue-2731-implementation-notes.html`, whose stated purpose is design decisions, deviations, tradeoffs, and open questions. The acceptance criteria require live probe notes, but not a complete inventory report covering every named path and transaction candidate.

7. Plan’s source-root count is stale or inconsistent. `Resource Intelligence Summary` says `data/document-index/mounted-source-registry.yaml` models roots and the distinct source count treats it as one source, while `docs/document-intelligence/data-intelligence-map.md` says mounted sources are “7 source definitions” and later “8 sources defined”; the actual fetched `data/document-index/mounted-source-registry.yaml` includes more than those counts. The plan should not build contract logic from uncorrected registry-count assumptions.

8. Plan does not include follow-up issue drafts for actual moves or unresolved classifications. Issue `#2731` required follow-up issue drafts for movement or bulk migration work that should not be bundled into this planning issue. The plan’s `Acceptance Criteria` only requires future transaction records with child-plan requirement; it does not require drafting/linking follow-up GitHub issues for move/defer decisions.
