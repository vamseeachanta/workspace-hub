## Findings

1. **PyYAML is the proxy, but the only acceptance criterion that tests the *actual* failing consumer is the weakest in the plan.** The issue's defect (`scripts/review/results/2026-06-08-plan-2975-claude.md` per plan line 38) is a *Go* YAML loader error (`invalid YAML: mapping values are not allowed in this context`), not PyYAML. The plan acknowledges this (line 246) and adds AC line 300, but that criterion — "either by rerunning a Codex-only plan review **or** by a minimal `codex exec` invocation that previously loaded the same skill surface" — has no falsifiable pass condition (what output proves the skill *loaded*?). Compounding it, project memory [[feedback_codex_exec_cpu_starved_in_claude_sandbox]] records that nested `codex exec` is CPU-starved and buffer-lossy under Claude, so the consumer-level check is both vaguely specified and operationally fragile. Mitigant: the specific fix (quoting a colon) is trivially valid in *every* YAML parser, so real PyYAML-pass/Go-fail divergence on this change is near-zero. MINOR — tighten AC line 300 to name a concrete command and a concrete success signal.

2. **The validator's scope silently expands CI enforcement to 2,100 archived files; the plan never decides whether `_archive/` belongs in scope.** The validator runs against all of `.claude/skills` (verified: `_archive`=2100 of 3111, 67% of the tree). Removing `continue-on-error: true` (plan's recommendation, line 339) makes every archived skill load-bearing for CI green. The plan's open question (lines 337-339) debates soft-vs-hard-fail but never addresses whether a *graveyard* directory should gate review-dispatch CI. They all pass today (verified), so it's not a correctness defect, but it's an unstated fragility: a future edit under `_archive/` could red the build for a reason unrelated to live skills. MINOR — add an explicit in-scope/exclude decision for `_archive/` (and `_internal/`) to the open questions.

3. **The "canonical" frontmatter splitter is overstated as a faithful loader proxy.** Plan lines 238-244 define the splitter as "find the next line whose stripped value equals `---`." A frontmatter value containing a lone `---` line (e.g. a `description: |` literal block) would be truncated early and mis-parsed or falsely passed. This is conservative and matches all 3,111 current files (verified), but the plan calls it "canonical" / a proxy for "the dispatch-time skill loaders" (line 246) without evidence that the real Claude/Codex loaders extract frontmatter the same way. MINOR — downgrade the language from "canonical" to "conservative heuristic, validated against current inventory."

4. **Plan header review-artifact paths (line 9) don't match the artifacts actually produced.** Line 9 names `scripts/review/results/2026-06-08-plan-2981-{claude,codex,gemini}.md`, but the review run produced r1/r2-suffixed files (`...-r1-claude.md`, `...-r2-claude.md`, present in the working tree per git status). Non-load-bearing, but the header points reviewers at the wrong filenames. MINOR — reconcile the header to the real artifact set.

5. **No finding (verified clean):** the `UV_CACHE_DIR=.claude/state/uv-cache` choice is git-safe (ignored by `.gitignore:170` — I assumed it might pollute the tree and was wrong); the RED/GREEN sequencing is coherent (current grep validator returns exit 0 on an unquoted-colon fixture, so `test_validator_fails_on_unquoted_colon_description` genuinely fails pre-implementation); the flywheel-closeout fix preserves all 5 trigger phrases and needs no quote-escaping; CI `uv` setup has in-repo precedent; the empty/non-string field tests (`name: 123`, `description: false/[]/""`) are well-formed against `isinstance(v, str)`. These were checked and found sound.
