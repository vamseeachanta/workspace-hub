### Verdict: APPROVE

### Summary
Plan v5 is a mature, contract-first design for an email-as-queue workflow that has already absorbed three rounds of adversarial review. The state machine, concurrency model, ownership split across #2017/#2024/#2026, and TDD list are internally consistent, and identified risks (Gmail scope, trash-purge, volume growth) are explicitly deferred with accepted boundaries. Remaining concerns are refinements, not blockers.

### Issues Found
- [P2] Important: Acceptance criterion says state-machine xfail tests flip when #2024 lands, but the v5 revision note and Dependency Contract assign queue-state storage (the thing under test) to #2026. The acceptance bullet contradicts the ownership matrix.
- [P2] Important: Composite key (account_id, thread_id) is declared, but the snapshot file shape is never specified. Pseudocode accesses entries as scalars (entry.completed_at, prior.state) without showing how the YAML snapshot is keyed, leaving room for #2026 to invent collision-prone storage.
- [P2] Important: Freshness check uses os.stat(log).st_size vs last_log_byte_offset for O(1) staleness. This shortcut breaks silently under any future compaction, which the Risks section already anticipates. The contract should explicitly invalidate byte-offset freshness on compaction or switch to a monotonic counter.
- [P3] Minor: ISO-8601 UTC with Z suffix is mandated, but no TDD entry asserts schema rejection of non-UTC timestamps.
- [P3] Minor: daily_sweep reads the snapshot then calls transition(); a concurrent inbound append between read and write could cause sweep to act on stale state. Sweep should re-validate snapshot freshness under the sweep lockfile.
- [P3] Minor: writer_identity.boot_id is Linux-specific; macOS/Windows fallback is unspecified.
- [P3] Minor: test_purged_treated_as_new_if_extraction_missing asserts the fresh-inbound outcome but does not assert emission of the extraction_missing_on_reactivation event to both queue-state.jsonl and queue-learning-log.jsonl, leaving the v4 contract unverified.
- [P3] Minor: 'No regression in existing suite' has no pinned baseline; if suite is currently red, the check is meaningless.
- [P3] Minor: Risks section cites a 1s snapshot-rebuild threshold for triggering compaction, but no benchmark test is listed to measure it.

### Suggestions
- Fix the xfail ownership line in Acceptance Criteria to read 'pending #2026' so it matches the Dependency Contract and v5 revision #2.
- Pin the snapshot on-disk shape in docs/design/email-queue-state-schema.yaml — e.g., top-level map keyed by '{account_id}::{thread_id}' — so #2026 implements composite keying correctly on the first pass.
- Add a compaction-aware freshness clause to D1 and a test (test_snapshot_rebuild_after_compaction) exercising it.
- Add test_schema_rejects_non_utc_timestamp to the Config validity block.
- Require daily_sweep to re-check meta-file freshness under the sweep lockfile before any transition, to close the read-then-write race.
- Specify a portable writer_identity fallback: boot_id on Linux, kern.bootsessionuuid on macOS, or a UUID cached to <repo>/.locks/process-id elsewhere.
- Strengthen test_purged_treated_as_new_if_extraction_missing to assert both JSONL event emissions AND the fresh-inbound treatment.
- Capture the baseline pass count for 'uv run pytest' (N tests passing at SHA X) so the no-regression criterion is falsifiable.
- Add a snapshot-rebuild latency benchmark test so the 1s compaction threshold is observable in CI.
