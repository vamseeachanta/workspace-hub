## Verdict

**MAJOR** — the split is directionally correct, but the repo-verified seams show a mixed-schema `--resume` path and stale-carryover risk. A one-line `enrich_one` patch is insufficient unless resume/carryover semantics are updated too.

## Retrieval Adequacy

The source review is grounded in the listed scripts. The plan file itself could not be verified from repo/GitHub in this session, so bundle-specific claims such as "11 tests," maturity YAML edits, registry edits, and runtime estimates are unverified.

## Root-Cause Fidelity

The conflation originates in `enrich_one`, which currently writes only `content_type` and `summary_done` (`enrich-summary-metadata.py:87-94`). Splitting the booleans there fixes the derivation point, but not stale state. Phase A carryover loads prior enriched fields by path (`_carryover_metadata.py:27-43`) and reapplies them with `setdefault` (`_carryover_metadata.py:46-54`), so an old `summary_done` or future `summary_file_exists` can survive even if the on-disk summary file changed or disappeared. That means the plan fixes the schema design, but only a full re-enrichment fixes stale values; otherwise the split can still mask old truth.

## Implementation Risk

The biggest concrete risk is `--resume`: `_is_already_enriched` checks only `"content_type"` and `"summary_done"` (`enrich-summary-metadata.py:104-105`). On a partially enriched index, old records lacking `summary_file_exists` will be skipped and re-emitted unchanged, producing mixed schema. Atomic rewrite itself looks sound: both enrich and carryover write to a temp file then `os.replace(...)` (`enrich-summary-metadata.py:153-160`; `_carryover_metadata.py:70-76`). The real ops risk is transient disk usage for backup + tmp + new file, not rename semantics.

## Missing Seams

Phase A's active main path does use carryover: `write_merged_index_with_carryover(...)` calls `extract_enriched_fields`, `apply_carryover`, then `atomic_write_index` (`phase-a-index.py:283-301`, called at `362-367`). I did not verify an active main-path bypass. However, `write_index(...)` still exists and writes raw merged records directly (`phase-a-index.py:262-280`); no caller was verified, so this is a latent seam, not a proven live path. Phase C default mode writes only `enhancement-plan.yaml`, not `index.jsonl`. Its `--writeback` mode mutates targeted records in place and re-emits the whole record, so it preserves existing fields but will not synthesize a missing `summary_file_exists`. Phase E behaves the same (`phase-e-backpopulate.py:121-176`).

## Test Gaps

Missing repo-verified tests are: `--resume` against an old-schema index; Phase C writeback on mixed-schema records; Phase E backpopulate on mixed-schema records; stale-carryover behavior when a summary file is removed/emptied after prior enrichment; and a guard that Phase A's raw `write_index(...)` is not used for production rewrites.

## Ops Sequencing

If maturity YAML is updated in the same PR before successful live re-enrichment, the repo can temporarily claim coverage the production index does not yet satisfy. Given the repo-verified mixed-schema resume risk, YAML should follow successful re-enrichment, not precede it. The "one PR" packaging is operationally risky unless the YAML change is deferred to the end of the rollout.

## Recommendation

Require the plan to explicitly patch three seams together: `enrich_one`, `_is_already_enriched`, and `CARRYOVER_FIELDS`. Also require tests for mixed-schema `--resume` and Phase C/E pass-through behavior. Approve only if the ops sequence states: code/tests first, full re-enrichment next, maturity YAML last after the live index is validated.
