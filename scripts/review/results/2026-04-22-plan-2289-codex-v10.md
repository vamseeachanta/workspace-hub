### Verdict: MAJOR

### Summary
The v9 draft is not ready for user approval. It closes several earlier contradictions, but two core classification rules remain too ambiguous to implement or audit reliably: approval binding for `log_only_approved_later`, and the eligibility boundary for `log_only_remediated_later`.

### Issues Found
- `docs/plans/2026-04-21-issue-2289-bypass-rollback-recovery.md:180,195-198,301-314` — `log_only_approved_later` still depends on an undefined concept: a "uniquely identified revision set" with "demonstrable" binding from marker/GitHub evidence. The policy never defines the allowed evidence fields, the equality rule for a revision set, or what must be persisted to prove that binding later. The audit contract also omits the binding provenance needed to verify this verdict after the fact. That leaves the highest-risk edge case open to divergent #2445 implementations.
- `docs/plans/2026-04-21-issue-2289-bypass-rollback-recovery.md:182,223,266-271,350-360` — `log_only_remediated_later` is still not operationally defined. "A later commit on the same branch ... carries review evidence for the bypassed change" does not say what qualifies as remediation, how it differs from ordinary later reviewed work, or how merge-based remediation is proven. The scenario matrix uses the verdict, but the TDD list does not require a boundary test for remediation classification, so this ambiguity can ship into implementation unchanged.

### Suggestions
- Define `log_only_approved_later` normatively: list the exact evidence sources/fields that may bind approval to a SHA or revision set, define what a "revision set" is, define the comparison rule, and add required audit fields capturing the winning evidence source and bound revision identity.
- Define `log_only_remediated_later` normatively: state the minimal evidence required, what relationship the remediating commit must have to the bypassed SHA, and how merge/cherry-pick cases are classified. Add explicit tests covering remediation vs approval vs non-remediating later commits.
- Once those rules are explicit, update the audit contract and TDD list so both verdicts are independently testable and reviewable before #2445 implementation begins.

### Questions for Author
- For `log_only_approved_later`, what exact artifact binds approval to a "revision set" if the original SHA is not the sole reviewed revision identifier?
- For `log_only_remediated_later`, what observable condition distinguishes a true remediation of the bypassed change from any later reviewed commit on the same branch?
