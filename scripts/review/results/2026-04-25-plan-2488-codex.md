## Findings
1. `Acceptance Criteria` requires approval-gate artifacts that are “fresh post-revision timestamped” and that “record the reviewed plan commit or plan SHA256,” but the current review generator does not produce either. `scripts/review/plan-review-fanout.sh` writes date-only files named `${TODAY}-plan-${ISSUE_NUM}-${prov}.md`, and its UNAVAILABLE stub writes only verdict/retrieval/findings/blockers text with no commit or SHA field. `Files to Change` does not include `scripts/review/plan-review-fanout.sh` or `scripts/review/lib/disagreement-diff.sh`, so the plan cannot satisfy its own gate-evidence contract as written.

2. The sparse-checkout/partial-inventory safeguard is asserted but not designed. The plan’s `Pseudocode` for `build_skill_inventory_with_git(...)` says only “call git_list_fn or default git ls-files,” while the `TDD Test List` and `Acceptance Criteria` require that sparse or partial `git ls-files` states be detected and downgraded to warnings. A successful `git ls-files` call is not itself evidence of completeness, and the plan never specifies an actual detection mechanism. As written, this leaves a correctness-critical gap around false `missing_tracked_*` findings in sparse or partial worktrees.

3. The section-order design is internally inconsistent with the current policy surface. `config/skills/weekly-audit-policy.yaml` has one linear `ranking_policy.section_order`, but the plan’s `Pseudocode` and `Acceptance Criteria` also require a fixed legacy block (`Content Quality`, `Grouping`, `Oversized`, `Usage`, `Follow-up`) to remain anchored between early sections and tail governance sections. The `TDD Test List` doubles down on this hybrid rule with `test_policy_section_order_consumes_yaml_for_governed_sections` and `test_markdown_refactor_preserves_legacy_literal_sections`. That means YAML order is not actually authoritative for full output order, and the plan does not define how invalid YAML orders are rejected. This is a schema/design contradiction, not just an implementation detail.

4. The proposed repo-root symlink integration test is grounded in local-only state, not a verified tracked contract. The plan’s `TDD Test List` adds `test_provider_skill_mirror_symlinks_real_paths` asserting `.codex/skills` and `.gemini/skills` are real symlinks in the repo root, but the only tracked evidence I could verify is `docs/reports/issue-2488-planning-inventory-snapshot.json`; there is no existing test or documented tracked contract for those root paths in `tests/skills/test_weekly_skills_audit.py`, `docs/ops/scheduled-tasks.md`, or `config/skills/weekly-audit-policy.yaml`. For a repository test suite, that is brittle and environment-dependent.
