In `docs/plans/2026-04-25-issue-2488-reconcile-untracked-active-skill-files-before-loss.md` under `Tentative disposition table`, the row for `.claude/skills/memory/hermes-memory-bridge/SKILL.md` says the ignored-path evidence is `(.gitignore:14 digitalmodel/)`. The actual relevant ignore rule in `.gitignore` is `memory/`, not `digitalmodel/`. This matters because the same plan later makes `force_add_attestation_when_ignored.{gitignore_rule, gitignore_line}` mandatory.
2. The plan claims a closeout-hard-fail mechanism without binding it to any enforced caller. In `docs/plans/2026-04-25-issue-2488-reconcile-untracked-active-skill-files-before-loss.md` `Acceptance Criteria`, the baseline-order helper “is run in manual closeout” and “closeout fails” if ordering is wrong, but `Files to Change` only creates `scripts/skills/verify_issue_2488_baseline_order.py`. No hook, CI workflow, or enforcement script is named. `docs/plans/README.md` `Enforcement` shows this repo’s real hard gates are explicit hooks/scripts; this new failure mode is prose-only as written.
3. The plan’s primary review-artifact citation points at the wrong evidence class. The plan frontmatter lists mutable files `scripts/review/results/2026-04-25-plan-2488-*.md`, while the same plan’s `Acceptance Criteria` and `Adversarial Review Summary` say the authoritative evidence before `status:plan-review` is the immutable set `scripts/review/results/20260425T125029Z-plan-2488-*.md`. That leaves the top-level `Review artifacts:` line pointing at files the plan itself says are not approval evidence.
4. The `Adversarial Review Summary` overclaims that Claude’s flagged issues are addressed. In `docs/plans/2026-04-25-issue-2488-reconcile-untracked-active-skill-files-before-loss.md` under `Adversarial Review Summary`, the Claude row says those findings “are addressed in this revision,” but two Claude findings remain unresolved in the current plan text: the unbound `verify_issue_2488_baseline_order.py` enforcement surface and the wrong gitignore evidence for `hermes-memory-bridge`. That makes the summary stale against both the immutable Claude artifact and the current plan body.
5. The duplicate/collision-regression contract is still underspecified. In `Acceptance Criteria`, the plan says implementation must “assert duplicate/collision delta is zero,” but it does not pin the comparison surface there. A count-only match would satisfy that wording while still allowing `finding_key` or path-scope drift. The nearby TDD rows mention “summary counts and finding IDs,” but the acceptance gate itself should name the invariant it relies on.
