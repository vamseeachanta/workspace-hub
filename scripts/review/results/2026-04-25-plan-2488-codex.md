## Findings
1. The plan is not approval-ready on its own stated evidence contract. Its frontmatter `Review artifacts:` still points at `scripts/review/results/20260425T125029Z-plan-2488-*.md`, and its `## Adversarial Review Summary` explicitly says the “current immutable review evidence ... still contain MAJOR findings” and “do not move to `status:plan-review` until a subsequent pushed re-review has no unresolved MAJOR findings.” The later acceptance criterion requiring “fresh post-revision timestamped `*-plan-2488-*.md`” therefore fails against the artifacts this revision cites. This is a blocker for any claim that the plan is ready to advance.

2. The manual replay trust contract is internally inconsistent. In the `manual CLI contract for scripts/skills/reconcile_filesystem_only_skills.py`, the plan says `--inventory-json PATH` is rejected unless paired with `--trust-attestation` “containing a matching live trust attestation generated during the same run.” In `validate_and_render_dispositions_for_manual_reconcile(...)`, the same plan says to “write trust_attestation JSON at the configured path.” That makes `--trust-attestation` both required preexisting input and generated output in the same execution. A single run cannot consume a file that only comes into existence later in that same run.

3. The source of truth for `issue_body_six_drift` is undefined. In `build_skill_inventory_with_git(...)`, the required JSON schema includes `inventory_summary.paths.issue_body_six_drift`, and later `validate_and_render_dispositions_for_manual_reconcile(...)` requires `issue_body_drift_note` when a known issue-body path vanished. But the only authoritative list of those six paths is prose in issue `#2488` / the plan narrative itself; no tracked config file, constant source, or ledger seed file is named for the weekly audit to read. As written, the implementation either has to hard-code issue prose in Python or cannot populate this field deterministically.

4. `_diverged` handling is still under-specified for the numeric counts. In `build_skill_inventory_with_git(...)`, the `active_filter(path)` description says `_archive` and `_archived` are non-active, while `_diverged` is “excluded from active-loss findings” and also reported separately in `legacy_diverged_compatibility_total`. The same function returns `tracked_active` and `filesystem_active`, but the plan never pins whether those counts include or exclude `_diverged`. Issue `#2488`’s baseline counts exclude only `_archive` and `_archived`; the plan’s loss-risk semantics additionally quarantine `_diverged`. Without an explicit rule for the count fields, future runs can drift while still appearing compliant.

5. The shell helper contract leaves a repo-policy violation path open. `AGENTS.md` says “Python: `uv run` always — never bare `python3`.” The plan creates `scripts/skills/verify_issue_2488_baseline_order.sh` plus `scripts/skills/verify_issue_2488_baseline_order.py`, but nowhere in `Files to Change`, `Pseudocode`, or `Acceptance Criteria` does it bind the shell wrapper to invoke the Python helper via `uv run --no-project python`. That omission is smaller than the blockers above, but it leaves an avoidable policy hole in an otherwise very prescriptive plan.
