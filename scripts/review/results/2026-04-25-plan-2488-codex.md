## Findings
1. The plan allows non-authoritative inventory data in the very mode that is supposed to prove reconciliation is complete. In `## Pseudocode`, `classify_filesystem_only_skill(path)` says “git-history lookup failures are non-fatal warnings in `weekly_report` and `manual_closeout` evidence,” while `validate_and_render_dispositions(disposition_yaml, mode)` makes `manual_closeout` the gate that must prove every active filesystem-only skill is resolved. The same draft also adds `test_git_inventory_failure_is_reported_not_cron_fatal` and `test_sparse_checkout_or_partial_git_inventory_is_warned_not_trusted`. A warning-only manual closeout is incompatible with the acceptance claim “Manual closeout validation confirms both `missing_tracked_active = 0` and `unresolved_filesystem_only_active = 0`.” This needs a hard-fail rule for `manual_closeout` when git inventory is partial/untrusted.
Citations: plan `## Pseudocode`; plan `## TDD Test List`; plan `## Acceptance Criteria`.

2. The plan introduces a mandatory “explicit user authorization” gate for `personal-tax-filing-packet` but never defines any workflow step that can satisfy it. The draft requires “Any promotion of `personal-tax-filing-packet` requires explicit user authorization in the disposition ledger,” and the tentative disposition table marks that file `pending_full_file_scan_and_user_authorization`. But `docs/plans/README.md` only defines user approval for the plan as a whole (`status:plan-approved`), not per-artifact authorization or user-authored ledger entries. As written, the plan adds a blocker with no acquisition path, so completion is underspecified.
Citations: plan `### Tentative disposition table for the known active filesystem-only skills`; plan `## Acceptance Criteria`; `docs/plans/README.md` sections `The Workflow`, `Step 6: User Approval`.

3. The draft widens the canonical scheduled audit executable into a dual-purpose closeout tool that can write tracked docs, but it does not isolate that risk from the cron-owned path. Current `scripts/skills/weekly_skills_audit.py` describes itself as a “read-only audit” that emits local artifacts only, and the approved parent plan `docs/plans/2026-04-24-issue-2486-v2-periodic-skill-ecosystem-housekeeping-audit.md` locks the scheduled/default run to writes under `logs/maintenance/skills-curation/` only. This draft instead puts `validate_and_render_dispositions(...)` and tracked output `docs/reports/2026-04-25-skills-disposition-2488.md` into the same script (`## Files to Change` says modify `scripts/skills/weekly_skills_audit.py` for ledger validation/rendering). A mode flag alone is not a sufficient isolation story for a cron-owned entrypoint; the plan should require a separate manual-closeout entrypoint/module or equivalent hard separation.
Citations: `scripts/skills/weekly_skills_audit.py` module docstring and `main()`/`run_audit()` behavior; `docs/plans/2026-04-24-issue-2486-v2-periodic-skill-ecosystem-housekeeping-audit.md` sections `### V2 scope boundaries` and `## Acceptance Criteria`; current plan `## Pseudocode`; current plan `## Files to Change`.

4. The plan changes the audit CLI contract (`--mode`, `--disposition-ledger`, `--disposition-report`) but omits the repo’s existing wrapper test surface from the change plan. The approved #2486 plan explicitly identifies `tests/cron/test_skills_curation.py` as the wrapper regression suite, and `scripts/cron/skills-curation.sh` is the only scheduled entrypoint. This draft adds only one wrapper-oriented test in the audit test list (`test_cron_wrapper_dry_run_command_parses_with_default_mode`) and does not list `tests/cron/test_skills_curation.py` in `## Files to Change`. That is under-scoped for a CLI change whose safety depends on preserving cron compatibility.
Citations: current plan `## Files to Change`; current plan `## TDD Test List`; `docs/plans/2026-04-24-issue-2486-v2-periodic-skill-ecosystem-housekeeping-audit.md` `## Artifact Map` and `## TDD Test List`; `scripts/cron/skills-curation.sh`.
