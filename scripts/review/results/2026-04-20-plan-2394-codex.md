### Verdict: MAJOR

### Summary
The dominant defect class is unverified correctness-critical assertions: the plan claims dependencies, sources, paths, and operating-model compliance without proving any of them. It also leaves at least one acceptance criterion and several risk paths without corresponding executable tests or ownership for implementation.

### Issues Found
- [P1] Resource Intelligence Summary contains unverified and internally weak evidence. The claim `scripts/conformance/ (if present) — where the new check lives` is explicitly conditional, so the cited path is not verified, and the summary still concludes `Distinct sources consulted: 9`. This fails the requirement that cited file paths and sources be verified, and several listed sources are not concrete findings (`Standards: Not applicable`, `LLM Wiki pages consulted: Not applicable`).
- [P1] Dependency correctness is unverified for `Related issue #2393 (embeddings index — parallel) — this tool depends on it` in `Documents consulted` and `Risk: Hard-depends on #2393` in `Risks and Open Questions`. The plan does not prove that issue #2393 exists, is open, or is at a status that makes this plan executable now.
- [P1] `doc_key` / operating-model §3 compliance is missing from the deliverable and pseudocode. The `Deliverable` and `Pseudocode` require a table with `doc_key`, but nowhere requires or verifies `sha256:` namespacing; the quoted output schema only says `| doc_key | layer | path | similarity | status |`. That is a correctness-critical omission.
- [P1] Operating-model ownership/layering is underspecified and likely non-compliant. `Pseudocode` uses `query_embeddings(query, top_k=10, layer="both")`, and `Documents consulted` states `Operating model §4 (L3+L2 → L5 flow — retrieval IS this flow; tool operationalizes it)`, but the plan never defines which concrete stores are L2/L3/L5, who owns them, or how `layer="both"` avoids forbidden between-layer abstractions. This is an unverified compliance claim.
- [P1] §4 flow compliance is not established. The plan asserts `retrieval IS this flow` in `Documents consulted` but does not specify whether the embeddings index is a durable L5 store, a cache, or shared metadata, nor how candidate paths are materialized without creating forbidden circular flows. The plan asks reviewers to trust an operating-model conclusion without evidence.
- [P1] §7 cross-machine tier rules are not addressed for hook wiring and retrieval state. `Artifact Map` cites `.git/hooks/pre-push` and `Files to Change` modifies `scripts/enforcement/install-hooks.sh`, but the plan never states what is git-tracked metadata vs local hook state vs any shared retrieval/index cache. That is a required correctness check left unverified.
- [P1] TDD coverage is incomplete against the acceptance criteria. `Acceptance Criteria` includes `CLI runs on 3 real open issues producing sensible output (manual check during review)`, `Conformance check integrated into pre-push hook`, `Template updated with example filled-in block`, and `Review artifacts posted`, but `TDD Test List` does not include a hook-installation/invocation test, a template-example-content test, or anything for review-artifact posting. Several ACs therefore lack corresponding tests.
- [P1] The plan introduces behavior that is not fully specified in files-to-change. `test_check_skip_flag_logged` requires `--skip-retrieval` and an `audit log entry`, and `Risks and Open Questions` says `--skip-retrieval flag with logged justification`, but no file is listed to own the audit-log implementation, schema, or storage path. This is a missing dependency/ownership defect.
- [P2] Scope control is weak. The nominal deliverable is `A CLI ... plus a conformance check`, but `Files to Change` also modify the planning skill, the plan template, hook installation, and `docs/plans/README.md`, while `Acceptance Criteria` require `Review artifacts posted`. That is more than a single-purpose CLI/check change and mixes feature work with workflow, docs, and review-process automation.
- [P2] Security/threat modeling is absent for code paths that will touch GitHub issue content, filesystem paths, local hooks, and whatever embeddings/index backend #2393 provides. No section identifies trust boundaries, path handling, secret usage for issue retrieval, or failure modes for malformed issue content.
- [P2] The `Artifact Map` entry `Pre-push hook wiring | .git/hooks/pre-push (via scripts/enforcement/install-hooks.sh)` is misleading because `.git/hooks/pre-push` is not a normal tracked repo artifact, while the plan treats it like one. That blurs repo-owned changes versus local side effects and makes the deliverable boundary unclear.
- [P2] `test_retrieve_returns_markdown_block` hardcodes `issue #2205 (known)` as input, but the plan never proves that issue is stable, suitable, or even relevant to the retrieval corpus. This is another dependency assertion presented as fact without verification.

### Suggestions
- Replace every unverified source/dependency claim with proven evidence, or explicitly mark it as a prerequisite gap. In particular, prove the existence/status of #2393 and any referenced sample review artifacts before keeping them in the plan.
- Add an explicit compliance subsection for operating-model §§2/3/4/7 that states: doc identity uses `sha256:` `doc_key`, what concrete stores are L2/L3/L5, what the embeddings index tier is, what machine tier owns hooks/index/cache, and why no forbidden flows are introduced.
- Expand the TDD matrix so every acceptance criterion has at least one test or an explicit non-test verification procedure with owner. Add tests for hook installation/invocation, template example content, and any skip/audit-log persistence behavior.
- Name the exact file/path that implements skip logging and define its retention/tier semantics. If no durable log is intended, remove `audit log entry` from the test/mitigation claims.
- Reduce scope or split the work: keep the CLI/check in this issue, and move hook/process/review-artifact concerns to separate issues unless they are strictly required blockers.
- Add a security section covering GitHub/API access, issue-body sanitization, path rendering in candidate tables, and local-hook side effects.
