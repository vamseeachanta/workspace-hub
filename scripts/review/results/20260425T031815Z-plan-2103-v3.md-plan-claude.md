### Verdict: MAJOR

### Summary
v3 is thorough and addresses all r2 P2s with explicit mechanisms (conftest for sys.path, #2124-v3 gating to avoid a duplicate helpers module, underscore rename of the two new ingesters, atomic writes, verbatim _load_topics citation). The attested-evidence block and ordered build sequence are strong. The remaining concerns are narrow but real: a new hyphen-named Python file is being introduced in direct contradiction to the anti-pattern the plan is closing out, the location/owner of the `_atomic_write_json` helper is unspecified (DRY / coordination risk), and the master-index merger's read-modify-write sequence is not concurrency-safe despite the claimed single-shell serial model.

### Issues Found
- [P2] `update-master-index.py` is a newly-created hyphen-named Python file, directly recurring the very anti-pattern v3 cites (feedback_llm_wiki_hyphen_module_path_pattern) and fixes for the two ingesters. Either rename to `update_master_index.py` (consistent with ingest_bemrosetta.py / ingest_aqwa.py), or add an explicit in-plan justification that it is CLI-only and never imported — silently reproducing the hyphen pattern while eliminating it elsewhere is inconsistent.
- [P2] `_atomic_write_json` is referenced in the pseudocode for both `ingest_bemrosetta.py` and `ingest_aqwa.py` but its definition location is not specified. If it lives in `orcina_common.py`, that adds a dependency on #2124 v3 beyond the four helpers currently attested — the attestation explicitly lists only html_to_markdown/fetch_page/_convert_element/_convert_table. If it is duplicated in each ingester, that is a DRY violation and two atomic-write implementations will drift. The merger uses a third inline implementation (lines 339-341). Pick one location and cite it in Files-to-Change.
- [P2] Master-index merger is not concurrency-safe despite the stated single-shell serial model. `merge_master_index` does read-modify-write: `existing = json.loads(master_path.read_text()); existing['products'][product] = ...; os.replace(tmp, master)`. Two concurrent merger runs will have last-writer-wins semantics on the `products` dict — atomic write of the final file does not protect the read-modify-write window. Either document an advisory lockfile / os.O_EXCL pattern, or downgrade the claim from 'safe' to 'serial-only; concurrent invocation will silently drop product entries'. Given the plan notes future automation may chain ingest→merge, the hazard is forward-facing.
- [P3] Tempfile cleanup on mid-write failure is not shown in pseudocode but is asserted by three tests (`test_bemrosetta_index_atomic_write`, `test_aqwa_index_atomic_write`, `test_update_master_index_atomic_write` all assert 'no leftover .tmp file in dir'). With `tempfile.NamedTemporaryFile(..., delete=False)` + json.dump raising, the tempfile remains unless a try/finally unlink is added. Spell this out in the pseudocode or the tests will fail on first run and mask the underlying implementation gap.
- [P3] `parse_wiki_sidebar` and `fetch_github_tree_for_repo_markdown` appear in `ingest_bemrosetta.py` pseudocode without indication of whether they are new local helpers or are expected from `orcina_common.py`. Since `orcina_common.py` is owned by #2124 v3, any expectation that new helpers be added there needs coordination that isn't called out in the gating-dependency section. Declare them local to `ingest_bemrosetta.py` explicitly.
- [P3] Test `test_search_wiki_surfaces_bemrosetta` needs to point `search-wiki.py` at the fixture wiki dir; the mechanism (env var, CLI flag to resolve_wiki_path, monkeypatch) is not specified and `search-wiki.py`'s argparse surface isn't shown. Readers cannot verify the test is actually wireable without that detail.
- [P3] Cross-review coverage is reduced: r2 Codex did not run (upstream regression #2479) and r3 will also skip Codex. Single-provider historical coverage (Claude+Gemini only) is weaker grounding for a plan that introduces cross-repo surface area. Not blocking, but worth noting in the review history.
- [P3] Registry.yaml and priority-queue.yaml updates are deferred to a follow-up sibling issue. This means ingested BEMRosetta/AQWA corpora will be functionally invisible to downstream registry consumers between this PR landing and the follow-up landing. An explicit SLA or link-target for the follow-up issue would reduce the ingested-but-unconsumed window.

### Suggestions
- Rename `update-master-index.py` to `update_master_index.py` — kills the last hyphen-named new Python file and lets the grep regression guard graduate to checking both imports AND filenames under `scripts/data/llm-wiki/*.py` (modulo the single grandfathered `ingest-orcina.py` noted in v3).
- Move `_atomic_write_json` into a single source of truth. If coordinated with #2124 v3, put it in `orcina_common.py` and extend the attested-helpers list in the Attested Evidence block. Otherwise, add it to a new local `scripts/data/llm-wiki/atomic_io.py` and have both ingesters plus the merger import from there.
- Add an advisory lockfile (e.g., `fcntl.flock` on `output_root/.index-lock`) around the master-index read-modify-write, or at minimum state in Risks: 'concurrent invocation not supported; automation must serialize'.
- Expand the `_atomic_write_json` pseudocode to show the try/finally tempfile unlink path so the three atomic-write tests have a clear implementation target.
- Add a row to the Attested Evidence block for `search-wiki.py`'s CLI interface (how it locates the wiki dir) so test-wiring is unambiguous.
- Consider pre-filing the registry.yaml + priority-queue.yaml follow-up issue now rather than at PR-open; linking to an existing issue number strengthens the acceptance-criterion commitment.
