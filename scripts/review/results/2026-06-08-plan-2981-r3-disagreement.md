- **Shell→Python dependency mechanism is unspecified, and the two strategies in the plan do not compose (MAJOR).** The plan says the workflow will "set up Python and install PyYAML" (line 238) — i.e., CI uses system pip — while local/test commands use `UV_CACHE_DIR=… uv run --no-project --with pyyaml` (lines 239, 272–273). AC line 274 requires `bash scripts/skills/validate-skills.sh` to pass, and the test design (plan lines 204–206) runs `subprocess → bash validate-skills.sh <tmp root>`. In both cases the shell spawns its own Python process; pytest's `uv run --with pyyaml` env does **not** propagate PyYAML into that subprocess. If the helper is invoked as bare `python3 helper.py`, it raises `ImportError` everywhere PyYAML isn't in the system interpreter — which is the exact "CI-doesn't-install-deps" failure class the r1 Claude/Codex reviews already flagged. The plan must pin a single end-to-end invocation (e.g., the shell script calls `uv run --no-project --with pyyaml python scripts/skills/validate_skills_frontmatter.py "$ROOT"` once), or the AC and the test are not implementable as written.

If the real loader is more lenient, the validator false-fails on the 128 `_internal/` and other files and turns CI red for files dispatch actually accepts; if stricter/different, it false-passes and the next dispatch break slips through. At minimum the plan should state PyYAML is a deliberate conservative proxy and cite *why* it's a safe lower bound for the loaders in question, rather than treating them as equivalent.
- **A second stale soft-fail block is not covered by the Files-to-Change/AC (MINOR).** AC line 280 and the Files table (line 252) target only the `continue-on-error` comment (workflow lines 31–33). The "Generate skills summary" step (lines 45–46) *also* asserts "Validation runs in soft-fail mode" and "Files under `_diverged/` and `_internal/` may lack frontmatter." `_diverged/` has 0 files and all `_internal/` files parse (verified), so this text is doubly stale and will keep emitting a false CI summary even after the fix. The cleanup AC should name lines 45–46 explicitly.
- **Soft-fail retention silently defeats the issue's enforcement intent (MINOR / decision-forcing).** The plan leaves `continue-on-error: true` removal as an open question (lines 280, 311) with a "keep soft-fail if code review finds CI risk" fallback. If soft-fail is retained, the workflow never blocks a malformed file — the validator becomes advisory and a future unquoted-colon description re-breaks review dispatch exactly as #2981 did. The plan should state plainly that retaining soft-fail leaves the root cause unguarded, so the reviewer/owner makes that trade-off knowingly rather than as a deferred "open question."

### r2-gemini

- **Target files do not exist at HEAD.** Plan references `scripts/skills/validate-skills.sh`, `.github/workflows/skills-validation.yml`, and `.claude/skills/coordination/flywheel-closeout/SKILL.md`. Searches confirm none of these files or their parent directories (`.claude`, `scripts`, `.github`) exist in the workspace. The plan is entirely disconnected from the repository's current state.
- **Unhandled Exception Risk in Type Checking.** Plan section "Implementation direction" states: "The helper will require `name` and `description` to be non-empty strings after `.strip()`, not merely YAML-present values. Reject `name: 123`". Because `yaml.safe_load` automatically casts `name: 123` to an `int`, calling `.strip()` on the value will raise an `AttributeError`, causing an unhandled Python traceback rather than a controlled validation rejection. The helper must explicitly verify `isinstance(value, str)` before calling `.strip()`.
- **Unhandled Exception on Missing Fields.** Plan asserts: "require non-empty name and description fields" and its test table references `tmp SKILL.md missing description`. If the `description` key is entirely missing from the YAML mapping, looking it up (e.g., `data.get("description")`) returns `None`. Calling `.strip()` on `None` raises an `AttributeError` instead of gracefully failing.
- **Incomplete Code Delegation.** Plan section "Files to Change" instructs to modify `scripts/skills/validate-skills.sh` to "Delegate to strict YAML parsing while preserving existing entrypoint." However, the plan fails to explicitly require the removal of the existing `grep`-based validation loops shown in the plan's excerpt. If the `grep` loops remain intact alongside the Python helper invocation, the script will double-validate and may falsely reject YAML-valid files whose formatting doesn't match the regex.
- **Broken Local Hermetic Execution.** Plan section "Implementation direction" instructs CI to "set up Python and install PyYAML before running the validator," implying the shell script uses bare `python` to execute the Python helper. However, local testing rules dictate using `uv run --with pyyaml` hermetically. If `validate-skills.sh` invokes bare `python`, running it locally (as explicitly required by AC #3: `bash scripts/skills/validate-skills.sh`) will crash with a `ModuleNotFoundError` for developers who do not have `pyyaml` installed globally on their system.
- **Inappropriate Path Filters in CI.** Plan section "Acceptance Criteria" requires the `.github/workflows/skills-validation.yml` path filters to include `tests/enforcement/test_validate_skills_frontmatter.py`. The `skills-validation.yml` workflow exists to validate the skills inventory (`.claude/skills/`), not to execute the Python test suite for the validator tool itself. Triggering a full inventory validation run because a unit test file was modified is an unnecessary CI trigger.
