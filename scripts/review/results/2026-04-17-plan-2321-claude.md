## Findings
- Plugin config location is explicitly left TBD in the Files-to-Change table — this is a planning gap, not a deliverable. Step 1 of the implementation should discover the config path and update the plan before any edits.
- No rollback plan for archival is documented. If moving `sparc:orchestrator` breaks an active script, how is recovery scoped? A revert commit is implicit but should be called out.
- The "≥5 canonical-vs-archive decisions" acceptance criterion is a number floor and can be gamed with trivial archives. The plan should either name the specific clusters (which it partially does in Open Questions) as committed deliverables, or state that each cluster requires an evidence-based justification (invocation count, reference count).
- The archive decisions would be materially stronger if fed by #2320 invocation data. The plan should either declare an explicit dependency on #2320 landing first or document the fallback heuristic when usage data is unavailable.
- `verify_semantic_scholar_state` requires a fresh `/plugin` session, which is a manual human step; acceptance criteria should make this explicit so that automated regression cannot claim pass without it.
- No evidence that `.claude/skills/_archive/` is the canonical archive target for skills owned by `plugins:*` families — the precedent from #2290 was workspace-hub-owned skills. Plugin-owned skills may have a different archive pathway.
