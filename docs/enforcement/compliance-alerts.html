Compliance alert interpretation

The cron wrapper reads the dashboard's top-level JSON metrics. Human-readable text and nested stage-prompt verdicts are excluded from metric selection. Invalid metrics or an execution-status mismatch produce an error exit before GitHub access. A window containing no reviewable commits produces no alert.

Method and sources

The existing dashboard defines reviewable = total − skipped and the integer percentage floor(100 × reviewed / reviewable). For a zero denominator, the dashboard stores zero and returns PASS; cron treats this as no reviewable work, rather than a measured failure rate. Count identities and the dashboard verdict are validated by the parser.

The threshold table in issue 3693 and the existing cron policy supply the alert boundaries: below 30% critical; 30% to below 50% high; 50% to below 80% medium; at least 80% no alert. These are repository policy values, not engineering acceptance limits. Alert policy remains separate from the dashboard's configurable pass threshold.

Verification and limits

The parser and dry-run cron tests cover nested verdicts, missing and malformed reports, inconsistent counts, threshold boundaries, no-reviewable windows, and execution failures. GitHub commands are stubbed and mutation attempts are rejected. Run the compliance cron and dashboard tests in tests/enforcement.

The dashboard's existing commit classification and review-evidence heuristics are unchanged. In particular, a review-related word in a commit message is not independent proof of review. Historical commit reviews, bypass investigation, weekly aggregation and independent provider review remain to be assessed. This change does not establish restored review compliance or close the alert.
