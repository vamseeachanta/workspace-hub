## 2. Root cause — `repository-sync` dead since 2026-07-12

Commit `74c4e4954` (#3466, "enforce singleton runtime health") landed on the
boxes 2026-07-12 18:33 and rewrote `scripts/cron-repository-sync.sh` to
`exec uv run --script scripts/cron/cron_runtime.py`. The YAML command in
`config/scheduled-tasks/schedule-tasks.yaml` gained a
`PATH=$HOME/.local/bin:$PATH;` prefix — **but installed crontabs are only
regenerated by `setup-cron.sh --replace`**, and ace1/ace2 crontabs carry
`# Generated: 2026-05-10T12:28:32Z`. They never got the prefix.

`uv` exists only at `~/.local/bin/uv`, which is not on cron's default PATH, so
every invocation died at `line 20: exec: uv: not found` (exit 127) **before
opening its log file**. That is why the failure was invisible in `logs/` —
no error log, just an absence of logs.

| Host | PATH prefix | Last good sync | Silent failures |

| ace-linux-1 | missing | 2026-07-12 16:00 | 84 (`logs/quality/cron-wrapper.log`) |

| gpu-claw | **present** | 2026-07-26 | none — enrolled after the change |

Ruled out with evidence: no stale singleton lock (`.claude/state/cron-runtime/`

responsible (18 logs survive back to 06-25; the gap is at the new end); no OOM,
kill, or causal reboot.

## 3. Fix applied

**Surgical**, not `setup-cron.sh --replace` — ace1's crontab holds hand-edited
and PAUSED lines outside the managed block that a regen could clobber. One line
changed per host, guarded by an exact-match count of 1:

```
- 0 */4 * * * mkdir -p $WORKSPACE_HUB/logs && cd $WH && bash scripts/cron-repository-sync.sh ...
+ 0 */4 * * * mkdir -p $WORKSPACE_HUB/logs && PATH=$HOME/.local/bin:$PATH; cd $WH && bash scripts/cron-repository-sync.sh ...
```

ace1 line 51 (73 lines preserved), ace2 line 28 (40 lines preserved).
Backups: `~/crontab-backups/crontab-<ts>-pre-uvpath.txt` on each host.

**Verified end-to-end** on the 20:00 scheduled run — not merely by inspection:
- ace1 `Done. ok=22 warn=0 fail=9`, ace2 `Done. ok=34 warn=0 fail=6`

  created 20:00 — the singleton runtime's first-ever execution on these boxes

## 5. macOS-specific findings and changes

This Mac is `macbook-portable`, `schedule_variant: none` — **deliberately outside
the equivalence roster**; it publishes no fingerprint by design and does not
trigger `absent-fingerprint`. Do not "fix" this by enrolling it.

Its nightly sync had four stacked defects: wrong path
(`/Users/krishna/workspace-hub`, nonexistent), direct exec of a `100644` script,
`uv` absent, and — the blocker — **`cron_runtime.py` is Linux-only**:
`_process_identity()` (`scripts/cron/cron_runtime.py:120-130`) reads
`/proc/<pid>/stat` and `/proc/<pid>/wchan`; macOS has no `/proc`, so it returns
None and line 247 raises `RuntimeError("process identity unavailable")`.

Applied: crontab rewritten to invoke `scripts/repository_sync` **directly**,
bypassing the wrapper, pinned to `/opt/homebrew/bin/bash` (script needs Bash 4+;
macOS `/bin/bash` is 3.2.57); installed `uv` 0.11.32 via Homebrew; set exec bits
and `core.fileMode=false` to match ace1; corrected `registry.yaml` `workspace_root`
and the notes block (which claimed "No cron" while a cron job existed).
Verified in a clean `env -i`: `ok=4 warn=0 fail=1`.

Trade-off accepted: the Mac loses the singleton/overlap guard and is now the one
host invoking sync differently. Proper fix is a `/proc`→`ps` fallback in
`cron_runtime.py` — **not filed as an issue.**

## 11. Operational gotcha discovered

**`crontab <file>` silently installs an EMPTY table** (exit 0, no error) when it
cannot read the source path — e.g. anything under `/private/tmp/claude-*` on
macOS. It wiped the Mac's crontab once mid-session; the pre-change backup made
it a non-event. Always `crontab -l > backup` first and stage the new table under
`~` or the repo.
