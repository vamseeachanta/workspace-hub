Manifest closure before data readback

Summary

Hash agreement over listed files cannot establish completeness. The shared scripts/data/manifest_closure.py validator accepts a dataset only when its inventory equals an independently pinned contract, its payload hashes agree, and its declared record counts, primary keys and foreign keys pass. It returns the verified bytes and a separate versioned integrity receipt. No engineering thresholds or source-rights decisions are inferred.

Basis and method

The governing requirement is issue 3952. The repository agent data handling contract (2026), sections “Original retention, rights and publication” and “Stable projection and shared conformance contract”, supplies retention, SHA-256, duplicate-key, finite-number and authority-separation requirements. This document defines the version-one protocol; version strings are protocol identifiers, not empirical coefficients. Counts and inventory are mandatory caller inputs. No physical equations or acceptance constants are introduced.

  1. Pin the contract SHA-256 through the consuming workflow's independently reviewed configuration. Computing the pin from an untrusted contract during acceptance defeats this boundary.
  2. Parse manifest and contract JSON with duplicate keys and non-finite numbers rejected. Require the exact documented fields and versions.
  3. Compare file ID sets for equality, then compare every role, path, format, record count and primary key. Extra entries fail as well as omitted entries. IDs and paths shall be unique.
  4. Resolve canonical owner-relative POSIX paths below the supplied owner root. Absolute paths, parent traversal, drive syntax, backslashes, aliases such as dot segments, and payload symlinks fail. Unlisted directory files are not implicitly part of the dataset; completeness is defined by the pinned inventory.
  5. Read each regular file once and compare its SHA-256 against the manifest. For record arrays, require the pinned number of rows, object rows, present and unique primary keys, and all declared foreign keys to resolve to a target primary key. Keys are nonempty strings or integers; types remain distinct. Booleans, nulls, containers and floating-point keys fail. Self-references are permitted; acyclicity is outside this contract.
  6. Return immutable byte mappings only after every check passes. Consume those bytes rather than reopening payload paths. Persist the returned receipt separately from the manifest; its manifest digest is calculated over the supplied raw bytes.

Protocol fields

A contract has exactly version (value manifest-closure-contract/v1), files and foreign_keys. Its nonempty file array declares exactly id, role, path, format, record_count, primary_key per entry. A manifest has exactly version (value manifest-closure/v1) and files; each manifest entry repeats the contract entry and adds sha256, a lowercase hexadecimal SHA-256 digest. The resource descriptor schema defines the SHA-256 representation basis; this file-field protocol uses bare hex rather than its namespaced resource-identity form.

format is bytes or json-records. Byte files require null count and primary key. Record files require an integer count greater than or equal to zero and a nonempty primary-key field name. An explicitly empty array means zero declared records, not missing evidence. The foreign-key list is explicit, including when empty. Each declaration has exactly from_file, field, to_file, key; both files must be counted record files, and key must equal the target's declared primary key. Duplicate declarations fail. Additional domain predicates remain the consumer's responsibility; a foreign-key list does not establish physical validity.

Worked example: inputs, method and answer

The committed synthetic inputs are under tests/fixtures/data/manifest_closure/. The byte file contains synthetic original followed by a newline. The two record rows are:

[{"id":"a","parent":"a"},{"id":"b","parent":"a"}]

Independent hand calculation: the file set is {original, records}; its cardinality is two. The record key set is {a, b}, with two unique values and two rows. Both parent values are a, which belongs to that key set. The expected answer is complete integrity closure for two files and two records. The role “retained-original” describes a synthetic fixture and makes no claim about received private originals or Git retention.

The exact example contract pin is c77d245c1e6f361a596b8e3b799fa989b713314515ea0f060a61bfe92e3b6f93. It is computed from the committed contract bytes by the standard library SHA-256 implementation; the example test independently recomputes it. A consumer shall obtain a production pin from its reviewed configuration, not this example.

python scripts/data/manifest_closure.py \
  --root tests/fixtures/data/manifest_closure \
  --manifest tests/fixtures/data/manifest_closure/manifest.json \
  --contract tests/fixtures/data/manifest_closure/contract.json \
  --contract-sha256 c77d245c1e6f361a596b8e3b799fa989b713314515ea0f060a61bfe92e3b6f93 \
  --view working-tree

On success, standard output contains a manifest-closure-receipt/v1 object with file_count: 2, the manifest and contract digests, the view, integrity: verified and authority: not-established. The CLI emits no receipt on failure and returns a nonzero exit code. Its failure message deliberately omits payload values and filesystem paths. To preserve a receipt, capture standard output in a separate evidence artifact; do not insert it into the manifest being hashed.

Independent byte views and limits

Run acceptance independently against retained originals, working-tree bytes, materialized staged bytes and a fresh-checkout snapshot. The explicit view labels are retained-original, working-tree, staged and fresh-checkout. The caller supplies the correct materialized root and manifest bytes for each view; this utility neither exports the Git index nor creates a checkout. A label alone does not prove its provenance. A passing working tree cannot substitute for staged or fresh-checkout evidence. The regression suite uses independent disposable materializations and corrupts one without changing the others.

Filesystem inputs shall remain quiescent during validation. The utility does not provide an atomic filesystem snapshot or protection against a concurrent malicious filesystem writer. Receipt serialization and durable evidence storage are the consuming workflow's responsibility. Receipt equality or a matching contract pin establishes integrity only; independent source rights, retention, units, engineering qualification, task authority and publication authorization remain required. Existing manifests in other repositories need explicit adapters and independently reviewed contracts; no ecosystem-wide installation is claimed.

Verification

The test module tests/data/test_manifest_closure.py enumerates positive closure and negative omissions, redirects, duplicate JSON keys, invalid digest syntax, count and key errors, rehashed invalid semantics, traversal, symlinks, missing files, malformed documents, numeric overflow and independent views. A subprocess started with python -O verifies that production checks do not depend on assertions. Expected set and count results are derived in test docstrings by direct enumeration, independently of the validator.
