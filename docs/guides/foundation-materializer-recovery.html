Foundation materializer recovery

Summary

Interrupted journal and restore staging no longer reserve a fixed filename needed by the next rollback attempt. Each new attempt creates an exclusive staging file; existing residue is retained. Recovery uses an operator-trusted receipt, bound roots, matching destination bytes and verified backup bytes. A filename is not evidence of ownership, and receipts do not authenticate permission. This is the bounded recovery contract for issue 3858.

Inputs and method

The entry point is scripts/skills/materialize_profile.py. Report mode requires explicit source root, source revision, Foundation profile, target root, provider and an external transaction directory on the destination volume. Its JSON manifest binds the actual source bytes, profile and destination preimages. Apply requires that exact manifest and roots. The existing Foundation profile is the payload boundary; no arbitrary profile expansion is supported.

Before recovery, stop competing writers through external coordination and retain the entire transaction directory. Load a separately trusted receipt or the last trusted journal.json. Never select the newest pending file as authority: it may be partial, stale or unrelated. If the authoritative receipt is missing or cannot be trusted, automatic recovery is NOT_EVALUATED; reconcile the transaction manually without deleting the evidence.

python -B scripts/skills/materialize_profile.py --rollback \
  --source-root "$SOURCE_ROOT" --target-root "$TARGET_ROOT" \
  --transaction-dir "$TRANSACTION_ROOT" --manifest "$TRUSTED_RECEIPT"

The environment must supply the utility's dependencies. All root variables denote explicit absolute paths chosen outside discovery subtrees for transaction storage. This command performs rollback, not forward completion of interrupted apply. A new apply after rollback requires a fresh report and a new transaction directory.

Observed destinationRecovery disposition
Equals recorded preimage, including recorded absenceAlready restored; skip replacement.
Equals postimage with replace-intent or written stateRestore verified backup bytes, or remove the transaction-created file when its preimage was absent.
Differs from bothReject before rollback writes; preserve the later writer.
Backup missing, linked or digest-mismatchedReject restoration; retain evidence.
Table 2. Equality is evaluated on actual bytes through the existing digest guards.

Backup bytes are checked during candidate selection and again after reading them for staging. Replacement rechecks the destination immediately before mutation. Already restored entries need no staging, so retry does not depend on candidate numbering from an earlier attempt. Only recorded, identity-matching empty directories are removed; foreign children prevent directory cleanup.

Worked example

The executable example is tests/skills/test_materialize_profile_recovery.py::test_repeated_rollback_preserves_staging_and_backup_evidence. Two selected skill files initially contain literal valid frontmatter plus original. Apply installs the synthetic profile bytes. Existing journal.pending and rollback-0000.payload contain unrelated literal bytes. Rollback is interrupted at the second replacement after a restore file has been staged.

On retry with the saved receipt, the first restored file equals its preimage and is skipped. The remaining file equals its postimage, so verified original bytes are copied into a fresh exclusive staging file and restored. The answer is both original files restored byte for byte, all original backups and interrupted staging unchanged, and a rolled-back receipt. A further retry has the same result. Expected bytes are the explicit example inputs, not values produced by the implementation under test.

*.preimage; numbered apply *.payloadBackup and staged source evidence; retained unless a staged payload was consumed by replacement.
Table 3. Retained evidence is expected residue, not an automatic cleanup authorization.

Each new staging file is flushed and file-fsynced before replacement. Exclusive creation guards name collisions; random names do not authenticate ownership. No existing pending or restore file is overwritten. Successful journal replacement publishes that attempt's receipt. Directory fsync, crash persistence of directory entries, whole-transaction atomicity and hostile concurrent-writer protection are not established. A storage or permission failure can still prevent recovery; unique staging removes fixed-name collisions, not these constraints.

A whole-set reapply is a validated no-op. In a mixed apply, entries whose current bytes already equal source bytes are omitted from the write set; their inode and modification time are preserved by the utility. This does not promise preservation of unrelated access metadata or protection from another writer. Rollback retains those pre-existing identical files.

Evidence boundaries

  • Git mode 120000 records a tracked symlink. A checkout with symlink materialization disabled may hold regular path-file bytes instead. Record both git ls-files -s -- .codex/skills and no-follow filesystem type; neither observation alone establishes native discovery. The materializer rejects indexed symlinks in the destination skills subtree even if their working bytes are regular.
  • Historical evidence in docs/reports/2026-09-11-agent-foundation-evidence.json records omitted family-nested project skills and a corrected flat fixture. That is a measured layout limitation, not a universal numeric traversal depth. A quantitative depth threshold is NOT_EVALUATED from the available public record. Native traversal repair and fresh native-provider probes remain outside this recovery change.
  • Issue 3858 distinguishes a historical 15-file source digest from a 23-item review packet. These are different sets; a source digest does not cover packet-only receipts or instructions. Exact historical membership and digest reproduction are not established here. New review evidence must enumerate both sets, record revision and raw-byte digest per member, and identify any excluded packet item.
  • Test-byte normalization requires recorded provenance: raw input digest, declared transformation, transformed digest and the exact bytes reviewed/executed. The profile permits only explicitly declared crlf-to-lf comparison; apply preserves source bytes and destination digests cover actual bytes. Historical normalization must not silently be treated as raw-byte equivalence. This change introduces no test-byte normalization.
  • The optional mock-envelope reference remains excluded by config/skills/profiles/foundation.yaml; its absence is a declared profile limitation. Recovery does not install missing examples or dependencies.

Checks and review limits

The materializer, filesystem and recovery regression suites exercise byte guards, interrupted publication, interrupted rollback, identical-entry metadata and real controlled global/system Git configuration exclusion. The latter first confirms that a control Git invocation reads the supplied configuration marker, then confirms that the production isolated reader cannot see it. Configuration bytes remain unchanged. Synthetic fixtures do not qualify installed runtime behavior.

The plan assessment and artifact inspection are local defect-hunting checks. Independent reciprocal provider review remains required before merge; it is not claimed by this guide. No live installation, hook repair or broad closure is included.
