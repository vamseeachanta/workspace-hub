#3555 Codex fleet configuration redesign

Date: 2026-08-02 · Status: owner-approved design, implementation still gated by adversarial plan review · Scope: every detected Codex installation in the workstation fleet

Owner decisions
  • Roll out immediately across the fleet rather than canary-first so requirement gaps surface quickly.
  • Enable request_user_input in Default mode across the fleet.
  • Run Codex with --yolo for work in trusted, solid repositories across the fleet.
  • Record unreachable, incompatible, or undeclared installations explicitly; do not treat configuration intent as successful coverage.

Outcome

The repository will own one merge-safe Codex baseline, one cross-platform mechanism that launches Codex in YOLO mode for trusted registered repo roots, and one attestation path that proves the effective configuration on each detected installation. Default-mode sessions will be able to ask structured requirements questions without switching to Plan mode.

default_mode_request_user_input is an under-development Codex 0.146.0 feature. The rollout will therefore probe each installed CLI for the key before replacing that machine's configuration. Stable workflow-critical features will be pinned intentionally; unrelated feature flags will remain at product defaults.

YOLO contract

ConcernDesign
Launch behaviorThe fleet launcher/wrapper will add --yolo at the highest practical CLI precedence for interactive and non-interactive Codex entry points.
ScopeYOLO is authorized when the working directory resolves inside a trusted repo root declared by the fleet registry or an empirically attested checkout inventory.
Escape hatchA clearly named raw/safe entry point will invoke the real Codex binary without the wrapper for untrusted directories, diagnostics, or future policy changes.
SecretsYOLO does not authorize hardcoded tokens, credential publication, or expansion outside the user's requested repo scope.
VerificationAttestation will record wrapper resolution, real binary path, CLI version, trusted-root decision, and a bounded effective-permission probe without recording credentials or private task content.

Deployment architecture

  1. Inventory: enumerate registered Codex-capable machines and actual reachable installations. Reconcile discrepancies before any fleet-complete claim.
  2. Canonical config: update config/agents/codex/config.toml to current syntax and contract-critical settings.
  3. Merge: extend scripts/_core/sync-agent-configs.sh to own only named keys and preserve authentication, MCP/plugin state, trust entries, machine-local paths, and unrelated settings.
  4. Launch: install a repo-managed cross-platform YOLO wrapper for Bash/Git Bash and PowerShell-compatible machines; avoid modifying vendor package files.
  5. Validate: parse TOML, query codex features list, verify wrapper precedence, and exercise Default-mode request_user_input behavior.
  6. Attest: emit per-machine success, incompatible-version, unreachable, missing-installation, or registry-drift evidence.

Fleet semantics

“Immediate fleet rollout” means every machine will be attempted in the same approved rollout wave. Reachable machines will be updated and verified immediately. Unreachable machines will remain named pending items, not silently excluded. Current evidence already shows roster drift: the public registry declares Codex on two Windows hosts, while the active Linux environment also runs Codex 0.146.0.

Settings intentionally excluded

  • Native memories: excluded pending conflict analysis with the repo-managed MEMORY.runtime.md read-back path.
  • Automatic approval reviewer: excluded because repository plan/user approval gates remain load-bearing even when command sandbox approval is bypassed.
  • Multi-agent v2 and other unstable flags: excluded; the requested Default-mode input flag is the only deliberate under-development exception.
  • Universal concurrency cap: excluded from the baseline because shared-tenancy and compute capacity differ by machine; any cap will be a tested machine overlay.
  • Hardcoded model upgrade: excluded from this configuration change and routed through the existing model-registry drift work.

Failure handling

  • An unsupported feature or invalid footer identifier will fail before replacement and preserve the prior machine config.
  • A wrapper that cannot resolve the real Codex binary will fail closed with a repair command.
  • A directory outside the trusted-root set will route to the safe entry point or stop for explicit operator choice.
  • A machine that cannot be reached will be reported as UNREACHABLE; it will not count as rolled out.
  • Default-mode questioning will remain optional model behavior, not a requirement to interrupt every task.

Testing and completion evidence

Implementation will use TDD. Tests will cover TOML key-level merging, legacy statusline migration, unsupported-feature rollback, cross-platform wrapper argument forwarding, trusted-root matching, safe escape behavior, wrapper recursion prevention, Default-mode tool availability, dry-run behavior, and per-machine evidence rendering. Completion will require legal scanning, adversarial code/artifact review, an issue implementation comment, and the repository cleanup audit.
