Strict input boundaries

Shared helpers normalize parser failures and prevent rejected arguments or embedded JSON from escaping their intended boundary. Consumer adoption is partial; inventory entries are discovery candidates, not a claim of repository-wide protection.

Use and limits

  • lib.strict_json.loads/read/load: use for untrusted JSON bytes, binary streams or regular files. Supply positive exact-integer max_bytes, max_depth and max_integer_digits. There are no default resource limits: RFC 8259 section 9 and Python 3.11 JSON implementation limitations prescribe no universal ceiling. A consumer must derive its budget from its own contract. The stream interface retains existing descriptor validation; the file interface rejects special files before reading and fails closed where required operating-system flags are absent. It does not establish ancestor trust.
  • The scanner counts open containers outside quoted strings before decoding; duplicate keys and nonstandard numeric constants are rejected. Floating-point overflow is rejected. Decoder resource and encoding exceptions become InputError with a fixed public dictionary. System termination and complete memory exhaustion remain outside application guarantees. The byte budget bounds input, not total decoder heap allocation.
  • Manifest consumers retain their pre-existing byte budgets. The same budget is a deliberately loose upper bound on depth and integer width: each opener and decimal digit consumes at least one byte (RFC 8259 sections 4–6). This is exception hardening, not a newly qualified depth or integer-domain policy. The stricter interpreter digit guard can still reject values within that budget.
  • lib.safe_cli.SafeArgumentParser: use at sensitive CLI boundaries and for inherited subparsers. Failure keeps usage and status 2, with the fixed diagnostic invalid arguments. Program names, usage, help and definitions must be trusted static text; application diagnostics and help defaults need separate review.
  • lib.strict_yaml.strict_yaml_load: use instead of ordinary safe loading when duplicate keys must fail. It retains SafeLoader constructors, rejects duplicate constructed keys and merge collisions, and returns a fixed public error. It is not a size/depth/alias resource limiter. exact_int and exact_bool reject cross-type equality; schema callers still check ranges and required fields.
  • PyYAML SafeLoader uses YAML 1.1-style implicit resolvers. In the tested resolver, [no, on, 1e3, 0o17] becomes [false, true, "1e3", "0o17"]. YAML 1.2.2 core resolution section 10.3.2 instead treats no/on as strings, recognizes scientific notation as float and the 0o prefix as octal. This helper preserves PyYAML behavior; it does not claim YAML 1.2 conformance. Merge-key overrides are deliberately rejected rather than silently combined.
  • lib.script_json.script_json: use for data inserted into script elements, including JSON data blocks and JavaScript data expressions. Unicode escapes replace HTML-significant characters and line separators; JSON readback is unchanged. This is not an HTML attribute encoder or a JavaScript program validator.

Adoption and remaining work

Both scaffold manifest readers use strict JSON without changing their retained-descriptor lifecycle. The authority-management and issue-reference CLIs use the non-reflecting parser. The skill-index configuration reader rejects duplicate YAML keys. Calculation-chart scripts and completeness output use the shared serializer. The authority codec is intentionally unchanged: an existing draft adds integer bounds before canonical serialization. A separate descriptor-reader draft retains responsibility for descriptor lifecycle corrections.

Later migrations require consumer-specific budgets, schema decisions and compatibility tests. Canonical protocols, token-preserving redactors, subprocess output readers, log readers and static HTML snapshots are inventoried but not rewritten. These changes do not close the four audit issues. Independent provider review remains pending before merge.
