Configuration contract and worked example

Source: issue 4069, item 1; the Gitleaks v8.21.2 configuration documentation and TOML 1.0.0 tables and booleans. The selected policy rejects every custom rule table, so no default rule identifier list needs to be copied or maintained. The only permitted extension key is useDefault, with Boolean value true. No engineering equations, coefficients or acceptance limits apply.

[extend]
useDefault = true

Method: parse the TOML; require that exact extension key set and value; reject any top-level rules declaration. Answer: the input above passes. Adding disabledRules = ["generic-api-key"] under the extension fails even though defaults remain enabled. Adding a [[rules]] table with either an existing or a new identifier also fails. These expected outcomes follow directly from the contract, independently of the validator implementation.

The tests in tests/quality/test_gitleaks_config.py check the real configuration and synthetic negative controls. The separate path-walker control parses its custom-rule input directly so that the path traversal check remains exercised after the loader begins rejecting custom rules.

Every allow-list path shall start with ^, end with $ or a directory slash, and have an individual reason immediately above it. Whole top-level directories and wildcard paths are rejected. The existing vendored test-asset subdirectory is the only permitted directory prefix. Fingerprint groups require adjacent reason comments; fingerprint bytes, order and membership remain unchanged.

Runtime worked example

Inputs: a temporary Git repository, one synthetic token assembled from fragments at runtime, a benign documentation line, and a copy of the repository configuration. The token follows the aws-access-token rule in the pinned default configuration; the test docstring gives an independent character-count and entropy calculation. No token is stored in the test source or printed.

gitleaks detect --source "$fixture" --config "$config" --exit-code 1 --redact=100 --report-format json --report-path "$report"
gitleaks protect --staged --source "$fixture" --config "$config" --exit-code 1 --redact=100 --report-format json --report-path "$report"

Method: for history, retain the synthetic input in an earlier commit and replace the current file with benign text; for staged mode, put the input only in the index. Answer required by --exit-code 1: the positive input exits nonzero and the redacted report identifies control.txt:1:aws-access-token. The benign input exits zero. Repeating the same positive input with an empty custom configuration exits zero, demonstrating the failure that defaults prevent. Reports and captured output are checked for synthetic-content leakage before metadata is examined. Missing binaries produce an explicit skip, not a detection claim. The scanner wrapper uses full redaction and withholds raw diagnostic output; missing configurations and scanner errors fail the scan.

The default rule identifier used by the controls is read from the pinned configuration cited above. A live comparison with embedded default-only detection is NOT_EVALUATED until Gitleaks is available. Static rejection of every custom rule table protects the entire default identifier set without maintaining a copy.
