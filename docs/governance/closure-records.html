Closure record drafts

The read-only builder prepares successor CSV, body-restoration records, replacement-scope drafts, import-label proposals, retirement triage and yes/no decisions. Outputs are proposals for maintainer assessment. No issue is posted, edited, labelled, closed or reopened. A supplied snapshot is not an exhaustive audit.

Sources and method

Issue-closing procedure, sections A.4, B, C.3, C.4, D.1 and E, supplies the disposition criteria. The existing closure checker supplies closure and import evaluation. No engineering equations or material coefficients apply.

Slice 1 will use explicit candidate mappings rather than infer successors from unrelated mentions in issue text. Open successors will remain subject to scope confirmation. Closed successors will qualify only when every existing checker rule passes. Cycles, missing targets, reopened targets without scope assessment, and a completed state without evidence will remain unresolved.

Slice 2 will separate verified original bodies from replacement scope. A caller will supply the original text, its source and an explicit verification flag. An edit summary alone will never populate a restore-body field. Missing evidence will produce NOT_EVALUATED rather than reconstructed text.

Slice 3 will produce import and retirement proposals and one yes/no question per proposed action. Import candidates will follow procedure E.9 and lack resolving delivery/test evidence. Retirement proposals will require an open issue, a reason, and either a retirement reference or an open destination.

Input and execution

Input is JSON on standard input. The issues array uses normalized checker records plus required repository_slug, number and state. Closed records retain checker evidence fields. The successors object maps fully qualified issue identities to candidate identities; both endpoints require independent assessment. Recovery records use issue, original_body, original_source, original_verified and replacing_scope. Retirement records use issue, action, reason, and retirement_reference or destination.

python scripts/governance/closure_records.py < docs/governance/examples/closure-records.json
python scripts/governance/closure_records.py --successor-csv < docs/governance/examples/closure-records.json

The example uses synthetic identities and shall not be submitted for live API validation. For an authorized real snapshot, --verify-live will read each unique reference with gh api --method GET and check its canonical repository and number. Structured identities require issues and reject pull requests. Mentions in restored or replacement text may resolve to canonical /pull/N URLs and report PASS (pull request). An identity used in both contexts retains the issue-only requirement. Source closure evidence is not scanned for draft references. Validation returns a nonzero exit status if any reference fails or remains NOT_EVALUATED. Live validation establishes reference resolution only; it does not refresh closure evidence or authenticate supplied original-body verification. JSON output retains each reference result; CSV output contains only successor rows. Malformed proposed-text identities are rejected before any live request; the CLI reports an input error with exit status 2. The shared extractor treats hash-prefixed digits as reference candidates. Zero, leading-zero and non-ASCII numbers, and dot-segment repository names, reject the whole input, including offline drafts. Literal colours or URL fragments with these shapes may therefore prevent drafting; verified original text is not rewritten.

--retries sets retries after the first request (integer from 0 to 10, default 5). --retry-delay sets seconds between retries (finite, from 0 to 300, default 60). Only HTTP 502, 503 and 504 failures are retried; other failures return NOT_EVALUATED immediately. The caps bound execution to eleven requests and 3,000 seconds of retry delay per reference, excluding request duration. These are operational limits, not acceptance criteria from the issue-closing procedure.

Known limits and remaining audit work

The builder does not enumerate repositories, infer a retired repository identity, reconstruct edit histories, or establish the provenance of caller-supplied evidence. Empty inputs mean no supplied records, not proof of no findings. A complete audit will require an enumerated repository/date boundary, pagination evidence, exact original-body sources and a retirement reference. The maintainer decision sheet will be assessed before any issue mutation.

Reference validation checks the canonical repository and issue number together. A successful response after an issue transfer, or an equal number in another repository, does not establish the identity originally cited. This defect class also applies to other issue-audit consumers.

The bounded recovery observations record the six explicitly requested histories, their evidence gaps and draft decisions. They do not claim recovery of original text or a complete closure sweep.
