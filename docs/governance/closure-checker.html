Read-only issue closure checker

The existing checker evaluates the ten closure rules and produces per-rule CSV and a Markdown summary. This change bounds individual API requests, preserves exact query identity in cache filenames, and requires a command alongside a test count. Results describe the evidence available at collection time, not delivery certification. No GitHub write is performed.

Sources and method

Issue-closing procedure, sections B.3 and E.4, requires a test command with a count. Issue 4073, plan item 3, supplies the ceiling of 500 API calls per run. These are workflow criteria; no engineering coefficients or physical equations apply. Request arithmetic is C = R + G, where R is the number of uncached REST response pages and G is the number of uncached GraphQL requests. Failed requests also consume budget. Cache hits consume none.

Each pagination page is requested separately through an explicit GET. The response Link header selects the next page, restricted to the public API origin. A repeated page, incomplete search result, malformed response or exhausted budget raises an error instead of saving a complete list. Budget exhaustion propagates through optional evidence reads. Collection responses must be JSON lists or search envelopes with list-valued items, a nonnegative integer total_count and, when present, a Boolean incomplete_results. An unknown object or scalar response is rejected before caching. Body references retain successor-state lookups, but only references in closing comments trigger recursive delivery-evidence reads. Cache filenames use SHA-256 of the exact request string; this digest identifies a request, not the integrity or freshness of its response. Legacy punctuation-based cache entries are not reused.

Common test tools must appear in command context: at a statement's start, in inline code, after an execution verb, or after a Tests:, Command: or Builder: label. Labelled custom builders require arguments or a script path. Placeholder values and explicit non-execution within the same clause are rejected, including negation around inline code. For example, pytest was not run; 3 tests remain. and Command: none; 3 passed both fail rule 4. A count alone also fails. This is a lexical text check; commands are never executed by the checker, and their claimed results are not independently authenticated.

Usage

python scripts/governance/check_issue_closures.py --fixture docs/governance/examples/closure-command-evidence.json --csv <output>.csv --markdown <output>.md
python scripts/governance/check_issue_closures.py --repo <repository> --issue <number> --cache-dir <cache> --csv <output>.csv --markdown <output>.md
python scripts/governance/check_issue_closures.py --repo <repository> --closed-from YYYY-MM-DD --closed-to YYYY-MM-DD --auditor <classification>.csv --cache-dir <cache> --csv <output>.csv --markdown <output>.md

The auditor CSV columns are number,auditor_class. Classes are DONE, PARTLY DONE and CLOSED WITHOUT DELIVERY. Agreement is matched classifications divided by supplied classifications for collected issues. It is not an estimate for uncollected issues.

Live observation and manual comparison

A read-only search for digitalmodel issues closed on 2026-07-27 returned 42 issues at the time of collection on 2026-10-22. The initial bounded invocation stopped at 500 requests after saving five complete issue observations. After body-only reference expansion was removed, collection resumed from saved responses and digest-checked observations: all 42 issues completed with 284 additional requests. Neither invocation exceeded its request ceiling. The first five observations were retained rather than fetched again.

Manual inspection classified each closing comment as lacking the resolving revision or pull request required by B.1. The checker returned 42 FAIL, zero WARN and zero PASS: agreement is 42 divided by 42, or 100.0 %. This compares overall classifications only, not every rule or the actual delivery of the underlying work. The manual comparison was performed with the checker results visible; it is not a blinded or independent-provider audit.

The compact comparison records issue numbers, manual classifications, checker outcomes, the manual criterion and SHA-256 digests of the closing comment text. Raw responses and complete observations are retained outside the repository; they are not published by this change. The search response digest is 8537c05e78f7234dead6e60bd8941eb4de2c07ca962a5a2af782bcafb8fba7c8. The public case URLs are formed from the repository being audited and the recorded issue numbers. Source comments can subsequently change; the digest identifies the text read during this collection.

Known limits

Collection currently evaluates the final closure represented by each issue; historical reopen and close cycles are not separate report rows. Review reads still inspect one page, and all related merged pull requests are checked rather than only the closing pull request. Existing neutralized public-case fixtures are regression models, not byte-for-byte API archives. Optional API errors other than budget exhaustion may still appear as absent evidence. Body edits and successor state are read at collection time, not reconstructed at closure time. Cached responses have no expiry; use a separate cache directory for a fresh observation. Independent provider review remains required before merge.
