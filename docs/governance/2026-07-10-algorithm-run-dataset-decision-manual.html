3. Identity and Determinism

The identifier contract uses domain-separated SHA-256 digests over canonical records. The child identity issue will lock the canonical JSON profile and byte-level construction. The following formula is normative in meaning and illustrative in serialization:

algorithm_version_id = sha256(
  algorithm_id + semantic_version + clean_git_commit +
  input_schema_version + output_schema_version + environment_digest
)

input_record_id = sha256(
  role + native_schema_version + source_snapshot + transformation_id +
  artifact_sha256 + redistribution_rights + complete_replay_location
)

input_set_id = sha256(sorted(role, input_record_id))

run_id = sha256(
  algorithm_version_id + input_set_id +
  canonical_execution_parameters + explicit_seed_descriptor
)

output_set_id = sha256(sorted(role, native_schema_version, equality_digest))
  • An input binding ID covers role, schema, source snapshot, transformation, and artifact digest. It is computed before and independently of run_id; a separate association links it to the run.
  • seed is explicit even when the algorithm declares no randomness.
  • Hardware and numeric-library details that can alter results belong in the environment manifest.
  • The output set is not part of run_id; it is the measured equality target for exact replay.
  • Byte hash is the default equality digest. A non-stable container format requires a versioned semantic canonicalizer, both raw and semantic hashes, and explicit approval; otherwise it is presentation-only.
  • A transient infrastructure error is not a reproducible failed run and does not publish.
  • A reproducible failed run compares normalized failure signatures and curated diagnostic digests instead of a successful output set.

7. Promotion and Acceptance

Contract states: Emitted, Validated, Replayed, Draft Rendered, Reviewed, HF Candidate, Report Pinned, Accepted, and Rejected.

  1. Emit locally: create a closed run bundle outside the public dataset.
  2. Validate: enforce schemas, canonicalization, hashes, licenses, public input completeness, clean source, and secret/legal scans.
  3. Reproduce: rerun from public candidate inputs in a clean environment. Successful runs compare output equality; reproducible failures compare normalized failure signatures and curated diagnostic digests.
  4. Draft-render: render the rolling report against the candidate run set without presenting it as accepted.
  5. Review: record explicit human promotion approval and adversarial artifact review.
  6. Commit to HF: preupload large blobs when needed, then create one candidate commit containing complete records and references.
  7. Pin the report: update the source-repository report to the exact candidate revision.
  8. Verify and accept: verify all objects, tables, report links, source commit, and exclusion rules; then append a Publication record that references the candidate revision and report commit.
Cross-system atomicity: GitHub and Hugging Face cannot commit atomically. The contract therefore guarantees atomic acceptance, not atomic visibility. A complete candidate HF commit may be visible before its source report lands, but it remains excluded from the accepted catalog, metrics, insights, and decisions until the final cross-system verification succeeds. Run records never mutate from candidate to accepted; a later append-only Publication record carries acceptance and can be superseded only by another explicit disposition record.

The publisher owns orphan-candidate recovery. It resumes from HF Candidate when the report pin can be completed; otherwise it appends a rejected disposition without mutating run records.

Accepted: validated, replayed, reviewed, HF-committed, report-pinned, and verified. Rejected: dirty source, missing input, uncertain rights, invalid schema, bad hash, nondeterministic replay, incomplete review, broken pin, or failed post-publication verification.

8. Existing Ecosystem Compatibility

The run ledger extends the existing execution and report contracts; it does not replace them.

Propagation across the repository ecosystem uses the shared workspace-hub schema, the fresh workflow discovery manifest, thin repository adapters, and common conformance tests. A repository may add native input, output, metric, and artifact schemas but may not redefine the shared envelope or promotion gates. Phase 1 publishes only the two named domain datasets; other registered repositories adopt the contract through their own independently approved issues when a public-run use case exists.

An existing registry workflow_id uses repo:id@integer-version. The run ledger will preserve that execution reference but will not infer a semantic algorithm version from the integer. A source-repository algorithm descriptor will declare the semantic version and map it to the exact workflow registry row, source commit, schemas, and environment.
