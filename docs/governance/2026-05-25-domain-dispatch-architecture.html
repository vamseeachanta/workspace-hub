Domain-Categorized Boards + Machine/Provider Dispatch

Architecture specification · ecosystem kanban · drafted 2026-05-25 · status: plan-review (awaiting user status:plan-approved)

GitHub is the center of record. Every unit of work is a GitHub issue; progress, updates, code status (author / review / push), and TDD state all live on GitHub. The kanban boards and dispatch queues are views and routers over that truth, never a parallel store.

6. Dispatch mechanics & safety

Tooling: scripts/dispatch/route.py (proposer), scripts/dispatch/dispatch.py (queue writer + capacity), config in routing-rules.yaml.

route.py            # dry-run summary (machine x provider)
route.py --detail   # per-card listing
route.py --apply    # write GH labels  (Phase B; disabled until approved)
dispatch.py         # dry-run: queue files that would be written
dispatch.py --write # materialize .claude/dispatch/<machine>.yaml  (Phase B)
dispatch.py --capacity   # supply (live agents) vs demand (assigned cards)
Runaway-pipeline safeguards. route.py only ever moves a card to dispatch:ready; it never spawns a worker. Execution is pull-based — each machine drains its own queue. WIP caps + the shared codex/hermes budget pool provide backpressure. initial_status: triage stays the load-bearing valve so a freshly loaded card cannot be auto-claimed. Phase A (this spec's build) wrote only local files; Phase B's GitHub mutations are gated on user approval and individually reversible.
