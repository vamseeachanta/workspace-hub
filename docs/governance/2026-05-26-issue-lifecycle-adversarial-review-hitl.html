Issue Lifecycle — Adversarial Review & Human-in-the-Loop

Governance flowchart · workspace-hub ecosystem · 2026-05-26 · synthesized from current session-memory practice (see source-map table at the end).

GitHub is the center of record — every unit of work is a GitHub issue; there are no local task IDs. The lifecycle has two non-negotiable adversarial-review gates (plan-stage and code-stage) and three human-in-the-loop gates (plan-approve, PR-merge, completeness-verify/close). Reviews are never skipped — what scales with scope is review depth (T1/T2/T3), not its presence.

3. Invariants

  • Review presence is fixed; depth is the dial. Never surface "skip review" as an option — only "T1-scoped single provider" vs. "full T2/T3."
  • Self-review ≠ adversarial review. The author finding their own bugs mid-build does not satisfy gate A or B.
  • The human gates are load-bearing, not friction. Provide links + CLI; the user performs the action. This holds even after repeated "continue" authorizations in a session.
  • If a provider is unavailable (Codex stdin-hang, Gemini 429/trust-folder), record it explicitly and proceed with available providers — never silently downgrade to "no review."
  • Discovery before execution. A plan-approved label is a contract about intent, not current state; verify the corpus first.
