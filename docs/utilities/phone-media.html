Phone media organization

The organizer copies supported files from PHONE/usb/ archives into YYYY/MM/PHONE/original-camera-folder/ destinations. Originals remain in place. Cross-phone byte duplicates are reported without deletion. A dry run is the default. Input and output directories shall be separate, non-overlapping trees.

Usage

Python 3.11 or later is required for hashlib.file_digest. Install ExifTool separately for embedded metadata extraction. Python packages are not required by the utility. Run from the repository root:

python scripts/utilities/phone_media.py phone-media organized-media > plan.json
python scripts/utilities/phone_media.py phone-media organized-media --apply > result.json

Reports contain relative filenames, content hashes, date provenance, duplicate groups, warnings and a conflicts list of relative destinations and reasons. A dry run exits successfully even when that list is nonempty; inspect it before using --apply, which refuses conflicting destinations before any copy. Reports can contain personal filenames and shall remain with private archives rather than be committed to this public repository. No real archive is read or copied by the regression tests.

Method

  1. Inventory HEIC, MOV, PNG, JPG, JPEG and AAE files, matching extensions without case sensitivity. Other extensions and directories outside each phone's usb tree are ignored. Scanned symlinks and Windows reparse points (including junctions) are rejected before directory traversal. Destination aliases, including output ancestors, are also rejected.
  2. For each media file, read DateTimeOriginal, then Keys CreationDate, then CreateDate, then MediaCreateDate with ExifTool UTF-8 JSON output. The first valid timestamp supplies the year and month. String dates retain their local calendar fields; offsets do not shift that month. Integer MOV CreateDate and MediaCreateDate fields are treated as UTC per the QuickTime specification and recorded as CreateDate_utc or MediaCreateDate_utc in date_source. They are not converted to the computer's timezone. Some cameras store local values in these fields; without an offset-bearing date the original capture-local month is unknown. Invalid values produce warnings. With no valid value, use file mtime interpreted in UTC, consistent across computer timezones. The acquisition workflow is responsible for establishing whether mtime represents capture time. Missing ExifTool produces explicit fallback warnings.
  3. Match AAE sidecars to a same-directory, case-insensitive filename stem. Prefer a still image to a MOV, then lexical filename order if multiple stills match. Copy the sidecar into its selected companion's month and directory. Warn if companions span months. An orphan sidecar uses its own UTC mtime and produces a warning. An edited filename with a different stem is not inferred.
  4. Retain the phone and original relative directory below the calendar folder. This avoids camera-folder filename collisions and keeps original names unchanged.
  5. Compute SHA-256 over each complete file. A duplicate group is reported only when identical media digests occur in more than one phone directory. Sidecars are copied and hashed but excluded from duplicate groups. Different encodings, resolutions or edits are not perceptual duplicates under this criterion.
  6. Before copying, reject all existing destinations whose bytes differ. Use exclusive file creation and verify the copied digest before preserving timestamps and mode with copystat. Identical existing destinations are reused. No existing file is overwritten. A partial or mismatched copy is retained for inspection. Errors identify its relative destination and reason; a later dry run lists it in conflicts, and a later apply refuses it.

Tag precedence, UTC fallback and pairing priority are declared application policies. No fitted coefficients or engineering acceptance limits are used.

Worked example

These inputs are synthetic. Both image files contain the same literal bytes; the sidecar contains distinct edit bytes.

Input relative to archiveMetadataExpected destination
phone-a/usb/100APPLE/IMG.JPGDateTimeOriginal = 2024:02:29 10:20:302024/02/phone-a/100APPLE/IMG.JPG
phone-a/usb/100APPLE/img.AAEPaired with IMG.JPG2024/02/phone-a/100APPLE/img.AAE
phone-b/usb/101APPLE/COPY.JPGDateTimeOriginal = 2024:02:29 10:20:302024/02/phone-b/101APPLE/COPY.JPG

Table 2. Hand-calculated calendar destinations.

Reading the first four date digits gives year 2024; the next date field gives month 02. The sidecar inherits that pair. Equal image bytes yield equal SHA-256 digests, so the two images form one cross-phone group; all three originals remain. With absent metadata and mtime zero, the Unix epoch definition gives 1970/01 in UTC. The tests write these expectations independently of the organizer.

Verification and limits

The synthetic regression suite covers calendar leap dates, invalid dates, timezone policy, missing metadata, all requested extensions, sidecars, duplicates, collisions, reruns, overwrite refusal, symlinks, CLI dry runs and a changed-source copy failure. Run:

python -m pytest tests/utilities/test_phone_media.py -q -p no:cacheprovider

A month-boundary regression uses a still dated 2024:02:29 20:00:00-06:00 and a MOV dated 2024:03:01 02:00:00 in UTC. With Keys CreationDate matching the still, both media files and the AAE go into 2024/02. Without it, the MOV goes into 2024/03 with a UTC basis, the AAE follows the still into 2024/02, and the report warns that companions span months. Windows reparse attributes are simulated in portable tests; native junction behavior requires Windows testing.

The source archive and destination shall remain quiescent during a run. Alias checks and exclusive creation do not establish protection against hostile concurrent directory replacement. This utility is not a transactional snapshot: failures may leave completed copies and an inspection copy. It does not recover from an interrupted copy automatically. A successful run verifies copy bytes, not backup redundancy, filesystem creation time, extended attributes or capture-date truth. Real-format ExifTool extraction requires an installed ExifTool and representative private media; adapter tests alone do not establish that integration.
