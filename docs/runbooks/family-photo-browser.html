Family photo browser evaluation

Summary: Trial Immich first for private family browsing; retain PhotoPrism as the alternative when folder-oriented indexing is preferred. This is a documentation-based trial order, not a deployment acceptance result. Neither product has been installed or tested against the archive by this evaluation. All real deployment checks remain NOT_EVALUATED.

Scope and basis

Issue #3588 requests browsing and search of an existing family archive over the tailnet, with no public media serving. The related archive epic #3589 separates organization and cross-phone content deduplication into #3585. Browser indexing must preserve that archive and must not replace its backup or deduplication workflow. The existing archive handoff establishes context only; no private locations, device identifiers, media, or inherited capacity estimates are reproduced here.

The implementation has three slices: a source-backed candidate comparison; an offline acceptance evaluator; and a synthetic worked example plus an operational trial procedure. Installing either service, changing access policy, reading the archive and scheduling jobs are later work. No deployment configuration is applied.

Recommendation and limits

Immich is the first trial candidate because its documented external-library timeline, people search and partner sharing closely match the requested family browsing workflow. PhotoPrism remains a credible alternative for indexing a curated folder archive in place. This preference is an interpretation of the comparison, without a numerical score. It does not establish usability, speed, accuracy, current security posture, licensing suitability or operating cost.

The publication date of a living documentation page is not a release pin. Recheck the selected release's installation, backup, upgrade and role documentation before deployment. No undocumented hardware floor, storage ratio, face threshold or acceptance percentage is embedded in the evaluator.

Read-only trial procedure

A maintainer will authorize deployment and private archive access separately. Keep the trial records in private storage, with release, image digest, observation date, test method and evidence locators. The public example contains no real results. Before starting, specify acceptable indexing time, preview latency, memory, disk and CPU budgets based on the intended environment; absent budgets leave resource_fit unevaluated.

  1. Prepare an authorized, representative sample without moving or deleting originals. Include HEIC, JPEG, PNG, MOV, a Live Photo pair, an edited image and its sidecar, known capture dates and a missing-date case, an exact duplicate across folders, a visually similar non-duplicate, and consenting face examples. These are coverage categories, not a statistical sample-size claim. Record expected dates, orientation, relationships and file digests independently before indexing.
  2. Use the selected release's official deployment instructions. Bind the application only to loopback; publish no database or machine-learning service ports. Mount originals read-only into every process that can access them; use separate writable database, index and thumbnail storage. Do not use import/move or mobile auto-upload on the archive. Keep application authentication and local face processing enabled. Record configuration inspection and the absence of external image-processing endpoints.
  3. Configure Serve without Funnel. Check Serve and Funnel state, container mappings, host listeners, existing reverse proxies and firewall rules. Verify browsing from an authorized family device and denial from an unauthorized tailnet identity, a non-tailnet LAN device, and an external network. Include IPv6 and authenticated device shares. If those negative probes cannot be performed, leave tailnet_only unevaluated; a missing public listener alone is insufficient.
  4. Run the feature procedures in the table below. Compare archive digests before and after; do not exercise deletion against real originals. Verify mount read-only enforcement with a disposable synthetic fixture. Keep duplicate suggestions as observations only, preserving both files. Measure resource peaks and derived storage separately from original bytes and compare against the recorded budgets.
  5. Back up application state and derived metadata using the selected release's documented method. Perform an isolated restore and verify browsing, date metadata, face labels and sharing policy against the original record. Original media needs its own verified backup; a browser database is not an archive backup.
  6. Record statuses and evidence references, then run the offline evaluator. On a failed security or preservation check, stop serving the trial and keep the archive intact. Retain private evidence for diagnosis. On success, a maintainer reviews the evidence before deciding deployment. Rollback removes trial exposure and stops trial services; it does not delete originals or backups.

Offline evaluator and worked example

Run from the repository root; set the environment's shared cache and temporary directory as required by the local execution environment. The evaluator reads only the supplied JSON and writes a report to standard output. It installs no service and opens no network connection.

uv run --no-project python scripts/phone_media/evaluate_browser.py examples/phone-media/browser-assessment.json

The input has exactly one top-level candidates object containing immich, photoprism, or both. Each candidate has version (a recorded release string, or null) and a checks object. Check names are the keys above; omitted checks are unevaluated. Each supplied check has exactly status (PASS, FAIL or NOT_EVALUATED), kind (observed or documentation) and a nonblank reference. For unknowns, the reference points to a private gap record. Unknown keys, duplicate JSON keys, non-finite constants and malformed values are rejected.

Method: any FAIL makes a candidate BLOCKED. Otherwise any missing observed PASS or missing release makes it NOT_EVALUATED. Otherwise it is READY_FOR_REVIEW. A documentation PASS is converted to NOT_EVALUATED; a documented FAIL still blocks. This is a logical conjunction of this runbook's local prerequisites, not a sourced engineering equation or weighted scoring model. Evidence locators and release strings are omitted from output. They are not verified by the program: a plausible reference does not prove that a test happened. Never publish private assessment input.

Worked inputs are browser-assessment.json; the independently written answer is browser-answer.json. Immich has documented HEIC support but no observed preview, no installed version and no restore evidence, so it is NOT_EVALUATED. The synthetic PhotoPrism record contains an observed network FAIL, so it is BLOCKED despite other unknowns. The eligible list is empty. These are invented test records, not findings about either product. The example exits with code 1 by design.

Exit codes are the CLI contract: 0 when at least one candidate is eligible, 1 when none is eligible, 2 for invalid or unreadable input. If both qualify, the output lists both without ranking. A ready alternative does not conceal another candidate's failed checks. The tests derive expected outcomes from the truth table, not from production function results.

uv run --no-project --with pytest python -m pytest tests/phone_media -q -rA -p no:cacheprovider
