Bounded Codex briefs

A brief is checked for explicit scope, exact owned file names, verification commands and stop conditions before instructions are rendered. Preservation constraints accompany every rendered brief. This preparation addresses issue 3828, “Codex config runs with approval never and full access”; it does not establish runtime isolation or authenticate task authority.

Method and inputs

The standalone helper scripts/agents/codex_brief.py reads JSON and renders Markdown to standard output. It neither starts Codex nor runs the proposed checks. Existing execution entry points are unchanged; adoption requires an explicit preparation step.

InputRequired content
objectiveNonempty single-line description of the intended result.
scopeNonempty list of specific proposed changes.
owned_filesNonempty list of unique, exact repository-relative file names.
checksNonempty list of verification commands or procedures.
stop_conditionsNonempty list of conditions requiring a report before affected work continues.

Table 2. Brief fields; unknown fields and duplicate JSON keys are rejected.

Absolute paths, traversal components, Git metadata components, glob patterns, backslashes, drive prefixes and noncanonical path spellings are rejected. Owned files may describe proposed new files. Their existence is not checked. The format deliberately lists files rather than granting an entire directory.

Worked example: parser correction

The illustrative task is to return an empty list for an empty document. The complete input is codex-bounded-brief.json. The example names src/parser.py and tests/test_parser.py as the only proposed write targets. These are fictional example files; the example does not assert that they exist in this repository.

python scripts/agents/codex_brief.py docs/examples/codex-bounded-brief.json

The method checks the required fields, validates the owned file names, then renders the objective, scope, file list, verification and stop conditions before the fixed preservation constraints. The expected answer includes:

## Scope
- Return an empty list for an empty document.

## Owned files
- src/parser.py
- tests/test_parser.py

## Verification
- python -m pytest tests/test_parser.py -q

The preservation section prohibits deletion of data, overwriting unrelated work, history rewriting, publication and runtime-permission changes. The example's verification command is rendered as text; it is not executed. An input with ../other.py instead of an owned file is rejected, produces no brief and returns failure. Expected outcomes are derived directly from the contract cases, without numerical calculations or engineering constants.

Preparation before execution

  1. Read the target repository instructions and verify the originating task authority.
  2. Inspect the effective approval and sandbox settings. The issue describes a no-prompt, broad-access configuration; that observation shall not be treated as a universal current runtime setting.
  3. Inspect existing changes and concurrent work, then fill the JSON fields with concrete task scope. Preserve unrelated changes.
  4. Run the helper and inspect the complete rendered brief. Reject placeholder, contradictory or overly broad prose even when syntax validation passes.
  5. Supply the reviewed output through the existing authorized execution route. Keep independent filesystem isolation, secret controls and review requirements.
  6. Require check results and a change summary. A scope expansion, conflicting change or missing authority stops affected work for clarification.

Limits and source basis

Syntactic validation cannot establish that prose is specific, authorized or non-destructive. Check strings are untrusted text and shall not be evaluated by this helper. Markdown rendering is not sanitization for a web application. Path validation is lexical: directories, symlinks, filesystem aliases and later file changes require independent inspection and runtime controls. No claim is made that a listed path is physically confined to the repository.

The governing source is issue 3828, section “Fix/workaround”: explicit scope, non-destructive constraints and owned paths before execution. The repository's Codex provider instructions require inspection of actual sandbox capabilities, while the shared authorization contract distinguishes task authority from consequential publication authority. No standards-derived values, coefficients or acceptance limits are used. Independent provider review and execution-route integration remain outside this standalone preparation utility.
