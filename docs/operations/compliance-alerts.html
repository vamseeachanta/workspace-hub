Compliance alert accounting

Summary

The daily alert decision is derived from the dashboard's top-level JSON report. Nested event verdicts describe separate checks. A window containing no reviewable commits produces no compliance alert. Invalid accounting or a dashboard execution failure exits with an error before GitHub is contacted.

Scope and method

  1. The parser reads exactly one JSON Report: section and validates integer counts, duplicate fields, accounting identities, rate and verdict.
  2. The cron wrapper retains the dashboard exit status and requires agreement with its verdict. It suppresses alerts when reviewable is zero and retains the existing alert thresholds for populated windows.
  3. Regression tests exercise the parser and the cron path with isolated substitutes for the dashboard and GitHub. Existing dashboard tests remain part of the regression command.

The accounting identities are total = skipped + reviewable and reviewable = reviewed + unreviewed. For a populated reviewable window, the displayed integer rate is floor(100 × reviewed / reviewable). The factor 100 expresses a fraction as a percentage. The dashboard stores zero for an empty reviewable window; that stored value does not establish a compliance failure.

Source for these identities, the integer-rate method and verdict semantics: scripts/enforcement/compliance-dashboard.sh, “Calculate rates” and “Determine verdict” (repository implementation, 2026).

Worked examples

All example counts are synthetic test inputs, not observations of repository compliance. Expected results follow the hand calculations below.

Inputs: total 7, skipped 7, reviewed 0 and unreviewed 0. Calculation: reviewable = 7 − 7 = 0. A percentage cannot be calculated with a zero denominator. The stored dashboard rate is zero and its verdict is PASS. Answer: no alert and no GitHub call; a critical alert would be unsupported by this window.

Inputs: total 5, skipped 0, reviewed 1 and unreviewed 4. Calculation: reviewable = 5 − 0 = 5 = 1 + 4; floor(100 × 1 / 5) = 20 percent. Against the retained 80 percent dashboard threshold, the verdict is FAIL. Against the alert policy's 30 percent boundary, the severity is critical. A nested drift-event verdict of pass does not alter this result.

The second example can be passed directly to the validator. The argument represents the dashboard's FAIL exit status:

printf '%s\n' 'JSON Report:' \
'{"total_commits":5,"skipped":0,"reviewable":5,"reviewed":1,"unreviewed":4,"compliance_rate":20,"threshold":80,"verdict":"FAIL","stage_prompt_drift":{"latest_event":{"verdict":"pass"}}}' \
| python3 scripts/enforcement/compliance_alert_report.py 1

Answer, as tab-separated fields: 20 5 1 4 FAIL 5 (rate, total, reviewed, unreviewed, verdict, reviewable).

Known limits and follow-up

This change establishes alert accounting consistency, not independent review evidence. Historical commits have not been reviewed or reclassified. The existing dashboard's message-based review detection remains unchanged; authenticated review evidence and retrospective backlog review require separate work. Weekly aggregation and commit classification are unchanged. No hosted alert publication is exercised by these tests. Second-provider review remains pending before merge.
