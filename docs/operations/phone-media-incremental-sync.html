Phone-media incremental sync decision

Summary

The decision aid compares periodic USB imports, PhotoSync Autotransfer to WebDAV, and an icloudpd server-side pull. It evaluates supplied prerequisites without accessing media, accounts, networks or services. The maintainer's final choice remains open. For manual imports, USB is the first option to evaluate because it reuses the existing bulk-import method without a new transfer entitlement. If automatic transfer is required, evaluate PhotoSync first; cloud pull also requires account-access and authentication decisions.

No live prerequisites are established by this document. A result of READY_FOR_TRIAL means only that caller-supplied facts permit a proposed trial. It does not establish a working transfer, an original-quality archive or an off-site backup. Existing inbox and WebDAV services remain unchanged.

Scope and evidence

Issue 3587 defines the three alternatives and reserves the decision for the maintainer. The existing extraction handoff describes a successful historical USB workflow, not current device or service readiness. Separate work covers bulk imports, organization, backup capacity and a media browser. This aid neither changes those workflows nor installs a scheduler.

The implementation is scripts/operations/phone_media_sync.py. Source pages were read on 2026-10-22. They are capability references rather than current observations of the intended destination. App price, entitlement terms and authentication refresh intervals are intentionally unspecified; confirm current terms before selection.

Prerequisites

Each JSON fact accepts true, false or null. Omitted facts mean unknown. Set a fact only after the corresponding observation or maintainer preference is recorded in a private operational record. Do not place personal media, credentials, destination addresses or device identities in this public repository.

Method and states

The method uses a Boolean conjunction over each candidate's prerequisite table. A known contradiction gives BLOCKED, even when other facts are missing. Otherwise any missing prerequisite gives NOT_EVALUATED; all matching facts give ELIGIBLE. This truth table is the method's definition, rather than an empirical coefficient or a numerical engineering limit.

Without --select, the decision remains AWAITING_SELECTION, even if a candidate is eligible. With explicit selection, the decision becomes PROPOSED, NEEDS_INPUT or BLOCKED. Trial readiness additionally requires confirmed backup capacity. Known failed capacity blocks the trial; unknown capacity leaves it NOT_EVALUATED. The selected method remains a proposal, not activation authority.

The command writes JSON to standard output only. A successful process exit means the input was evaluated, including blocked or incomplete results; inspect the JSON statuses. Malformed JSON, duplicate keys, non-Boolean facts and unknown fields are rejected. No commands are generated or executed for importing media.

Worked example

The example is synthetic. Its inputs represent an available USB source, accepted manual operation, no automation requirement and confirmed capacity. They are not measurements.

python scripts/operations/phone_media_sync.py \
  docs/operations/examples/phone-media-usb-facts.json --select usb

phone-media-usb-facts.json supplies:

{
  "automation_required": false,
  "usb_access": true,
  "manual_accepted": true,
  "backup_capacity_verified": true
}

Independent hand evaluation: no automation requirement matches manual USB; USB access and manual acceptance both match. Therefore USB is ELIGIBLE. Explicit selection makes the decision PROPOSED; confirmed capacity gives READY_FOR_TRIAL. PhotoSync and cloud pull remain NOT_EVALUATED because their prerequisites were not supplied. No best-option claim follows from this example.

If capacity is omitted, USB remains proposed but trial readiness is NOT_EVALUATED. If automation is required, USB is BLOCKED. These expected outcomes are derived from the table independently in the tests.

Trial and ongoing import procedure

  1. Record the maintainer's selected method, evidence date, prerequisites and destination in a private operational record. Leave unknown facts unset. Preserve existing services.
  2. Confirm capacity and a distinct archive namespace for the source device. Before USB copying, inspect a dry run with rsync --archive --ignore-existing --itemize-changes --dry-run -- "$USB_DCIM/" "$ARCHIVE/". Both variables must identify verified local directories. The aid does not execute this command. Do not use deletion or source-removal options.
  3. For USB, --ignore-existing preserves existing destination files but also skips same-name collisions, including changed content. Review those collisions separately by content digest; do not infer completeness from a quiet repeat run. The default rsync quick check uses size and modification time, not a full content audit. See rsync manual, DESCRIPTION, --ignore-existing, --dry-run and --checksum.
  4. For PhotoSync, transfer representative originals and associated files to the verified WebDAV destination. Check original dimensions and content integrity using originals when available, plus video, Live Photo and sidecar behavior. File counts alone do not establish original quality. Confirm a repeat automatic trigger imports new items without losing old ones.
  5. For cloud pull, use copy mode only. The upstream README distinguishes default copy from sync with local deletion and move with cloud deletion; deletion modes are outside this procedure. Test authentication and original-media behavior before unattended operation. Keep credentials in the existing private secret store.
  6. Repeat with new media and an interrupted transfer. Record counts, bytes and digest comparisons, and investigate every missing, changed or colliding item before acceptance. Confirm that deleting a source item does not remove an archive item. Do not delete real media for a trial; use disposable synthetic fixtures to test that behavior.
  7. Verify the off-site copy independently under the capacity and backup procedure. Record the accepted interval and authentication recovery process. Only then arrange ongoing operation through the separately authorized service workflow.

Checks and limits

The tests exercise every alternative, failed and missing prerequisites, ADP exclusion, manual-versus-automatic requirements, capacity states, explicit selection, duplicate keys, invalid inputs, a read-only CLI and the worked fixture. Expected values come from hand Boolean evaluations in the tests, not outputs copied from the implementation.

Live imports, account access, destination reachability, entitlement verification, original-quality verification and off-site backup remain NOT_EVALUATED. The maintainer's final selection and independent provider review remain pending. The guide does not claim to close the decision issue.
