# OrcaWave / OrcaFlex Native Load-Run Proof Protocol

> **Purpose:** define how a licensed solver machine proves that native OrcaWave (`.owd`/`.yml`) and OrcaFlex (`.dat`/`.yml`/`.sim`) inputs generated from semantic-proof fixtures actually load and (where bounded) run, and what durable evidence is returned to GitHub.
>
> **Audience:** licensed-win-1 operators (Claude Code CLI, Codex CLI, or human), and dev-primary planners who dispatch proof work via `queue/pending/` or via direct prompts.
>
> **Authority:** this protocol is the contract referenced by the licensed-win-1 prompt at `docs/plans/licensed-win-1-semantic-proof-load-run-prompt.md` and by the evidence manifest template at `docs/solver/templates/semantic-proof-evidence-manifest.yaml`.
>
> **Issue:** [#2475](https://github.com/vamseeachanta/workspace-hub/issues/2475). Companion contract: [#2476](https://github.com/vamseeachanta/workspace-hub/issues/2476) (semantic-equivalence cookbook).
>
> **Status:** v1 — issued under the approved plan `docs/plans/2026-04-23-issue-2475-licensed-load-run-proof-protocol.md`.

---

## 1. Why this protocol exists

The first-wave deterministic semantic-proof fixtures merged via digitalmodel PR #528 (and tracked through issues [#2455](https://github.com/vamseeachanta/workspace-hub/issues/2455), [#2456](https://github.com/vamseeachanta/workspace-hub/issues/2456), [#2457](https://github.com/vamseeachanta/workspace-hub/issues/2457)) prove **structural correctness** of generated native inputs against canned expected YAML/dict snapshots. They do not prove that OrcaWave or OrcaFlex — the licensed commercial applications — will actually open the file, parse it, and run a calculation.

The deterministic-semantic-proof exit handoff (`docs/handoffs/2026-04-23-orcawave-orcaflex-semantic-proof-exit-handoff.md`) calls this gap out explicitly: dev-primary cannot exercise OrcFxAPI without an OrcaFlex license, so a separate, smaller proof contract is needed for the licensed machine.

This protocol is that contract. It is intentionally narrow: it does **not** add new structure families or modify queue code or solver source. Its job is to define the evidence bundle and the classification of outcomes.

## 2. Scope

In scope:
- Native input files generated by the dev-primary semantic-proof fixtures for OrcaWave (e.g., L03 ship roundtrip — #2457) and OrcaFlex (e.g., rigid jumper PLET-to-PLEM — #2455; lazy-wave and steep-wave risers — #2456).
- Load-only proof on licensed-win-1.
- Run proof on licensed-win-1, only when the fixture's runtime is documented as bounded.
- Evidence bundle authoring and return via git + GitHub comment.
- Failure classification.

Out of scope (tracked elsewhere):
- New structure families or expanded fixture sets — covered by future scope plans, not by #2475.
- Queue schema upgrades for proof metadata — tracked under [#1650](https://github.com/vamseeachanta/workspace-hub/issues/1650).
- Solver-version drift remediation — tracked under issues raised by classification, not by this protocol.
- CI dependency health (`pylife`, etc.) — out of scope per #2475 issue body.

## 3. Proof levels

Four levels, each strictly stronger than the last. Every fixture passes through level 1 on dev-primary before licensed-win-1 sees it. Levels 2-4 are licensed-machine work and are the subject of this protocol.

### Level 1 — deterministic semantic proof

- **Where:** dev-primary (no license required).
- **What:** generated native input matches the deterministic expected YAML/dict snapshot.
- **Tool:** `pytest` against the semantic-proof harness in digitalmodel.
- **Verdict:** PASS / FAIL on an exact-equality basis (with documented tolerance for whitespace and formatting only).
- **Status today:** PR #528 has shipped this for the first wave; #2455/#2456/#2457 are CLOSED on this basis.

### Level 2 — licensed load proof

This level is the **load-only proof**: the file is opened, parsed, and inspected, but no calculation is performed.

- **Where:** licensed-win-1 (OrcFxAPI required).
- **What:** the licensed application opens the generated file without raising; the solver reports a sane object/body/frequency/heading count.
- **Tool:** `OrcFxAPI.Diffraction(...)` for OrcaWave, `OrcFxAPI.Model(...)` for OrcaFlex. No `Calculate()` or `RunSimulation()` call.
- **Verdict:** PASS / FAIL based on the load call returning an object whose `state` or `objectCount` is non-degenerate.
- **Mandatory:** required for every fixture in scope. A fixture that cannot load on a licensed machine is treated as a regression of level 1, even if level 1 passed.
- **Why it can fail when level 1 passed:** the deterministic snapshot can be byte-equal to the expected YAML and still hit a parser-level rejection (unknown key, value out of accepted range, mesh/path resolution failure) when the licensed application reads it.

### Level 3 — licensed run proof

- **Where:** licensed-win-1 (OrcFxAPI required).
- **What:** the licensed application performs a bounded calculation (`Calculate()` for OrcaWave, `CalculateStatics()` and a brief `RunSimulation()` for OrcaFlex) and writes a result file (`.owr` for OrcaWave, `.sim` for OrcaFlex) without raising.
- **Tool:** as above, plus result-file existence check and optional `LoadResults` round-trip.
- **Verdict:** PASS / FAIL based on result-file presence and a non-error solver state. Numerical correctness is not a proof-level-3 outcome — that is a separate semantic-equivalence contract (#2476).
- **Conditional:** allowed **only** when one of the following holds:
  - The fixture has a documented short analysis duration (OrcaFlex `StageDuration` short enough to expect <15 minute wall-clock, with all stages combined).
  - The OrcaWave frequency × heading grid is small enough to expect <15 minute wall-clock based on prior fixtures of comparable size.
  - The runtime upper bound is otherwise demonstrable from the fixture's own metadata.
- **Skip-run classification:** if none of the above holds, the fixture is recorded as `skip-run` (see §6) and only level 2 is attempted.

### Level 4 — evidence bundle accepted

- **Where:** dev-primary review.
- **What:** the returned evidence manifest, logs, screenshots, and result/output paths satisfy the manifest template's required fields and the classification is consistent with the artifacts.
- **Tool:** `docs/solver/templates/semantic-proof-evidence-manifest.yaml` filled and committed alongside (or referenced by) the proof artifacts.
- **Verdict:** PASS / RETURN-FOR-REWORK based on completeness of required keys (machine, solver version, OrcFxAPI version, git SHAs, input paths, output paths, classification, issue/PR links).
- **Why this level exists:** without it, a licensed run can be reported as "passing" while leaving no auditable trail. Level 4 is the gate that turns a one-off licensed run into a defensible engineering artifact.

## 5. Evidence bundle shape

Each proof attempt produces an evidence record. The reference template is `docs/solver/templates/semantic-proof-evidence-manifest.yaml` and is the canonical source of required keys. At minimum every record contains:

- `machine` — hostname and OS identifier of the licensed machine (e.g., `licensed-win-1` / `Windows`).
- `solver` — application name and version (e.g., `OrcaWave 11.5e`, `OrcaFlex 11.5e`).
- `orcfxapi` — `OrcFxAPI` Python wheel version (output of `OrcFxAPI.version()` if available, otherwise the wheel filename).
- `git` — workspace-hub SHA, digitalmodel SHA, optional dirty flag.
- `inputs` — generated native input file paths (relative to repo root) and optional content hashes.
- `outputs` — produced result file paths (`.owr` / `.sim` / `.dat` / `.yml`) plus any sidecar `.xlsx`, plus the queue `result.yaml` if the queue was used. May be empty when classification is `skip-run` or `missing input`.
- `proof_level` — the highest level reached: `level1`, `level2`, `level3`, or `level4`.
- `classification` — one of the values listed in §6.
- `evidence` — log paths, screenshots/exports, console excerpts, and any stderr captured during the load/run.
- `issue` — GitHub issue number for the fixture (e.g., `2455`).
- `links` — list of issue/PR URLs supporting the bundle (`#2475` plus the fixture's own issue and PR).

The evidence manifest is authored directly by the licensed-win-1 operator (or by the prompt-driven agent) after each command. The queue's `result.yaml` is a useful **input** to the manifest but is not a substitute for it — `result.yaml` does not capture solver version, git SHAs, screenshots, or classification.

## 6. Failure classification matrix

Every proof attempt records exactly one classification. The set is closed; new classes require a protocol revision (and a follow-up issue against #2475).

| Class | When to use | Required evidence |
|---|---|---|
| `pass-load` | Level 2 succeeded; level 3 not attempted | Console excerpt showing object/body/frequency count |
| `pass-run` | Level 3 succeeded | Result file path + size + non-error solver state |
| `semantic mismatch` | Licensed application rejects the file with a parse-level or schema error that contradicts the level-1 deterministic snapshot | Stderr/console excerpt with the rejection message + the fixture's level-1 snapshot reference |
| `solver-version/default drift` | Licensed application accepts the file but produces results that differ from a known-good baseline due to default-value or version differences (not a generation bug) | OrcFxAPI version, OrcaWave/OrcaFlex application version, the differing field name and observed values |
| `missing license/API` | OrcFxAPI import fails or license check fails | Exact import or license-error message |
| `missing input artifact` | Generated native input or referenced mesh/include file is not present on disk | Path expected, path actually checked, source plan/issue |
| `unrelated environment failure` | Failure is in the test harness, Python environment, git, or filesystem — not in the solver or generated input | Failing command + traceback + a one-line hypothesis why this is environmental |
| `runtime/disk guard exceeded` | Level 3 attempted but exceeded the documented bound or filled the disk; level 2 still passes | Wall-clock observed, disk-usage observed, the rule that fired |
| `skip-run` | Level 3 not attempted because runtime cannot be bounded; level 2 still passes | One-line reason citing the unbounded grid/duration/missing-bound metadata |

A fixture may post multiple classifications **only** if level 2 passes (`pass-load`) and level 3 separately fails or is skipped (e.g., `pass-load` plus `runtime/disk guard exceeded`). In that case the manifest records both.

## 7. Dispatch and execution

The licensed-machine workflow is documented in `docs/plans/licensed-win-1-semantic-proof-load-run-prompt.md`. In summary:

1. Operator (human or Claude/Codex CLI) starts on licensed-win-1, in `D:\workspace-hub`.
2. `git pull origin main` for both workspace-hub and digitalmodel.
3. Verify OrcFxAPI / pyyaml / openpyxl / numpy import (install if missing per the prompt).
4. For each fixture in §4, attempt level 2.
5. If runtime bound holds per §4, attempt level 3.
6. Author evidence manifest and write log/console excerpts under a fixture-specific path.
7. Commit only docs/evidence files (manifest, logs, small screenshots/exports). Binary outputs above the size policy are referenced but not committed.
8. Push and post a GitHub comment on the fixture's issue summarizing pass/fail and naming the manifest path.
9. If proof is run via the queue, the queue's `result.yaml` is referenced in the manifest but does not replace manifest authoring.

## 8. What this protocol does not authorize

To prevent scope creep, the protocol explicitly refuses the following without a separate approved plan:

- Modifying `scripts/solver/process-queue.py` or the queue job schema. Schema upgrades for proof metadata go to [#1650](https://github.com/vamseeachanta/workspace-hub/issues/1650).
- Adding new structure families or fixtures beyond the §4 table. New fixtures arrive via their own deterministic-proof issues first.
- Committing large binary `.sim` or `.owr` files into either workspace-hub or digitalmodel without size-policy review. Manifest + small evidence artifacts are the primary commit; binary outputs are typically referenced by path/hash only.
- Performing an unbounded full OrcaWave full-grid or full-duration OrcaFlex simulation. Run proof is bounded by definition.
