Solver result qualification

Summary

The solver result interface can now evaluate declared numerical evidence separately from execution success. An offline checker reads an existing JSON result, required acceptance criteria, output units and an assumption ledger. It never loads or executes a licensed solver. A passing report establishes only agreement with the supplied criteria; it does not certify an engineering design.

Three implementation slices

  1. src/solvers/qualification.py defines immutable criteria, individual comparisons, assumptions and qualification reports.
  2. SolverResult.qualify() exposes the checker through the existing result interface. It preserves execution status and result data.
  3. scripts/solver/qualify_result.py provides an offline JSON interface, with examples/solver-qualification/synthetic.json as executable input.

Method and source

The comparison uses the symmetric absolute/relative rule from PEP 485 (2015), Implementation:

|a - b| <= max(r × max(|a|, |b|), t)

Here a is the observed scalar, b is the independent reference, r is a dimensionless relative tolerance and t is an absolute tolerance in the quantity's units. Both tolerances are mandatory, finite, non-negative inputs. Zero allows exact comparison. There are no default engineering acceptance limits. Each criterion requires a reference description and a tolerance basis; these are declarations supplied by the caller, not verified citations or proof of independent derivation.

The equation is evaluated using exact rational representations of the supplied integer and binary floating-point values. This avoids intermediate overflow and loss of integer differences during float conversion. Boundary decisions can differ from math.isclose because intermediate products are not rounded. Precision already lost when a JSON decimal becomes a binary float cannot be recovered. Scalars must pass finite binary64 range screening; larger integers are rejected. This is not a decimal-arithmetic interface. Non-finite inputs are rejected even if both values are identical infinities. No unit conversion occurs.

Evidence and status

StatusMeaning
PASSExecution succeeded, at least one criterion exists, every required comparison passed, and no declared assumption is unresolved.
FAILExecution failed, or a required output is non-numeric, non-finite, outside its tolerance, or carries different units.
NOT_EVALUATEDNo failure was found, but criteria, required outputs or unit evidence are missing, or an assumption is unresolved.

Failure takes precedence over missing evidence. Every declared criterion gets a check entry. Reports retain criteria, observed values, units, the method reference and assumptions. Invalid scalar output is represented by a null observed value and a failure reason, so JSON reports remain finite. A null assumption value means unresolved; a nonempty value and basis record a declared resolution. Duplicate criterion quantities are rejected.

The JSON input requires exactly result, criteria, output_units and assumptions. Result fields are exactly success (boolean), solver_name and result_data (object or null). Unknown top-level/result fields, duplicate JSON keys and non-standard numeric constants are rejected. Invalid input exits without echoing its content or filesystem details.

Worked example: inputs, method and answer

The example is an intentionally synthetic scalar multiplication exercise, not a validated spring model. Its benchmark is defined by the expression 8 N/m × 2 m = 16 N. Both factors, the observed 16 N and the absolute tolerance 1 N are synthetic example inputs; no design coefficient is adopted. Relative tolerance is set to zero by the example author. The JSON reference and tolerance basis explicitly retain this origin.

uv run --no-project python scripts/solver/qualify_result.py \
  examples/solver-qualification/synthetic.json

The hand calculation gives |16 − 16| = 0 N and a permitted difference max(0 × 16, 1) = 1 N. Therefore the report is PASS and the command exits with code 0. With an observed 17 N the inclusive bound still passes; with 18 N the difference is 2 N and the report is FAIL (exit 1). Removing the output-unit entry gives NOT_EVALUATED (exit 2). Invalid input also exits 2, with a diagnostic on standard error and no report.

Independent tests also cover a synthetic relative limit 0.2: observed 10 and reference 8 give a difference 2 and allowance 2, while observed 11 gives a difference 3 and allowance 2.2. Signed values, zero references, exact bounds, integer precision, extreme finite inputs and CLI rejection paths are covered.

Integration and limits

report = existing_result.qualify(
    criteria,
    output_units=declared_units,
    assumptions=declared_assumptions,
)
if report.accepted:
    consume(existing_result.result_data)

Consumers must call qualification and enforce its result. The registry and legacy NumericalSolver.verify_accuracy() retain their existing behavior; this addition does not install a universal execution gate. Use an independent reference, qualified units and reviewed criteria. The checker cannot establish that a source is authentic, that an assumption is physically justified, that all governing outputs were declared, or that result metadata belongs to a particular native run. Empty assumption lists do not establish assumption completeness.

Later work includes domain-specific adapters, range and conservation checks, native-run evidence binding, governed criteria, atlas coverage and confidence qualification, and integration into existing hosted checks. The wider initiative remains open. Cross-provider review is pending with the maintainers.
