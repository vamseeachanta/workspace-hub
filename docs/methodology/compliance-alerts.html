Compliance alert interpretation

Summary

The daily alert uses the dashboard's root JSON commit metrics. A window with no reviewable commits requires no review action. A stored zero percentage in that case is a legacy sentinel, rather than evidence of failed review.

Method and sources

The existing Compliance Dashboard Guide, “How Compliance is Calculated”, steps 4–5, defines the reviewable denominator, percentage and default threshold. The alert bands are the Thresholds table in issue 3809 (2026-08-17), consistent with scripts/enforcement/compliance-cron.sh. These are repository workflow criteria; no engineering standard or physical coefficient is used.

reviewable = total_commits - skipped = reviewed + unreviewed
rate = floor(100 × reviewed / reviewable), when reviewable > 0

The factor 100 converts a ratio to percent. Integer truncation preserves the existing dashboard contract. When reviewable equals zero, no ratio is calculated; the stored zero is retained for compatibility and the cron exits without an alert.

A stricter configured dashboard threshold can also require an alert at or above 80%; its severity remains medium. A lower configured dashboard threshold does not lower the cron's alert bands.

Worked examples

Exempt window: total = 7, skipped = 7, reviewed = 0, unreviewed = 0. Reviewable = 7 − 7 = 0. The dashboard stores rate = 0 and verdict = PASS. The cron records “No reviewable commits” and creates no alert.

Review backlog: total = 11, skipped = 7, reviewed = 1, unreviewed = 3. Reviewable = 11 − 7 = 4; rate = floor(100 × 1 / 4) = 25%. Against the default 80% criterion, the verdict is FAIL; 25% is below the 30% critical boundary. The alert reports exactly one reviewed and three unreviewed commits, regardless of nested event counters or verdicts.

Validation and error handling

The parser requires a single JSON Report section, nonnegative integer counts, consistent totals and rates, a percentage threshold and the matching verdict. Duplicate JSON keys, missing fields and malformed JSON are rejected. The cron also verifies the dashboard exit status against the verdict before any GitHub access. The dashboard runs from the resolved repository root so that the caller cannot redirect the analyzed history or the saved report through its working directory. Invalid evidence produces a nonzero exit and an ERROR in the daily log, rather than a fabricated compliance result.

Run the regression and existing dashboard tests using pytest on tests/enforcement/test_compliance_alert.py and tests/enforcement/test_compliance_dashboard.py. Tests use disposable repositories and synthetic fixtures with independent arithmetic in docstrings. Git bindings inherited from the caller are removed before fixture initialization.

Limits and next action

This correction changes alert interpretation, not commit classification or review-evidence qualification. A keyword in a commit message remains heuristic evidence under the existing dashboard. Historical commits are not retrospectively reviewed, and historical issues are not edited. The weekly report remains unchanged. The maintainers should inspect the daily log and obtain actual review evidence before treating an alert as a verified account of missing reviews.
