Compliance alert reconciliation

The daily alert validates the dashboard's top-level JSON before a percentage is compared with the alert thresholds. A window without reviewable commits produces no alert. An inconsistent report produces a nonzero exit status and an error in the daily log, without publishing a compliance conclusion.

Method and sources

Let T be total commits, S skipped commits, R reviewed commits, and U unreviewed commits. The reviewable count N = T − S shall equal R + U. For N greater than zero, the dashboard rate is floor(100 × R / N), in percent. The formula follows Compliance Dashboard Guide, How Compliance is Calculated and its implementation in scripts/enforcement/compliance-dashboard.sh. For N = 0 the dashboard stores a zero rate and PASS; the alert treats this as no applicable denominator, not evidence of failed review compliance.

Alert boundaries follow the Thresholds table in issue 3855, Thresholds table, 2026-09-14: at least 80 percent requires no alert; 50 to below 80 percent is medium; 30 to below 50 percent is high; below 30 percent is critical. These are repository monitoring criteria, not engineering design limits.

Operation and checks

The cron wrapper reads one JSON object after the dashboard's JSON Report marker. Counts shall be nonnegative integers; boolean values are rejected. The total, skipped, reviewable, reviewed and unreviewed counts shall reconcile. The calculated rate, configured dashboard threshold, verdict and process exit status shall agree. Nested stage-event verdicts are not commit verdicts.

DRY_RUN=true bash scripts/enforcement/compliance-cron.sh logs the proposed alert without calling GitHub. Regression fixtures substitute local scripts and preserve both the caller's repository and its Git metadata. Run tests/enforcement/test_compliance_cron.py together with tests/enforcement/test_compliance_dashboard.py for the consumer and producer regression checks.

Limits and follow-up

The examples reproduce the alert mechanism; the historical daily logs and review artifacts were not supplied, so the review disposition of the historical commits is not established. The existing dashboard's commit classifier and review-evidence heuristics are unchanged. This repair does not conduct historical cross-reviews, prove the absence of bypasses, change review requirements, or establish that the scheduled task is installed. Second-provider review remains required before merge. The daily error log and nonzero process status require monitoring when report validation fails.
