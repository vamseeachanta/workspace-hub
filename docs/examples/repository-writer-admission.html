Repository writer admission

The preflight blocks a Codex writer while another writer uses the same repository. The decision is conditional on a complete current roster and a coordinator that serializes admission with registration.

Source and method

Source: issue 3829 (2026), repository writer serialization, and the execution standard. No physical constants, timing thresholds or engineering acceptance limits are used.

For each active record, conflict = same repository AND candidate writes AND active task writes AND (candidate is Codex OR active task is Codex). Admission requires no conflicts and a complete roster. This predicate does not establish path ownership for other combinations of providers.

Inputs

Save the following synthetic candidate as candidate.json:

{
  "task": "change-b",
  "repository": "example/repository",
  "provider": "codex",
  "access": "write"
}

Save the current coordinator roster as roster.json:

{
  "complete": true,
  "active": [{
    "task": "change-a",
    "repository": "example/repository",
    "provider": "claude",
    "access": "write"
  }]
}

All records require exactly the four task fields shown. Repository keys are lowercase namespace/repository identifiers, without URL, checkout path or .git suffix. Every checkout of the same repository shall use the same key; renames and aliases shall be resolved by the coordinator. Task tokens and provider tokens contain lowercase letters, digits, underscores or hyphens and begin with a letter or digit. Recognized providers are codex, claude, agy, gemini, hermes and other; aliases are rejected. The coordinator shall identify Codex writers as codex, never other. Access is exactly read or write; a task that may later edit is a writer from startup.

Invocation and answer

uv run --no-project python scripts/coordination/repo_write_admission.py \
  --candidate candidate.json --roster roster.json

Independent evaluation: the repositories match; both access values are write; the candidate is Codex. Every term is true, so the answer is:

{"allowed": false, "blockers": ["change-a"], "status": "BLOCKED"}

The exit code is 1. After the active writer and its children finish and integration is handed back, the coordinator removes that registration. For a fresh complete empty roster, no conflicts exist: the answer is ALLOWED, with an empty blocker list and exit code 0. The coordinator then registers the candidate before starting it, within the same serialized scheduling operation.

Changing the active access to read, or using a different repository, also removes this conflict. A second Codex writer remains blocked even in a different worktree or when it reuses the same task token.

Missing evidence and limitations

An incomplete roster, unreadable input, malformed JSON, duplicate JSON keys or invalid records yield NOT_EVALUATED, allowed: false, and exit code 2. These exit codes are interface definitions, not measured acceptance limits. Input errors omit paths and excerpts from output.

The completeness flag is a caller assertion. Freshness and identity cannot be verified by this pure helper. No expiry or automatic stale-registration removal is provided. Read-only tasks cannot escalate to writes without admission again. This preflight is optional tooling; existing launchers are not automatically wrapped, and independent callers require an existing atomic coordination backend.
