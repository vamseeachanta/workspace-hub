#3555: persistent goals and native Codex statusline

Status: draft · Complexity: T3 · Lane: Claude orchestration

Gate: implementation will remain blocked until three-provider adversarial plan review completes and the user explicitly approves the reviewed plan.

Outcome

Substantive interactive Claude and Codex work will attach a provider-native goal. Goal progress will use native UI, while the statusline/footer will independently show context and usage. The configuration will be repo-managed, safely merged into machine-local settings, piloted on ace-win-2, and reported through per-machine equivalence evidence.

Current defects

  • The repo Codex template uses obsolete [status_line] syntax; current Codex uses [tui] status_line = [...].
  • The live Codex footer omits context-remaining and the five-hour limit.
  • Claude project, global, and sibling-repo statusline paths are split.
  • The current matrix reports only 4 of 5 active machines, and registry paths disagree with the live Windows checkout.
  • The older #2893 implementation is branch-only and assumes Codex has no native footer.

Execution sequence

  1. Empirically attest native goal UI and exact Codex footer identifiers in disposable fresh sessions.
  2. Add the goal-use contract to the canonical cross-provider soul and rebuild runtimes.
  3. Migrate Codex to key-level [tui] management and converge Claude deployment paths.
  4. Extend setup verification and equality collection with separate session-UX rows.
  5. Pilot on ace-win-2, then require fresh evidence from each machine before any fleet-complete claim.

Fail-closed decisions

  • If Codex cannot keep native goal progress visibly available, work will return to plan review; no custom footer emulation will be invented.
  • An unsupported footer item will preserve the prior config and fail installation.
  • Missing or stale machine evidence will remain MISSING-EVIDENCE, STALE-CHECKOUT, or UNREACHABLE.
  • Goal text and transcripts will never enter equality evidence.

Approval checkpoint

After adversarial review, the issue will move to status:plan-review. Only the user may approve it and create the approval marker. TDD implementation will begin afterward.
