Operational Semantics

pending_work_report() treats an account as clean only when tracked in-scope threads have no pending inbound states or decision/schema flags and a supplied inbox snapshot contains no unknown in-scope thread. Without an inbox snapshot, the report returns unknown_status: not_evaluated and mailbox_empty: null. This avoids falsely claiming that Gmail is empty when only local state was inspected.

awaiting-reply is not pending by itself; a newer inbound Gmail message detected through the supplied inbox snapshot is what turns it back into actionable work. sweep --dry-run is read-only. Local completed-to-purged apply requires a clean reactivation precheck covering cleanup-enabled accounts only. skestates uses keep-forever retention; important messages are surfaced through the starred method and Telegram Family - Finance channel.

Boundaries

Gmail label creation/mirroring is implemented as an injectable read/assist account adapter seam and fails closed if queue-state account mapping disagrees with the Gmail helper mapping. This session did not apply live Gmail labels because the runtime did not expose verified per-account Gmail clients for the read/assist account set. Gmail archive or delete automation remains follow-on issue #2423.
