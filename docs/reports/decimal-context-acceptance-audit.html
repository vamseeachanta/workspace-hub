Decimal context acceptance comparison audit

Summary

Two inspected comparison routines can change their result when Decimal inputs are evaluated under a modified arithmetic context. Their Decimal paths now use exact rational arithmetic. Existing float paths and strict or inclusive comparator semantics are retained. The publication validator already uses exact construction and equality and requires no arithmetic correction. This is a bounded software audit for repository issue 3859, not numerical qualification of an analysis.

Comparison basis

The governing equations are the existing repository contracts: abs((calculated - expected) / expected) <= tolerance for a nonzero reference, abs(calculated) < tolerance for a zero reference, and abs(current - previous) <= tolerance for trend stability. Sources: NumericalSolver.verify_accuracy and compare_direction at the base revision (2026). No new engineering coefficient or acceptance limit is introduced.

When any operand or tolerance is Decimal, all comparison operands are converted to Fraction before arithmetic. Python 3.11 Library Reference, fractions — Rational numbers (retrieved 2026-10-22, HTTP 200), specifies exact conversion from Decimal and binary float. Mixed floats retain their binary value; converting through a string would change the supplied value. Finite rational arithmetic needs no Decimal context, mutable DefaultContext copy, precision estimate, rounding policy or exponent bound. Non-finite values have no finite rational representation and raise ValueError or OverflowError. The original float-only path is unchanged.

Worked example: diagnostic idle capacity

The inputs and criterion are from repository issue 3859 (2026): four logical cores, utilization 50.0001 percent, required idle capacity two core-equivalents. The percentage identity gives idle = cores × (1 - utilization / 100). An independent hand calculation is:

idle = 4 × (100 - 50.0001) / 100
     = 1999996 / 1000000
     = 499999 / 250000 core-equivalents
required - idle = 1 / 250000 core-equivalents
idle < required, so the operational criterion is not met.

The exact fractions retain the near-boundary distinction without reporting rounded display values as calculation inputs. This example does not install a resource policy here; its inputs are diagnostic issue evidence rather than engineering acceptance limits. The executable example is test_worked_idle_example in tests/analysis/test_decimal_context_acceptance.py.

Verification

The initial matrix produces 48 failures and 45 passes before the comparison corrections, then 93 passes after them. The expanded matrix contains 193 passing cases. It includes six context configurations: rounding down/up with traps, rounding down/up without traps, modified DefaultContext alone, and simultaneous ambient/default mutation. Precision, exponent bounds, clamp, capitalization, flags and every trap are modified. Ambient state is checked after each case; default state is restored in a finally block. Boundary cases cover both signs, strict/inclusive comparisons, mixed float operands, non-finite rejection and boundaries beyond the default decimal precision. Publication equality is checked with representable values and lossy tokens.

The combined new and related module suites produce 314 passes and two pre-existing failures. Ruff reports 25 pre-existing diagnostics in the two production files and no diagnostics in the new test file. Base source readback confirms the unchanged failing logic and lint findings. File-level checks run on the uncommitted tree; commit hooks and publication belong to the subsequent maintainer-controlled handoff.
