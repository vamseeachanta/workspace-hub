Proposed sequence after explicit recovery approval

  1. Freeze and drain. The operator will pause new submissions and queue automation under the approved writer inventory. An active solver will finish within the approved drain bound; expiry or uncertain child ownership will quarantine the lane and require the approved cleanup procedure. Killing only the agent while its supervisor can restart it will not establish quiescence. The operator will stop approved supervisors/tasks, verify descendant and Git-writer absence, and repeat queue/lock checks. A busy lock will be attributed to its owner, not deleted because of age.
  2. Capture immutable recovery evidence. After quiescence, the operator will record HEAD, branch/upstream refs, status including untracked files, request/result identities and hashes, rebase metadata and reflogs. A protected complete repository/Git-directory copy will preserve objects, index, configuration, rebase state and reflogs; linked-worktree common directories will be included if detected. Copy verification will compare a per-file SHA-256 manifest while writers remain stopped.
  3. Preserve reachable histories separately. After the complete snapshot, explicit uniquely named recovery refs will protect detached HEAD and original main. A Git bundle will include those refs and all branch refs; git bundle verify, git bundle list-heads, and a private restore trial will verify the expected object IDs and request/result content. The bundle will supplement the complete copy: it will not be claimed to preserve reflogs, index or rebase state. Failed backup or restore verification will stop recovery before abort.
  4. Recheck the heartbeat-only condition. The operator will enumerate every local-only commit's changed paths, not just its subject or net tree difference. Every path will have to belong to the expected host heartbeat record. Intermediate request/result changes, untracked data, unexpected refs, new conflicts or changed writer state will stop this bounded procedure and trigger a revised preview. Retained snapshots will protect evidence even when changes cancel in the final tree.
  5. Inspect remote truth without replay. Under the approved mutation scope, an isolated recovery clone will fetch the configured remote with noninteractive authentication and a finite timeout. The operator will compare the fetched tip against preserved histories, enumerate remote pending/running requests and terminal results, and identify heartbeat conflicts. The live queue will remain stopped; no approved request will be automatically executed as a side effect of inspection.
  6. Select reconciliation explicitly. If all local-only changes remain heartbeat-only, the preferred proposal will use the verified remote branch in a new isolated queue candidate and retain local heartbeat history in its recovery refs/archive; stale heartbeat values will not overwrite newer remote evidence. That proposal will explicitly disclose whether any local commit will remain archival rather than be published. If the owner instead requires reuse of the live clone, an approved git rebase --abort will occur only after verified backups and preserved refs, followed by inspection of restored main and a reviewed conflict resolution. There will be no reset --hard, blind skip, force push, or wholesale remote/local file preference.
  7. Verify before releasing the maintenance hold. The selected queue will have an attached tracked branch, no active rebase/merge or conflicts, and an inventory reconciling every preserved request/result with remote truth. Unexpected pending work will require owner disposition before any consumer resumes. The final report will bind backup digests, before/after refs, archive disposition, queue identity checks and remaining quarantine status.

Rollback and runtime boundary

At any uncertainty, the lane will remain stopped/quarantined with the complete backup intact. Rollback will first prove candidate writers and owned children absent. Restoration will use the verified backup or an isolated restored copy, preserve newly acquired remote evidence, and revalidate task/environment/policy hashes. Restoring files will not authorize restarting the known-broken legacy consumer, replaying requests, or removing quarantine.

The existing upstream Git repair will be reused rather than recreated. Starting an upgraded agent against the unpreserved stale rebase will remain prohibited because its abort logic could abandon the detached heartbeat chain. The separate cleanup/quarantine repair, integrated runtime pin, neutral scope and smoke-only effective policy will gate task cutover. Credentialed-local and Linux-origin acceptance will remain later steps; queue recovery alone will not qualify either route.

Review will compare this preview with the private writer inventory and backup/restore procedure before an exact recovery request reaches the owner. Preparation will preserve all live state. The next decision will concern the fully specified queue-only recovery package; missing private inputs or unresolved runtime cleanup will not be represented as deployment approval readiness.
