Root cause (runtime) — Critical skill-registry drift drove a crash-respawn storm

The --triage "safety" model is defeated by config default kanban.auto_decompose: true (config.py:1566): the gateway dispatcher auto-decomposes triage every tick and spawns workers for any ready task with an assignee. Those workers then crash instantly:

Error: Unknown skill(s): kanban-worker — every worker, in boards/<slug>/logs/*.log

The kanban-worker skill exists on disk (~/.hermes/skills/devops/kanban-worker/ and ~/.hermes/hermes-agent/skills/devops/kanban-worker) but the .venv/bin/hermes runtime the workers execute under does not register it — a two-venv skill-registry drift. The result is a fast crash→respawn loop, not idle hangs:

  • Real resource burn (not model quota — workers die before any API call): systemd cgroup showed 18h55m CPU in ~4h wall (~969% ≈ 10 cores), 18.7 GB RAM, load avg 30 from the plugin-discovery storm on each respawn.
  • Zero useful output over 7 days: 37/37 task workspaces empty, 1613/1621 runs crashed, 0 done, zero commits attributable to the swarm.
  • Stale config never reloaded: the kill-switch was written to disk at 05:10 but the gateway (pid 1332383) had started 01:16 and held ~4h of stale in-memory config — dispatch stayed ON until the systemd restart.

Note: an earlier draft described the workers as "idle-wedged, 0% CPU, no quota burn." That was a snapshot artifact (sampled during a sleep window) — the parallel re-audit with log access established the crash-loop + real CPU burn above. No model quota was spent (workers never reach a model call); the cost was CPU/RAM/process churn.
