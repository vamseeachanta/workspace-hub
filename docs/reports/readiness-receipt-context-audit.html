Readiness receipt provenance and context audit

Summary

The native runtime receipt consumer accepts relative source and user-root identities when the caller's working directory completes them. The repair rejects relative context fields before resolution. Provenance rejection, exact version comparison and project/source binding remain required. Synthetic tests establish these software behaviours; live execution and source authenticity are not established by this audit.

Worked example: identity before resolution

Inputs: a disposable temporary directory T contains repo/config/agents/claude/SOUL.runtime.md and a matching synthetic receipt. The recorded source is changed from the absolute T-prefixed path to repo/config/agents/claude/SOUL.runtime.md. Both receipt copies are rewritten identically, and cwd is set to T. No live provider is called.

Method: by path concatenation, cwd plus the relative source resolves to the original file. Its digest is unchanged. That proves file equality, while the recorded path still depends on cwd. The absolute-path predicate is therefore evaluated before resolve.

Answer: the previous consumer reports NATIVE_VERIFIED; the repaired consumer reports BLOCKED. The test test_relative_context_cannot_borrow_callers_directory records this independent derivation. Fully absolute synthetic controls continue to exercise the accepted software branch, without claiming real native execution.

Adversarial verification

Regression cases cover relative context fields, Windows drive-relative and root-only paths, fully qualified drive and UNC paths, POSIX roots, malformed identity types, source classes contradicted by a caller's live role, version lookalikes and another project with equal protected settings. Pure path flavours exercise Windows syntax without claiming a Windows filesystem run.

Existing workflow receipt tests retain provisional comparison results and reject changed governing keys. Existing native tests retain byte, executable, protected configuration, recovery and replica binding checks.

The focused check completed with 168 passing tests. The expanded check completed with 189 passing tests, 8 skips and 36 failures from existing scratch-placement and tool-launch constraints. Ruff reports six existing findings on unchanged lines; the added validation and test cases introduce no reported findings.

Review and known limits

Plan defect review identifies the masking risk: changing only one receipt copy would fail the digest check without exercising context validation. Regression fixtures update both copies. Artifact review checks each context field, native path semantics and the retained provisional workflow result. Independent provider review remains pending; no external assistant is invoked by this change.

A caller able to fabricate both receipt and evidence can still forge claims. This repair does not create an execution attestation service, authenticate arbitrary manifests, change data ownership or qualify live readiness. Historical relative receipts will require fresh absolute context evidence.

Follow-up

Issue 3865 remains the checkpoint for private renderer review and any additional consumer audit. Broader authentication changes require a separately bounded contract. No whole-ecosystem readiness claim is made.
