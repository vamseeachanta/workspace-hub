Static decision list

C01 — Use plain engineering English, with a small terminology check

Add a short editing pass: one idea per sentence, one defined term per concept, explicit subjects, unfamiliar abbreviations expanded and conditions beside conclusions. Preserve units, uncertainty, requirement/advice distinctions and report-present passive methods. Do not claim formal ASD-STE100 compliance or a measurable 80% compliance score.

Tradeoff: Less interpretation work for the reader. Strict controlled-language enforcement could distort engineering terms or conflict with the established report register.

Recommendation: Try the small clarity pass in the pilot; keep the existing engineering register.

Options: Pilot the clarity pass / Investigate formal STE separately / Defer

C02 — Choose the smallest form that answers the review question

Use a schematic for configuration, a table for alternatives and a plot for magnitudes or trends. Add interaction only when switching cases or inspecting a dependency answers a real question. A short status update can remain plain text.

Tradeoff: Targets comprehension without turning every response into a presentation. Formal ten-section reports keep their existing structure; brief explanation views supplement them.

Recommendation: Use the simplest sufficient form, with a static equivalent for every interactive explanation.

Options: Select by the review question / Rich media for each major report / Defer

C03 — Make dependencies and unresolved consequences visible

Add a compact result → criterion → conclusion view, with each material assumption connected to the conclusions it affects. Case selectors will filter frozen, sourced evidence only. Show units, applicability, revision and evidence status; unavailable evidence remains missing. No new solver runs, interpolated results or engineering calculations are implied.

Tradeoff: Helps identify which conclusions can proceed and which await evidence. Extra views create consistency work, so every display must trace to the same qualified source.

Recommendation: Pilot one dependency view and one frozen comparison; keep affected limitations visible without opening a detail panel.

Options: Pilot linked evidence views / Use static dependency tables only / Defer

C04 — Lead recurring updates with what changed and what needs attention

For follow-up sessions and machine work, show changed since the last checkpoint, current blocker, decision needed and next action. Link the full evidence once. Workload counts and ETA carry an observation time; estimates stay labelled. No decision needed is a valid update.

Tradeoff: Reduces repeated histories and unnecessary approval requests. Periodic complete handoffs remain necessary so a new session can recover context.

Recommendation: Use concise change summaries for recurring updates; retain complete, revision-bound handoffs.

Options: Use change summaries plus full handoffs / Keep full summaries every update / Defer

C05 — Keep explainer video optional

Use an animated or narrated explainer only where motion, sequence or repeated confusion remains unresolved by a diagram. Each proposed video will name its audience, subject, duration, compute/cost cap and evidence source before production. Supply captions, transcript and equivalent static evidence. External narration requires applicable data-sharing and service authorization.

Tradeoff: Video may explain a mechanism, but it is slower to inspect, update and cite. A visually persuasive animation can conceal unsupported physics.

Recommendation: Exclude video from the first pilot; request it per case after a diagram has proved insufficient.

Options: Video only by separate request / Prepare a bounded video proposal / Keep text and diagrams only

C06 — Extend the existing pilot before ecosystem rollout

Prepare one synthetic offline review board on this Windows workstation, with three cases: configuration choice, uncertain input and comparison result. Reuse the existing shared review tool. Add a decision-first opening, one schematic, one frozen comparison and a visible limitations panel. Proposed initial production cap: 60 minutes; stop and report gaps at the cap. No live report, shared instruction or machine installation changes.

Tradeoff: Tests whether the changes save review effort before multiplying them across repos. Record production time, review time, clarification requests, missed limitations and defects; a single trial is feedback, not statistical proof.

Recommendation: Run the synthetic pilot after the selected scope is confirmed. Advance only if all seeded material facts/limitations survive, the reviewer can locate decision/criterion/consequence, and offline, keyboard, print and Save/Load checks pass. Then prepare exact repo/machine targets for a separate rollout decision.

Options: Approve the bounded synthetic pilot / Revise pilot scope in notes / Defer pilot
