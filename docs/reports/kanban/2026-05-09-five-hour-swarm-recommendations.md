## Decision summary

Recommended immediate sequence:

1. **Do not launch implementation from the full `status:plan-approved` pool yet.** The board already shows 83 approval-drift issues, and the targeted live checks caught at least one board-vs-live label drift case (`digitalmodel#598`).
2. **Run a short live-state / approval-state audit window first** for `status:working`, approval-marker gaps, stale plan-review labels, and board drift. This avoids duplicate swarms and false execution readiness.
3. **Use 5-hour windows by lane**, not by repo alone: governance repair batches, approval-decision batches, one-issue execution windows, planning factory windows, and status-audit windows.
4. **Prefer control-plane and machine-readiness issues first** because they increase throughput for every later repo-specific swarm.

## Swarm packaging rules

For each 5-hour execution window, create a self-contained prompt with:

- issue URL and approved plan path
- allowed write paths and forbidden paths
- exact tests/verification commands
- GitHub authority split: worker may report evidence; orchestrator owns labels/closeout unless explicitly delegated
- required same-window sequence: resource preflight → RED test/evidence → implementation → verification → commit/push → issue comment/closeout or blocker comment
- future-issue capture rule for adjacent scope

## Other methodology recommendations

1. **Make GitHub Projects the presentation layer, not the source of truth.** Continue deriving boards from issues/labels/plan artifacts, then optionally sync selected fields to Projects v2.
2. **Add computed readiness fields** in generated JSON/HTML: `executable_candidate`, `governance_drift_reason`, `working_audit_required`, `recommended_window_type`, and `file_contention_risk`.
3. **Introduce weekly portfolio WIP caps:** 2 execution issues, 1 governance/approval batch, 1 planning batch, and 1 working-state audit batch active at once.
4. **Treat unlabeled-domain as a first-class gap.** There are 373 unlabeled-domain issues; schedule labeling/planning factory windows before creating more broad issue trees.
5. **Separate approval repair from implementation.** Approval drift is a throughput blocker, but implementing during drift repair violates the gate.
6. **Use batchable lanes for low-contention work only:** plan-review, governance repair, label/domain cleanup, and closed-issue duplicate mining. Implementation remains one issue/window unless file ownership is provably non-overlapping.
7. **Refresh live state before every launch.** The targeted check for this report found live board drift, so each window should begin with `gh issue view` for its issue set.
8. **Keep closeout transactional.** Every execution window must include commit, push, branch/worktree disposition, clean-state proof, and issue update/closure in the same window.
