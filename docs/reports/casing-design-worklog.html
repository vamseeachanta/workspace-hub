Production casing design — algorithms, explorer & wiki notes

Session work review — 2026-07-02 · a public technical presentation turned into a tested design-check layer in digitalmodel, an interactive explorer on the capabilities page, and citable wiki notes — the full repo-ecosystem loop in one pass.

One-line finding. digitalmodel already had the ratings layer (API 5C3 burst / 4-regime collapse / body yield — what a casing product can take). The source deck prescribes the design layer — what the well asks of it: load cases, design factors, sour-service screening and frac limits. That gap is now closed with ~50% reuse of existing code, and the published worked example (5-1/2" 23# P110 → 14,520 psi Barlow burst) is preserved as a golden test.

Source

B. Hansen (Devon Energy), Production Casing Design Considerations, EPA Hydraulic Fracturing Technical Workshop — Session 2: Well Design, August 2011 (public EPA workshop material, 41 pages). Standards referenced: API 5C3 / API TR 5C3 (pipe performance), API 5CT (grades), NACE MR0175 / ISO 15156 (sour service).

Why it matters

Every prior capability (rudder manoeuvring, dynacard troubleshooting, container utilization) followed the same flywheel: public source → issue-planned algorithms → golden-number tests → frozen-artifact explorer with a CI drift guard → capabilities card → wiki knowledge page. Casing design now joins that catalog, and the design-check layer composes cleanly with the existing tubular ratings and VME envelopes — nothing was duplicated.

Verification posture. The build script is byte-reproducible (two consecutive runs produce identical files); the drift-guard test re-runs every published product case against the live checker so a published design factor cannot silently drift; and the explorer’s JavaScript only reads the frozen JSON — no physics re-implementation to diverge.
