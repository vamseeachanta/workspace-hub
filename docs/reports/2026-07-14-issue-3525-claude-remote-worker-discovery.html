3. Exact gaps and security risks

  • Identity gap: no cross-individual-account invitation, delegated machine role, or per-job local authorization principal is documented.
  • Host exposure: the remote operator receives the local process’s filesystem, tools, project configuration, and MCP reach. An ordinary owner OS profile would expose too much.
  • Concurrency: Remote Control server mode defaults to high capacity and shared-directory mode can conflict. A pilot should use capacity one and worktree isolation.
  • Sandbox: server-mode sandboxing is off by default. A pilot should enable it and still enforce OS/repository boundaries.
  • Transcript residency: Remote Control stores messages, responses, and tool activity on Anthropic servers while connected, although execution and files stay local.
  • Wake dependency: Remote Control, Dispatch, Channels, and local Desktop tasks cannot execute while the host is asleep/off or the required process/app is stopped. Desktop “keep awake” does not wake a sleeping or powered-off PC.
  • Permission relay: allowed remote/channel senders can approve tools. Pairing and sender allowlists are high-trust controls, not low-risk notification plumbing.
  • Consumer spend: official docs expose usage limits but no per-job monetary ceiling for Remote Control/Desktop tasks. A custom API runner has stronger workspace attribution and budget controls.
  • Preview risk: Remote Control, Channels, Dispatch, and Routines include preview/beta surfaces whose limits and APIs may change.
  • Audit gap: native features expose session history, but no documented tamper-evident local job ledger, durable queue, or delegated-execution audit contract was found.
Credential-sharing prohibition
  • Do not share passwords or account login links.
  • Do not copy session cookies or browser profiles.
  • Do not copy raw OAuth credentials or subscription tokens.
  • Do not share a personal API key; use a scoped organization credential for automation.

5. Go / no-go decision

GO — use the existing native feature stack for a bounded same-account pilot.

Use Remote Control first, under a dedicated Windows OS profile authenticated personally by the remote operator. This satisfies “machine under the operator’s account” without sharing credentials. Treat Desktop scheduling and Dispatch as optional additions after a separate implementation plan verifies Desktop, permissions, wake behavior, and logging.

Blocking precondition: the machine owner and organization security owner must approve this dedicated-profile posture before any login, pairing, or pilot run. Without both approvals, the decision is DEFER.

NO-GO for cross-account delegation, copied credentials, owner-profile execution, high-capacity shared-directory server mode, or production webhooks through preview Channels without a separate threat model.

Do not build a custom runner yet. Escalate to the API/WIF runner only if distinct identities, durable authenticated queueing, hard spend controls, or always-on webhook operation are mandatory.

6. Smallest safe fallback architecture

If the native same-account boundary is unacceptable, the minimum defensible runner is outbound-pull only. It should expose jobs, not a shell.

Least privilegeMinimal filesystem, Git, network, tool, and branch permissions.
Authenticated pull queuePrivate immutable envelopes, expiry, nonce, signature/authorized writer, outbound polling only.
Repository/action allowlistRepository IDs and fixed workflows; reject arbitrary command strings.
Audit logStructured append-only job, lease, command-class, result, and redaction evidence.
Concurrency lockOne job initially; fenced lease, stale recovery, isolated worktree per job.
Spend/rate limitPer-job token/time ceiling, workspace limits, daily circuit breaker, usage reporting.
Failure quarantineBounded retries, poison-job isolation, kill switch, no automatic privilege expansion.
Wake handlingStart-when-available task, explicit sleep policy, optional wake timer/Wake-on-LAN, powered-off state reported—not hidden.

Planning assumption: 600–1,200 production lines plus comparable tests, approximately 2–3 engineer-weeks and 3–5 calendar weeks under planning, TDD, adversarial review, and Windows smoke gates. This ROM estimate is based on decomposition of the ten controls above and reuse of an internal outbound worker pattern; it has not been validated by an implementation spike. Confidence: medium. Identity authorization, coding isolation, hard budgets, and wake semantics are the security-critical remainder.
