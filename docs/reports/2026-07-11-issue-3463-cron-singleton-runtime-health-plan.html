Cron singleton and bounded runtime health

Issue: workspace-hub #3463
Status: draft · T3 · lane:claude · 2026-07-11

Outcome

Repository sync will become a tested singleton. Cron health will report runtime and log evidence independently, validate PID identity without broad process or filesystem scans, and expose safe operator evidence without terminating anything automatically.

Chosen design

Separate task-owned active, contention, and last-result records plus a nonblocking lock will replace heuristic pgrep -f identity. Each active record will carry task ID, PID, process-group/session IDs, process start token, start time, process state, and wait channel. PID start-token validation will reject stale or reused PIDs without conflating a completed run with stale evidence.

ApproachDecisionReason
Task-owned state + lockUseBounded, exact, testable, reusable
Substring pgrep -fRejectSelf-matches and confuses descendants
Scheduler migrationDeferOwned by issues #2762/#2765

Implementation slices

  1. Write RED runtime-contract and schedule-schema tests.
  2. Implement the minimal atomic runtime runner, PID validation, signal forwarding, and lock retention until the child group exits.
  3. Enforce repository-sync singleton and reconcile its declared/rendered log.
  4. Add independent runtime states to cron-health console and JSON output.
  5. Test transactional reconciliation of stale catalog entries and preserved external entries.
  6. Update scheduled-task inventory and create the safe process-response runbook.

Safety invariants

  • No broad FUSE, repository-tree, or process-substring scan.
  • No automatic process termination or escalation.
  • A fresh bounded PID/PPID/PGID/SID/elapsed/wchan snapshot and user approval will precede TERM.
  • The cron daemon's shared process group will never be a termination target.
  • Exact live command evidence will be required before classifying an import-timing process.
