Objective and deliverable

The work will prove a local end-to-end operational workflow for library/templates/mooring_buoy/spec.yml: immutable configuration, generated inputs, native analysis, saved-result readback, selected output tables and an HTML report. It will retain the 11.5-second buildup and 100-second main stage, 0.01-second timestep and 0.1-second logging interval. It will distinguish execution acceptance, numerical fidelity and physical qualification. Missing strength allowables, calibrated damping or reference tolerances will remain explicit gaps.

The scope will include a narrow generated restart-script default repair, an audited-model mode in the existing local bounded harness, a thin model probe and a case evidence manifest. It will not change production queues/tasks, damping, source duration or the claim registry.

Execution method and limits

  1. The work will use the integrated validator repair or an explicitly pinned reviewed dependency containing it. It will record the base commit, existing Python/API environment, source hashes and fixed Python hash seed. Seed-independent ordering will remain a parallel follow-on; the immutable bundle will permit this case to progress.
  2. A manifest will enumerate the master and every include, reject escaping/changed paths, unsupported external dependencies and execution hooks, and declare exact objects/results/locations/units. The default empty script will receive a narrow TDD repair before native invocation; nonempty scripts will remain prohibited for this case. Original inputs will remain immutable.
  3. An audited-model mode will create OrcFxAPI.Model(threadCount=1), load the pinned master, verify observed thread count and read back exact settings/object inventory. It will calculate statics and run complete source stages. A Windows Job Object deadline of at most 300 wall-clock seconds per process will cover import, licence acquisition, load, solve, extraction and save. Only one solver process will run at a time; timeout or uncertain cleanup will stop dependent work.
  4. The probe will extract Mooring End A/End B effective tensions, static line positions and buoy position, plus buoy X/Z/pitch and sea-surface Z histories at the buoy, using verified API names and coordinate frames. Unsupported selections, nonfinite/empty output or incomplete time coverage will fail the stage. Warnings will remain visible.
  5. The solver process will save its simulation and close. Cleanup will retain a queryable Job handle, terminate remaining owned processes and observe both root exit and job ActiveProcesses=0 before releasing the handle or launching readback. A separate ten-second cleanup deadline will bound this drain; query failure or nonzero activity will emit cleanup_unknown and block all further native phases. Closing a kill-on-close handle alone will not count as observed whole-job exit. A new contained one-thread process will independently reload the simulation and verify completion, settings, sample times and selected histories. Exact equality of corresponding finite result arrays, counts and sample times will be required. No result-value tolerance will be widened to obtain a pass.
  6. The report will show provenance, stage outcomes, version, units/frames, extrema/histories, reference differences and unresolved acceptance. Original-model execution will occur only after an offline comparison establishes compatible inputs and the same hook/dependency policy passes. This approval scope will permit at most two full solve attempts (candidate plus compatible original), each with one independent readback process and the same 300-second limit. Additional retries, altered settings or convergence campaigns will require a new checkpoint.

Concrete interface and comparison contract

The GeneralBuilder default will become the Python empty string "", emitted as a quoted empty YAML string, not omission, false or null. Tests will verify that exact field while retaining unrelated nulls and explicit overrides. An explicit null/nonempty override in this audited case will fail preflight; it will not be silently rewritten.

The existing PowerShell wrapper will add -Mode Smoke|Model (default Smoke) and -Manifest required only in Model mode. Model mode will dispatch the new CLI with --manifest, --phase solve|readback and --output; it will not modify the fixed smoke CLI. The wrapper will set and record PYTHONHASHSEED=0 before every generation/native/readback process starts. Generation will finish before native execution, and hashes will be rechecked immediately before each load and after each process.

The tracked qualification.yml will be a version-1 YAML case contract with required case_id, source relative path, expected objects/settings, required result selectors, period, units/frames, equality policy and resource bounds. A private generated JSON run manifest will add schema_version, run/attempt identity, source revision/hash, master relative path, complete sorted include/file SHA-256 list, dependency/hook decisions, seed and output-relative locations. Unknown/missing fields, duplicate identities, escaping paths, unlisted reachable includes and changed bytes will fail closed. No selector will contain executable expressions. A strict JSON proof will report phase statuses, actual version/threads, output hashes, comparison verdicts, warnings and exact failure stage; public derivatives will omit private paths.

All listed outputs will be required, with no minimum-subset fallback: static End A/End B effective tension, static Mooring XYZ along arc length and buoy-origin XYZ; and six main-stage histories comprising two endpoint effective tensions plus buoy-origin X, Z, Rotation 2 and Sea surface Z. The latter four selections will follow the Orcina 6D-buoy result definitions; Rotation 2 will be labelled as global-axis orientation, not dynamic local pitch. Runtime API availability will be checked without silently renaming or dropping a selector. Units will be kN, m and degrees as appropriate. Histories will cover the complete main stage [0,100] seconds at the source logging interval; expected times will be independently constructed from the frozen contract and compared with a predeclared 1e-9-second absolute grid tolerance, solely for floating-point time representation.

Saved-result readback will require exact equality of corresponding finite numeric result arrays, sample counts and sample times emitted before save and after independent reload; no result-value tolerance will be introduced in this increment. The time-grid tolerance above will not permit result-value drift. Mismatch will block acceptance and produce a follow-on investigation. Original-model comparisons will be descriptive only in this increment: no quantitative parity verdict or invented tolerance will be assigned. The offline source/reference difference manifest will be produced before the first solve; preflight will not consume a native attempt. The guide and original YAML will remain separate provenance sources, neither a calibrated oracle.

The 300-second process limit will be an authorized exposure cap, not a measured or predicted solve duration. Its exhaustion will record an incomplete attempt and will not authorize shortening stages or increasing the cap. Cleanup will have the separate bounded drain interval specified above. Maximum process usage will remain two solve attempts plus their two independent readbacks, sequentially.

Acceptance and risks

Operational acceptance will require the exact case/settings manifest, full-duration solve, finite selected results, independent saved-result fidelity, observed one-thread execution, bounded cleanup and truthful report. Numerical equivalence will require compatible reference inputs and predeclared criteria; absent criteria will produce an unqualified comparison. Physical acceptance will remain open until equilibrium/load-path evidence, response/convergence tolerances and damping/strength basis are justified. No invented percentage or native-success flag will replace those requirements.

Load/statics failure will preserve the exact failing include/object and stop dependent phases. The responsible issue will receive the failure evidence; coefficients and source fields will not be retuned or deleted to force success. Unresolved explicit-null script semantics will block native execution rather than trigger global normalization.
