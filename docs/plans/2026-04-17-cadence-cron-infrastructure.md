## Deliverable

A reusable cron-cadence pattern, expressed as `scripts/cron/lib/cadence-common.sh`
helpers and a canonical report-file naming convention, that lets each of the 8
cadence issues ship as a thin (~80–120 line) shell script + a thin (~50 line)
pytest. Each cadence emits a single markdown report to `docs/reports/` per period
with GREEN/YELLOW/RED health bands and a top-N table.

## Pseudocode

```
# scripts/cron/lib/cadence-common.sh — sourced by every cadence cron
emit_report_header() {
    local name="$1" period="$2" status="$3" summary="$4"
    cat <<HEADER
# ${name} — ${period}

**Status:** ${status} — ${summary}

HEADER
}

compute_status_band() {
    local value="$1" warn="$2" block="$3"
    if (( value > block )); then echo RED
    elif (( value > warn )); then echo YELLOW
    else echo GREEN
    fi
}

cadence_period() {
    # cadence_period weekly|monthly|quarterly  → 2026-W16, 2026-04, or 2026-Q2
    case "$1" in
        weekly)    date +%Y-W%V ;;
        monthly)   date +%Y-%m ;;
        quarterly) printf '%s-Q%d\n' "$(date +%Y)" "$(( ($(date +%-m) - 1) / 3 + 1 ))" ;;
    esac
}

# scripts/cron/<name>.sh — per-cadence template
source "$(dirname "$0")/lib/cadence-common.sh"

NAME="<cadence-name>"
PERIOD="$(cadence_period <weekly|monthly|quarterly>)"
OUT="${REPO_ROOT}/docs/reports/${NAME}-${PERIOD}.md"

# 1. Collect data (per-cadence specifics)
# 2. Compute headline metric + status band
status="$(compute_status_band "$metric" "$WARN" "$BLOCK")"

# 3. Render report
{
    emit_report_header "$NAME" "$PERIOD" "$status" "<one-line summary>"
    # table rows from collected data
    echo "## Source"
    echo "Generated by \`scripts/cron/${NAME}.sh\` (#<issue>)."
} > "$OUT"

echo "[${NAME}] wrote $OUT (status: $status)"
```

## Risks and Open Questions

- **Risk:** ISO week vs week-of-month variance — `date +%Y-W%V` is ISO-8601 (Mon-start), but Sun-start systems differ. Documented and standardized to `%V`.
- **Risk:** Quarterly cron `1 1,4,7,10` runs on Jan/Apr/Jul/Oct 1 — leap-year robust, but means a quarterly that needs current-quarter data must look back, not forward.
- **Risk:** `scripts/cron/lib/cadence-common.sh` becomes a new dependency for 8 scripts at once. If the helper has a bug, all 8 break. Mitigation: TDD the helpers first; any helper change requires re-running all 8 cadence tests.
- **Open:** Should each cadence's report file overwrite the previous period's, or accumulate? Current plan: one file per period (deterministic name) — old reports stay for history. May need a quarterly cleanup if `docs/reports/` bloats.
- **Open:** Should the cadence schedule live in cron or in GitHub Actions? Current plan: local cron via `scripts/cron/crontab-template.sh` to match existing convention. Migration to Actions is a separate decision.
