## Option Selection

The issue body lists three options. This plan chooses **Option A** and explicitly rejects B and C with rationale:

### Option A (chosen) — extend `build.js` to copy sitemap.xml → dist/sitemap.xml
- Pro: smallest change (one new function, one call site); matches the existing `copyAssets()` pattern; no new dependencies; no build-semantics change.
- Pro: directly addresses the documented defect without adding indirection.
- Con: `sitemap.xml` source and deployed copy can drift if build is not re-run. Mitigated by Vercel rebuilding on every push (the source lives in git; any sitemap edit triggers a build).

### Option B (rejected on fitness) — Vercel rewrite serving sitemap.xml

Vercel's `rewrites` field in `vercel.json` supports same-application rewrites within the deployed app and rewrites to external origins, per the [Vercel Rewrites docs](https://vercel.com/docs/routing/rewrites) and [vercel.json reference](https://vercel.com/docs/project-configuration/vercel-json). Rewrites **cannot** reach repo-root files that are not part of `outputDirectory`. To serve `sitemap.xml` via Option B, we would need to either:

- (a) include `sitemap.xml` in `outputDirectory` — which is Option A by another name;
- (b) serve it from a Vercel Function that reads and returns the XML body at request time; or
- (c) rewrite to an external origin that hosts the sitemap.

Each of these adds operational complexity for a single static XML file:

- Adding a rewrite (with (b) or (c)) introduces a request-time indirection for what is otherwise a plain static asset.
- It increases the `vercel.json` surface area reviewed on every deploy, and couples sitemap availability to routing config (or a Function / external origin) rather than file presence.
- A serverless function (or external proxy) for one static file is a runtime dependency where none is needed — strictly more complex than the ~5-line `build.js` extension in Option A.
- Option A's build-time copy keeps `sitemap.xml` as a plain static asset, matching the semantics of every other file Vercel serves from `dist/`.

Rejected on fitness — more moving parts and more `vercel.json` surface to review per deploy than a one-function build-time copy.

### Option C (rejected for this PR; kept as follow-up) — auto-generate sitemap.xml at build time from `dist/` listing
- Pro: eliminates source/deploy drift by construction; always matches the deployed pages; dovetails with #2357 (can emit `www.` host for every entry consistently).
- Con: scope creep for a 404 fix. Requires design decisions (lastmod source, priority heuristic, excludes list) that are not part of #2391's acceptance. Changes the "source of truth" semantics.
- Disposition: file as a separate follow-up issue at PR time ("auto-generate sitemap.xml at build"). Not bundled with this plan.

### #2357 bundling decision — deploy-gate: both-ready or defer

**Recommendation: keep PRs separate, gate #2391 on #2357 readiness.** #2357 (apex→www backfill of the **34** existing apex `<loc>` entries) is a distinct editorial change to `sitemap.xml` with its own approved-plan workflow (currently `status:plan-review`). Bundling would:
- Enlarge the blast radius of this defect fix (changing 34 lines + the build pipeline in the same commit).
- Force a re-review of #2357's plan inside this plan.
- Delay the 404 fix, which unblocks all sitemap-dependent issues.

**Sequencing commitment (revised in v3, per Codex round-2 REQUEST-CHANGES F2):** Once #2391 lands, crawlers will see 34 apex-host URLs that each 301-redirect to the `www.` host. Until #2357 lands, this is a visible, measurable canonicalization-hop window — not a trivial redirect. To prevent opening that window without a known close, the sequencing is a **deploy-gate**:

- **#2391 shall not merge to main until #2357 is also approved-and-ready.**
- At-merge-time, #2391 and #2357 enter the deploy queue together (whether as two back-to-back merges or a single bundled PR is an operational choice, see Alternative below).
- If #2357 is not approved-and-ready at the moment #2391 is ready to merge, **#2391 is deferred** until both are ready. The canonicalization-hop window is never opened without a guaranteed close.

This deploy-gate replaces v2's "same day, back-to-back" language — which was not operationally bounded — with a concrete readiness condition that is enforceable at merge time.

**Alternative (retained for user choice): bundle into one PR.** Pragmatic; reduces reviewer surface for a tightly coupled pair of edits but makes the change larger. If the user prefers this path, approve this plan with the instruction "bundle #2357" and the implementer will fold the #2357 edits into the same commit after dispatching a re-review.
