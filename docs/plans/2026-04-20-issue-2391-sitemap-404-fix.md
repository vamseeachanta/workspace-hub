## Option Selection

The issue body lists three options. This plan chooses **Option A** and explicitly rejects B and C with rationale:

### Option A (chosen) — extend `build.js` to copy sitemap.xml → dist/sitemap.xml
- Pro: smallest change (one new function, one call site); matches the existing `copyAssets()` pattern; no new dependencies; no build-semantics change.
- Pro: directly addresses the documented defect without adding indirection.
- Con: `sitemap.xml` source and deployed copy can drift if build is not re-run. Mitigated by Vercel rebuilding on every push (the source lives in git; any sitemap edit triggers a build).

### Option B (rejected) — Vercel rewrite serving sitemap.xml from repo root
- Vercel rewrites route requests to files/functions **inside `outputDirectory` (`dist/`)**. They cannot reach arbitrary repo-root files that were never deployed. Even if a workaround existed via a serverless function, it would add a runtime dependency for a static file — strictly worse than Option A.
- Therefore Option B is not viable as described in the issue. Rejected.

### Option C (rejected for this PR; kept as follow-up) — auto-generate sitemap.xml at build time from `dist/` listing
- Pro: eliminates source/deploy drift by construction; always matches the deployed pages; dovetails with #2357 (can emit `www.` host for every entry consistently).
- Con: scope creep for a 404 fix. Requires design decisions (lastmod source, priority heuristic, excludes list) that are not part of #2391's acceptance. Changes the "source of truth" semantics.
- Disposition: file as a separate follow-up issue at PR time ("auto-generate sitemap.xml at build"). Not bundled with this plan.

### #2357 bundling decision
**Kept separate.** #2357 (apex→www backfill of the 32 existing `<loc>` entries) is a distinct editorial change to `sitemap.xml` with its own approved-plan workflow (currently `status:plan-review`). Bundling would:
- Enlarge the blast radius of this defect fix (changing 32 lines + the build pipeline in the same commit).
- Force a re-review of #2357's plan inside this plan.
- Delay the 404 fix, which unblocks all sitemap-dependent issues.

Plan ordering: land #2391 first (sitemap starts serving 33 entries including the jumper www entry; 32 apex entries 301 through Vercel redirect — functional but imperfect). Then land #2357 in a follow-up PR (rewrites the 32 apex entries to www, eliminating the redirect hop for crawlers).

Note this plan for the user: if you would prefer to bundle #2391 and #2357 into a single PR for atomicity, approve this plan with that instruction and the implementer will fold the #2357 edits into the same commit after dispatching a re-review.

## Rollback Plan

Single-commit revert inside `aceengineer-website/` restores the pre-fix state:
```
cd aceengineer-website && git revert <sha> && git push
```
Vercel rebuilds ≤5 min; sitemap returns to 404; robots advertises the apex URL again. Blast radius: two files (`build.js`, `robots.txt`). No other deploy artefacts are touched.

Known-good commit: the last `aceengineer-website` `main` commit before this fix lands. SHA captured at PR time.

Failure modes and responses:
- `copySitemap()` throws on `fs.copyFileSync`: the build will fail and Vercel will serve the prior deploy; no production regression. Fix forward.
- `robots.txt` edit accidentally breaks syntax: crawlers fall back to defaults; revert the single-line change without touching `build.js`.
- Post-deploy 404 persists (unexpected): verify `dist/sitemap.xml` in the Vercel build logs; if absent, the copy call was not reached — add a log line and redeploy.

## Risks and Open Questions

- **Risk:** once sitemap.xml begins serving, all 32 apex-host `<loc>` entries become visible to crawlers that previously saw 404. Each apex URL 301-redirects to `www.` via `vercel.json`, so Googlebot will index the `www.` variant — acceptable, but adds a redirect hop on every crawl until #2357 lands. Mitigation: prioritize #2357's approval + merge after #2391 lands.
- **Risk:** Vercel may not infer `Content-Type: application/xml` for `.xml` files in every edge region. Mitigation: post-deploy test `prod_sitemap_content_type` verifies. If missing, add a `vercel.json` `headers` entry for `/sitemap.xml` in a follow-up.
- **Risk:** source/deploy drift if someone edits `sitemap.xml` but forgets to redeploy. Mitigation: Vercel rebuilds on every push; any `sitemap.xml` edit triggers a rebuild. Option C (follow-up) removes this class of risk entirely.
