## Option Selection

The issue body lists three options. This plan chooses **Option A** and explicitly rejects B and C with rationale:

### Option A (chosen) — extend `build.js` to copy sitemap.xml → dist/sitemap.xml
- Pro: smallest change (one new function, one call site); matches the existing `copyAssets()` pattern; no new dependencies; no build-semantics change.
- Pro: directly addresses the documented defect without adding indirection.
- Con: `sitemap.xml` source and deployed copy can drift if build is not re-run. Mitigated by Vercel rebuilding on every push (the source lives in git; any sitemap edit triggers a build).

### Option B (rejected on fitness, not feasibility) — Vercel rewrite serving sitemap.xml

Option B is technically feasible. Vercel rewrites can serve from paths outside `outputDirectory` and can proxy to external origins via `vercel.json` `rewrites` (see [Vercel Rewrites docs](https://vercel.com/docs/routing/rewrites) and [vercel.json reference](https://vercel.com/docs/project-configuration/vercel-json)). The earlier v1 claim that rewrites "cannot reach files/functions outside `outputDirectory`" was incorrect.

Rejected on **fitness**, not feasibility:
- Adding a rewrite for a single static XML file introduces a request-time indirection for what is otherwise a plain static asset.
- It increases the `vercel.json` surface area reviewed on every deploy, and couples sitemap availability to routing config rather than file presence.
- A serverless function (or external proxy) for one static file is a runtime dependency where none is needed — strictly more complex than the ~5-line `build.js` extension in Option A.
- Option A's build-time copy keeps `sitemap.xml` as a plain static asset, matching the semantics of every other file Vercel serves from `dist/`.

Rejected on fitness, not feasibility.

### Option C (rejected for this PR; kept as follow-up) — auto-generate sitemap.xml at build time from `dist/` listing
- Pro: eliminates source/deploy drift by construction; always matches the deployed pages; dovetails with #2357 (can emit `www.` host for every entry consistently).
- Con: scope creep for a 404 fix. Requires design decisions (lastmod source, priority heuristic, excludes list) that are not part of #2391's acceptance. Changes the "source of truth" semantics.
- Disposition: file as a separate follow-up issue at PR time ("auto-generate sitemap.xml at build"). Not bundled with this plan.

### #2357 bundling decision — same-day back-to-back merge commitment

**Recommendation: keep PRs separate, commit to same-day back-to-back merge.** #2357 (apex→www backfill of the **34** existing apex `<loc>` entries) is a distinct editorial change to `sitemap.xml` with its own approved-plan workflow (currently `status:plan-review`). Bundling would:
- Enlarge the blast radius of this defect fix (changing 34 lines + the build pipeline in the same commit).
- Force a re-review of #2357's plan inside this plan.
- Delay the 404 fix, which unblocks all sitemap-dependent issues.

**Sequencing commitment (new in v2, per Codex MAJOR):** Once #2391 lands, crawlers will see 34 apex-host URLs that each 301-redirect to the `www.` host. Until #2357 lands, this is a visible, measurable canonicalization-hop window — not a trivial redirect. To bound that window:

- Land #2391 first.
- Merge #2357 **the same day**, back-to-back — not "within 7 days," not "prioritized." Same calendar day, with #2357 already at `status:plan-review` and ready for fast approval after #2391 lands.
- If the #2357 plan is not yet reviewer-ready on #2391's merge day, delay #2391's merge until both are ready. The canonicalization-hop window is the reason; do not start the window unless it can be closed the same day.

**Alternative (retained for user choice): bundle into one PR.** Pragmatic; reduces reviewer surface for a tightly coupled pair of edits but makes the change larger. If the user prefers this path, approve this plan with the instruction "bundle #2357" and the implementer will fold the #2357 edits into the same commit after dispatching a re-review.

## Rollback Plan

Single-commit revert inside `aceengineer-website/` restores the pre-fix state:
```
cd aceengineer-website && git revert <sha> && git push
```
Vercel rebuilds ≤5 min; sitemap returns to 404; robots advertises the apex URL again. Blast radius: two files (`build.js`, `robots.txt`). No other deploy artefacts are touched.

Known-good commit: the last `aceengineer-website` `main` commit before this fix lands. SHA captured at PR time.

Failure modes and responses:
- `copySitemap()` throws on `fs.copyFileSync`: the build will fail and Vercel will serve the prior deploy; no production regression. Fix forward.
- `robots.txt` edit accidentally breaks syntax: crawlers fall back to defaults; revert the single-line change without touching `build.js`.
- Post-deploy 404 persists (unexpected): verify `dist/sitemap.xml` in the Vercel build logs; if absent, the copy call was not reached — add a log line and redeploy.

## Risks and Open Questions

- **Risk (crawler canonicalization window, strengthened in v2):** once `sitemap.xml` begins serving, all **34 apex-host `<loc>`** entries become visible to crawlers that previously saw 404. Each apex URL 301-redirects to `www.` via `vercel.json`, so Googlebot will index the `www.` variant. This is **not a trivial redirect** — it is a measurable canonicalization hop on every sitemap-driven crawl until #2357 lands. Mitigation: same-day back-to-back merge of #2357 committed in Option Selection § "#2357 bundling decision"; #2391 merge will be deferred if #2357 is not reviewer-ready the same day.
- **Risk:** Vercel may not infer `Content-Type: application/xml` for `.xml` files in every edge region. Mitigation: post-deploy test `prod_sitemap_content_type` verifies. If missing, add a `vercel.json` `headers` entry for `/sitemap.xml` in a follow-up.
- **Risk (source/deploy drift):** if someone edits `sitemap.xml` but forgets to redeploy, the live copy diverges. Mitigation: Vercel rebuilds on every push; any `sitemap.xml` edit triggers a rebuild. Option C (follow-up) removes this class of risk entirely.
- **Risk (inverse drift, new in v2 per Claude MINOR):** `build.js:89-92` calls `fs.rmSync(distDir, { recursive: true, force: true })` at the start of every build, wiping `dist/` before regenerating. Any post-build edit made directly to `dist/sitemap.xml` will be **silently lost on the next build**. The source at `aceengineer-website/sitemap.xml` remains the single point of truth. Operationally: do not hot-patch `dist/sitemap.xml`; always edit the source and rebuild.

Plan recommends keeping separate with the same-day merge gate. If the user chooses to bundle, the implementer will fold #2357's 34-line sitemap edit into the same commit and re-dispatch an adversarial review.
- **Open question for user:** accept the deferred Option C follow-up, or escalate to in-scope for this PR? Plan recommends deferral.
