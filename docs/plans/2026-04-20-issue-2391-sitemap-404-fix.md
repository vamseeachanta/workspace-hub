## Option Selection

The issue body lists three options. This plan chooses **Option A** and explicitly rejects B and C with rationale:

### Option A (chosen) — extend `build.js` to copy sitemap.xml → dist/sitemap.xml
- Pro: smallest change (one new function, one call site); matches the existing `copyAssets()` pattern; no new dependencies; no build-semantics change.
- Pro: directly addresses the documented defect without adding indirection.
- Con: `sitemap.xml` source and deployed copy can drift if build is not re-run. Mitigated by Vercel rebuilding on every push (the source lives in git; any sitemap edit triggers a build).

### Option B (rejected on fitness) — Vercel rewrite serving sitemap.xml

Vercel's `rewrites` field in `vercel.json` supports same-application rewrites within the deployed app and rewrites to external origins, per the [Vercel Rewrites docs](https://vercel.com/docs/routing/rewrites) and [vercel.json reference](https://vercel.com/docs/project-configuration/vercel-json). Rewrites **cannot** reach repo-root files that are not part of `outputDirectory`. To serve `sitemap.xml` via Option B, we would need to either:

- (a) include `sitemap.xml` in `outputDirectory` — which is Option A by another name;
- (b) serve it from a [Vercel Function](https://vercel.com/docs/functions) that reads and returns the XML body at request time; or
- (c) rewrite to an external origin that hosts the sitemap.

Each of these adds operational complexity for a single static XML file:

- Adding a rewrite (with (b) or (c)) introduces a request-time indirection for what is otherwise a plain static asset.
- It increases the `vercel.json` surface area reviewed on every deploy, and couples sitemap availability to routing config (or a Function / external origin) rather than file presence.
- A serverless function (or external proxy) for one static file is a runtime dependency where none is needed — strictly more complex than the ~5-line `build.js` extension in Option A.
- Option A's build-time copy keeps `sitemap.xml` as a plain static asset, matching the semantics of every other file Vercel serves from `dist/`.

Rejected on fitness — more moving parts and more `vercel.json` surface to review per deploy than a one-function build-time copy.

### Option C (rejected for this PR; kept as follow-up) — auto-generate sitemap.xml at build time from `dist/` listing
- Pro: eliminates source/deploy drift by construction; always matches the deployed pages; dovetails with #2357 (can emit `www.` host for every entry consistently).
- Con: scope creep for a 404 fix. Requires design decisions (lastmod source, priority heuristic, excludes list) that are not part of #2391's acceptance. Changes the "source of truth" semantics.
- Disposition: file as a separate follow-up issue at PR time ("auto-generate sitemap.xml at build"). Not bundled with this plan.

### #2357 sequencing decision — decouple and ship #2391 immediately (v5)

**Decision: ship #2391 independently; #2357 lands on its own schedule.** #2357 (apex→www backfill of the **34** existing apex `<loc>` entries) is a distinct editorial change to `sitemap.xml` with its own approved-plan workflow (currently `status:plan-review`).

**v5 decoupling rationale (Codex round-4 MAJOR finding):** Codex round-4 argued — correctly on balance, after weighing against Codex round-2's own prior demand for a deploy-gate — that blocking a live 404 production fix on a separate editorial cleanup inflates the avoidable risk window. The sitemap has been 404 for weeks; the crawler-canonicalization-hop window (34 apex URLs each 301-redirecting to `www.`) is a shorter, less-bad problem than indefinite sitemap-404 while #2357 drifts through review. 2/3 of round-4 reviewers (Claude APPROVE, Gemini MINOR "effectively mitigates risks") approved the v4 deploy-gate; Codex's round-4 argument is a principled reversal of its round-2 position, and on the production-fix-priority axis it wins.

**Residual risk (canonicalization window):** once `sitemap.xml` begins serving under v5, Googlebot and other crawlers will see the 34 apex-host URLs and follow each to `www.` via the existing `vercel.json` 301. This is a real but bounded cost:
- Each apex URL resolves via 1 redirect, not a chain. Browser-behavior impact: nil. Crawler-ranking impact: non-zero but bounded (a 301 is the standard canonicalization signal; Googlebot handles this cleanly).
- #2357 remains open and should ship soon — closing the window. But it does not gate #2391.
- If #2357 is already approved-and-ready at the time #2391 is merged, the implementer may opt to merge both in the same deploy window as a coincidence, not a requirement.

**Alternative (user can still choose): bundle.** If the user explicitly prefers the "no canonicalization window ever" posture, approve this plan with the instruction "bundle #2357" and the implementer will fold the #2357 sitemap edits into the same commit. The v5 default is decouple.

**Prior gating language (removed in v5):** v3/v4 required "#2391 shall not merge to main until #2357 is also approved-and-ready" per Codex round-2 F2. v5 removes that gate per Codex round-4. The revision-history entries for v3 and v4 preserve the prior language for audit.

## Risks and Open Questions

- **Risk (crawler canonicalization window, v5 posture — accepted, bounded):** once `sitemap.xml` begins serving, all **34 apex-host `<loc>`** entries become visible to crawlers that previously saw 404. Each apex URL 301-redirects to `www.` via `vercel.json`, so Googlebot will index the `www.` variant. This is a measurable canonicalization hop on every sitemap-driven crawl until #2357 (the apex→www backfill) lands. **Accepted in v5** per Codex round-4 P1 argument: blocking a live 404 fix on a separate editorial cleanup is worse than accepting a bounded 301-hop window. Mitigation: ship #2357 on its own schedule as soon as practical; the window closes when #2357 lands. Prior deploy-gate (v3/v4) removed.
- **Risk:** Vercel may not infer `Content-Type: application/xml` for `.xml` files in every edge region. Mitigation: post-deploy test `prod_sitemap_content_type` verifies. If missing, add a `vercel.json` `headers` entry for `/sitemap.xml` in a follow-up.
- **Risk (source/deploy drift):** if someone edits `sitemap.xml` but forgets to redeploy, the live copy diverges. Mitigation: Vercel rebuilds on every push; any `sitemap.xml` edit triggers a rebuild. Option C (follow-up) removes this class of risk entirely.
- **Risk (inverse drift, added in v2 per Claude MINOR; citation corrected in v3 per Claude round-2 MINOR):** `build.js:89-91` clears `dist/` at the start of every build via `if (fs.existsSync(distDir)) { fs.rmSync(distDir, { recursive: true }); }` (line 92 is the separate `fs.mkdirSync(distDir)` that rebuilds it). Any post-build edit made directly to `dist/sitemap.xml` will be **silently lost on the next build**. The source at `aceengineer-website/sitemap.xml` remains the single point of truth. Operationally: do not hot-patch `dist/sitemap.xml`; always edit the source and rebuild.
- **Open question for user (optional override):** v5 decouples #2391 from #2357 by default. If the user explicitly prefers "no canonicalization window ever", approve with the instruction "bundle #2357" and the implementer will fold the #2357 34-line sitemap edit into the same commit and re-dispatch an adversarial review. Plan default (v5): decouple and ship.
