## Goal

Build a pipeline that will read threads under Gmail `label:CRE`, apply the `cre-listing.yaml` extraction template, and write one structured YAML listing per thread into `assethold/data/cre-listings/<yyyy-mm>/<thread_id>.yaml`. The pipeline will gate every commit behind `scripts/legal/legal-sanity-scan.sh`, and will be idempotent — re-runs against the same `label:CRE` cohort will produce no new files or commits.

## Phase B — Architecture

### Module tree (proposed, new files under `scripts/email/`)

```
scripts/email/
  extract/
    __init__.py
    cli.py              # entry point: gmail-extract-and-act
    templates.py        # YAML template loader + schema validator
    fields.py           # regex/transform engine driven by template fields
    gmail_reader.py     # Gmail MCP wrapper for label:CRE threads (read-only)
    writer.py           # per-thread YAML writer to assethold/data/cre-listings/
    legal_gate.py       # subprocess wrapper for scripts/legal/legal-sanity-scan.sh
    state.py            # v1 JSON state file stub (pre-#2026)
```

Entry point will be exposed as `uv run scripts/email/gmail-extract-and-act.py --label CRE --account ace --max 50 [--dry-run]`; the top-level script will be a thin shim that delegates to `extract.cli.main`.

### Template loader pattern

`templates.py` will load any template under `scripts/email/templates/*.yaml`, validate against a minimal schema (`template.name`, `template.version`, `fields[*].name`, `output.destination`), and return an immutable object consumed by `fields.py`. This loader is domain-agnostic — `cre-listing.yaml` is the v1 consumer, but the same loader will later accept `invoice.yaml`, `tenant-comm.yaml`, `tax-doc.yaml` without code change.

### Gmail read path

Pipeline reads exclusively via Gmail MCP:
- `search_threads(query="label:CRE", account=ace, pageSize=…)` — paginated thread list
- `get_thread(thread_id)` — full headers + body for extraction

No browser, no mutation, no `gmail.modify` scope. Gmail-side label changes belong to #2423 and remain out-of-scope here.

### State file (v1 stub, pre-#2026)

Until #2026 lands the full state machine, v1 will persist a minimal JSON state file at `~/.hermes/email-state.json`:

```
{
  "version": 1,
  "seen_threads": {
    "<account_id>::<thread_id>": {
      "extracted_at_utc": "2026-04-24T…",
      "output_path": "assethold/data/cre-listings/2026-04/…yaml",
      "template": "cre-listing",
      "template_version": "1.0"
    }
  }
}
```

The key shape `<account_id>::<thread_id>` matches #2017 v9's composite-key contract so that #2026 can migrate the stub's contents into JSONL without schema translation.

### Legal scan integration

Before any git commit to `assethold/`, `legal_gate.py` will `subprocess.run(["scripts/legal/legal-sanity-scan.sh", "--repo=assethold", "--diff-only"])` and abort commit on non-zero exit. The gate fires once per batch (not per thread), after all `<thread_id>.yaml` files for the run are written but before `git add`. Failures print the scan report and leave the working tree dirty for user triage.

### Output path

`assethold/data/cre-listings/<yyyy-mm>/<thread_id>.yaml`, where `<yyyy-mm>` comes from the thread's `listing_date` (falling back to message `Date` header). One YAML file per thread. Note: `cre-listing.yaml`'s declarative `filename_pattern: "{tenant}_{state}_{listing_date:%Y%m%d}.yaml"` will be overridden by the pipeline to `<thread_id>.yaml` for idempotency (tenant/state can be extracted wrongly; `thread_id` cannot collide). Pattern field retained for future human-facing views.

### Idempotency

On each run, before `get_thread`, the pipeline consults `seen_threads`. Threads whose key is present are skipped (no fetch, no write, no commit). The state file is updated only after a successful write + legal scan + commit. A re-run over the same `label:CRE` cohort produces no filesystem change and no commit.

## Phase C — Task breakdown

1. **Scaffold module tree** — create `scripts/email/extract/{__init__,cli,templates,fields,gmail_reader,writer,legal_gate,state}.py` with docstring-only stubs. Acceptance: `uv run python -c "import scripts.email.extract"` succeeds.
2. **Template loader + schema validator** — `templates.py` loads YAML, validates shape, returns frozen dataclass. Files: `scripts/email/extract/templates.py`. Acceptance: pytest covers valid / missing-required-key / malformed-YAML / unknown-field cases.
3. **Field extraction engine** — `fields.py` applies `source`, `patterns`, `transform`, `default_by_domain` per the template. Files: `scripts/email/extract/fields.py`. Acceptance: three real Sands IG listing bodies (captured as fixtures) produce the expected `property_name`, `price`, `cap_rate`, `state`.
4. **Gmail MCP reader wrapper** — `gmail_reader.py` with `iter_threads_for_label(label, account, page_size)` + `fetch_thread(thread_id)`. Acceptance: unit tests mock MCP client; integration test (manual) against `label:CRE` on ace returns >=1 thread.
5. **YAML writer + path resolver** — `writer.py` writes `<yyyy-mm>/<thread_id>.yaml` under the template's `output.destination`. Acceptance: writer is a pure function of (extracted fields, thread_id, destination); idempotent re-invocation produces byte-identical file.
6. **State file store** — `state.py` with `has_seen(key) / mark_seen(key, record)` over `~/.hermes/email-state.json`. Acceptance: pytest covers first-run-empty, round-trip, composite-key format, schema-version check.
7. **Legal scan gate** — `legal_gate.py` invokes `scripts/legal/legal-sanity-scan.sh`, parses exit code. Acceptance: mock subprocess; exit 0 allows commit, exit 1 raises `LegalScanFailure`.
8. **CLI wiring** — `cli.py` with `--label`, `--account`, `--max`, `--dry-run`, `--state-report` flags. Top-level shim `scripts/email/gmail-extract-and-act.py` delegates. Acceptance: `--dry-run` prints intended writes without touching disk or git.
9. **End-to-end integration path** — read → extract → write → legal-scan → commit → mark-seen. Acceptance: integration test uses 3 fixture threads, produces 3 YAML files, 1 commit, 3 state entries.
10. **Idempotency test** — re-run integration test with unchanged state file. Acceptance: zero new files, zero commits, state unchanged.
11. **Error-path tests** — malformed thread, legal-scan failure, state file write failure. Acceptance: each leaves the working tree in a deterministic, recoverable state (documented in test docstrings).
12. **Documentation update** — add `## v1 consumer: #2024` section under `docs/design/email-as-queue-workflow.md`. Acceptance: section cross-links plan + CLI invocation.

## Risks / open questions

1. **Fixture redaction** — the three Sands IG example threads will contain real broker names, phone numbers, property addresses. The #2017 v8 fixture-redaction pre-commit hook must be in place before any fixture lands; if it isn't yet, this plan blocks on that gate.
2. **`thread_id` stability across Gmail sessions** — Gmail `thread_id` is stable per-account, but if the ace account is ever re-authed, IDs persist (documented). Worth a one-line confirmation test.
3. **`~/.hermes/` directory assumption** — `email-state.json` assumes `~/.hermes/` exists. Pipeline will create it on first run with `mkdir -p`; failure to create (permission, read-only home) is a fatal error with actionable message.
4. **Commit granularity** — one commit per batch vs one per thread. v1 chooses per-batch for atomic legal-scan semantics; if review flags this, revisit.
5. **Legal scan false positives on tenant names** — CRE listings legitimately contain tenant brand names (e.g., "Chipotle", "Dollar General"). Confirm `.legal-deny-list.yaml` for `assethold/` does not list public tenant brands as block-severity.
