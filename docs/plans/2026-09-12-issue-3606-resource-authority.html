Resource descriptor and workflow receipt interface

The resource descriptor will be a versioned observation of an existing owner resource, not a new dataset identity authority. It will refer to stable catalog source IDs and owner-defined dataset IDs. Legacy identifiers will be retained with explicit namespace/crosswalk evidence; unavailable IDs will not be synthesized as established identities.

  • Identity/provenance: schema_version, inherited doc_key where document-based, source_id, dataset_id, owner repository identity, owner-relative manifest locator, source version, derived-from references and source edition where relevant.
  • Evidence: content SHA-256 or explicit unavailable status, digest scope, manifest revision, retrieval/verification timestamps, units per measured field and governing intended use. Unknown, not applicable and zero will have distinct representations.
  • Access/rights: source class, license/rights evidence reference and revision, permitted operation/destination classes, observation time and access status. No credentials, client names or raw private paths will be included in public receipts.
  • Readiness/freshness: readiness_status: unverified | partial | ready | unavailable, freshness basis, source-data vintage separate from refresh time, expiry/recheck condition, governing criterion and limitations. Structural validity alone will never establish ready.

The companion workflow receipt will store resource_descriptor_schema and resource_descriptor_sha256, and resource_stable_sha256, with an authorized evidence locator. The sole production canonicalization/validation authority will be the companion plan's scripts/governance/workflow_receipt.py. This resource slice will define shape and literal conformance vectors, not a second executable canonicalizer. Canonical bytes will use UTF-8, sorted object keys, no insignificant whitespace, unescaped Unicode (ensure_ascii=False), no Unicode normalization and non-finite rejection (allow_nan=False). Hashed projection leaves will be strings or the typed sentinel objects defined below; numeric leaves will be rejected. Derived-source arrays will follow the sorted-set rule below. Volatile timestamps will not silently redefine content identity; observation digests and resource-content digests will remain distinct.

The workflow plan will own the receipt format and the complete reuse key; receipt persistence will remain outside its first slice. The complete key field enumeration will be defined only by the companion workflow plan; this plan will supply its resource interface by reference and will not enumerate workflow-owned key components. Reuse will additionally recheck access, rights, freshness and expiry. Unknown dependencies, changed permissions or incompatible intended use will deny reuse even if a stored hash matches. The resource plan will not duplicate this receipt engine.

Projection values and shared conformance vectors

  • derived_from will be a lexicographically sorted unique array of canonical owner-scoped source/dataset identifier strings or full namespaced document keys. Aliased file paths and nested objects will be rejected; the empty array will mean no recorded derivation, not unknown ancestry.
  • digest_scope will be exactly source-bytes | canonical-json | not-applicable | unknown. A reusable content-bearing resource will require source-bytes or canonical-json and a sha256: plus 64 lowercase-hex content_digest. Scope will specify which artifact is hashed; it will never equate a derived-output hash to source identity. The digest_scope enum literals unknown and not-applicable will remain distinct from typed sentinel objects with state unknown or not_applicable and a required reason. Both scope literals will deny content-bearing reuse; permitted identity/unit not_applicable objects will not supply missing content evidence.
  • units will be an object from field identifiers to exact unit strings. "1" will mean dimensionless; no case folding, unit conversion or alias normalization will occur during hashing. Object keys will sort canonically. Unit values may instead carry the typed sentinels below when evidence is missing or inapplicable.
  • Unavailable scalar evidence will use {"state":"unknown","reason":"nonempty reason"}; genuinely inapplicable identity/unit evidence will use {"state":"not_applicable","reason":"nonempty reason"}. Unknown anywhere in required evidence, unknown lineage, unknown digest scope, or a missing rights/content digest will deny reuse. Not-applicable will be accepted only for non-document/non-dataset identity slots or inapplicable units with an explicit reason, not as a replacement for required content or rights evidence. True zero will remain a numerical value outside the string-valued projection and will never mean unknown. Source/criteria/rights versions will be strings; no timestamp-only access update will change their substantive revision.
  • The schema's x-conformance entries will contain literal validated input/projection objects and literal expected observation/stable SHA-256 constants. Vectors will cover object-key order, sorted/duplicate derivation entries, Unicode, dimensionless units, unknown/not-applicable sentinels, unchanged content with refreshed observations, 64-hex legacy reads, ambiguous 32-hex rejection, missing digests, unknown identity and forbidden content/rights sentinels. This enumeration will be normative for both suites; invalid vectors will carry expected rejection rather than a reusable digest. Resource tests will validate schema and literal vector shape; workflow tests will run the sole production canonicalizer against these same vectors. Test-local duplicate canonicalizers will be prohibited.

A conformance mismatch will halt cross-plan acceptance. Canonical bytes, expected constants and implementation behavior will be compared before attributing the fault. The resource owner will correct a defective constant within its approved isolated six-path transaction and repeat its checks/review; a closed transaction or changed scope will require a bounded corrective plan before edits. Workflow tests will never be relaxed to fit a mismatch, and the workflow transaction will never edit the resource schema outside its manifest. Resource-only structural acceptance will not claim digest agreement.

  5. Hub integration will require its own concrete approval checkpoint. A subsequent consumer plan will enumerate each affected skill/rule and the exact sibling metadata pointer; unresolved identity/semantics will remain blocked before redirect/removal.

A known-path metadata read will not attest raw-content digests, source entitlement or calculation accuracy. Live ingest, private-data retention and publication will remain separately authorized operations.
