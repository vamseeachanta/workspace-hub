Gate destination classification

Implementation will classify each caller by effect: local preparation/commit, CI on an already-published branch, automated push, or report/site publication. Identifier blocking will retire from local preparation, CI, automatic pushes and Pages publishing. Final-report audience and source-rights review will be a manual pre-publication duty; this change will not invent a new receipt gate or disable automatic publication. Independent secret and access controls will remain enforced. CI on a public branch will not be described as preventing the initial push. Mixed secret rules will remain executable. Public-repository destinations and scope-specific rights will be resolved before migration, not inferred from repository names.

Proposed changes

  1. The implementation will inventory tracked live references at each pinned repo revision, distinguish historical documents from active callers, and inspect installed hooks and remote check requirements. Scope will enumerate every affected repo and mark unavailable machines explicitly.
  2. Tests will first reproduce current gate invocation and readiness/prompt requirements in disposable repositories, without actual sensitive identifiers or credentials. Synthetic fixtures will establish expected post-retirement behavior.
  3. The hub will remove automatic scanner invocations, scanner-only CI, readiness requirements and reinstallation advice. Document-index paths will retain ingestion behavior without scanner-result claims or misleading “legal passed” output.
  4. The scanner script will be removed after consumers migrate. Unknown legacy calls will fail visibly as missing commands; the implementation will not replace scanning with a silent exit-zero stub or a fake PASS. A prose retirement entrypoint will explain the replacement report workflow.
  5. Sibling repositories will remove the old scanner hooks/callers and reconcile scanner-specific tests. Mixed secret/traversal/publication logic will retain equivalent independent coverage. Option B will additionally remove identifier-only gates according to the reviewed inventory.
  6. The report-audience rule will define final verification of the exact outgoing artifact bundle. Report-claim discipline and HTML-report verification will consume this rule. Generic chat closeout will report whether an artifact exists and whether verification is complete; it will not manufacture a report-verification PASS.
  7. Canonical instruction sources and generated skill/runtime indexes will be reconciled only where needed; generated outputs will not be hand-edited. Historical reports will remain historical evidence.

Final-report verification contract

Each actual deliverable will identify its audience and destination, the exact report/attachment/embedded-data bundle, revision or digest, reviewed identifier disclosure, source-rights limitations, separate secret-check evidence, reviewer and unresolved findings. Verification will occur before issuing or publishing that bundle. Allowed internal identifiers will not be rejected merely because a repository contains them. A public repository push will remain a publication event; a later report will not be treated as retroactive authorization for restricted data.

The replacement will be a manual, documented review checklist and evidence record, not a newly invented automated legal gate. The report will state verified, needs-review or not-applicable with evidence and reason. Missing output, unknown audience, unreviewed attachments or unresolved release restrictions will prevent the reviewer from claiming “verified.” Changing a reviewed artifact will require a fresh review record. Secret handling, engineering qualification and access permissions will remain separate controls.

TDD and acceptance criteria

  • Synthetic identifier content will flow through the selected retired gates; secret fixtures will still fail retained secret checks.
  • Phase D/E ingestion and cron commit paths will no longer call the retired scanner or report its PASS status.
  • Readiness and prompt producers will no longer require, restore or recommend the old scanner.
  • Raw-to-knowledge import/redaction consumers will continue to operate, with secret/traversal positive controls where currently supported.
  • Manual report-verification examples will cover HTML/PDF and associated CSV/JSON/attachments. Adversarial review will reject example receipts that omit an attachment or bind to an outdated artifact digest. These examples will validate the checklist, not imply automatic publication blocking.
  • A bounded live-reference census will find no executable old-scanner caller within the enumerated migrated scope. Remaining historical references and inaccessible fleet configurations will be listed, not hidden.
  • Generated guidance will match source; existing code/security tests appropriate to each touched path will pass; independent plan and artifact reviews will finish before closeout.

Risks, rollout and rollback

Rollout will proceed in coordinated repository PRs: retained security dependencies first, caller migration second, script retirement last. Migrated consumer revisions will be pinned and verified before removing a shared scanner. If a remote protection rule requires a retired job, its exact check-name migration will be added to the reviewed scope and authorized before changing that protection. The final report will list per-repo commit and deployment status; a local change will not establish fleet-wide retirement. Rollback will revert the coordinated commits without resetting unrelated worktrees. No source data, historical reports, credentials or Git history will be deleted.

Existing duplicate-resolver false-PASS reports (3935, 3871) will be linked as supersession candidates after retirement succeeds. They will not be closed merely because this plan exists.
