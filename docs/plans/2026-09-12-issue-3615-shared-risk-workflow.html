Shared risk workflow: extend existing governance, preserve authority

Decision boundary. This plan will specify a bounded implementation under governance issue 3296, with operational integration routed through epic 3615 and initiative 3606. The user-approved risk model will remain the policy premise: authorized routine reversible work will proceed autonomously; substantial unapproved work and consequential actions will require applicable user approval. Approval of this plan will authorize only the finite first slice below. It will not authorize live hook replacement, global runtime changes, label application, publication, or integration.

Objective and deliverable

Stage A (the first slice) will reuse the existing evaluator, add operation assessment in workflow_decision.py and add receipt comparison in workflow_receipt.py. It will deliver one CLI and one canonical authored skill. Both provider test sessions will receive the explicit skill-file path and load it before calling the CLI; this will establish explicit loading only, not native or implicit discovery of an uninstalled skill. The result will separate risk, reported authorization, metric-based readiness advice, and candidate reusable verification evidence. It will not equate an eligibility score, local receipt, or provider identity with permission to act.

The first slice will close a bounded gap between existing governance code and reproducible task decisions. Later slices will align effective consumers and shared instructions. This staged design will avoid claiming that a new advisory helper fixes every enforcement path.

First-slice contract and dependency boundary

The existing 360-line evaluator will remain shadow-only and backward compatible; edits will be limited to path normalization and protected-policy classification. New operation logic in workflow_decision.py will use an explicit operation kind, exact changed-path set, effect declarations, existing authorization reference, and scope identity. Load-bearing indicators will dominate benign labels. Changes to governance, shared instructions, schemas, approvals, permissions, security/legal rules, public destinations, or engineering basis will never graduate because they happen to be Markdown or configuration. Unknown operation effects or ambiguous scope will return needs-context, not an allow decision.

The CLI will return the closed vocabulary below; unknown outputs will fail validation. Assessments will be advisory and will execute no operation. Routine work with session authorization independently established by the orchestrator will not require historical metric thresholds. This pure first-slice CLI will not authenticate that session: its authorization field will remain unverified-reference or missing, with conditional advice only. No output will assert verified authority, rights or access. The orchestrator will retain the actual session authorization boundary. Substantial unapproved scope or a consequential action without matching approval will return approval-required. Supplied authorization references will identify evidence to verify; self-asserted booleans, marker age, a review verdict, or receipt possession will never authenticate an owner approval.

Normative complete reuse key — workflow ownership only

The named key object will contain exactly repository_id, task_id, operation_id, changed_paths, code_revision, dirty_diff_sha256, resource_stable_sha256s, environment_sha256, criteria_revision, and verification_procedure_version. Identities/revisions will be explicit nonempty strings. changed_paths will be sorted unique normalized owner-relative paths, including both rename endpoints; resource_stable_sha256s will be a sorted unique set, explicitly empty for code-only tasks. SHA-256 will cover canonical JSON of this object, never ambiguous concatenation. Full descriptor observation hashes, timestamps, authorized locators and evidence_artifact_sha256 will remain outside the key. Evidence-artifact hash validation will be a separate mandatory integrity check; moving an identical verified artifact will not force recomputation. The sibling plan will reference this definition rather than enumerate another key.

Closed advisory output vocabulary

  • risk_class: read-only | routine-reversible | substantial | consequential | unknown.
  • authorization_assessment: not-required-for-assessment | unverified-reference | missing. No verified-authority value will exist.
  • action_boundary: assessment-only | conditional-routine | approval-required | needs-context. This field will separate action requirements from evidence provenance; no assessment will execute that action.
  • metric_advice: not-requested | eligible-shadow | ineligible-shadow | unavailable. Historical manual mode will map to ineligible-shadow advice, not revocation of standing task authorization.
  • reuse_assessment: not-requested | invalid | candidate-pending-live-validation | needs-context.
  • reason_codes: sorted unique values from READ_ONLY_ASSESSMENT, ROUTINE_CONDITIONAL, PROTECTED_CHANGE, CONSEQUENTIAL_EFFECT, UNKNOWN_EFFECT, MISSING_CONTEXT, UNVERIFIED_AUTHORITY, APPROVAL_REQUIRED, METRIC_INELIGIBLE, METRIC_UNAVAILABLE, RECEIPT_INVALID, KEY_CHANGED, EVIDENCE_DIGEST_MISMATCH, MUTABLE_VALIDATION_REQUIRED, RESOURCE_UNVERIFIED, SCHEMA_UNAVAILABLE. Empty reasons will be valid only when all optional assessments are not requested.

Protected indicators will dominate routine classification; unknown effects/scope will produce unknown plus needs-context. Consequential effects without matching action authority will produce approval-required; supplied reference provenance will still remain unverified.

One production canonicalizer and sentinel boundary

workflow_receipt.py will solely implement the resource contract's canonicalization and workflow-key serialization. Resource schema x-conformance will carry literal stable_projection/expected resource_stable_sha256 vectors. Resource tests will validate those literals structurally; workflow tests will compute their hashes through this production module. Neither suite will create a second canonicalizer. The resource contract will exclusively define digest_scope, derived_from ordering, units, identity normalization and canonical UTF-8 serialization; workflow will validate against it. Unknown/unverified identity or unavailable content digests will refuse stable reuse. Explicit not_applicable states will be accepted only where the resource schema permits them with a reason, never in place of missing content or rights evidence.

Verification receipts will describe evidence, not grant permission. They will bind repository/task/operation identity, normalized finite path set, source revision and dirty-diff digest, input descriptors, environment digest, governing criteria revision, verification procedure version, and evidence-artifact digest. Resource inputs will reference resource_descriptor_schema and resource_descriptor_sha256, owned exclusively by the linked resource-authority plan. The workflow schema will reference that schema rather than duplicate source rights or catalog ownership. Code-only tasks will explicitly use an empty resource-descriptor set; resource tasks with missing descriptors will be non-reusable.

Resource comparison will consume the resource schema's stable_projection: source_id, dataset_id, doc_key, owner_repo, source_version, content_digest, digest_scope, derived_from, units, intended_use, criteria_revision, and rights_revision. The full resource_descriptor_sha256 will attest the observation; resource_stable_sha256, the canonical stable-projection digest, will enter the reuse key, excluding observation/access-refresh timestamps. An authorized locator will remain an opaque reference, not a private path copied into a public receipt. The workflow will not redefine descriptor fields or readiness vocabulary.

Comparison will use canonical JSON, reject duplicate keys/non-finite values/unknown schema versions, and require independent revalidation of access, source rights, revocation and freshness/expiry separately from static digests. In this pure slice, supplied attestations will remain unverified; structural equality will produce only candidate-pending-live-validation, never verified reuse. Changed criteria will invalidate applicability; changed inputs/code will invalidate affected verification; unchanged unrelated task metadata will not force a rerun. Unknown dependency closure or unverifiable receipt provenance will forbid reuse. A successful comparison will report an evidence candidate only; current action authorization will still be checked independently. This slice will not introduce signatures, claim tamper-proof storage, replace the historical governance ledger, or mint approval receipts.

Dependency order: the resource-authority plan will be the predecessor. Its approved schema and literal conformance vectors will be available before resource integration tests. The workflow worktree will consume the recorded approved isolated resource snapshot, verified by exact path/SHA-256 manifest and base revision; if separately committed, its commit ID will also be recorded. A verified predecessor overlay will not imply canonical integration or authorize a commit. Independently approved classifier/code-only/CLI development may proceed earlier, but its checkpoint will be partial: independent subset verified; resource acceptance pending, not full completion or integration approval. No guessed schema will replace the predecessor. Receipt persistence will remain outside both first slices and will require a future workflow implementation plan. A vector mismatch will halt acceptance and follow the resource-owned correction procedure; no test relaxation or out-of-manifest schema edit will be permitted.

Later stages, risks, rollback and human decisions

Stage B will remain a separate plan: reconcile shared instruction authority and actual Claude/tool/Git consumers; specify every source, generated output, caller and trusted authorization-evidence ingress. It will prove equivalent handling of Write/Edit, shell writes, PowerShell, staging and worktrees before claiming coverage. An advisory receipt will never become a bypass merely by wiring it into a hook.

Stage C will remain a separate approval: verify live repository variables, owner-label protection, branch required checks, and installed hook paths; migrate selected consumers with a tested rollback and retain owner-only label/revision checks. Deployment will not be inferred from source checkout changes. Legacy heuristics and blanket exemptions will remain explicitly open until replaced.

The critical implementation decision will be approval of the ten-path, advisory-only first slice, with no live gate changes. The standing risk model will not be renegotiated. A future enforcement slice will require a concrete decision on trustworthy session/owner authorization transport; this plan will not pretend agent-authored JSON solves that boundary. Numerical graduation thresholds will remain historical advice, not a new prerequisite for routine work.

Implementation will begin in an isolated worktree after approval and parallel-work checks. The nine integrated foundation files and unrelated canonical changes will remain preserved. Rollback will restore only the four modified files from pre-change bytes and remove the six additions only if their hashes still match the transaction; unexpected concurrent changes will stop rollback. No user skill roots, stashes, sibling sources, policy hooks or remote state will be swept into cleanup.

Completion for this slice will require the finite diff, both independent and predecessor-gated tests passing without prerequisite skips, reviewed authority/reuse separation, source hashes, and named expected residue. It will not close all acceptance criteria of either epic. Commit, push, issue comments, live installation, integration, and publication will remain separate authorized actions.
