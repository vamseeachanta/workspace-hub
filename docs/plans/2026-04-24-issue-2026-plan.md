## State machine

Declared states (unchanged from #2017 v9): `{ inbound, extracted, awaiting-reply, completed, purged }`.

Transitions:

```
inbound
  -- filter-mesh match (CRE/AutoNoise/Industry/etc.) --> (no #2026 entry; handled by filter at ingestion)
  -- classified actionable/data_extract/drive_doc/archive --> extracted
extracted
  -- user replies in-thread --> awaiting-reply
  -- resolved, no reply needed --> completed
awaiting-reply
  -- other party replies --> extracted (reactivated, linked to prior extraction)
  -- user marks complete --> completed
completed
  -- 7-day grace elapsed --> purged
  -- new reply arrives during grace --> extracted (reactivated)
purged
  -- new reply arrives --> extracted (reactivated; D3 trash-purge recovery per #2017)
```

Composite key `(account_id, thread_id)` is enforced at every boundary per #2017 v9 D1. Snapshot derivation + atomic rewrite + meta-file freshness check are implemented verbatim from #2017 D1.

## Gmail labels (v1)

Three wh-email/* labels, created once and written via Gmail MCP label-thread tools:

- `wh-email/extracted` — data pulled to target repo; thread carries this label while `state in {extracted, awaiting-reply}`
- `wh-email/awaiting-reply` — optional sub-label applied alongside `extracted` when state transitions to `awaiting-reply`; surfaces as its own Gmail view
- `wh-email/completed` — topic resolved; applied at `→ completed` and removed at `→ purged` (or `→ extracted` on reactivation)

**Out of scope for v1 (in filter mesh already):** `wh-email/noise` and `wh-email/CRE` are NOT created — those cohorts are `label:AutoNoise` / `label:CRE` from the 2026-04-24 filter install and are the filter's responsibility, not the state machine's.

## Local state file

- Primary key: composite `(account_id, thread_id)` per #2017 v9
- **Dedup key (R1, see below):** `(account_id, thread_id, from_state, to_state, triggering_message_id)` — retries dedup, but legitimate repeats across reactivation cycles are preserved as distinct events
- Schema fields (per-entry): `account_id`, `thread_id`, `triggering_message_id`, `from_state`, `to_state`, `ts_utc` (ISO-8601 UTC with `Z`), `writer_identity` (nested: `{process_name, pid, hostname, boot_id}`), `reason?`, `linked_extraction?`, `label_mirror_applied?`

## Grace-period logic

- `completed` threads carry a `completed_at` timestamp
- Daily sweep (cron wired by #2024) scans for `now_utc - completed_at > 7d` → transitions to `purged`
- **Purged action:** local-queue-state marker only; NO Gmail-side archive/delete — that is #2423's contract
- During the 7-day grace window, a new reply on the thread transitions back to `extracted` (state=reactivated), and the `wh-email/completed` label is removed + `wh-email/extracted` re-applied via Gmail MCP
- Grace boundary is a strict `>` inequality (7d+0s stays completed; 7d+1s purges) — matches #2017 v9 exact-second tests

## R1 + R2 fixes (from #2017 v9 approval)

### R1 — Dedup key includes `triggering_message_id`

**Rationale:** #2017 v9 dropped `ts_utc` from the dedup composite to make retries idempotent. That fix over-corrected for legitimate repeats: a thread reactivating twice (`completed → extracted` then later `completed → extracted` again) would see the second reactivation silently deduplicated, since the `(account_id, thread_id, completed, extracted)` tuple already exists. Adding `triggering_message_id` (the Gmail `Message-ID` header of the message that caused the transition) restores distinguishability: retries share a `Message-ID` and dedup; reactivations have distinct `Message-ID`s and write distinct rows.

**Acceptance criterion:** `test_dedup_preserves_reactivation_cycle` passes — same thread reactivated twice (distinct `Message-ID`s) writes two rows; retries with identical `Message-ID` write one.

### R2 — Import via pytest fixture for xfail compatibility

**Rationale:** `tests/email/test_state_machine_contract.py` currently uses `pytest.importorskip('scripts.email.queue_state')` at module level (per #2017 v9). `importorskip` raises `_pytest.outcomes.Skipped`, which short-circuits BEFORE `@pytest.mark.xfail` evaluates — tests end up SKIPPED rather than XFAIL, and `--runxfail` never lists them as failing. Moving the import into a fixture (`@pytest.fixture def queue_state(): import scripts.email.queue_state; return ...`) causes `ImportError` to raise inside the test body, where `@pytest.mark.xfail(raises=ImportError)` catches it and `--runxfail` lists them as XFAIL-converted-to-FAIL per #2017 v9's gate.

**Acceptance criterion:** `test_xfail_runxfail_lists_state_machine_tests_as_failing` passes — `uv run pytest tests/email/test_state_machine_contract.py --runxfail --collect-only -q` lists every state-machine test in the failure set when `queue_state.py` is absent.

## Phase B — Architecture

**Module layout** under `scripts/email/state/`:

```
scripts/email/state/
  __init__.py        # re-exports public API: transition, read_snapshot, sweep_grace
  machine.py         # state transition table + validator
  store.py           # JSONL append + snapshot rewrite (atomic tmpfile+rename; fcntl.LOCK_EX)
  dedup.py           # R1 key: (account_id, thread_id, from_state, to_state, triggering_message_id)
  grace.py           # 7-day sweep; invokes store.append for each purged transition
  label_mirror.py    # Gmail MCP wrapper — reads label list, writes wh-email/* labels
  meta.py            # snapshot-meta freshness check (O(1) via last_log_byte_offset + log_generation)
scripts/email/queue_state.py  # thin top-level module re-exporting state package API
```

**MCP integration:** label_mirror.py will use `mcp__claude_ai_Gmail__list_labels`, `mcp__claude_ai_Gmail__label_thread`, `mcp__claude_ai_Gmail__unlabel_thread` — all within current read+compose scope per `reference_gmail_mcp_scope.md`. The memory's "untested but likely works" hedge on `label_thread` will be verified live in task 5 (see Phase C).

**No browser dependency.** All mutations are MCP calls. #2423's browser automation is orthogonal.

**Idempotency:** state transitions are commutative under re-runs. Re-running `transition(inbound → extracted)` with identical `triggering_message_id` appends zero rows. Re-running with a different `triggering_message_id` appends one row (legitimate repeat).
