Approach A is the proposed simplest path but its behavior under Claude Code must be reproduced before committing to it. ## Deliverable

**Phase 1 — Claude auto-load via `@file` import (Approach A)**: Add `@config/agents/claude/SOUL.runtime.md` as a single line to `CLAUDE.md`. Verify empirically by starting a fresh Claude Code session and grepping for a sentinel string from the SOUL runtime. If verified, commit; the wiring is durable (no per-machine setup) and respects the 20-line harness limit (CLAUDE.md goes from 11 → 12 lines).

**Phase 2 — Gemini auto-load (research-first)**: Research Gemini CLI's bundle spec for an `@import` equivalent. Three branches based on outcome:
- **2a**: Gemini supports `@import` (or equivalent) → mirror Approach A in `GEMINI.md`
- **2b**: Gemini has no import directive but supports a per-project bundle file under a known path → wire there
- **2c**: Gemini bundle spec only accepts inline content → document the limitation explicitly in `GEMINI.md`; SOUL rules remain by-reference-only for Gemini; file follow-on if a workaround surfaces later

**Phase 3 — Drift check extension**: Add an auto-load assertion to `scripts/enforcement/check-soul-runtime-drift.sh`: verify CLAUDE.md and GEMINI.md each contain the chosen reference mechanism (`@config/agents/claude/SOUL.runtime.md` for Claude; Gemini-specific per Phase 2 outcome). Catches manual edits that accidentally break auto-load wiring.

**Phase 4 — Empirical regression test**: Add `tests/enforcement/test_soul_auto_load.py` with a small in-CI verification: a sentinel string in `SHARED_SOUL.md` is propagated through `build-soul-runtime.sh` into the per-provider runtime artifacts AND the wiring mechanism in CLAUDE.md/GEMINI.md points at the correct path. (The test cannot verify the live session loads it — that requires an actual fresh Claude/Gemini session — but it can verify the wiring is in place.)

**Out of scope**: Modifying Claude Code or Gemini CLI runtime behavior. Modifying skill auto-load (skills remain on-demand by design). Cross-machine symlink propagation for Approach C if needed (already covered by `bootstrap-machine.sh §2.5` integration from #2719).

| Gemini CLI has no `@import` equivalent (Phase 2c) | MEDIUM-HIGH — Gemini bundle spec is less well-documented than Claude Code | Document limitation explicitly; SOUL rules remain by-reference for Gemini until upstream support lands; file follow-on issue for re-evaluation |
| Symlink fallback breaks under per-machine bootstrap | LOW — `bootstrap-machine.sh §2.5` already creates symlinks for Hermes/Codex; same pattern extends | Add `.claude/rules/SOUL.runtime.md` symlink creation to bootstrap if Approach C wins |
| 181-line auto-loaded file blows context budget visibly | LOW — global+workspace CLAUDE.md is currently ~15 lines combined; adding 181 lines is ~8% of typical 2KB budget allocation | Acceptable per CONTROL_PLANE_CONTRACT.md scope; if pressure arises later, split SHARED_SOUL into "always-on" subset + "on-demand" rest |
| Drift check grows brittle as auto-load mechanism evolves | LOW — single-mechanism assertion is easy to maintain | Use a literal-string grep, not regex; comment the script with the rationale linking back to #2725 |
| Concurrent Hermes session edits during impl (per `feedback_hermes_active_preflight_check`) | MEDIUM — Hermes runs on this machine continuously | Use pathspec commits (per `feedback_multi_agent_commit_serialization`); preflight `pgrep` before commit |
