## Resource Intelligence Summary

This is the fourth automation-pipeline child of self-improvement epic #3248. It supplies the
**dormant-by-design adaptation machinery for gap #6** ("hard-coded confidence threshold — never
adapts to whether promoted learnings actually survive") and **closes gap #8** ("no distinction
between Gemini-specific skill needs and shared cross-provider patterns").

**Honest scoping (round-2 major #3 — read before grading deliverable claims).** gap #6 is **NOT
closed by this plan**; it remains **OPEN** until a *human-provenance* writer populates a `reviewed_by`
marker on terminal ledger entries — and neither this plan nor sibling #3252 owns that writer (verified
live: `correction-promotions.yaml` has 5 entries, all `status: identified`, zero `reviewed_by`; the
field does not exist in the schema). This plan ships the **read-only** adaptation loop in a fail-safe
**dormant** state (human-terminal count == 0 ⇒ permanent hold at 80) so gap #6 becomes *closeable* the
moment such a writer lands, without ever building an unsafe auto-promote→auto-lower loop (Hard Rule 1).
The `#3252` "MUST NOT write `reviewed_by`" contract below is **advisory and unenforceable** from this
plan. gap #8's classifier, by contrast, is **fully functional today**.

Unlike its siblings #3250/#3251/#3255 — which each minted a new machines×dimensions *matrix cell* —
both halves of #3256 are **repo-global control loops** whose output is machine-invariant *and is made
fleet-visible only by an explicit git-commit path this plan now plumbs*. The decision below justifies
that they hook into the existing **nightly learning orchestrator + post-commit consumer + candidate
machinery**, and add **no matrix dimension** (Hard Rule 6).

## Decision: pipeline control loop, NOT a new matrix dimension

**Recommend: hook both halves into the existing learning pipeline (nightly producer + post-commit /
candidate consumers). Add NO matrix dimension, NO collect-equality emit, NO curate-wrapper wiring, NO
reconcile verdict.** Justification (directly addresses Hard Rule 6):

1. **The outputs are machine-invariant *and now genuinely git-distributed*.** The adapted threshold
   derives deterministically from the **git-tracked** `correction-promotions.yaml`; the scope
   classification derives from the **committed** skill tree (`git ls-tree HEAD`, the same basis
   `audit_skill_currency` already uses). Every box that runs the producer computes the *same* number /
   *same* tag, and (with the `.gitignore` + `commit-learning-artifacts.sh` edits in Step 7) the JSON
   is committed nightly and pulled fleet-wide — so the matrix would have no cross-machine divergence to
   grade; a cell would be permanently EQUAL/green, i.e. pure noise. The three siblings each graded a
   genuinely per-machine quantity (per-box curation freshness, per-box memory mtime, per-box link
   health); #3256 has no per-machine quantity.
2. **The cadences already exist.** Threshold adaptation belongs to the **daily** learning cadence
   (`comprehensive-learning-nightly.sh`), not the 6-hourly curation cron; the consumer
   (`extract-learnings.sh`) is **per-commit**. Forcing this into the curation→collect→matrix substrate
   would invert the natural cadence and add a permanently-green cell.
3. **Rule-2 trigger is not met.** Rule 2 fires "if the design adds any session/curation audit." This
   design adds none — so the `.sh`/`.ps1` curation wrappers, `collect-equality.*`, and
   `reconcile-ecosystem.sh` OK-skip list are intentionally **untouched**. (Confirmed against
   `build-equality-matrix.py:461` and `reconcile-ecosystem.sh:204`.)

**Rejected alternatives:**
- *New `correction_threshold` matrix dimension.* Rejected: machine-invariant → permanently green →
  would trip the ~11-touchpoint dimension cost (Rule 3) for zero divergence signal, and would force a
  collect-equality emit + curate-wrapper wiring + reconcile OK-skip entry for a non-equality concern.
- *Adapting the GLOBAL `AUTO_ISSUE_THRESHOLD` (all five signal types).* **Rejected (round-1 major #2 —
  population mismatch):** the survival signal is sourced from `correction-promotions.yaml`, the
  corrections ledger, but the global bar also gates `tdd_gap`/`skill_update`/`config_drift`/`repeated`
  signals that have nothing to do with corrections. Steering the whole bar from the corrections
  sub-population steers the wrong knob. **Adopted instead: scope the adaptive bar to the
  `session_corrections` signal type only**, so the survival *source* (corrections→skill promotions in
  the ledger) and the control *target* (corrections-derived auto-issues) are **both
  corrections-derived** — a far tighter coupling than steering the global bar from a corrections
  sub-population. **Proxy caveat (round-2 minor #4):** these two are *not* the identical population —
  `correction-promotions.yaml` records correction→skill PROMOTION survival, while the
  `session_corrections` signal is a raw count of `"correction"` lines in the session log
  (`extract-learnings.sh:168-171`). Promotion-survival is therefore a documented **proxy** for the
  quality of corrections auto-issues, not a direct measurement (risk flagged below, consistent with
  the round-1 causal-link framing). The other four types keep the static `AUTO_ISSUE_THRESHOLD=70`
  (line `:21` untouched). This is also *more* faithful to gap #6's "correction-confidence threshold"
  framing than a global knob.
- *Mutating the threshold inside `extract-learnings.sh` itself (read ledger inline each commit).*
  Rejected: couples per-commit consumption to ledger parsing on every commit (slow; the hook must be
  <5 s), and re-derives the policy on every box from possibly-divergent local ledgers. A single nightly
  producer writing a state file the consumer simply reads is cleaner and machine-invariant.
- *Adapter decides "survived review" itself (e.g., closes/labels issues as accepted).* **Rejected on
  Hard Rule 1** — survive-review is the owner's gate. The adapter only *reads* terminal statuses that
  carry a human-provenance marker; it never writes them and never applies any `status:*` label.

## Deliverable

**(a)** `scripts/learnings/adapt-correction-threshold.py` — a pure `adapt_threshold(...)` core (no IO)
plus a thin CLI that reads the `correction-promotions.yaml` ledger, counts ONLY entries that carry
BOTH a terminal `status:` (SURVIVED vs REJECTED vocab) AND a non-empty human-provenance marker
(`reviewed_by`), reads the current scoped threshold, computes a **bounded** new threshold in the real
`session_corrections` bucket band `[80, 90]`, and writes
`.claude/state/correction-confidence-threshold.json` with full provenance.
`extract-learnings.sh` reads `.threshold` from that JSON and applies it **only to
`session_corrections`-typed signals**, precedence **explicit env override → adaptive JSON → 80**
(behavior-identical to the old global-70 outcome for that population), fail-soft. The JSON is
un-ignored and added to the nightly commit allowlist so it propagates fleet-wide.

**Scope honesty (round-2 major #3).** Because no ledger entry carries `reviewed_by` today and **this
plan adds no writer for it**, the human-terminal count is `0` and the loop is **dormant by design** —
it holds at 80 and never moves the bar until a human-provenance writer lands. This deliverable ships
the *machinery* for gap #6, **not** gap-#6 closure; the acceptance criteria assert the dormant hold,
not adaptation. gap #6 remains OPEN in epic #3248 until a human-review entry point that stamps
`reviewed_by` is defined and shipped (out of this plan's scope; see Risks → Rule 1).

**(b)** `scripts/curation/classify_skill_scope.py` — a pure `classify_scope(family, …)` core that
**reuses** `audit_skill_currency._families`, `_load_allow`, and a refactored module-level `_allowed`,
classifying each candidate skill family as `gemini-specific` / `shared` / `gemini-drift` and writing
`.claude/state/skill-scope-classification.json` (also un-ignored + allowlisted) as its **single,
durable output**. **It does NOT edit `skill-candidates.md`** (round-2 major #2): that file is
cron-regenerated, append-structured, and "do not edit manually" with two existing append-owners
(`session-analysis.sh:213`, `comprehensive_learning_pipeline.py:481`); a second in-place writer would
race them and be clobbered on the morning regeneration. The classification JSON is the source of truth;
if a future enhancement wants the scope tag rendered into the candidate md, it must invert ownership —
have `session-analysis.sh` / `comprehensive_learning_pipeline.py` **READ** this JSON at generation
time — which is explicitly out of scope here. Wired best-effort into the nightly after the
skill-currency audit.

Both CLIs **always exit 0** (signal via JSON, never exit code — Rule 4); neither pushes to a state-ref
(Rule 5); neither writes a `status:*` label or decides review survival (Rule 1).

## Risks & Hard-Rule Compliance

**Rule 1 — never self-apply `status:plan-approved` / `status:completeness-verified`; review gate is
HUMAN.** The "corrections-promotion survived review" signal is counted ONLY from entries that carry a
terminal status **AND** a non-empty human-provenance marker (`reviewed_by`); `status` alone — which a
machine such as sibling #3252 could write — is insufficient (`_is_human_terminal`,
`test_cli_ignores_machine_written_status`). The adapter never writes those statuses, never closes/labels
issues, never applies any `status:*` label, and never decides survival itself
(`test_cli_never_writes_status_label`). The plan's own owner-approval gate (Implementation Step 9)
remains a human step; this plan does not self-advance it.
**Honest-scoping caveat (round-2 major #3 — deliverable, not a Rule-1 violation):** the `reviewed_by`
field **does not exist in the ledger schema today, and this plan introduces no writer for it.** The
`#3252` "MUST NOT write `reviewed_by`" contract is therefore **ADVISORY and unenforceable** from within
this plan — this plan cannot prevent another process from writing the field, and cannot guarantee a
human writes it. The consequence is scoped honestly: the adaptation loop **ships DORMANT**
(`terminal == 0 ⇒ permanent hold @80`, `dormant:true` in the JSON, `test_cli_dormant_on_real_ledger`),
and **gap #6 remains OPEN** in epic #3248 until a human-review entry point that stamps `reviewed_by` is
defined and lands (recommend a follow-on child of #3248 to own that writer + entry point). Shipping
inert machinery is the correct fail-SAFE posture for Rule 1; it never moves the bar without human
provenance, and an auto-promote→auto-lower-threshold→more-auto-issues loop is structurally impossible.

**Rule 2 — wire any session/curation audit into BOTH `.sh` and `.ps1`; reuse the audit→state→collect→
verdict substrate.** This design adds **no** session/curation audit and **no** matrix cell, so the
`curate-session-memory.sh`/`.ps1` wrappers, `collect-equality.*`, and the verdict engine are
deliberately untouched. The producers run in the **dev-primary nightly** (a centralized Linux cadence
that already aggregates fleet learning); the threshold consumer is the cross-platform per-commit hook
reading a **now-git-distributed** JSON (un-ignored + added to `commit-learning-artifacts.sh`), so
Windows boxes get the adapted value via `git pull` with no `.ps1` audit needed. `classify_skill_scope.py`
lives in `scripts/curation/` but is **repo-global**, does not call `audit_skill_currency.audit(machine)`,
does not use `machine_label()`, and does not feed the equality matrix — so the Rule-2 BOTH-wrapper /
machine_label trigger is genuinely unmet. Where reuse IS applicable it is honored: the classifier
imports `audit_skill_currency._families/_load_allow/_allowed` rather than reimplementing the family diff.

**Rule 3 — a new matrix dimension touches ~11 places; new OK verdicts must enter the reconcile
OK-skip.** No dimension and no verdict string are added (Decision section), so none of the ~11
touchpoints (`build-equality-matrix.py` `BASE_DISPLAY_DIMS:461` / `GROUPS:475` /
`ROLLUP_SEVERITY:491` / `OK_VERDICTS:516` / `remediate:521` / CSS / legend + `collect-equality.sh`
emit + `reconcile-ecosystem.sh:204` OK-skip + SKILL.md fix-table + tests) are modified, and no spurious
reconcile action can fire. Verified by reading both files.

**Rule 4 — do not overload exit codes (Windows cron runs under `$ErrorActionPreference='Stop'`).**
Both new CLIs **always exit 0** (`test_cli_*_exit_zero`, including on malformed input); they signal
exclusively via their state JSONs. `extract-learnings.sh` keeps its existing exit semantics — the
consumer edit is a fail-soft value read (`… || echo 80` inside a `${x:-…}` default) under
`set -euo pipefail`, never a new exit path, **and crucially does NOT `source` python-resolver.sh**
(whose `exit 1` would have introduced a new abort path on python-broken boxes — round-2 major #1).
`test_cli_dormant_on_real_ledger` + the no-working-python shell row prove the post-commit hook cannot
die. The nightly wiring uses the established `… || echo "WARNING …"` best-effort idiom (matching the
existing pattern at `comprehensive-learning-nightly.sh:155-158/160-163`) so a failure of either step
cannot abort the orchestrator.

**Rule 5 — cross-machine state-ref pushes HANG (operator issue); bound them.** This design performs
**no state-ref push at all.** The threshold/classification derive deterministically from the
git-tracked ledger + committed skill tree, so they are machine-invariant by construction; fleet
distribution is the **ordinary nightly `git commit` + pull** path (Step 7b/7c — `.gitignore` exception

state-ref. There is therefore nothing to transport over the hanging push and no timeout is needed. (If
a future variant ever publishes to a state-ref, it must adopt the `publish_fingerprint` 90 s

**Rule 6 — first assess whether a new matrix dimension is warranted.** Assessed and **rejected** with

**Additional risks**
- *Proxy-signal assumption (round-2 minor #4).* The survival source (ledger correction→skill PROMOTION
  outcomes) and the control target (`session_corrections` auto-issues, raw `"correction"`-line count at
  `extract-learnings.sh:168-171`) are **both corrections-derived but not identical** — promotion
  survival is a *proxy* for auto-issue quality, not a direct measurement. If the two diverge
  materially, the adapted bar may track the wrong quantity. Mitigated structurally: the loop only ever
  moves ±10 within `[80,90]`, ships dormant until human provenance exists, and is owner-review-gated
  before activation. Flagged for owner judgement.
- *Direction of adaptation is a policy choice.* "High survival → admit single-occurrence
  session_corrections (+recall, lower→80); low survival → demand count>10 corroboration (+precision,
  raise→90)." Because the `session_corrections` lattice is exactly `{80, 90}` the lever is effectively
  a 2-state precision control, which is why band `[80, 90]` / `STEP=10` is intentionally coarse and
  maps onto the real buckets (round-1 minor #5). The policy lives in named constants
  (`TARGET_HIGH/LOW`, `STEP`, `FLOOR/CEIL`) tunable in one place and is the first thing flagged for
  owner review.
- *Sparse / biased ledger + dormancy.* Today all entries are `status:identified` with no `reviewed_by`
  (0 human-terminal) → fail-safe dormant hold at 80 (`test_cli_dormant_on_real_ledger`).
  `MIN_SAMPLE=8` additionally prevents a 2-of-2 fluke from swinging the bar once a writer exists. The
  adapter depends only on the READ contract (terminal `status` + human `reviewed_by`); it is robust
  whether or not sibling #3252 ever ships its status writer, and gap #6 stays OPEN until a
  human-provenance writer lands (honest scoping).
- *Issue text path drift.* The issue says Gemini lives under `.gemini/`; the real skill surface is
  `.agents/skills` (`audit_skill_currency.py:44`). The classifier binds to `.agents/skills` to match
  the audit; `.gemini/` (GSD/agent config) is out of scope.
- *Consumer-on-fresh-box.* A box that has never pulled the committed JSON falls back to 80 for
