Plan: preserve licensed-run ownership until cleanup is proven

Issue: Deckhand 591 · Status: adversarial-reviewed; user approval pending · Revision 3 · Complexity: T2 · Client: N/A · Lane: lane:claude · Date: 2026-09-11 UTC

Execution mode will be parallel-readonly for planning/review, followed by one isolated implementation worktree with parallel test/review ownership after user approval. This plan will authorize no production task change, queue repair or solver request.

Outcome and scope

The licensed agent will release its execution guard only after a structured, validated cleanup outcome proves no owned execution remains. Unknown cleanup will leave the guard occupied across retries and agent restarts and will force a failed result even when the direct child exits zero. The first production-capable containment backend will cover Windows through a Job Object; non-Windows default licensed execution will fail before spawning until an equally strong backend is qualified. Existing watchdog process-group helpers will retain their signatures and existing behavior; watchdog repair 592 will own its separate cleanup/restart gap. This plan will qualify trusted uv/Python descendants created through normal CreateProcess inheritance only. Brokered WMI/service launches, external functions and arbitrary executable hooks will remain excluded from approved workloads; Job Objects will not be represented as a sandbox for arbitrary code.

This bounded change will repair the default licensed runner, its lock/result integration, deadline validation and tests. It will not add automatic stale-lock recovery, POSIX containment, queue repair, host migration, batch dispatch, standing approvals or a new scheduler. Injected runners will require the same explicit cleanup contract; their legacy call signature will remain, but missing proof will no longer imply safe release.

Proposed lifecycle and concrete design

  1. Guard before execution. The existing exclusive-create lock path will remain the serialization primitive. Acquisition will write a versioned owner record with an unpredictable ownership token and available host/process/start identity, then flush/fsync before invoking any runner. The held file identity and token will be checked before deletion. Existing, malformed, partial and legacy PID locks will remain busy; neither age nor PID absence alone will remove them. Acquisition/write failure will launch nothing and preserve uncertainty.
  2. Default to retained ownership. The lock context will start in a retained state. Only a validated outcome cleanup_state=confirmed or not_started from the trusted runtime will permit explicit release. Exceptions, missing/invalid result contracts and nonlocal return paths will retain it. Quarantine metadata will be written through the held guard where possible; persistence failure will still leave the original guard, and will never trigger unlink. Replacement/identity mismatch will preserve the path and force failure. The threat boundary will be cooperating managed writers in a private protected directory; malicious same-account replacement and manual deletion will remain outside the guarantee.
  3. Contain before resume on Windows. A dedicated runtime module will target Windows 10/11 or Server 2016+ and create a non-inheritable Job Object configured through JobObjectExtendedLimitInformation with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE set and JOB_OBJECT_LIMIT_BREAKAWAY_OK / JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK unset, create the child suspended and hidden, assign it to the job, and resume only after assignment succeeds. A child that cannot be assigned will never run. The adapter will retain process/job handles through verification. Every partial-construction branch will either prove no process started/remains or return unknown and retain the guard. Native API errors will be checked; tests will exercise CREATE_BREAKAWAY_FROM_JOB attempts and assignment failure under an incompatible parent job. It will use existing Python/Win32 facilities without installing a service or dependency.
  4. Observe the whole job. On normal parent completion, the adapter will require a signaled direct-child handle and successful job accounting with zero active processes. Surviving descendants will be terminated under the cleanup budget and will force a failed job result even if parent exit was zero. Timeout, cancellation and unexpected exceptions will attempt job termination and bounded direct-child reap/job-empty observation. Successful termination API return alone, pipe EOF, a PID scan or close-handle success will never count as absence proof. All empty-job observations will occur while the job handle is valid, before closure. ERROR_INVALID_HANDLE will always mean unknown, never confirmed-empty. Handles will close in nested finally blocks; unknown final observation will retain quarantine.
  5. Bound execution and cleanup separately. Configuration will reject boolean, zero, negative, NaN and infinite deadlines before spawn. The existing finite execution deadline will be preserved; cleanup will use one monotonic 30-second budget shared by termination, observation and output finalization, not 30 seconds per operation. Execution and cleanup elapsed-time decisions will use time.monotonic; duration validation will use an explicit boolean rejection and math.isfinite. Private file-backed stdout/stderr will avoid pipe-holder hangs; each returned diagnostic tail will be capped at 4096 characters, and raw paths will not be published. OS process creation/scheduling and durable storage calls will be explicitly excluded from a hard real-time claim; isolated native tests will use an outer watchdog. Exhausting the cleanup budget will intentionally block the lane indefinitely until owner-reviewed recovery; retry will not regain execution by waiting out a timer. Queue result serialization will occur after cleanup/guard disposition and outside that cleanup budget. If result writing fails after proven absence and release, it will remain an error with no success claim; it will not fabricate a new guard or claim a durable result. Unknown cleanup will retain the original guard even if serialization fails. Tests will cover both result-write failures.
  6. Result semantics. Runner dictionaries will retain returncode/stdout/stderr/timed_out compatibility and add versioned cleanup state, containment kind and sanitized reason. Confirmed ordinary completion will preserve its exit code; confirmed timeout will retain 124; failed spawn proven not_started will retain 127; uncertainty will force a nonzero failure and retained quarantine. Unexpected descendants followed by confirmed cleanup will force workload failure while permitting safe guard release. _execute_with_lock will validate the contract before release. Serialization will explicitly add summary.cleanup in _summary_payload; no existing nested runner payload will be assumed. Its version-1 fields will be schema, state (confirmed/not_started/unknown), containment (windows_job/none/trusted_adapter), parent_reaped (boolean), active_processes (nonnegative integer or null), and reason_code (bounded allowlisted token). Windows confirmed will require parent_reaped=true and active_processes=0; not_started will require evidence that no process was created, containment=none and parent_reaped=false; uncertain or contradictory values will normalize to unknown. A separate agent-authored summary.guard_state (released/retained) will reflect actual release outcome, never adapter authority. Trusted adapters will affirm equivalent absence and be identifiable as adapters. The same validator will run before guard release and serialization. Schema-1 legacy queue reads will remain supported but absence of cleanup proof will never qualify new execution acceptance. Round-trip tests through actual write_result/read_result will prove retained and released outcomes survive serialization. Producer success will require the final nonzero/zero decision, not an unvalidated supplied returncode.
  7. Unsupported and injected paths. Backend selection will be frozen once before any spawn; a post-spawn failure will never be reclassified as not_started. Non-Windows default licensed execution will return an explicit unsupported-containment failure before spawn and safely release a not_started guard. Test/custom injected runners will keep their input/cwd call signature but must supply a valid cleanup contract. They will be trusted in-process adapters, never authority granted by queued input. Missing proof will fail and retain ownership; affected tests will supply intentional fake proofs. The watchdog helper functions will stay separate from this new backend; watchdog restarts will not clear the retained disk guard.
  8. Recovery boundary. A retained guard will block later execution until a separate owner-reviewed recovery procedure establishes writer quiescence, process ownership/absence and preserved diagnostics. This repair will provide inspection documentation, not an automatic unlock command. No code path will silently downgrade to taskkill/process-group proof or clear a legacy lock.

Risks and compatibility boundaries

Native API structure/layout or nested-job restrictions will fail before resume or retain quarantine, never trigger an uncontained fallback. New non-Windows execution refusal and injected-runner proof requirements will be intentional breaking behavior requiring owner approval. Protected file-backed output will require sufficient private disk capacity, bounded returned tails and an explicit retention disposition; it will not imply a hard storage quota. Agent crash/restart persistence will be qualified separately from power-loss/filesystem corruption durability. Guard write/delete failures will cause conservative unavailability and manual recovery, not silent release. Watchdog overlap will remain separately tracked in 592; candidate deployment will reconcile that owner before claiming one managed lane.
