Runtime clock-domain audit and replay

The inspected paths use monotonic clocks for local deadlines and wall clocks for persisted freshness. The audit identifies evidence gaps; it does not establish that all collectors are free of mixed-clock comparisons. An offline replay now requires explicit clock origins, domains, resolutions and acceptance limits before comparing values. A replay PASS establishes only agreement with the supplied replay criteria; it provides no admission, capacity qualification or reservation.

Replay contract

Input is one JSON object with criteria, now and a nonempty samples array. Each sample has start, end, interval and observed_at. Each reading has integer value_ns, domain wall or monotonic, a nonempty clock_id, and positive integer resolution_ns. The interval is a duration tagged with its originating clock, rather than an absolute reading.

The equations are duration = end - start and age = now - latest observed_at. Source: Python 3.13 time documentation, monotonic_ns(), time_ns() and get_clock_info(). The monotonic reference is undefined: only differences within a common reference are meaningful. Clock IDs shall distinguish origin/reset boundaries; the label alone cannot authenticate provenance. Integer nanoseconds avoid floating-point serialization loss. The replay accepts nonnegative integer readings and explicit positive integer resolution metadata. Resolution does not imply that ticks are divisible by that value: Python does not guarantee alignment to the clock epoch. The integer-resolution schema cannot represent fractional-nanosecond resolution; such evidence requires a future schema rather than rounding. Matching resolution does not establish measurement accuracy or an uncertainty margin around limits.

Criteria min_duration_ns, max_duration_ns and max_age_ns are required nonnegative integer inputs. No operational constant or tolerance is supplied. Duration limits and latest-observation freshness are inclusive. Every observation shall be no later than now; observation order shall not move backward. Earlier samples may be older than the freshness limit: freshness applies to the latest sample only. Duration windows may have gaps but shall not overlap. Thus this replay does not certify gapless capacity coverage.

Endpoint and interval clock domain, origin and resolution shall match across all samples. Freshness uses wall readings with a common origin and resolution. There is no wall-to-monotonic subtraction. Mixed origins or resolutions return NOT_EVALUATED; no implicit conversion or tolerance repairs them. A future extension will require a separately reviewed conversion and uncertainty bound before allowing such comparisons. Comparable readings violating criteria return FAIL. Missing/invalid evidence returns NOT_EVALUATED. A gap may mask additional violations; neither result qualifies admission. Supplied limits are replay criteria, not approved operational criteria. Sampling simultaneity and source authenticity cannot be established by this schema alone.

The result retains a deep copy of the parsed input as evidence; it neither edits source files nor clamps, rounds or repairs observations. JSON whitespace is not retained; original raw evidence shall be retained separately by its authoritative collector. Duplicate keys and non-finite JSON constants are rejected before replay. CLI exit codes are zero for PASS, one for evaluated or unevaluated non-pass, and two for malformed JSON.

Worked example

All following numbers are synthetic illustrative inputs. Independent hand calculation: first duration = 110 − 100 = 10 ns; second duration = 120 − 110 = 10 ns; latest age = 220 − 210 = 10 ns. Both durations equal the inclusive bounds [10, 10] ns; age equals the supplied maximum of 10 ns. The second start equals the first end. The result is PASS. Increasing now to 221 gives age 11 ns and FAIL. Changing only the interval clock resolution to 2 ns gives NOT_EVALUATED, even when ticks appear numerically comparable.

python scripts/monitoring/clock_replay.py < evidence.json
{
  "criteria": {"min_duration_ns": 10, "max_duration_ns": 10, "max_age_ns": 10},
  "now": {"value_ns": 220, "domain": "wall", "clock_id": "synthetic-epoch", "resolution_ns": 1},
  "samples": [{
    "start": {"value_ns": 100, "domain": "monotonic", "clock_id": "synthetic-origin", "resolution_ns": 1},
    "end": {"value_ns": 110, "domain": "monotonic", "clock_id": "synthetic-origin", "resolution_ns": 1},
    "interval": {"value_ns": 10, "domain": "monotonic", "clock_id": "synthetic-origin", "resolution_ns": 1},
    "observed_at": {"value_ns": 210, "domain": "wall", "clock_id": "synthetic-epoch", "resolution_ns": 1}
  }]
}

The one-sample JSON example returns durations_ns [10], age_ns 10, replay_status PASS, an empty reasons array and the parsed input under evidence. The test fixture extends it to two adjacent samples, with the same independently calculated result.
