# Generated-file conflict regeneration during repo sync

Use this when a sync/merge conflict lands in a deterministic generated artifact rather than a hand-authored source file.

## Pattern

1. Confirm the file is generated from a known script or source-of-truth input.
   - Look for nearby generator scripts, file comments, documented maintenance commands, or repo docs.
   - Do not assume a file is generated solely because it is YAML/JSON or large.
2. Preserve situational evidence before changing it:
   - `git status --short`
   - conflicted file path
   - generator command and exit code
3. Prefer regeneration over manual conflict editing:
   - run the documented generator from repo root
   - validate the resulting file with a parser appropriate to the format
4. Stage and commit the regenerated artifact with any related local changes only after re-checking status.
5. Re-fetch and compare `HEAD` against upstream before pushing or declaring push unnecessary.

## Example from workspace-hub

`config/ai_agents/ai-tools-status.yaml` is generated by:

```bash
bash scripts/maintenance/ai-tools-status.sh
```

After regeneration, validate it before staging:

```bash
python - <<'PY'
import pathlib, yaml
path = pathlib.Path('config/ai_agents/ai-tools-status.yaml')
yaml.safe_load(path.read_text())
print('yaml ok')
PY
```

## Guardrails

- This is not permission to auto-resolve arbitrary conflicts.
- If the generator is missing, fails, or produces unexpected broad changes, stop and report the conflict.
- Do not hand-pick one side of a conflict in generated artifacts unless the generator is unavailable and the user explicitly approves that approach.
- If skill/content scanners flag wording in nearby skill files, fix the wording narrowly and rerun the scanner on the exact changed files before committing.
