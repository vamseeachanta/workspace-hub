# Agent/runtime folder authority map

Use this reference when work touches provider identity/config folders, agent runtime files, local home-directory symlinks, memory bridges, or skill roots. The durable lesson is that these paths are confusing for both humans and agents unless every surface is classified by authority before editing.

## Trigger phrases

- "agent folders are confusing"
- "where should SOUL / AGENTS / GEMINI live?"
- "canonical vs runtime"
- "local config vs repo-tracked config"
- "provider setup across machines"
- "memory bridge / runtime symlink / skill external_dirs"

## Authority classes

| Class | Meaning | Agent behavior |
|---|---|---|
| Canonical source | Repo-tracked source humans should edit directly. Example families: `config/agents/SHARED_SOUL.md`, provider source/delta files, canonical `.claude/skills/` content. | Edit only through normal repo workflow; commit/push with verification. |
| Generated runtime | Materialized output produced by scripts from canonical source. Example families: `SOUL.runtime.md`, `AGENTS.runtime.md`. | Do not hand-edit; patch generator or canonical source, then regenerate and verify. |
| Local runtime/symlink | User-home paths consumed by a specific runtime, often symlinked into repo artifacts. Example families: `~/.hermes/SOUL.md`, `~/.codex/AGENTS.md`. | Inspect/verify target and install shape; do not treat local path as canonical source. |
| Bridge output | Synchronized content between tools, often delimited or script-managed. Example families: memory bridge blocks in `.claude/memory/`. | Patch bridge source or bridge script unless explicitly maintaining the bridge output contract. |
| Cache/snapshot/state | Ephemeral or historical runtime state. Example families: memory snapshots, provider cache/state files. | Do not use as source-of-truth; classify before referencing or committing. |

## Required workflow before file changes

1. Inventory the touched folder families and symlink targets.
2. Classify each path as canonical source, generated runtime, local runtime/symlink, bridge output, or cache/snapshot/state.
3. State which files may be edited directly and which must be regenerated by script.
4. If the user is asking about confusion/legibility rather than an immediate implementation, create a planning issue first; do not move or rename folders in the same step.
5. Use a temp body file plus `gh issue create --body-file ...` for structured architecture/UX issues, then verify with `gh issue view --json number,title,url,labels,body`.

## Issue-body shape for recurring folder-confusion reports

Include:

- Summary: explicitly say the layout is confusing for humans and agents.
- Why it matters: wrong edits, source/runtime drift, local-vs-repo ambiguity, cross-machine onboarding friction.
- Current evidence: observed folder families and conceptual overlaps.
- Desired outcome: authority map, naming convention, symlink/install shape, onboarding rule.
- Acceptance criteria: canonical doc, per-provider/per-machine table, generated-vs-source distinction, no moves until reviewed/approved.

## Pitfalls

- Do not soften the user-facing answer when the evidence shows confusion. Say "yes" and convert the confusion into a concrete architecture/UX issue.
- Do not create root-level documentation drafts for this; use `/tmp` for issue bodies or canonical `docs/` paths only when a plan explicitly calls for repo artifacts.
- Do not collapse provider-specific files into one folder naming scheme without a plan and adversarial review; this can break runtime lookup paths.
- Do not hand-edit generated runtime artifacts to "quickly fix" a local symptom.
