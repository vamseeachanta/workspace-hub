# Hermes gateway systemd unit — annotated template + drop-in override variations

Reference material for the `telegram-hermes-bot` skill, §3.4. The goal is a durable systemd-managed deployment whose env loading survives `hermes update`.

## Why a drop-in override (not direct unit edit)

`hermes gateway install --system` (and the older `hermes-cli` equivalents) regenerate `/etc/systemd/system/hermes-gateway.service` from a template every time. Memory `project_hermes_installation.md` records this as the **shebang-revert recurring failure mode** (3 occurrences in the v0.4.0 era). Any direct edit to the base unit is reverted on the next install.

systemd drop-in overrides live in `/etc/systemd/system/<unit>.service.d/*.conf` and are **merged on top** of the base unit at every load. The Hermes installer does not touch this directory. This is the canonical Linux pattern for "add a setting that survives upstream regeneration."

The `[Service]` section in a drop-in is **additive** for most directives (e.g., `Environment=`, `EnvironmentFile=`) but **replacing** for some (`ExecStart=` requires the empty-string reset trick: `ExecStart=` followed by the new value). Our use case is purely additive — we're adding `EnvironmentFile=` and adjusting `TimeoutStopSec=`.

## Canonical Hermes base unit (as of 2026-05-13, `ace-linux-1`)

Captured for reference. Do NOT edit this file directly.

```ini
[Unit]
Description=Hermes Agent Gateway - Messaging Platform Integration
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=600
StartLimitBurst=5

[Service]
Type=simple
User=vamsee
Group=vamsee
ExecStart=/home/vamsee/.hermes/hermes-agent/.venv/bin/python -m hermes_cli.main gateway run --replace
WorkingDirectory=/home/vamsee/.hermes/hermes-agent
Environment="HOME=/home/vamsee"
Environment="USER=vamsee"
Environment="LOGNAME=vamsee"
Environment="PATH=/home/vamsee/.hermes/hermes-agent/.venv/bin:/home/vamsee/.hermes/hermes-agent/node_modules/.bin:/usr/bin:/home/vamsee/.local/bin:/home/vamsee/.npm-global/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
Environment="VIRTUAL_ENV=/home/vamsee/.hermes/hermes-agent/.venv"
Environment="HERMES_HOME=/home/vamsee/.hermes"
Restart=on-failure
RestartSec=30
KillMode=mixed
KillSignal=SIGTERM
TimeoutStopSec=60
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

Notable gaps in the base unit, addressed by the drop-in:

1. **No `EnvironmentFile=`** — the gateway loads `${HERMES_HOME}/.env` via python-dotenv at process start, not via systemd. This means env-only edits don't propagate without a stop+start cycle, and the env-file's existence is not a systemd unit-start precondition.
2. **`TimeoutStopSec=60`** — the gateway's `agent.restart_drain_timeout=180` default plus a 30s grace period requires `TimeoutStopSec ≥ 210`. systemd will SIGKILL the gateway mid-drain at 60s, possibly losing in-flight Telegram messages.

## Drop-in override — minimal hardened version

Path: `/etc/systemd/system/hermes-gateway.service.d/override.conf`

Created via: `sudo systemctl edit hermes-gateway`

```ini
[Service]
EnvironmentFile=/home/vamsee/.hermes/.env
TimeoutStopSec=210
```

Three rules:

1. **No leading dash** on `EnvironmentFile=`. The dashed form (`EnvironmentFile=-/path`) silently ignores a missing file. We want fail-closed: if the env file disappeared, the gateway should fail to start, not silently start with no token.
2. **No quoting** of the path. systemd treats the rest of the line as the value verbatim.
3. **One file per directive.** If multiple env files are needed, repeat the directive: `EnvironmentFile=/path/a` on one line, `EnvironmentFile=/path/b` on the next.

After saving:

```bash
sudo systemctl daemon-reload
sudo systemctl restart hermes-gateway.service
```

## Drop-in override — fuller version (logging + journald rate-limit relaxation)

If the Hermes gateway is logging heavily (cron mode, multi-platform routing) and systemd journald is dropping lines, append:

```ini
[Service]
EnvironmentFile=/home/vamsee/.hermes/.env
TimeoutStopSec=210
# Increase the unit's per-second log rate (journald default = 1000 messages/30s)
LogRateLimitIntervalSec=0
LogRateLimitBurst=0
```

`LogRateLimitIntervalSec=0` disables the per-unit rate limit. Use sparingly — a misbehaving Hermes plugin can fill `/var/log/journal/` quickly.

## Drop-in override — webhook-mode variation

If using Telegram webhook mode (not the default polling), the gateway needs network ingress, which usually means a TLS reverse proxy. systemd-side additions:

```ini
[Service]
EnvironmentFile=/home/vamsee/.hermes/.env
TimeoutStopSec=210
# Wait for the reverse proxy unit (nginx/caddy) to be up before starting
After=nginx.service
Wants=nginx.service
```

Also requires `TELEGRAM_WEBHOOK_SECRET` in `${HERMES_HOME}/.env` (GHSA-3vpc-7q5r-276h: the secret is required when `TELEGRAM_WEBHOOK_URL` is set; the Hermes env-var doc enforces this).

## Verification commands (post drop-in install)

```bash
# Drop-in file exists with no leading dash.
grep -E "^EnvironmentFile=/home/.+/.hermes/.env$" \
    /etc/systemd/system/hermes-gateway.service.d/override.conf
# expect: one matching line

# systemd merged the override.
systemctl cat hermes-gateway
# expect: the base unit, then the override section at the bottom

# systemd actually loaded the env file at unit start.
systemctl show hermes-gateway -p EnvironmentFiles
# expect: EnvironmentFiles=/home/<user>/.hermes/.env (ro)

# Stale-unit warning is gone after restart.
journalctl -u hermes-gateway --since "5 minutes ago" --no-pager | \
    grep -c "Stale systemd unit"
# expect: 0
```

## What to do if `hermes update` regenerates the base unit

The drop-in survives by design — verify:

```bash
ls -la /etc/systemd/system/hermes-gateway.service.d/
cat /etc/systemd/system/hermes-gateway.service.d/override.conf
sudo systemctl daemon-reload
sudo systemctl restart hermes-gateway
systemctl show hermes-gateway -p EnvironmentFiles
```

If the drop-in was somehow lost (e.g., `/etc/systemd/system/hermes-gateway.service.d/` was deleted by hand), re-run `sudo systemctl edit hermes-gateway` and re-paste the override content.

## What to do if you really must edit the base unit

Don't. But if you absolutely must (e.g., changing `User=` or `ExecStart=`), accept that `hermes update` will revert it, and:

1. Make the edit in a Git-tracked copy at `/etc/systemd/system/hermes-gateway.service.local-edit`
2. Document the diff in `docs/runbooks/telegram-hermes-mobile.md` under "Post-update reapplication"
3. After every `hermes update`, diff the regenerated unit against your local-edit copy and reapply with `sudo cp` + `sudo systemctl daemon-reload` + `sudo systemctl restart hermes-gateway`

This is the path memory says recurred 3× in the v0.4.0 era. Drop-in override is preferable in every case where the change is `Environment*=` or `Timeout*=`.
